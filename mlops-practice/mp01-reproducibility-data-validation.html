MLOps in Practice 1:
Reproducibility & Data Validation

Before any model trains, an MLOps engineer answers two questions: can I rebuild this exactly? and is this data even fit to train on? Most production ML incidents trace back to one of them — a dataset that silently changed upstream, a dependency that floated to a new major version, a "great" offline metric that came from leakage. This chapter is the daily toolkit: run manifests, seeding, dataset fingerprints, requirements hygiene, data-quality gates, data contracts, and the leakage/skew checks interviewers love to probe.

1.1 — What "Reproducible" Actually Requires

"I can't reproduce last month's model" is one of the most expensive sentences in ML. A trained model is a function of five things, and reproducing it means pinning all five: the code (a git commit, not "main"), the data (an immutable snapshot or fingerprint, not "the table"), the config (every hyperparameter, including the defaults you never typed), the environment (Python and every library version, including transitive dependencies), and the randomness (seeds — see 1.2). Miss one and "same code" still gives a different model. The habit that makes this practical is a run manifest: one small, canonical JSON document listing all five, hashed into a run id you store next to the model.

A run manifest: change ANY pinned input and the run id changes
import hashlib import json def run_id(code_version, data_hash, config, seed, env): manifest = {'code': code_version, 'data': data_hash, 'config': config, 'seed': seed, 'env': env} blob = json.dumps(manifest, sort_keys=True).encode() return hashlib.sha256(blob).hexdigest()[:12] base = dict( code_version='a1b2c3d', # git commit SHA data_hash='d4e5f6a7', # fingerprint of the training data (see 1.3) config={'lr': 0.05, 'max_depth': 6}, seed=42, env={'python': '3.11', 'numpy': '1.26.4', 'scikit-learn': '1.4.2'}, ) print('baseline :', run_id(**base)) print('same inputs :', run_id(**base) == run_id(**base)) print('seed 42 -> 43 :', run_id(**{**base, 'seed': 43}) == run_id(**base)) print('numpy upgraded :', run_id(**{**base, 'env': {**base['env'], 'numpy': '2.0.0'}}) == run_id(**base)) print('new data :', run_id(**{**base, 'data_hash': '00ff00ff'}) == run_id(**base))
🧠
Why hash a canonical manifest? sort_keys=True makes the JSON byte-identical no matter how the dict was built, so the same five inputs always give the same run id, and any drift — a bumped library, a re-exported dataset — shows up as a different id. That is the whole trick behind experiment trackers, build caches and model registries.
1.2 — Seeding Correctly

Everyone knows to "set the seed". Fewer people know why it still fails. The classic mistake is one shared random stream consumed by several stages (split, augmentation, weight init): change the order or the number of draws in one stage and every stage after it silently changes too. Prefer local generators (np.random.default_rng(seed), random.Random(seed)) over global state, and derive an independent child stream per stage from one root seed with SeedSequence.spawn — then reordering stages cannot change the train/test split.

Local generators beat global seeds — and independent streams beat one shared stream
import random import numpy as np # 1) A local generator with the same seed always gives the same stream a = np.random.default_rng(42) b = np.random.default_rng(42) print('same seed, same draws :', a.integers(0, 10**6, 5).tolist() == b.integers(0, 10**6, 5).tolist()) print('stdlib Random(7) reproducible:', random.Random(7).random() == random.Random(7).random()) # 2) The fragile part: ONE shared generator consumed by several stages def shared_stream(order, seed=7): rng = np.random.default_rng(seed) out = {} for stage in order: out[stage] = rng.permutation(10).tolist() return out split_first = shared_stream(['split', 'augment'])['split'] split_second = shared_stream(['augment', 'split'])['split'] print('shared rng, stages reordered -> same split? ', split_first == split_second) # 3) The fix: give each stage its OWN child stream from one root seed def independent_streams(order, seed=7): children = np.random.SeedSequence(seed).spawn(2) rngs = {'split': np.random.default_rng(children[0]), 'augment': np.random.default_rng(children[1])} return {stage: rngs[stage].permutation(10).tolist() for stage in order} print('child streams, stages reordered -> same split?', independent_streams(['split', 'augment'])['split'] == independent_streams(['augment', 'split'])['split'])
⚠️
Never assert on raw random draws — assert on properties ("same seed gives identical output", "split is disjoint"). Draw values differ across NumPy versions, so a test that hard-codes them breaks on upgrade. Also remember what a seed does not cover: the PYTHONHASHSEED that randomizes string hashing (and set/dict-of-string ordering in old code paths), multi-threaded reductions, and GPU kernels that are nondeterministic unless you opt into deterministic algorithms in your framework.
1.3 — Dataset Fingerprinting

If the data can change without anyone noticing, you cannot reproduce anything. A fingerprint is a hash of a dataset's canonical form, stored in the run manifest. The word that matters is canonical: two files with identical content but different row order, column order, float formatting or NaN spelling must hash the same, or you will drown in false alarms and start ignoring the alarm. So: sort columns, (optionally) sort rows, serialize with a fixed float format and an explicit null token, then sha256 the bytes.

A dataset fingerprint: canonical CSV bytes -> sha256
import hashlib import pandas as pd def fingerprint(df, ignore_row_order=True, float_digits=10): cols = sorted(df.columns) # column order must not matter canon = df[cols] if ignore_row_order: canon = canon.sort_values(cols, kind='mergesort') csv = canon.to_csv(index=False, lineterminator='\n', float_format=f'%.{float_digits}g', na_rep='<NA>') return hashlib.sha256(csv.encode('utf-8')).hexdigest() a = pd.DataFrame({'id': [3, 1, 2], 'amount': [19.99, 5.0, 12.5], 'status': ['paid', 'paid', 'refunded']}) shuffled = a.iloc[[2, 0, 1]].reset_index(drop=True) edited = a.copy(); edited.loc[0, 'amount'] = 19.98 noisy = a.copy(); noisy['amount'] = noisy['amount'] + 1e-13 # float noise from a different machine print('shuffled rows, order-insensitive :', fingerprint(a) == fingerprint(shuffled)) print('shuffled rows, order-sensitive :', fingerprint(a, ignore_row_order=False) == fingerprint(shuffled, ignore_row_order=False)) print('one value edited -> detected :', fingerprint(a) != fingerprint(edited)) print('1e-13 float noise absorbed :', fingerprint(a) == fingerprint(noisy)) print('raw floats: 0.1+0.2 == 0.3 :', 0.1 + 0.2 == 0.3) print('rounded to 10 digits :', f'{0.1 + 0.2:.10g}' == f'{0.3:.10g}') print('digest length (hex chars) :', len(fingerprint(a)))
⚠️
Floats and dtypes are the usual culprits. 0.1 + 0.2 != 0.3, and the same number can come back as 1.0000000000000002 from a different machine or aggregation order — so fix the digits you hash. An int column that becomes float because one value is missing changes the CSV text (3 vs 3.0); decide whether that should count as a change. For very large data you hash file chunks or use the storage layer's checksums (that is what DVC and object stores do) instead of re-serializing everything.
1.4 — Capturing and Auditing the Environment

An import numpy that works today and breaks next month usually means a dependency floated. Every line of a requirements.txt is one of three kinds: pinned (==: exactly this version), ranged (>=, ~=: any version in a window) or unpinned (a bare name: whatever is newest today). Reproducible builds want everything pinned — including transitive dependencies you never wrote down, which is why teams keep a human-edited requirements.in and compile it into a fully pinned lock file. Parsing these lines correctly (comments, -r includes, extras like pydantic[email], environment markers after ;) is a classic small CI check.

Parsing requirements.txt and classifying pinned / ranged / unpinned
import re REQ = re.compile(r'^(?P<name>[A-Za-z0-9_.\-]+)(?:\[[^\]]*\])?\s*(?P<op>==|>=|<=|~=|!=|>|<)?\s*(?P<ver>[A-Za-z0-9_.*+!\-]+)?') def parse_requirement(line): line = line.split('#')[0].split(';')[0].strip() # drop comments and environment markers if not line or line.startswith('-'): # blank lines and options like -r base.txt return None m = REQ.match(line) name = m['name'].lower().replace('_', '-') return name, m['op'], m['ver'] def classify(op): if op == '==': return 'pinned' if op is None: return 'unpinned' return 'ranged' text = """ # model service numpy==1.26.4 pandas>=2.0 scikit-learn requests==2.31.0 ; python_version >= "3.9" pydantic[email]==2.6.1 -r base.txt """ for raw in text.splitlines(): parsed = parse_requirement(raw) if parsed: name, op, ver = parsed print(f'{name:14s} {classify(op):9s} op={op} ver={ver}')
Locking a fully pinned environment (pip-tools / uv) — reference only
# requirements.in -> the few packages YOU depend on (ranges are fine here) # pandas>=2.0 # scikit-learn~=1.4 # # compile to a lock file with every transitive dependency pinned (+ hashes) pip-compile --generate-hashes requirements.in -o requirements.txt # or, with uv: uv pip compile requirements.in -o requirements.txt # install EXACTLY what the lock file says, and fail if anything is missing/extra pip install --require-hashes -r requirements.txt # what is actually installed right now (audit, or capture into the run manifest) pip freeze
⚠️
Reference-only. pip, uv and Docker need a real operating system, which this in-browser Python does not have — run these on your own machine. The parsing logic above is the part you can practice here.
1.5 — Data-Quality Checks as a Pass/Fail Report

Data checks are unit tests for data. The useful families are: schema (columns and dtypes exist), range (age between 18 and 100), domain (country is one of a known set), completeness (null rate under a threshold), uniqueness (keys are unique), referential (every id exists in the reference table), volume (row count within an expected band) and freshness (newest record is recent enough). Return a structured report — check name, pass/fail, detail — not a bare assert: a report can be logged, diffed between runs, and turned into an alert that says which check failed and by how much.

Data-quality checks as a structured pass/fail report
import pandas as pd loans = pd.DataFrame({ 'loan_id': [101, 102, 103, 104, 104, 106, 107, 108], 'age': [34, 29, 41, 17, 52, 38, 240, 45], 'income': [52000, None, 61000, 48000, 75000, None, 58000, None], 'country': ['IN', 'IN', 'US', 'US', 'DE', 'IN', 'XX', 'US'], 'default': [0, 1, 0, 0, 1, 0, 0, 1], }) def check_quality(df): report = {} report['loan_id_unique'] = (not df['loan_id'].duplicated().any(), f"{int(df['loan_id'].duplicated().sum())} duplicate key(s)") bad_age = ~df['age'].between(18, 100) report['age_in_18_100'] = (not bad_age.any(), f'{int(bad_age.sum())} row(s) out of range') null_rate = float(df['income'].isna().mean()) report['income_null_rate<=0.20'] = (null_rate <= 0.20, f'null rate {null_rate:.3f}') bad_country = ~df['country'].isin(['IN', 'US', 'DE']) report['country_allowed'] = (not bad_country.any(), f'{int(bad_country.sum())} unknown value(s)') report['label_is_binary'] = (set(df['default'].unique()) <= {0, 1}, 'labels ok') return report report = check_quality(loans) for name, (ok, detail) in report.items(): print(f"{'PASS' if ok else 'FAIL'} {name:24s} {detail}") failed = [name for name, (ok, _) in report.items() if not ok] print('gate:', 'BLOCK the training run' if failed else 'proceed', '->', failed)
⭐
Where the gate goes and what it does. Run checks before training, as the first pipeline step, and make failure loud: block the run (or quarantine the bad partition) and notify the dataset owner. Derive thresholds from history — "null rate has never exceeded 2%" — rather than guessing; a check nobody trusts gets disabled the first time it fires on a Friday.
1.6 — Row-Level Validation and Data Contracts with pydantic

pandas checks are column-wise and vectorized; pydantic v2 validates one record at a time against a typed model, which is exactly what you want at a boundary — a request payload, a message from a queue, a sample of a new feed. The model doubles as a data contract written in code: field types, ranges (Field(ge=..., le=...)), allowed values (Literal) and, with extra='forbid', a rule that unexpected columns are violations rather than silently ignored. Each error carries a location and a machine-readable type, so you can count failures by field.

Row-level validation with a pydantic v2 model — the data contract in code
from typing import Literal, Optional from pydantic import BaseModel, ConfigDict, Field, ValidationError class LoanRow(BaseModel): model_config = ConfigDict(extra='forbid') # unexpected columns are a contract violation loan_id: int age: int = Field(ge=18, le=100) income: Optional[float] = Field(default=None, ge=0) country: Literal['IN', 'US', 'DE'] default: Literal[0, 1] rows = [ {'loan_id': 1, 'age': 34, 'income': 52000.0, 'country': 'IN', 'default': 0}, {'loan_id': 2, 'age': 17, 'income': 48000.0, 'country': 'US', 'default': 0}, {'loan_id': 3, 'age': 41, 'income': -5.0, 'country': 'XX', 'default': 1}, {'loan_id': 'abc', 'age': 29, 'country': 'DE', 'default': 0, 'risk_band': 'B'}, {'age': 52, 'country': 'IN', 'default': 1}, ] problems = {} for i, row in enumerate(rows): try: LoanRow(**row) except ValidationError as e: problems[i] = sorted((err['loc'][0], err['type']) for err in e.errors()) print('valid rows :', len(rows) - len(problems), 'of', len(rows)) for i, errs in problems.items(): print(f'row {i}:', errs)
🧠
A data contract is more than a schema. It is an agreement between the team that produces a dataset and the teams that consume it: schema, semantics (what does income mean — gross or net, which currency?), quality guarantees, freshness SLA, an owner to page, and a version. Removing, renaming or re-typing a column is a breaking change (major version bump, announced in advance); adding an optional column is not. The value is catching the change at the producer's CI instead of in your model's metrics three weeks later.
⚠️
Use the right tool for the volume. Validating millions of rows one pydantic object at a time is slow. Use pydantic for boundaries and samples, and vectorized pandas (or a dedicated library, 1.8) for bulk checks.
1.7 — Leakage and Train/Serve Skew

Leakage means the model saw information at training time that will not exist at prediction time — so the offline metric is fiction. It comes in three everyday forms. (a) Split leakage: a random split of time-ordered data lets the training set contain the future of your test rows; a random split of per-customer data puts the same customer on both sides. The fixes are a time split (optionally with an embargo gap when labels take days to resolve) and a group split (a customer lives entirely on one side).

Random split vs time split vs group split on the same events
import pandas as pd events = pd.DataFrame({ 'customer': ['a', 'a', 'b', 'b', 'c', 'c', 'd', 'd'], 'day': [1, 5, 2, 6, 3, 7, 4, 8], 'churned': [0, 1, 0, 0, 1, 1, 0, 1], }) # A "random" split (fixed indices so the demo is deterministic): rows 1, 4, 6 go to test test_idx = [1, 4, 6] rand_train, rand_test = events.drop(index=test_idx), events.loc[test_idx] print('random split -> train contains days after the earliest test day:', rand_train['day'].max() > rand_test['day'].min()) print('random split -> customers on BOTH sides:', sorted(set(rand_train['customer']) & set(rand_test['customer']))) # Time split: everything before the cutoff trains, everything after tests cutoff = 5 t_train, t_test = events[events['day'] < cutoff], events[events['day'] >= cutoff] print('time split -> train max day < test min day:', t_train['day'].max() < t_test['day'].min()) # Group split: a customer lives entirely on one side test_customers = {'c', 'd'} g_train = events[~events['customer'].isin(test_customers)] g_test = events[events['customer'].isin(test_customers)] print('group split -> customers on BOTH sides:', sorted(set(g_train['customer']) & set(g_test['customer'])))

(b) Target leakage: a feature that is really a consequence of the label — a cancel_reason field that support fills in after the customer churns. The tell is a feature that is suspiciously perfect; a correlation screen catches the crude cases, and the real fix is asking, for every feature, "would I have this value at the moment the prediction is made?"

Target leakage: the feature that is suspiciously perfect
import pandas as pd df = pd.DataFrame({ 'tenure_months': [24, 3, 36, 5, 12, 2, 48, 7], 'support_calls': [1, 6, 0, 4, 2, 5, 1, 3], 'cancel_reason_present': [0, 1, 0, 1, 0, 1, 0, 1], # filled in by support AFTER the customer churns 'churned': [0, 1, 0, 1, 0, 1, 0, 1], }) corr = df.drop(columns='churned').corrwith(df['churned']).abs().round(2).sort_values(ascending=False) for feature, value in corr.items(): flag = ' <-- too good to be true' if value >= 0.95 else '' print(f'{feature:24s} |corr| = {value:.2f}{flag}')

(c) Train/serve skew is the production twin of leakage: the features the model sees live differ from the ones it trained on — a different code path computes them, a unit changes (dollars vs cents), a timezone shifts, a default fills a missing value. Save summary statistics at training time and compare them with what serving actually sends.

Train/serve skew: compare what the model trained on with what it now sees
import pandas as pd train_stats = {'income': (52000.0, 9000.0), 'age': (38.0, 8.5)} # (mean, std) saved at training time serving = pd.DataFrame({'income': [31000, 29500, 33200, 30800], 'age': [37, 41, 36, 39]}) for feature, (mean, std) in train_stats.items(): shift = abs(serving[feature].mean() - mean) / std # shift in training standard deviations print(f'{feature:7s} shift = {shift:.2f} std', '-> SKEW' if shift > 1.0 else '-> ok')
⚠️
The interview tell. "Offline AUC 0.99, production is a coin flip" almost always means leakage or skew, not a bad algorithm. State the checklist out loud: split strategy, features unavailable at prediction time, labels that resolve late, and a feature-level comparison of training vs serving distributions.
1.8 — Tools You Will Meet: pandera, Great Expectations, DVC

Everything above is what these tools do for you at scale. pandera lets you declare a DataFrame schema (dtypes, checks, uniqueness) and validate it — with lazy=True it reports all failures instead of stopping at the first. Great Expectations models checks as reusable "expectations" grouped into suites that run in a pipeline and publish human-readable reports (its API has changed considerably between major versions, so follow the docs for the version you install). DVC versions large data next to your git history: git stores a small pointer file, the data lives in remote storage.

pandera: the 1.5 checks declared as a schema — reference only
import pandera as pa schema = pa.DataFrameSchema( { "loan_id": pa.Column(int), "age": pa.Column(int, pa.Check.in_range(18, 100)), "income": pa.Column(float, pa.Check.ge(0), nullable=True), "country": pa.Column(str, pa.Check.isin(["IN", "US", "DE"])), }, unique=["loan_id"], # duplicate keys fail strict=True, # unexpected columns fail ) try: schema.validate(df, lazy=True) # lazy=True collects ALL failures except pa.errors.SchemaErrors as err: print(err.failure_cases) # a DataFrame: column, check, failing value, row index
DVC: version a dataset alongside git — reference only
dvc init dvc add data/train.parquet # writes data/train.parquet.dvc (a pointer with a checksum) git add data/train.parquet.dvc data/.gitignore git commit -m "Track training data v1" dvc push # data -> remote storage (S3/GCS/...), pointer stays in git # months later: get EXACTLY the data that commit trained on git checkout <old-commit> dvc checkout
⚠️
Reference-only. pandera, Great Expectations and DVC are not available in this in-browser Python (DVC also needs git and remote storage). The snippets show the shape of the tools; the exercises below build the same ideas from scratch so you understand what they do.
Chapter Summary
  • Reproducible = five pins: code, data, config, environment, randomness — captured in a hashed run manifest.
  • Seed with local generators and per-stage child streams, and assert on properties, never on raw draws.
  • Fingerprint data in canonical form (sorted, fixed float format, explicit nulls) so only real changes change the hash.
  • Audit requirements: pinned vs ranged vs unpinned; lock transitive dependencies.
  • Data checks are unit tests for data — a structured report, run first, blocking on failure, thresholds from history.
  • Contracts = schema + semantics + SLA + owner + version; pydantic validates records at boundaries, pandas validates in bulk.
  • Leakage and skew explain "great offline, bad in production": time/group splits, features unavailable at prediction time, training-vs-serving stats.

🏗️ Capstone: DatasetGate — a CI Step for Data

Every serious ML pipeline has a step that answers "is this data fit to train on?" before any compute is spent. Build it as a reusable class driven by a data contract: it takes a DataFrame, returns PASS or FAIL, and — crucially — tells you why, with stable machine-readable reason codes a CI job or alert can act on.

data contracts quality gate reason codes

📋 What to Build

  • A DatasetGate class configured by the CONTRACT dict in the starter code (required columns, unique key, ranges, allowed values, max null rates, min rows)
  • check(df) returns (status, reasons): status is 'PASS' when there are no reasons, else 'FAIL'; reasons is a SORTED list of codes like missing_column:income, duplicate_keys:customer_id, out_of_range:age, not_allowed:country, null_rate:income, too_few_rows
  • A column that is missing is reported once as missing_column and skipped by every other check; range checks ignore null values (nulls are the null-rate check's job)
  • Run it on the three datasets provided and print one line each: name: STATUS | reason; reason (reasons joined by '; ')

10 questions MLOps and ML-platform interviewers ask about reproducibility, data quality, leakage and skew. Click a question to reveal what a strong answer sounds like.

What makes an ML experiment reproducible, and what do people usually forget?▶
Five things have to be pinned: the code (a commit SHA, not a branch), the data (an immutable snapshot or a content fingerprint), the config (all hyperparameters including defaults), the environment (Python plus every library, including transitive dependencies) and the randomness (seeds). I record them together in a hashed run manifest stored next to the model. What people forget most often is the data — "the table" changed under them — and transitive dependencies that floated to a new version. A strong answer also admits the limits: GPU kernels and multi-threaded reductions can be nondeterministic unless you explicitly opt into deterministic algorithms, so I define reproducible as "within a stated tolerance" when bit-exactness is not achievable.
Why is calling random.seed(42) or np.random.seed(42) at the top of a script not enough?▶
Global seeding is fragile because all code shares one stream. If one stage draws one extra number, or stages run in a different order, everything downstream changes silently. It also does nothing for libraries with their own generators, for PYTHONHASHSEED, or for nondeterministic GPU/threaded operations. Better practice is local generators (np.random.default_rng(seed)), one independent child stream per stage derived from a root seed with SeedSequence.spawn, seeds passed explicitly into functions, and tests that assert properties (same seed gives the same split) rather than hard-coded random values.
How would you version a 200 GB training dataset?▶
Not in git. I would store the data in immutable, content-addressed storage (object storage with versioned partitions, or a table format with time travel such as Delta or Iceberg) and version a small pointer with the code: a manifest listing the files and their checksums, or a DVC .dvc file. Training records the dataset fingerprint in the run manifest, so any model can be traced to the exact data. Key properties are immutability (new data is a new version, never an in-place edit), cheap access to old versions, and a fingerprint computed on a canonical form so cosmetic changes such as row order do not create false differences.
Give three examples of data leakage and how you would detect each.▶
Split leakage: a random split of time-ordered data puts future rows in training, or the same customer appears on both sides — detect by checking that max(train time) is before min(test time) and that group ids do not overlap. Target leakage: a feature that is a consequence of the label (a cancellation reason filled in after churn) — detect with a suspiciously high single-feature score or correlation, and by asking of every feature whether it exists at prediction time. Preprocessing leakage: fitting a scaler, imputer or encoder on the full dataset before splitting — detect by reviewing the pipeline order and fitting every transform on training data only (a scikit-learn Pipeline inside cross-validation does this correctly).
Why is a random split wrong for time-dependent data, and what do you do instead?▶
Because production predicts the future from the past. A random split lets the model train on rows after the test rows, so the offline metric measures interpolation, not forecasting, and is optimistic. Use a time-based split (train before a cutoff, test after), or walk-forward validation with several cutoffs for a more stable estimate. If labels take days to resolve — a fraud chargeback, a 30-day churn window — add an embargo gap so training rows whose labels overlap the test period are dropped. For per-entity data, also group the split so one customer never appears on both sides.
What is train/serve skew, what causes it, and how do you catch it?▶
It is when the features the model sees at serving time differ from those it trained on, so accuracy drops even though the model did not change. Typical causes: feature logic implemented twice (a SQL job for training, application code for serving), unit or timezone differences, different handling of missing values, and stale or late features. Prevention is one shared feature definition (a feature store or a shared library). Detection is logging the served features and comparing their distributions with the training statistics — mean and standard deviation shifts, null rates, category frequencies — and alerting when they diverge.
What is a data contract, and who owns it?▶
A data contract is an explicit agreement between the team producing a dataset and the teams consuming it: the schema, the semantics (units, currency, time zone, what null means), quality guarantees, a freshness SLA, a named owner and a version. The producer owns it and enforces it in their own CI, so a breaking change (removing, renaming or re-typing a column) fails there, is versioned as a major change and is announced, instead of silently breaking downstream models. Consumers can then validate incoming data against the same contract, for example with a pydantic model or a pandera schema.
What checks would you put in front of a training pipeline, and what happens when one fails?▶
Schema (columns and dtypes), volume (row count within an expected band), freshness (latest timestamp is recent), completeness (null rates), domain and range checks, key uniqueness, referential integrity, and distribution checks against a reference window. Thresholds come from historical data rather than guesses. It runs as the first pipeline step and returns a structured report with reason codes. On failure the run is blocked or the bad partition is quarantined, the dataset owner is alerted with the specific failing check, and the previous good model stays in production. Softer checks can warn instead of block, as long as that policy is explicit.
Offline AUC is 0.99 but the model does badly in production. How do you debug it?▶
Suspect leakage or skew before the algorithm. First the split: was it random on time-ordered or per-customer data? Then features: is any of them unavailable, or different, at prediction time — check for suspiciously perfect features. Then labels: do they resolve late, so the training labels used information from the future? Then skew: compare the training feature distributions with the logged serving features. Also check for sampling differences between the evaluation set and live traffic. The fastest confirmation is re-evaluating on a strictly time-later holdout that mimics production; if the score collapses, the original number was leakage.
When would you use pydantic, pandera or Great Expectations, versus hand-written pandas checks?▶
Pydantic validates one record at a time against a typed model, which suits API and message boundaries and small samples but is slow for millions of rows. pandera declares a DataFrame schema (dtypes, checks, uniqueness) and validates whole frames vectorized, which fits inside Python pipelines and tests. Great Expectations adds reusable expectation suites, checkpoints and human-readable reports, which suits shared platforms where non-authors need to see results. Hand-written pandas checks are fine for a handful of rules and for learning, but they tend to grow inconsistent, so past a few checks I would move to a declared schema or expectation suite.
