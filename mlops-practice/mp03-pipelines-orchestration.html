MLOps Practice 3:
Pipelines & Orchestration

Every ML platform job posting says "Airflow", "Kubeflow" or "Prefect", and every interview for one probes the same handful of ideas: dependency graphs, retries, idempotency, caching, backfills. Instead of memorising tool syntax, you will build a working mini-orchestrator in about seventy lines of plain Python, then see exactly how Airflow, Prefect, Dagster and Kubeflow spell the same ideas. The tools change every few years; these ideas do not.

🕐 ~70 min read 💻 5 exercises 🏗️ Capstone Project 🧪 5-question quiz 💼 10 Interview Prep Q&A
3.1 — Why Pipelines, Not One Giant Script

Every ML system starts as one notebook or one train.py. Then it gets put on a schedule, and it starts failing at 3 a.m. — usually at the last step, after two hours of work. A pipeline is the same work split into named steps with declared inputs and outputs, so a supervisor (the orchestrator) can do five things a script cannot: run steps in dependency order, run independent steps in parallel, retry only the step that failed, skip steps whose inputs have not changed, and tell you exactly which step is red. Everything in this chapter — and everything Airflow, Prefect, Dagster and Kubeflow do — is a variation on those five.

A giant script vs. named, recorded steps
def ingest(): return 1200 def validate(n): if n < 1000: raise ValueError("too few rows") return n def featurize(n): return n * 12 def train(x): raise RuntimeError("OOM while training") # step 4 blows up # One giant script: a late crash throws everything away print("== giant script ==") try: n = validate(ingest()); x = featurize(n); model = train(x) except Exception as e: print(f"crashed: {e} -> nothing saved, rerun ALL of it") # The same work as named steps whose results are recorded print("== recorded steps ==") state = {} steps = [ ("ingest", lambda: ingest()), ("validate", lambda: validate(state["ingest"])), ("featurize", lambda: featurize(state["validate"])), ("train", lambda: train(state["featurize"])), ] failed = None for name, fn in steps: try: state[name] = fn() print(f"{name:<10} ok -> {state[name]}") except Exception as e: failed = name print(f"{name:<10} FAIL -> {e}") break print("kept:", sorted(state)) print("resume from:", failed)
⭐
The orchestrator supervises; it should not do the heavy lifting.A good task launches the work (a Spark job, a Kubernetes pod, a warehouse query) and reports success or failure. If your Airflow worker is itself holding a 40 GB DataFrame, you have rebuilt the giant script inside a scheduler — with worse debugging.
3.2 — A DAG Is Just Data: Task → Dependencies

The dependency structure of a pipeline is a DAG — a directed acyclic graph. Tasks are nodes; an edge means "this must finish before that can start". In Python the most honest representation is a dict mapping each task to the tasks it depends on (Airflow writes the same edges as a >> b). A task with no dependencies is a root, a task nothing depends on is a leaf, and everything that has to wait for a task is downstream of it. The example below is the pipeline the rest of the chapter reuses: two ingests feed validation, which fans out to feature building and data docs; two models train in parallel; and a quality gate decides whether the winner may be registered.

The ML pipeline as a dict, plus reverse edges and downstream lookup
ml_dag = { "ingest_events": [], "ingest_users": [], "validate": ["ingest_events", "ingest_users"], "data_docs": ["validate"], "featurize": ["validate"], "train_lr": ["featurize"], "train_rf": ["featurize"], "evaluate": ["train_lr", "train_rf"], "gate": ["evaluate"], "register": ["gate"], } def dependents(dag): out = {t: [] for t in dag} for task, deps in dag.items(): for d in deps: out[d].append(task) return {t: sorted(v) for t, v in out.items()} def all_downstream(dag, task): down, stack, seen = dependents(dag), [task], set() while stack: for child in down[stack.pop()]: if child not in seen: seen.add(child) stack.append(child) return sorted(seen) down = dependents(ml_dag) print("roots :", [t for t, deps in ml_dag.items() if not deps]) print("leaves:", [t for t, kids in down.items() if not kids]) print("edges :", sum(len(deps) for deps in ml_dag.values())) print("validate feeds:", down["validate"]) print("if train_rf breaks, blocked:", all_downstream(ml_dag, "train_rf"))
💡
The DAG is a description; running it is a separate step.Because the graph is plain data, the orchestrator can validate it, draw it, and compute what to re-run before executing a single task. That separation is the whole trick.
⚠️
Why acyclic?If a waits for b and b waits for a, neither can ever start. A cycle is a deadlock written down, so orchestrators reject cyclic graphs at parse time.
3.3 — Topological Sort (Kahn's Algorithm) and Readable Cycle Errors

To run a DAG you need an order in which every task comes after everything it depends on: a topological order. Kahn's algorithm gets it in three moves: count each task's unmet dependencies (its indegree); start with every task at zero; repeatedly take one, emit it, and decrement its children — any child that reaches zero joins the ready set. Two production details matter. First, tie-breaking: with several tasks ready, pick deterministically (here alphabetically, via a heap), or your logs and tests change from run to run. Second, cycle detection comes free: if the loop ends with tasks never emitted, they are stuck in a cycle or waiting behind one.

Kahn's algorithm with a cycle error a human can act on
import heapq def topo_order(dag): indegree = {t: len(deps) for t, deps in dag.items()} children = {t: [] for t in dag} for t, deps in dag.items(): for d in deps: children[d].append(t) ready = [t for t, n in indegree.items() if n == 0] heapq.heapify(ready) # alphabetical tie-break -> same order every run order = [] while ready: t = heapq.heappop(ready) order.append(t) for c in children[t]: indegree[c] -= 1 if indegree[c] == 0: heapq.heappush(ready, c) if len(order) != len(dag): blocked = sorted(set(dag) - set(order)) raise ValueError(f"cycle detected; blocked tasks: {blocked}") return order def find_cycle(dag): color, stack = {t: 0 for t in dag}, [] # 0 = unseen, 1 = on the current path, 2 = done def visit(t): color[t] = 1 stack.append(t) for d in sorted(dag[t]): if color[d] == 1: return stack[stack.index(d):] + [d] if color[d] == 0: found = visit(d) if found: return found color[t] = 2 stack.pop() for t in sorted(dag): if color[t] == 0: found = visit(t) if found: return found ml_dag = { "ingest_events": [], "ingest_users": [], "validate": ["ingest_events", "ingest_users"], "data_docs": ["validate"], "featurize": ["validate"], "train_lr": ["featurize"], "train_rf": ["featurize"], "evaluate": ["train_lr", "train_rf"], "gate": ["evaluate"], "register": ["gate"], } print(topo_order(ml_dag)) broken = {"a": [], "b": ["a", "d"], "c": ["b"], "d": ["c"], "e": ["c"]} try: topo_order(broken) except ValueError as err: print(err) print("one cycle ('depends on'):", " -> ".join(find_cycle(broken)))
⚠️
The 'blocked' list is bigger than the cycle.Task e is not part of the cycle — it is merely downstream of it, so it is blocked too. Reporting all four as 'the cycle' sends someone hunting in the wrong place, which is why find_cycle walks the graph again to print an actual loop.
3.4 — Parallel Levels and the Critical Path

A task's level is the length of the longest chain of dependencies leading to it (roots are level 0). Everything in one level can run at the same time, given enough workers. But wall-clock time is not the sum of task durations and not the number of levels either: it is the duration of the slowest chain, the critical path. That is why "make it faster" has a precise answer. Speeding up train_lr or data_docs buys nothing here, because neither sits on the critical path; shaving minutes off featurize or train_rf shortens every single run.

Levels, sequential time vs. parallel time, and the critical path
ml_dag = { "ingest_events": [], "ingest_users": [], "validate": ["ingest_events", "ingest_users"], "data_docs": ["validate"], "featurize": ["validate"], "train_lr": ["featurize"], "train_rf": ["featurize"], "evaluate": ["train_lr", "train_rf"], "gate": ["evaluate"], "register": ["gate"], } minutes = {"ingest_events": 6, "ingest_users": 4, "validate": 3, "data_docs": 2, "featurize": 9, "train_lr": 5, "train_rf": 14, "evaluate": 3, "gate": 1, "register": 1} def levels(dag): level = {} def lv(t): if t not in level: level[t] = 0 if not dag[t] else 1 + max(lv(d) for d in dag[t]) return level[t] for t in dag: lv(t) grouped = {} for t, l in level.items(): grouped.setdefault(l, []).append(t) return [sorted(grouped[l]) for l in sorted(grouped)] def critical_path(dag, minutes): finish, via = {}, {} def fin(t): if t not in finish: best = max(dag[t], key=fin, default=None) via[t] = best finish[t] = minutes[t] + (fin(best) if best else 0) return finish[t] end = max(dag, key=fin) path = [] while end: path.append(end) end = via[end] return finish[path[0]], path[::-1] for i, group in enumerate(levels(ml_dag)): print(f"level {i}: {group}") total, path = critical_path(ml_dag, minutes) print(f"one at a time : {sum(minutes.values())} min") print(f"with parallelism: {total} min") print("critical path :", " -> ".join(path))
⭐
The interview question hiding here:'Our nightly pipeline takes 37 minutes. Where do you look first?' A strong answer is 'find the critical path, then optimise or split the slowest task on it' — not 'add more workers', which does nothing once every level already has enough.
3.5 — Failure Propagation: Skip Downstream, Keep Independent Branches

When a task fails after its retries, what should happen to the rest of the run? The standard rule: a task runs only if every upstream task succeeded. If any upstream task failed or was itself skipped, the task is marked skipped (Airflow calls it upstream_failed) and never starts. Branches that do not depend on the failed task carry on. You end up with the most possible progress and a single red root cause instead of ten confusing errors. Orchestrators let you override this per task — Airflow's trigger rules (all_done for cleanup, one_failed for alerting) — but the default is the one to reason from.

A run where train_rf runs out of memory
import heapq from collections import Counter ml_dag = { "ingest_events": [], "ingest_users": [], "validate": ["ingest_events", "ingest_users"], "data_docs": ["validate"], "featurize": ["validate"], "train_lr": ["featurize"], "train_rf": ["featurize"], "evaluate": ["train_lr", "train_rf"], "gate": ["evaluate"], "register": ["gate"], } order = ["ingest_events", "ingest_users", "validate", "data_docs", "featurize", "train_lr", "train_rf", "evaluate", "gate", "register"] def run_dag(dag, order, actions): status = {} for t in order: if any(status[d] != "success" for d in dag[t]): status[t] = "skipped" # upstream failed (Airflow: upstream_failed) continue try: actions[t]() status[t] = "success" except Exception as e: status[t] = "failed" print(f" ! {t} raised {type(e).__name__}: {e}") return status def ok(): pass def out_of_memory(): raise MemoryError("OOM on a 16 GB worker") actions = {t: ok for t in ml_dag} actions["train_rf"] = out_of_memory status = run_dag(ml_dag, order, actions) for t in order: print(f"{t:<14}{status[t]}") print(dict(sorted(Counter(status.values()).items())))
🚫
Never run a task on stale or partial upstream output.A green run that registered a model built from yesterday's features is far worse than a red run that registered nothing. Skipping is the safe failure mode; make it the default and opt out deliberately.
3.6 — Retries: Attempt Counting, Backoff, and What NOT to Retry

Many production failures are weather, not bugs: a connection reset, a 503, a spot instance reclaimed mid-task. A retry policy has four parts — a maximum number of attempts, a delay between attempts that grows (exponential backoff: 2 s, 4 s, 8 s…), a cap on that delay, and a rule for which errors are retryable. The last one is the one people forget. A ValueError from a missing column will fail identically on every attempt; retrying it burns time, hides the bug, and delays the alert. The code below injects the failures and records the delays it would sleep instead of sleeping, so it runs instantly and deterministically.

Retries with exponential backoff, and one error that must not be retried
class TransientError(Exception): pass def run_with_retries(fn, max_attempts=3, base_delay=2, cap=30): delays = [] for attempt in range(1, max_attempts + 1): try: return "success", attempt, delays, fn(attempt) except TransientError: if attempt == max_attempts: return "failed", attempt, delays, None delays.append(min(cap, base_delay * 2 ** (attempt - 1))) # a real system sleeps here # any OTHER exception type is a bug, not weather: it propagates immediately def flaky_until_third(attempt): if attempt < 3: raise TransientError("connection reset") return "features.parquet" def always_down(attempt): raise TransientError("warehouse unreachable") def schema_bug(attempt): raise ValueError("column 'age' missing") print(run_with_retries(flaky_until_third)) print(run_with_retries(always_down)) try: run_with_retries(schema_bug) except ValueError as e: print("not retried:", e)
💡
Add jitter in real systems.If 500 tasks all fail at once and all retry after exactly 2 seconds, they hit the recovering service in one synchronised wave (a thundering herd). Randomising each delay slightly spreads the load. It is left out above only so the output is deterministic.
3.7 — Caching: Skip Steps Whose Inputs Have Not Changed

Re-running a fifteen-minute ingest because you tweaked a training hyper-parameter is pure waste. The fix is a cache key: a hash of everything that determines a task's output — its name, its code version, its parameters and the keys of its upstream tasks. Same key means same output, so skip it. Including the upstream keys is what makes a change propagate: alter featurize and its key changes, so the keys of everything after it change too, while ingest and validate are untouched. This is the idea behind make, DVC's dvc repro, Kubeflow step caching, Prefect cache policies and Dagster's notion of a stale asset.

An input-hash cache: change a parameter, watch only the affected tasks re-run
import hashlib, json ml_dag = { "ingest_events": [], "ingest_users": [], "validate": ["ingest_events", "ingest_users"], "data_docs": ["validate"], "featurize": ["validate"], "train_lr": ["featurize"], "train_rf": ["featurize"], "evaluate": ["train_lr", "train_rf"], "gate": ["evaluate"], "register": ["gate"], } order = ["ingest_events", "ingest_users", "validate", "data_docs", "featurize", "train_lr", "train_rf", "evaluate", "gate", "register"] def task_key(name, version, params, upstream_keys): payload = json.dumps([name, version, params, sorted(upstream_keys)], sort_keys=True) return hashlib.sha256(payload.encode()).hexdigest() def run_pipeline(dag, order, versions, params, cache): keys, report = {}, {} for t in order: keys[t] = task_key(t, versions[t], params.get(t, {}), [keys[d] for d in dag[t]]) if keys[t] in cache: report[t] = "cached" else: cache.add(keys[t]) report[t] = "ran" return report versions = {t: "v1" for t in ml_dag} params = {"featurize": {"window": 7}, "train_rf": {"trees": 200}, "gate": {"min_auc": 0.75}} cache = set() def show(label): report = run_pipeline(ml_dag, order, versions, params, cache) ran = [t for t in order if report[t] == "ran"] print(f"{label}: ran={len(ran)} cached={len(order) - len(ran)} {ran}") show("run 1, cold cache ") show("run 2, nothing changed") params["featurize"] = {"window": 14} show("run 3, window 7 -> 14 ") params["gate"] = {"min_auc": 0.70} show("run 4, gate threshold ")
⚠️
Three ways a cache silently lies to you.1. Leaving the code version out of the key, so an edited task still serves its old result. 2. Serialising params without sort_keys=True, so equal dicts hash differently. 3. Putting a timestamp or random seed into the params, so the key is new every time and nothing is ever cached. Failed tasks must never be cached at all.
3.8 — Idempotency: Safe to Run Twice

An orchestrator gives you at-least-once execution: after a timeout it cannot know whether the task finished, so it runs it again. Add manual "clear and re-run", and backfills, and every task will be executed more than once in its life. A task is idempotent when running it N times leaves the world in the same state as running it once. The classic bug is a load that appends: the write succeeds, the acknowledgement is lost, the retry appends again, and the table now holds duplicates that quietly corrupt every metric downstream.

Append vs. overwrite-the-partition, after a retry
table = {} # partition -> rows, standing in for a warehouse table def load_append(partition, rows): table.setdefault(partition, []).extend(rows) def load_overwrite(partition, rows): table[partition] = list(rows) # replace the whole partition: same end state every time rows = [("u1", 3), ("u2", 5)] # The load succeeded but the acknowledgement was lost, so the orchestrator retries it once for _ in range(2): load_append("2026-03-01", rows) load_overwrite("2026-03-02", rows) print("append ->", len(table["2026-03-01"]), "rows", table["2026-03-01"]) print("overwrite ->", len(table["2026-03-02"]), "rows", table["2026-03-02"])
⭐
Recipes that make a task idempotent:Overwrite the partition (INSERT OVERWRITE, or delete-then-insert in one transaction). Upsert on a natural key (MERGE). Write to a temporary path, then atomically rename. Derive output paths from the logical date, never from now(). For side effects you cannot undo (an email, a payment call), send an idempotency key so the receiver can drop duplicates.
3.9 — Logical Dates, Backfills and Catchup

Batch pipelines process partitions — usually one per day. A daily run is identified by its logical date (Airflow: ds, or logical_date since 2.2): the start of the data interval it processes. And it fires after that interval ends. So the run for Monday's data starts on Tuesday; logical date is Monday, run date is Tuesday. Mixing the two up is the most common off-by-one bug in data engineering, and the cure is one rule: a task must derive its partition from the logical date the orchestrator hands it, never from datetime.now(). Get that right and two more ideas fall out. A backfill deliberately re-runs a range of past partitions (after a bug fix, or a new column). Catchup is the scheduler doing it automatically — creating a run for every interval missed since the DAG was last active.

Logical date vs. run date, and how catchup floods a scheduler
from datetime import date, timedelta def run_date(logical_date): return logical_date + timedelta(days=1) # a daily run fires AFTER its data interval has ended def partitions(start, end): d, out = start, [] while d <= end: out.append(d) d += timedelta(days=1) return out def waves(items, size): return [items[i:i + size] for i in range(0, len(items), size)] paused_since, unpaused_on = date(2026, 3, 1), date(2026, 3, 31) missed = partitions(paused_since, unpaused_on - timedelta(days=1)) print(f"logical date {missed[0]} runs on {run_date(missed[0])}") print("catchup=True queues", len(missed), "runs at once") batches = waves(missed, 5) print(f"max_active_runs=5 -> {len(batches)} waves; first = {[d.isoformat() for d in batches[0]]}") print(f"catchup=False -> 1 run, for {missed[-1]} only")
⚠️
Catchup can take a system down.Unpause a daily DAG after a month and catchup=True queues thirty runs at once, all hammering the same source database and the same worker pool. Cap it with max_active_runs (work through the backlog in waves), or set catchup=False when old partitions are not needed. Backfills of non-idempotent tasks are worse still: every backfilled day duplicates data.

The remaining two differ in philosophy rather than mechanics. Dagster is asset-centric: you declare the data assets (a features table, a model) and their dependencies, and it derives what is stale and needs recomputing — the caching idea of 3.7 promoted to the core model. Kubeflow Pipelines (and Argo Workflows) run each step as a container on Kubernetes with per-step caching and GPU scheduling, at the cost of operating Kubernetes.

Chapter Summary
  • A pipeline is a DAG stored as data — task → dependencies — so it can be validated, drawn and scheduled before anything runs. Cycles are deadlocks and are rejected at parse time.
  • Kahn's algorithm gives a deterministic run order and detects cycles for free. The 'blocked tasks' it reports include innocents downstream of the cycle.
  • Wall-clock time is set by the critical path, not the task count. Optimise tasks on it; ignore the rest.
  • Failure propagation: run a task only if all upstream succeeded, otherwise skip it; independent branches continue. Never run on stale or partial inputs.
  • Retry transient errors with capped exponential backoff (plus jitter); never retry deterministic bugs. Retries only make sense for idempotent tasks.
  • A cache key (name + code version + params + upstream keys) lets unchanged work be skipped; failures are never cached.
  • Derive partitions from the logical date, not now(); a run fires after its interval ends. Backfill deliberately, and bound catchup with max_active_runs.

💼 Pipelines & Orchestration — Interview Prep

10 questions that ML platform, MLOps and data engineering interviewers use to check whether you have actually operated scheduled pipelines, not just drawn a DAG. Click a question to reveal what a strong answer sounds like, including the pitfall to avoid.

What does it mean for a pipeline task to be idempotent, and how do you make one?▶
Running it once or ten times with the same inputs leaves the system in the same end state. That matters because orchestrators give at-least-once execution: after a timeout they cannot know whether the task finished, so they run it again — and retries, manual clears and backfills do the same. To achieve it: overwrite the partition (INSERT OVERWRITE, or delete-then-insert in one transaction) instead of appending; upsert on a natural key (MERGE); write to a temporary location and atomically rename; derive output paths from the logical date; and attach an idempotency key to side effects you cannot undo, such as a payment or an email. A classic pitfall is calling datetime.now() inside the task: a re-run on a different day then writes a different partition.
Explain backfill versus catchup, and what can go wrong with each.▶
A backfill is a deliberate re-run of a range of past partitions — after a bug fix, a schema change, or when adding a new feature column. Catchup is the scheduler doing this automatically: it creates a run for every interval missed since the DAG's start date or since it was last active. What goes wrong: an unpaused DAG can queue dozens of runs at once and flood the source database or worker pool (bound it with max_active_runs, pools, or catchup=False); non-idempotent tasks duplicate data on every backfilled day; and tasks that read 'the latest snapshot' rather than a point-in-time input produce wrong history, which for ML means silent label or feature leakage in retrained models. Good practice: backfill in chunks, dry-run first, and make sure every task derives its inputs from the logical date.
At-least-once versus exactly-once: which does an orchestrator give you?▶
At-least-once. If a worker dies after doing the work but before reporting, the orchestrator has to assume it failed and run it again. True exactly-once across independent systems is not achievable in general — a call to a third-party API sits outside any transaction you control. What you build is effectively-once: at-least-once delivery plus idempotent writes (upserts, dedupe keys, transactional commits), so the duplicates are harmless. Streaming systems (Kafka transactions, Flink checkpoints) do offer exactly-once semantics, but only inside their own boundary. The pitfall in an interview is claiming exactly-once without saying where its boundary ends.
Airflow, Prefect, Dagster, Kubeflow: how do you choose?▶
There is no universal winner, so answer with trade-offs and the team's context. Airflow is the most widely deployed, centred on scheduled, time-partitioned batch DAGs, with a huge provider ecosystem; graph structure is mostly fixed at parse time and it is operationally heavy. Prefect is Python-native, with dynamic control flow, easy local development and API or event-triggered runs. Dagster is asset-centric — you declare data assets and dependencies, and get lineage, freshness and testing as first-class ideas. Kubeflow Pipelines (or Argo) runs each step as a container on Kubernetes, which suits GPU and large ML steps and gives per-step caching, at the cost of owning Kubernetes. Match the choice to what you already run, whether work is batch or event-driven, Kubernetes maturity, and how much lineage matters.
What is a sensor, and what are the pitfalls of using one?▶
A sensor is a task whose job is to wait for something external — a file landing in object storage, an upstream partition becoming ready, an API returning 200 — before letting downstream tasks run. The classic pitfall is poke mode, where the sensor occupies a worker slot for the whole wait; enough of them starve the pool and unrelated DAGs stop running. Prefer reschedule mode or deferrable operators that free the slot while waiting. Always set a timeout (and decide whether a timeout fails or soft-fails the run). Better still, prefer data-aware or event-driven triggers (Airflow datasets, Dagster asset sensors) over polling on the clock, and make sure the thing being waited on is parameterised by the logical date.
How do you handle late-arriving data in a batch pipeline?▶
First decide what a partition means: event time (when it happened) or ingestion time (when it arrived). Then combine a few tools: a watermark or delay so a run waits, say, two hours past the interval end; a lookback window that idempotently reprocesses the last N partitions on every run; and re-running (clearing) an affected partition when a late batch lands, letting downstream tasks re-trigger. Add a completeness check before the gate so you never train or report on a partial day. For ML there is a second flavour: late labels — ground truth arrives days after the prediction, so evaluation must be joined point-in-time. The pitfall is silently using partial data, which produces a plausible-looking but biased model.
Why not just use cron and shell scripts?▶
Cron only answers 'when'. It has no dependency graph, so step 3 happily runs on stale data when step 2 fails; no retries with backoff; no backfill or per-partition state; no history of what ran, no per-task logs and no alerting; no concurrency limits, so slow runs overlap; and no shared secrets handling or UI. An orchestrator supplies all of that. The honest counterpoint: for one small, independent job, cron plus a lock file and log rotation is perfectly fine, and adopting a platform for it is over-engineering. The signal to move is the second job that depends on the first.
Which failures should a task retry, and how?▶
Retry transient failures — timeouts, connection resets, 429 and 503 responses, a spot instance being reclaimed. Do not retry deterministic ones — a schema mismatch, a failed assertion, bad configuration, a quality gate saying no — because they fail identically every time, waste compute, and delay the alert. Use a bounded number of attempts, exponential backoff with a cap and jitter so a fleet of retries does not hit a recovering service in one synchronised wave, and alert once the attempts are exhausted. Retries are only safe on idempotent tasks. In Airflow this is retries, retry_delay, retry_exponential_backoff and max_retry_delay; in Prefect, retries and retry_delay_seconds (which can be a list).
How should tasks pass data to each other?▶
Pass references and small metadata, not payloads. Return a path or URI, a partition key, a run id or a handful of metrics — via XCom or return values, which live in the orchestrator's metadata database — and let the bulk data travel through proper storage (object storage, the warehouse, a feature store) at deterministic locations derived from the logical date and run id. Pushing a large DataFrame through XCom bloats the metadata database, hits size limits and serialisation problems, and makes runs hard to reproduce. For ML the same rule applies to models: write the artifact to a registry or object store and hand downstream tasks its URI.
A daily job's 'Monday' run started on Tuesday. Is that a bug?▶
No — that is normal. A daily run processes a data interval (Monday 00:00 to Tuesday 00:00) and can only start once that interval has ended. Its logical date (ds) is Monday, and its actual start is Tuesday. The bug to watch for is code that uses datetime.now() instead of the logical date, so it processes Tuesday's data under Monday's label — and a backfill of last month then processes today's data thirty times. Always derive the partition from the value the orchestrator passes (templated {{ ds }}, data_interval_start, or a flow parameter). Airflow renamed execution_date to logical_date in 2.2 partly because of this confusion.
