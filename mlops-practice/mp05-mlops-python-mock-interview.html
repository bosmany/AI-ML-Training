MLOps Python Bonus 5:
The Mock Interview

The last chapter of the MLOps track is the one interviews actually feel like. ML-platform and MLOps loops mix a pandas round with a systems-flavoured round — and in both, the trap is almost never the algorithm. It's a data problem: a join that leaks the future, a feature that means something different in production, an A/B test read too early, a stream that delivers the same event twice. This chapter works through the eight problems that come up again and again, each as real, runnable code you can narrate out loud, then closes with a timed 3-problem mock.

5.1 — How to Attack an ML-Systems Coding Question

Interviewers grade the process at least as much as the final code: did you clarify the inputs, name the failure modes, test before you trusted it, and state the complexity out loud? A repeatable routine is what keeps you calm when the problem is unfamiliar.

  • Restate and clarify. Units, ordering, nulls, time zones, scale — and what "late" or "duplicate" actually means in this system.
  • Name the failure modes first. Leakage, duplicates, out-of-order data, skew, thin samples. In ML questions the bug is usually in the data, not the model.
  • Write three tiny tests before the code: empty, ordinary, and the nasty case.
  • Say the brute force out loud, with its complexity, then improve on it.
  • Code in small verified steps. Run after each function, not once at the end.
  • Close the loop: final complexity, edge cases handled (and deliberately not handled), and what you would monitor in production.
A tiny test harness — write the cases BEFORE the function
def check(name, got, want): status = 'PASS' if got == want else f'FAIL (got {got!r}, want {want!r})' print(f'{name}: {status}') def dedupe_keep_order(items): seen = set() out = [] for x in items: if x not in seen: seen.add(x) out.append(x) return out # Write the tiny cases BEFORE the code: empty, typical, adversarial. check('empty input', dedupe_keep_order([]), []) check('no duplicates', dedupe_keep_order([1, 2, 3]), [1, 2, 3]) check('keeps FIRST occurrence', dedupe_keep_order([3, 1, 3, 2, 1]), [3, 1, 2])
🗣
How to narrate it: "Before I write anything, here are three cases I want this to pass: empty input, an ordinary case, and the nasty one — duplicates that arrive after my state has been evicted." Interviewers hear that as someone who has shipped this before.
5.2 — Point-in-Time Correct Joins (and the Leak Everyone Introduces Once)

A model trained on feature values that were computed after the label event learns from the future. In production that information doesn't exist yet, so offline metrics look superb and online performance collapses. It is the single most common silent bug in tabular ML, and it is exactly what feature stores exist to prevent. The fix is an as-of join: for each label row, take the most recent feature value with a timestamp at or before the label time.

Naive "latest value" join vs a point-in-time join with merge_asof
import pandas as pd # LABEL side: one row per loan application, and whether the customer later defaulted. labels = pd.DataFrame({ 'customer_id': ['c1', 'c1', 'c2', 'c3'], 'applied_at': pd.to_datetime(['2024-03-01', '2024-06-01', '2024-04-15', '2024-05-10']), 'defaulted': [0, 1, 0, 1], }) # FEATURE side: snapshots of a feature over time (history, not just the latest value). features = pd.DataFrame({ 'customer_id': ['c1', 'c1', 'c1', 'c2', 'c3'], 'computed_at': pd.to_datetime(['2024-02-20', '2024-05-20', '2024-07-01', '2024-04-01', '2024-06-15']), 'avg_txn_30d': [120.0, 340.0, 910.0, 75.0, 500.0], }) # NAIVE: join the LATEST feature value per customer -> silently uses the future. latest = features.sort_values('computed_at').groupby('customer_id', as_index=False).last() naive = labels.sort_values('applied_at').merge(latest, on='customer_id', how='left') # POINT-IN-TIME: for each label, the most recent feature computed at or before applied_at. pit = pd.merge_asof( labels.sort_values('applied_at'), features.sort_values('computed_at'), left_on='applied_at', right_on='computed_at', by='customer_id', direction='backward', ) print('customer applied_at naive point-in-time') for i in range(len(pit)): n_val = naive['avg_txn_30d'].iloc[i] p_val = pit['avg_txn_30d'].iloc[i] p_txt = 'no feature yet' if pd.isna(p_val) else f'{p_val:.0f}' print(f"{pit['customer_id'].iloc[i]:<9} {pit['applied_at'].iloc[i].date()} {n_val:>5.0f} {p_txt}") leaky = int((naive['avg_txn_30d'].to_numpy() != pit['avg_txn_30d'].fillna(-1).to_numpy()).sum()) print(f'Rows where the naive join used future data: {leaky} of {len(pit)}')
📖
Read the output: customer c1 applied on 2024-03-01, but the naive join gave them 910 — a value computed on 2024-07-01, four months after the application. Customer c3 had no feature at all when they applied, yet the naive join invented one. The point-in-time join returns the honest answer: 120 for c1, and "no feature yet" for c3.

Real features go stale, so a good join also bounds how old a matched value may be with tolerance:

tolerance, and the sortedness gotcha
import pandas as pd labels = pd.DataFrame({ 'customer_id': ['c1', 'c1', 'c2'], 'applied_at': pd.to_datetime(['2024-03-01', '2024-06-01', '2024-04-15']), }) features = pd.DataFrame({ 'customer_id': ['c1', 'c1', 'c2'], 'computed_at': pd.to_datetime(['2024-02-20', '2024-05-20', '2024-04-01']), 'avg_txn_30d': [120.0, 340.0, 75.0], }) def pit_join(tolerance): return pd.merge_asof( labels.sort_values('applied_at'), features.sort_values('computed_at'), left_on='applied_at', right_on='computed_at', by='customer_id', direction='backward', tolerance=tolerance, ) print('no tolerance :', pit_join(None)['avg_txn_30d'].fillna(-1).tolist()) print('tolerance 30 days :', pit_join(pd.Timedelta(days=30))['avg_txn_30d'].fillna(-1).tolist()) print('tolerance 11 days :', pit_join(pd.Timedelta(days=11))['avg_txn_30d'].fillna(-1).tolist()) # The classic gotcha: merge_asof needs BOTH sides sorted by the time key. try: pd.merge_asof(labels.sort_values('customer_id', ascending=False), features.sort_values('computed_at'), left_on='applied_at', right_on='computed_at', by='customer_id') except ValueError as e: print('unsorted left side ->', type(e).__name__)
⚠️
Three things interviewers probe here: (1) merge_asof requires both frames sorted by the time key or it raises. (2) by= keeps the match within the same entity — without it you would match customer A's label to customer B's feature. (3) direction='nearest' is almost always wrong for training data because it can pick a row from the future; use 'backward'. Also mention an availability lag: a value "computed at" 10:00 may not reach the store until 10:20.
🗣
How to narrate it: "I'll join on entity and time, not just entity, taking the latest feature at or before the label timestamp. I'll add a test that asserts max(feature_ts) <= label_ts for every row, and I'll split train and validation by time, not randomly."
5.3 — Training/Serving Skew: A Detector You Can Write in 20 Lines

Skew means the model receives different inputs in production than it was trained on at the same point in time. Typical causes: different code paths for offline and online features (pandas here, SQL or Java there), a units mismatch, stale online features, categories never seen in training, and different null handling. It is distinct from drift, which is the world changing gradually over time — skew is usually a step change and almost always a bug. A cheap detector that compares summary statistics per feature catches most of it.

Compare serving to training: mean ratio, unseen categories, new nulls
import pandas as pd train = pd.DataFrame({ 'age': [23, 35, 41, 29, 52, 38, 45, 31], 'income': [42.0, 61.5, 75.0, 52.0, 98.0, 66.0, 80.0, 58.0], # $ thousands 'country': ['US', 'US', 'DE', 'IN', 'US', 'DE', 'IN', 'US'], 'clicks_7d': [3, 8, 5, 2, 9, 4, 6, 3], }) serve = pd.DataFrame({ 'age': [27, 44, 33, 39, 50, 36], 'income': [51000.0, 72000.0, 64000.0, 88000.0, 91000.0, 59000.0], # BUG: raw dollars 'country': ['US', 'BR', 'DE', 'US', 'BR', 'IN'], # BR never seen in training 'clicks_7d': [4, None, 6, None, 7, 3], # nulls appear only at serving }) def skew_report(train, serve, mean_tol=0.25, null_tol=0.10): flagged = {} for col in train.columns: reasons = [] if pd.api.types.is_numeric_dtype(train[col]): t_mean, s_mean = train[col].mean(), serve[col].mean() ratio = s_mean / t_mean if abs(ratio - 1) > mean_tol: reasons.append(f'mean ratio {ratio:.2f} (train {t_mean:.2f}, serve {s_mean:.2f})') else: unseen = sorted(set(serve[col].dropna()) - set(train[col].dropna())) if unseen: reasons.append(f'unseen categories {unseen}') null_gap = serve[col].isna().mean() - train[col].isna().mean() if null_gap > null_tol: reasons.append(f'null rate up {null_gap:.0%}') if reasons: flagged[col] = reasons return flagged report = skew_report(train, serve) print('Flagged features:', list(report)) for col, reasons in report.items(): for r in reasons: print(f' {col}: {r}')
⚠️
A mean ratio of 1064 is not drift — it is a units bug (thousands of dollars in training, raw dollars in serving). Say that distinction out loud: gradual movement suggests drift, an instant order-of-magnitude jump suggests a pipeline bug. The strongest prevention is "log and wait": log the exact features you served, and train on those logged values.
🗣
How to narrate it: "I'd compute per-feature mean, null rate and category set on both sides, alert on step changes, and add a golden-row integration test that pushes one raw record through both the training and serving paths and asserts identical feature vectors."
5.4 — Batch vs Online Inference: Put Numbers on the Decision

The batch-vs-online question is really "who is waiting, and how fresh must the answer be?" Nobody waiting and hours-old scores acceptable? Batch. A user or transaction waiting? Online. Strong candidates back the choice with arithmetic, not adjectives. Online capacity comes from Little's law: requests in flight = arrival rate × time in system.

A small latency and cost calculator
import math def online_cost(peak_qps, p95_latency_s, concurrency_per_replica, target_util, replica_hourly_usd): in_flight = peak_qps * p95_latency_s # Little's law: L = arrival rate x time in system replicas = math.ceil(in_flight / (concurrency_per_replica * target_util)) replicas = max(replicas, 2) # one replica is an outage waiting to happen return replicas, replicas * replica_hourly_usd * 730 def batch_cost(rows, rows_per_node_hour, nodes, node_hourly_usd, runs_per_month): hours = math.ceil(rows / (rows_per_node_hour * nodes)) return hours, hours * nodes * node_hourly_usd * runs_per_month def choose(max_latency_ms, freshness_hours): if max_latency_ms < 1000: return 'online' # a human/transaction is waiting if freshness_hours >= 6: return 'batch' # scores can be precomputed and looked up return 'online' replicas, online_month = online_cost(peak_qps=400, p95_latency_s=0.12, concurrency_per_replica=8, target_util=0.6, replica_hourly_usd=0.40) hours, batch_month = batch_cost(rows=20_000_000, rows_per_node_hour=2_500_000, nodes=4, node_hourly_usd=0.80, runs_per_month=30) print(f'Churn scores for 20M users: online {replicas} replicas = ${online_month:,.2f}/mo, ' f'batch {hours}h nightly = ${batch_month:,.2f}/mo') print('Nightly churn scores ->', choose(max_latency_ms=60_000, freshness_hours=24)) print('Card-fraud check ->', choose(max_latency_ms=150, freshness_hours=0)) print('Homepage recs (hourly)->', choose(max_latency_ms=300, freshness_hours=1))
FactorBatchOnline
Latency needMinutes to hours is fineMilliseconds to a second; someone is waiting
FreshnessAs fresh as the last runAs fresh as the online feature store
Cost shapePay for the hours the job runsPay for capacity 24/7, including idle time

⭐
Hybrid is the answer interviewers like: precompute the expensive scores in batch, write them to a key-value store, and only compute the fresh signal online. You get online latency at close to batch cost.
5.5 — A/B Test Significance, Sample Size and the Peeking Trap

You will be asked to decide whether a model change "won". For a conversion metric that is a two-proportion z-test: pool the two rates, compute the standard error, divide the difference by it, and turn the z-score into a two-sided p-value. Implement it by hand, then cross-check against scipy — the two ways to check are worth knowing because a z-test on two proportions is the same thing as a chi-square test on the 2×2 table (z² = χ²).

Two-proportion z-test by hand, cross-checked with scipy, plus sample size
import math from scipy import stats def two_prop_ztest(n_a, x_a, n_b, x_b): p_a, p_b = x_a / n_a, x_b / n_b p_pool = (x_a + x_b) / (n_a + n_b) se = math.sqrt(p_pool * (1 - p_pool) * (1 / n_a + 1 / n_b)) z = (p_b - p_a) / se p_value = math.erfc(abs(z) / math.sqrt(2)) # two-sided, standard normal return p_a, p_b, z, p_value p_a, p_b, z, p = two_prop_ztest(10_000, 1_000, 10_000, 1_090) print(f'A={p_a:.2%} B={p_b:.2%} lift={(p_b - p_a) / p_a:+.1%}') print(f'by hand : z={z:.4f} p={p:.4f}') # Cross-check two ways with scipy: the normal tail, and a chi-square test (z**2 == chi2). print(f'norm.sf : p={2 * stats.norm.sf(abs(z)):.4f}') chi2, p_chi = stats.chi2_contingency([[1_000, 9_000], [1_090, 8_910]], correction=False)[:2] print(f'chi2 : chi2={chi2:.4f} (z**2={z**2:.4f}) p={p_chi:.4f}') # Sample size per arm to detect 10% -> 11% at alpha=0.05, power=0.80. z_a, z_b = stats.norm.ppf(0.975), stats.norm.ppf(0.80) p1, p2 = 0.10, 0.11 n_exact = (z_a + z_b) ** 2 * (p1 * (1 - p1) + p2 * (1 - p2)) / (p2 - p1) ** 2 n_rule = 16 * 0.10 * 0.90 / 0.01 ** 2 # rule of thumb: 16 * p(1-p) / delta^2 print(f'n per arm: exact {math.ceil(n_exact):,} rule-of-thumb {math.ceil(n_rule):,}')
📐
Sample size before you start. Detecting a lift from 10% to 11% at α = 0.05 with 80% power needs about 14,750 users per arm. The quick rule of thumb n ≈ 16·p(1−p)/δ² lands within a few percent, which is enough to say in an interview. If someone proposes a test that will only collect 2,000 users, the right answer is "it can't detect that effect".

The other classic trap is peeking: checking the dashboard repeatedly and stopping the first time p < 0.05.

Five looks at the same experiment — only the first crosses 1.96
import math def z_stat(n_a, x_a, n_b, x_b): p_pool = (x_a + x_b) / (n_a + n_b) se = math.sqrt(p_pool * (1 - p_pool) * (2 / n_a)) # equal arm sizes return (x_b / n_b - x_a / n_a) / se # Cumulative results at five planned looks (users per arm, conversions A, conversions B). looks = [(2000, 200, 252), (4000, 404, 452), (6000, 596, 650), (8000, 804, 852), (10000, 1000, 1049)] for i, (n, a, b) in enumerate(looks, start=1): z = z_stat(n, a, n, b) flag = ' <-- "significant!" (a peeker stops here)' if abs(z) > 1.96 else '' print(f'look {i}: n/arm={n:>6,} z={z:5.2f}{flag}') print('Planned-horizon verdict at look 5: not significant')
⚠️
Repeated looks inflate false positives. A fixed-horizon test assumes one look; with five equally spaced looks and stop-at-first-significant, the true false-positive rate is about 14%, not 5%. Fix it by fixing the horizon and sample size in advance, or by using a method built for continuous monitoring (sequential testing, alpha-spending such as O'Brien–Fleming, or mSPRT). Also check for sample ratio mismatch first — if a 50/50 split delivered 52/48 traffic, distrust the lift before you celebrate it.
5.6 — Deduplicating a Prediction-Event Stream With a Watermark

Queues such as Kafka and SQS deliver at least once, so duplicates are normal, and events arrive out of order. The naive fix — remember every event id forever — leaks memory until the job falls over. A watermark bounds the state: it is the newest event time seen minus an allowed lateness, and anything older than it is either forgotten (state) or rejected (late arrivals).

A watermark deduper: emit once, drop the hopelessly late, keep state bounded
class WatermarkDeduper: """Emit each event_id once. Drop events older than the watermark. Keep state bounded.""" def __init__(self, allowed_lateness): self.allowed_lateness = allowed_lateness self.max_ts = None self.seen = {} # event_id -> event time def process(self, event_id, ts): if self.max_ts is None or ts > self.max_ts: self.max_ts = ts watermark = self.max_ts - self.allowed_lateness for old in [k for k, t in self.seen.items() if t < watermark]: del self.seen[old] # state older than the watermark is safe to forget if ts < watermark: return 'late' if event_id in self.seen: return 'duplicate' self.seen[event_id] = ts return 'emit' events = [('a', 100), ('b', 103), ('a', 100), ('c', 108), ('d', 95), ('b', 103), ('e', 125), ('c', 108), ('f', 118), ('g', 112)] dedupe = WatermarkDeduper(allowed_lateness=10) for event_id, ts in events: print(f'{event_id}@{ts:<3} -> {dedupe.process(event_id, ts):<9} state size {len(dedupe.seen)}')
📖
Read the trace: the second b@103 is a duplicate because b is still remembered. But when e@125 arrives, the watermark jumps to 115 and the deduper forgets a, b and c — so the later c@108 is rejected as late rather than recognised as a duplicate. That is the deliberate trade: bounded memory in exchange for a lateness cut-off.
🗣
How to narrate it: "Exactly-once processing is really at-least-once delivery plus an idempotent consumer. I'll key on event id, bound the state with a watermark, and tell you what lateness I'm assuming — and I'd emit a metric for late and duplicate counts so we can tune it."
5.7 — A Rollout Decision: Promote, Hold or Roll Back

Deploying a new model is a decision under uncertainty, and interviewers like it because it forces you to encode judgement as code. The structure that scales: enough traffic first (a 0% error rate on 300 requests proves nothing), then hard guardrails — errors and latency — that trigger rollback, and only then the softer quality check that triggers a hold.

Canary metrics in, decision and reasons out
def rollout_decision(baseline, canary, min_requests=1000, max_err_delta=0.005, max_latency_ratio=1.25, min_conv_ratio=0.98): if canary['requests'] < min_requests: return 'hold', [f"only {canary['requests']} requests, below the {min_requests} minimum"] b_err = baseline['errors'] / baseline['requests'] c_err = canary['errors'] / canary['requests'] reasons = [] if c_err - b_err > max_err_delta: reasons.append(f'error rate {c_err:.2%} vs baseline {b_err:.2%}') if canary['p95_ms'] > baseline['p95_ms'] * max_latency_ratio: reasons.append(f"p95 {canary['p95_ms']}ms vs baseline {baseline['p95_ms']}ms") if reasons: return 'rollback', reasons # hard guardrails: never trade safety for quality if canary['conversion'] < baseline['conversion'] * min_conv_ratio: return 'hold', [f"conversion {canary['conversion']:.3f} < {baseline['conversion'] * min_conv_ratio:.4f}"] return 'promote', ['all guardrails healthy'] baseline = {'requests': 50_000, 'errors': 100, 'p95_ms': 180, 'conversion': 0.120} scenarios = { 'healthy': {'requests': 5_000, 'errors': 12, 'p95_ms': 190, 'conversion': 0.121}, 'thin traffic': {'requests': 300, 'errors': 0, 'p95_ms': 170, 'conversion': 0.130}, 'error spike': {'requests': 5_000, 'errors': 80, 'p95_ms': 185, 'conversion': 0.121}, 'quality dip': {'requests': 5_000, 'errors': 9, 'p95_ms': 185, 'conversion': 0.110}, } for name, canary in scenarios.items(): decision, reasons = rollout_decision(baseline, canary) print(f"{name:<13} -> {decision.upper():<8} ({'; '.join(reasons)})")

5.8 — Feature Hashing, Unseen Categories and Serving-Time Surprises

High-cardinality categoricals (user agents, product ids) are often hashed into a fixed number of buckets so the model input size never grows. Two decisions decide whether that works in production: which hash function you use, and what happens on values the encoder has never seen.

A stable hash bucket, a vocabulary with an UNK slot, and a collision check
import hashlib def bucket(value, n_buckets=8, salt='device_type'): digest = hashlib.md5(f'{salt}:{value}'.encode()).hexdigest() # stable across processes and machines return int(digest, 16) % n_buckets devices = ['ios', 'android', 'web', 'tv', 'watch', 'kiosk', 'car', 'toaster'] print('hashed buckets :', {d: bucket(d) for d in devices}) print('same call twice:', bucket('ios') == bucket('ios')) # A vocabulary encoder needs an explicit answer for values it has never seen. vocab = {'ios': 0, 'android': 1, 'web': 2} UNK = len(vocab) # reserved index for "unseen" encode = lambda v: vocab.get(v, UNK) print('vocab encoding :', [encode(d) for d in ['ios', 'web', 'toaster', 'tv']]) # Collisions are the price of a fixed-size table: measure them, don't guess. for n in (4, 8, 64): used = len({bucket(d, n) for d in devices}) print(f'{n:>2} buckets -> {used} distinct buckets for {len(devices)} values')
⚠️
Never use Python's built-in hash() for strings here. It is salted per process (see PYTHONHASHSEED): run python -c "print(hash('ios'))" twice in a terminal and you get two different numbers. A training job and a serving container would then send the same value to different buckets — training/serving skew you cannot see. Use a stable hash such as hashlib.md5 or zlib.crc32.
🗣
How to narrate it: "I'd define behaviour for unseen values up front — a reserved UNK index or hashing — and log the unseen rate as a monitor, because a sudden rise usually means an upstream schema change, not a real new category."
MLOps 5 Summary
  • A repeatable routine — clarify, name the failure modes, test first, brute force then improve, verify in small steps, close the loop — matters as much as the code.
  • Point-in-time joins (merge_asof, direction='backward', tolerance, by=) prevent label leakage; a naive "latest value" join uses the future.
  • Skew (train vs serve, same time, usually a bug) is different from drift (the world moving); detect it with per-feature summary statistics and prevent it with one shared feature definition.
  • Batch vs online is decided by who is waiting; back it with Little's law and a cost comparison, and consider the hybrid.
  • A/B tests need a sample size and a fixed horizon; peeking inflates false positives (about 14% with five looks); check sample ratio mismatch first.
  • Watermarks bound dedupe state; rollout gates check traffic, then hard guardrails, then quality; stable hashes keep training and serving consistent.

💼 MLOps & ML-Platform Interview Prep

10 questions that ML-platform and MLOps interviews ask again and again, with the answer a strong candidate gives — including the pitfall to name. Click a question to reveal the answer. Not graded — this is here so you walk in prepared, not just quizzed.

What is the difference between an offline and an online feature store, and why do you need both?▶
The offline store holds the full history of every feature (warehouse tables or Parquet in object storage) and is what training reads, using point-in-time joins so each training row only sees values that existed at its label time. The online store (Redis, DynamoDB, Bigtable) holds only the latest value per entity key and answers single-key lookups in milliseconds for serving. You need both because the access patterns are opposite: huge scans over history versus tiny, latency-critical lookups. The important part is that both are fed from one feature definition — a materialisation job writes the same computed values to both — otherwise you have built training/serving skew into the platform. Expect follow-ups on TTLs and freshness, backfills, and how you populate the online store for a brand-new feature.
What is point-in-time correctness and how do you enforce it?▶
For each training example you may only use feature values that were available at prediction time — never anything computed after the label event. The failure is silent: offline metrics are inflated and production is near random. Enforce it structurally: keep timestamped feature history (not just the latest value), join with an as-of join (pandas.merge_asof, or the feature store's historical-features API), account for an availability lag, and add a test asserting max(feature_ts) <= label_ts for every row. Also split train and validation by time, not randomly, for anything time-dependent.
What is training/serving skew, how do you detect it, and how do you prevent it?▶
Skew is a difference between the inputs a model was trained on and what it receives online at the same point in time — as opposed to drift, which is the world changing over time. Typical causes: separate code paths for offline and online feature computation, units or encoding differences, stale online features, null handling, unseen categories, and library version differences. Detect it by logging the features actually served and comparing per-feature summary statistics (mean, null rate, category set) against the training set, alerting on step changes. Prevent it with a single shared feature definition, preprocessing code packaged with the model, golden-row integration tests that push one raw input through both paths, and ideally "log and wait" — train on the features you actually logged at serving time.
What does CI/CD look like for an ML system, and how is it different from ordinary software CI/CD?▶
You version and test three things instead of one: code, data and model. CI runs unit tests, data validation (schema, ranges, null rates) and a fast training smoke test. A training pipeline produces a candidate model plus an evaluation report, and a gate compares it against the current production model on a fixed evaluation set and on important slices — promoting only if it wins by a margin and passes latency and fairness checks. CD then rolls out through shadow or canary with automatic rollback on guardrail regressions. The differences: the artefact is not reproducible from code alone (you need pinned data and seeds), you need continuous-training triggers (schedule, drift, new labels), and monitoring is part of the pipeline rather than an afterthought.
How do you version models and roll back safely?▶
Treat a release as an immutable bundle: weights, preprocessing code, feature schema, a training-data hash or snapshot id, the code commit, an environment lockfile and the evaluation report, stored in a registry with stage aliases such as staging, production and archived. Serving resolves an alias, so rollback is repointing "production" to the previous version — seconds, no rebuild. Keep the previous version warm for a fast cutover, keep feature schemas backward compatible for at least one version, and make rollback a rehearsed runbook step with an automatic trigger on guardrail breaches. The trap worth naming: a rollback is only safe if the previous model still works with the current feature pipeline.
How do you monitor a model in production when ground-truth labels arrive late, or never?▶
Layer it. Available immediately: system metrics (latency percentiles, error rate, throughput), data quality (null rates, ranges, schema), input drift per feature (PSI, KS test, category shares) and prediction drift (score distribution, class balance). Then proxies: business or engagement signals that correlate with quality, and model confidence or calibration. When labels eventually arrive, join them back by prediction id and compute real performance over the delayed window; if they never arrive, run a labelled-sample or human-review programme. Alert on sustained deviation rather than single points, and tune thresholds so on-call is not paged by noise.
Batch versus online inference — how do you choose?▶
Ask who is waiting and how fresh the answer must be. If nobody is waiting and hours-old scores are fine (nightly churn, weekly recommendations), batch wins on cost, simplicity and throughput: you pay for hours used, can retry a failed job, and can use warehouse joins. If a user or transaction is waiting (fraud checks, search ranking) you need online serving with an SLO, redundancy and a low-latency feature store, and you pay for capacity even when it is idle. Hybrids are common: precompute expensive scores in batch, serve them from a key-value store, and run the model online only for the fresh signal. Back the choice with numbers — replicas from Little's law versus the hours a nightly job takes.
When should you retrain a model?▶
On evidence or a schedule justified by how fast the domain changes — not on a whim. Triggers: monitored performance decay once labels arrive, significant input or concept drift, enough new labelled data, or a fixed cadence for fast-moving domains. Before promoting, the retrained model must beat the current one on a fixed evaluation set through the normal gate. Pitfalls: retraining on data corrupted by an upstream bug (you bake the bug in), feedback loops where the model's own predictions shape the labels, and retraining so often that cost and instability outweigh the gain. First diagnose whether a drop is a pipeline bug (fix the pipeline) or real drift (retrain).
Inference is too expensive and p99 latency is too high. What levers do you pull?▶
Measure first — profile where the time and money actually go — then, roughly in order of payoff: cache repeated predictions; use dynamic batching to raise hardware utilisation; use a smaller, distilled or quantised model when the accuracy loss is tolerable; right-size and autoscale on concurrency rather than CPU alone; move non-urgent traffic to batch; precompute and look up instead of computing; and use a cascade (a cheap model first, the expensive one only for uncertain cases). State the accuracy cost of each lever and use the SLO and error budget to decide.
What is a shadow deployment, and when would you use one instead of a canary?▶
In a shadow deployment the new model receives a copy of live traffic and its predictions are logged but never returned to users. It shows real-world latency, errors and how much the model disagrees with the current one, with zero user impact — ideal before a risky replacement. Limits: it costs double the compute, side effects must be disabled, and because users never act on its output you cannot measure business impact or feedback effects. The usual ladder is shadow (is it safe and sane?), then a canary at 1–5% with automatic rollback (does it behave under real serving?), then an A/B test (does it actually improve the metric?).
