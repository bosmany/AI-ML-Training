MLOps Python 2:
Experiment Tracking & Model Registry Patterns

Every ML team eventually gets asked "which run produced the model that's in production, and can you rebuild it?" This chapter is how you make that question boring. You will build the object model behind MLflow and Weights & Biases from scratch (runs, stepped metrics, tie-broken comparisons, hyperparameter grids), then the part production teams argue about: a model registry with versions and stages, promotion gates that explain themselves, rollback driven by history, and the lineage that makes a deployed model auditable. These are the exact patterns, and the exact edge cases, MLOps interviewers probe.

2.1 — What Goes Into an Experiment Record (and Why "I Remember the Settings" Fails)

Every ML team starts the same way: a notebook, a few good runs, and a spreadsheet of numbers. Six weeks later someone asks "which run produced the model that's in production, and can we rebuild it?" and nobody can answer. Experiment tracking is the discipline of writing down, automatically, everything needed to answer that question. A run record is more than params and metrics: it also pins the data version (a hash of the training data), the code version (git commit), the environment (Python and library versions), the random seed, and the artifacts the run produced (model file, plots) by checksum.

A run record, and a check for what's missing
run_record = { "run_id": "run-0042", "params": {"lr": 0.1, "max_depth": 4, "n_estimators": 200}, "metrics": {"val_auc": 0.913, "val_loss": 0.271}, "tags": {"model": "churn-classifier", "owner": "ml-platform"}, "data_sha256": "9f2c41aa07d3", "git_sha": "3e7b1c9", "env": {"python": "3.11.8", "scikit-learn": "1.4.2"}, "seed": 0, } REQUIRED = ["params", "metrics", "data_sha256", "git_sha", "env", "seed"] def missing_fields(record): # `in (None, "", {})` instead of `not record.get(key)`, so seed=0 still counts as logged return [key for key in REQUIRED if record.get(key) in (None, "", {})] print("complete record ->", missing_fields(run_record)) sloppy = {"params": {"lr": 0.1}, "metrics": {"val_auc": 0.913}} print("sloppy record ->", missing_fields(sloppy))
⚠️
The falsy-zero bug. not record.get("seed") treats seed=0 as "missing" because 0 is falsy. Validators like this are everywhere in MLOps code (seeds, learning rates of 0, empty-but-valid params), so test for None/empty explicitly instead of relying on truthiness.
2.2 — A Tiny Tracker: Run and Tracker

MLflow, Weights & Biases, Neptune and Comet all boil down to the same small object model: a run holds params, stepped metrics, tags and artifact checksums; a tracker creates runs and keeps them. Building a 40-line version makes every real tool's API obvious. Two behaviors are worth copying exactly: params are write-once (silently overwriting a param would make the record lie), and a crashed run is still recorded with status FAILED — the failures are often the most informative rows.

Run + Tracker with write-once params and a context manager
import hashlib from contextlib import contextmanager from dataclasses import dataclass, field @dataclass class Run: run_id: str name: str params: dict = field(default_factory=dict) metrics: dict = field(default_factory=dict) # key -> [(step, value), ...] tags: dict = field(default_factory=dict) artifacts: dict = field(default_factory=dict) # name -> short sha256 status: str = "RUNNING" def log_param(self, key, value): if key in self.params and self.params[key] != value: raise ValueError(f"param {key!r} already logged as {self.params[key]!r}") self.params[key] = value def log_metric(self, key, value, step=0): self.metrics.setdefault(key, []).append((step, value)) def log_artifact(self, name, content): self.artifacts[name] = hashlib.sha256(content).hexdigest()[:12] class Tracker: def __init__(self): self.runs = [] def start_run(self, name): run = Run(run_id=f"run-{len(self.runs) + 1:04d}", name=name) self.runs.append(run) return run @contextmanager def track(self, name): run = self.start_run(name) try: yield run run.status = "FINISHED" except Exception: run.status = "FAILED" raise tracker = Tracker() with tracker.track("baseline") as run: run.log_param("lr", 0.1) for step, loss in enumerate([0.90, 0.62, 0.48]): run.log_metric("val_loss", loss, step) run.log_artifact("model.bin", b"fake-model-bytes") try: with tracker.track("too-big") as run2: run2.log_param("lr", 0.3) raise RuntimeError("CUDA out of memory") except RuntimeError: pass print([(r.run_id, r.status) for r in tracker.runs]) print(tracker.runs[0].metrics) print(tracker.runs[0].artifacts) try: tracker.runs[0].log_param("lr", 0.5) except ValueError as err: print("blocked:", err)
🧠
Why the run id is deterministic here. Real tools use UUIDs. A counter is used in this tiny tracker so tests and this chapter's graders are reproducible — the general rule is to inject anything non-deterministic (ids, clocks, randomness) so the logic around it stays testable.
2.3 — Stepped Metrics: Final vs Best vs Last

A single number per run hides the learning curve. Log a metric per step (epoch or iteration) and you can answer three different questions: what was the best value and when, what was the last value (what you actually shipped if you didn't checkpoint), and how big the gap is. A validation loss that bottoms out at epoch 3 and then rises is the signature of overfitting, and the last-vs-best gap quantifies it. The same history drives early stopping: stop after patience steps without improvement and keep the checkpoint from the best step.

Best step, last step, and early stopping on a val_loss curve
history = [(0, 0.90), (1, 0.62), (2, 0.48), (3, 0.44), (4, 0.47), (5, 0.53)] # (step, val_loss) def best_step(history, mode="min"): pick = min if mode == "min" else max return pick(history, key=lambda sv: sv[1]) # on ties the FIRST best step wins step, value = best_step(history, "min") last_step, last_value = history[-1] print(f"best val_loss {value} at step {step}") print(f"last val_loss {last_value} at step {last_step}") print(f"overfit gap {last_value - value:.2f}") def early_stop_step(history, patience=2, mode="min"): best, best_at, waited = None, None, 0 for step, value in history: better = best is None or (value < best if mode == "min" else value > best) if better: best, best_at, waited = value, step, 0 else: waited += 1 if waited >= patience: return step, best_at # (where we stopped, which step to restore) return None, best_at print("early stop (stopped_at, restore_step):", early_stop_step(history, patience=2))
⭐
Compare runs on the same footing. Comparing run A's best epoch to run B's last epoch is a classic unfair comparison. Decide once — usually "best step on the validation set, evaluated once on the untouched test set" — and apply it to every run.
2.4 — Comparing Runs: DataFrames and Deterministic Tie-Breaking

Once you have dozens of runs, you compare them as a table: one row per run, param columns plus a metric. The subtle bug is ties. Three runs at val_auc = 0.912 and code that just takes the first row will pick a different "winner" whenever the row order changes — a different machine, a re-sorted export, a parallel sweep finishing in another order. Fix it with an explicit total ordering: metric (descending), then a cost such as training time (ascending), then run_id as the final, always-unique tiebreaker.

Rank runs with an explicit tie-break (pandas and plain Python)
import pandas as pd rows = [ {"run_id": "run-0001", "lr": 0.10, "max_depth": 4, "val_auc": 0.912, "train_s": 41}, {"run_id": "run-0002", "lr": 0.30, "max_depth": 4, "val_auc": 0.905, "train_s": 39}, {"run_id": "run-0003", "lr": 0.10, "max_depth": 6, "val_auc": 0.912, "train_s": 77}, {"run_id": "run-0004", "lr": 0.01, "max_depth": 6, "val_auc": 0.912, "train_s": 41}, {"run_id": "run-0005", "lr": 0.30, "max_depth": 2, "val_auc": 0.871, "train_s": 12}, ] df = pd.DataFrame(rows) ranked = df.sort_values(by=["val_auc", "train_s", "run_id"], ascending=[False, True, True]) for rec in ranked.to_dict("records"): print(f"{rec['run_id']} val_auc={rec['val_auc']} train_s={rec['train_s']}") print("winner:", ranked.iloc[0]["run_id"]) best = min(rows, key=lambda r: (-r["val_auc"], r["train_s"], r["run_id"])) print("plain-python winner:", best["run_id"])
2.5 — Hyperparameter Grids with itertools.product

A grid search is the cross product of the values you list for each hyperparameter: 3 learning rates × 3 depths = 9 runs. itertools.product generates it lazily and in a stable order, so run ids line up between reruns. Every combination becomes a tracked run — including the bad ones, because a sweep that only records winners can't tell you the shape of the search space. The training call below is a deterministic stand-in formula (no randomness), which keeps the output identical everywhere.

Enumerate a grid, track every run, pick the best and worst
from itertools import product def fake_train(lr, max_depth): # deterministic stand-in for a real training run return round(0.70 + 0.05 * max_depth - 0.004 * max_depth ** 2 - 0.5 * abs(lr - 0.1), 4) grid = {"lr": [0.01, 0.1, 0.3], "max_depth": [2, 4, 6]} keys = list(grid) runs = [] for i, values in enumerate(product(*grid.values()), start=1): params = dict(zip(keys, values)) runs.append({"run_id": f"run-{i:04d}", **params, "val_auc": fake_train(**params)}) print(f"{len(runs)} runs") print("best :", max(runs, key=lambda r: r["val_auc"])) print("worst:", min(runs, key=lambda r: r["val_auc"]))
🧠
Grids explode. 5 hyperparameters × 5 values each is 3,125 runs. That is why real sweeps use random search or Bayesian optimization (Optuna, Ray Tune, W&B Sweeps) — the tracking discipline stays identical, only the way configurations are proposed changes.
2.6 — A Model Registry: Versions and Stages

A tracker answers "what did we try?" A model registry answers "what are we serving, and what is allowed to serve?" It stores each registered model as an immutable numbered version that points back to the run that produced it, plus a lifecycle stage: None → Staging → Production → Archived. The invariant that matters most: at most one version per model is in Production, so promoting a new version must archive the old one in the same operation.

ModelRegistry with auto-incrementing versions and a one-production invariant
class ModelRegistry: STAGES = ("None", "Staging", "Production", "Archived") def __init__(self): self.versions = {} # (name, version) -> info def register(self, name, run_id, val_auc, data_sha, git_sha): version = 1 + max((v for (n, v) in self.versions if n == name), default=0) self.versions[(name, version)] = { "run_id": run_id, "val_auc": val_auc, "data_sha": data_sha, "git_sha": git_sha, "stage": "None", } return version def transition(self, name, version, stage): if stage not in self.STAGES: raise ValueError(f"unknown stage {stage!r}") if stage == "Production": # invariant: only ONE production version for (n, v), info in self.versions.items(): if n == name and info["stage"] == "Production": info["stage"] = "Archived" self.versions[(name, version)]["stage"] = stage def stages(self, name): return {v: info["stage"] for (n, v), info in sorted(self.versions.items()) if n == name} reg = ModelRegistry() v1 = reg.register("churn", "run-0001", 0.912, "9f2c41", "3e7b1c9") v2 = reg.register("churn", "run-0007", 0.921, "9f2c41", "a41d0e2") reg.transition("churn", v1, "Production") print(reg.stages("churn")) reg.transition("churn", v2, "Production") print(reg.stages("churn"))
⚠️
Reference only below — needs a real MLflow server. There is no Run button on the next block: MLflow talks to a tracking server (or a local mlruns/ directory), which a browser sandbox cannot do. The runnable classes above mirror this API on purpose, so the skill transfers.

Recent MLflow versions deprecate the fixed Staging/Production stages in favor of aliases (champion, challenger, shadow): named pointers you can create freely and move atomically, several per model. The promotion logic you will build in 2.7 is identical either way — you are just moving a pointer.
2.7 — Promotion Gates and Rollback

Moving a model to Production should be a decision made by code, not by whoever feels confident that day. A promotion gate lists the conditions a candidate must meet, and returns all the reasons it failed (a list is far more useful in CI than a bare False). Typical gates: a metric floor, a required margin over the current production model (small gains are usually noise), a passing validation suite, and no open data-quality flags. The other half is rollback: because every transition is written to a history list, restoring the previous production version is a lookup, not an archaeology project.

A promotion gate that explains itself
def can_promote(candidate, production, min_auc=0.80, margin=0.01): reasons = [] if candidate["val_auc"] < min_auc: reasons.append(f"val_auc {candidate['val_auc']} below floor {min_auc}") if production is not None: delta = round(candidate["val_auc"] - production["val_auc"], 4) # round before comparing floats if delta < margin: reasons.append(f"gain {delta} is under the required margin {margin}") if not candidate.get("validation_passed"): reasons.append("validation suite failed") if candidate.get("open_dq_flags"): reasons.append(f"{len(candidate['open_dq_flags'])} open data-quality flag(s)") return (not reasons), reasons prod = {"val_auc": 0.912} cases = { "good": {"val_auc": 0.925, "validation_passed": True, "open_dq_flags": []}, "tiny gain": {"val_auc": 0.914, "validation_passed": True, "open_dq_flags": []}, "dq flag": {"val_auc": 0.930, "validation_passed": True, "open_dq_flags": ["null spike in tenure"]}, "below floor": {"val_auc": 0.780, "validation_passed": False, "open_dq_flags": []}, } for name, cand in cases.items(): ok, why = can_promote(cand, prod) print(f"{name:12s} -> {'PROMOTE' if ok else 'BLOCK'} {why}") # why the delta is rounded before comparing: a gain of exactly 0.005 is not exactly 0.005 in floating point print("raw delta:", 0.938 - 0.933, "| rounded:", round(0.938 - 0.933, 4))
⭐
Why round before comparing. 0.938 - 0.933 is 0.004999999999999893 in floating point, not 0.005. Compare that raw value against a margin of 0.005 and a candidate that beats production by exactly the required amount gets blocked. Rounding the difference to a sensible precision makes the boundary behave the way the policy is written.
Rollback driven by a transition history
class Registry: def __init__(self): self.stage = {} # version -> stage self.history = [] # (version, from_stage, to_stage, reason) def set_stage(self, version, to, reason=""): self.history.append((version, self.stage.get(version, "None"), to, reason)) self.stage[version] = to def production(self): return next((v for v, s in self.stage.items() if s == "Production"), None) def promote(self, version): current = self.production() if current is not None: self.set_stage(current, "Archived", f"replaced by v{version}") self.set_stage(version, "Production", "gates passed") def rollback(self, reason): current = self.production() previous = next((v for (v, frm, to, why) in reversed(self.history) if frm == "Production" and to == "Archived" and why == f"replaced by v{current}"), None) if previous is None: raise RuntimeError("no previous production version") self.set_stage(current, "Archived", f"rolled back: {reason}") self.set_stage(previous, "Production", "rollback restore") reg = Registry() reg.promote(1) reg.promote(2) print("before rollback:", dict(sorted(reg.stage.items()))) reg.rollback("canary error rate 9%") print("after rollback :", dict(sorted(reg.stage.items())), "-> production is v" + str(reg.production())) for entry in reg.history[-2:]: print(entry)
2.8 — Semantic Versioning, Model Cards, and Lineage

Registry versions are just counters (1, 2, 3). Consumers of a model care about something else: will my integration break? Semantic versioning answers that for models: bump MAJOR when the input/feature contract or the metric definition changes (callers must change), MINOR when you retrain on new data with the same contract, PATCH for a threshold or config fix. A model card is the human-readable record next to the artifact — intended use, what it must not be used for, metrics (including the worst segment, not just the average), limitations. And lineage ties the deployed model back to the exact run, data hash, code commit, params, seed and environment — the difference between "we think this is the model" and an answer an auditor accepts.

bump(), a model card, and a lineage completeness check
def bump(version, kind): major, minor, patch = (int(p) for p in version.split(".")) if kind == "major": return f"{major + 1}.0.0" if kind == "minor": return f"{major}.{minor + 1}.0" if kind == "patch": return f"{major}.{minor}.{patch + 1}" raise ValueError(f"unknown bump {kind!r}") v = "1.4.2" print("new feature contract ->", bump(v, "major")) print("retrained, same schema ->", bump(v, "minor")) print("threshold tweak ->", bump(v, "patch")) LINEAGE_KEYS = ("run_id", "data_sha256", "git_sha", "params", "seed", "env") def lineage_gaps(card): lineage = card.get("lineage", {}) return [k for k in LINEAGE_KEYS if lineage.get(k) in (None, "", {})] card = { "name": "churn-classifier", "version": "1.5.0", "owner": "ml-platform", "intended_use": "rank customers by 30-day churn risk for retention outreach", "not_for": "credit or pricing decisions", "metrics": {"val_auc": 0.921, "val_auc_worst_segment": 0.884}, "limitations": ["trained on 2023-24 EU customers only"], "lineage": {"run_id": "run-0007", "data_sha256": "9f2c41aa07d3", "git_sha": "a41d0e2", "params": {"lr": 0.1, "max_depth": 4}, "seed": 42, "env": {"python": "3.11.8"}}, } print("lineage gaps:", lineage_gaps(card)) del card["lineage"]["git_sha"] print("lineage gaps:", lineage_gaps(card))
⭐
The six-month test. Pick a model that has been in production for six months and try to rebuild it from the registry alone. If any of data hash, git commit, params, seed, environment lock is missing, you found a hole in your process while it is still cheap to fix.
Chapter Summary
  • A run record is more than params + metrics: pin the data hash, git commit, environment, seed and artifact checksums, or the run cannot be reproduced.
  • Log metrics per step so you can tell best from last, quantify overfitting, and implement early stopping. Compare runs on the same footing.
  • Break ties with an explicit total ordering (metric, then cost, then run_id) — never rely on row order.
  • A registry gives each model an immutable version and a lifecycle; exactly one version serves as Production, and modern tools move aliases instead of fixed stages.
  • Promotion is a gate, not a feeling: metric floor, margin over production, passing validation, no open data-quality flags — and the gate returns all reasons it failed.
  • Rollback is a history lookup if every transition is recorded; lineage and a model card make the deployed model auditable.

What belongs in an experiment record beyond hyperparameters and a final metric?▶
Everything you would need to reproduce and audit the run: params, metrics per step (not just the last value), tags (owner, model name, purpose), a data version (content hash or table snapshot id), the git commit (and whether the working tree was dirty), the environment (Python and library versions, ideally a lockfile hash), the random seed, and artifacts stored with checksums. A strong answer also mentions failed runs — you keep those, with status FAILED, because "what didn't work and why" saves the next person days.
Why do you log a hash of the training data and the git SHA instead of just a dataset name and a branch?▶
Names and branches are mutable: train_v3.csv gets overwritten and main moves. A content hash and a commit SHA are immutable identifiers, so they answer "exactly which bytes and which code produced this model" even a year later. If the working tree was dirty at run time, a SHA alone is misleading — log the dirty flag (or refuse to track from a dirty tree in CI).
How do you compare two experiments fairly?▶
Same data split (a fixed, versioned split — never re-split per run), same metric definition, same evaluation protocol (best-step on validation, one shot on the untouched test set), and enough seeds to see the variance: if the seed-to-seed spread is 0.004 AUC, a 0.002 difference means nothing. Also compare cost (train time, latency, model size), not just the headline metric. Mention data leakage — a suspiciously large jump is more often a leak than a breakthrough.
What is the difference between an experiment tracker and a model registry?▶
The tracker records what you tried — many runs, most of them discarded — and is optimized for comparison. The registry records what you serve — a small set of named, versioned, approved models with a lifecycle — and is optimized for governance and deployment. The link between them is lineage: every registered version points back to the run (and thereby the data and code) that produced it. Feature stores are a third, separate concern: they version the inputs.
Stages (Staging/Production) versus aliases (champion/challenger) — why did MLflow move toward aliases?▶
Stages are a fixed vocabulary of four, one meaning per model, which does not fit real workflows (shadow, canary, per-region champions, A/B challengers). Aliases are arbitrary named pointers to a version; you can move one atomically and have several per model, and deployment tooling just resolves models:/churn@champion. The promotion logic doesn't change — it's still gates deciding whether a pointer may move.
What gates would you require before a model reaches production?▶
A metric floor and a margin over the current production model (so noise doesn't cause churn), a passing validation suite (schema, slice/segment metrics — the worst segment, not only the average — fairness and bias checks where relevant), no open data-quality flags, a successful load and latency test, and a human approval for high-risk models. Return all failing reasons from the gate so the person fixing it isn't playing whack-a-mole. Then deploy gradually: shadow, canary, then full traffic.
A model you just promoted is misbehaving. Walk me through rolling back.▶
First, rollback must be fast and boring: the previous production version is still in the registry, its artifact is immutable, and the transition history says exactly which version it was, so it's a pointer move (or alias flip), not a rebuild. Keep the old version warm (still deployable, dependencies available). Watch the trap: if the new model needed new features or a changed schema, rolling back the model alone may break — the feature contract has to be compatible (or versioned together). Afterwards, record why in the history and add a test or gate so the failure can't recur silently.
How would you reproduce a model that has been in production for six months?▶
Look up the registry version and follow lineage: run id → data hash (fetch that exact snapshot from versioned storage), git SHA (check out that commit), params and seed, and the environment lock (rebuild the same container or venv). Re-run training and compare metrics to the recorded ones; small differences from non-deterministic GPU ops are normal, large ones mean something wasn't captured. If any link is missing, that's the finding — you fix the process so the next model has it.
MLflow versus Weights & Biases (or Neptune, Comet, SageMaker Experiments) — how do you choose?▶
MLflow is open source and self-hostable, has an integrated model registry and broad framework support — you control cost and data location but you run and secure the server. W&B and similar hosted tools have polished UIs, collaboration, reports and sweeps with little setup, at a per-seat price and with data leaving your network (or an enterprise self-host option). Decide on data-residency/compliance, team size and how much platform effort you can spend. The tracking discipline matters more than the tool, and wrapping the calls behind your own thin interface avoids lock-in.
Is there a downside to tracking too much?▶
Yes: storage and cost (large artifacts every run), slower training if logging is synchronous or per-step for huge models, noise that hides the signal, and sensitive data leaking into logs and artifacts (samples of PII, credentials in params). Log metrics at a sensible cadence, store big artifacts by reference plus checksum, log asynchronously, redact secrets, and set retention policies — keep everything for registered models, expire the rest.
