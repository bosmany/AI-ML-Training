1.2 — Recap: Linear Regression, Closed Form vs. Gradient Descent

For one feature and squared error, the best-fit line has an exact formula — no iteration required. It falls straight out of setting the derivative of the loss to zero (the same derivative rule from ch10): the slope is the covariance of x and y divided by the variance of x, and the intercept follows from the means.

closed-form-linear-regression.py
import numpy as np x = np.array([1.0, 2.0, 3.0, 4.0]) y = np.array([3.0, 5.0, 7.0, 9.0]) # true relationship: y = 2x + 1 x_mean, y_mean = x.mean(), y.mean() w = np.sum((x - x_mean) * (y - y_mean)) / np.sum((x - x_mean) ** 2) b = y_mean - w * x_mean print(f"w = {w:.3f}, b = {b:.3f}")

Gradient descent solves the exact same problem a different way: start anywhere, repeatedly nudge w and b opposite the gradient of the loss, and stop after enough steps. Same convention as ch10 — error = predictions - y, dw = (2/n) * sum(error * x), db = (2/n) * sum(error).

gradient-descent-linear-regression.py
import numpy as np x = np.array([1.0, 2.0, 3.0, 4.0]) y = np.array([3.0, 5.0, 7.0, 9.0]) w, b = 0.0, 0.0 learning_rate = 0.05 n = len(x) for step in range(500): predictions = w * x + b error = predictions - y dw = (2 / n) * np.sum(error * x) db = (2 / n) * np.sum(error) w -= learning_rate * dw b -= learning_rate * db print(f"w = {w:.3f}, b = {b:.3f}")

Both land on the same w = 2.000, b = 1.000. So why bother with the iterative version at all when the exact formula exists? Because the closed form is a special case: it only exists because squared error plus a linear model happens to have a solvable derivative. The moment you add a sigmoid (logistic regression) or a hidden layer (a neural net), there is no clean formula to solve for — gradient descent is the technique that still works. Exercise 1 asks you to reproduce this side-by-side comparison yourself, with the gradient formulas removed.

1.3 — Recap: Logistic Regression, From a Line to a Probability

Logistic regression keeps the same linear combination z = X @ w + b from linear regression, then squashes it through the sigmoid function so the output lands in (0, 1) and can be read as a probability.

sigmoid.py
import numpy as np def sigmoid(z): return 1 / (1 + np.exp(-z)) for z in [-4, -1, 0, 1, 4]: print(f"sigmoid({z}) = {sigmoid(z):.4f}")

The cost function changes too: instead of mean squared error, logistic regression minimizes log-loss (cross-entropy). This is not a stylistic choice. Squaring the error of a sigmoid output produces a loss surface with large FLAT regions whenever the model is confidently wrong — the gradient nearly vanishes exactly when you need it most. Log-loss keeps the gradient large in proportion to how wrong the confident prediction is, and it stays convex for this model, so gradient descent has a well-behaved surface to walk down. The elegant part: once you take the derivative through the sigmoid and the log-loss together, the gradient comes out in the exact same SHAPE as linear regression's — dw = (1/n) * X.T @ (predictions - y), db = (1/n) * sum(predictions - y). Same update rule, different predictions. Exercise 2 asks you to implement this entire pipeline — sigmoid, cost, gradients, training loop, evaluation — from a blank page, with only the dataset and the expected printed output given.

1.4 — Beyond Plain SGD: Momentum (and a Nod to Adam)

Plain SGD (what you just used twice above) follows the raw gradient every step, with one shared learning rate. That works fine when the loss surface is a nice round bowl. Real loss surfaces are usually ill-conditioned — steep in some directions, shallow in others — and a single learning rate that is safe for the steep direction is painfully slow for the shallow one. Momentum fixes this by keeping a running "velocity": instead of stepping by the raw gradient, you step by an exponentially-weighted average of recent gradients.

plain SGD vs. momentum, one parameter update
plain SGD:    w = w - lr * grad(w)

momentum:     v = beta * v - lr * grad(w)      # beta ~ 0.9: how much of the PAST velocity survives
              w = w + v

On a direction where the gradient keeps pointing the same way, velocity keeps accumulating and you travel further per step. On a direction where the gradient keeps flipping sign (the oscillating, steep direction), the flips partially cancel inside the running average, damping the oscillation instead of letting it dominate. Below is that effect on a deliberately ill-conditioned bowl — steep in one direction, shallow in the other — after the same fixed number of steps and the same learning rate for both:

momentum-vs-plain-sgd.py
import numpy as np def grad(w): return np.array([2.0 * w[0], 40.0 * w[1]]) # steep in w[1], shallow in w[0] lr = 0.02 w_plain = np.array([5.0, 5.0]) w_mom = np.array([5.0, 5.0]) v = np.zeros(2) beta = 0.85 for step in range(60): w_plain = w_plain - lr * grad(w_plain) v = beta * v - lr * grad(w_mom) w_mom = w_mom + v loss_plain = w_plain[0]**2 + 20*w_plain[1]**2 loss_mom = w_mom[0]**2 + 20*w_mom[1]**2 print(f"plain SGD loss after 60 steps: {loss_plain:.4f}") print(f"momentum loss after 60 steps: {loss_mom:.4f}")

Same 60 steps, same learning rate, and momentum ends up over a hundred times closer to the minimum. dl/ch22-intro-to-pytorch.html showed you torch.optim.Adam(...) as a one-line black box — the table below places it next to what you are about to build.

OptimizerUpdate ruleWhat it fixesExtra memory
Plain SGDw -= lr * gradNothing extra — one gradient, one stepNone
Momentumv = beta*v - lr*grad; w += vOscillation on ill-conditioned or noisy loss surfaces, by remembering recent directionOne velocity array per parameter
AdamTracks a running mean of the gradient AND of its square, then divides the step by the square root of that second momentDifferent parameters needing very different step sizes — the common case in deep, multi-layer networksTwo arrays per parameter

Exercise 3 gives you a working plain-SGD trainer and asks you to add the momentum block yourself, on a fresh ill-conditioned problem, and show the numbers proving it converges faster.

1.5 — Recap: Backpropagation, the Chain Rule Applied Twice

A tiny 2-layer network is: input x, a hidden layer (W1, b1, sigmoid), an output layer (W2, b2, sigmoid), then a loss comparing the output to the true label. Backprop walks that chain in reverse, applying the chain rule once to reach W2 (one hop: loss → output → W2) and again to reach W1 (two hops: loss → output → hidden → W1). Nothing new here versus ch21 — this is the recap, in the same notation, on one worked example so the shapes are fresh before exercise 4 makes you debug a broken version of it.

forward, then backward through the same two hops
FORWARD:   x --(W1,b1)--> z1 --sigmoid--> a1 --(W2,b2)--> z2 --sigmoid--> a2 --loss(a2,y)

BACKWARD (chain rule, twice):
  hop 1 (loss -> output -> W2):  d_z2 = d_loss/d_a2 * a2*(1-a2)      d_W2 = a1.T @ d_z2
  hop 2 (loss -> output -> hidden -> W1):
                                  d_a1 = d_z2 @ W2.T
                                  d_z1 = d_a1 * a1*(1-a1)
                                  d_W1 = x.T @ d_z1
backprop-one-example.py
import numpy as np def sigmoid(z): return 1 / (1 + np.exp(-z)) x = np.array([0.5, 0.8]) w1 = np.array([0.3, -0.2]) # one hidden unit, two inputs w2 = 0.6 # one output unit, one hidden unit y_true = 1.0 z1 = np.dot(x, w1); a1 = sigmoid(z1) z2 = a1 * w2; a2 = sigmoid(z2) loss = (a2 - y_true) ** 2 d_loss_d_a2 = 2 * (a2 - y_true) d_a2_d_z2 = a2 * (1 - a2) # hop 1 d_loss_d_w2 = d_loss_d_a2 * d_a2_d_z2 * a1 d_z2_d_a1 = w2 # hop 2 starts here d_a1_d_z1 = a1 * (1 - a1) d_loss_d_w1 = d_loss_d_a2 * d_a2_d_z2 * d_z2_d_a1 * d_a1_d_z1 * x print(f"a1 = {a1:.4f}, a2 = {a2:.4f}, loss = {loss:.4f}") print(f"d_loss/d_w2 = {d_loss_d_w2:.4f}") print(f"d_loss/d_w1 = {d_loss_d_w1}")

Notice d_loss_d_w1 is a longer product than d_loss_d_w2 — it carries every factor from both hops. Miss one factor (say, the local sigmoid derivative at the hidden layer) and the gradient reaching W1 is simply wrong, even though nothing crashes. Get an orientation wrong (a transpose in the wrong place) and NumPy usually crashes loudly with a shape error instead. Exercise 4 hands you a version with the second kind of bug.

1.6 — Assembling One Trainer: Forward + Backward + Optimizer

Every "from scratch" trainer you will ever write — here, or a real one in PyTorch under the hood — is the same three-part loop, no matter how many layers or which optimizer: predict, work out who caused how much error, then decide how to use that information to move the parameters.

the whole trainer, three parts, one loop
for epoch in range(epochs):
    a1, a2      = forward(X, W1, b1, W2, b2)      # 1. predict
    grads       = backward(X, y, a1, a2, W2)      # 2. chain rule: who caused the error, how much
    W1,b1,W2,b2 = update(params, grads, velocity)  # 3. SGD, momentum, or Adam decides HOW to apply it

Section 1.2's gradient descent IS update() for plain SGD. Section 1.4's momentum block IS a different update(). Section 1.5's chain rule IS backward(). Nothing in exercise 5 or the Project is a new idea — it is exactly these three pieces, wired together, run until the loss reaches a target and held out on data the trainer never saw.

🧪 Classical Foundations Quiz

5 questions testing WHY each piece works, not just whether your code ran. You need 4/5 (80%) to pass. Retake as often as you like.

Score: 0/5
Question 1 of 5
Simple linear regression has an exact closed-form solution — no loop required. Why bother with gradient descent at all for this family of problems?
Why: Both methods find the exact same optimum here — neither is "more accurate," and the closed form does generalize to multiple features (via a matrix normal equation). What it does NOT generalize to is any model where the loss/model combination has no clean derivative to solve for zero, which is every model past this one.
Question 2 of 5
Logistic regression minimizes log-loss (cross-entropy), not mean squared error, even though both could technically be computed on a sigmoid output. Why is log-loss the correct choice?
Why: The problem is specifically the sigmoid+MSE combination's vanishing-gradient behavior near confident-wrong predictions, not classification in general and not raw operation count. Log-loss's gradient through a sigmoid simplifies to exactly (prediction - label), which stays large until the prediction is actually correct.
Question 3 of 5
On the ill-conditioned bowl in section 1.4, momentum reached a loss over a hundred times lower than plain SGD after the identical number of steps and the identical learning rate. What mechanism causes this?
Why: There is no randomness in this example — both trainers are fully deterministic, so it is not a seed coincidence. Momentum never computes second derivatives (that would be a Newton or quasi-Newton method, meaningfully more expensive); it only keeps a first-moment running average of the gradient itself.
Question 4 of 5
In exercise 4, the broken backprop implementation raised ValueError: operands could not be broadcast together with shapes (2,4) (4,2) (2,4) on the very first epoch instead of quietly training to a wrong answer. Why is that actually useful?
Why: A silent wrong answer (the exercise 5 kind of missing-term bug) is strictly harder to find than a crash, because nothing points you at a line. A shape-mismatch crash is the friendlier bug precisely because the traceback and the shapes in the message narrow the search immediately.
Question 5 of 5
Suppose you forget to multiply by a1 * (1 - a1) when computing d_z1 from d_a1 in a sigmoid hidden layer (i.e. you propagate the raw upstream gradient straight through, skipping that one local-derivative factor). Predict what happens to training, and how this differs from exercise 4's bug.
Why: This is exactly the missing-chain-rule-term bug, and its signature is the opposite of exercise 4's: shapes stay consistent (no crash) but the numbers are quietly wrong, since a1*(1-a1) is a real, required factor in the chain rule — not an optional tuning knob — for both W1 and b1.
