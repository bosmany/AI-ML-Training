2.2 — Recap: Scaled Dot-Product Attention

Ch25 §25.3–25.4 built this in full: three learned projections of each token's embedding — Q = X @ W_Q, K = X @ W_K, V = X @ W_V — then Attention(Q,K,V) = softmax(Q @ K.T / sqrt(d_model)) @ V. The division by sqrt(d_model) keeps the dot-product scores from growing too large as dimensionality increases, which would otherwise push softmax into an overly peaked, badly-behaved regime. That single formula, plus a numerically-stable softmax, is the entire mechanism. Exercise 1 gives you nothing but a numpy array of token embeddings, three weight matrices, and the exact printed output your implementation must reproduce — no formula written out in the task itself, no partial code. If you find yourself unsure of an ordering or a shape, that is the signal to re-read §25.4 rather than guess.

2.3 — Recap: The Full Transformer Block — Given, Working, Reused

Ch25 §25.7–25.9 built residual connections (x + Sublayer(x), giving gradients an unobstructed path through depth), Layer Normalization (per-token re-centering/re-scaling, gamma/beta learned), and assembled both into one reusable TransformerBlock: multi-head attention wrapped in a residual + LayerNorm, then a position-wise feed-forward network wrapped in its own residual + LayerNorm. That class's FINAL form — the one ch25 ends on — is reproduced below exactly, and it is the reference every remaining exercise in this chapter reuses. Read it once, run it, and treat it as a black box you can call, the same way you'd treat a well-tested library function on the job.

the given, working Transformer block (from ch25 §25.9, reused verbatim)
import numpy as np def softmax(x, axis=-1): e = np.exp(x - np.max(x, axis=axis, keepdims=True)) return e / np.sum(e, axis=axis, keepdims=True) def layer_norm(x, gamma, beta, eps=1e-5): mean = x.mean(axis=-1, keepdims=True); var = x.var(axis=-1, keepdims=True) return gamma * (x - mean) / np.sqrt(var + eps) + beta def multi_head_attention(X, WQ, WK, WV, WO, num_heads, mask=None): seq_len, d_model = X.shape; head_dim = d_model // num_heads Q, K, V = X @ WQ, X @ WK, X @ WV def split(M): return M.reshape(seq_len, num_heads, head_dim).transpose(1, 0, 2) Qh, Kh, Vh = split(Q), split(K), split(V) scores = Qh @ Kh.transpose(0, 2, 1) / np.sqrt(head_dim) if mask is not None: scores = np.where(mask, scores, -1e9) out = (softmax(scores, axis=-1) @ Vh).transpose(1, 0, 2).reshape(seq_len, d_model) return out @ WO def feed_forward(x, W1, b1, W2, b2): return np.maximum(0, x @ W1 + b1) @ W2 + b2 class TransformerBlock: def __init__(self, d_model, num_heads, d_ff, seed): rng = np.random.RandomState(seed); self.num_heads = num_heads self.WQ = rng.randn(d_model, d_model)*0.1; self.WK = rng.randn(d_model, d_model)*0.1 self.WV = rng.randn(d_model, d_model)*0.1; self.WO = rng.randn(d_model, d_model)*0.1 self.W1 = rng.randn(d_model, d_ff)*0.1; self.b1 = np.zeros(d_ff) self.W2 = rng.randn(d_ff, d_model)*0.1; self.b2 = np.zeros(d_model) self.g1 = np.ones(d_model); self.bt1 = np.zeros(d_model) self.g2 = np.ones(d_model); self.bt2 = np.zeros(d_model) def forward(self, X, mask=None): X = layer_norm(X + multi_head_attention(X, self.WQ, self.WK, self.WV, self.WO, self.num_heads, mask), self.g1, self.bt1) return layer_norm(X + feed_forward(X, self.W1, self.b1, self.W2, self.b2), self.g2, self.bt2) np.random.seed(0) X_demo = np.random.randn(3, 8) * 0.1 block_demo = TransformerBlock(d_model=8, num_heads=2, d_ff=16, seed=1) out_demo = block_demo.forward(X_demo) print(f'Input shape: {X_demo.shape}') print(f'Output shape: {out_demo.shape}') print(f'Row means (LayerNorm always renormalizes to ~0): {[round(float(v),4) for v in out_demo.mean(axis=1)]}')

Notice the last printed line: every row's mean comes out ~0 regardless of what went in, because LayerNorm renormalizes ANY input to zero mean / unit variance per row. Keep that in mind for exercise 2 — a summary statistic like "row mean is ~0" being correct tells you almost nothing about whether the code that produced it was wired correctly, since LayerNorm would produce that same clean statistic even from a broken input.

2.4 — Recap: Causal Masking, and Token Embeddings as a Lookup Table

Ch25 §25.10 showed that encoder-only (bidirectional), decoder-only (causal), and encoder-decoder architectures are all the SAME Transformer block — the only difference is which mask, if any, gets passed into multi_head_attention. A causal mask (np.tril of ones) blocks every position from attending to anything after it, which is exactly the constraint "predict the next token from everything before it" requires; that single mechanical trick is why one architecture (decoder-only) can both train and generate. Exercise 3 reuses causal_mask and positional_encoding exactly as given in ch25 — nothing new to build there, only to wire correctly.

Ch25 §25.2 (and nlp/ch27-nlp-fundamentals.html) covered embeddings: a token is an integer index, and looking it up is nothing more than embedding_table[index] — fancy indexing into a matrix where row i is that token's learned vector. Exercise 4 makes the alternative concrete: a one-hot vector (all zeros except a single 1) is also a valid way to represent a token, but its width equals the vocabulary size and every one-hot vector is exactly the same distance from every other — no learned structure at all. A dense embedding is small, fixed-width, and — once trained — encodes real similarity between tokens. The lookup mechanics are identical between the two; what differs is only which table you're indexing into.

2.5 — Recap: Framework-Free RAG, and the Gap Ch35 Left Open

Ch35's RagChatbot built a complete, real, framework-free RAG pipeline: tokenize/remove_stop/tf/idf/cosine_sim to build TF-IDF vectors over a knowledge base, embed_query to vectorize an incoming question the same way, build_prompt to insert the retrieved text into a template string, a mock generation step, and a similarity-threshold health check. That machinery is not repeated here. But look closely at ch35's knowledge base: every "document" is already a single short sentence. Nothing in that pipeline ever splits a LONG document into smaller pieces before retrieving over it — ch35's own interview-prep material even flags this explicitly as a real production concern it deliberately didn't implement.

why a long document needs chunking before retrieval
one long document, embedded whole:
  [topic A ... topic B ... topic C ... topic D]  -->  ONE vague vector
  a query about topic B matches this vector only a little -- diluted by A, C, D

the same document, chunked into overlapping windows:
  [A A A][A A B B B][B B B C C][C C C D D D]        (each bracket = one chunk)
  a query about topic B now matches ONE sharp, focused chunk vector

Exercise 5 fills exactly that gap: given raw multi-sentence documents and a query, you implement chunking (splitting each document into fixed-size, overlapping windows of words), a simple bag-of-words retrieval step (score every chunk against the query by dot product, keep the highest), and prompt assembly — with nothing scaffolded but the documents, the query, and the exact expected output. It deliberately varies from ch35 rather than repeating it: different corpus, a genuinely new chunking step, and a simpler dot-product score instead of full TF-IDF, so you are writing real retrieval logic yourself rather than recalling ch35's exact lines.

Two design knobs matter here, and they're the same two ch35's own interview-prep material calls out as real production tradeoffs. Chunk size: too small and a chunk loses the surrounding context needed to make sense of a matched sentence; too large and you're back to the dilution problem the diagram above shows. Overlap: a chunk boundary that lands in the middle of the one sentence that actually answers the query silently splits the evidence across two weaker chunks; a few words of overlap between consecutive windows makes that far less likely at the cost of storing (and scoring) somewhat more chunks. Exercise 5 fixes both knobs (chunk_size=5, overlap=2) so the output is exactly reproducible, but the underlying tradeoff is real and the same one a production system has to tune empirically.

Question 1 of 5
In exercise 2, the BUGGY block (missing both residual adds) still ran without crashing, and its output rows still had mean ~0 and std ~1, identical to the correct version. Why does that NOT prove the wiring was correct?
Why: LayerNorm's whole job is producing that exact per-row mean/std regardless of its input, so it is structurally incapable of exposing this particular bug. The bug is silent precisely because nothing crashes and no summary statistic changes — only the actual numbers do, which is why exercise 2 checks exact rounded values, not shape or mean/std.
Question 2 of 5
Exercise 2's block was tested with mask=None (bidirectional attention), while exercise 3's mini forward pass uses a real causal mask. Why is that difference correct, not an inconsistency?
Why: This is ch25 SS25.10's whole point restated: encoder-only, decoder-only and encoder-decoder are the SAME block, distinguished only by the mask argument. mask=None and a causal mask produce very different outputs (bidirectional vs. restricted attention) — they are not interchangeable, they are just both valid depending on what the code is testing.
Question 3 of 5
A colleague suggests skipping dense embeddings entirely and just using one-hot vectors for a vocabulary of 50,000 words, reasoning "the lookup code is identical either way." What's wrong with that reasoning?
Why: The colleague is right that the lookup mechanics (fancy indexing into a table) are identical -- that part of exercise 4 is deliberately the same code for both. What differs is entirely which table: a 50,000-wide sparse, structureless one vs. a small dense, learnable one.
Question 4 of 5
Ch35's RAG knowledge base never needed chunking. What specific retrieval failure does exercise 5's chunking step fix that ch35 never encountered?
Why: This mirrors ch35's own interview-prep answer on chunking tradeoffs almost exactly: dilution is the failure mode, and it only shows up once a "document" can span multiple topics -- which ch35's short, single-topic knowledge base never did.
Question 5 of 5
The Project's every shape check and row-sum check passes, and it prints a confident "Predicted tokens" list. Why is that predicted list meaningless as an actual answer to the query, even though nothing is broken?
Why: This is exactly ch25's own closing warning restated: a forward pass is not a trained model. Retrieval and chunking are correct and the math is exactly what a real GPT-family model runs -- what's missing is the billions of gradient steps that would make the weights (and therefore the predictions) actually reflect language.
