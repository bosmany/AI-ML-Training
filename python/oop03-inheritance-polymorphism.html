3.1 — The Problem: Copy-Pasting Classes

In the first two OOP parts you learned to write a class, which is a blueprint, and to build objects from it, which are the actual things made from that blueprint. You know that __init__ runs once when an object is created and stores its starting data as attributes (values that belong to the object). You know that a method is a function that lives inside a class, and that self is the object the method is working on. From Part 2 you also know that special methods such as __str__ control how an object looks when printed. Here is a quick reminder in one small class.

Recap: one class, one object
class Dog: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" def speak(self): return f"{self.name} says Woof!" rex = Dog("Rex", 3) print(rex.describe()) print(rex.speak()) print(vars(rex))
Output
Rex is 3 years old Rex says Woof! {'name': 'Rex', 'age': 3}

In the last line, vars(rex) shows the attributes an object currently stores, as a dictionary. We will use it often in this chapter to look inside objects.

Now imagine you are writing software for an animal shelter. The shelter takes in dogs, cats and birds. Every animal has a name and an age. Every animal can describe itself and can make a sound. Only the sound is different. You already know how to write a class, so the natural thing to do is write one class for each kind of animal. Copy the Dog class, paste it twice, and change a few words. Try it.

Three classes, copy-pasted
class Dog: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" def speak(self): return f"{self.name} says Woof!" class Cat: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" def speak(self): return f"{self.name} says Meow!" class Bird: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" def speak(self): return f"{self.name} says Tweet!" for pet in [Dog("Rex", 3), Cat("Mimi", 2), Bird("Kiwi", 1)]: print(pet.describe(), "|", pet.speak())
Output
Rex is 3 years old | Rex says Woof! Mimi is 2 years old | Mimi says Meow! Kiwi is 1 years old | Kiwi says Tweet!

It works, and for a moment it feels fine. Look closely at the code, though. Each class has eight lines, and six of them are word-for-word the same in all three classes. Only the class name and the sound change. That is what programmers mean by duplication: the same idea written down in several places.

The same shape, three times
   Dog                  Cat                  Bird
 +---------------+   +---------------+   +---------------+
 | __init__      |   | __init__      |   | __init__      |
 | describe      |   | describe      |   | describe      |
 | speak: Woof   |   | speak: Meow   |   | speak: Tweet  |
 +---------------+   +---------------+   +---------------+
    identical           identical           identical
   (2 methods)         (2 methods)         (2 methods)
   only "speak" is different in each box
Two of the three methods are copies. Only the sound changes from class to class.
Why duplication hurts

Copy-paste hides its cost until the first change. Suppose a volunteer points out a bug: a one-year-old animal is described as "1 years old", which sounds wrong. You fix it in Dog. Then the phone rings, you get distracted, and you never fix Cat or Bird. Run the next block and read the output carefully.

The bug is fixed in one place only
class Dog: def __init__(self, name, age): self.name = name self.age = age def describe(self): unit = "year" if self.age == 1 else "years" # the fix return f"{self.name} is {self.age} {unit} old" class Cat: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" # still has the bug print(Dog("Rex", 1).describe()) print(Cat("Mimi", 1).describe())
Output
Rex is 1 year old Mimi is 1 years old

The two animals now disagree, and nothing in Python warns you. With three classes that is annoying. With thirty species it becomes a real problem, because every fix must be repeated thirty times and you will eventually miss one. Programmers have a rule for this called DRY, short for "Don't Repeat Yourself". Each piece of knowledge should live in exactly one place.

Another way copy-paste fails

Copying also goes wrong when you forget to copy something. Here a Bird class was written from memory instead of pasted, and the describe method was left out. Python only finds out when you call the missing method.

Forgot to copy a method
class Bird: def __init__(self, name, age): self.name = name self.age = age def speak(self): return f"{self.name} says Tweet!" kiwi = Bird("Kiwi", 1) print(kiwi.speak()) print(kiwi.describe())
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 10, in <module> print(kiwi.describe()) ^^^^^^^^^^^^^ AttributeError: 'Bird' object has no attribute 'describe'

Read a traceback from the bottom up. The last line, AttributeError: 'Bird' object has no attribute 'describe', is the actual complaint: the object has no such attribute. The line above it shows where it happened: line 10, the call to describe, and the ^^^^ marks underline the exact part Python could not do. Everything above is the path Python took to get there (here it is short, because the mistake is in the main program, which Python calls <module>). In a large copy-pasted program, this error is easy to trigger because each class must be kept complete by hand.

The idea: write shared code once

What we want is one place that says "every animal has a name and an age, and every animal can describe itself", plus a small extra piece for each species that says only what makes it different. Think of a family recipe book. The base recipe for bread lives on one page. The page for raisin bread says "make the base bread, then add raisins". You never copy the base recipe; you point back to it. If grandma improves the base recipe, every bread that points to it improves too.

Python's version of this is called inheritance. You do not need to understand every detail yet. Here is a preview so you can see the shape of the solution.

Preview: shared code written once
class Animal: def __init__(self, name, age): self.name = name self.age = age def describe(self): unit = "year" if self.age == 1 else "years" return f"{self.name} is {self.age} {unit} old" class Dog(Animal): def speak(self): return f"{self.name} says Woof!" class Cat(Animal): def speak(self): return f"{self.name} says Meow!" for pet in [Dog("Rex", 1), Cat("Mimi", 2)]: print(pet.describe(), "|", pet.speak())
Output
Rex is 1 year old | Rex says Woof! Mimi is 2 years old | Mimi says Meow!

Notice three things. Dog and Cat contain no __init__ and no describe, yet Dog("Rex", 1) works and can describe itself. The bug fix lives in one place, Animal, and both animals get it. And the only code inside Dog and Cat is the part that is genuinely different. The rest of this chapter explains exactly how that works and how to use it safely.

Try it.
Check yourself: in the copy-pasted shelter program, you find a bug in describe. How many classes must you edit, and what could go wrong?

You must edit every class that contains a copy of describe, which is all three of them. What can go wrong is that you forget one (or fix it slightly differently in each), so the classes quietly disagree. That is why the DRY rule says to keep each idea in a single place.

Check yourself: what does AttributeError: 'Bird' object has no attribute 'describe' tell you?

It says you asked a Bird object for something named describe, and neither the object nor its class has anything with that name. Usually the method was never written, was misspelled, or was left behind when code was copied.

Recap
  • Duplication means the same code written in several places; fixing a bug then requires several edits and it is easy to miss one.
  • The DRY rule (Don't Repeat Yourself) says every idea should live in one place.
  • Three near-identical classes (Dog, Cat, Bird) differ only in their sound, yet copy-paste repeats everything else.
  • Inheritance lets a class reuse another class's code; class Dog(Animal) gives Dog everything Animal has.
  • Read tracebacks from the bottom line upward: the last line names the error, the lines above show where it happened.
3.2 — The is-a Relationship and class Dog(Animal)

To decide when two classes should be linked, programmers use a simple sentence test. Say it out loud: "A Dog is an Animal." That sentence is true, so Dog is a good candidate to build on Animal. Now try "A Car is an Engine." That sentence is false, because a car has an engine inside it but is not one. So a Car should not be built on an Engine. (Objects that contain other objects are the topic of OOP Part 4.) This test is called the is-a relationship.

Think of a family tree. A child inherits features from a parent: eye colour, a family name, maybe a talent for music. The child does not ask for these; they arrive automatically. Python classes work the same way. The class you build on is called the parent class (also base class or superclass). The class that builds on it is the child class (also subclass or derived class). All these names mean the same thing, and you will meet all of them in documentation, so it is worth learning them now.

An inheritance tree
                 +-----------+
                 |  Animal   |    <- parent (base class, superclass)
                 |  __init__ |
                 |  describe |
                 +-----------+
                  ^    ^    ^
        is-a      |    |    |      is-a
       +----------+    |    +----------+
       |               |               |
  +---------+     +---------+     +---------+
  |   Dog   |     |   Cat   |     |  Bird   |   <- children (subclasses)
  |  speak  |     |  speak  |     |  speak  |
  +---------+     +---------+     +---------+
The arrows point UP from child to parent, because a child knows who its parent is. A parent knows nothing about its children.
The syntax

You write the parent's name in parentheses after the child's name. That is the whole syntax. Here is the smallest useful example.

The smallest inheritance example
class Animal: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" class Dog(Animal): # Dog is built on Animal pass # nothing new yet rex = Dog("Rex", 3) print(rex.describe()) print(vars(rex))
Output
Rex is 3 years old {'name': 'Rex', 'age': 3}

The word pass means "nothing goes here". Dog is completely empty, yet Dog("Rex", 3) works and rex.describe() works. The child received everything the parent has.

What Python does, line by line

It is worth understanding exactly how the empty Dog managed this, because every later section builds on it.

  1. You write Dog("Rex", 3). Python creates a brand-new, empty Dog object.
  2. Python needs to run __init__. It first looks inside the Dog class for a method named __init__. There is none.
  3. So it moves up one step to the parent and looks inside Animal. It finds __init__ there.
  4. Python calls Animal.__init__, passing the new object as self, plus "Rex" and 3. The attributes name and age are stored on the new Dog object.
  5. Later, rex.describe() follows the same search: not in Dog, found in Animal, called with self being rex.

You can check this with your own eyes. Every class keeps a dictionary of the things defined directly inside it, and __dict__ lets you look at that dictionary. The is operator tells us whether two names point at exactly the same thing.

Proof that Dog borrows from Animal
class Animal: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" class Dog(Animal): pass print("init defined inside Dog? ", "__init__" in Dog.__dict__) print("init defined inside Animal?", "__init__" in Animal.__dict__) print("Same function object? ", Dog.__init__ is Animal.__init__) print("Dog's parents:", [b.__name__ for b in Dog.__bases__])
Output
init defined inside Dog? False init defined inside Animal? True Same function object? True Dog's parents: ['Animal']

There is no copy. Dog and Animal share one single __init__ function. That is exactly what DRY asks for.

Children can add, parents cannot borrow

A child is allowed to have extra methods that the parent does not have. A dog can fetch a ball; a generic animal cannot. The relationship only goes one way.

A child adds its own method
class Animal: def __init__(self, name, age): self.name = name self.age = age class Dog(Animal): def fetch(self): return f"{self.name} brings the ball back" class Cat(Animal): pass print(Dog("Rex", 3).fetch()) for pet in [Animal("Generic", 1), Cat("Mimi", 2)]: print(type(pet).__name__, "can fetch?", hasattr(pet, "fetch"))
Output
Rex brings the ball back Animal can fetch? False Cat can fetch? False

The built-in hasattr(obj, "name") answers "does this object have something called name?" with True or False. Only Dog objects can fetch. Animal and Cat cannot.

isinstance and issubclass

Because a Dog is an Animal, Python lets you ask that question directly. isinstance(obj, SomeClass) asks whether the object was made from that class or from any class built on it. issubclass(A, B) asks the same question about two classes.

Asking is-a questions in code
class Animal: pass class Dog(Animal): pass class Cat(Animal): pass rex = Dog() print(isinstance(rex, Dog)) # made from Dog print(isinstance(rex, Animal)) # Dog is an Animal too print(isinstance(rex, Cat)) # not a Cat print(issubclass(Dog, Animal)) # class vs class print(issubclass(Animal, Dog)) # the arrow only goes one way print(type(rex) == Animal) # type() is exact, no family
Output
True True False True False False

Notice the last line. type(rex) reports only the exact class, Dog, so it is not equal to Animal. isinstance understands families. That difference matters, and it is why isinstance is the usual tool.

Common mistakes

Mistake 1: forgetting the parentheses. If you write class Dog: and skip (Animal), you have written an unrelated class. It inherits nothing, so the arguments you give it have nowhere to go.

Forgot (Animal)
class Animal: def __init__(self, name, age): self.name = name self.age = age class Dog: # oops: no (Animal) pass rex = Dog("Rex", 3)
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 9, in <module> rex = Dog("Rex", 3) ^^^^^^^^^^^^^ TypeError: Dog() takes no arguments

The message TypeError: Dog() takes no arguments means: Dog has no __init__ of its own and inherited none, so Python used a default one that accepts nothing. Fix it by writing class Dog(Animal):.

**Mistake 2: swapping the arguments of isinstance.** The object comes first and the class second, like the sentence "rex is a Dog".

isinstance arguments in the wrong order
class Animal: pass class Dog(Animal): pass rex = Dog() print(isinstance(Dog, rex))
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 4, in <module> print(isinstance(Dog, rex)) ^^^^^^^^^^^^^^^^^^^^ TypeError: isinstance() arg 2 must be a type, a tuple of types, or a union

Python tells you exactly what it expected: the second argument must be a type. Swap them and it works.

Try it.
Check yourself: is "A Library is a Book" a good candidate for inheritance? What about "A Novel is a Book"?

"A Library is a Book" is false: a library contains books but is not one. It should not inherit from Book. "A Novel is a Book" is true, so class Novel(Book) is a sensible design.

Check yourself: rex = Dog("Rex", 3) where Dog(Animal) is empty. Where does Python find __init__?

It looks in Dog first and finds nothing, then looks in the parent Animal and finds it there. It runs Animal.__init__ with rex as self.

Recap
  • The is-a test ("a Dog is an Animal") decides whether inheritance makes sense.
  • class Dog(Animal) makes Animal the parent (base class, superclass) and Dog the child (subclass).
  • The child receives every attribute and method of the parent automatically; there is no copying, only a search that moves up the tree.
  • Children may add methods; parents never receive them.
  • isinstance(obj, Class) respects families; type(obj) == Class does not. issubclass(A, B) compares two classes.
3.3 — super(): Letting the Child Call the Parent

So far Dog has been empty. Real children are rarely empty. A dog has a breed, and Animal knows nothing about breeds. So we give Dog its own __init__ that also accepts a breed. This looks reasonable. Run it and see what goes wrong.

A child __init__ that ignores the parent
class Animal: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" class Dog(Animal): def __init__(self, name, age, breed): self.breed = breed rex = Dog("Rex", 3, "Beagle") print(rex.breed) print(rex.describe())
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 15, in <module> print(rex.describe()) ^^^^^^^^^^^^^^ File "<exec>", line 7, in describe return f"{self.name} is {self.age} years old" ^^^^^^^^^ AttributeError: 'Dog' object has no attribute 'name'

The first print works and shows Beagle. The second one fails. This is a traceback with two frames, so let us read it slowly. Read from the bottom. The last line says AttributeError: 'Dog' object has no attribute 'name'. The frame immediately above it says the failure happened inside describe, on the line return f"{self.name} ...". The frame above that says describe was called from your print(rex.describe()). So the real question is: why does the Dog object have no name? Because nobody ever ran the line self.name = name.

Why the parent's __init__ disappeared

Recall the search from section 3.2: Python looks in the child first and only moves up if it finds nothing. Now Dog does define __init__, so Python finds it immediately and stops looking. The parent's __init__ still exists, but it never runs, because the child's version came first in the search. Nothing is broken in Animal; the child's method is hiding it. (Section 3.4 calls this overriding.)

We need a way for the child to say: "first let my parent do its setup, then I will add my own bits." That way is super(). Think of it as a phone line straight to the parent class. super().__init__(name, age) means "call my parent's __init__ and give it these arguments."

The fix, with prints to watch it happen
class Animal: def __init__(self, name, age): print(" Animal.__init__ starts. self has:", vars(self)) self.name = name self.age = age print(" Animal.__init__ ends. self has:", vars(self)) class Dog(Animal): def __init__(self, name, age, breed): print("Dog.__init__ starts. self has:", vars(self)) super().__init__(name, age) self.breed = breed print("Dog.__init__ ends. self has:", vars(self)) rex = Dog("Rex", 3, "Beagle")
Output
Dog.__init__ starts. self has: {} Animal.__init__ starts. self has: {} Animal.__init__ ends. self has: {'name': 'Rex', 'age': 3} Dog.__init__ ends. self has: {'name': 'Rex', 'age': 3, 'breed': 'Beagle'}

Look at the printed dictionaries. vars(self) shows the attributes stored on the object at that moment. It starts empty, Animal.__init__ fills in name and age, and finally Dog.__init__ adds breed.

What Python does, line by line
  1. You write Dog("Rex", 3, "Beagle"). Python creates an empty Dog object. Its attribute dictionary is {}.
  2. Python looks for __init__ and finds the one inside Dog. It calls it with self set to the new object, plus "Rex", 3 and "Beagle".
  3. The first line of Dog.__init__ prints an empty dictionary, which proves nothing has been stored yet.
  4. Then comes super().__init__(name, age). super() means "the parent class, but working on this same object". Python jumps into Animal.__init__, with the same self, and name="Rex", age=3.
  5. Animal.__init__ stores self.name and self.age, then returns. Python goes back to where it left off inside Dog.__init__.
  6. Dog.__init__ continues with self.breed = breed and finishes. The finished object has all three attributes.
The chain of calls
 Dog("Rex", 3, "Beagle")       object created, self = { }
      |
      v
 Dog.__init__ starts
      |
      |  super().__init__(name, age)      jump to the parent
      v
   Animal.__init__ runs         self = { name, age }
      |
      |  returns                          back to the child
      v
 Dog.__init__ continues
      |  self.breed = breed
      v
 finished object                self = { name, age, breed }
One object, one self. Both __init__ methods write onto the same object; the parent's runs first, then control returns to the child.

The important detail is that self is the same object all the way through. The parent does not build a separate parent object. It writes its attributes onto the one Dog object that is being created.

Variations

Calling the parent by name. Before super() was popular, people wrote the parent's name explicitly, passing self by hand. It works, and you will see it in older code.

The older, explicit way
class Animal: def __init__(self, name, age): self.name = name self.age = age class Dog(Animal): def __init__(self, name, age, breed): Animal.__init__(self, name, age) # explicit parent name, explicit self self.breed = breed rex = Dog("Rex", 3, "Beagle") print(vars(rex))
Output
{'name': 'Rex', 'age': 3, 'breed': 'Beagle'}

Prefer super(). It does not repeat the parent's name, so renaming the parent later touches fewer lines, and it keeps working in the more advanced situations of section 3.8.

A child that needs fewer arguments. The child does not have to accept the same arguments as the parent. A Puppy might always be zero years old, so it asks only for a name and passes 0 upward itself.

The child decides what to pass upward
class Animal: def __init__(self, name, age): self.name = name self.age = age class Puppy(Animal): def __init__(self, name): super().__init__(name, 0) # the age is always 0 pup = Puppy("Bit") print(vars(pup)) print(isinstance(pup, Animal))
Output
{'name': 'Bit', 'age': 0} True
Common mistakes

**Mistake 1: forgetting super().__init__() entirely.** This is the error at the top of this section: AttributeError: 'Dog' object has no attribute 'name'. It appears later, at the moment something reads the missing attribute, not at the moment you forgot. That gap makes it confusing. When a child class has its own __init__ and an attribute the parent should have set is missing, check for super().__init__ first.

You can catch this mistake by comparing what each object actually stores. sorted(vars(obj)) lists the attribute names in alphabetical order.

Spot the missing attributes
class Animal: def __init__(self, name, age): self.name = name self.age = age class Good(Animal): def __init__(self, name, age, breed): super().__init__(name, age) self.breed = breed class Bad(Animal): def __init__(self, name, age, breed): self.breed = breed # no super() call for cls in (Good, Bad): obj = cls("Rex", 3, "Beagle") print(cls.__name__, sorted(vars(obj)))
Output
Good ['age', 'breed', 'name'] Bad ['breed']

Mistake 2: giving the parent too few arguments. Animal.__init__ needs two values. If the child forgets one, Python names the missing one.

Not enough arguments passed upward
class Animal: def __init__(self, name, age): self.name = name self.age = age class Dog(Animal): def __init__(self, name, age, breed): super().__init__(name) # forgot age self.breed = breed rex = Dog("Rex", 3, "Beagle")
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 11, in <module> rex = Dog("Rex", 3, "Beagle") ^^^^^^^^^^^^^^^^^^^^^^^ File "<exec>", line 8, in __init__ super().__init__(name) # forgot age ^^^^^^^^^^^^^^^^^^^^^^ TypeError: Animal.__init__() missing 1 required positional argument: 'age'

Read the last line: TypeError: Animal.__init__() missing 1 required positional argument: 'age'. The frame above shows the line inside Dog.__init__ that made the call. So the bug is in Dog, even though the complaint names Animal.

**Mistake 3: passing self yourself to super().** With super() Python supplies self automatically. Writing super().__init__(self, name, age) sends four values to a method expecting three.

Passing self twice
class Animal: def __init__(self, name, age): self.name = name self.age = age class Dog(Animal): def __init__(self, name, age): super().__init__(self, name, age) # self is already passed rex = Dog("Rex", 3)
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 10, in <module> rex = Dog("Rex", 3) ^^^^^^^^^^^^^ File "<exec>", line 8, in __init__ super().__init__(self, name, age) # self is already passed ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ TypeError: Animal.__init__() takes 3 positional arguments but 4 were given

The message says the method "takes 3 positional arguments but 4 were given". Count them: self, name, age are three; the extra self you typed makes four. The fix is to delete that extra self.

Try it.
Check yourself: a child class defines its own __init__ but never calls super().__init__. Does the parent's __init__ run anyway?

No. Python runs the first __init__ it finds, which is the child's. The parent's __init__ stays unused unless the child calls it with super().__init__(...).

Check yourself: in Dog.__init__, is self the same object inside the Animal.__init__ call?

Yes. super() does not create a new object; it calls the parent's method on the same self. That is why the attributes the parent sets end up on the Dog object.

Recap
  • If a child defines __init__, Python uses it and does not run the parent's automatically.
  • super().__init__(...) calls the parent's __init__ on the same object; call it first in the child's __init__.
  • The trace: create empty object, child __init__ starts, parent __init__ fills in its attributes, control returns, child adds its own.
  • AttributeError: 'Dog' object has no attribute 'name' after a custom __init__ usually means super().__init__ is missing.
  • Do not pass self to super().__init__; do pass every argument the parent needs.
3.4 — Overriding and Extending Methods

Inheritance gives a child everything the parent has. But sometimes the child needs to do one of those inherited things differently. For this section we leave the animal shelter and use a bank, because money rules make the difference clear. Here is a plain Account class. Its withdraw method refuses only when the account would go below zero.

The base class: a plain Account
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def withdraw(self, amount): if amount > self.balance: return "Not enough money" self.balance -= amount return f"Took {amount}, balance is {self.balance}" acc = Account("Asha", 500) print(acc.withdraw(450)) print(acc.withdraw(100))
Output
Took 450, balance is 50 Not enough money

Now the bank introduces a savings account. It is still an account (so SavingsAccount is-a Account), but it has a stricter rule: the balance must never drop below a minimum. The withdraw method has to behave differently. We could copy the whole Account class and edit it, but that is the duplication problem from section 3.1 again. Inheritance gives a better tool.

Overriding: replace the parent's version

To override a method, define a method with the same name in the child. Because Python searches the child first, it finds the child's version and stops. The parent's version is still there, hidden behind it, like a family rule that a child's house rule has replaced.

Overriding withdraw completely
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def withdraw(self, amount): if amount > self.balance: return "Not enough money" self.balance -= amount return f"Took {amount}, balance is {self.balance}" class SavingsAccount(Account): def __init__(self, owner, balance, minimum): super().__init__(owner, balance) self.minimum = minimum def withdraw(self, amount): # same name: overrides the parent's if self.balance - amount < self.minimum: return f"Refused: must keep at least {self.minimum}" self.balance -= amount return f"Took {amount}, balance is {self.balance}" sav = SavingsAccount("Ben", 500, 100) print(sav.withdraw(450)) print(sav.withdraw(300))
Output
Refused: must keep at least 100 Took 300, balance is 200

The savings account now enforces its minimum. Look at the last two lines of the child's withdraw, though: self.balance -= amount and the return are copied from the parent. If the bank later adds a transaction fee to Account.withdraw, savings accounts would silently miss it. We are back to duplication.

Extending: add to the parent's version

The better move is to do only the new work in the child and hand the rest to the parent with super().withdraw(amount). That is called extending a method. It is the same super() from section 3.3, now calling an ordinary method instead of __init__.

Extending withdraw with super()
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def withdraw(self, amount): if amount > self.balance: return "Not enough money" self.balance -= amount return f"Took {amount}, balance is {self.balance}" class SavingsAccount(Account): def __init__(self, owner, balance, minimum): super().__init__(owner, balance) self.minimum = minimum def withdraw(self, amount): if self.balance - amount < self.minimum: # the new rule return f"Refused: must keep at least {self.minimum}" return super().withdraw(amount) # everything else: the parent sav = SavingsAccount("Ben", 500, 100) print(sav.withdraw(450)) print(sav.withdraw(300))
Output
Refused: must keep at least 100 Took 300, balance is 200

The output is the same, but the design is better. The child contains only what makes it special. Everything else lives in one place. As a rule of thumb, ask yourself: "Do I want to replace the parent's behaviour, or add to it?" Replace means writing a full new body. Add means doing your extra work and calling super().method_name(...).

Which withdraw runs?
   sav.withdraw(450)
        |
        v
  +---------------------------+
  | SavingsAccount            |
  |   withdraw   <-- FOUND    |   1. Python looks here first and stops
  |   __init__                |
  +-------------+-------------+
                |  super().withdraw(amount)   2. only if the child asks
                v
  +---------------------------+
  | Account                   |
  |   withdraw   (hidden, but |
  |   __init__    reachable)  |
  +---------------------------+
The child's method is found first. The parent's method is not gone; it runs only when the child calls super().

You can prove that both versions still exist. The parent's function is a different object from the child's, and you can still call the parent's version by name, skipping the savings rule.

Both versions exist
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def withdraw(self, amount): self.balance -= amount return f"balance is {self.balance}" class SavingsAccount(Account): def withdraw(self, amount): return "savings rule first, then " + super().withdraw(amount) sav = SavingsAccount("Ben", 500) print(SavingsAccount.withdraw is Account.withdraw) print(sav.withdraw(50)) print(Account.withdraw(sav, 50)) # calls the parent's version directly
Output
False savings rule first, then balance is 450 balance is 400
Extending other methods: describe

Any method can be extended, not only withdraw. A very common pattern is a describe method where the child appends extra facts to the parent's sentence.

Extending describe
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def describe(self): return f"{self.owner} has {self.balance}" class SavingsAccount(Account): def __init__(self, owner, balance, minimum): super().__init__(owner, balance) self.minimum = minimum def describe(self): return super().describe() + f" (savings, minimum {self.minimum})" print(Account("Asha", 500).describe()) print(SavingsAccount("Ben", 500, 100).describe())
Output
Asha has 500 Ben has 500 (savings, minimum 100)
Common mistakes

Mistake 1: a typo in the name. Python does not warn you that you meant to override. A misspelled name is a brand-new method, and the parent's version keeps running.

The silent typo
class Account: def __init__(self, balance): self.balance = balance def withdraw(self, amount): return "parent rule" class SavingsAccount(Account): def withdrawl(self, amount): # typo: withdrawl return "savings rule" print(SavingsAccount(500).withdraw(50))
Output
parent rule

The output says parent rule, not savings rule. Whenever your override "does not seem to run", compare the spelling with the parent's method character by character.

**Mistake 2: forgetting return in an extended method.** The parent's answer is only useful if the child passes it back. Without return, the method quietly gives back None.

The forgotten return
class Account: def __init__(self, owner): self.owner = owner def describe(self): return f"Account of {self.owner}" class SavingsAccount(Account): def describe(self): super().describe() + " (savings)" # computed, then thrown away print(SavingsAccount("Ben").describe())
Output
None

Mistake 3: changing the parameters. An override should accept the same arguments as the original, otherwise code that calls it the usual way will break.

Override with different parameters
class Account: def withdraw(self, amount): return f"took {amount}" class SavingsAccount(Account): def withdraw(self): # forgot the amount parameter return "took nothing" print(SavingsAccount().withdraw(50))
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 9, in <module> print(SavingsAccount().withdraw(50)) ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ TypeError: SavingsAccount.withdraw() takes 1 positional argument but 2 were given

Python says SavingsAccount.withdraw() takes 1 positional argument but 2 were given. The two given are self (which Python adds for you) and 50. The method only declared room for self.

Mistake 4: calling yourself instead of the parent. If you write self.withdraw(amount) inside withdraw, the method calls itself forever. Python stops it with a RecursionError (a function calling itself too many times).

The next block uses try and except, which Chapter 5 teaches in full. For now, read it like this: "try to run the indented code; if it fails with a RecursionError, do not crash, run the except part instead." We use it here so the error message can be printed as ordinary output.

Calling self instead of super
class Account: def withdraw(self, amount): return f"took {amount}" class SavingsAccount(Account): def withdraw(self, amount): return self.withdraw(amount) # should be super().withdraw(amount) try: SavingsAccount().withdraw(50) except RecursionError as err: print("RecursionError:", err)
Output
RecursionError: maximum recursion depth exceeded

The fix is a single word: super() instead of self. self.withdraw means "look up withdraw starting at the child", which finds the child's own method again.

Try it.
Check yourself: what is the difference between overriding a method and extending it?

Overriding gives the child its own method with the same name, so Python runs the child's version instead of the parent's. Extending is a kind of overriding in which the child's version also calls super().method(...), so the parent's work still happens and the child adds to it.

Check yourself: a child's describe calls super().describe() but has no return. What does print(obj.describe()) show?

It shows None. The parent's text is computed and then dropped, and a function without a return gives back None.

Recap
  • Overriding: define a method with the same name in the child; Python finds the child's first.
  • Extending: override, and call super().method(...) to keep the parent's behaviour and add to it. This avoids copying the parent's code.
  • The parent's version still exists; super() or Parent.method(obj, ...) reaches it.
  • Typos silently create a new method instead of overriding; check spelling when an override does not run.
  • Keep the same parameters, remember return, and use super() rather than self when you mean the parent.
3.5 — Polymorphism: One Message, Many Behaviours

Back to the animal shelter. Every morning the shelter wants each animal to make its noise, one after another. Suppose the animal classes were written by different volunteers, who each chose their own method name: bark, meow and tweet. To get everyone to make a noise, the program has to ask every object what it is and then call the right method.

The type-checking chain
class Dog: def bark(self): return "Woof!" class Cat: def meow(self): return "Meow!" class Bird: def tweet(self): return "Tweet!" pets = [Dog(), Cat(), Bird()] for pet in pets: if isinstance(pet, Dog): print(pet.bark()) elif isinstance(pet, Cat): print(pet.meow()) elif isinstance(pet, Bird): print(pet.tweet())
Output
Woof! Meow! Tweet!

It works, but it is fragile. The shelter now takes in a fish. You write a Fish class with a blub method and add a fish to the list. What happens?

The chain silently ignores the new animal
class Dog: def bark(self): return "Woof!" class Cat: def meow(self): return "Meow!" class Fish: def blub(self): return "Blub!" pets = [Dog(), Fish(), Cat()] for pet in pets: if isinstance(pet, Dog): print(pet.bark()) elif isinstance(pet, Cat): print(pet.meow()) print("done")
Output
Woof! Meow! done

The fish said nothing, and no error was raised. You must remember to add another elif here, and in every other place in the program that has such a chain. Forgetting is likely and the failure is silent.

The idea: same message, different behaviour

Polymorphism is a Greek-sounding word for a small idea: many forms. Different objects respond to the same method name, and each responds in its own way. The code that uses the objects does not need to know which kind it is talking to. It sends the message, and each object handles it.

Think of a teacher who says to a classroom: "Everyone, introduce yourself." The teacher does not walk to each pupil with a different instruction. One sentence, and each pupil says their own name. Or think of the "play" button on a media player: it means something different for a CD, a radio and a streaming app, yet you press the same button.

To get this in code, we agree on one method name, speak, and give each class its own version. Because Dog, Cat and Bird are all animals, we put a default speak in the parent and let each child override it (section 3.4).

Polymorphism: the loop never checks the type
class Animal: def __init__(self, name): self.name = name def speak(self): return f"{self.name} makes a sound" class Dog(Animal): def speak(self): return f"{self.name} says Woof!" class Cat(Animal): def speak(self): return f"{self.name} says Meow!" class Bird(Animal): def speak(self): return f"{self.name} says Tweet!" for pet in [Dog("Rex"), Cat("Mimi"), Bird("Kiwi"), Animal("Generic")]: print(pet.speak())
Output
Rex says Woof! Mimi says Meow! Kiwi says Tweet! Generic makes a sound

The loop is one line: pet.speak(). It has no if, no isinstance, no knowledge of the classes at all. Yet each animal answers differently.

What Python does, line by line
  1. The loop takes the first item, a Dog object, and names it pet.
  2. pet.speak() asks: "which class was this object made from?" Python looks at the object itself, not at the name pet. The answer is Dog.
  3. Python searches Dog for speak and finds it. It calls that version with self set to this object.
  4. The loop takes the next item, a Cat. The same line pet.speak() now searches Cat and finds the cat's version.
  5. For Animal("Generic"), Animal is its own class, so Python finds the default version in Animal.

The decision about which code to run is made fresh each time round the loop, based on the object in front of Python at that moment. Programmers call this dynamic dispatch ("dispatch" means sending the call to the right place). You do not have to write anything for it; it is how method calls work.

One call, many answers
                     pet.speak()
                          |
      +-------------------+-------------------+
      |                   |                   |
 pet is a Dog        pet is a Cat        pet is a Bird
      |                   |                   |
      v                   v                   v
 Dog.speak()         Cat.speak()         Bird.speak()
 "Rex says Woof!"    "Mimi says Meow!"   "Kiwi says Tweet!"
The caller writes one line. The object's own class decides which code runs.
Adding a new kind costs nothing

Remember the fish that broke the if/elif chain. With polymorphism, adding it means writing one small class. The loop is not touched.

A new animal, no loop changes
class Animal: def __init__(self, name): self.name = name def speak(self): return f"{self.name} makes a sound" class Dog(Animal): def speak(self): return f"{self.name} says Woof!" class Fish(Animal): # the only new code def speak(self): return f"{self.name} says Blub!" for pet in [Dog("Rex"), Fish("Bubbles")]: print(pet.speak()) # unchanged
Output
Rex says Woof! Bubbles says Blub!
Polymorphism you already use

You have used polymorphism since your first chapter without the name. The built-in len() works on strings, lists and dictionaries. The + operator adds numbers but joins strings. One name, many behaviours, and each type knows what to do.

Built-in polymorphism
print(len("hello")) # a string counts characters print(len([10, 20, 30])) # a list counts items print(len({"a": 1})) # a dict counts keys print(3 + 4) # numbers add print("3" + "4") # strings join print([1] + [2]) # lists join
Output
5 3 1 7 34 [1, 2]

The same holds for your own objects when you write __str__ (Part 2). print(obj) is one message, and every class answers it in its own way.

Another example: shapes

Polymorphism is not only about animals. Any time you have a group of related things and one question to ask all of them, it fits. Here is the classic case: a list of shapes, each with its own way to compute its area. In the code, sum(shape.area() for shape in shapes) works like a list comprehension without the square brackets: it produces one area per shape, and sum adds them all up.

Total area of mixed shapes
class Circle: def __init__(self, radius): self.radius = radius def area(self): return 3.14159 * self.radius * self.radius class Rectangle: def __init__(self, width, height): self.width = width self.height = height def area(self): return self.width * self.height shapes = [Circle(1), Rectangle(2, 3), Circle(2)] total = sum(shape.area() for shape in shapes) print(f"Total area: {total:.2f}")
Output
Total area: 21.71

Notice that Circle and Rectangle are not related by inheritance here. They both offer an area() method. Polymorphism only needs the same method name. (Section 3.6 explores this.)

Common mistakes

Mistake 1: an object that lacks the method. If one item in the list has no speak, the loop fails when it reaches that item.

One object has no speak
class Dog: def speak(self): return "Woof!" class Rock: pass for thing in [Dog(), Rock()]: print(thing.speak())
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 9, in <module> print(thing.speak()) ^^^^^^^^^^^ AttributeError: 'Rock' object has no attribute 'speak'

The output starts with Woof! for the dog. Then the traceback ends with AttributeError: 'Rock' object has no attribute 'speak'. The message names the class, so you know exactly which object broke the promise.

Mistake 2: methods that answer in different ways. Polymorphism works best when every version behaves alike from the caller's point of view. If Dog.speak returns text but Cat.speak prints the text itself, the caller cannot use them the same way.

Inconsistent versions
class Dog: def speak(self): return "Woof!" class Cat: def speak(self): print("Meow!") # prints instead of returning for pet in [Dog(), Cat()]: print(pet.speak())
Output
Woof! Meow! None

The cat prints Meow! itself and returns nothing, so the outer print shows a stray None. Decide once what a method returns, and let every version follow that decision.

Mistake 3: forgetting the parentheses. Writing pet.speak without () does not call the method. Python shows something like <bound method Dog.speak of ...>, which is Python saying "here is the method itself, not its result".

Try it.
Check yourself: why does pet.speak() in a loop run different code for different objects, even though the line never changes?

Python decides which speak to run each time, by looking at the class of the object that pet refers to at that moment. Each class supplies its own version, so the same line produces different behaviour.

Check yourself: give one benefit of polymorphism compared with an if/elif chain of isinstance checks.

Adding a new kind of object needs only a new class; existing code that calls the shared method does not change. With a chain, every place that has the chain must be edited, and forgetting one fails silently.

Recap
  • Polymorphism ("many forms"): different objects respond to the same method name, each in its own way.
  • Python picks the version to run by looking at the object's own class at the moment of the call (dynamic dispatch).
  • It replaces long if/elif chains and lets you add new kinds without touching the calling code.
  • You already use it: len(), + and print() behave differently for different types.
  • Keep every version's inputs and return values consistent, or the caller cannot treat them alike.
3.6 — Duck Typing: What an Object Can Do

The shelter gets a new attraction: a toy robot dog that can also speak. It is not a living animal, so nobody made it a child of Animal. Meanwhile, a function called make_noise was written earlier by a careful programmer who wanted to be safe. It checks that it has been given an animal before it does anything.

A function that is too strict
class Animal: def __init__(self, name): self.name = name class Dog(Animal): def speak(self): return f"{self.name} says Woof!" class Robot: # not an Animal def speak(self): return "Beep boop!" def make_noise(thing): if not isinstance(thing, Animal): raise TypeError("only animals can make noise") return thing.speak() print(make_noise(Dog("Rex"))) try: print(make_noise(Robot())) except TypeError as err: print("Refused:", err)
Output
Rex says Woof! Refused: only animals can make noise

(Two new pieces of code appear above. raise TypeError(...) means "stop here and signal an error with this message". And try/except catches such an error so the program can print it instead of crashing, as in section 3.4.) The robot has a perfectly good speak method, but make_noise turns it away because of who its parent is. That is a shame: the function only ever needed one thing, a speak method. The check asks the wrong question. Python has a saying for the better question.

The idea: if it quacks like a duck

"If it walks like a duck and quacks like a duck, then it is a duck." In programming this is called duck typing. Instead of asking "what family does this object belong to?", you ask "can this object do what I need?" and try it. If the object has the method, everything works. If it does not, Python raises an error at that point.

An everyday comparison is a wall socket. The socket does not care whether your plug belongs to a lamp, a phone charger or a kettle. It cares only that the pins fit. Likewise, make_noise should care only that the thing has a speak method, not what it inherited from.

The socket does not check the brand
   make_noise(thing)  needs:  thing.speak()

   Dog      -- has speak() --> works
   Robot    -- has speak() --> works    (no shared parent needed!)
   Person   -- has speak() --> works
   Rock     -- no speak()  --> AttributeError
Duck typing asks "can it do this?", not "what is it?". Any object with a matching method fits.
Duck typing: drop the family check
class Dog: def speak(self): return "Woof!" class Robot: def speak(self): return "Beep boop!" class Person: def speak(self): return "Hello!" def make_noise(thing): return thing.speak() # no isinstance check: try it for item in [Dog(), Robot(), Person()]: print(make_noise(item))
Output
Woof! Beep boop! Hello!

Three classes with no shared parent all work with the same function. Polymorphism (section 3.5) was about objects answering the same message. Duck typing is the permission slip that lets unrelated classes take part. Inheritance is one way to share behaviour; it is not required.

What it IS versus what it CAN DO

There are two different questions you can ask about an object, and it helps to keep them apart.

  • What is it? This is a question about the object's family. isinstance(obj, Animal) answers it.
  • What can it do? This is a question about its abilities. hasattr(obj, "speak") answers it, or you can call the method and see what happens.

If your code only needs an ability, ask about the ability. If your code truly cares about the family, ask about the family.

Trying versus checking first

There are two styles for handling an object that might not have the ability. Programmers give them long names, but the ideas are plain.

  • Look before you leap (LBYL): check first with hasattr, then act.
  • Easier to ask forgiveness than permission (EAFP): act, and catch the error with try/except if it fails.
Two styles side by side
class Dog: def speak(self): return "Woof!" class Rock: pass def check_first(thing): if hasattr(thing, "speak"): return thing.speak() return "(silent)" def try_first(thing): try: return thing.speak() except AttributeError: return "(silent)" for item in [Dog(), Rock()]: print(check_first(item), try_first(item))
Output
Woof! Woof! (silent) (silent)

Both give the same answers here. The try style is very common in Python. Use whichever reads more clearly, but avoid wrapping a large block in try, because it can also hide unrelated AttributeError mistakes.

Duck typing is everywhere in Python

Python's own tools use duck typing. The len() function does not check the family of what you give it. It asks the object for its length through the special method __len__ (Part 2). A for loop does not care whether it gets a list, a string or something you built, as long as the object can be stepped through by __iter__. Watch your own class join in.

Your own class works with len() and for
class Playlist: def __init__(self, songs): self.songs = songs def __len__(self): return len(self.songs) def __iter__(self): return iter(self.songs) mix = Playlist(["Aria", "Blue", "Comet"]) print(len(mix)) for song in mix: print("Now playing:", song) print("Blue" in mix)
Output
3 Now playing: Aria Now playing: Blue Now playing: Comet True

Playlist inherits from nothing except Python's basic object, yet len(mix), the for loop and even in all work, because the class has the abilities they look for.

When checking the family is the right choice

Duck typing does not mean you should never use isinstance. Checking the family is sensible in two situations. The first is at the edge of your program, where data arrives from outside (a user, a file, another team) and a wrong kind of value would cause a confusing failure much later. The second is when you truly need to treat different kinds differently, and the kinds are Python's own, such as numbers versus text.

A sensible use of isinstance
def to_cents(amount): if isinstance(amount, (int, float)): return round(amount * 100) if isinstance(amount, str): return round(float(amount) * 100) raise TypeError(f"cannot convert {type(amount).__name__} to cents") print(to_cents(2.5)) print(to_cents("3.25")) try: to_cents([1, 2]) except TypeError as err: print("Error:", err)
Output
250 325 Error: cannot convert list to cents

What you should avoid is using isinstance chains to choose behaviour among your own classes. That is the if/elif mess from section 3.5. Give the classes a shared method and let polymorphism do the choosing.

Common mistakes

Mistake 1: the "method" is really a plain value. If an object stores a string under the name speak instead of defining a method, then hasattr says yes but calling it fails.

speak exists, but is not callable
class Parrot: def __init__(self): self.speak = "Polly wants a cracker" # a string, not a method bird = Parrot() print(hasattr(bird, "speak")) print(bird.speak())
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 7, in <module> print(bird.speak()) ^^^^^^^^^^^^ TypeError: 'str' object is not callable

The message TypeError: 'str' object is not callable means "you put () after something that is a string, and strings cannot be called". Look for a name being used both as data and as a method. callable(bird.speak) would have returned False.

Mistake 2: a differently spelled method. One class says speak, another says Speak or talk. To a person they look the same; to Python they are different names, so the duck does not fit the socket. Whenever a "duck" fails, compare the method names character by character.

Mistake 3: checking too early, and rejecting good objects. The strict make_noise at the top of this section is the classic example. If you catch yourself writing isinstance(thing, SomeClass) only to call one method, delete the check and call the method.

Mistake 4: assuming duck typing means no rules. The object must still honour the same promise: the same method name, the same parameters, and a similar return value. A speak(self, loudly) on one class and speak(self) on another will fail when the caller uses one style for both.

Try it.
Check yourself: a function calls thing.area() and nothing else on it. Should it check isinstance(thing, Shape) first?

Usually not. It needs only an area() method, so any object with that method will work, whether or not it inherits from Shape. Checking the family would reject valid objects for no good reason.

Check yourself: what is the difference between hasattr(obj, "speak") and isinstance(obj, Animal)?

hasattr asks about an ability: does the object have something named speak? isinstance asks about family membership: was the object made from Animal or a class built on it? An object can pass one test and fail the other.

Recap
  • Duck typing: care about what an object can do, not what family it belongs to.
  • Unrelated classes can take part in polymorphism if they share method names.
  • hasattr checks for an ability first (LBYL); calling and catching AttributeError is the other style (EAFP).
  • Python's own tools (len, for, in) use duck typing through special methods.
  • Use isinstance at boundaries and for Python's built-in kinds; avoid it for choosing behaviour among your own classes.
3.7 — Chains of Parents and the Method Resolution Order

Families have more than two generations. A puppy is a kind of dog, and a dog is a kind of animal. Python lets you build this chain: Puppy inherits from Dog, and Dog inherits from Animal. This is called multi-level inheritance. The puppy gets everything from the dog, and everything the dog got from the animal.

Three generations
class Animal: def __init__(self, name): self.name = name def breathe(self): return f"{self.name} breathes" class Dog(Animal): def fetch(self): return f"{self.name} fetches" class Puppy(Dog): def play(self): return f"{self.name} plays" pup = Puppy("Bit") print(pup.breathe()) # from Animal, two levels up print(pup.fetch()) # from Dog, one level up print(pup.play()) # from Puppy itself print(isinstance(pup, Animal), isinstance(pup, Dog), isinstance(pup, Puppy))
Output
Bit breathes Bit fetches Bit plays True True True

The puppy can do all three things, and isinstance says yes to all three classes. Now a harder question arises. What if two levels define the same method name? Which version wins? Python answers with a strict search order.

The search order

When you write pup.something, Python looks in a fixed sequence of places and uses the first match. It checks the object itself first (its own attributes), then its class, then the parent, then the grandparent, and so on up the chain. The very last stop is a built-in class called object, which every class inherits from even when you do not write it. The default __init__ and __str__ come from object.

The ordered list of classes Python searches is called the method resolution order, or MRO for short. Every class has one, and you can print it.

Print the search order
class Animal: pass class Dog(Animal): pass class Puppy(Dog): pass print([cls.__name__ for cls in Puppy.__mro__]) print([cls.__name__ for cls in Dog.__mro__]) print("object" in [cls.__name__ for cls in Animal.__mro__])
Output
['Puppy', 'Dog', 'Animal', 'object'] ['Dog', 'Animal', 'object'] True

__mro__ is a tuple of classes. We turn it into a list of names to keep it readable. For Puppy, the answer is Puppy, Dog, Animal, object, in that order.

Lookup order for Puppy
   pup.speak()

   1. the object itself   {name: "Bit"}      no "speak" here
   2. class Puppy                            no speak
   3. class Dog                              speak found -> STOP, call it
   4. class Animal                           (never reached)
   5. class object                           (never reached)
Python walks down the MRO from first to last and uses the first match. Later classes are not consulted once a match is found.
What Python does, line by line

Suppose Animal and Dog both define speak, but Puppy does not, and Animal alone defines describe.

  1. For pup.speak(), Python first checks whether the object pup itself has an attribute called speak. No.
  2. Next, class Puppy. It does not define speak. Move on.
  3. Next, class Dog. It defines speak. Python stops here and calls Dog.speak with pup as self. Animal.speak is never consulted.
  4. For pup.describe(), the same search runs. Puppy no, Dog no, Animal yes. It runs Animal.describe.
  5. If no class in the list has the name, Python raises AttributeError.
Chains of super()

Each super() call moves one step further down the MRO. That means a method that extends its parent by calling super() builds a chain, with each level doing a little work. Follow the prints to see the order.

A chain of super() calls
class Animal: def speak(self): return "..." class Dog(Animal): def speak(self): return super().speak() + " woof" class Puppy(Dog): def speak(self): return super().speak() + " yip" print(Animal().speak()) print(Dog().speak()) print(Puppy().speak())
Output
... ... woof ... woof yip

Puppy().speak() calls Puppy.speak, which calls Dog.speak through super(), which calls Animal.speak through its own super(). The answer builds up from the top: ..., then woof, then yip.

Class attributes and instance attributes

Attributes follow the same search. A value written in a class body (a class attribute) is shared by all objects of that class. A value stored with self.x = ... (an instance attribute) belongs to one object. The search checks the instance first, then the classes, so an instance attribute hides a class attribute of the same name without changing it.

Instance first, then class
class Animal: legs = 4 # class attribute: shared class Bird(Animal): legs = 2 # overrides the shared value for birds rex = Animal() kiwi = Bird() print(rex.legs, kiwi.legs) kiwi.legs = 1 # creates an instance attribute on kiwi only print(kiwi.legs, Bird.legs) # the class is untouched del kiwi.legs # remove the personal value print(kiwi.legs) # back to the class's value
Output
4 2 1 2 2
Common mistakes

Mistake 1: a broken link in the chain. In multi-level inheritance, every level with its own __init__ must call super().__init__. If the middle level forgets, the levels above it never run.

The middle class forgot super().__init__
class Animal: def __init__(self, name): self.name = name class Dog(Animal): def __init__(self, name, breed): self.breed = breed # forgot super().__init__(name) class Puppy(Dog): def __init__(self, name, breed): super().__init__(name, breed) pup = Puppy("Bit", "Beagle") print(pup.name)
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 14, in <module> print(pup.name) ^^^^^^^^ AttributeError: 'Puppy' object has no attribute 'name'

Follow the chain. Puppy.__init__ correctly calls super().__init__, which runs Dog.__init__. But Dog.__init__ never calls its own super(), so Animal.__init__ never runs and name is never set. The error AttributeError: 'Puppy' object has no attribute 'name' appears at the line that reads name, not where the mistake lives. Trace it back through the classes in MRO order.

Mistake 2: assuming assignment through an object changes the class. In the class-attribute example, kiwi.legs = 1 did not change Bird.legs. It made a new personal attribute on kiwi. If you want to change the shared value, assign through the class: Bird.legs = 1.

Mistake 3: very deep chains. Being able to build ten levels does not mean you should. When you read a method, you may have to check several classes to know which version runs. Most well-designed programs keep hierarchies shallow, often two or three levels. If the tree keeps growing, that is a sign to reconsider the design (OOP Part 4 shows an alternative).

Check yourself: what does Puppy.__mro__ look like for Puppy(Dog), Dog(Animal), Animal with no parent written?

Puppy, Dog, Animal, object. Animal inherits from object automatically, and object is always last.

Check yourself: Dog sets the class attribute legs = 4 and rex = Dog(). After rex.legs = 3, what are rex.legs and Dog.legs?

rex.legs is 3, because the instance now has its own attribute. Dog.legs is still 4, because assigning through an object never changes the class.

Recap
  • Multi-level inheritance: a child can itself be a parent; features pass down every generation.
  • The MRO (method resolution order) is the list of classes Python searches: the object, then its class, parents in order, then object.
  • The first match wins; later classes are not consulted. Print it with ClassName.__mro__.
  • super() means "the next class in the MRO", so super() calls can chain up through several levels.
  • Instance attributes hide class attributes; every level with an __init__ must call super().__init__.
3.8 — Multiple Inheritance and Mixins

Until now every child had one parent. Real things are messier. A duck can fly and swim. A bird class might know how to fly, a fish class might know how to swim, and a duck needs both abilities. With one parent only, you would have to copy one of the abilities into the duck, and the duplication problem returns.

Without multiple parents, we copy again
class Bird: def fly(self): return f"{self.name} flies" class Fish: def swim(self): return f"{self.name} swims" class Duck: def __init__(self, name): self.name = name def fly(self): # copied from Bird return f"{self.name} flies" def swim(self): # copied from Fish return f"{self.name} swims" d = Duck("Donna") print(d.fly(), "and", d.swim())
Output
Donna flies and Donna swims

Python allows a class to have several parents. You list them all in the parentheses, separated by commas. This is called multiple inheritance. The child receives the abilities of every parent.

Mixins: small, single-purpose helpers

The most useful style of multiple inheritance uses a mixin. A mixin is a small class that offers one ability (flying, swimming, logging) and is never meant to be used on its own. You "mix" it into other classes, the way you stir raisins into bread dough. Mixins usually have a name that ends in Mixin so readers recognise them.

Mixins give a Duck both abilities
class FlyMixin: def fly(self): return f"{self.name} flies" class SwimMixin: def swim(self): return f"{self.name} swims" class Animal: def __init__(self, name): self.name = name class Duck(FlyMixin, SwimMixin, Animal): pass d = Duck("Donna") print(d.fly(), "and", d.swim()) print([cls.__name__ for cls in Duck.__mro__])
Output
Donna flies and Donna swims ['Duck', 'FlyMixin', 'SwimMixin', 'Animal', 'object']

Duck has three parents and contains no code of its own. Each ability is written once, and any other class can reuse it. The MRO from section 3.7 still governs everything: Python searches Duck, then FlyMixin, then SwimMixin, then Animal, then object, in the order you listed the parents.

Order matters

If two parents define the same method name, the parent listed first wins. You can see this by swapping the order.

The first parent wins
class LoudMixin: def speak(self): return "LOUD" class QuietMixin: def speak(self): return "quiet" class A(LoudMixin, QuietMixin): pass class B(QuietMixin, LoudMixin): pass print(A().speak(), B().speak()) print([c.__name__ for c in A.__mro__]) print([c.__name__ for c in B.__mro__])
Output
LOUD quiet ['A', 'LoudMixin', 'QuietMixin', 'object'] ['B', 'QuietMixin', 'LoudMixin', 'object']
The diamond problem

Now the tricky case. Suppose Flyer and Swimmer both inherit from Animal, and Duck inherits from both. Drawn on paper the family tree forms a diamond, which is why this is called the diamond problem. The question is: Animal sits at the top of both branches. Does its __init__ run once, twice, or never?

The diamond
              +----------+
              |  Animal  |     <- reachable by TWO paths
              +----------+
               ^        ^
               |        |
        +---------+  +----------+
        |  Flyer  |  | Swimmer  |
        +---------+  +----------+
               ^        ^
                \      /
                +------+
                | Duck |
                +------+
Duck reaches Animal through Flyer and through Swimmer. Python must decide on ONE order that visits every class exactly once.

Python solves it with the MRO. It builds a single list in which each class appears once, following two plain rules: a child always comes before its parents, and the left-to-right order you wrote in the parentheses is respected. For the diamond the list is Duck, Flyer, Swimmer, Animal, object. The shared parent Animal comes after both branches. And super() follows exactly this list, one step at a time.

Cooperative super(): Animal runs once
class Animal: def __init__(self, name): print(" Animal.__init__") self.name = name class Flyer(Animal): def __init__(self, name): print(" Flyer.__init__") super().__init__(name) class Swimmer(Animal): def __init__(self, name): print(" Swimmer.__init__") super().__init__(name) class Duck(Flyer, Swimmer): def __init__(self, name): print(" Duck.__init__") super().__init__(name) d = Duck("Donna") print([c.__name__ for c in Duck.__mro__])
Output
Duck.__init__ Flyer.__init__ Swimmer.__init__ Animal.__init__ ['Duck', 'Flyer', 'Swimmer', 'Animal', 'object']

Read the printed order: Duck, Flyer, Swimmer, Animal. Notice that Flyer's super() did not go straight to Animal. It went to Swimmer, the next class in Duck's MRO. That is the deeper meaning of super(): not "my parent", but "whoever comes next in the list". And Animal.__init__ ran exactly once.

Now compare with the older explicit style from section 3.3, where each class calls its parent by name.

Calling parents by name: Animal runs twice
class Animal: def __init__(self, name): print(" Animal.__init__") self.name = name class Flyer(Animal): def __init__(self, name): Animal.__init__(self, name) class Swimmer(Animal): def __init__(self, name): Animal.__init__(self, name) class Duck(Flyer, Swimmer): def __init__(self, name): Flyer.__init__(self, name) Swimmer.__init__(self, name) d = Duck("Donna")
Output
Animal.__init__ Animal.__init__

Animal.__init__ ran twice. For a name that is harmless. If Animal.__init__ opened a file or added to a counter, it would run twice and cause real trouble. This is the main reason to prefer super().

When to use it, and when to avoid it

Mixins are a good idea when the ability is small and independent of the rest of the class: logging, saving to a file, comparing. They are a poor idea when the parents overlap heavily, define the same names, or depend on each other's state, because you can no longer read one class and know what happens. When in doubt, keep to a single parent and use the "has-a" approach from OOP Part 4.

Common mistakes

Mistake 1: using a mixin alone. A mixin usually relies on attributes that its host class provides. On its own it has nothing to work with.

A mixin cannot stand alone
class FlyMixin: def fly(self): return f"{self.name} flies" # expects the host to set self.name thing = FlyMixin() print(thing.fly())
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 6, in <module> print(thing.fly()) ^^^^^^^^^^^ File "<exec>", line 3, in fly return f"{self.name} flies" # expects the host to set self.name ^^^^^^^^^ AttributeError: 'FlyMixin' object has no attribute 'name'

The message AttributeError: 'FlyMixin' object has no attribute 'name' tells you the mixin assumed a name that nobody provided. Document what a mixin expects, and only ever combine it with classes that supply it.

Mistake 2: parents in an impossible order. If you list a parent before its own child, Python cannot build a consistent list and refuses.

An impossible MRO
class Animal: pass class Duck(Animal): pass class Weird(Animal, Duck): # parent listed before its child pass
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 7, in <module> class Weird(Animal, Duck): # parent listed before its child TypeError: Cannot create a consistent method resolution order (MRO) for bases Animal, Duck

The error TypeError: Cannot create a consistent method resolution order (MRO) for bases Animal, Duck (Python prints it split over two lines) says the two rules from earlier contradict each other: your order demands Animal first, but a child must come before its parent. Swap the order to Weird(Duck, Animal) or drop the redundant parent.

Mistake 3: forgetting that the first parent wins. If a mixin and the base both define describe, the one listed first is used. Put mixins before the main base class so their methods are found first.

**Mistake 4: mixing super() and named calls.** In a diamond, if one class calls super() and another calls its parent by name, some __init__ methods run twice or not at all. Pick super() everywhere.

Try it.
Check yourself: for class Duck(Flyer, Swimmer), both defining speak, which speak does a Duck use?

Flyer's. Python searches Duck, then Flyer, so it finds Flyer.speak first and stops. Reversing the parents would make Swimmer's win.

Check yourself: in a diamond, why does Animal.__init__ run only once when every class uses super().__init__?

super() follows the MRO, which lists each class exactly once. Flyer passes control to Swimmer (the next class in the list), and Swimmer passes it to Animal, so Animal is reached one time only.

Recap
  • Multiple inheritance: class Duck(A, B, C) gives the child every parent's abilities.
  • A mixin is a small, single-purpose class made to be mixed into others, not used alone.
  • The first-listed parent wins when names collide; put mixins before the main base class.
  • The diamond problem: the MRO lists each class once, children before parents, respecting your left-to-right order.
  • super() means "the next class in the MRO", so use it consistently; avoid multiple inheritance when parents overlap heavily.
3.9 — Abstract Base Classes, and When Inheritance Is the Wrong Tool

Our Animal parent has one weakness. In section 3.5 we gave it a default speak that returns something bland. That default makes it possible for a new child class to forget its own version, and nothing complains. Here a volunteer adds Cat and forgets to write speak.

The forgotten override goes unnoticed
class Animal: def __init__(self, name): self.name = name def speak(self): return f"{self.name} makes a sound" class Dog(Animal): def speak(self): return f"{self.name} says Woof!" class Cat(Animal): pass # forgot speak! for pet in [Dog("Rex"), Cat("Mimi")]: print(pet.speak())
Output
Rex says Woof! Mimi makes a sound

The program runs, and the cat says something that is technically fine but not what we wanted. A common fix is to make the parent's method raise NotImplementedError, which is Python's way of saying "a child was supposed to write this".

Raising NotImplementedError
class Animal: def __init__(self, name): self.name = name def speak(self): raise NotImplementedError("children must write speak") class Cat(Animal): pass mimi = Cat("Mimi") # creating the cat is fine try: mimi.speak() # the failure only appears here except NotImplementedError as err: print("Error:", err)
Output
Error: children must write speak

This is better, but the mistake is discovered late, only when someone calls speak. In a big program that might be weeks after the class was written. We would like Python to refuse the incomplete class immediately, when we try to create an object.

The idea: an abstract base class

An abstract base class (ABC) is a parent class that is not meant to be created itself. Its job is to be a contract: it lists the methods that every child must provide. Think of a job description. It says "the person hired must be able to type and answer phones", but there is no such person as "the job description". Only real people who meet the description can be hired.

You build one with the abc module that comes with Python. You make the parent inherit from ABC and mark each required method with @abstractmethod. A method marked this way is an abstract method: it is declared but has no real body.

A first abstract base class
from abc import ABC, abstractmethod class Animal(ABC): def __init__(self, name): self.name = name @abstractmethod def speak(self): pass # children must fill this in def describe(self): # ordinary method, shared by all return f"{self.name} says: {self.speak()}" class Dog(Animal): def speak(self): return "Woof!" rex = Dog("Rex") print(rex.describe()) print(sorted(Animal.__abstractmethods__)) print(sorted(Dog.__abstractmethods__))
Output
Rex says: Woof! ['speak'] []

The line @abstractmethod above a def is called a decorator: a marker that gives the method special treatment. Notice that Animal still has ordinary methods (__init__, describe) that children share. Only speak is abstract. Dog writes the required method, so Dog("Rex") works. Animal.__abstractmethods__ is the set of names that are still unfinished. For Dog it is an empty list, which means the contract is fulfilled.

What Python does, line by line
  1. When Python reads class Animal(ABC), it notices the @abstractmethod on speak and records the name speak in the class's list of unfinished methods.
  2. When it reads class Dog(Animal), it copies that list and crosses off every name the child defines. Dog defines speak, so the list becomes empty.
  3. When you write Dog("Rex"), Python checks the list. It is empty, so the object is created normally.
  4. When you write Animal("Generic") or create a child that left a name on the list, Python sees a non-empty list and raises TypeError before any object exists.
The contract
   +-----------------------------+
   |  Animal  (abstract)         |
   |  contract: speak() required |
   +-----------------------------+
        ^                 ^
        |                 |
   +---------+       +---------+
   |   Dog   |       |   Cat   |
   | speak() |       | (none)  |
   |  ok     |       | BLOCKED |
   +---------+       +---------+
   Dog("Rex") works   Cat("Mimi") -> TypeError
A child that keeps its promise can be created. A child that forgets a required method cannot, and the error comes at creation time.

Here are the two errors you will meet. First, trying to create the abstract class itself.

Creating the abstract class
from abc import ABC, abstractmethod class Animal(ABC): @abstractmethod def speak(self): pass pet = Animal()
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 8, in <module> pet = Animal() ^^^^^^^^ TypeError: Can't instantiate abstract class Animal without an implementation for abstract method 'speak'

The last line is the message to remember: TypeError: Can't instantiate abstract class Animal without an implementation for abstract method 'speak'. To instantiate a class means to create an object from it. The fix is to create a concrete child instead (a concrete class is one with no unfinished methods).

Second, a child that forgets to keep the promise.

A child that forgot the required method
from abc import ABC, abstractmethod class Animal(ABC): @abstractmethod def speak(self): pass class Cat(Animal): def purr(self): # wrote a different method return "Purr" mimi = Cat()
What Python prints (traceback)
Traceback (most recent call last): File "<exec>", line 12, in <module> mimi = Cat() ^^^^^ TypeError: Can't instantiate abstract class Cat without an implementation for abstract method 'speak'

The error names both the class and the missing method, and it fires the moment you try to create the cat, not weeks later. If a child has several missing methods, Python lists them all.

Common mistakes

**Mistake 1: forgetting ABC or the decorator.** The enforcement needs both pieces. Leave one out and Python treats the method as ordinary, and nothing is enforced.

No ABC, no enforcement
from abc import abstractmethod class Animal: # forgot (ABC) @abstractmethod def speak(self): pass pet = Animal() # allowed: nothing is enforced print("created:", type(pet).__name__) print(pet.speak()) # prints None
Output
created: Animal None

Mistake 2: a misspelled override. If the child writes speek, the required speak is still unfinished, so Python blocks the child. That is a helpful error: the typo that silently passed in section 3.4 is now caught at once.

Mistake 3: making everything abstract. An abstract method should be something children truly must decide for themselves. Behaviour that most children share belongs in an ordinary method, like describe above.

The Liskov substitution rule, in plain words

A contract is only useful if children honour it. The rule is named after the computer scientist Barbara Liskov, and in plain words it says: anywhere your code uses a parent, you should be able to use any child instead, without surprises. If code works with an Animal, it must still work when you hand it a Dog or a Cat.

Children break the rule when they refuse to do what the parent promised. The classic example is a penguin. If Bird promises a fly method, a Penguin child cannot keep that promise.

A child that breaks the promise
class Bird: def fly(self): return "flying" class Sparrow(Bird): pass class Penguin(Bird): def fly(self): raise NotImplementedError("penguins cannot fly") def migrate(birds): for bird in birds: print(bird.fly()) try: migrate([Sparrow(), Penguin()]) except NotImplementedError as err: print("Migration failed:", err)
Output
flying Migration failed: penguins cannot fly

migrate works for any Bird until a Penguin arrives. The problem is not migrate; it is the design. Penguin is-a Bird, but the Bird class promised something that not every bird can do. The fix is a better hierarchy: make Bird promise only what all birds do, and put fly in a separate FlyingBird class or mixin. Contracts should be small and honest.

When inheritance is the wrong tool

Inheritance is a strong link: the child depends on the parent's every detail. Use it only when the is-a test is true and the child can keep all the parent's promises. Here is a temptation: a Stack (last in, first out) built by inheriting from list.

Inheriting too much
class Stack(list): def push(self, item): self.append(item) s = Stack() s.push("a") s.push("b") s.insert(0, "sneaky") # a list can do this; a stack must not print(list(s))
Output
['sneaky', 'a', 'b']

Stack inherited every list method, including insert, which lets anyone break the "last in, first out" rule. A stack is not really a list; it uses a list inside. That "has-a" relationship is called composition, and it is the subject of OOP Part 4. Ask two questions before inheriting: "Is it truly an X?" and "Do I want all of X's methods?" If either answer is no, hold an X inside instead.

Try it.
Check yourself: what happens when you run Animal("x") if Animal has an @abstractmethod and inherits ABC?

Python raises TypeError: Can't instantiate abstract class Animal without an implementation for abstract method 'speak'. No object is created. You must create a concrete child that implements every abstract method.

Check yourself: in plain words, what does the Liskov substitution rule ask of a child class?

It asks that the child can stand in wherever the parent is used without breaking the code. The child must keep every promise the parent made, so a function written for the parent keeps working when it is given the child.

Recap
  • An abstract base class (class X(ABC)) is a contract: it lists methods (@abstractmethod) that children must write.
  • You cannot create an object from an abstract class, or from a child that leaves a required method unfinished; Python raises TypeError at creation time.
  • Ordinary methods in the ABC are still shared by all children.
  • Liskov substitution: any child must work wherever the parent is expected; a child that refuses a parent's promise signals a bad design.
  • Inheritance is a strong link. When the is-a test fails or the child does not want all the parent's methods, use composition (OOP Part 4).
OOP Part 3 Summary
  1. Duplication hurts. Copy-pasted classes drift apart; the DRY rule says each idea lives in one place.
  2. Inheritance (class Dog(Animal)) passes a parent's attributes and methods to a child. Use the is-a test, and check with isinstance / issubclass.
  3. super() lets a child call its parent. Call super().__init__(...) first in a child's __init__, without passing self.
  4. Overriding replaces a parent's method; extending calls super().method() and adds to it. Keep the same parameters and remember return.
  5. Polymorphism: one method name, many behaviours. The object's own class decides which code runs, so if/elif type chains disappear.
  6. Duck typing cares about what an object can do rather than what family it belongs to. Use isinstance at boundaries, not to choose behaviour among your own classes.
  7. MRO: Python searches the object, then its class and parents in a fixed order (Class.__mro__) and uses the first match. Instance attributes hide class attributes.
  8. Multiple inheritance and mixins combine small abilities. The MRO puts each class in the list once; super() means "next in the MRO".
  9. Abstract base classes (ABC, @abstractmethod) enforce a contract at creation time. Children must be able to stand in for the parent (Liskov), and when is-a fails, prefer composition (OOP Part 4).
