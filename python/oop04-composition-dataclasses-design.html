OOP Part 4:
Designing With Objects

You can build classes, hide their insides, and extend them with inheritance. Now comes the skill that separates code that merely works from code that stays pleasant to change: deciding what the objects should be and how they fit together. We will build objects out of other objects, let Python write the boring parts of a class for you, replace magic strings with proper choices, and end by turning a written requirement into a small working program.

4.1 — Objects That Contain Objects: "Has-A"

Welcome back. Before we learn anything new, here is a very short recap of the last three chapters, because this chapter builds on all of it. A class is a blueprint. An object is one thing built from that blueprint, and it stores its own facts in attributes (like self.name). A method is a function that lives inside a class and works on one object through self. Encapsulation means a class keeps its details tidy and hidden behind a few clear methods. Inheritance lets a new class start from an old one (class Dog(Animal)) and change only what differs. If any of that feels shaky, a quick look back at OOP 1 to 3 is time well spent.

Now for the new question. So far, when we built a class, its attributes held simple things: a name, a number. But an attribute is just a name pointing at a value, and a value can be anything, including another object. That opens up a new way to organise a program, and it is the most important design idea in this whole chapter.

The problem first. Imagine you are writing the order screen for a small bakery. Without objects that hold other objects, you might store one order as several parallel lists, one list per fact. Run this and read the answer carefully.

Parallel lists: an order the hard way
names = ["Croissant", "Bagel", "Muffin"] prices = [2.50, 1.80, 3.00] qtys = [2, 1] # oops: we forgot the quantity for the Muffin total = 0 for name, price, qty in zip(names, prices, qtys): total += price * qty print("Total:", total) print("Lines counted:", len(list(zip(names, prices, qtys))))

The order has three items, but the program quietly counted two and printed a total that is too low. Nothing crashed, so nothing warned us. The three lists must always stay the same length and in the same order, and nothing enforces that. Every new fact (a discount, a note like "no nuts") means yet another list to keep in step. Here zip stops at the shortest list, which is why the Muffin vanished.

The idea. Give each real-world thing its own small class, and let bigger things contain the smaller ones. A car has an engine. A bookshelf has books. A bakery order has order lines. We call this a has-a relationship, and the technique of building objects out of other objects is called composition. Think of a toy made of building bricks: the toy is one thing to you, but inside it is a set of smaller parts, each with its own job.

The smallest has-a: a Car has an Engine
class Engine: def __init__(self, horsepower): self.horsepower = horsepower def start(self): return f"Engine with {self.horsepower} hp is running" class Car: def __init__(self, name, engine): self.name = name self.engine = engine # a Car HAS an Engine motor = Engine(90) car = Car("Blue Beetle", motor) print(car.engine.horsepower) print(car.engine.start()) print(car.engine is motor)

Read car.engine.start() from left to right: "take the car, look at its engine attribute, then call start on that engine." Each dot moves one step deeper. Nothing new is happening in the language; it is the same attribute lookup you already know, repeated.

What Python does, line by line, for the last three lines of that program:

  • motor = Engine(90) builds one Engine object in memory. The name motor points at it.
  • car = Car("Blue Beetle", motor) builds a Car object. Python does not copy the engine. It hands the Car a reference, which is a pointer to the same Engine object.
  • Inside __init__, the line self.engine = engine stores that pointer in the car's engine attribute.
  • car.engine is motor asks "are these the very same object?" The answer is True, because both names point at one Engine.
Two names, one Engine object
  motor ──────────────┐
                      ▼
                 ┌──────────────────┐
                 │ Engine           │
                 │ horsepower: 90   │
                 └──────────────────┘
                      ▲
  car ─► ┌──────────────────────┐
         │ Car                  │
         │ name:   "Blue Beetle"│
         │ engine: ─────────────┘
         └──────────────────────┘
The car does not contain a copy of the engine; it holds an arrow to it. The variable motor and the attribute car.engine are two arrows to the same box.

You can look inside any object with vars(), which shows its attributes as a dictionary. The engine appears as just another value.

Peeking inside with vars()
class Engine: def __init__(self, horsepower): self.horsepower = horsepower class Car: def __init__(self, name, engine): self.name = name self.engine = engine car = Car("Blue Beetle", Engine(90)) print(list(vars(car))) print(vars(car.engine)) print(type(car.engine).__name__)

Delegation. Outside code should not have to reach through the car into the engine every time. A better design is for the Car to offer its own start() method and quietly pass the job to its engine. Handing a job to a part you contain is called delegation, like a manager asking a team member to do the task. The caller only knows the manager. This also shows a variation: what happens when two cars are given the same engine object?

Delegation, and one engine shared by two cars
class Engine: def __init__(self, hp): self.hp = hp def start(self): return f"{self.hp} hp engine running" class Car: def __init__(self, name, engine): self.name = name self.engine = engine def start(self): # delegation return f"{self.name}: " + self.engine.start() shared = Engine(90) alpha = Car("Alpha", shared) beta = Car("Beta", shared) print(alpha.start()) shared.hp = 120 # upgrade the one engine print(beta.start()) print(alpha.engine is beta.engine)

Both cars point at one engine, so upgrading it changed what beta reports. Sometimes that sharing is what you want (many orders pointing at one menu item). Sometimes it is a surprise. The other choice is to build a fresh part inside the class, as in self.engine = Engine(90), so each car owns its own engine. A useful rule: if the part is given to the class from outside, it may be shared; if the class creates it, the class owns it.

Back to the bakery. Here is the same order, rebuilt with composition. There are three small classes: a MenuItem (what we sell), an OrderLine (one item and how many), and an Order (the customer and all their lines). This is the running example for the rest of the chapter, so take a moment to read it slowly.

The bakery order, built from parts
class MenuItem: def __init__(self, name, price): self.name = name self.price = price class OrderLine: def __init__(self, item, quantity): self.item = item # an OrderLine HAS a MenuItem self.quantity = quantity def line_total(self): return self.item.price * self.quantity class Order: def __init__(self, customer): self.customer = customer self.lines = [] # an Order HAS OrderLines def add(self, item, quantity): self.lines.append(OrderLine(item, quantity)) def total(self): return sum(line.line_total() for line in self.lines) order = Order("Asha") order.add(MenuItem("Croissant", 2.50), 2) order.add(MenuItem("Muffin", 3.00), 1) print(order.total(), len(order.lines))
An Order is a tree of small objects
  Order ("Asha")
   ├── lines[0] ─► OrderLine (qty 2) ─► MenuItem ("Croissant", 2.5)
   └── lines[1] ─► OrderLine (qty 1) ─► MenuItem ("Muffin", 3.0)

  order.total()  asks each line:   line.line_total()
  line_total()   asks its item:    self.item.price
Each object knows only about the parts it holds. Order never looks at a price directly; it delegates to its lines, and each line delegates to its item.

Notice how the earlier problem disappeared. There is no way for a quantity to go missing, because a quantity lives inside the line that also holds the item. Adding a new fact later, such as a "no nuts" note, means adding one attribute to OrderLine, not another list to keep aligned.

Is-a or has-a? You now have two ways to relate classes, and choosing between them is a skill. Say the relationship out loud as a sentence. If "X is a kind of Y" sounds right, inheritance may fit. If "X has a Y" or "X is made of Ys" sounds right, use composition.

SentenceRight toolPython shape
A Dog is an Animalinheritance (is-a)class Dog(Animal)
A Car has an Enginecomposition (has-a)self.engine = engine
An Order has OrderLinescomposition (has-a)self.lines = []
An Order is a list?no, it only has a listsee section 4.2

Common mistakes. The first is forgetting self. when storing the part. Python happily creates a plain local variable that disappears when __init__ ends. Read the error this program produces:

Mistake 1: forgetting self. when storing the part
class Engine: def start(self): return "vroom" class Car: def __init__(self, engine): engine = engine # BUG: should be self.engine = engine car = Car(Engine()) try: print(car.engine.start()) except AttributeError as error: print("AttributeError:", error)

Without the try, you would see a traceback ending in AttributeError: 'Car' object has no attribute 'engine'. To read a traceback, start at the last line: it names the problem. Here it says the Car object has no attribute called engine, which points straight at __init__, where the attribute should have been set. The fix is self.engine = engine.

The second mistake is calling a method that the container never defined. The engine has start(), but the car does not, and Python does not search inside contained objects for you:

Mistake 2: expecting the container to know its parts' methods
class Engine: def start(self): return "vroom" class Car: def __init__(self, engine): self.engine = engine car = Car(Engine()) try: car.start() except AttributeError as error: print("AttributeError:", error) print(car.engine.start()) # works: go through the part

You have two fixes: call it through the part (car.engine.start()), or add a start() method to Car that delegates, as we did above. The second is usually nicer, because the caller no longer needs to know how the car is built inside.

Check yourself: A Library holds many Book objects. Is that inheritance or composition, and how would __init__ store the books?
Composition: a library has books, it is not a kind of book. Store them in a list attribute: self.books = [].
Check yourself: In the shared-engine example, what does alpha.engine is beta.engine tell you that alpha.engine == beta.engine might not?
is asks whether both names point at the exact same object. Without a custom __eq__, == gives the same answer for plain objects, but is is the direct way to ask about sharing.
Try it: In the bakery example, add a third line to the order and print order.lines[2].item.name. Then add a method describe() to OrderLine that returns text like "2 x Croissant".

Recap

  • An attribute can hold another object. That is a has-a relationship, called composition.
  • Parts are stored as references (arrows), not copies, so two containers can share one part.
  • Delegation means the container passes work to its parts, so callers only talk to the container.
  • Test the relationship with a sentence: "is a" suggests inheritance, "has a" suggests composition.
  • If a part is missing, read the last line of the traceback: it is almost always a forgotten self. or a method the container never defined.
4.2 — Prefer Composition Over Inheritance

In OOP 3 you learned that a child class inherits everything its parent has. That is powerful, and like most powerful tools it is easy to use in the wrong place. Experienced programmers repeat a piece of advice so often that it has become a slogan: prefer composition over inheritance. It does not say "never inherit". It says: when you are unsure which one fits, start with composition, because it is harder to get wrong. This section shows you why by breaking two plausible inheritance designs and then fixing them.

The problem first. Suppose you are writing a nature game. It seems natural that a Penguin is a Bird, so you make it a child class. Every Bird can fly, so the parent has a fly() method. Here is where it goes wrong.

A plausible tree that breaks: Penguin is a Bird
class Bird: def __init__(self, name): self.name = name def fly(self): return f"{self.name} flaps into the sky" class Penguin(Bird): def fly(self): raise NotImplementedError("penguins cannot fly") def release(birds): for bird in birds: print(bird.fly()) try: release([Bird("Robin"), Penguin("Pingu")]) except NotImplementedError as error: print("NotImplementedError:", error)

The robin flew, and then the program crashed on the penguin. The function release was written to accept birds, and the tree told it every Bird can fly, so it trusted the tree. A child class that cannot honour everything its parent promises is a broken promise. The rule of thumb is: anywhere the parent works, the child must work too. If it does not, the "is-a" sentence was only true in casual speech, not in your program.

You can patch it in three ways, and all are bad. You can raise an error, as above, which just moves the crash. You can make Penguin.fly() return a fake message, which hides the lie. Or you can add if isinstance(bird, Penguin) checks in every place that uses birds, which spreads the mess across the whole program. The real mistake is upstream: "can fly" is not a property of all birds, so it does not belong in the Bird parent.

The idea. Instead of baking behaviour into a family tree, treat behaviours as separate small parts and give each bird the part it needs. Think of a game character who can be handed a sword, a bow, or a broom. The character is one class, and the tools are separate objects it holds. Here a Bird has a way of moving.

The composition rewrite: a Bird has a way of moving
class Flying: def move(self): return "flaps into the sky" class Swimming: def move(self): return "glides through the water" class Bird: def __init__(self, name, mover): self.name = name self.mover = mover # the part that knows how to move def travel(self): return f"{self.name} {self.mover.move()}" for bird in [Bird("Robin", Flying()), Bird("Pingu", Swimming())]: print(bird.travel())
  • Python builds a Flying object and a Bird named Robin, and stores the Flying object in robin.mover.
  • It builds a Swimming object and a Bird named Pingu with that mover.
  • In the loop, bird.travel() runs. It does not know or care which kind of mover it has; it just asks self.mover.move().
  • Each mover answers in its own way. There is no crash, no if, and no broken promise, because Bird never promised flight. It promised travel.
Inheritance tree versus composition
  INHERITANCE (breaks)          COMPOSITION (works)

     Bird                          Bird ──has-a──► mover
      │ fly()  "all fly"           travel()         ├─ Flying.move()
      ▼                                             └─ Swimming.move()
   Penguin  ✗ cannot fly
With inheritance, a behaviour is fixed the moment you pick the parent. With composition, the behaviour is a part you can choose, and even swap later.

Because the mover is just an attribute, you can even swap it while the program runs. Try adding this to the example: pingu.mover = Flying() and call travel() again. Composition makes that natural. With inheritance you would have to change the class of an object, which is awkward and rarely a good idea.

A common beginner mistake here is forgetting to supply the part when you create the object. Python reports it clearly:

Mistake: creating a Bird without giving it a mover
class Bird: def __init__(self, name, mover): self.name = name self.mover = mover try: Bird("Sam") except TypeError as error: print("TypeError:", error)

The message says Bird.__init__() missing 1 required positional argument: 'mover'. In plain words: "you called the constructor but skipped a value it requires". The name in quotes tells you which one. If a part is optional, give it a default value in the signature; if it is required, this error is a helpful reminder.

A second broken tree: Stack(list). A stack is a pile where you only touch the top item, like plates in a cafeteria: last in, first out. Python's built-in list can do that job, so it is tempting to write "a Stack is a list" and inherit. Watch what you accidentally inherit.

Stack(list): all of list's methods come along for free
class Stack(list): def push(self, item): self.append(item) def peek(self): return self[-1] plates = Stack() plates.push("plate 1") plates.push("plate 2") plates.push("plate 3") plates.insert(0, "sneaky plate") # slid one under the bottom! plates.sort() # re-ordered the pile! print(plates)

A stack is defined by refusing those moves. Inheriting from list gave the Stack a dozen public methods it should never have (insert, sort, remove, reverse...). Anyone using the class can break the rule, and you cannot promise "last in, first out" anymore. The class has a wide interface (many doors) when it should have a narrow interface (only the doors you chose).

The composition rewrite: a Stack has a list
class Stack: def __init__(self): self._items = [] # hidden inside; only our methods touch it def push(self, item): self._items.append(item) def pop(self): return self._items.pop() def peek(self): return self._items[-1] def __len__(self): return len(self._items) s = Stack() s.push("plate 1") s.push("plate 2") print(len(s), s.peek(), s.pop(), len(s)) try: s.insert(0, "sneaky plate") except AttributeError as error: print("AttributeError:", error)

Now the sneaky move is impossible, and the error is exactly what we want: 'Stack' object has no attribute 'insert'. The list still does the hard work, but it is a private detail behind four small doors. The special method __len__ is what lets the built-in len(s) work on our class; we add only the special methods we choose to support.

Wide interface versus narrow interface
  Stack(list)  IS a list             Stack  HAS a list
  ┌────────────────────┐             ┌────────────────────┐
  │ push  peek         │             │ push  pop  peek    │
  │ append insert sort │             │ len()              │
  │ remove reverse ... │             │  ┌──────────────┐  │
  │ (a dozen+ doors)   │             │  │ _items (list)│  │
  └────────────────────┘             │  └──────────────┘  │
                                     └────────────────────┘
Composition lets you expose only the operations that make sense, so the object cannot be used in ways you did not intend.

The same reasoning applies to our bakery. It is tempting to write class Order(list) because an order is "a list of lines". But then order.append("banana") is accepted, and so is a quantity of minus five, because a plain list checks nothing. Compare it with an Order that has a list:

Order that has a list can guard its rules
class Order: def __init__(self, customer): self.customer = customer self._lines = [] def add(self, name, quantity): if quantity <= 0: raise ValueError("quantity must be positive") self._lines.append((name, quantity)) def __len__(self): return len(self._lines) order = Order("Asha") order.add("Croissant", 2) try: order.add("Muffin", 0) except ValueError as error: print("ValueError:", error) print(len(order))

So when is inheritance right? Use it when the "is-a" sentence is true without exceptions, when the child really can do everything the parent can, and when you want code to treat a whole family the same way (the polymorphism you met in OOP 3). A SavingsAccount really is a BankAccount. A Stack is not a list. If you catch yourself inheriting only to reuse some code, that is the signal to use composition.

A quick decision testAsk two questions. (1) "Can I use the child anywhere I can use the parent, with no surprises?" If no, do not inherit. (2) "Am I inheriting mostly to save typing?" If yes, hold a part instead.
Check yourself: A Square class inherits from Rectangle, which has set_width() and set_height() that can differ. Why is this a risky tree?
A square must keep width and height equal, so it cannot honour a promise to set them independently. Code written for Rectangles could break when handed a Square. Composition or two separate classes is safer.
Check yourself: Why did Stack with a hidden _items list solve the "sneaky plate" problem?
Outside code can only use the methods the Stack defines (push, pop, peek, len). Methods such as insert simply do not exist on it, so Python raises AttributeError.

Recap

  • A child class must be usable wherever its parent is. If it cannot keep the parent's promises (Penguin and fly()), inheritance was the wrong tool.
  • Composition breaks behaviour into small parts an object holds, which you can choose or swap.
  • Inheriting from a built-in like list hands you a wide interface you did not want. Holding a private list gives a narrow one.
  • Inherit for true "is-a" families and shared polymorphic behaviour. Compose when you mainly want to reuse code or add abilities.
  • A missing constructor part shows up as TypeError: ... missing 1 required positional argument.
4.3 — Too Much Typing: Meet @dataclass

Many classes exist mainly to hold a few facts together: a menu item is a name and a price, an order line is an item and a quantity. For these "data holder" classes you end up writing the same boring code every time. This section shows the boring code, lets you feel how annoying it is, and then introduces a Python feature that writes it for you.

The problem first. Here is a plain MenuItem class, then two identical-looking items. Read what Python says about them.

A plain class is a poor communicator
class MenuItem: def __init__(self, name, price): self.name = name self.price = price a = MenuItem("Croissant", 2.50) b = MenuItem("Croissant", 2.50) print(str(a)[:24]) print(a == b) print(a is b) print(a.name == b.name and a.price == b.price)

Two things are unhelpful. First, printing an item gives text that starts with <__main__.MenuItem object at 0x..., followed by a memory address that changes every run (we cut it off with [:24], so the example prints the same every time). It tells you nothing about the item. Second, a == b is False, even though both items hold the same facts. By default Python treats two objects as equal only if they are the very same object, which is what is checks.

The fix from OOP 2 is to write the special methods __repr__ (how an object describes itself) and __eq__ (what "equal" means). Watch how much code that takes for just three facts.

Doing it by hand: __init__, __repr__ and __eq__
class MenuItem: def __init__(self, name, price, vegan): self.name = name self.price = price self.vegan = vegan def __repr__(self): return f"MenuItem(name={self.name!r}, price={self.price!r}, vegan={self.vegan!r})" def __eq__(self, other): return (self.name, self.price, self.vegan) == (other.name, other.price, other.vegan) print(MenuItem("Bagel", 1.8, True)) print(MenuItem("Bagel", 1.8, True) == MenuItem("Bagel", 1.8, True))

It works, but look at the pain. Each field name appears seven times in the class. Add a fourth field, say gluten_free, and you must remember to edit three separate places. Forget one and you get a silent bug: an __eq__ that ignores the new field will call two different items equal. That repetition is called boilerplate: code you must write but that carries no new ideas.

The idea. Python's standard library has a tool called dataclasses. You list the fields once, and it writes __init__, __repr__ and __eq__ for you. To use it you need one new piece of syntax. A decorator is a line that starts with @ and sits directly above a class (or a function). It hands the class to some helper, which adds features and gives the class back. Think of a decorator as sticking an extra gadget onto your creation before it leaves the workshop.

The same class with @dataclass
from dataclasses import dataclass @dataclass class MenuItem: name: str price: float item = MenuItem("Croissant", 2.50) print(item) print(item == MenuItem("Croissant", 2.50)) print(item is MenuItem("Croissant", 2.50)) print(vars(item))

Four lines of class body and we get a readable printout, a meaningful ==, and a normal object underneath (vars shows its attributes just like before). The is check still says False: equal values, but two separate objects. Equality asks "same facts?"; identity asks "same object?".

What Python does, step by step:

  • Python reads the class body and notices two lines of the form name: type. These are annotations, a colon and a type placed after a variable name. In a dataclass, each annotated line becomes a field, in the order written.
  • The @dataclass decorator receives the finished class and reads its list of fields.
  • It generates __init__(self, name, price), which stores each argument as an attribute of the same name.
  • It generates __repr__, which prints MenuItem(name=..., price=...), and __eq__, which compares all the fields in order.
  • It returns the improved class, and the name MenuItem now points at it. From here on it behaves like any class you wrote yourself.
What @dataclass writes for you
  You write:                   Python adds:
  ┌─────────────────────┐      ┌──────────────────────────────────┐
  │ @dataclass          │      │ def __init__(self, name, price): │
  │ class MenuItem:     │ ───► │     self.name = name             │
  │     name: str       │      │     self.price = price           │
  │     price: float    │      │ def __repr__(self): ...          │
  └─────────────────────┘      │ def __eq__(self, other): ...     │
                               └──────────────────────────────────┘
You state the facts once. The boilerplate is generated from them, so it can never fall out of step with the field list.

Defaults. A field can have a default value, written with =, and then you may leave that argument out. There is one rule: fields with defaults must come after fields without. Python enforces it the same way it does for normal function parameters.

Default values, and the ordering rule
from dataclasses import dataclass @dataclass class OrderLine: name: str price: float quantity: int = 1 print(OrderLine("Bagel", 1.8)) print(OrderLine("Muffin", 3.0, 4)) try: @dataclass class Broken: quantity: int = 1 name: str except TypeError as error: print("TypeError:", error)

The last message, non-default argument 'name' follows default argument, means "you gave quantity a default and then asked for name without one". Move the field with a default to the end and it goes away.

The mutable-default trap. Now an Order needs a list of lines, and a new order should start with an empty list. The obvious attempt is lines: list = []. To see why Python forbids that, first look at the same idea in an ordinary function. This is one of the most famous surprises in the language.

Why a shared default list is dangerous
def add_line(line, lines=[]): lines.append(line) return lines print(add_line("Bagel")) print(add_line("Muffin")) # expected ['Muffin'] ... but!

The second call printed ['Bagel', 'Muffin']. A default value is created once, when the function is defined, and every call reuses that same list. One order's items leak into the next. A dataclass would have the same problem if it allowed a shared list, so it refuses. The fix is field(default_factory=list). A factory is a recipe for making something: default_factory takes a function (here list, which builds a new empty list when called), and the dataclass calls it once per new object.

default_factory gives each order its own list
from dataclasses import dataclass, field try: @dataclass class Oops: customer: str lines: list = [] except ValueError as error: print("ValueError:", error) @dataclass class Order: customer: str lines: list = field(default_factory=list) a = Order("Asha") b = Order("Ben") a.lines.append("Bagel") print(a) print(b) print(a.lines is b.lines)

Read the error: mutable default <class 'list'> for field lines is not allowed: use default_factory. Python tells you the problem (a mutable value, one that can change, is used as a default) and the cure in the same sentence. Afterwards Asha's order and Ben's order each hold a separate list, and a.lines is b.lines is False. The rule to remember: numbers, strings and None are safe defaults; lists, dicts and sets need default_factory.

The same trap exists in hand-written classes. def __init__(self, customer, lines=[]) makes every order share one list, and unlike a dataclass, plain Python will not warn you. That is one more reason to like dataclasses.

A subtle mistake: forgetting the annotation. Only annotated lines become fields. Write price = 2.5 without : float and it is quietly an ordinary class attribute instead:

Mistake: a line without an annotation is not a field
from dataclasses import dataclass @dataclass class MenuItem: name: str price = 2.5 # no ": float", so NOT a field try: MenuItem("Bagel", 3.0) except TypeError as error: print("TypeError:", error) print(MenuItem("Bagel"))

The error MenuItem.__init__() takes 2 positional arguments but 3 were given counts the hidden self too: 2 accepted (self and name), 3 supplied (self, name, price). When a dataclass rejects an argument you expected it to take, check that the field has a colon and a type. Another beginner slip is forgetting from dataclasses import dataclass, which gives NameError: name 'dataclass' is not defined.

Types here are labels, not rulesWriting price: float does not stop someone passing a string. Python does not check. The annotation tells readers, and tools, what you intend. Section 4.6 covers exactly what type hints do and do not do.

A single list object would be shared by every instance, so changes to one order would appear in all of them. Use lines: list = field(default_factory=list) so each object gets its own new list.

Recap

  • Plain classes print an unhelpful address and treat equal-looking objects as different unless you write __repr__ and __eq__.
  • @dataclass (a decorator) reads annotated fields and writes __init__, __repr__ and __eq__ for you.
  • Only lines like name: type become fields, in the order written. Fields with defaults must come last.
  • Never use a list, dict or set as a plain default. Use field(default_factory=list) so each object gets a fresh one.
  • == compares values; is asks whether two names point at the same object.
4.4 — More Dataclass Power: Frozen, Ordered, Checked

Basic dataclasses save typing. The extra options in this section save you from real bugs. Each one is switched on by putting a setting inside the brackets of the decorator, like @dataclass(frozen=True), or by adding a small special method. We will meet five tools, one at a time, always starting with the problem each one solves.

1. Frozen: objects that cannot change. Imagine a menu item shared by fifty orders. If some part of the program quietly changes its price from 2.50 to 9.99, every order that points at it changes too, and finding the culprit is miserable. What you want is a fact that is immutable, meaning it cannot be changed after it is created. A frozen dataclass gives you exactly that. Tuples and strings already work this way; frozen=True gives the same protection to your own classes.

frozen=True locks the fields
from dataclasses import dataclass, FrozenInstanceError @dataclass(frozen=True) class MenuItem: name: str price: float item = MenuItem("Croissant", 2.5) try: item.price = 9.99 except FrozenInstanceError as error: print("FrozenInstanceError:", error) print(item)

Python refuses with FrozenInstanceError: cannot assign to field 'price' and the item keeps its old price. A traceback for this error ends with that line. The name is long but the meaning is short: "this object is frozen, you may not assign to its fields." It is a special kind of AttributeError, so it is also caught by except AttributeError.

2. Hashing: frozen objects can be dictionary keys. A dictionary or a set finds things quickly by turning each key into a number called a hash, a fingerprint of the value. That only works if the fingerprint never changes. If the value could change after you stored it, the dictionary would look in the wrong drawer and lose it. So Python refuses to hash an ordinary dataclass, and allows it once you freeze the class.

Only frozen dataclasses can be dict keys or set members
from dataclasses import dataclass @dataclass class Loose: name: str @dataclass(frozen=True) class Fixed: name: str try: stock = {Loose("Bagel"): 10} except TypeError as error: print("TypeError:", error) stock = {Fixed("Bagel"): 10, Fixed("Muffin"): 4} print(stock[Fixed("Bagel")]) print(len({Fixed("Bagel"), Fixed("Bagel"), Fixed("Muffin")}))

The error unhashable type: 'Loose' means "I cannot fingerprint this, because it can change." With the frozen class, a new Fixed("Bagel") finds the stored one, because equal frozen objects have equal hashes. In the set, the duplicate Bagel collapsed into one, so the length is 2. A menu item with a stock count is a natural use.

3. Order: sorting your own objects. Sort a list of plain numbers and it just works. Sort a list of your own objects and Python does not know which one is "smaller". The setting order=True teaches it: objects compare field by field, in the order the fields were written, like sorting a phone book by surname and then by first name.

order=True lets you sort and compare
from dataclasses import dataclass @dataclass(order=True) class MenuItem: name: str price: float @dataclass class Plain: name: str items = [MenuItem("Muffin", 3.0), MenuItem("Bagel", 1.8), MenuItem("Bagel", 1.5)] for item in sorted(items): print(item) print(MenuItem("Bagel", 1.8) < MenuItem("Muffin", 3.0)) try: Plain("a") < Plain("b") except TypeError as error: print("TypeError:", error)
How order=True compares two objects
  MenuItem("Bagel", 1.8)  vs  MenuItem("Bagel", 1.5)

  step 1: compare name   "Bagel" == "Bagel"  -> tie, keep going
  step 2: compare price  1.8 > 1.5           -> first is larger

  Same as comparing tuples ("Bagel", 1.8) and ("Bagel", 1.5)
Field order matters. Put the field you most want to sort by first. If you want a different sort just once, use sorted(items, key=lambda i: i.price) instead.

The bakery items came out sorted by name, and the two Bagels were separated by price. Without order=True, Python answers '<' not supported between instances of 'Plain' and 'Plain': "you asked which is smaller, but I was never told how to decide."

4. __post_init__: checking and preparing values. A dataclass writes __init__ for you, so where do you put the checks you would normally write in it? Python gives you a hook: if the class defines a method named __post_init__, the generated __init__ calls it right after storing all the fields. Use it to reject bad values or to tidy them.

__post_init__ validates and derives values
from dataclasses import dataclass, field @dataclass class MenuItem: name: str price: float def __post_init__(self): if self.price < 0: raise ValueError(f"price cannot be negative: {self.price}") self.name = self.name.strip().title() @dataclass class OrderLine: item: MenuItem quantity: int total: float = field(init=False) # not a constructor argument def __post_init__(self): self.total = self.item.price * self.quantity print(MenuItem(" croissant ", 2.5)) try: MenuItem("Bagel", -1) except ValueError as error: print("ValueError:", error) print(OrderLine(MenuItem("Muffin", 3.0), 4))
  • You call MenuItem(" croissant ", 2.5). The generated __init__ stores the two arguments in self.name and self.price.
  • Right afterwards it calls self.__post_init__().
  • Your method checks the price (raising ValueError if it is negative) and cleans the name to "Croissant".
  • For OrderLine, field(init=False) says "this field exists and shows in the printout, but you do not pass it in". Your __post_init__ fills it with the price times the quantity.

One caution about derived fields. The total is calculated once, when the object is created. If you later change line.quantity, the stored total does not update, so it goes stale. When a value must always be current, write a method instead (as we did with line_total() in section 4.1).

Here is a mistake that Python will not warn you about. If you misspell the hook, for example __post_init without the final underscores, it is just another method that nobody calls:

Mistake: a misspelled hook silently never runs
from dataclasses import dataclass @dataclass class MenuItem: name: str price: float def __post_init(self): # typo: needs two trailing underscores if self.price < 0: raise ValueError("negative price") print(MenuItem("Bagel", -5)) # accepted, no error!

No error, and a negative price got through. Whenever a validation "does not fire", check the spelling of __post_init__ first: two underscores before, two after.

5. asdict and replace. Two helper functions from the same module finish the toolkit. asdict(obj) turns a dataclass into an ordinary dictionary, including any dataclasses nested inside it. That is handy when you want to print, save or send the data. replace(obj, field=value) makes a modified copy and leaves the original untouched, which is how you "change" a frozen object.

asdict makes a dict, replace makes a changed copy
from dataclasses import dataclass, asdict, replace @dataclass(frozen=True) class MenuItem: name: str price: float @dataclass class OrderLine: item: MenuItem quantity: int line = OrderLine(MenuItem("Bagel", 1.8), 3) print(asdict(line)) dearer = replace(line.item, price=2.0) print(dearer) print(line.item) print(dearer is line.item)

The bakery raised the Bagel's price, yet the old object is still intact, so orders already placed keep the price they were made with. That is often exactly what you want in a shop.

Dataclass or normal class? Neither is better everywhere. Use this table as a starting rule.

SituationChoose

A word about moneyWe keep prices as decimals like 2.5 to keep the examples short. Real shops usually store whole cents (250) or use Python's decimal module, because floating-point numbers can produce tiny rounding surprises such as 0.1 + 0.2.
Check yourself: Why can Fixed("Bagel") be a dictionary key but Loose("Bagel") cannot?
Dictionary keys need a hash that never changes. A frozen dataclass cannot change after creation, so Python allows a hash. A normal dataclass is mutable, so it is marked unhashable (TypeError: unhashable type).
Check yourself: You change line.quantity after creating an OrderLine whose total was set in __post_init__. Is total still right?
No. __post_init__ ran once at creation, so total keeps the old value. Use a method that recalculates when you need an always-current value.

Recap

  • frozen=True makes fields read-only (FrozenInstanceError) and lets the object be a dict key or set member.
  • order=True adds <, > and sorting, comparing fields in the order they are written.
  • __post_init__ runs right after the generated __init__: use it to validate or to compute derived fields (field(init=False)).
  • asdict gives a plain dictionary; replace gives a modified copy and leaves the original alone.
  • Dataclasses suit "holders of facts". Normal classes suit objects that mostly do work and hide their insides.
4.5 — Enums: Named Choices Instead of Magic Strings

An order in our bakery moves through stages: it is placed, then paid, then ready, then collected. Something has to remember which stage it is in. The quickest idea is a string, such as "pending" or "shipped". This section shows why that quick idea causes trouble and how Python's Enum fixes it.

The problem first. A plain string looks harmless until one letter goes wrong. Run this and predict the output before you look.

Magic strings fail silently
class Order: def __init__(self): self.status = "pending" order = Order() order.status = "shiped" # typo: one "p" missing if order.status == "shipped": print("On its way!") else: print("Still waiting?!")

Python found nothing wrong. A string is just text, and "shiped" is perfectly good text that happens to match no stage. The program took the wrong branch and told the customer nothing useful. Strings used this way are called magic strings: special words that only work if every line of the program spells them identically, with nothing checking that they do. The bug shows up far from the typo, and the error message never appears.

The idea. An enumeration (or Enum) is a small class that lists all the allowed choices as named constants. Think of a traffic light: it can only be red, amber or green, and everyone shares those three names. You define the list once, and after that Python protects you from inventing a fourth colour by accident.

Your first Enum
from enum import Enum, auto class Status(Enum): PLACED = auto() PAID = auto() READY = auto() COLLECTED = auto() s = Status.PAID print(s) print(s.name, s.value) print(type(s).__name__) print(s is Status.PAID)

Here auto() means "pick the next number for me" (1, 2, 3, ...). Each line inside the class creates one member: a single named choice. Every member has a name (the text you wrote, like PAID) and a value (the number Python picked). Member names are written in CAPITALS by convention, to show they are fixed constants.

  • Python reads the class body and creates exactly one object for each line: one for PLACED, one for PAID, and so on.
  • It stores them on the class, so you reach them as Status.PAID.
  • Asking for Status.PAID a second time returns the same object. Members are singletons, meaning there is only ever one of each.
  • Because there is only one, the right way to compare members is with is: s is Status.PAID. (== works too and gives the same answer, but is says exactly what you mean.)
An Enum holds exactly one object per choice
  variables               class Status: one object per choice

  s ───────────┐          ┌──────────────────────────┐
               ├────────► │ PAID = 2                 │
  order.status ┘          └──────────────────────────┘

  (PLACED, READY, COLLECTED are three other single objects)
No matter how many variables or orders point at Status.PAID, they all point at the same single box. There is no way to create a fifth stage by mistake.

Variations. Enums are also easy to loop over and to look up. You can find a member by its name (square brackets) or by its value (round brackets), which is useful when data arrives as text or a number from a file.

Looping over and looking up members
from enum import Enum, auto class Status(Enum): PLACED = auto() PAID = auto() READY = auto() COLLECTED = auto() for status in Status: print(status.value, status.name) print(len(Status)) print(Status["READY"]) print(Status(2))

You can also choose the values yourself instead of using auto(). Strings are a common choice when the value must be saved to a file, like SHIPPED = "shipped". Then Color("red") turns the saved text back into the member.

Common mistakes, with the real messages. Now the payoff: each kind of slip gives a loud, clear error instead of silent nonsense.

Enums turn silent bugs into clear errors
from enum import Enum, auto class Status(Enum): PLACED = auto() PAID = auto() try: Status.SHIPED # typo in a member name except AttributeError as error: print("AttributeError:", error) try: Status(9) # no member has this value except ValueError as error: print("ValueError:", error) try: Status["shipped"] # no member has this name except KeyError as error: print("KeyError:", error) print(Status.PAID == "PAID") # a member is not a string

Read them one at a time. The first, type object 'Status' has no attribute 'SHIPED', is the typo from our problem, now caught the instant that line runs. The second, 9 is not a valid Status, tells you a number matches no member. The third is a KeyError because lookup by name works like a dictionary. The last line prints False, and this one surprises people: Status.PAID == "PAID" is False, because a member is its own kind of object, not a string. Compare a member with another member, never with a string or a number. Ordering comparisons like Status.PAID < Status.READY raise a TypeError for the same reason; members are choices, not numbers.

Enums inside a real class. Now we can give the bakery Order a proper status. A dataclass field can be an Enum member, and the class can protect its own rules, such as "you can only pay for an order that is still PLACED".

An Order with a Status and a rule
from enum import Enum, auto from dataclasses import dataclass class Status(Enum): PLACED = auto() PAID = auto() READY = auto() @dataclass class Order: customer: str status: Status = Status.PLACED def pay(self): if self.status is not Status.PLACED: raise ValueError(f"cannot pay an order that is {self.status.name}") self.status = Status.PAID order = Order("Asha") print(order) order.pay() print(order.status) try: order.pay() except ValueError as error: print("ValueError:", error)

Notice how much reads like plain English: self.status is not Status.PLACED. A misspelled stage cannot sneak in, and the error message can use self.status.name to give a friendly word. When a class has many stages and rules, a small dictionary of allowed moves keeps the logic in one place:

A table of allowed moves
from enum import Enum, auto class Status(Enum): PLACED = auto() PAID = auto() READY = auto() COLLECTED = auto() CANCELLED = auto() ALLOWED = { Status.PLACED: [Status.PAID, Status.CANCELLED], Status.PAID: [Status.READY, Status.CANCELLED], Status.READY: [Status.COLLECTED], Status.COLLECTED: [], Status.CANCELLED: [], } def can_move(current, target): return target in ALLOWED[current] print(can_move(Status.PLACED, Status.PAID)) print(can_move(Status.READY, Status.CANCELLED)) print([s.name for s in ALLOWED[Status.PAID]])
The order life cycle as a table of allowed moves
  PLACED ──► PAID ──► READY ──► COLLECTED
    │          │
    └──────────┴──► CANCELLED        (no way back out of the last two)
Each arrow is one entry in the ALLOWED dictionary. Notice that the Enum members are used as dictionary keys; they can be, because each member is a single unchanging object.
Check yourself: Why is order.status == "paid" a bug when order.status is an Enum member?
A member is not a string, so the comparison is always False, even when the order really is paid. Compare against the member: order.status is Status.PAID.
Check yourself: What is the difference between Status["PAID"] and Status(2) in our Enum?
Square brackets look a member up by name; round brackets look it up by value. Both return Status.PAID in our example.
Try it: Add a member REFUNDED = auto() to the Enum and rerun the looping example. Then change one member to use a string value such as PAID = "paid" and print Status("paid").

Recap

  • Magic strings fail silently: a typo like "shiped" is valid text, so nothing warns you.
  • An Enum lists the allowed choices once. Each member has a name and a value, and there is exactly one object per member.
  • Compare members with is (or ==) against other members, never against strings or numbers.
  • Typos and bad values now raise AttributeError, ValueError or KeyError immediately, at the line that caused them.
  • Enums make status fields, allowed-move tables and readable error messages easy.
4.6 — Type Hints on Classes: Talking to Readers and Tools

You have already written annotations such as name: str in dataclasses. Those are called type hints: notes that say what kind of value something is supposed to hold. This section explains what hints are good for, how to read the more complicated ones, and, just as important, what they cannot do. Many beginners assume they are a safety net. They are not, and it is worth seeing that with your own eyes.

The problem first. Look at a function with no hints at all: def add(self, item, quantity=1). To use it you must guess. Is item a name like "Bagel" or a whole MenuItem object? Is quantity the number 3 or the text "3"? Does it return something? You would have to open the function and read its body. In a class with fifteen methods, that reading adds up. Hints answer those questions right in the signature.

The idea. A hint is a colon and a type after a name, or an arrow and a type after a function's parentheses. Think of the labels on kitchen jars: the label does not change what is inside, but it stops you grabbing salt when you wanted sugar. Here is the bakery order again, fully labelled.

Type hints on a small class family
from dataclasses import dataclass, field @dataclass class MenuItem: name: str price: float @dataclass class OrderLine: item: MenuItem quantity: int def line_total(self) -> float: return self.item.price * self.quantity @dataclass class Order: customer: str lines: list[OrderLine] = field(default_factory=list) note: str | None = None def add(self, item: MenuItem, quantity: int = 1) -> None: self.lines.append(OrderLine(item, quantity)) print(Order.__annotations__) print(OrderLine.line_total.__annotations__)

Now read the shapes one at a time. price: float says "a decimal number". -> float after line_total(self) says "this method gives back a float". -> None after add says "this method returns nothing; it works by changing the order". list[OrderLine] reads as "a list of OrderLine objects". Square brackets name what is inside the container, and the same pattern works for others: dict[str, int] is "a dictionary from text to whole numbers" and tuple[float, float] is "a pair of decimals". Finally, str | None is read "a string or None" (the bar means "or"). It marks a value that might be missing.

The last two lines of the program print the hints Python stored, a dictionary named __annotations__. That proves the hints are real data attached to the class, and that is how tools such as your editor read them.

Who reads your type hints?
  your hints ──┬──► Python at run time   ... ignores them
               ├──► your editor / mypy   ... autocompletes, warns
               └──► your teammates       ... read them
Hints are a communication tool. Only the second and third readers act on them; the running program does not.

What hints do NOT do. This is the most important sentence in the section: Python does not enforce type hints when the program runs. The hint quantity: int is a promise you write down, not a lock. Run this and see what happens when the promise is broken.

Hints are not enforced
from dataclasses import dataclass @dataclass class MenuItem: name: str price: float @dataclass class OrderLine: item: MenuItem quantity: int def line_total(self) -> float: return self.item.price * self.quantity line = OrderLine(MenuItem("Bagel", 1.8), "3") # a string, not an int! print(line) try: line.line_total() except TypeError as error: print("TypeError:", error)
  • Python creates the OrderLine with quantity="3". The hint said int, but nothing checks, so the object is built and printed without complaint. The quotes around 3 in the printout are the only clue.
  • Later, line_total() multiplies 1.8 * "3". Python cannot multiply a decimal by text.
  • The crash is TypeError: can't multiply sequence by non-int of type 'float'. It appears far from the real mistake, at the moment of the calculation, not where the bad value went in.

A checker such as mypy (a separate free tool, not part of Python itself) would have flagged the line that passed "3" before you ever ran the program. Many editors do a lighter version of this check as you type. If you want run-time protection, you write it yourself, for example with an if not isinstance(quantity, int) check in __post_init__, as we did for prices in 4.4.

Reading X | None properly. A value that "might be missing" needs special care. A function that searches a menu returns an item if it finds one, and None if it does not. The hint MenuItem | None is a warning to every caller: "check before you use it."

Handling a value that might be None
from dataclasses import dataclass @dataclass class MenuItem: name: str price: float MENU = [MenuItem("Bagel", 1.8), MenuItem("Muffin", 3.0)] def find_item(name: str) -> MenuItem | None: for item in MENU: if item.name == name: return item return None missing = find_item("Pizza") try: print(missing.price) # forgot to check! except AttributeError as error: print("AttributeError:", error) if missing is None: print("not on the menu") else: print(missing.price)

The first attempt gives one of the most common errors in Python: AttributeError: 'NoneType' object has no attribute 'price'. Read it as "you asked None for a price, and None has no such thing." The hint on find_item is exactly what tells a reader, or a checker, to test if missing is None first. Use is None (not == None) for this test, because there is only ever one None object.

How much should you annotate? Add hints where they help a reader most: the fields of a dataclass, the parameters and return types of methods other code will call. You do not need a hint on every tiny local variable. Two habits keep them useful. Keep them accurate (a wrong hint is worse than none), and keep them simple. If a hint becomes hard to read, that is often a sign the function is doing too much.

  • Read list[X] as "a list of X" and X | None as "an X, or nothing".
  • Python does not enforce hints when the program runs. A wrong type crashes later, far from the mistake.
  • Editors and checkers such as mypy use hints to warn you before you run the program.
  • When a hint says | None, check is None before using the value, or you will meet 'NoneType' object has no attribute.
4.7 — Three Design Principles in Plain Words

A design principle is a rule of thumb that experienced programmers use to keep code easy to change. None of them is a law, and you can break them on purpose. But each one grows out of a real pain, and once you have felt the pain the rule makes sense. We will take three of the most useful, one at a time, each with a small "before" that hurts and an "after" that does not. To keep the examples short, an order line is stored as a tuple (name, price, quantity) here.

Principle 1: single responsibility. A class should have one job, or as programmers say, one reason to change. Think of a restaurant: the cook cooks, the cashier takes payment. If one person did everything, changing the till software would disturb the cooking. Here is a bakery Order that has slowly become a "do-everything" class.

Before: an Order that does three jobs
class Order: def __init__(self, customer): self.customer = customer self.lines = [] # (name, price, quantity) def add(self, name, price, quantity): self.lines.append((name, price, quantity)) def total(self): return sum(price * qty for name, price, qty in self.lines) def receipt(self): # job 2: formatting text rows = [f"{qty} x {name} {price * qty:.2f}" for name, price, qty in self.lines] return "\n".join(rows) + f"\nTOTAL {self.total():.2f}" def save(self): # job 3: storage return f"saved order for {self.customer}" order = Order("Asha") order.add("Croissant", 2.5, 2) order.add("Muffin", 3.0, 1) print(order.receipt())

It works today. The trouble comes later. The shop wants a shorter receipt for the till screen, so you edit Order. The shop moves from files to a database, so you edit Order again. Every change, for three unrelated reasons, lands in the same class, and each edit risks breaking the pricing logic that had nothing to do with it. A quick test: describe the class in one sentence. If you need the word "and" ("it stores items and formats receipts and saves files"), it probably has too many jobs.

After: the Order only knows about orders
class Order: def __init__(self, customer): self.customer = customer self.lines = [] def add(self, name, price, quantity): self.lines.append((name, price, quantity)) def total(self): return sum(price * qty for name, price, qty in self.lines) def short_receipt(order): return f"{order.customer}: {order.total():.2f}" def long_receipt(order): rows = [f"{qty} x {name} {price * qty:.2f}" for name, price, qty in order.lines] return "\n".join(rows) + f"\nTOTAL {order.total():.2f}" order = Order("Asha") order.add("Croissant", 2.5, 2) order.add("Muffin", 3.0, 1) print(short_receipt(order)) print(long_receipt(order))

The receipt formats moved into their own small functions. Adding a third format touches neither Order nor the other formats. (A function is enough here; a class is fine when the formatter needs its own settings.) The warning on the other side: do not shatter everything into tiny classes. "One responsibility" means one reason to change, not one method per class.

Principle 2: tell, don't ask. The idea is that you should tell an object what you want done and let it apply its own rules, rather than asking for its data, deciding yourself, and changing it from outside. Compare a waiter who says "please prepare table 4's bill" with one who walks into the kitchen and rewrites the ledger himself. Watch the "ask" style go wrong.

Ask style: the rules live outside the object
from enum import Enum, auto class Status(Enum): PLACED = auto() PAID = auto() class Order: def __init__(self): self.lines = [] self.status = Status.PLACED def total(self): return sum(self.lines) empty = Order() if empty.status is Status.PLACED: # forgot the "not empty" rule! empty.status = Status.PAID print(empty.status, "with total", empty.total())

An empty order was marked as paid. The rule "you cannot pay for nothing" was supposed to be checked by whoever changes the status, and this caller forgot. In a large program, that check would have to be copied into every place that touches the status, and sooner or later one copy would go missing. Now the "tell" version, where the object owns the rule:

Tell style: the object guards its own rules
from enum import Enum, auto class Status(Enum): PLACED = auto() PAID = auto() class Order: def __init__(self): self.lines = [] self.status = Status.PLACED def pay(self): if not self.lines: raise ValueError("cannot pay for an empty order") if self.status is not Status.PLACED: raise ValueError("order was already paid") self.status = Status.PAID order = Order() try: order.pay() except ValueError as error: print("ValueError:", error) order.lines.append(2.5) order.pay() print(order.status)

Callers now write one line, order.pay(), and cannot forget any rule, because the rules live in exactly one place. This is encapsulation from OOP 2 put to work: hiding details is only useful if the object is also trusted to use them correctly.

Principle 3: keep input and output out of your logic classes. I/O (input/output) means talking to the outside world: print, input, reading and writing files. A class that mixes I/O into its calculations is hard to test and hard to reuse. Suppose a function calculates a total and prints it:

Before: logic tangled with print
def show_total(prices): total = sum(prices) print(f"Total: {total:.2f}") # prints, and returns None result = show_total([2.5, 3.0]) print(result) try: assert result == "Total: 5.50" except AssertionError: print("AssertionError: the test cannot see what was printed")

Here we met assert, a statement meaning "this must be true; if not, stop with an AssertionError". It is the simplest way to write a test, a tiny check that code gives the answer you expect. The test failed, not because the arithmetic was wrong, but because the answer was thrown at the screen and the function returned None. To check it, you would have to capture what was printed, which is clumsy. If the function used input() instead, a test would need a human to type. The cure is to let logic return values and let a thin outer layer do the printing.

After: logic returns, tests are easy
def total_text(prices): return f"Total: {sum(prices):.2f}" def check(label, actual, expected): print(("PASS" if actual == expected else "FAIL"), label) check("two items", total_text([2.5, 3.0]), "Total: 5.50") check("no items", total_text([]), "Total: 0.00") try: assert total_text([1.0]) == "Total: 2.00", "one item should be 1.00" except AssertionError as error: print("AssertionError:", error)

Now the checks run instantly, with no screen and no typing, and the same total_text could feed a web page or a receipt printer. The third example shows that text after the comma in an assert becomes the error message, which helps when a test fails. The shape to remember is: logic classes compute and return; only the outermost layer prints, reads input or touches files.

Keep I/O at the edge
  ┌──────────────────────┐ calls  ┌──────────────────────┐
  │ Outer layer (edge)   │        │ Logic classes        │
  │ print(), input(),    │ ─────► │ Order, MenuItem,     │
  │ files                │ ◄───── │ Status               │
  └──────────────────────┘ return └──────────────────────┘
   hard to test by machine          easy to test and reuse
Arrows only ever go from the edge into the logic. The logic never reaches out to the screen or keyboard by itself.

4.8 — Three Friendly Patterns: Strategy, Factory, Observer

A design pattern is a named, reusable solution to a problem that programmers meet again and again. The name is useful because it lets people say "let's use a strategy here" instead of describing the whole idea each time. There are dozens of patterns, and some are complicated. The three below are gentle, and you already know everything needed to write them: they are just objects, functions and lists used in clever ways. For each one we begin with the pain it removes.

Pattern 1: Strategy, a swappable way of doing something. The bakery wants discounts: none, ten percent off, a flat 2.00 off, and more next month. A first attempt puts the choice inside total(), using a text label.

Before: a growing if/elif chain
class Order: def __init__(self, customer, discount_kind="none"): self.customer = customer self.discount_kind = discount_kind self.prices = [2.5, 3.0, 4.5] def total(self): subtotal = sum(self.prices) if self.discount_kind == "none": return subtotal elif self.discount_kind == "ten_percent": return subtotal * 0.9 elif self.discount_kind == "flat_two": return subtotal - 2.0 else: return subtotal print(Order("Asha").total()) print(Order("Ben", "ten_percent").total()) print(Order("Chen", "tenpercent").total()) # typo, no error, no discount

Two things hurt. Every new discount means editing total(), the heart of the class. And the last line shows the magic-string problem again: a typo silently gave no discount. The pattern that fixes this is called strategy: the way of doing the job (the "strategy") is passed in as a part, so the class does not need to know the options. In Python, the simplest strategy is just a function, because functions are objects you can store in a variable or pass around, exactly as you did with key= when sorting.

After: the discount is a part you pass in
def no_discount(amount): return amount def ten_percent(amount): return amount * 0.9 class FlatOff: # a strategy that needs its own setting def __init__(self, off): self.off = off def apply(self, amount): return max(0, amount - self.off) class Order: def __init__(self, customer, discount=no_discount): self.customer = customer self.discount = discount # has-a strategy self.prices = [2.5, 3.0, 4.5] def total(self): return self.discount(sum(self.prices)) print(Order("Asha").total()) print(Order("Ben", ten_percent).total()) print(Order("Chen", lambda amount: amount - 1).total()) print(Order("Dana", FlatOff(2.0).apply).total())
  • Each discount is a tiny piece of code that takes an amount and returns a new amount.
  • The Order stores whichever one it was given in self.discount. Notice this is composition again: the order has a discount.
  • In total(), self.discount(sum(self.prices)) calls whichever function is stored there. The Order never asks which discount it is.
  • A new discount is a new function. Order is not edited at all. A FlatOff object works too, because FlatOff(2.0).apply is also something you can call with an amount.
Strategy: an Order with a swappable part
                                     ┌─ no_discount(amount)
  Order ──has-a──► self.discount ───►├─ ten_percent(amount)
  total() calls it                   ├─ lambda amount: amount - 1
                                     └─ FlatOff(2.0).apply(amount)
The Order only knows "something I can call with an amount". You choose which one when you create the order, or swap it later with order.discount = ten_percent.

If you get it wrong, the errors are clear. Pass a string where a function belongs and you get TypeError: 'str' object is not callable ("you tried to call text as if it were a function"). Add brackets by accident, discount=ten_percent(), and Python calls the function on the spot with no argument: ten_percent() missing 1 required positional argument: 'amount'. Pass the function without brackets; the brackets mean "run it now".

Pattern 2: Factory, a helper that builds objects for you. The bakery's menu comes from a text file, one line per item, like "Croissant:2.50". Each place that reads a line must split on the colon, convert the price, and build a MenuItem. That parsing gets copied around. A factory puts the "how to build one" knowledge in a single spot. In classes, the usual home for it is a class method: a method marked with @classmethod that receives the class itself (named cls) instead of one object (self). Calling cls(...) inside it builds a new object of that class.

A classmethod factory: MenuItem.from_text
from dataclasses import dataclass @dataclass class MenuItem: name: str price: float @classmethod def from_text(cls, text): parts = text.split(":") if len(parts) != 2: raise ValueError(f"expected 'name:price', got {text!r}") name, price = parts return cls(name.strip(), float(price)) print(MenuItem.from_text("Croissant:2.50")) menu = [MenuItem.from_text(t) for t in ["Bagel: 1.8", "Muffin:3"]] print(menu) try: MenuItem.from_text("Bagel") except ValueError as error: print("ValueError:", error)

Notice that you call it on the class: MenuItem.from_text(...), with no object yet. That is the point; it is a second way to construct a MenuItem, next to the normal MenuItem("Bagel", 1.8). The messy work (splitting, trimming, converting) happens once, and bad input is rejected with a clear message. Forgetting the decorator is a classic slip:

Mistake: forgetting @classmethod
class Broken: def from_text(cls, text): # missing @classmethod above return text try: Broken.from_text("a:1") except TypeError as error: print("TypeError:", error)

The message says from_text() missing 1 required positional argument: 'text'. Without the decorator Python treats the first parameter as an ordinary argument, so "a:1" landed in cls and nothing was left for text. Add the decorator line and it works. A factory does not have to be a class method; a plain function such as make_discount("ten_percent") that returns the right strategy is also a factory, and it is a fine place to raise ValueError: unknown discount when the name is wrong.

Pattern 3: Observer, "tell me when something happens". When an order is paid, the kitchen screen should update and an email should go out. The lazy way is to write both actions inside Order.pay(). Then the order knows about kitchens and emails, and every new reaction (a text message, a log line) edits the order class. The observer pattern turns this around. The order keeps a list of listeners, ordinary functions that others have handed it, and calls each one when something changes. Think of a doorbell: the button does not know who is home or what they will do; it just rings, and whoever is listening reacts. A function you hand over to be called later is often called a callback.

Observer: listeners are called when the status changes
class Order: def __init__(self, customer): self.customer = customer self.status = "placed" self._listeners = [] def subscribe(self, listener): self._listeners.append(listener) def set_status(self, status): self.status = status for listener in self._listeners: listener(self) # tell everyone who asked def kitchen_screen(order): print(f"[kitchen] {order.customer}'s order is now {order.status}") def email_customer(order): print(f"[email] to {order.customer}: status {order.status}") order = Order("Asha") order.subscribe(kitchen_screen) order.set_status("paid") order.subscribe(email_customer) order.set_status("ready")

Follow the two calls. The first set_status("paid") found one listener, so only the kitchen line printed. After the second subscribe, set_status("ready") called both, in the order they were added. The Order class was never edited to add the email. It also works with tiny throwaway functions: order.subscribe(lambda o: log.append(o.status)) would quietly record each new status in a list called log.

Observer: one event, many listeners
  order.set_status("ready")
       │
       ▼
  for listener in self._listeners:
       ├──► kitchen_screen(order)
       ├──► email_customer(order)
       └──► (anything you subscribe later)
The order announces the change and does not care who listens. The listeners, not the order, decide what to do about it.
⚠️
Mistakes to watch forSubscribing something that is not callable (for example order.subscribe("email")) only fails later, at the moment the status changes, with TypeError: 'str' object is not callable. Also remember a listener runs every time, so a slow or crashing listener affects the change that triggered it.

Check yourself: In the strategy example, why did Order("Chen", lambda amount: amount - 1) work even though we never wrote a class for that discount?
The Order only needs "something callable that takes an amount and returns an amount". A lambda is a small function, so it qualifies.
Check yourself: What is the difference between self and cls in a method?
self is one particular object; cls is the class itself. That is why cls(...) inside a @classmethod builds a new object.

Recap

  • Strategy: pass in the changing behaviour (a function or object) so the class never needs an if/elif chain.
  • Pass functions without brackets; brackets call them immediately.
  • Factory: keep the "how to build one" code in one place, such as a @classmethod called on the class (MenuItem.from_text).
  • Observer: the object keeps a list of listener functions (callbacks) and calls them when something changes.
  • All three are composition: an object holds parts, and you choose the parts.
4.9 — Modelling a Domain End to End

You now own a full toolbox: composition, dataclasses, enums, hints, principles and patterns. The hardest part of real programming is not any single tool, though. It is starting from a blank page with a paragraph of English and deciding what the classes should be. This final section walks through that whole process on a new, small problem, in the order a working programmer would do it. Your only starting point is the requirement, so read it first.

Step 1: the written requirement. Here is what the customer, Ben, tells you.

Ben's requirement (nouns in bold, verbs in italics): Ben runs a small bike shop. Each bike has an id, a kind (city or electric) and a price per day. A bike is either available, rented or in repair. A customer can rent a bike for a number of days, but only if it is available. The cost is the days times the price per day, plus a fixed fee of 5.00 for electric bikes. When a bike is returned it becomes available again. The shop must list the available bikes and report its total earnings.

Step 2: nouns become candidates for classes or data, verbs become methods. Read the text slowly with two coloured pens. Underline the nouns (things) and the verbs (actions). Then ask of each noun: does it have facts and rules of its own (a class), is it one of a fixed list of choices (an Enum), or is it just a value (a plain attribute)?

Noun in the textDecisionWhy
bike shopclass Shopholds the bikes and the rentals, and offers the operations
bikedataclass Bikehas facts (id, price) and its own rules (can it be rented?)
kindEnum Kinda fixed list of choices: city or electric
available / rented / repairEnum Statea fixed list of stages, like our order status
rental (implied by "rent")frozen dataclass Rentala record of who rented what; it never changes once made
customer, days, cost, feeplain valuesa customer is only a name for now; days and cost are numbers

The verbs give the method names: rent and returned (give_back) belong to the Shop and, for the actual state change, to the Bike; list becomes available(); report becomes earnings(). Notice a deliberate choice: we did not make a Customer class. The requirement gives a customer no facts or rules, so a name is enough. Add classes when the problem demands them, not because a noun appeared.

Step 3: sketch the relationships. Before typing any code, draw who holds whom. This picture uses the has-a idea from 4.1.

Sketch: who has what in the bike shop
  Shop ──has many──► Bike ──has-a──► Kind   (Enum)
    │                  └───has-a──► State  (Enum)
    └──has many──► Rental (bike_id, customer, days, cost)

  Shop:  available()  rent(id, who, days)  give_back(id)  earnings()
  Bike:  cost_for(days)  check_out()  check_in()
The Bike guards its own rule ("only rent me if I am available") in check_out(). The Shop coordinates, and tells each Bike what to do (tell, don't ask).

Step 4: build it in small stages. A programmer would not type the whole thing and hope. We build the smallest piece, run it, then add the next. These four blocks form one growing program, so run them in order; the console remembers what earlier blocks defined. (If you run block 2 first, Python will say NameError: name 'Kind' is not defined, which simply means "I have not been told what that is yet.") First, the two Enums:

Stage 1: the choices
from enum import Enum, auto class Kind(Enum): CITY = auto() ELECTRIC = auto() class State(Enum): AVAILABLE = auto() RENTED = auto() REPAIR = auto() print([k.name for k in Kind]) print([s.name for s in State])

Next the Bike. It carries its facts and its two rules: how to price a rental, and when it may be checked out. The rule raises a clear error rather than returning a hidden failure code.

Stage 2 (continues stage 1): the Bike
from dataclasses import dataclass @dataclass class Bike: bike_id: int kind: Kind per_day: float state: State = State.AVAILABLE def cost_for(self, days): extra = 5.0 if self.kind is Kind.ELECTRIC else 0.0 return self.per_day * days + extra def check_out(self): if self.state is not State.AVAILABLE: raise ValueError(f"bike {self.bike_id} is {self.state.name}") self.state = State.RENTED def check_in(self): self.state = State.AVAILABLE bike = Bike(2, Kind.ELECTRIC, 20.0) print(bike) print(bike.cost_for(3))

The electric bike for three days costs 20 x 3 + 5 = 65, which matches the requirement, so this stage is checked before we go on. Now the Shop and the Rental record.

Stage 3 (continues stage 2): Rental and Shop
from dataclasses import dataclass @dataclass(frozen=True) class Rental: bike_id: int customer: str days: int cost: float class Shop: def __init__(self, bikes): self._bikes = {b.bike_id: b for b in bikes} self._rentals = [] def _find(self, bike_id): if bike_id not in self._bikes: raise ValueError(f"no bike with id {bike_id}") return self._bikes[bike_id] def available(self): return [b for b in self._bikes.values() if b.state is State.AVAILABLE] def rent(self, bike_id, customer, days): bike = self._find(bike_id) bike.check_out() rental = Rental(bike_id, customer, days, bike.cost_for(days)) self._rentals.append(rental) return rental def give_back(self, bike_id): self._find(bike_id).check_in() def earnings(self): return sum(r.cost for r in self._rentals)

Look at how the earlier ideas snapped in. self._bikes is a dictionary from id to Bike, so lookups are quick (composition with a container). rent is a "tell": it tells the bike to check itself out, then records a frozen Rental. The leading underscore on _find and _bikes marks them as private helpers, as you learned in OOP 2. Nothing in the Shop calls print, so it is easy to test. Finally, the outer layer uses it:

Stage 4 (continues stage 3): using the shop
shop = Shop([Bike(1, Kind.CITY, 10.0), Bike(2, Kind.ELECTRIC, 20.0), Bike(3, Kind.CITY, 10.0)]) print([b.bike_id for b in shop.available()]) print(shop.rent(2, "Asha", 3)) shop.rent(1, "Dana", 2) print([b.bike_id for b in shop.available()]) for bad_id in (2, 99): try: shop.rent(bad_id, "Chen", 1) except ValueError as error: print("ValueError:", error) shop.give_back(2) print([b.bike_id for b in shop.available()]) print("Earnings:", shop.earnings())
  • All three bikes start available, so the first list is [1, 2, 3].
  • Asha rents bike 2 for three days. The Shop finds it, calls check_out(), and stores a Rental costing 65.0.
  • Dana rents bike 1. Only bike 3 is left in the list.
  • Chen tries bike 2 (already rented) and bike 99 (does not exist). Each gets its own clear ValueError message, and nothing is changed.
  • Bike 2 is given back, so it is available again. Earnings add up the two rentals: 65 + 20 = 85.

Step 5: review your own classes. Good programmers read their own design critically before showing it to anyone. Use this checklist on any class you write. Each item points back to a section of this chapter.

  • Has-a or is-a? Did I use inheritance only where the sentence "X is a Y" is always true? (4.1, 4.2)
  • Narrow doors: Does the class expose only the methods callers need? (4.2)
  • Facts or work? Is a data holder a dataclass, with mutable defaults using default_factory? (4.3)
  • Frozen where possible: Could this value be immutable, and does it need validation in __post_init__? (4.4)
  • No magic strings: Are choices and stages Enums? (4.5)
  • Hints: Do public methods and fields say what they take and return, including | None? (4.6)
  • One job, tell don't ask, no I/O inside: Can I describe the class without "and", do callers just tell it what to do, and can I test it without a screen? (4.7)
  • Swappable parts: Is anything that varies (a discount, a format) passed in rather than hard-coded? (4.8)

Run the checklist on the bike shop. It passes most items, and the one honest gap is the rental cost: the electric fee is a fixed number inside cost_for. If Ben starts adding several kinds of pricing, that would be a good place to apply the strategy pattern from 4.8. Design is a series of small improvements, not a single perfect drawing.

Check yourself: Why did we not create a Customer class in the bike shop?

Check yourself: Which object enforces "only an available bike can be rented", and why is that a good place for the rule?

Recap

  • Turn a written requirement into classes by marking nouns (things) and verbs (actions).
  • Ask of each noun: class with rules, Enum of choices, or just a value? Do not invent classes with nothing to do.
  • Sketch who has what before coding, then build and run in small stages.
  • Put each rule with the object that owns the data, and keep printing in the outer layer.
  • Review with the checklist: has-a, narrow doors, dataclass, enums, hints, one job, swappable parts.
OOP 4 Summary: What You Can Now Do

You began this chapter able to build classes. You finish it able to design with them. Here is the whole chapter in one page, followed by a list of skills you can honestly claim.

  • Has-a (composition): an attribute can hold another object. Objects are built from parts, and a container delegates work to them. Test a relationship with a sentence: "is a" suggests inheritance, "has a" suggests composition.
  • Prefer composition: inheriting from list or building a Penguin under Bird gives you promises you cannot keep. Hold a part instead and expose a narrow set of methods.
  • @dataclass: list annotated fields once and get __init__, __repr__ and __eq__. Use field(default_factory=list) for mutable defaults.
  • Dataclass options: frozen=True (read-only and hashable), order=True (sortable), __post_init__ (validate and derive), asdict and replace.
  • Enum: named choices replace magic strings. Members are single objects: compare with is; typos fail loudly.
  • Type hints: labels for readers and tools (list[X], X | None, -> float). Python does not enforce them at run time.
  • Principles: one job per class; tell, don't ask; keep input and output at the edge so logic is testable.
  • Patterns: strategy (pass in behaviour), factory (one place that builds), observer (call registered callbacks on change).
  • Modelling: mark nouns and verbs, decide class or Enum or plain value, sketch who has what, build in stages, then review with the checklist.

After this chapter you can: build a program out of small cooperating objects; write a data-holding class in a handful of lines; describe an object's life cycle with an Enum; read and write type hints; split code so it can be tested without a screen; swap behaviour without editing a class; and take a paragraph of requirements and turn it into a working design. from dataclasses import dataclass from enum import Enum, auto def no_discount(amount): return amount def ten_percent(amount): return amount * 0.9 class Status(Enum): CART = auto() PAID = auto() SHIPPED = auto() CANCELLED = auto() @dataclass(frozen=True) class Book: title: str price: float def __post_init__(self): if self.price <= 0: raise ValueError(f"price must be positive: {self.price}") @classmethod def from_text(cls, text): title, price = text.split("|") return cls(title.strip(), float(price)) @dataclass class CartItem: book: Book quantity: int = 1 def line_total(self): return self.book.price * self.quantity class Order: def __init__(self, customer, discount=no_discount): self.customer = customer self.discount = discount self.items = [] self.status = Status.CART self.listeners = [] def subscribe(self, listener): self.listeners.append(listener) def _set_status(self, new_status): self.status = new_status for listener in self.listeners: listener(self) def _require(self, allowed, action): if self.status not in allowed: raise ValueError(f"cannot {action} an order that is {self.status.name}") def add(self, book, quantity=1): self._require([Status.CART], "add to") self.items.append(CartItem(book, quantity)) def subtotal(self): return sum(item.line_total() for item in self.items) def total(self): return self.discount(self.subtotal()) def pay(self): if not self.items: raise ValueError("cannot pay an empty order") self._require([Status.CART], "pay for") self._set_status(Status.PAID) def ship(self): self._require([Status.PAID], "ship") self._set_status(Status.SHIPPED) def cancel(self): self._require([Status.CART, Status.PAID], "cancel") self._set_status(Status.CANCELLED) def receipt(order): lines = [f"{item.quantity} x {item.book.title} {item.line_total():.2f}" for item in order.items] lines.append(f"Total: {order.total():.2f}") return "\n".join(lines)
