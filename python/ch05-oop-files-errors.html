5.1 — Bridge: From Objects to the Outside World

You have just finished the OOP track, so you already know how to build objects: a class is a blueprint, an instance is one thing made from it, and methods, inheritance, __str__, properties, dataclasses and unittest are the tools that keep such objects tidy. This chapter does not repeat any of that. If a word like super() or @property feels rusty, the track is one click away: OOP 1: Classes and Objects, OOP 2: Encapsulation and Special Methods, OOP 3: Inheritance and Polymorphism, OOP 4: Composition, Dataclasses and Design and OOP 5: Project, Testing and Pitfalls.

Here is the problem this chapter solves. Every object you build lives only while the program runs, and everything it works on is data you typed into the code. Real programs are different. The data sits in files on disk, written by other people or other programs. Those files may be missing, half-written, in the wrong text encoding, or full of values like 'absent' where a number should be. Any step can fail, and a program that has no plan for failure simply stops with a wall of red text.

So this chapter has two halves that belong together. First, errors: how to read the message Python prints when something breaks, how to catch an error and carry on, how to raise your own errors, and how to keep a trail from a friendly message back to the real cause. Second, files and formats: how to open and close a file safely, how to handle paths, and how to read and write the two formats you will meet constantly, CSV (tables) and JSON (nested data).

The journey of a piece of data
  disk            your program                              result
 +---------+ open +---------+ parse +---------+ check +---------+
 |scores.csv|---->|  text   |------>| dicts & |------>|  clean  |
 | (a file) |     |(strings)| csv,  | lists   | raise |  data   |
 +---------+      +---------+ json  +---------+       +---------+
     ^                 ^                ^                  ^
     |                 |                |                  |
 FileNotFound-     UnicodeDecode-   ValueError,       your own errors
 Error,            Error, wrong     KeyError,         (raise), caught
 PermissionError   newlines         JSONDecodeError   with try/except
At every arrow something can go wrong. The names underneath are the errors you will learn to read, catch and raise in this chapter.

Notice the second connection to the OOP track: errors are objects too. Every error name you have ever seen, such as ValueError, is a class, and the classes form a family tree with parents and children, exactly like the inheritance you just studied. That is why you will be able to write your own error class in one short line later on. Let us prove it with a tiny run.

Errors are classes with parents
print(ValueError.__mro__) print(issubclass(FileNotFoundError, OSError)) problem = ValueError('score must be a number') print(type(problem).__name__) print(problem.args)
Output
(<class 'ValueError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
True
ValueError
('score must be a number',)

__mro__ lists a class followed by its parents, in order. So ValueError is a kind of Exception, which is a kind of BaseException, which is a kind of plain object. The issubclass line confirms that a FileNotFoundError counts as an OSError. On the last two lines we built an error object by hand, the same way you would build any instance, and asked it for its type and its message. Nothing is raised yet: an error is only an object until somebody raises it.

Throughout the chapter we follow one small running example, a class quiz log. It starts as a list of strings such as 'Asha,92', and by the end it is read from files, parsed, validated and written back out. Each section adds one safety feature.

Which idea from the OOP track lets you write your own kind of error that still counts as a ValueError?
Inheritance. A subclass of ValueError is also a ValueError, so any handler that catches ValueError also catches your new error.
Try it. Change ValueError in the first line to KeyError and to ZeroDivisionError, and compare the parent lists. Which two names appear in every list?
Recap

  • Real data lives in files and is often messy, so a real program must expect failure at every step.
  • Errors are objects made from classes in a family tree; __mro__ shows a class and its parents.

5.2 — Reading a Traceback: What Python Is Telling You

Before we learn to catch errors, we need to read them, because the message Python prints is the best debugging help you will ever get for free. Beginners often glance at the wall of red text and panic. It is much friendlier than it looks. Let us build a small program on our running example that fails three function calls deep, and look at the whole message.

Three functions deep, then a crashreal traceback
import traceback def parse_score(text): return int(text) def average_score(lines): total = 0 for line in lines: name, raw = line.split(',') total += parse_score(raw) return total / len(lines) try: print(average_score(['Asha,92', 'Ben,eighty'])) except Exception: traceback.print_exc()
What Python says
Traceback (most recent call last):
  File "<exec>", line 14, in <module>
  File "<exec>", line 10, in average_score
  File "<exec>", line 4, in parse_score
ValueError: invalid literal for int() with base 10: 'eighty'

The try/except around the call is there only so this page can show you the message and carry on; it is explained fully in the next section. traceback.print_exc() prints the same text Python would have printed if the program had really crashed. That is worth doing here for a specific reason: this page's console shows only the last line of an uncaught error, while desktop Python prints the whole traceback, so we ask for it explicitly.

A traceback is the list of function calls that were active when the error happened, printed so that the newest call is at the bottom. Think of a stack of paper trays on a desk: average_score handed a sheet to parse_score, which handed a piece to int, and int is where it tore. Python walks you down the stack from the first call to the exact place of the failure.

Anatomy of a traceback
 Traceback (most recent call last):     <- header: newest call LAST
   File "<exec>", line 14, in <module>       <- main program called...
   File "<exec>", line 10, in average_score <- ...average_score, which
   File "<exec>", line 4, in parse_score    <- ...called parse_score
 ValueError: invalid literal for int() with base 10: 'eighty'
 ^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
 |           +-- message: WHAT was wrong, often with the bad value
 +-- error type: WHAT KIND of problem (what `except` matches)

 Read order: 1) last line  2) last File line  3) go upwards if needed
On your own computer each File line is followed by the source line itself. Inside the browser the code has no file name, so Python leaves the source out and shows <exec> instead. The line numbers still count from the first line of the block.
How to read it, step by step
  • Start at the bottom. ValueError: invalid literal for int() with base 10: 'eighty' names the type of the problem and the offending value. It already says most of what you need.
  • Look at the last File line above it. line 4, in parse_score is where Python was standing when it gave up: the line return int(text).
  • Ask who called that function. The File line above it says average_score at line 10 made the call, using the string raw it had just split off.
  • Decide where the real fault is. The crash happened in parse_score, but the cause is the input 'Ben,eighty'. The error line shows where Python noticed; you decide where to fix.

Errors have names for a reason. Six of them cause most beginner crashes, and they read very clearly once you know the pattern TypeName: what happened. The block below triggers each one on purpose. It uses eval, which runs a string as Python code; that is fine for a demo like this, but never use it on text you did not write yourself.

The usual suspects, each triggered on purpose
snippets = ["int('abc')", "'5' + 3", "[1, 2, 3][5]", "{'a': 1}['b']", "10 / 0", "undefined_name"] for code in snippets: try: eval(code) except Exception as e: print(f'{code:16} -> {type(e).__name__}: {e}')
Output
int('abc')       -> ValueError: invalid literal for int() with base 10: 'abc'
'5' + 3          -> TypeError: can only concatenate str (not "int") to str
[1, 2, 3][5]     -> IndexError: list index out of range
{'a': 1}['b']    -> KeyError: 'b'
10 / 0           -> ZeroDivisionError: division by zero
undefined_name   -> NameError: name 'undefined_name' is not defined

Each output line follows the same shape: the code that was run (the :16 in the f-string pads it to 16 characters so the columns line up), then the error type, then the explanation. ValueError means the right kind of value in a wrong form, like text that is not a number. TypeError means the wrong kind of value altogether. IndexError is a list position that does not exist, KeyError is a dictionary key that does not exist, ZeroDivisionError needs no explanation, and NameError usually means a typo or a variable used before it was created.

⚠️
Common mistake: reading from the top.The first line of a traceback is only the header. Beginners scroll to the top and get lost in the middle of the call chain. Always start with the last line, then move up only if you need to know how the program got there.
In the traceback above, which function was running when the error happened, and which function called it?
parse_score was running (the last File line), and average_score called it (the line above). Before that, the main program called average_score.
What would change in the traceback if you replaced 'Ben,eighty' with 'Ben,80'?
Nothing would print at all, because there would be no error. The average of 92 and 80 would be displayed as 86.0.
Try it. Change 'Ben,eighty' to 'Ben,80' and confirm that the traceback disappears. Then change it to 'Ben' (no comma). Which line of the traceback moves, and what is the new message?
Recap
  • A traceback lists the active function calls, oldest at the top and newest at the bottom.
  • Read it from the bottom: the last line gives the error type and message, the last File line gives where Python was when it failed.
  • The place where Python noticed the problem is not always the place where the mistake lives; follow the calls upwards to find out who passed in the bad value.
  • The common types: ValueError, TypeError, IndexError, KeyError, ZeroDivisionError, NameError.
5.3 — try/except: Surviving Bad Data

Reading an error is good. Not being stopped by it is better. Imagine the quiz log arrives with one student marked 'absent' instead of a number. Without any protection, the program dies on that row and the rows after it are never read, even though most of them are fine. A pipeline that dies on row 4,000 of 10,000 wastes everything it has done so far.

The idea behind try/except is a safety net under a trapeze. You say: try this risky thing; if it fails in this particular way, do that instead, and then keep going. The code in the try block runs normally. The moment an error is raised (Python's word for signalling a problem) the rest of the try block is skipped, and Python looks for an except clause that names that error type. If it finds one, its block runs and the program continues after the whole statement.

The path through a try/except
   try:  <risky code>
     |
     +--- no error ------------------------------+
     |                                           |
     +--- error raised --> does an except        |
                           name it?              |
                  yes: run that block            |
                            |                    |
                            +--------------------+
                            |                    |
                            v                    v
              no: the error keeps       carry on with the
                  travelling upward     next line
                  (crash if nobody
                  catches it)
Only errors that an except clause names are stopped. Everything else travels up the call stack, just as if the try were not there.
The smallest safety net
raw = 'eighty' try: score = int(raw) print('parsed', score) except ValueError: print('not a number:', raw) print('the program keeps going')
Output
not a number: eighty
the program keeps going
What Python does, line by line
  • raw is set to the text 'eighty'.
  • Python enters the try block and evaluates int(raw). The text cannot be converted, so a ValueError is raised.
  • The remaining line of the try block, print('parsed', score), is skipped. That is why parsed never appears.
  • Python compares the error type with except ValueError. It matches, so the handler prints not a number: eighty.
  • The statement is finished. Execution continues at the last line, which prints normally.

Now the loop from our quiz log. Each pass through the loop gets its own chance to fail, and a failure only affects that one pass.

Skipping bad rows and counting them
raw_scores = ['92', '85', 'absent', '78'] good = [] skipped = 0 for raw in raw_scores: try: good.append(int(raw)) except ValueError: skipped += 1 print('skipping', repr(raw)) print('good:', good, 'skipped:', skipped)
Output
skipping 'absent'
good: [92, 85, 78] skipped: 1

Adding as e after the error type gives you the error object itself, so you can print Python's own explanation instead of writing one. That is useful for a log file, because the message includes the bad value. Try the three inputs below and note that int('7.5') also fails: int accepts only whole-number text, so a decimal needs float first.

Catching the message with as e
for raw in ['92', '', '7.5']: try: print(int(raw)) except ValueError as e: print('problem:', e)
Output
92
problem: invalid literal for int() with base 10: ''
problem: invalid literal for int() with base 10: '7.5'
Name the error you expect

An except clause catches only the types it names. Below, a missing dictionary key raises a KeyError, but the inner handler is for ValueError, so the error passes straight through it to the outer handler. A wrong guess about the type gives you no protection at all.

A handler only catches what it names
import traceback scores = {'Asha': 92} try: try: print(scores['Ben']) except ValueError: print('this handler is only for ValueError') except KeyError: traceback.print_exc()
What Python says
Traceback (most recent call last):
  File "<exec>", line 6, in <module>
KeyError: 'Ben'
Common mistake: the bare except

The lazy way to guard code is a bare except: with no type, which catches everything. It also catches your own typos. In the block below the variable bonus was never created, so every pass raises a NameError, but the bare handler hides it and the program quietly reports a total of zero. That is the worst kind of bug: wrong answers with no complaint.

A bare except hides a real bug
total = 0 for raw in ['10', '20']: try: total += int(raw) + bonus except: pass print('total =', total)
Output
total = 0

The fix is to name the error you expect. Then the typo is no longer swallowed. In the version below we add a second handler only so that the page can show you the message and finish; in your own code you would simply fix the typo.

Naming the error lets the bug show itself
total = 0 for raw in ['10', '20']: try: total += int(raw) + bonus except ValueError: pass except NameError as e: print('bug found:', e) break print('total =', total)
Output
bug found: name 'bonus' is not defined
total = 0
💡
Keep the try block small.Put only the risky line inside try. If you wrap thirty lines, an error from any of them will be attributed to the one handler you wrote, and you will misread what went wrong.
What does int('7.5') do inside try: ... except ValueError:, and why?
It raises a ValueError, so the handler runs. int() only accepts text that spells a whole number. To read '7.5' you would convert with float('7.5') first.
Why is except: with no type dangerous?
It catches every error, including mistakes in your own code such as a misspelled variable, and hides them. The program keeps running with silently wrong results.
Try it. In the loop with absent, add a fifth value '9x' and a sixth None. Predict the output first. Does None get caught by except ValueError? Run it and read the traceback if it does not.
Recap
  • try: runs risky code; if an error is raised, Python skips the rest of the block and looks for a matching except.
  • Name the error you expect: except ValueError:. A handler never catches a type it does not name.
  • except ValueError as e gives you the error object; printing e shows Python's own explanation.
  • A bare except: hides real bugs. Keep the try block small so the handler matches what you meant.
5.4 — else, finally, and the Family of Errors

So far a try had one except. Real code often needs more. Suppose you parse a score and want to print a success message only when parsing worked, and you also want a line of bookkeeping to run whatever happens. Putting the success message inside try is risky: if that print line itself failed, your except would wrongly blame the parsing. Python gives you two extra clauses for this, else and finally.

else runs only when the try block finished with no error. finally runs no matter what: after success, after a handled error, even after a return. Think of leaving a rented flat. You might sort the rubbish only if you had a party (else), but you always hand back the keys (finally).

All four clauses in one function
def parse(raw): try: n = int(raw) except ValueError: print(' except: bad value', repr(raw)) return None else: print(' else: parsed fine') return n finally: print(' finally: finished with', repr(raw)) print(parse('7')) print(parse('x'))
Output
  else: parsed fine
  finally: finished with '7'
7
  except: bad value 'x'
  finally: finished with 'x'
None
What Python does, line by line
  • parse('7'): the try line succeeds, so the except block is skipped and the else block runs. It prints and executes return n.
  • Before the function really returns, Python runs the finally block. That is why finally: finished with '7' appears before 7 is printed by the outer print.
  • parse('x'): int('x') raises ValueError, so except runs, prints and hits return None. else is skipped.
  • Again finally runs just before the function leaves, and only then does the outer print display None.
The order of the four clauses
   try:      the risky line(s)   ----- always first
   except:   only if try raised a matching error
   else:     only if try finished with NO error
   finally:  ALWAYS, last (even after a return or an uncaught error)

            +--------+   error   +--------+
     start->|  try   |---------->| except |--\
            +--------+           +--------+   \   +---------+
                 | no error                    +->| finally |--> continue
                 v                             /  +---------+
            +--------+                        /
            |  else  |-----------------------/
            +--------+
Exactly one of except or else runs (or neither, if the error is not caught). finally runs in every case.

finally is the place for cleanup that must not be skipped, such as closing a file. It even runs when the error is not caught at all: the cleanup happens, and then the error keeps travelling upward.

finally runs even when the error is not caught here
def risky(): try: return int('x') finally: print('cleanup runs first') try: risky() except ValueError: print('the caller caught it afterwards')
Output
cleanup runs first
the caller caught it afterwards
Several handlers, and the family tree

You can stack several except clauses, and you can list more than one type in a tuple. Python checks them from top to bottom and runs the first one that fits. Below, a missing name, a bad value and a missing score each get their own message.

One try, several except clauses
def lookup(scores, name): try: return int(scores[name]) except KeyError: return 'no such student' except (ValueError, TypeError): return 'bad score value' scores = {'Asha': '92', 'Ben': 'n/a', 'Chen': None} for who in ['Asha', 'Ben', 'Chen', 'Dana']: print(who, '->', lookup(scores, who))
Output
Asha -> 92
Ben -> bad score value
Chen -> bad score value
Dana -> no such student

Chen has the value None, and int(None) raises a TypeError, not a ValueError, which is why the tuple lists both. Now recall from section 5.1 that error types are classes with parents. That family tree decides what a handler catches: a handler for a parent type also catches every child type. Print the parents of four errors you will meet in this chapter to see the tree.

Reading the family tree with __mro__
import json for cls in (FileNotFoundError, KeyError, json.JSONDecodeError, UnicodeDecodeError): chain = [c.__name__ for c in cls.__mro__] print(' -> '.join(chain))
Output
FileNotFoundError -> OSError -> Exception -> BaseException -> object
KeyError -> LookupError -> Exception -> BaseException -> object
JSONDecodeError -> ValueError -> Exception -> BaseException -> object
UnicodeDecodeError -> UnicodeError -> ValueError -> Exception -> BaseException -> object
A small part of the error family tree
 BaseException
  +-- KeyboardInterrupt     (Ctrl+C; you almost never catch this)
  +-- Exception             (parent of the errors you normally handle)
       +-- OSError          (files and the operating system)
       |    +-- FileNotFoundError, PermissionError,
       |        FileExistsError, IsADirectoryError
       +-- ValueError       (right type, unusable value)
       |    +-- json.JSONDecodeError
       |    +-- UnicodeError -> UnicodeDecodeError
       +-- LookupError
       |    +-- KeyError, IndexError
       +-- TypeError, NameError, ArithmeticError -> ZeroDivisionError
Catch a parent to catch a whole branch. except OSError covers every file error at once; except LookupError covers both KeyError and IndexError.
A parent handler catches its children
import json try: json.loads('{bad json}') except ValueError as e: print('caught as ValueError, real type:', type(e).__name__)
Output
caught as ValueError, real type: JSONDecodeError
Common mistake: the general handler first

Because Python takes the first handler that fits, putting a wide handler above a narrow one makes the narrow one unreachable. Python does not warn you. The code below looks careful and behaves carelessly.

The specific handler never runs
try: int('abc') except Exception: print('handler 1: the general one') except ValueError: print('handler 2: never reached')
Output
handler 1: the general one

The fix is to order handlers from the most specific to the most general, with Exception last if you use it at all.

💡
Use else to keep try small.Put only the risky call in try, and the code that depends on it succeeding in else. Then a bug in that later code cannot be mistaken for the error you were guarding against.
In parse('7'), why does finally: finished with '7' print before the 7 from the outer print?
return n does not leave the function until finally has run. So the finally print happens first, then the function hands back 7, and only then does the outer print display it.
Would except OSError catch a FileNotFoundError?
Yes. FileNotFoundError is a child of OSError in the family tree, so a handler for the parent catches it.
Try it. Swap the order of the two handlers in the last block so that ValueError comes first. Run it and confirm that the message changes to the specific one.
Recap
  • else runs when the try block finished without an error; finally runs always, last, even around return.
  • Several except clauses are checked from the top, and the first match wins.
  • Error types form a family tree; catching a parent (like OSError or ValueError) catches its children too.
  • Order handlers from most specific to most general.
5.5 — raise: Refusing Bad Input and Making Your Own Errors

Until now Python raised the errors. Sometimes your own code should raise them. Consider a function that averages quiz scores. It happily accepts nonsense, and the result is nonsense that looks like a real answer.

Nonsense in, nonsense out
def average(scores): return sum(scores) / len(scores) print(average([90, 80])) print(average([-500, 90]))
Output
85.0
-205.0

The second answer, -205.0, is impossible for scores between 0 and 100, yet nothing complained. The bad value would travel on into later calculations, and you would discover the problem much later, far from its cause. A better habit is to fail early and loudly: check the input at the door and refuse it with a clear message. Think of a form that rejects a birth year of 3025 the moment you type it.

The tool for this is raise. It creates an error object and throws it, which stops the current function on the spot. The error then travels up through the callers until an except catches it, and that is exactly the path a traceback records.

Raising ValueError with a clear message
def check_score(score): if not 0 <= score <= 100: raise ValueError(f'score must be 0-100, got {score}') return score for value in [92, 150]: try: print('valid:', check_score(value)) except ValueError as e: print('rejected:', e)
Output
valid: 92
rejected: score must be 0-100, got 150
What Python does, line by line
  • check_score(92): the condition 0 <= 92 <= 100 is true, so not makes it false, the if is skipped, and the function returns 92.
  • check_score(150): the condition is false, not turns it true, so raise runs. The line after it, return score, is never reached.
  • The ValueError object leaves check_score and arrives at the caller, which sits inside try. The matching except prints the message inside the error object.
An error travels up until someone catches it
  main program   try:
       |           total(...)         <-- 4. except ValueError catches
       v
  total()          for s in scores:
       |             check_score(s)   <-- 3. no handler: passes upward
       v
  check_score()    raise ValueError   <-- 1. raised; this function stops

  1. raise  2. the function ends at once  3. each caller is abandoned
  4. the first matching except ends the journey
Every function the error passes through is abandoned, and none of its remaining lines run. That is the same list of calls you learned to read in section 5.2.
Your own error types

A message is enough for a person, but a program that needs to react to a problem wants a type to match on. ValueError is broad. You can make a narrower one in a single line, using the inheritance from the OOP track. Because it is a child of ValueError, old code that catches ValueError keeps working. You can also give the error object extra attributes with __init__, just as with any class.

A custom error with extra data
class ScoreError(ValueError): def __init__(self, value): super().__init__(f'score must be 0-100, got {value!r}') self.value = value def check_score(score): if not 0 <= score <= 100: raise ScoreError(score) return score try: check_score(-5) except ScoreError as e: print('rejected:', e) print('offending value:', e.value)
Output
rejected: score must be 0-100, got -5
offending value: -5

Sometimes a function wants to notice an error, do something such as writing a log line, and let the error carry on to its caller. A bare raise with nothing after it re-raises the error that is currently being handled.

Log it, then re-raise with a bare raise
class ScoreError(ValueError): pass def check_score(score): if score > 100: raise ScoreError(f'too high: {score}') return score try: try: check_score(150) except ScoreError as e: print('logging:', e) raise except ValueError as caller_view: print('caller still sees a', type(caller_view).__name__)
Output
logging: too high: 150
caller still sees a ScoreError
Common mistakes

You can only raise error objects, not plain text. Raising a string is a classic slip when you are in a hurry. Also avoid raise Exception('...') for everything: callers cannot tell your problem apart from any other, so pick the most specific built-in type that fits, or make your own.

Raising something that is not an error
try: raise 'bad score' except TypeError as e: print('TypeError:', e)
Output
TypeError: exceptions must derive from BaseException
💡
Which type should I raise?Use ValueError when the value has the right type but is unusable (like 150 as a percentage), TypeError when the type itself is wrong, and KeyError or IndexError for missing lookups. Create your own subclass when callers need to react to your specific situation.
After raise ValueError('x') runs inside a function, does the next line of that function ever execute?
No. raise stops the function immediately. Python only continues at the first except that matches, in one of the callers.
Why make ScoreError a child of ValueError instead of Exception?
Then any existing code that says except ValueError also catches it, and the error correctly describes itself as a bad value.
Try it. Add a second check to check_score that raises ScoreError when the score is not a whole number, using isinstance(score, int). Test it with check_score(7.5).
Recap
  • Validate at the door: raise an error with a clear message instead of letting bad data travel.
  • raise stops the current function; the error goes up through the callers until a matching except catches it.
  • Subclass a built-in error (class ScoreError(ValueError): pass) to get a precise type, optionally with extra attributes.
  • A bare raise re-raises the current error. Only error objects can be raised, never plain strings.
5.6 — Exception Chaining: raise ... from e

A low-level message such as invalid literal for int() with base 10: 'eighty' helps a programmer but tells a user nothing about what they were trying to do. The natural reaction is to catch it and raise a clearer error such as could not read the score for Ben. But if you simply replace one error with another, the original message, the real cause, may vanish from the report. It is like an incident report that says only "delivery failed" and never mentions that the truck broke down.

Exception chaining solves this by attaching the original error to the new one. You write raise NewError(...) from original. The new error carries the original in an attribute called __cause__, and a traceback prints both.

Translating an error without losing it
def parse_score(name, raw): try: return int(raw) except ValueError as e: raise ValueError(f'could not read the score for {name}') from e try: parse_score('Ben', 'eighty') except ValueError as e: print('Error:', e) print('Cause:', type(e.__cause__).__name__, '-', e.__cause__)
Output
Error: could not read the score for Ben
Cause: ValueError - invalid literal for int() with base 10: 'eighty'

The friendly message is what you show to users, and the cause is what you would look at when debugging. Now let us see how a real traceback presents the chain. Read from the top: the original error comes first, then a sentence linking it to the second error, which comes last, just as in an incident report.

The traceback of a chained error
import traceback def parse_score(name, raw): try: return int(raw) except ValueError as e: raise ValueError(f'could not read the score for {name}') from e try: parse_score('Ben', 'eighty') except ValueError: traceback.print_exc()
What Python says
Traceback (most recent call last):
  File "<exec>", line 5, in parse_score
ValueError: invalid literal for int() with base 10: 'eighty'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "<exec>", line 10, in <module>
  File "<exec>", line 7, in parse_score
ValueError: could not read the score for Ben

What if you forget from? Python still records the connection, because the new error was raised while the old one was being handled, but its wording is different. It says *During handling of the above exception, another exception occurred*, which reads like an accident inside your handler rather than a deliberate translation. Here are the two versions side by side, along with from None, which hides the original on purpose when it would only confuse the reader.

from, no from, and from None
def convert(raw, how): try: return int(raw) except ValueError as inner: if how == 'from': raise RuntimeError('bad score') from inner if how == 'plain': raise RuntimeError('bad score') raise RuntimeError('bad score') from None for how in ['from', 'plain', 'none']: try: convert('x', how) except RuntimeError as e: cause = type(e.__cause__).__name__ context = type(e.__context__).__name__ print(f'{how:5} __cause__={cause:10} __context__={context}')
Output
from  __cause__=ValueError __context__=ValueError
plain __cause__=NoneType   __context__=ValueError
none  __cause__=NoneType   __context__=ValueError

Read the three lines like this. __context__ is filled in every time, because the new error really was raised while the old one was being handled. __cause__ is filled in only by an explicit from. With from, the traceback says "the direct cause". With no from, it shows the original as background ("during handling"). With from None, Python marks the context as hidden, so the traceback no longer prints the original at all. Use from e whenever you translate an error; use from None only when you are certain the original adds nothing.

The original error object. That is how you can print its type and message after catching X.
Which form would you use to translate a ValueError into a clearer error but keep the debugging trail?

Recap

  • A traceback prints the original first, then "the above exception was the direct cause", then the new error.
  • Without from, Python still shows the original, but as "during handling of the above exception, another exception occurred".
  • from None deliberately hides an original that would only confuse.
5.7 — Reading and Writing Files: open, close, and with

Every variable you have made so far vanishes the moment the program ends. To keep results, or to receive data from someone else, a program has to use files. A file is a named container on disk that holds a sequence of bytes, and text files are the ones people can read, like scores.txt or notes.csv. Python reaches a file through the built-in function open.

Think of a paper notebook. Before you can read or write, you have to open it to a page. When you are done you close it and put it away. If you leave it open and walk off, someone else may be unable to use it, and pages you were still writing may not be saved. open(name, mode) opens the notebook and gives you a file object (a handle), and you use that handle to read or write. The mode says what you plan to do: 'r' to read (the default), 'w' to write.

Writing a file, then reading it back
with open('quiz.txt', 'w') as f: f.write('Asha,92\n') f.write('Ben,85\n') with open('quiz.txt') as f: text = f.read() print(text) print(repr(text))
Output
Asha,92
Ben,85

'Asha,92\nBen,85\n'

The first print shows the text as you would see it in an editor. The second uses repr, which shows the exact characters, including the invisible \n (newline) at the end of each line. Writing does not add newlines for you; the \n is part of the text you wrote.

What Python does, line by line
  • open('quiz.txt', 'w') asks the operating system for the file, creating it if it does not exist. Python returns a file object, and as f gives it the name f.
  • Each f.write(...) puts text into the file. The text may wait in a buffer (a small holding area) rather than reaching the disk at once.
  • When the indented block ends, with automatically closes the file. Closing flushes the buffer to disk, so nothing is lost.
  • The second with opens the same file in the default read mode. f.read() returns the whole content as one string, and closing happens again at the end of the block.
The life of a file handle
   open('quiz.txt', 'w')        with open(...) as f:
          |                               |
          v                               v
    +-----------+  write/read     +------------------+
    |  file  f  | <-------------> |   your program   |
    +-----------+                 +------------------+
          |
     .close()  <-- flushes the buffer, frees the file for others

   with open(...) as f:          <-- close() is called for you, always
       ...work with f...         <-- even if an error happens in here
A with block is a promise: whatever happens inside, the file is closed on the way out.
Why with, and what goes wrong without it

You can call open and close yourself, but you must not forget the close, and a crash in the middle would skip it. The next block shows the file object's closed flag in both styles.

Manual close versus with
f = open('notes57.txt', 'w') f.write('draft') print('manual, before close: closed =', f.closed) f.close() print('manual, after close: closed =', f.closed) with open('notes57.txt') as g: print('inside with: closed =', g.closed) print('after with: closed =', g.closed)
Output
manual, before close: closed = False
manual, after close:  closed = True
inside with:          closed = False
after with:           closed = True

The with version needs no close() line, so there is nothing to forget. It also closes the file when an error interrupts the block, which matches the finally idea from section 5.4. You can see that here:

with closes the file even when the block fails
with open('notes57.txt', 'w') as f: f.write('safe') try: with open('notes57.txt') as f: int('oops') except ValueError: print('the error happened; closed =', f.closed)
Output
the error happened; closed = True
Common mistakes

Using a file after its block has ended is the most common one. The handle still exists as a variable, but the file behind it is closed, and Python says so plainly. The second case is opening a file that is not there.

Using a closed file, and a missing file
with open('notes57.txt', 'w') as f: f.write('safe') try: f.read() except ValueError as e: print('ValueError:', e) try: open('no_such_scores.txt') except FileNotFoundError as e: print(type(e).__name__, '|', e.strerror, '|', e.filename)
Output

Both messages tell you exactly what happened. For a missing file the fix depends on the situation: correct the name, create the file first, or catch FileNotFoundError and tell the user which file to provide. Relative names such as 'no_such_scores.txt' are looked for in the program's current working directory, which is not always the folder you expect. Section 5.10 shows how to make paths explicit.

Four ways to read, and the file cursor

A file object remembers a position, called the cursor, that starts at the beginning. Each read moves the cursor forward and hands back what it passed. A bookmark is the right picture. That explains a surprise that trips up many beginners: reading the same open file twice gives an empty string the second time, because the bookmark is already at the end.

The cursor moves as you read
   file: Asha,92\nBen,85\nChen,78\n
         ^ cursor starts here
   readline() -> 'Asha,92\n'       cursor: start of line 2
   read(3)    -> 'Ben'            cursor: after 'Ben'
   read()     -> ',85\nChen,78\n' cursor: the very end
   read()     -> ''               nothing left to read
   seek(0)                        cursor: back to the start
read() takes everything, read(n) takes n characters, readline() takes one line, and readlines() returns every line as a list. seek(0) rewinds.
readline, read, readlines and seek
with open('cursor.txt', 'w') as f: f.write('Asha,92\nBen,85\nChen,78\n') with open('cursor.txt') as f: print(repr(f.readline())) print(repr(f.read(3))) print(repr(f.read())) print(repr(f.read())) f.seek(0) print(f.readlines())
Output

'Ben'
',85\nChen,78\n'
''
['Asha,92\n', 'Ben,85\n', 'Chen,78\n']

For large files the best way to read is to loop over the file object itself. Python hands you one line at a time and never loads the whole file into memory. Here it builds the average score, using .strip() to remove the newline and split(',') to break the line into its two parts.

Looping over lines, one at a time
with open('cursor.txt', 'w') as f: f.write('Asha,92\nBen,85\nChen,78\n') with open('cursor.txt') as f: total = 0 count = 0 for number, line in enumerate(f, start=1): name, score = line.strip().split(',') print(number, name, score) total += int(score) count += 1 print('average:', total / count)
Output
1 Asha 92
2 Ben 85
3 Chen 78
average: 85.0
Common mistakes

Two more slips are easy to make. Writing to a file opened for reading, or reading from one opened for writing, raises an error from the io module. And because write accepts only strings, a bare number must be converted with str(). Notice that print(..., file=f) is a convenient alternative that adds the newline for you.

Wrong direction, wrong type, missing newline
import io with open('mistakes.txt', 'w') as f: try: f.read() except io.UnsupportedOperation as e: print('UnsupportedOperation:', e) try: f.write(92) except TypeError as e: print('TypeError:', e) f.write('Asha,92') f.write('Ben,85') print('Chen,78', file=f) with open('mistakes.txt') as f: print(repr(f.read()))

The last line shows the missing-newline mistake: Asha,92 and Ben,85 ran together into one line because nothing separated them, while print(..., file=f) finished its line properly.

You open an existing file with 'w' and immediately close it without writing. What is in the file now?
Nothing. The file is empty, because 'w' erases the old content as soon as the file is opened.
Why does a second f.read() on the same open file return ''?
The first read moved the cursor to the end of the file. There is nothing left after it, so the second read returns an empty string. f.seek(0) moves the cursor back.

Recap

  • A file has a cursor: each read moves it forward, so a second read() gives '' until you seek(0).
  • Loop over the file object to read line by line; use .strip() to remove the newline.
  • write needs a string and adds no newline; print(..., file=f) adds one.
5.9 — Text, Encodings and Newlines: The Invisible Pitfalls

So far the file contents looked like plain letters. Under the surface a file only holds bytes, numbers from 0 to 255. Python has to turn characters into bytes when writing and back into characters when reading. The rulebook for that translation is called an encoding. The one you should use almost always is UTF-8, which can represent every alphabet. The trouble starts when the writer and the reader use different encodings.

Characters are not bytes
text = 'café' print(len(text), 'characters') print(text.encode('utf-8')) print(text.encode('latin-1')) print(len(text.encode('utf-8')), 'bytes in UTF-8')
Output
4 characters
b'caf\xc3\xa9'
b'caf\xe9'
5 bytes in UTF-8

The accented é is one character but two bytes in UTF-8 (\xc3\xa9), and one byte in an older encoding called Latin-1 (\xe9). If someone saves a file in Latin-1 and you read it as UTF-8, Python meets a byte that makes no sense in UTF-8 and raises an error.

Text and bytes
    characters ('café')  --- encode (write) --->  bytes on disk
                         <--- decode (read) ---

     'é'  --UTF-8-->    C3 A9      (two bytes)
     'é'  --Latin-1-->  E9         (one byte)

     reading E9 as UTF-8  -->  UnicodeDecodeError
     (the reader and the writer must agree on the encoding)
open(..., encoding="utf-8") names the rulebook explicitly. Do not rely on the default; it differs between computers.
UnicodeDecodeError: the mismatch, and two ways out
with open('names_latin.txt', 'w', encoding='latin-1') as f: f.write('café noir') try: with open('names_latin.txt', encoding='utf-8') as f: f.read() except UnicodeDecodeError as e: print('UnicodeDecodeError:', e) with open('names_latin.txt', encoding='utf-8', errors='replace') as f: print('errors=replace:', f.read()) with open('names_latin.txt', encoding='latin-1') as f: print('right encoding:', f.read())
Output
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 3: invalid continuation byte
errors=replace: caf� noir
right encoding: café noir

Read the error like a sentence: the utf-8 codec could not decode byte 0xe9 at position 3 because it was an invalid continuation byte. The real fix is to use the encoding the file was really written in. errors='replace' lets you read anyway by swapping the unreadable byte for a replacement mark, which is good for looking at a file and bad for data you rely on. The habit that prevents all of this is to write encoding='utf-8' whenever you open a text file.

Newlines: the line ending is not the same everywhere

A newline is the invisible character that ends a line. Unix-like systems and macOS use \n, while Windows uses two characters, \r\n. Python smooths this over: when you read in text mode it translates every kind of line ending to a plain \n, and when you write it converts \n to whatever the current system prefers. That is usually what you want. It becomes a problem when you must see or preserve the exact endings, and the fix is newline='', which switches the translation off.

The same bytes, three ways of reading
with open('lines.txt', 'w', newline='') as f: f.write('Asha,92\r\nBen,85\r\n') with open('lines.txt', 'rb') as f: print('raw bytes :', f.read()) with open('lines.txt') as f: print('default read :', repr(f.read())) with open('lines.txt', newline='') as f: print("newline='' :", repr(f.read()))
Output
raw bytes    : b'Asha,92\r\nBen,85\r\n'
default read : 'Asha,92\nBen,85\n'
newline=''   : 'Asha,92\r\nBen,85\r\n'

The file was written with Windows-style endings. Reading it normally hides the \r, while newline='' shows exactly what is in the file. Section 5.11 comes back to this: the csv module asks you to open files with newline='' so that it can handle line endings itself, including line breaks inside quoted fields.

Splitting text into lines
text = 'Asha,92\nBen,85\n' print(text.split('\n')) print(text.splitlines()) print([line for line in text.split('\n') if line])
Output
['Asha,92', 'Ben,85', '']
['Asha,92', 'Ben,85']
['Asha,92', 'Ben,85']

A file that ends with a newline gives an extra empty string when you split('\n'). That trailing '' later fails int('') or a two-way unpack. splitlines() does not produce it, and neither does looping over the file object.

Recap
  • A file holds bytes; an encoding such as UTF-8 turns characters into bytes and back. Reader and writer must agree.
  • UnicodeDecodeError means the bytes did not fit the encoding you named. Fix it by naming the correct encoding, not by ignoring the problem.
  • Always pass encoding='utf-8' for text files you share.

5.10 — pathlib: Handling File Paths Properly

Every file has a path: the directions from a starting folder to the file, like data/quiz/scores_2024.csv. Beginners build paths by gluing strings together, and it works until it does not. Watch what happens when one separator is forgotten, and how much string surgery it takes just to get a file's name.

Paths as plain strings are fragile
folder = 'data' name = 'scores.csv' print(folder + '/' + name) print(folder + name) path = 'data/quiz/scores_2024.csv' print(path.split('/')[-1]) print(path.split('/')[-1].split('.')[0])
Output
data/scores.csv
datascores.csv
scores_2024.csv
scores_2024

The second line silently glued the words into datascores.csv. On Windows the separator is a backslash, so hard-coded slashes break there. Extracting the name and the extension needs two chained splits. The pathlib module in the standard library replaces all of this with a Path object: a path that knows it is a path. You combine parts with the / operator, and Python picks the right separator for the computer it runs on.

The anatomy of a Path
   Path('data') / 'quiz' / 'scores_2024.csv'

                   .suffix = .csv          (the extension, with its dot)

   .parts = ('data', 'quiz', 'scores_2024.csv')

Creating, finding and reading files with Path
from pathlib import Path folder = Path('quizdata') folder.mkdir(exist_ok=True) (folder / 'week1.txt').write_text('Asha,92\n', encoding='utf-8') (folder / 'week2.txt').write_text('Ben,85\n', encoding='utf-8') (folder / 'notes.md').write_text('hello', encoding='utf-8') print(folder.exists(), folder.is_dir(), (folder / 'week1.txt').is_file()) for path in sorted(folder.glob('week*.txt')): print(path.name, '->', path.read_text(encoding='utf-8').strip()) print([p.name for p in sorted(folder.iterdir())])

What Python does, line by line
  • Path('quizdata') only creates an object that describes a location. No file or folder is touched yet.
  • mkdir(exist_ok=True) creates the folder, and does nothing (instead of raising FileExistsError) if it is already there.
  • Each write_text opens the file, writes the text, and closes it, in one call.
  • glob('week*.txt') yields the paths that match the pattern, where * stands for any characters. sorted puts them in a fixed order.
  • iterdir() lists everything in the folder, including notes.md, which the glob pattern skipped.
Common mistakes

Two slips are common. Adding a string to a Path with + fails, because the operator for joining is /. And writing into a folder that does not exist yet fails with the same FileNotFoundError as a missing file. The cure is mkdir(parents=True, exist_ok=True) on the parent first.

import shutil from pathlib import Path shutil.rmtree('reports', ignore_errors=True) try: Path('reports') + '/summary.txt' except TypeError as e: print('TypeError:', e) target = Path('reports') / 'june' / 'summary.txt' try: target.write_text('ok', encoding='utf-8') except FileNotFoundError as e: print('FileNotFoundError:', e.strerror, '|', e.filename) target.parent.mkdir(parents=True, exist_ok=True) target.write_text('ok', encoding='utf-8') print('written:', target.read_text(encoding='utf-8'))

  • write_text, read_text, mkdir, exists, glob and iterdir cover most everyday file work.

  • Path works anywhere a file name string does, including open().
5.11 — CSV: Tables as Text

CSV stands for comma-separated values: a table where each line is a row and commas separate the columns. Spreadsheets, databases and almost every dataset you download can produce it. Splitting on commas seems easy, until a value itself contains a comma. Then the value has to be wrapped in quotes, and a plain split(',') cuts it in two.

Why split(",") is not enough
import csv line = '"Ng, Dana",78' print(line.split(',')) print(next(csv.reader([line])))
Output
['"Ng', ' Dana"', '78']
['Ng, Dana', '78']

The standard library csv module understands quotes, so the row correctly has two columns. csv.reader gives each row as a list. csv.DictReader is friendlier: it takes the first line as the column names and gives each row as a dictionary, so you write row['score'] instead of remembering that the score is at position 1. Because a CSV is text, every value arrives as a string, and you must convert it yourself.

DictReader: rows become dictionaries
import csv with open('scores.csv', 'w', newline='', encoding='utf-8') as f: f.write('name,score\nAsha,92\nBen,85\nChen,78\n') with open('scores.csv', newline='', encoding='utf-8') as f: rows = list(csv.DictReader(f)) print(rows[0]) print(rows[0]['name'], type(rows[0]['score']).__name__) scores = [int(row['score']) for row in rows] print(scores, sum(scores) / len(scores))
Output
{'name': 'Asha', 'score': '92'}
Asha str
[92, 85, 78] 85.0
What Python does, line by line
  • The file is written with newline='', so that the line endings are exactly what we put in (section 5.9).
  • csv.DictReader(f) reads the first line, name,score, and remembers it as the column names.
  • list(...) pulls every remaining line through the reader; each becomes a dictionary such as {'name': 'Asha', 'score': '92'}.
  • rows[0]['score'] is the text '92', not the number 92. That is why the list comprehension calls int(...) before the sum.

To write a CSV, use csv.DictWriter. It needs the column names, writeheader() writes them, and writerows writes many rows. Values that contain commas are quoted for you. Look at the raw text with repr and you will see \r\n line endings: that is the CSV standard, and it is the reason we opened the file with newline=''.

DictWriter adds the quotes for you
import csv rows = [{'name': 'Asha', 'score': 92}, {'name': 'Ng, Dana', 'score': 78}] with open('out.csv', 'w', newline='', encoding='utf-8') as f: writer = csv.DictWriter(f, fieldnames=['name', 'score']) writer.writeheader() writer.writerows(rows) with open('out.csv', newline='', encoding='utf-8') as f: print(repr(f.read()))
Output
'name,score\r\nAsha,92\r\n"Ng, Dana",78\r\n'
Surviving messy rows

Real files have blank cells and typos. Combining csv with try/except from section 5.3 lets you keep the good rows and report the bad ones with their line numbers. enumerate(..., start=2) numbers the rows as an editor would, because line 1 is the header.

Keeping the good rows, listing the bad ones
import csv raw = 'name,score\nAsha,92\nBen,\nChen,seventy\nDana,88\n' with open('messy.csv', 'w', newline='', encoding='utf-8') as f: f.write(raw) good, bad = [], [] with open('messy.csv', newline='', encoding='utf-8') as f: for line_no, row in enumerate(csv.DictReader(f), start=2): try: good.append(float(row['score'])) except ValueError as e: bad.append((line_no, row['name'], str(e))) print('good:', good) for item in bad: print('bad row:', item)
Output
good: [92.0, 88.0]
bad row: (3, 'Ben', "could not convert string to float: ''")
bad row: (4, 'Chen', "could not convert string to float: 'seventy'")
Common mistakes

The most common trap is a header that is not exactly what you typed: a capital letter or a space after the comma makes row['score'] a KeyError. A short row leaves the missing columns as None. Here io.StringIO acts as a file made from a string, which is handy for quick experiments and tests.

A header with a stray space, and a short row
import csv import io raw = 'Name, score\nAsha,92\nBen\n' rows = list(csv.DictReader(io.StringIO(raw))) print(list(rows[0])) try: print(rows[0]['score']) except KeyError as e: print('KeyError:', e) print(rows[1])
Output
['Name', ' score']
KeyError: 'score'
{'Name': 'Ben', ' score': None}

The column is really called ' score', with a leading space, so 'score' does not exist. When you hit a KeyError, print list(rows[0]) to see the exact names. Also note 'Ben': only one column was present, so score became None, which would fail in int(None) with a TypeError.

Why does csv.DictReader give you '92' and not 92?
A CSV file is only text, and the reader does not guess types. Convert with int(...) or float(...), ideally inside try/except ValueError.
Which argument should you pass to open when reading or writing CSV files, and why?
newline=''. It stops Python from translating line endings, so the csv module can handle them itself, including line breaks inside quoted values.

Recap
  • csv.reader gives lists, csv.DictReader gives dictionaries keyed by the header, and csv.DictWriter writes them back.
  • Every CSV value is a string; convert it yourself and guard the conversion with try/except ValueError.
  • Open CSV files with newline='' (and encoding='utf-8').
  • A KeyError on a column usually means the header has a different spelling or a stray space; print list(rows[0]).
5.12 — JSON: Nested Data as Text

CSV is perfect for flat tables. Much data is not flat: a class with a name, a list of scores, and a small dictionary of settings. JSON (JavaScript Object Notation) writes such nested data as text, and almost every web service and configuration file uses it. It looks very much like Python dictionaries and lists, but it is not the same thing. Printing a Python dictionary does not give valid JSON.

A dictionary is not JSON
import json config = {'name': 'quiz', 'open': True, 'limit': None} print(str(config)) print(json.dumps(config))
Output
{'name': 'quiz', 'open': True, 'limit': None}
{"name": "quiz", "open": true, "limit": null}

JSON uses double quotes only, true and false in lowercase, and null where Python says None. The json module translates in both directions. Remember the four functions by their last letter: s means string. dumps turns a Python object into a JSON string and loads turns a JSON string back into a Python object; dump and load do the same with a file.

The four json functions
             json.dumps(obj)            json.dump(obj, file)
   Python  ------------------> JSON  ----------------------> file
   object  <------------------ text  <----------------------  on disk
             json.loads(text)           json.load(file)

   dict <-> object {}    list, tuple -> array []    str <-> string
   int, float <-> number   True/False <-> true/false   None <-> null
The functions with an s work on strings held in memory; the ones without it work on open files.
loads and dumps
import json text = '{"class": "Room 4", "scores": [92, 85, 78], "meta": {"term": 2, "open": true}}' data = json.loads(text) print(type(data).__name__, data['class']) print(data['scores'][1], data['meta']['open']) data['scores'].append(88) print(json.dumps(data, indent=2))

What survives a round trip

JSON in files

To save a report, open a file with 'w' and hand it to json.dump; to read it back, use json.load. Both take the open file, not a file name.

dump and load with a file
import json report = {'class': 'Room 4', 'scores': {'Asha': 92, 'Ben': 85}} with open('report.json', 'w', encoding='utf-8') as f: json.dump(report, f, indent=2) with open('report.json', encoding='utf-8') as f: loaded = json.load(f) print(loaded == report) print(loaded['scores']['Ben'])
Output
True
85
Common mistakes

Bad JSON raises json.JSONDecodeError, a child of ValueError as you saw in section 5.4. Its message includes a line and column, which is very helpful in a big file. The typical culprits are single quotes and a trailing comma. Another common error is passing a Python object that JSON cannot express, such as a set.

Reading JSONDecodeError and TypeError
import json bad_texts = ["{'name': 'Asha'}", '{"name": "Asha",}', '{"name": "Asha"'] for text in bad_texts: try: json.loads(text) except json.JSONDecodeError as e: print(f'line {e.lineno}, column {e.colno}: {e.msg}') try: json.dumps({'tags': {1, 2}}) except TypeError as e: print('TypeError:', e)
Output
line 1, column 2: Expecting property name enclosed in double quotes
line 1, column 17: Expecting property name enclosed in double quotes
line 1, column 16: Expecting ',' delimiter
TypeError: Object of type set is not JSON serializable

The last mix-up is calling loads on an open file, or load on a string. The message names the type it received, so read it as "I wanted text and got a file".

loads wants text, not a file
import json with open('report.json', 'w', encoding='utf-8') as f: f.write('{"ok": true}') with open('report.json', encoding='utf-8') as f: try: json.loads(f) except TypeError as e: print('TypeError:', e) f.seek(0) print(json.load(f))
Output
TypeError: the JSON object must be str, bytes or bytearray, not TextIOWrapper
{'ok': True}

Finally, JSON often arrives with some keys missing. Reading with .get(key, default) supplies a fallback, while plain indexing raises a KeyError, which you can catch as in section 5.3.

Missing keys: get or KeyError
import json config = json.loads('{"epochs": 5}') print(config.get('epochs', 1), config.get('batch_size', 32)) try: config['batch_size'] except KeyError as e: print('KeyError:', e)
Output
5 32
KeyError: 'batch_size'
Which function turns a Python dictionary into a JSON string, and which reads JSON from an open file?
json.dumps produces the string. json.load reads from an open file. The trailing s in dumps/loads means "string".
Why is json.loads("{'a': 1}") an error, when the same text is a valid Python dictionary?
JSON requires double quotes around strings. Single quotes are valid Python but not valid JSON, so json.JSONDecodeError is raised.

Recap
  • JSON is nested data as text: objects become dicts, arrays become lists, true/false/null become True/False/None.
  • dumps/loads work with strings; dump/load work with open files. Use indent=2 for readable output.
  • Bad JSON raises JSONDecodeError (a ValueError) with the line and column; unsupported types raise TypeError.
  • Use .get(key, default) when a key may be missing.
5.13 — A Quick Recap: How with Works Underneath

You have used with open(...) all chapter. Why does it clean up so reliably? Because a file object promises two things, and with calls them at the right moments. This is a context manager: any object that has the special methods __enter__ (run when the block starts) and __exit__ (run when it ends, however it ends). These are the dunder methods you met in the OOP track, doing a useful job. You do not need to write your own often, but seeing one makes the magic of with disappear.

A tiny context manager that announces itself
class Announce: def __init__(self, name): self.name = name def __enter__(self): print('enter:', self.name) return self def __exit__(self, exc_type, exc_value, traceback): error = exc_type.__name__ if exc_type else None print('exit :', self.name, '| error:', error) return False with Announce('report') as a: print('inside, working on', a.name) try: with Announce('bad run'): int('oops') except ValueError: print('the error still reached the caller')
Output
enter: report
inside, working on report
exit : report | error: None
enter: bad run
exit : bad run | error: ValueError
the error still reached the caller

__enter__ runs first, and what it returns becomes the name after as (that is why a is the object itself). __exit__ always runs at the end. It receives the type, value and traceback of any error that happened inside the block, or None for all three if the block finished normally. Returning False means "I have cleaned up; let the error continue", which is what you almost always want. Returning True would swallow the error silently, exactly like a bare except. Chapter 6 shows a shorter way to make these with a generator function and @contextmanager.

Which two methods make an object usable in a with statement?
__enter__ and __exit__.
What happens to an error raised inside the block if __exit__ returns False?
It continues upward to the caller, as in the run above where except ValueError still caught it after exit : was printed.
Recap
  • with calls __enter__ at the start and __exit__ at the end, even after an error.
  • Files are context managers, so with open(...) closes them for you.
  • __exit__ returning False lets errors continue; True would hide them.

Look before you leap, or ask forgiveness?

There are two styles for dealing with a file that might not be there. Look before you leap (LBYL) checks first with exists(). Ask forgiveness (in Python this is called EAFP) just tries and catches the error. Python code usually prefers the second: the check and the use are two separate moments, and the file can vanish between them, and a try also covers problems you did not think to check, such as permissions.

Two styles, same result
from pathlib import Path name = 'ghost.txt' if Path(name).exists(): print('LBYL: would read', name) else: print('LBYL: file is missing') try: text = Path(name).read_text(encoding='utf-8') except FileNotFoundError: print('EAFP: file is missing')
Output
LBYL: file is missing
EAFP: file is missing
