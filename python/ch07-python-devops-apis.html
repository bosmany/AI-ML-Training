7.1 — What Is a Command-Line Program? Meeting sys.argv

Everything so far, you ran by clicking a button. Real automation is rarely run that way. A script that deploys software, cleans up old files or checks whether a website is alive is started by typing a line into a terminal (also called the command line or shell: a window where you type a command and press Enter). A program you start this way is a command-line program, often shortened to CLI (command-line interface). This chapter is about the small set of tools that let a Python script behave like one, talk to other services, and stay tidy while doing it. We begin with the very first question: how does a script receive its inputs?

Here is the problem. Below is a script that checks a service, but every value is written into the code. To check a different city or a different number of retries, you must open the file, edit it, and save it. If ten people use the script, they each keep their own edited copy.

The hard-coded way: to change anything, edit the code
city = "Pune" retries = 3 print("Checking services in", city) print("Will retry up to", retries, "times")
Output
Checking services in Pune
Will retry up to 3 times

The fix is to let the person who starts the program supply the values on the same line they type. Think of ordering at a coffee counter. The program name is the counter you walk up to. The extra words are your order: check.py Pune 3 means "run check.py, and here are two details for you". Those extra words are called command-line arguments.

From the terminal line to a Python list
  what you type:     python check.py Pune 3
                        |      |     |   |
  the shell splits   ["python","check.py","Pune","3"]   (the words)
  on spaces:               |      |     |   |
                         (the interpreter  ["check.py","Pune","3"]
                          removes itself)          |
                                                   v
  what your script sees:      sys.argv = ["check.py", "Pune", "3"]
                                            [0]        [1]     [2]
Python collects the words after the interpreter name into the list sys.argv. Position 0 is always the script's own name. Every item is a string, even the 3.

The list is named sys.argv (argument vector, an old name for "list of arguments"). It lives in the sys module, which you import like any other. A browser page has no terminal, so we cannot type the line. Instead we assign a list to sys.argv ourselves, pretending a terminal did it. Everything else behaves exactly as it would in a real terminal.

Reading the arguments the program was started with
import sys sys.argv = ["check.py", "Pune", "3"] # pretend the terminal built this print("the whole list:", sys.argv) print("script name :", sys.argv[0]) print("first arg :", sys.argv[1]) print("second arg :", sys.argv[2])
Output
the whole list: ['check.py', 'Pune', '3']
script name  : check.py
first arg    : Pune
second arg   : 3
What Python does, line by line
  • import sys loads the module that holds facts about the running interpreter, including argv.
  • We assign a list of three strings to sys.argv. In a real terminal, Python does this for you before your first line runs.
  • sys.argv[0] is the position-0 item, "check.py". Counting starts at 0, exactly like any list from Chapter 2.
  • sys.argv[1] and sys.argv[2] are the first and second things the user typed after the script name.
Why reading argv by hand gets painful

Reading sys.argv directly works, but it has three sharp edges. First, every item is a string, so numbers need converting. Second, if the user forgets an argument, the list is simply shorter, and your code crashes. Third, nothing tells the user what the program expects. Let us meet the first two.

Everything in argv is a string
import sys sys.argv = ["check.py", "Pune", "3"] retries = sys.argv[2] print("retries is", repr(retries), "and its type is", type(retries).__name__) print("doubling it:", retries * 2) # string repetition, not arithmetic! print("doubling properly:", int(retries) * 2)
Output
retries is '3' and its type is str
doubling it: 33
doubling properly: 6

The line retries * 2 did not give 6. Multiplying a string by 2 repeats it, so "3" became "33". Wrapping the value in int() fixes it. Now the sad path: what if the user types only the city and forgets the number?

A forgotten argumentread-only
import sys sys.argv = ["check.py", "Pune"] # the user forgot the retries number city = sys.argv[1] retries = int(sys.argv[2])
What Python says
Traceback (most recent call last):
  File "<exec>", line 5, in <module>
IndexError: list index out of range

Read the last line first: IndexError: list index out of range. The list has only two items (positions 0 and 1), and we asked for position 2. The message does not say "you forgot the retries number", and a non-programmer would have no idea what to do. You could add if len(sys.argv) < 3: checks and print your own help text, but every script would repeat that work. That repeated work is exactly what the next section removes.

One more piece of background: how did the shell decide where one word ends and the next begins? It splits on spaces, unless you use quotes. The standard library has the same splitter, shlex.split, so we can watch it work.

How a terminal line becomes words
import shlex line = 'python check.py --city "New York" --retries 3' words = shlex.split(line) for number, word in enumerate(words): print(number, repr(word))
Output
0 'python'
1 'check.py'
2 '--city'
3 'New York'
4 '--retries'
5 '3'

The quotes kept New York together as one word and disappeared. Without them, New and York would be two separate arguments, which is a very common cause of "my script got the wrong value" bugs.

If the terminal line is python report.py daily 7, what are sys.argv[0], sys.argv[1], and the type of sys.argv[2]?
"report.py", "daily", and str. Position 0 is the script name, and the 7 arrives as the string "7".
Why does sys.argv[1] * 2 on the input 3 give 33 instead of 6?
Because sys.argv[1] is the string "3", and * on a string repeats it. Convert first with int(sys.argv[1]) * 2.
Try it. Change the list in the second block to have four items, then print len(sys.argv). Then try sys.argv = ["check.py"] and see what sys.argv[1:] (a slice, from Chapter 2) gives you. A slice never raises IndexError.
Recap
  • A command-line program is started from a terminal, and extra words after its name are arguments.
  • Python hands those words to your script as the list sys.argv; item 0 is the script name and every item is a string.
  • Reading sys.argv by hand means converting types yourself and crashing with unhelpful errors when something is missing. argparse (next) solves both.
7.2 — argparse: Describe the Arguments Once, Let Python Do the Boring Work

At the end of the last section we had three annoyances: values arrive as strings, missing values crash with a confusing error, and nobody can ask the program what it expects. The standard library module argparse removes all three. Instead of digging through sys.argv yourself, you first describe the arguments your program accepts. Then you hand the raw words to argparse and it gives back tidy, converted values, or a clear error message if something is wrong.

An everyday comparison is a paper form at a clinic. The form has labelled boxes: name (text), age (whole number), phone (optional). The receptionist does not guess; they check that the required boxes are filled in, and they hand back the form if you wrote "twenty" in the age box. An argparse parser is that receptionist. Each add_argument call draws one labelled box.

Describe once, parse many times
   Step 1: describe the form (once)              Step 2: hand it real words
   +-------------------------------+             +----------------------+
   | parser = ArgumentParser()     |             | ["--city", "Pune",   |
   | --city     text,  required    |  <--------  |  "--retries", "5"]   |
   | --retries  number, default 3  |   parse     +----------------------+
   +-------------------------------+
                   |
                   v
   Step 3: get back an object with tidy attributes
        args.city     ->  "Pune"    (str)
        args.retries  ->  5         (int, already converted)
The parser turns a list of strings into an object whose attributes are named after your flags. parse_args() with no list reads the real sys.argv; here we always pass an explicit list because a browser has no terminal.
The smallest argparse program
import argparse parser = argparse.ArgumentParser(prog="check.py") parser.add_argument("--city") args = parser.parse_args(["--city", "Pune"]) print(args) print(args.city)
Output
Namespace(city='Pune')
Pune
What Python does, line by line
  • ArgumentParser(prog="check.py") creates an empty parser. prog is the program name shown in help and error messages; in a real terminal argparse fills it in for you.
  • add_argument("--city") registers one option. A name that starts with two dashes is a flag: the user writes --city and then its value.
  • parse_args([...]) walks the list. It sees --city, takes the next word "Pune" as its value, and stores it.
  • It returns a Namespace, a plain container. Each flag became an attribute: args.city is "Pune". The leading dashes were dropped from the attribute name.
Types, defaults and required

By default every value is a string. Add type=int (or float) and argparse converts it for you, and rejects anything that cannot be converted. Add default= for a value to use when the flag is missing, and required=True to insist the flag is present. A flag with neither is optional and becomes None when absent.

type, default and required
import argparse parser = argparse.ArgumentParser(prog="check.py") parser.add_argument("--city", required=True) parser.add_argument("--retries", type=int, default=3) parser.add_argument("--note") args = parser.parse_args(["--city", "Pune"]) print("city :", repr(args.city)) print("retries:", repr(args.retries), "(default used)") print("note :", repr(args.note), "(optional, absent)") args = parser.parse_args(["--city", "Pune", "--retries", "5"]) print("retries:", repr(args.retries), args.retries + 1)
Output
city   : 'Pune'
retries: 3 (default used)
note   : None (optional, absent)
retries: 5 6

Notice args.retries + 1 gave 6. That is arithmetic on a real integer, because type=int did the conversion. Compare this with the string "33" surprise from the last section.

What argparse says when the input is wrong

This is where argparse earns its keep. When a required flag is missing, argparse prints a short usage line, an error, and exits the program with status code 2 (which in a terminal means "the command was used wrongly"). Here we read both messages exactly as a real run prints them. SystemExit: 2 on the last line is how exiting shows up inside Python.

A required flag is missingread-only
import argparse parser = argparse.ArgumentParser(prog="check.py") parser.add_argument("--city", required=True) parser.add_argument("--retries", type=int, default=3) parser.parse_args(["--retries", "5"])
What Python says
usage: check.py [-h] --city CITY [--retries RETRIES]
check.py: error: the following arguments are required: --city
SystemExit: 2

Read it line by line. The first line, usage: check.py [-h] --city CITY [--retries RETRIES], is the program's own summary of what it accepts. Square brackets mean optional, so --city (no brackets) is required. The second line names the exact problem: the following arguments are required: --city. The user learns what to fix without you writing a single if.

A value of the wrong typeread-only
import argparse parser = argparse.ArgumentParser(prog="check.py") parser.add_argument("--retries", type=int, default=3) parser.parse_args(["--retries", "many"])
What Python says
usage: check.py [-h] [--retries RETRIES]
check.py: error: argument --retries: invalid int value: 'many'
SystemExit: 2

Again a clear message: argument --retries: invalid int value: 'many'. If you had used sys.argv directly, the failure would have been a ValueError from your own int() call deep inside your code, with no mention of which flag was at fault.

Which two things does add_argument("--limit", type=int, default=10) give you when the user does not type --limit at all?
args.limit exists and equals the integer 10. The default is used as-is (it is already an int), so no error and no None.
A user types --retries five. Does your own code run at all?
No. argparse rejects the value while parsing, prints the usage and error message, and exits with code 2 before any line after parse_args runs.
Try it. Add parser.add_argument("--timeout", type=float, default=2.5) to the third block. Predict repr(args.timeout) first, then run it. Then pass ["--timeout", "1"] and notice that 1 becomes 1.0.
Recap
  • An argparse parser is a description of the arguments you accept: create it, call add_argument for each one, then call parse_args.
  • parse_args(list) returns a Namespace; each flag becomes an attribute, with the dashes dropped.
  • type=, default= and required= handle conversion, fallbacks and mandatory values, and bad input produces a readable usage message plus exit code 2.
7.3 — More argparse: Switches, Choices, Help Text and a Testable main()

A real tool has more than text and number flags. This section adds the remaining pieces you will use constantly: on/off switches, a fixed list of allowed values, help text, positional arguments, and a way of organising the code so it can be tested without a terminal.

A switch (or boolean flag) has no value. Writing --verbose means yes, leaving it out means no. Think of a light switch on a wall: the position carries the meaning, you do not type a value. In argparse you create one with action="store_true". It stores True when present and False when absent.

A switch, and dashes that become underscores
import argparse parser = argparse.ArgumentParser(prog="check.py") parser.add_argument("--verbose", action="store_true") parser.add_argument("--dry-run", action="store_true") print(parser.parse_args([])) print(parser.parse_args(["--verbose"])) args = parser.parse_args(["--dry-run"]) print(args.dry_run) # the dash became an underscore
Output
Namespace(verbose=False, dry_run=False)
Namespace(verbose=True, dry_run=False)
True

Two things happened. Without any words, both switches are False, so you never have to check for None. And the flag --dry-run became the attribute args.dry_run. Python names cannot contain a dash (it would read as subtraction), so argparse swaps it for an underscore.

Sometimes a value must be one of a known set. choices=[...] makes argparse check it for you. This is much safer than accepting any text and discovering the typo later. Here is the sad path first, so you see the real message.

A value that is not in the allowed listread-only
import argparse parser = argparse.ArgumentParser(prog="check.py") parser.add_argument("--env", choices=["dev", "staging", "prod"]) parser.parse_args(["--env", "production"])
What Python says
usage: check.py [-h] [--env {dev,staging,prod}]
check.py: error: argument --env: invalid choice: 'production' (choose from 'dev', 'staging', 'prod')
SystemExit: 2

The message lists every valid option: invalid choice: 'production' (choose from 'dev', 'staging', 'prod'). The user does not need to read your source code to find out the spelling.

Positional arguments and help text

An argument without dashes is positional: its meaning comes from its place in the line, not from a flag name. It is required unless you say otherwise. Use it for the one thing the program obviously cannot work without, like the file to process. Use flags for everything optional. Adding help="..." describes each argument, and argparse builds a --help screen from your descriptions for free.

A positional argument plus help text (what --help prints)
import argparse parser = argparse.ArgumentParser(prog="check.py", description="Check a service.") parser.add_argument("service", help="name of the service to check") parser.add_argument("--retries", type=int, default=3, help="how many times to retry") args = parser.parse_args(["auth-service", "--retries", "2"]) print(args.service, args.retries) parser.print_help()
Output
auth-service 2
usage: check.py [-h] [--retries RETRIES] service

Check a service.

positional arguments:
  service            name of the service to check

options:
  -h, --help         show this help message and exit
  --retries RETRIES  how many times to retry

print_help() is what runs automatically when a user types python check.py --help. You wrote three short strings, and got a manual page that can never go out of date, because it is generated from the very same lines that do the parsing.

Putting it in a function: main(argv=None)

Every example here passes an explicit list. That is not only a browser trick. It is how professionals test command-line programs, because a test cannot type into a terminal. The usual shape is a main function that takes the list as a parameter, defaulting to None. When argv is None, argparse reads the real command line. When you pass a list, it uses that instead.

The main(argv=None) pattern
import argparse def main(argv=None): parser = argparse.ArgumentParser(prog="check.py") parser.add_argument("--city", default="Pune") parser.add_argument("--retries", type=int, default=3) args = parser.parse_args(argv) # None -> real sys.argv return f"checking {args.city} with {args.retries} retries" print(main(["--city", "Lima"])) # a test: no terminal needed print(main([])) # all defaults
Output
checking Lima with 3 retries
checking Pune with 3 retries
What Python does, line by line
  • main(["--city", "Lima"]) builds the parser and calls parse_args with the list it was given, not with sys.argv.
  • city is "Lima"; retries was not supplied, so its default 3 fills in.
  • The function returns an ordinary string, which is easy to compare in a test. Nothing was printed or exited inside main.
  • The second call passes an empty list, so both defaults are used. In a real terminal, calling main() would read whatever the user typed.
--dry-run is defined. What is the attribute name on the result?
args.dry_run. Dashes in flag names become underscores.
When should something be a positional argument and when a --flag?
Positional for the one required main input (like a file name). Flags for options with defaults, switches, and anything the user may reasonably leave out.
Try it. Add parser.add_argument("--env", choices=["dev", "prod"], default="dev") to main, return it in the string, and call main(["--env", "prod"]). Then call main(["--env", "test"]) and read what happens.
Recap
  • action="store_true" makes an on/off switch that is False unless present; --some-flag becomes args.some_flag.
  • choices= restricts a value to a fixed list, and help= text becomes the automatic --help page.
  • Wrap parsing in main(argv=None) so you can test with a list now and read the real command line later.
7.4 — pathlib: Paths That Know They Are Paths

Automation scripts are full of file locations: a log to read, a report folder to create, a config file to load. Chapter 5 showed you files. Now the question is how to write down the *location* of a file without bugs. The obvious tool is a string, and it works, until it does not. Look at what happens when we try to pull a file extension out of a path with string tools.

The string way, and where it breaks
path = "reports/v1.2/run.final.log" name = path.split("/")[-1] extension = name.split(".")[1] print("name :", name) print("extension:", extension) # we wanted 'log' print("joined :", "reports" + "/" + "run.log")
Output
name     : run.final.log
extension: final
joined   : reports/run.log

The extension came out as final, not log, because the name contains two dots. And the joined path uses /, which is right on Linux and macOS but not on Windows, where the separator is \. Hand-made string surgery is fragile.

The module pathlib fixes this by giving paths their own type. A Path object is like a structured postal address rather than a scribbled line: it knows that it has a street (the folder), a house number (the file name) and so on, and it can hand each part back correctly. It also joins pieces with the / operator, using whatever separator the current operating system needs.

The anatomy of a Path
   Path("reports") / "v1.2" / "run.final.log"

   reports/v1.2/run.final.log
   |___________| |__________|
     .parent        .name

   run.final.log
   |_______| |__|
    .stem   .suffix
.parent is everything except the last piece (reports/v1.2), .name is the last piece, .suffix is the final extension including the dot (.log), and .stem is the name without that extension (run.final).
Building a Path and asking it questions
from pathlib import Path p = Path("reports") / "v1.2" / "run.final.log" print("path :", p) print("name :", p.name) print("stem :", p.stem) print("suffix:", p.suffix) print("parent:", p.parent) print("parts :", p.parts)
Output
path  : reports/v1.2/run.final.log
name  : run.final.log
stem  : run.final
suffix: .log
parent: reports/v1.2
parts : ('reports', 'v1.2', 'run.final.log')
What Python does, line by line
  • Path("reports") wraps a string in a Path object. Nothing is looked up on disk; it is only a description.
  • / "v1.2" uses the / operator, which Path redefines to mean "append a piece". The result is a new Path.
  • .suffix correctly finds the last dot, so .log is right even with two dots in the name.
  • .parts shows the pieces as a tuple, so you can inspect or loop over every folder in the path.
Working with real files

A Path also carries the file operations. .exists() asks whether the location is real, .mkdir() creates a folder, .write_text() and .read_text() save and load whole small files, and .glob("*.log") finds files by pattern. We use a temporary folder so the example cleans up after itself.

Create, write, read and search files
import tempfile from pathlib import Path with tempfile.TemporaryDirectory() as tmp: folder = Path(tmp) / "reports" folder.mkdir(parents=True, exist_ok=True) (folder / "a.log").write_text("all good\n") (folder / "b.txt").write_text("notes\n") print("exists:", (folder / "a.log").exists()) print("text :", (folder / "a.log").read_text().strip()) print("logs :", [f.name for f in sorted(folder.glob("*.log"))]) print("no file:", (folder / "zzz.log").exists())
Output
exists: True
text  : all good
logs  : ['a.log']
no file: False

mkdir(parents=True, exist_ok=True) is the safe way to make a folder: parents=True creates missing parent folders too, and exist_ok=True means "do not complain if it is already there". Without it, running the script twice would crash on the second run.

Two common mistakes
Reading a file that does not existread-only
from pathlib import Path Path("missing/run.log").read_text()
What Python says (last line)
FileNotFoundError: [Errno 44] No such file or directory: 'missing/run.log'

FileNotFoundError means exactly what it says: nothing exists at that path. The [Errno 44] number is an operating-system code that differs between systems (you will see [Errno 2] on Linux); the words after it are the same everywhere. The fix is to check .exists() first, or to catch the error with try / except FileNotFoundError (Chapter 4).

Trying to join with + like a stringread-only
from pathlib import Path folder = Path("reports") print(folder + "/run.log")
What Python says (last line)
TypeError: unsupported operand type(s) for +: 'PosixPath' and 'str'

A Path is not a string, so + does not work. Use /. If you need a real string (for example to print or to give to an older function), convert with str(path).

For Path("data/archive.tar.gz"), what are .name, .stem and .suffix?
"archive.tar.gz", "archive.tar" and ".gz". The suffix is only the last extension.
Does Path("nowhere") / "x.txt" touch the disk?
No. It only builds a description. The disk is touched by methods like .exists(), .read_text() or .mkdir().
Try it. Change the file name in the first Path example to "backup.2024.tar.gz" and predict .stem and .suffix before running. Then try p.with_suffix(".txt"), which returns a new Path with the extension swapped.
Recap
  • A Path is an object that understands its own pieces: .name, .stem, .suffix, .parent, .parts.
  • Join with /, never with + or manual slashes; it works on every operating system.
  • File actions live on the Path: .exists(), .mkdir(parents=True, exist_ok=True), .read_text(), .write_text(), .glob().
7.5 — JSON: A Shared Language for Sending Data Between Programs

Programs need to hand data to each other: your script asks a service for information, or saves settings for the next run. But a Python dictionary lives inside Python's memory. You cannot post it through a wire or save it as a file in that form. What travels is text. So both sides need to agree on how a dictionary is spelled as text. The agreement almost everyone uses is JSON (JavaScript Object Notation, pronounced "jay-son"). Despite the name, every language reads it, and it looks a lot like the dicts and lists you already know.

You may wonder why we do not simply use str(my_dict). Let us try, and compare it with the proper tool.

str() is not the same as JSON
import json order = {"id": 7, "paid": True, "note": None, "items": ["tea", "milk"]} print("str :", str(order)) print("json:", json.dumps(order))
Output
str : {'id': 7, 'paid': True, 'note': None, 'items': ['tea', 'milk']}
json: {"id": 7, "paid": true, "note": null, "items": ["tea", "milk"]}

Spot the differences. Python prints single quotes, True and None. JSON demands double quotes, lowercase true and null. Another program (written in Go or JavaScript, say) understands only the JSON spelling. Serializing means turning an in-memory object into text like this, and parsing (or deserializing) means turning the text back into objects.

Two functions, one round trip
     Python object                       JSON text
   {"id": 7, "paid": True}   ---dumps--->   '{"id": 7, "paid": true}'
                                            (sent over a network, or
                                             saved in a file)
   {"id": 7, "paid": True}   <---loads---   '{"id": 7, "paid": true}'

   mnemonic:  dumps = dump to a String      loads = load from a String
The trailing s in dumps and loads stands for "string". Without the s, json.dump and json.load work with an open file instead.
PythonJSON text
dictobject {...} (keys must be strings)
list, tuplearray [...]
strstring, always in double quotes
int, floatnumber
True / Falsetrue / false
Nonenull
Parsing JSON text into Python objects
import json text = '{"ok": true, "count": 2, "tags": ["a", "b"], "owner": null}' data = json.loads(text) print(type(data).__name__) print(data["ok"], type(data["ok"]).__name__) print(data["count"] + 1) print(data["tags"][0]) print(data["owner"])
Output
dict
True bool
3
a
None
What Python does, line by line
  • text is only a string: Python sees characters, not structure.
  • json.loads(text) reads it and builds real objects: a dict, with a bool, an int, a list and a None inside.
  • data["count"] + 1 works as arithmetic because 2 became an actual integer, not the character "2".
  • data["owner"] is None because JSON null maps to Python None.
Nested data: reading it step by step

Real API answers are nested: a dict that contains a list that contains more dicts. Read them from the outside in, one index at a time, just as you would with any nested dict or list from Chapters 2 and 3.

Digging into nested JSON

7.6 — HTTP: How Programs Ask Other Programs for Things

Sooner or later your script needs information that lives on another computer: the status of a service, the weather, a list of orders. That computer runs a program too, and your script must ask it politely in a language both understand. On the internet, that language is HTTP (HyperText Transfer Protocol), a fixed pattern of one request followed by one response. A service that answers HTTP requests with data (rather than web pages for humans) is called an API (application programming interface).

Picture ordering food with a paper slip. The slip has an address (which restaurant), a verb ("show me the menu" or "here is my order"), some notes on the side ("table 4", "I am a member") and possibly the order itself. The kitchen sends back a slip too: a number that says how it went ("ready", "we are out of that"), notes, and the food. Every part of that story has a name in HTTP.

One HTTP conversation
   YOUR SCRIPT                               THE SERVICE
       |                                          |
       |  REQUEST                                 |
       |    method   GET                          |
       |    url      /v1/services?status=down     |
       |    headers  Accept: application/json     |
       |    body     (none for GET)               |
       | ---------------------------------------> |
       |                                          |
       |                              RESPONSE    |
       |                status   200              |
       |                headers  Content-Type ... |
       |                body     {"services": []} |
       | <--------------------------------------- |
The method says what you want (GET reads, POST creates). The status code is a three-digit number that says how it went. Headers are labelled notes, and the body is the actual content, usually JSON text.

A response is only text. To prove it, here is one written out by hand as a string, and a few lines of Python that take it apart. This is what libraries do for you, so seeing it once removes the mystery.

A response is just structured text
import json raw = ("HTTP/1.1 200 OK\r\n" "Content-Type: application/json\r\n" "\r\n" '{"service": "auth", "up": true}') head, body = raw.split("\r\n\r\n", 1) # blank line separates head from body status_line, *header_lines = head.split("\r\n") status = int(status_line.split()[1]) headers = dict(line.split(": ", 1) for line in header_lines) print("status :", status) print("headers:", headers) print("body :", json.loads(body))
Output
status : 200
headers: {'Content-Type': 'application/json'}
body   : {'service': 'auth', 'up': True}
What Python does, line by line
  • The string has three parts: a status line, header lines, a blank line, and the body. The blank line is the divider.
  • raw.split(..., 1) cuts at the first blank line only, giving the head text and the body text.
  • The status line HTTP/1.1 200 OK has the code as its second word; int(...) turns "200" into the number 200.
  • Each header line is Name: value, so splitting on the first ": " builds a dictionary.
  • The body is JSON text, so json.loads (previous section) turns it into a dict.
Reading a URL

The address of a request is a URL. It also has parts, and the standard library can split them, just like Path split a file path.

The parts of a URL
from urllib.parse import urlparse, parse_qs url = "https://api.example.com/v1/services?status=down&limit=5" parts = urlparse(url) print("scheme:", parts.scheme) print("host :", parts.netloc) print("path :", parts.path) print("query :", parts.query) print("params:", parse_qs(parts.query))
Output
scheme: https
host  : api.example.com
path  : /v1/services
query : status=down&limit=5
params: {'status': ['down'], 'limit': ['5']}

The scheme (https) says how to talk, the host says which computer, the path says which thing on it, and the query after the ? carries filters as name=value pairs joined with &. Anything after the ? is a query parameter.

Status codes: the first thing to check

The first digit of the status code tells you almost everything. Your code should look at it before touching the body, because an error response has a different shape from a success response.

CodeNameWho is at fault / what to do

201CreatedA POST made a new thing

400Bad RequestYou sent something malformed; fix the request
401UnauthorizedMissing or wrong credentials

What happens if you ignore the statusread-only

What Python says (last line)
KeyError: 'results'

This code assumed success and went straight for data["results"]. The server had said 404, so the body has no such key, and we get a confusing KeyError: 'results' far from the real cause. The rule of thumb: check the status first, read the body second.

A response arrives with status 503. Whose problem is it, and is it worth retrying?
The server's (5xx means their side). 503 means temporarily unavailable, so retrying after a short wait is reasonable.
In https://api.example.com/v1/orders?limit=5, which part is the path and which is the query?
Path: /v1/orders. Query: limit=5.

Recap
  • HTTP is one request (method, URL, headers, optional body) answered by one response (status code, headers, body).
  • A URL has a scheme, host, path and optional ?name=value query parameters; urllib.parse can split one.
  • Read the status code before the body: 2xx success, 4xx your request was wrong, 5xx the server had trouble.
7.7 — The requests Library: Let Python Hold the Conversation

Writing the request text by hand and opening network connections yourself is slow and easy to get wrong. So almost every Python script uses a third-party library called requests. You give it a URL, it does the whole HTTP conversation, and it hands back a Response object with the parts already separated: .status_code, .headers, .text and a .json() method. Think of it as a personal assistant who makes the phone call and gives you the notes.

There is a catch for this course. A browser page cannot make arbitrary calls to other websites (a browser safety rule called CORS blocks most of them), and your script would depend on someone else's server being up. So the block below is reference only: it shows the exact code you would run in a real terminal. Right after it, we practise everything else with a fake response.

Real script: fetch a list of servicesreference only, no Run button
import requests response = requests.get( "https://api.example.com/v1/services", params={"status": "down", "limit": 5}, # becomes ?status=down&limit=5 timeout=5, # give up after 5 seconds ) response.raise_for_status() # stop here on 4xx / 5xx data = response.json() # same as json.loads(response.text) print([s["name"] for s in data["services"]])
What each line does
   requests.get(url, params=..., timeout=5)
        |         builds ?status=down&limit=5, sends the request,
        |         waits at most 5 seconds for the reply
        v
   response  (a Response object)
        |-- .status_code   200
        |-- .headers       {"Content-Type": "application/json", ...}
        |-- .text          '{"services": [...]}'     (the raw body text)
        |-- .json()        {"services": [...]}       (parsed for you)
        '-- .raise_for_status()   does nothing if 2xx, raises HTTPError otherwise
The Response object is the same information you parsed by hand in 7.6, packaged with helpful methods.

Two lines in that script matter more than they look. timeout=5 tells requests how long to wait. Without it, a stuck server makes your script wait forever, which is one of the most common causes of hung automation jobs. Always pass a timeout. And raise_for_status() turns a 4xx or 5xx status into a Python exception, so the failure stops your script at the right line instead of leaking into the JSON code below it. Silent failures are the worst kind.

Because you cannot call a real service here, we build a small fake response class. It has the same attributes as the real one. Code written against it works unchanged against the real library, and testers use exactly this trick.

A fake Response with the real attribute names
import json class HTTPError(Exception): pass class FakeResponse: def __init__(self, status_code, text, url="https://api.example.com/v1/services"): self.status_code, self.text, self.url = status_code, text, url def json(self): return json.loads(self.text) def raise_for_status(self): if 400 <= self.status_code < 600: raise HTTPError(f"{self.status_code} error for url: {self.url}") ok = FakeResponse(200, '{"services": [{"name": "auth"}, {"name": "db"}]}') ok.raise_for_status() # 200: silently passes print([s["name"] for s in ok.json()["services"]])
Output
['auth', 'db']
What Python does, line by line
  • FakeResponse(200, ...) stores the status, the body text and the URL, just as a real Response would.
  • ok.raise_for_status() checks the range 400 <= 200 < 600, which is false, so it returns without doing anything.
  • ok.json() parses .text with json.loads, so ok.json()["services"] is a list of dicts.
  • The list comprehension picks out each service's name.

Now the sad path: what does the real library say when the server answers 404? We can ask the real requests package to raise its own error, and quote it exactly, because a Response can be filled in by hand.

Real requests error message (run on a normal computer)reference only

The message starts with the code and says whose fault it is: Client Error for 4xx (you asked wrongly) and Server Error for 5xx (they failed). It ends with the URL, so a log line points at the exact call that failed. Here is how the same idea handles both outcomes with our fake class.

Handling a good and a bad response the same way
import json class FakeResponse: def __init__(self, status_code, text): self.status_code, self.text = status_code, text def json(self): return json.loads(self.text) def service_names(response): if response.status_code != 200: return f"request failed with status {response.status_code}" return [s["name"] for s in response.json()["services"]] print(service_names(FakeResponse(200, '{"services": [{"name": "auth"}]}'))) print(service_names(FakeResponse(500, '{"error": "boom"}')))

request failed with status 500

Notice the function returns early when the status is wrong. It never touches the body of a failed response. That is the habit you want.

Ways a call can fail

There are two very different kinds of failure. In the first, the server answered, but with a 4xx or 5xx code: that is an HTTPError (from raise_for_status). In the second, no answer arrived at all, because the network was down or the server too slow: requests raises ConnectionError or Timeout. All of these share a parent, requests.exceptions.RequestException, so one except can catch them all.

Why is timeout= important on every real call?
Without it, requests can wait indefinitely for a server that never answers, and your script hangs instead of failing cleanly.
What is the difference between HTTPError and Timeout?
HTTPError means the server replied with an error status (4xx or 5xx). Timeout means no reply arrived in time.

7.8 — Sending Data: POST, Headers, Tokens, and Retrying Failures

So far we only read with GET. To create something (register a service, submit an order) you send a POST request with a body, usually JSON. Most APIs also want to know who you are. The standard way is to send a secret token in a header called Authorization. A good comparison is a festival wristband: you prove who you are once to get it, then show the wristband at every gate instead of your passport. The token is that wristband, and like a wristband it belongs on your wrist, not in the public URL, and never in code you share.

Real script: POST a JSON body with a bearer tokenreference only, no Run button
import requests response = requests.post( "https://api.example.com/v1/services", json={"name": "cache", "port": 6379}, # body; sets Content-Type for you headers={"Authorization": "Bearer <your-token>"}, timeout=5, ) if response.status_code == 201: print("created:", response.json()) elif response.status_code == 401: print("token missing or wrong") else: response.raise_for_status()

json= does two jobs: it turns your dict into JSON text for the body, and it adds the header Content-Type: application/json so the server knows how to read it. The word Bearer in the header just means "whoever carries this token is allowed in". Because a live call cannot run in the browser, we build a fake server as an ordinary function. It returns a status code and body text, and it checks the same things a real API would: token, valid JSON, required field.

A fake server, and a client that handles every outcome
import json def fake_server(headers, body): if headers.get("Authorization") != "Bearer demo-token": return 401, '{"error": "bad token"}' try: data = json.loads(body) except ValueError: return 400, '{"error": "body is not JSON"}' if "name" not in data: return 400, '{"error": "name is required"}' return 201, json.dumps({"id": 1, "name": data["name"]}) def create(token, body): status, text = fake_server({"Authorization": f"Bearer {token}"}, body) if status == 201: return "created " + json.loads(text)["name"] return f"failed {status}: " + json.loads(text)["error"] print(create("demo-token", '{"name": "cache"}')) print(create("wrong-token", '{"name": "cache"}')) print(create("demo-token", '{"port": 6379}')) print(create("demo-token", "not json"))
Output
created cache
failed 401: bad token
failed 400: name is required
failed 400: body is not JSON
What Python does, line by line
  • create builds the header Authorization: Bearer demo-token and calls the server with the header and the body text.
  • fake_server first checks the token. In the second call it does not match, so the answer is 401 and nothing else is looked at.
  • In the third call the token is fine, but the parsed data has no name, so the answer is 400 with a message that says what to fix.
  • In the fourth call the body is not JSON at all, so json.loads raises ValueError (which JSONDecodeError is a kind of) and the server answers 400.
  • Only the first call reaches 201, and create reports the name from the response body.

Every failure came back as a clear, different message because we looked at the status code. That is what real API client code looks like: a chain of status checks, each with a useful message.

Retrying: because networks hiccup

A 500 or 503 is often temporary. A good script retries a few times, but never forever. Notice the loop below has a fixed maximum of three attempts. A retry loop without a limit is a bug that hammers a struggling server. (Real scripts also time.sleep() between attempts, with growing waits. We leave it out so the output stays instant.)

Retry up to three times on 5xx
attempts_seen = [] def flaky_call(): attempts_seen.append(1) if len(attempts_seen) < 3: return 503 # first two calls fail return 200 for attempt in range(1, 4): status = flaky_call() print(f"attempt {attempt}: status {status}") if status < 500: break else: print("gave up after 3 attempts")
Output
attempt 1: status 503
attempt 2: status 503
attempt 3: status 200

The for ... else block (Chapter 2) runs the else only if the loop was never stopped by break. Change < 3 to < 9 and the service stays down for all three attempts, so you see "gave up". Do not retry a 400 or 401 though: repeating a wrong request never makes it right.

⚠️
Secrets do not belong in your source code. The token above is a made-up demo value. A real token pasted into a script ends up in git history and in screenshots. Section 7.10 shows how to read it from an environment variable instead.
Which statuses are sensible to retry, and which are not?
Retry temporary server-side failures (500, 502, 503) and rate limits (429, after waiting). Do not retry 400, 401, 403 or 404, because the same request will fail the same way.
What does json= do that data= with a dict would not?
It converts the dict to JSON text and sets Content-Type: application/json. A dict passed to data= would be sent as a form, which JSON-only APIs reject.

Recap
  • POST sends data to create something; json= builds the JSON body and its Content-Type header.
  • Authentication is usually a token in the Authorization: Bearer ... header, never in the URL.
  • Branch on the status code (201, 401, 400, ...), and retry only temporary 5xx/429 failures, with a fixed limit.
7.9 — subprocess: Running Other Programs From Python

DevOps scripts rarely work alone. They ask git for the current branch, tell docker to restart a container, or run a linter over a folder. Those tools already exist, so your Python script should start them and read what they say. To understand how, you need one idea: the process. A process is a program while it is running, with its own memory and its own life. When you start git status in a terminal, a new process appears, does its work, prints something, and disappears. Python can start such a child process for you with the subprocess module.

Think of a manager handing a task to a colleague. The manager gives instructions, waits, and gets back three things: the colleague's report (stdout, the normal output), any complaints or warnings (stderr, the error output), and a verdict number called the return code (also called exit status). By long tradition, return code 0 means "it worked" and any other number means "it failed", with each program deciding what its own numbers mean.

Python starts a child process
   YOUR PYTHON SCRIPT                        CHILD PROCESS (e.g. git)
   ------------------                        ------------------------
   subprocess.run(["git","status"]) ------>  starts, does its work
        waits ...                             writes normal output  -> stdout
                                              writes complaints     -> stderr
   <------------------------------------     ends with a number    -> returncode
   CompletedProcess(
       args=[...], returncode=0,
       stdout="...", stderr="")
subprocess.run starts the program, waits until it ends, and returns one object that bundles the three results.

A browser has no operating system underneath to start programs with, so the examples in this section come in two flavours. Reference blocks show the real code and the real output, captured by running it on a normal computer. Runnable blocks use a fake runner that returns the same shape of result, so you can practise handling it.

List arguments vs shell strings: a safety rule

You can give run the command in two ways. As a list, ["echo", "hello"], each item is one separate word and Python starts the program directly. As a single string with shell=True, a whole shell (a command interpreter) reads and interprets the text first. The shell treats characters like ; as "end of this command, start another". If any part of that string came from a user, they can smuggle in their own commands. This attack is called command injection. Watch what a shell would do with a string that has a ; in it.

Why gluing user text into a command line is dangerous
user_text = "hello; echo INJECTED" # what a hostile user might type as_string = "echo " + user_text # the shell=True way print("shell sees one line:", as_string) print("it splits into commands at ';':") for command in as_string.split(";"): print(" run ->", command.strip()) as_list = ["echo", user_text] # the list way print("list way: 1 program, 1 argument ->", as_list)
Output

   run -> echo hello
   run -> echo INJECTED
list way: 1 program, 1 argument -> ['echo', 'hello; echo INJECTED']

Handling results with a fake runner

Deciding what to do from a return code
class Done: def __init__(self, returncode, stdout="", stderr=""): self.returncode, self.stdout, self.stderr = returncode, stdout, stderr def fake_runner(args): if args == ["git", "status", "--short"]: return Done(0, " M app.py\n") return Done(127, "", f"{args[0]}: command not found") def describe(runner, args): result = runner(args) if result.returncode != 0: return f"FAILED ({result.returncode}): {result.stderr}" return "OK: " + (result.stdout.strip() or "no output") print(describe(fake_runner, ["git", "status", "--short"])) print(describe(fake_runner, ["deploytool", "go"]))

7.10 — Environment Variables: Configuration and Secrets Outside Your Code

Look at this script. It works, and it is dangerous.

The problem: a secret written into the source
API_TOKEN = "tk_live_51H8xample" # made-up demo value DB_HOST = "localhost" print("connecting to", DB_HOST) print("token starts with", API_TOKEN[:7] + "...")
Output

If this file is saved in git, the token is now copied to every laptop and every backup, and it stays in the history even after you delete the line. Also, DB_HOST is right for your laptop but wrong on the production server, so you would need a different edited copy of the file for each place it runs. The cure is to keep settings and secrets outside the code and let each environment supply its own.

The mechanism is the environment variable: a named text setting attached to a running process by whoever started it (your shell, Docker, a CI system). Imagine sticky notes on the door of the room where your program runs. The program does not carry the notes; it reads whatever notes the room has. Move the same script to another room and it reads that room's notes. Python exposes them as os.environ, which behaves like a dictionary.

7.11 — asyncio, Part 1: The Waiting Problem and the Event Loop

Suppose your health-check script must ask five services whether they are alive. Each answer takes about a second to arrive over the network. Written the ordinary way, the script asks the first service, waits a second, asks the second, waits a second, and so on: five seconds in total. But during every one of those seconds your computer is doing nothing. It is just waiting for a reply. The work is not heavy; the waiting is what costs time. Work like this, dominated by waiting for the network or a disk, is called I/O-bound (input/output bound).

Here is the ordinary way, with the waiting shown as a message. Pay attention to the order of the lines.

The ordinary (synchronous) way: one thing at a time
def check(name, seconds): print("ask ", name, "(reply takes", seconds, "s)") # ... imagine the program doing nothing for `seconds` here ... print("done", name) for name in ["auth", "db", "cache"]: check(name, 1)
Output
ask  auth (reply takes 1 s)
done auth
ask  db (reply takes 1 s)
done db
ask  cache (reply takes 1 s)
done cache

Each service is fully finished before the next one is even asked. A better plan is what a cook does with three pots of water. The cook does not stare at the first pot until it boils and only then start the second. The cook puts all three on the stove and then checks whichever pot is ready. There is still only one cook, but several dishes are in progress at the same time. Programmers call this concurrency: many tasks in progress, sharing one worker, each one stepping aside while it waits.

Same three checks, two strategies (each # is one second)
   ONE AT A TIME (total 3 s)
   auth   ####
   db         ####
   cache          ####
   time   0---1---2---3

   CONCURRENT with asyncio (total about 1 s)
   auth   ####
   db     ####
   cache  ####
   time   0---1
The waits overlap, so the total is the longest wait rather than the sum of all waits. This only helps when the time is spent waiting. It does not make heavy calculation faster.

Python's tool for this is the standard module asyncio. It has three key ideas.

First, a function declared with async def is a coroutine function. Calling it does not run the body. It hands you a coroutine object, which is like a recipe card that has not been started yet. Second, the keyword await means "start this, and while it is waiting, let others take a turn". await can only appear inside an async def. Third, the event loop is the cook: a manager that keeps a list of coroutines, runs one until it hits an await that must wait, sets it aside, runs another, and comes back when the waiting thing is ready.

Your first coroutine
import asyncio async def greet(): await asyncio.sleep(0) # a "wait" that ends immediately return "hello from a coroutine" card = greet() # nothing has run yet print(type(card).__name__) result = await card # now the event loop runs it print(result)
Output
coroutine
hello from a coroutine
What Python does, line by line
  • async def greet() defines a coroutine function. Python only stores it, as with any def.
  • card = greet() calls it. No line of the body executes. card is a coroutine object, and type(card).__name__ shows coroutine.
  • await card hands the coroutine to the event loop. It runs asyncio.sleep(0), which pauses for a moment (letting other tasks run, if there were any), then continues.
  • The return value becomes the value of the whole await card expression, so result holds the greeting.
💡
Top-level await works in this browser console. Real scripts have no such shortcut and start the loop with asyncio.run(main()). This console already runs an event loop, so a bare await ... at the left margin works here. Section 7.12 shows both forms.
The two classic beginner mistakes

The first mistake is calling a coroutine function and forgetting await. The call creates the recipe card, nobody follows it, and Python warns you when the card is thrown away.

Calling without awaitread-only
import gc async def greet(): return "hello" greet() # forgot await: nothing runs gc.collect()
Output
<exec>:6: RuntimeWarning: coroutine 'greet' was never awaited
RuntimeWarning: Enable tracemalloc to get the object allocation traceback

RuntimeWarning: coroutine 'greet' was never awaited is Python telling you exactly this: a coroutine object was created and thrown away without ever running. The fix is to write await greet(). The second mistake is using await inside a normal def.

await inside a plain functionread-only
import asyncio def check(): result = await asyncio.sleep(0)
What Python says (last line)
SyntaxError: 'await' outside async function

SyntaxError: 'await' outside async function is precise: change def check() to async def check(), and remember that whoever calls it must then await it too. Async code spreads upward through the callers, which is the price of the technique.

What does greet() return when greet is defined with async def?
A coroutine object. The body has not run yet. It runs only when the coroutine is awaited (or scheduled on the event loop).
Would asyncio speed up a function that spends 5 seconds adding numbers in a loop?
No. That work is CPU-bound: the computer is busy, not waiting. Asyncio helps only when tasks spend their time waiting (network, disk, timers).
Try it. In the first coroutine block, change the last two lines to print(await greet()). Predict whether the output changes, then run it.
Recap
  • Slow I/O makes scripts wait; asyncio lets one worker keep several tasks in progress by switching whenever one is waiting.
  • async def makes a coroutine function; calling it gives a coroutine object, and await is what actually runs it.
  • The event loop is the scheduler that runs whichever task is ready. Forgetting await or using it outside async def are the two classic errors.
7.12 — asyncio, Part 2: Running Tasks Together with gather and create_task

One coroutine awaited by itself is no faster than ordinary code. The gain comes from having several in progress at once. To see it without any real network, we use asyncio.sleep(seconds), a coroutine that waits without blocking, as a stand-in for a slow reply. First, let us watch the cook switch between two tasks. Each task prints a line, takes a short wait, and prints another.

Two tasks taking turns
import asyncio async def worker(name): print(name, "starts") await asyncio.sleep(0.01) # a wait: the loop can run someone else print(name, "finishes") async def main(): await asyncio.gather(worker("A"), worker("B")) await main()
Output
A starts
B starts
A finishes
B finishes

If the tasks ran one after another, we would see A starts, A finishes, B starts, B finishes. Instead, both start first, and both finish afterwards. That interleaving is the event loop at work. The tool that made it happen is asyncio.gather(): it takes several coroutines, runs them concurrently, waits until all are done, and returns their results as a list in the same order you passed them in.

What Python does, line by line
  • gather(worker("A"), worker("B")) wraps both coroutines as tasks on the event loop.
  • The loop runs A until its await asyncio.sleep. A prints A starts and is set aside for 0.01 s.
  • The loop switches to B immediately. B prints B starts and is set aside too.
  • After the wait, the loop resumes A (A finishes), then B (B finishes). gather has collected both results and lets main continue.
gather returns results in the order you passed the calls
import asyncio async def fetch(name, delay): await asyncio.sleep(delay) return f"{name} answered" async def main(): results = await asyncio.gather( fetch("slow", 0.03), fetch("fast", 0.01), fetch("medium", 0.02), ) print(results) await main()
Output
['slow answered', 'fast answered', 'medium answered']

The fast service replied first, but results[0] is still the slow one. Position in the list follows the order of the arguments, not the order of completion. That makes results easy to match up with what you asked. The total wait is about the longest delay (0.03 s), not the sum (0.06 s).

create_task: start now, collect later

gather starts things and waits for them in one go. Sometimes you want to start a job, do something else, and collect its result afterwards. asyncio.create_task(coroutine) schedules the coroutine to run on the loop right away and gives you a task, a handle you can await later. Think of putting a dish on the stove now and coming back to plate it when you need it.

Start early with create_task, await later
import asyncio async def slow_report(): print("report: started") await asyncio.sleep(0.02) print("report: finished") return 42 async def main(): task = asyncio.create_task(slow_report()) # starts running "in the background" print("main: doing other work meanwhile") await asyncio.sleep(0) # give the loop a turn so the task starts print("main: now I need the report") value = await task print("main: got", value) await main()
Output
main: doing other work meanwhile
report: started
main: now I need the report
report: finished
main: got 42

Read the output order. main printed its own line, then yielded a turn so the task could begin, then waited for it. If you forget to await a task, the result is lost (and errors inside it may never be seen). So each create_task should end up being awaited.

ToolWhat it doesUse it when
await coro()runs one coroutine and waits for ityou need one result now

Real scripts versus this console

Everything above ends with a bare await main() because this console already has an event loop running. In a real script file, nothing is running yet, so you start the loop yourself with asyncio.run(main()), exactly once, at the bottom of the file. Trying that inside this console fails, because a loop is already running, and Python says so.

Real script: start the event loop once, at the bottomreference only, no Run button
import asyncio async def main(): results = await asyncio.gather(fetch("a", 1), fetch("b", 1)) print(results) if __name__ == "__main__": asyncio.run(main()) # creates the loop, runs main(), closes the loop
asyncio.run() inside a loop that is already runningread-only
import asyncio async def main(): return 1 asyncio.run(main())
What Python says (last line)
RuntimeError: asyncio.run() cannot be called from a running event loop
Three calls each wait 2 seconds. About how long does await asyncio.gather(...) of all three take, and how long would three awaits in a row take?
About 2 seconds with gather (the longest wait). About 6 seconds one after another (the sum).
What is the difference between gather and create_task in one sentence?
gather starts a batch and waits for all of it right there; create_task only starts one job and hands back a handle so you can decide later when to wait for it.
Try it. In the gather block, add a fourth call fetch("instant", 0) at the very end and predict what is at results[3]. Then move it to the front and see which position changes.
Recap
  • asyncio.gather(a, b, c) runs coroutines concurrently and returns their results in the order you passed them, not the order they finished.
  • asyncio.create_task(coro) starts work immediately and returns a handle that you await later.
  • Real scripts start the loop once with asyncio.run(main()); this browser console lets you write await main() directly.
7.13 — asyncio, Part 3: When One Task Fails, Time Limits, and async for / async with

Real services fail. When you check five at once and one of them is down, what should happen to the other four? By default, gather is strict: the first exception is raised out of await asyncio.gather(...), and you never see the other results in that call. This is the sad path, shown first.

Default gather: one failure raises, the batch is lost
import asyncio async def check(service, fail=False): await asyncio.sleep(0.01) if fail: raise ConnectionError(f"{service} unreachable") return f"{service}: OK" async def main(): try: results = await asyncio.gather(check("auth"), check("db", fail=True), check("cache")) print(results) except ConnectionError as err: print("whole batch failed:", err) await main()
Output
whole batch failed: db unreachable

auth and cache were perfectly healthy, but the batch reported one failure and you lost their answers. For a health check that is the wrong behaviour. The fix is the option return_exceptions=True. With it, gather never raises for a failed task. Instead it puts the exception object into the results list, at the position of the failed call, next to the normal results.

return_exceptions=True: failures become values
import asyncio async def check(service, fail=False): await asyncio.sleep(0.01) if fail: raise ConnectionError(f"{service} unreachable") return f"{service}: OK" async def main(): results = await asyncio.gather( check("auth"), check("db", fail=True), check("cache"), return_exceptions=True, ) for r in results: print("FAILED:" if isinstance(r, Exception) else "ok :", r) print("checked", len(results), "services") await main()
Output
ok    : auth: OK
FAILED: db unreachable
ok    : cache: OK
checked 3 services
What Python does, line by line
  • All three checks start together. db raises ConnectionError after its wait.
  • Because of return_exceptions=True, gather catches that exception and stores the exception object in slot 1 of the results, instead of raising it.
  • auth and cache finish normally, so slots 0 and 2 hold their strings. Order still follows the arguments.
  • The loop tests each item with isinstance(r, Exception) to tell an error apart from an ordinary result. Without that test you could not tell them apart.
Time limits

A service that never answers would keep an awaiting script waiting forever, the async twin of a missing timeout= in requests. asyncio.wait_for(coroutine, timeout) sets a limit in seconds. If the coroutine is not done in time, it is cancelled and TimeoutError is raised, which you can catch like any other error.

Giving a slow call a time limit
import asyncio async def very_slow(): await asyncio.sleep(5) return "finally" async def main(): try: await asyncio.wait_for(very_slow(), timeout=0.01) except TimeoutError: print("gave up after 0.01 s") await main()
Output
gave up after 0.01 s
⚠️
One blocking call freezes all the tasks. The event loop can only switch at an await. A call such as time.sleep(2) or a long calculation inside a coroutine never lets go, so every other task waits behind it. Inside async code, use await asyncio.sleep(...), and use libraries designed for async.
Blocking versus awaiting: watch the order
import asyncio, time async def blocking(name): print(name, "start") time.sleep(0.01) # blocks the whole loop, no switching possible print(name, "end") async def main(): await asyncio.gather(blocking("A"), blocking("B")) await main()
Output
A start
A end
B start
B end

Compare with the earlier A starts, B starts, A finishes, B finishes. With a blocking call, task A ran from start to end before B got its first turn. There was no overlap, so no speed-up.

async for and async with (brief)

You may meet two more forms in async libraries. async for loops over a source that produces items one at a time, where fetching each item may itself need to wait (a stream of messages, pages of results). Such a source is an async generator: an async def that uses yield. async with is the async twin of the with statement from Chapter 5: setup and cleanup steps that may need to wait, such as opening and closing a network connection. Both work only inside async def.

async for over an async generator
import asyncio async def pages(): for number in [1, 2, 3]: await asyncio.sleep(0) # pretend each page takes a moment yield f"page {number}" async def main(): async for page in pages(): print("got", page) await main()
Output
got page 1
got page 2
got page 3
async with: waiting setup and cleanup
import asyncio class Connection: async def __aenter__(self): await asyncio.sleep(0) print("connected") return self async def __aexit__(self, exc_type, exc, tb): await asyncio.sleep(0) print("disconnected") async def main(): async with Connection(): print("working") await main()
Output
connected
working
disconnected

The important part is the order: connected, working, disconnected. The cleanup runs even if the body fails, which is why this shape is used for connections. If nothing inside ever needs to wait, an ordinary generator or with is simpler.

With return_exceptions=True, how do you tell whether a result is an error?
Test each item with isinstance(item, Exception). Failed calls appear in the list as exception objects.
Why is time.sleep(2) inside an async def a problem?
It blocks the event loop, so no other task can run for those 2 seconds. Use await asyncio.sleep(2) instead.
Try it. In the return_exceptions block, make cache fail too. Predict the two FAILED: lines and the order, then run. Change return_exceptions=True to False and read what changes.
Recap
  • By default one failing task makes gather raise. Add return_exceptions=True to get errors back as list items, and test them with isinstance(r, Exception).
  • asyncio.wait_for(coro, timeout) puts a time limit on a wait and raises TimeoutError when it is exceeded.
  • Never block inside async def. async for and async with are the same ideas as for and with when each step may wait.
7.14 — Packaging and Entry Points: Turning a Script Into a Command

Suppose your health-check script is useful and a teammate wants it. You email them check.py. They need the right Python, the right libraries, the right folder, and they must type python /some/path/check.py every time. When you fix a bug, they need a new copy. This is the problem that packaging solves: bundling your code, its list of needed libraries, and a command name into something that installs with one command, like any tool from the internet.

Think of a recipe scribbled on a napkin versus the same dish sold as a labelled product with ingredients printed on the box. The napkin works for you. The product works for anyone. A Python package is a folder of code that carries a label, and the label is a file called pyproject.toml. This section is reference only, because it needs a real file system and terminal. But it is short, and every line has a purpose.

What a small package looks like on disk
   healthcheck-cli/
   |-- pyproject.toml           <- the label: name, version, needs, command
   '-- healthcheck_cli/         <- the code itself (a package folder)
       |-- __init__.py          <- empty file that marks the folder as a package
       '-- cli.py               <- contains def main(argv=None): ...
The folder name with dashes is the install name; the folder with underscores is what you import. Python names cannot contain dashes.
pyproject.toml: the labelreference only, no Run button
[project] name = "healthcheck-cli" version = "0.1.0" dependencies = ["requests>=2.31"] # libraries it needs; pip installs them for you [project.scripts] healthcheck = "healthcheck_cli.cli:main" # command name = module.path:function [build-system] requires = ["setuptools>=68"] build-backend = "setuptools.build_meta"

The important line is under [project.scripts]. It says: "create a terminal command named healthcheck. When someone runs it, import the module healthcheck_cli.cli and call its function main." That pair, a name and a module:function target, is called an entry point. Notice it is the same main(argv=None) shape you built in section 7.3. Now the runnable part: we can imitate what the installer's generated launcher does with that string, using only the standard library.

How an entry-point string finds its function
import importlib def resolve(entry_point): module_name, function_name = entry_point.split(":") module = importlib.import_module(module_name) return getattr(module, function_name) func = resolve("math:sqrt") # a stand-in for "healthcheck_cli.cli:main" print(func) print(func(81))
Output
<built-in function sqrt>
9.0
What Python does, line by line
  • The string "math:sqrt" is split at the colon: module name math, function name sqrt.
  • importlib.import_module("math") does what import math does, but with the name held in a variable.
  • getattr(module, "sqrt") fetches the attribute called sqrt, which is the function itself, not a call to it.
  • The launcher then calls that function. For your package it would call main() with no list, so argparse reads the real sys.argv.

Now the code file. The last two lines matter: main returns a number (0 for success, non-zero for failure), and the launcher passes it to the operating system as the process's return code, the same one section 7.9 read with subprocess. That is how a CI system knows your tool failed.

healthcheck_cli/cli.pyreference only, no Run button
import argparse def main(argv=None): parser = argparse.ArgumentParser(prog="healthcheck") parser.add_argument("--city", required=True) parser.add_argument("--threshold", type=float, default=0.8) args = parser.parse_args(argv) print(f"Checking {args.city} with threshold {args.threshold}") return 0 if __name__ == "__main__": # so `python cli.py` also works raise SystemExit(main())

Finally the install and use. pip install -e . installs the package from the current folder (.) in editable mode (-e), meaning edits to your files take effect immediately, which is handy while developing. Below is a real session, with the command names run exactly as typed.

Terminal: install and run (bash)reference only, no Run button

Everything you built earlier appears here: argparse gave the tool its options and its error message, the main(argv=None) shape made it testable, and the entry point made it a real command. Typing healthcheck in a terminal now behaves like any professional tool.

In healthcheck = "healthcheck_cli.cli:main", what is the part before the colon and the part after it?
Before the colon: the module to import (healthcheck_cli.cli). After the colon: the function inside it to call (main).
Why does main return 0, and where does that number end up?
By convention 0 means success. The launcher hands it to the operating system as the program's return code, which other programs (a CI job, a shell script) can check.

Recap
  • Packaging bundles code, its dependencies and a command name so others can install it with pip.
  • pyproject.toml holds the label; the [project.scripts] entry name = "package.module:function" is the entry point that becomes a terminal command.
  • The function behind the command should be main(argv=None) returning an exit code, so it works in the terminal and in tests.

What is the GIL (Global Interpreter Lock), and why does it matter?▶
The GIL is a mutex in CPython that allows only one thread to execute Python bytecode at a time, even on a multi-core machine. It means CPU-bound multithreaded Python code doesn't get real parallelism (use multiprocessing instead, which uses separate processes). I/O-bound code (waiting on network/disk) still benefits from threads or asyncio, since the GIL is released during I/O waits.
Why is a mutable default argument (e.g. def f(x=[]):) a classic Python bug?▶
Default argument values are evaluated ONCE, when the function is defined, not on every call. A mutable default (a list, dict) is shared across every call that doesn't explicitly pass a value — mutating it in one call leaks into every future call. Fix: use def f(x=None): x = x if x is not None else [].
What's the practical difference between a list and a tuple?▶
Lists are mutable (can append/remove/change elements); tuples are immutable (fixed once created). This has real consequences: tuples are hashable (usable as dict keys or set members) if their contents are hashable, lists are not. Tuples are also a signal of intent — "this is a fixed-shape record," like coordinates or a database row — vs. a list's "this is a variable-length collection."
What does a decorator actually do, mechanically?▶
@decorator above a function definition is exactly equivalent to func = decorator(func) — it replaces the function with whatever the decorator returns (usually a wrapper function that calls the original and adds behavior before/after). This is why decorators commonly use *args, **kwargs in their wrapper — to transparently forward any arguments to the original function regardless of its signature.
When would you choose a generator over building a full list?▶
When the sequence is large (or infinite) and you only need to iterate over it once — a generator produces values lazily, one at a time, without holding the whole sequence in memory. Trade-off: you lose the ability to index into it, check its length, or iterate it more than once (it's exhausted after one pass), which a list allows.
What problem do virtual environments solve?▶
Different projects on the same machine often need different, sometimes conflicting, versions of the same package. A virtual environment gives each project its own isolated set of installed packages, so installing/upgrading a dependency for one project can never break another. requirements.txt (or a lockfile) then makes that exact set of dependencies reproducible on any other machine.
What does it mean for an API endpoint to be idempotent, and why does it matter?▶
An idempotent request produces the same end state no matter how many times it's repeated (e.g. PUT /users/5 {name: "Alice"} — setting the name to Alice twice has the same effect as once). This matters because networks are unreliable: if a client doesn't get a response, it needs to be safe to retry. GET, PUT, and DELETE are expected to be idempotent by convention; a plain POST (e.g. "charge this credit card") usually is NOT, which is why retrying a failed payment POST blindly is dangerous.
Why should secrets (API keys, database passwords) be read from environment variables instead of hard-coded in source?▶
Hard-coded secrets end up in git history (and stay there even if later deleted — anyone with repo access, or an old clone, can recover them), get copy-pasted into logs/screenshots, and can't differ between dev/staging/production without editing code. Environment variables (or a secrets manager) keep secrets out of version control entirely and let the exact same code run with different credentials in different environments.
What's the difference between concurrency (asyncio) and parallelism (multiprocessing)?▶
Concurrency (asyncio, threads) interleaves multiple tasks on a single core, useful when tasks spend most of their time WAITING (network calls, disk I/O) — nothing is truly simultaneous, but idle wait time gets used productively. Parallelism (multiprocessing) runs tasks truly simultaneously on multiple CPU cores, useful for CPU-bound work (heavy computation) where there's no idle time to reclaim.
What are the typical stages of a CI/CD pipeline?▶
Roughly: (1) checkout code, (2) install dependencies, (3) run linters/static checks, (4) run automated tests, (5) build an artifact (e.g. a Docker image), (6) deploy to staging, (7) run integration/smoke tests against staging, (8) deploy to production (often gated by manual approval or automatic canary rollout). CI (Continuous Integration) usually refers to steps 1-4/5; CD (Continuous Deployment/Delivery) covers 6-8.
Why pass a list to subprocess.run() instead of a raw shell string?▶
subprocess.run(['git', 'status', user_input], shell=False) (the default) passes each argument as a separate, un-interpreted string — no shell parsing happens, so special characters in user_input can't break out and run arbitrary commands. subprocess.run(f'git status {user_input}', shell=True) passes the whole string to a real shell, which is a classic command-injection vulnerability if user_input isn't fully trusted.
What's the difference between *args and **kwargs?▶
*args collects any extra POSITIONAL arguments into a tuple; **kwargs collects any extra KEYWORD arguments into a dict. Together, def f(*args, **kwargs) can accept literally any call signature — this is exactly how decorator wrapper functions transparently forward calls to the function they're wrapping, regardless of what arguments it expects.
