Chapter 3:
Functions & Modules

Every ML library you will ever use, such as sklearn.metrics.accuracy_score() or torch.nn.functional.relu(), is a function someone wrote once and packaged so everyone could reuse it. This chapter teaches you to write your own, from the first def to your own importable module. You need only Chapters 1 and 2: variables, conditions and loops. Every idea comes with a small program you can run, a trace of what Python does, and the real error messages you will meet along the way.

3.1 — Why Functions? The Pain of Copy-Paste

Chapter 2 ended with a loop you can now write from memory: count how many predictions match the true answers, then divide by the total. That fraction is called accuracy. It is a useful measurement, so you will want it often. Imagine you have the true answers for four test questions and three different models that each made a guess. To score all three, the only tool you have so far is copy and paste.

The same loop, pasted three times
truth = [1, 0, 0, 1] # Model A preds_a = [1, 0, 1, 1] correct = 0 for p, t in zip(preds_a, truth): if p == t: correct += 1 print("Model A accuracy:", correct / len(truth)) # Model B preds_b = [1, 1, 1, 1] correct = 0 for p, t in zip(preds_b, truth): if p == t: correct += 1 print("Model B accuracy:", correct / len(truth)) # Model C preds_c = [0, 0, 0, 0] correct = 0 for p, t in zip(preds_c, truth): if p == t: correct += 1 print("Model C accuracy:", correct / len(truth))
Output
Model A accuracy: 0.75
Model B accuracy: 0.5
Model C accuracy: 0.5

This works, and that is the trap. Nothing is wrong yet, but three problems are waiting. First, a bug has to be fixed in every copy. Suppose you later decide to skip empty lists, or to print percentages. You must change three places, and on the day you forget one, your models are scored by two different rules and nobody notices. Second, the intent is buried. To understand this program you have to read all 21 lines and notice that they are three copies of one idea. Third, the idea has no name. You cannot say "accuracy of B" in code, only repeat the steps that compute it.

Programmers call this problem repetition, and they have a rule against it: DRY, short for Don't Repeat Yourself. Every piece of logic should live in exactly one place. Python's tool for that is the function. A function is a block of code with a name. You write the block once, and then you call it, which means you ask Python to run it, as often as you like.

Think of a recipe card in a kitchen. The recipe for pancakes is written once. Every time you want pancakes you take out the card, gather this morning's ingredients, and follow the same steps. If you improve the recipe, you improve the one card, and every later pancake benefits. A function is that card. The ingredients change from call to call; the steps stay the same.

The same program, with a function

Do not worry about the exact syntax yet. The next two sections explain every word. Just look at the shape: the loop appears once at the top, and each model is scored by one short line.

One definition, three short calls
def accuracy(predictions, truth): correct = 0 for p, t in zip(predictions, truth): if p == t: correct += 1 return correct / len(truth) answers = [1, 0, 0, 1] print("Model A accuracy:", accuracy([1, 0, 1, 1], answers)) print("Model B accuracy:", accuracy([1, 1, 1, 1], answers)) print("Model C accuracy:", accuracy([0, 0, 0, 0], answers))
Output
Model A accuracy: 0.75
Model B accuracy: 0.5
Model C accuracy: 0.5

The output is identical, but the program is half as long and says what it means. If the formula changes, you edit the six lines under def once. You have also been using functions since Chapter 1: print, len, sum, range and zip are all functions someone wrote once so that everybody could reuse them. In this chapter you become the person who writes them.

✅
This is exactly what a library is. When you later call accuracy_score(y_true, y_pred) from scikit-learn, you are calling a function somebody else wrote and packaged. By the end of this chapter you will understand precisely what happens inside a call like that, and you will be able to build and share your own.
The pasted version has three copies of the accuracy loop. If you find a mistake in the loop, how many places must you fix? And in the version with def accuracy?
Three places in the pasted version, and easy to miss one. Only one place in the function version, because the logic exists once and every call reuses it.
Try it. Add a fourth model to the function version: print("Model D accuracy:", accuracy([1, 0, 0, 0], answers)). Notice how little you had to write compared with pasting the whole loop again.
Recap
  • Copy-pasted logic must be fixed in every copy, hides the intent of the program, and has no name.
  • The rule is DRY: keep each piece of logic in exactly one place.
  • A function is a named block of code. You write it once and call it as often as you like, like a recipe card you reuse with different ingredients.
3.2 — A Function Is a Machine: Defining Versus Calling

You have already met the idea of a machine that takes something in and hands something out: a vending machine takes coins and a button press, then gives you a snack. A function is a machine made of code. You feed it inputs, it runs its steps in private, and it hands back an output. You do not need to look inside to use it, and one machine can serve any number of customers.

A function is a machine
   inputs                 the machine                  output
 (what you give)          (the function)          (what you get back)

 [1, 0, 1, 1] --+       +------------------+
                +-----> |    accuracy      | ------>   0.75
 [1, 0, 0, 1] --+       |  count matches,  |
                        |  divide by total |
                        +------------------+
The caller only sees what goes in and what comes out. The steps in the middle are written once, inside the function.
Defining a function: writing the recipe

To create a function you write a definition with the keyword def. Here is the smallest useful one. It has no inputs and no output. It only prints a line, so we can focus on the parts.

Anatomy of a definition
 def   greet   ( name ) :          <- the header
 ^     ^         ^      ^
 |     |         |      +-- colon: "a block starts here"
 |     |         +-- parameter: a blank the caller fills in
 |     +-- the function's name (you choose it)
 +-- keyword that says "I am defining a function"

     print("Hello,", name)         <- the body, indented 4 spaces
The header names the function and lists its inputs. The indented body is the code that runs each time the function is called.
Define once, call twice
def greet(name): print("Hello,", name) print("before the calls") greet("Asha") greet("Ben") print("after the calls")
Output
before the calls
Hello, Asha
Hello, Ben
after the calls
What Python does, line by line
  • Python reads def greet(name):. It does not run the body. It builds a function object, remembers the body inside it, and attaches the name greet to it, the same way x = 5 attaches the name x to a number.
  • print("before the calls") runs normally.
  • greet("Asha") is a call. Python jumps into the body, with the blank name filled in by "Asha". The body prints Hello, Asha. Then Python jumps back to the line after the call.
  • greet("Ben") does the same with "Ben". Same recipe, different ingredient.
  • The last print runs. The definition itself never printed anything.
Define versus call

These are two separate events, and mixing them up is the most common beginner confusion. Defining (def) writes the recipe down and runs nothing. Calling (name(...)) actually cooks. A program with a def and no call does nothing visible at all. Try this experiment to see it for yourself.

A definition alone runs nothing
def shout(): print("HEY!") print("The def line has finished. Was HEY! printed?") shout() print("Now it was, because of the call.")
Output
The def line has finished. Was HEY! printed?
HEY!
Now it was, because of the call.

The parentheses in shout() are the call. They mean "run it now". If you leave them off, you are only naming the machine, not switching it on. Python will not complain, which is why this mistake is sneaky.

shout without parentheses only names the function
def shout(): print("HEY!") shout print(type(shout)) shout()
Output
<class 'function'>
HEY!

The line shout on its own is a valid but useless statement. It looks up the function and does nothing with it. type(shout) confirms that shout is a function object. Only shout() prints.

Common mistakes, with the real error messages

Mistake 1: calling a function before defining it. Python reads a file from top to bottom. When it reaches the call, the name does not exist yet.

Call before defread-only
greet("Asha") def greet(name): print("Hello,", name)
What Python says
Traceback (most recent call last):
  File "<exec>", line 1, in <module>
NameError: name 'greet' is not defined

Read errors from the bottom. NameError: name 'greet' is not defined says Python has never heard of greet at that moment. The line above it tells you which line of your code was running. The fix is to move the def above the first call.

Mistake 2: forgetting to indent the body. The colon promised a block, so Python needs indented lines under it.

Body not indentedread-only
def greet(name): print("Hello,", name)
What Python says
  File "<exec>", line 2
    print("Hello,", name)
    ^^^^^
IndentationError: expected an indented block after function definition on line 1

This is the same IndentationError you met with if in Chapter 2. Every construct that ends its header with a colon needs an indented body.

What does a program that contains only def hello(): print('hi') and nothing else print?
Nothing at all. def only defines the function. Without a call such as hello(), the body never runs.
What is the difference between shout and shout()?
shout is the function itself, a value you can pass around. shout() calls it, which runs its body.
Try it. In the greet example, add a third call with your own name. Then delete the parentheses from one call and see that nothing is printed for it.
Recap
  • A function is a machine: inputs go in, the body runs, an output comes back.
  • def name(parameters): followed by an indented body defines a function and runs nothing.
  • name(...) calls it. Without the parentheses you only refer to the function.
  • A call before the definition gives NameError: name '...' is not defined.
3.3 — Parameters and Arguments: Positional and Keyword

So far greet had one blank to fill in. Real functions often have several, and now the words matter. A parameter is the name in the definition, a labelled blank on a form. An argument is the actual value you supply in a call, the thing you write in the blank. People mix the two words up in casual talk, but reading error messages is easier when you keep them apart: parameters live in the def line, arguments live in the call.

Two parameters, three ways of calling
def describe(name, score): print(name, "scored", score) describe("Asha", 91) # positional describe(score=78, name="Ben") # keyword describe("Chen", score=85) # mixed
Output
Asha scored 91
Ben scored 78
Chen scored 85
Matching arguments to parameters
 def describe(name, score):
                ^      ^
                |      |
 describe("Asha", 91)        positional: matched by ORDER
             ^     ^
             1st   2nd

 describe(score=78, name="Ben")   keyword: matched by NAME
 describe("Chen", score=85)       mixed: positional first,
                                  then keywords
Positional arguments are matched left to right. Keyword arguments carry their own label, so their order does not matter.
What Python does, line by line
  • In describe("Asha", 91) Python matches by position. The first argument fills the first parameter, so name is "Asha" and score is 91.
  • In describe(score=78, name="Ben") each argument names its parameter. Order is irrelevant, so name is "Ben" and score is 78.
  • In describe("Chen", score=85) the positional argument fills name first, and the keyword argument fills score.
  • In all three calls the body then runs with these two names holding those values.

Positional arguments are short but depend on memory: is the order name then score, or score then name? Keyword arguments cost a few extra characters and pay back in clarity. Compare train(10, 32, 0.01) with train(epochs=10, batch_size=32, learning_rate=0.01). The second version tells the reader what each number means, and it survives someone reordering the parameters.

Common mistakes, with the real error messages

Python checks every call against the definition before running the body, and it is picky. Here are the four messages you will see most often. Each one names the function and the parameter that caused trouble.

Too few arguments. A blank was left empty.

Missing an argumentread-only
def describe(name, score): print(name, "scored", score) describe("Asha")
What Python says
Traceback (most recent call last):
  File "<exec>", line 4, in <module>
TypeError: describe() missing 1 required positional argument: 'score'

Too many arguments. Three values were given for two blanks. Notice that Python counts Asha, 91 and 100 as three even though the function only takes two.

One argument too manyread-only
def describe(name, score): print(name, "scored", score) describe("Asha", 91, 100)
What Python says
Traceback (most recent call last):
  File "<exec>", line 4, in <module>
TypeError: describe() takes 2 positional arguments but 3 were given

A keyword that is not a parameter. Perhaps a typo, or the function was renamed.

Unknown keywordread-only
def describe(name, score): print(name, "scored", score) describe("Asha", points=91)
What Python says
Traceback (most recent call last):
  File "<exec>", line 4, in <module>
TypeError: describe() got an unexpected keyword argument 'points'

A positional argument after a keyword argument. Python would not know which blank the loose value belongs to, so it refuses before running anything. The rule is simple: positional first, keywords after.

Positional after keywordread-only
def describe(name, score): print(name, "scored", score) describe(name="Asha", 91)
What Python says
  File "<exec>", line 4
    describe(name="Asha", 91)
                            ^
SyntaxError: positional argument follows keyword argument
With def describe(name, score), what do describe(91, "Asha") and describe(score=91, name="Asha") do?
The first matches by position, so name becomes 91 and score becomes "Asha". Python does not complain, and the output is silently backwards. The second names each argument, so it is correct. This is the strongest argument for keywords.
Which is the parameter and which is the argument in def f(x): ... and f(7)?
x is the parameter (in the definition). 7 is the argument (in the call).
Try it. Call describe with the arguments in the wrong order, describe(91, "Asha"), and read the silent nonsense it prints. Then fix it using keywords.
Recap
  • Parameters are the names in the def line; arguments are the values in the call.
  • Positional arguments match by order; keyword arguments (name=value) match by name and can come in any order, but only after all positional ones.
  • A call that does not fit the definition fails with a TypeError that names the function and the parameter, or with a SyntaxError for positional-after-keyword.
3.4 — What Happens During a Call: Nested Calls and the Call Stack

Functions can call other functions. This is where beginners start to lose track: when one function is in the middle of running and another begins, who is running, and how does Python find its way back? The answer is a tidy structure called the call stack. It is worth understanding once, because it also explains how to read error messages, scope, and recursion later in this chapter.

Picture a stack of sticky notes on a desk. Each time a function is called, Python writes a new note holding that call's own parameters and variables, and places it on top of the pile. Only the top note is being worked on. When that function finishes, its note is thrown away, and the note underneath becomes the active one again. Each note is called a frame.

A function that calls another function
def square(x): print(" square starts with", x) result = x * x print(" square ends, gives back", result) return result def sum_of_squares(a, b): print(" sum_of_squares starts with", a, b) total = square(a) + square(b) print(" sum_of_squares ends, gives back", total) return total print("main: calling sum_of_squares(3, 4)") answer = sum_of_squares(3, 4) print("main: got", answer)
Output
main: calling sum_of_squares(3, 4)
  sum_of_squares starts with 3 4
    square starts with 3
    square ends, gives back 9
    square starts with 4
    square ends, gives back 16
  sum_of_squares ends, gives back 25
main: got 25

The indentation of the printed lines shows the depth of the stack. The keyword return is explained fully in the next section. For now read it as "finish and hand this value back".

The call stack at the moment square(3) is running
   top     | square:  x = 3, result = 9      |  <- running now
           | sum_of_squares:  a = 3, b = 4   |  <- waiting for square
   bottom  | main program:  (no answer yet)  |  <- waiting for both
Only the top frame runs. Each frame keeps its own variables, so x in square and a in sum_of_squares never collide.
What Python does, line by line
  • The main program calls sum_of_squares(3, 4). A frame for it is pushed on the stack, with a = 3 and b = 4.
  • Inside, Python must evaluate square(a) + square(b). It starts on the left with square(3). A new frame for square is pushed on top, with x = 3. The sum_of_squares frame pauses, mid-line, waiting.
  • square computes 9 and returns it. Its frame is popped off and destroyed, and the value 9 is delivered to the paused line in sum_of_squares.
  • Python now evaluates the right side, square(4). Another new frame, x = 4, is pushed, returns 16 and is popped.
  • 9 + 16 is 25. sum_of_squares stores it in total, returns it, and its frame is popped. The main program stores 25 in answer.
Reading an error message is reading the stack

When a program crashes, Python prints the traceback, and now you can read it for what it is: a snapshot of the stack when things went wrong. It lists the frames from the outermost call at the top to the one that actually failed at the bottom. Look at the last two lines first, because they say what went wrong and where.

A crash three calls deepread-only
def average(total, count): return total / count def report(total, count): return "Average: " + str(average(total, count)) print(report(10, 0))
What Python says
Traceback (most recent call last):
  File "<exec>", line 7, in <module>
  File "<exec>", line 5, in report
  File "<exec>", line 2, in average
ZeroDivisionError: division by zero

Read it from the bottom. The last line is the error: ZeroDivisionError: division by zero. The frame just above it says the division happened at line 2 inside average. The frame above that says average was called from line 5, inside report. The top frame says report was called from line 7 of the main program (<module> is Python's name for the main program). So the traceback answers "who called whom" all the way down.

In the trace above, what is on the stack at the deepest moment, and in what order?
From bottom to top: the main program, sum_of_squares, then square. square is on top because it is the one running.
What happens to the variable result inside square after the function returns?
It is destroyed along with the frame. Only the returned value survives, because the caller receives it. This is why variables inside a function are private, which section 3.7 explores.
Try it. Change sum_of_squares so it also prints square(a) a second time, and predict how many square starts lines will now appear before you run it.
Recap
  • Each call creates a frame holding that call's own parameters and variables; frames are stacked, and only the top one runs.
  • When a function returns, its frame is thrown away and Python resumes exactly where the call was made.
  • A traceback is the call stack printed out: read it from the bottom (the error) upwards (who called whom).
3.5 — return vs print: Handing a Value Back

Here is a mistake almost every beginner makes. You write a function that calculates something, you use print inside it to see the answer, and everything looks fine. Then you try to use the answer in the next step, and it is gone. Let us watch that happen.

A function that prints its answer
def add(a, b): print(a + b) total = add(2, 3) print("total is", total)
Output
5
total is None

The 5 on the first line came from the function's print. The second line shows that total holds None. None is Python's special value meaning "nothing here". Every function hands something back to its caller. If the function never says what, Python hands back None automatically. So print(a + b) displayed the answer to a human, but the caller received nothing to work with.

If you now try to use that None in arithmetic, Python stops you:

Using the None that came backread-only
def add(a, b): print(a + b) total = add(2, 3) print(total * 10)
What Python says
Traceback (most recent call last):
  File "<exec>", line 5, in <module>
TypeError: unsupported operand type(s) for *: 'NoneType' and 'int'

unsupported operand type(s) for *: 'NoneType' and 'int' reads as "you tried to multiply nothing by a number". Whenever you see NoneType in an error, ask: which function did I call that forgot to return?

The fix: return

The keyword return ends the function and sends a value back to the exact spot where the function was called. The call itself then *becomes* that value, as if you had typed it there. Think of the difference between shouting an answer across the room and handing over a note. print shouts, so a person hears it, but nobody can pick it up and use it. return hands over the note, which the caller can store, add to, compare, or print if it likes.

Same function, with return
def add(a, b): return a + b total = add(2, 3) print("total is", total) print(total * 10) print(add(add(1, 2), 4))
Output
total is 5
50
7
What Python does, line by line
  • add(2, 3) runs the body with a = 2 and b = 3.
  • return a + b computes 5, ends the function at once, and delivers 5 to the call site.
  • So the line total = add(2, 3) behaves like total = 5.
  • Because the call *is* a value, it can be nested: add(add(1, 2), 4) first evaluates the inner call to 3, then runs add(3, 4).

A useful rule: functions that calculate should return; functions whose whole job is to show something (like a report) may print. Keeping the two apart lets you reuse calculations in many places.

return stops the function: early return

The moment Python executes return, the function is over. Lines after it are skipped. That lets you write functions that answer as soon as they know, instead of piling up nested else blocks.

Several returns, only one runs
def sign(n): if n < 0: return "negative" if n == 0: return "zero" return "positive" print(sign(-5), sign(0), sign(12))
Output
negative zero positive
Returning more than one value

A function may return several values by separating them with commas. Python packs them into one bundle called a tuple (a fixed group of values, like a list you cannot change; Chapter 4 studies them properly). The caller can unpack the bundle into separate names in one line.

Returning two values
def low_high(values): return min(values), max(values) low, high = low_high([4, 9, 2, 7]) print("low:", low, "high:", high) both = low_high([4, 9, 2, 7]) print(both, type(both))
Output
low: 2 high: 9
(2, 9) <class 'tuple'>

The names on the left of low, high = must match the count of values returned. Otherwise Python tells you exactly how many it found:

Wrong number of names when unpackingread-only
def low_high(values): return min(values), max(values) low, high, middle = low_high([4, 9, 2, 7])
What Python says
Traceback (most recent call last):
  File "<exec>", line 4, in <module>
ValueError: not enough values to unpack (expected 3, got 2)
⚠️
Beginner trap: if a path through the function reaches the end without hitting return, the result is None. A function with if n > 0: return "positive" and no final return gives back None for zero and negative numbers. Make sure every path returns something.
What does print(add(2, 3)) display if add uses print(a + b) instead of return a + b?
It displays 5 from inside the function, and then None, because the outer print receives the function's result, which is None.
What does def f(): return 1, 2 give back when called?
One tuple, (1, 2). Writing x, y = f() unpacks it into two names.
Try it. Write def square(n): return n * n and print square(square(3)). Predict the answer first, then check it.
Recap
  • return value ends the function and hands the value back to the caller; the call then acts as that value.
  • print only displays. A function without return gives back None, which causes NoneType errors later.
  • Several return lines are fine, because only one runs. return a, b gives back a tuple you can unpack.
  • Make sure every path through a function returns something.
3.6 — Default Values, a Famous Trap, and *args / **kwargs

Some parameters almost always take the same value. If a formatting function nearly always shows four decimals, forcing every caller to type 4 is noise. A default value lets the parameter be optional: write name=value in the definition, and callers who leave the argument out get that value.

A parameter with a default
def format_metric(name, value, decimals=4): return f"{name}: {value:.{decimals}f}" print(format_metric("loss", 0.123456)) print(format_metric("accuracy", 0.9423, decimals=2)) print(format_metric("f1", 0.88, 1))
Output
loss: 0.1235
accuracy: 0.94
f1: 0.9

The first call omits decimals, so Python uses 4. The second overrides it with a keyword. The third overrides it by position. One rule keeps this readable: parameters with defaults must come after those without. Python enforces it.

A default before a required parameterread-only
def format_metric(decimals=4, name, value): return f"{name}: {value:.{decimals}f}"
What Python says
  File "<exec>", line 1
    def format_metric(decimals=4, name, value):
                                  ^^^^
SyntaxError: parameter without a default follows parameter with a default
The mutable default trap

Defaults hide one surprise that catches experienced programmers too. The default value is created once, at the moment Python runs the def line, and not fresh at every call. For numbers and strings that does not matter, because they cannot be changed in place. For a list it matters a lot, because the same list is reused every time. Watch a shopping basket that is supposed to start empty on each call:

A default list that remembers
def add_item(item, basket=[]): basket.append(item) return basket print(add_item("apple")) print(add_item("pear")) print(add_item("plum")) print(add_item.__defaults__)
Output
['apple']
['apple', 'pear']
['apple', 'pear', 'plum']
(['apple', 'pear', 'plum'],)

The three baskets are not separate: it is the same list, growing. The last line shows the culprit sitting inside the function object, holding all three items. Python built that empty list once when it read the def, and every call that omitted basket used it.

When the default is created
 def add_item(item, basket=[]):  <- runs ONCE: the empty list is created here
     ...
 add_item("apple")   -> basket is that same list -> ['apple']
 add_item("pear")    -> basket is that same list -> ['apple', 'pear']
The def line runs once. The body runs at every call. A default written in the header is created at the first moment, not the second.

The standard fix uses None as a stand-in and builds the fresh list inside the body, where it runs on every call.

The fix: None as the default
def add_item(item, basket=None): if basket is None: basket = [] basket.append(item) return basket print(add_item("apple")) print(add_item("pear")) print(add_item("plum", ["fig"]))
Output
['apple']
['pear']
['fig', 'plum']
*args: any number of positional arguments

Sometimes you cannot know how many values the caller will send, as with the built-in max(3, 9, 4). A parameter written *numbers collects every extra positional argument into a tuple. The name args is only a convention, and the star is what matters.

*args collects extras into a tuple
def average(*numbers): print("received:", numbers) return sum(numbers) / len(numbers) print(average(4, 8)) print(average(1, 2, 3, 4)) scores = [90, 70, 80] print(average(*scores))
Output
received: (4, 8)
6.0
received: (1, 2, 3, 4)
2.5
received: (90, 70, 80)
80.0

On the last call the star works in reverse. average(*scores) unpacks the list so that each item becomes a separate argument. So a star in the definition collects, and a star in the call spreads.

**kwargs: any number of named settings

Two stars collect extra keyword arguments into a dictionary, a lookup table of name-and-value pairs. The dictionary method .get(key, default) reads a value, and gives the default if the key is missing. This is the pattern behind calls like model.fit(X, y, epochs=10, batch_size=32).

**kwargs collects named extras into a dictionary
def train(model, **settings): print("training", model, "with", settings) print("epochs:", settings.get("epochs", 1)) train("tiny", epochs=5, rate=0.1) train("small")
Output
training tiny with {'epochs': 5, 'rate': 0.1}
epochs: 5
training small with {}
epochs: 1
Why does add_item("apple") keep growing the same basket when the default is []?
Because a default value is created once, when def runs. Every call that omits the argument receives that same list. Using None and creating the list inside the body makes a new one per call.
What type is numbers inside def f(*numbers) when called as f(1, 2)?
A tuple, (1, 2). Inside the function you can loop over it, take len(), or pass it to sum().
Try it. Call average() with no arguments and read the error. Why does it happen, and what could the function check for to avoid it?
Recap
  • name=value in a definition makes a parameter optional; defaulted parameters go after required ones.
  • A default is created once, when def runs, so a list default is shared between calls. Use None and create the list in the body.
  • *args collects extra positional arguments into a tuple; **kwargs collects extra keyword arguments into a dictionary.
  • A star in a call (f(*items)) does the reverse and spreads a collection into separate arguments.
3.7 — Scope: Which Names Can a Function See?

You saw in the call stack that every call gets its own private frame. That has a big consequence. A variable created inside a function belongs to that function's frame, and it vanishes when the function returns. The region of a program where a name can be used is called its scope. Variables created inside a function have local scope. Variables created at the top of your file have global scope.

Think of a function as a room with its own whiteboard. Whatever you write on it stays in the room and is wiped when you leave. From inside the room you can look out through the window at the main hall's notice board (globals), but people in the hall cannot see your whiteboard.

A local variable is invisible outsideread-only
def make_total(a, b): total = a + b return total make_total(2, 3) print(total)
What Python says
Traceback (most recent call last):
  File "<exec>", line 6, in <module>
NameError: name 'total' is not defined

The variable total existed only during the call. The fix is to keep the value the function returned: total = make_total(2, 3) creates a new name in the outer scope, and the value travels through return.

The lookup order: LEGB

When Python meets a name, it searches four places in a fixed order, and uses the first match. The order is remembered by the word LEGB.

Where Python looks for a name
 L  Local      names created inside this function        (searched 1st)
 E  Enclosing  names in any function this one sits in    (2nd)
 G  Global     names at the top level of the file        (3rd)
 B  Built-in   names Python provides: print, len, sum... (last)

 not found in any of the four  ->  NameError
Python stops at the first match. If you create a local named count, it hides any global count while the function runs.
Local names hide global ones
count = 10 def show_local(): count = 99 print("inside:", count) def show_global(): print("reading the global:", count) show_local() show_global() print("outside:", count)
Output
inside: 99
reading the global: 10
outside: 10

show_local creates its own count, so the global stays at 10. show_global never assigns, so Python falls through to the global. Reading a global from a function works. Assigning creates a local, and that is where trouble starts.

Changing a global: global, and why it is risky

If a function assigns to a name anywhere in its body, Python decides at the start that the name is local for the whole function. Then a line like total = total + n reads total before the local one has a value:

Reading and assigning the same nameread-only
running_total = 0 def add_to_total(n): running_total = running_total + n add_to_total(5)
What Python says
Traceback (most recent call last):
  File "<exec>", line 6, in <module>
  File "<exec>", line 4, in add_to_total
UnboundLocalError: cannot access local variable 'running_total' where it is not associated with a value

The keyword global tells Python that a name in this function refers to the global one, so assignments change it:

global changes the outer variable
running_total = 0 def add_to_total(n): global running_total running_total = running_total + n add_to_total(5) add_to_total(3) print(running_total)
Output
8

That works, so why do experienced programmers avoid it? Because add_to_total now has a hidden connection to the outside world. Its result depends on a variable that is not among its parameters, and its effect changes that variable without saying so in its signature. To predict what a call does you must read the whole program. Two functions that both touch the same global can break each other, and testing one function alone gets harder. The cleaner design passes values in and returns the result:

The same job without a global
def add_to_total(total, n): return total + n running_total = 0 running_total = add_to_total(running_total, 5) running_total = add_to_total(running_total, 3) print(running_total)
Output
8

Now everything that add_to_total needs arrives as an argument and everything it produces leaves as a return value. You can understand it by reading four lines. A last hazard is shadowing a built-in: naming your own variable sum or max hides the real function from LEGB's last step.

Shadowing a built-inread-only
sum = 100 print(sum([1, 2, 3]))
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
TypeError: 'int' object is not callable

The error reads oddly until you decode it. After the first line, the name sum refers to the number 100, not to the built-in function, so sum([1, 2, 3]) tries to call a number like a function. 'int' object is not callable is Python's way of saying "you put parentheses after something that is not a function". Choose names like total or scores_sum instead.

What does this print? x = 5, then def f(): x = 8, then f(), then print(x).
5. Inside f the assignment creates a separate local x. The global is untouched.
Give two reasons to prefer return over global.
The function's inputs and outputs are all visible in its signature, so you can understand and test it alone. And no other code can change your variable behind your back.
Try it. Delete the global running_total line from the global example and run it to see the UnboundLocalError for yourself.
Recap
  • Variables assigned inside a function are local: they exist only during the call.
  • Python looks names up in the order Local, Enclosing, Global, Built-in.
  • Reading a global works; assigning to a name makes it local unless you declare global name.
  • Prefer passing arguments in and returning results out; avoid global and never reuse names like sum or list.
3.8 — Recursion: A Function That Calls Itself

Because every call has its own frame, a function can safely call itself. This is called recursion, and it fits problems that contain smaller copies of themselves. Take "add the numbers from 1 to 4". That is 4 plus "add the numbers from 1 to 3", which is 3 plus "add the numbers from 1 to 2", and so on. The problem shrinks each time until it becomes trivially small. Russian nesting dolls work the same way: open one and find a smaller one, until you reach a doll that does not open.

Every correct recursive function has two parts. The base case is the smallest problem, which the function answers directly without calling itself. The recursive case reduces the problem and calls itself on the smaller version. Miss the base case and the calls never stop.

Adding 1 to n, recursively
def total_to(n): if n == 1: return 1 return n + total_to(n - 1) print(total_to(4))
Output
10

This prints 10, and you can watch the mechanism if the function announces each step. The indent shows the stack depth:

Watching the stack grow and shrink
def total_to(n, depth=0): pad = " " * depth print(pad + "total_to(" + str(n) + ") called") if n == 1: print(pad + "base case: return 1") return 1 result = n + total_to(n - 1, depth + 1) print(pad + "total_to(" + str(n) + ") returns " + str(result)) return result total_to(4)
Output
total_to(4) called
  total_to(3) called
    total_to(2) called
      total_to(1) called
      base case: return 1
    total_to(2) returns 3
  total_to(3) returns 6
total_to(4) returns 10
What Python does, line by line
  • total_to(4) is called. It is not the base case, so it needs total_to(3) before it can add 4. It pauses, with a frame that remembers n = 4.
  • total_to(3) pauses waiting on total_to(2), and that on total_to(1). Four frames are now stacked.
  • total_to(1) hits the base case and returns 1 without calling anything.
  • The frames finish in reverse order: 2 + 1 = 3, then 3 + 3 = 6, then 4 + 6 = 10.
  • Each frame had its own n, which is exactly why the calls do not confuse one another.

A second classic is the factorial, written n!, the product of 1 through n, so 4! = 4 x 3 x 2 x 1 = 24. The definition is itself recursive: n! = n x (n-1)!.

Factorial
def factorial(n): if n <= 1: return 1 return n * factorial(n - 1) for n in range(1, 6): print(n, "! =", factorial(n))
Output
1 ! = 1
2 ! = 2
3 ! = 6
4 ! = 24
5 ! = 120
Forgetting the base case

If nothing ever stops the recursion, the stack grows until Python protects itself and raises a RecursionError. Python allows about a thousand frames by default. The real traceback repeats the same line hundreds of times, so only its final line is shown here.

A recursion with no base caseread-only
def countdown(n): return countdown(n - 1) countdown(3)
What Python says (last line of a very long traceback)
RecursionError: maximum recursion depth exceeded

For a job like adding 1 to n, a plain for loop does the same work with less memory, and often reads just as clearly. Use recursion when the problem is naturally made of smaller copies of itself, such as folders inside folders, which you will meet later, and use a loop when you are simply counting.

What are the base case and the recursive case in factorial?
Base case: n <= 1 returns 1 with no further calls. Recursive case: n * factorial(n - 1), which shrinks the problem by one and calls itself.
What would happen if you changed the base case in total_to to if n == 0: and called total_to(-1)?
It never reaches 0, because n only counts down from -1 to -2 and so on. You would get a RecursionError.
Try it. Call factorial(10), then factorial(5.5). The n <= 1 base case still stops the second one. Now change the base case to n == 1 and call factorial(5.5) again. Why does that one never stop?
Recap
  • Recursion means a function calls itself on a smaller version of the problem.
  • Every recursive function needs a base case that stops the calls, and a recursive case that moves toward it.
  • Each call has its own frame, so the calls do not confuse each other; the answers come back in reverse order.
  • With no reachable base case Python raises RecursionError after about a thousand calls.
3.9 — lambda: A Tiny Function Without a Name

Some functions are so small and so temporary that naming them feels like overkill. Suppose you have a list of (name, score) pairs, and you want them ordered by score. The built-in sorted can do that if you tell it how to pick the value to sort by. You do this with the key parameter, which expects a function. sorted calls that function once on each item and orders the items by whatever comes back.

Sorting with a named function as the key
results = [("Asha", 72), ("Ben", 95), ("Chen", 81)] def get_score(pair): return pair[1] print(sorted(results, key=get_score)) print(sorted(results, key=get_score, reverse=True))
Output
[('Asha', 72), ('Chen', 81), ('Ben', 95)]
[('Ben', 95), ('Chen', 81), ('Asha', 72)]

Here pair[1] means "the item at position 1" of the pair. Counting starts at 0, so position 0 is the name and position 1 is the score. The definition of get_score takes three lines for one tiny idea. A lambda expresses the same function in one line, right where it is needed.

A lambda is a one-line function
 def get_score(pair):         lambda pair: pair[1]
     return pair[1]           ^      ^     ^
                              |      |     +-- the value it gives back
                              |      +-- parameters, then a colon
                              +-- keyword (no def, no name, no return)
A lambda has parameters before the colon and one expression after it. The result of that expression is automatically returned.
The same sort with a lambda
results = [("Asha", 72), ("Ben", 95), ("Chen", 81)] ranked = sorted(results, key=lambda pair: pair[1], reverse=True) print(ranked) print("Top:", ranked[0][0]) print(max(results, key=lambda pair: pair[1])) add = lambda a, b: a + b print(add(2, 3))
Output
[('Ben', 95), ('Chen', 81), ('Asha', 72)]
Top: Ben
('Ben', 95)
5
What Python does, line by line
  • sorted visits each pair and calls the lambda with it. The lambda receives ("Asha", 72) as pair and gives back 72. It does the same for the other two pairs, collecting 72, 95, 81.
  • sorted orders the pairs by those collected numbers. reverse=True puts the highest first.
  • ranked[0][0] means "the first pair, then the first item of it", which is the name "Ben".
  • max accepts the same key idea and returns the single pair with the biggest score.
  • The last two lines show that a lambda is an ordinary function object. Giving it a name with add = ... works, though a def is the better choice once a function deserves a name.
What a lambda cannot do

A lambda holds exactly one expression: something with a value. It cannot contain statements such as return, if blocks over several lines, loops or assignments. If you need those, use def.

A statement inside a lambdaread-only
bad = lambda x: return x + 1
What Python says
  File "<exec>", line 1
    bad = lambda x: return x + 1
                    ^^^^^^
SyntaxError: invalid syntax
What does (lambda a, b: a * b)(3, 4) evaluate to?
12. The lambda is created and immediately called with 3 and 4.
When should you prefer def over lambda?
When the function needs a name you will reuse, more than one line, or a docstring. Lambdas are for tiny, one-off jobs, typically passed as an argument.
Try it. Sort results by name length using key=lambda pair: len(pair[0]), then sort by name alphabetically with key=lambda pair: pair[0].
Recap
  • lambda params: expression builds a small anonymous function whose expression value is returned automatically.
  • Its main use is as the key for sorted, max and min, which call it on each item.
  • A lambda can only contain one expression. Use def for anything larger.
3.10 — Docstrings and Type Hints: Explaining Your Functions

Imagine opening a function you wrote three months ago: def f1(a, b):. What are a and b? What comes back? Good names help, but two extra tools make a function explain itself. A docstring says in words what the function does. Type hints say what kinds of values go in and come out.

Docstrings

A docstring is a string written as the very first line inside a function's body, using triple quotes. It does not run as code. Python stores it on the function, and tools such as help() and code editors display it.

A function with a docstring
def f1_score(precision, recall): """Return the F1 score: the harmonic mean of precision and recall.""" return 2 * precision * recall / (precision + recall) print(f1_score(0.8, 0.6)) print(f1_score.__doc__) help(f1_score)
Output
0.6857142857142857
Return the F1 score: the harmonic mean of precision and recall.
Help on function f1_score in module __main__:

f1_score(precision, recall)
    Return the F1 score: the harmonic mean of precision and recall.

__doc__ is the stored text, and help() formats it with the function's signature. For a longer function, write a short summary line, then a blank line, then details about the parameters and the return value. A good first line says what the function *does*, in the imperative: "Return the average of the numbers", not "This is a function".

Type hints

A type hint is a note that names the expected type of a parameter or return value. Parameters get a colon and a type (x: int). The return type follows an arrow after the parentheses (-> float). A function that returns nothing is hinted -> None.

Type hints on a definition
def average(values: list[float]) -> float: return sum(values) / len(values) def repeat(word: str, times: int = 2) -> str: return word * times def announce(message: str) -> None: print("NOTE:", message) print(average([0.5, 0.75, 1.0])) print(repeat("ha")) announce("done") print(average.__annotations__)
Output
0.75
haha
NOTE: done
{'values': list[float], 'return': <class 'float'>}

The hints appear in __annotations__, but Python does not enforce them. They are documentation for people and for checking tools such as mypy and your editor, which can warn you before you run the code. Watch what happens when you break the promise:

Hints are not enforced
def double(x: int) -> int: return x * 2 print(double(4)) print(double("ab"))
Output
8
abab

double("ab") ignores the hint and repeats the string, because "ab" * 2 is valid Python. The hint said int, and nobody checked. The hint is a promise you make to the reader, and the checking tools hold you to it. Also note how defaults combine with hints: times: int = 2 puts spaces around the equals sign when a hint is present.

What does the hint -> None tell the reader?
That the function is called for its effect (printing, saving) and gives back nothing useful, so there is no point storing the result.
If a function has type hints but you pass a value of the wrong type, will Python stop you?
No. Python ignores hints at run time. Only external tools such as mypy, or your editor, warn about it.
Try it. Add a docstring and hints to add(a, b) from section 3.5, then print add.__doc__.
Recap
  • A docstring is a triple-quoted string as the first line of a function body; read it with help(f) or f.__doc__.
  • Type hints (x: int, -> float, -> None) document the inputs and output but are never enforced by Python.
  • Together they let a function explain itself to you, your teammates, and your tools.
3.11 — Closures and nonlocal: Functions That Remember

Functions are values, so a function can return another function. Sometimes you want a family of similar functions: one that doubles, one that triples. Writing each separately repeats yourself. Instead, write a function that *builds* them. A function defined inside another function is a nested function. If the inner function uses a variable from the outer function, it keeps that variable alive even after the outer function has finished. That combination is a closure: the function plus the surrounding variables it remembers.

A function that builds functions
def make_multiplier(factor): def multiply(x): return x * factor return multiply double = make_multiplier(2) triple = make_multiplier(3) print(double(5), triple(5)) print(double(10), triple(10))
Output
10 15
20 30
Each closure carries its own backpack
 make_multiplier(2)  ->  multiply  + backpack {factor: 2}   = double
 make_multiplier(3)  ->  multiply  + backpack {factor: 3}   = triple

 double(5): x=5 arrives, factor=2 comes from the backpack -> 10
 triple(5): x=5 arrives, factor=3 comes from the backpack -> 15
The outer function is finished, yet factor survives, because the inner function holds on to it.
What Python does, line by line
  • make_multiplier(2) runs, so its frame gets factor = 2. Inside, def multiply creates a new function object that refers to that factor.
  • return multiply hands the inner function back. Normally the frame would now be discarded, but the inner function still needs factor, so Python keeps that one variable alive.
  • A second call make_multiplier(3) creates a completely separate frame and a separate multiply, with its own factor = 3.
  • double(5) runs multiply with x = 5. Python finds x locally and factor in the enclosing scope, which is the E in LEGB from section 3.7. The answer is 10.

Notice that return multiply has no parentheses. We return the function itself and do not call it. Writing return multiply(...) would run the inner function early instead.

Changing the remembered variable: nonlocal

A closure can also keep state between calls, like a counter, with no global variable. There is one catch that follows the scope rules. Assigning to a name inside the inner function would create a new local, as with global earlier. The keyword nonlocal says "this name belongs to the nearest enclosing function".

A counter that remembers its count
def make_counter(): count = 0 def increment(): nonlocal count count += 1 return count return increment first = make_counter() second = make_counter() print(first(), first(), first()) print(second())
Output
1 2 3
1

Each counter keeps its own count, so first reaches 3 while second is still at 1. Without nonlocal, the line count += 1 would try to read a local count before it has a value, and fail exactly as in section 3.7:

Forgetting nonlocalread-only
def make_counter(): count = 0 def increment(): count += 1 return count return increment counter = make_counter() counter()
What Python says
Traceback (most recent call last):
  File "<exec>", line 9, in <module>
  File "<exec>", line 4, in increment
UnboundLocalError: cannot access local variable 'count' where it is not associated with a value
💡
nonlocal versus global: global reaches the top level of the file; nonlocal reaches only the nearest enclosing function. Use closures when a little private state is needed, and a class (Chapter 5) once the state grows.
Why does double(5) still know factor = 2 after make_multiplier has finished?
The inner function holds a reference to factor, so Python keeps that variable alive as part of the closure.
What is the difference between return multiply and return multiply(2) in the outer function?
The first returns the function itself. The second calls it right away and returns its result, which is a number, not a function.
Try it. Write make_greeter(greeting) that returns a function taking a name and returning greeting + ", " + name. Make one that says Hello and one that says Hi.
Recap
  • A function can return a function. The inner function remembers variables from the outer one: a closure.
  • Each call of the outer function makes a separate set of remembered variables.
  • To reassign a remembered variable from the inner function, declare it nonlocal.
3.12 — functools: Ready-Made Tools for Functions

Python ships with a module (a file of ready-made code; section 3.13 explains modules) called functools, full of tools that work on functions. Three of them are worth knowing now. Each solves a problem that you would otherwise solve with more code.

partial: pre-fill some arguments

Suppose power(base, exponent) exists and you often need squares. You could write a wrapper by hand, as in section 3.11. partial(function, arguments...) does it in one line, returning a new function with those arguments locked in.

partial locks in an argument
from functools import partial def power(base, exponent): return base ** exponent square = partial(power, exponent=2) cube = partial(power, exponent=3) print(square(5), cube(5))
Output
25 125
reduce: fold many values into one

reduce(function, items) takes the first two items, combines them with the function, then combines that result with the third, and so on until one value remains. Adding is the easiest picture. Multiplying shows it is more general.

reduce combines items pairwise
from functools import reduce numbers = [2, 3, 4] total = reduce(lambda acc, x: acc + x, numbers) product = reduce(lambda acc, x: acc * x, numbers) print(total, product)
Output
9 24
What Python does, line by line
  • reduce starts with the first two items: acc = 2, x = 3. The lambda returns 5 (or 6 for the product).
  • That result becomes the new acc. The next item x = 4 is combined with it: 5 + 4 = 9 (or 6 x 4 = 24).
  • No items are left, so the last acc is the answer.
lru_cache: remember answers

Some functions are slow and get called with the same input repeatedly. Recursion makes this worse. The naive Fibonacci function (each number is the sum of the previous two) recomputes the same values over and over. A decorator is a line starting with @ just above a def, which wraps the function with extra behaviour. @lru_cache gives it a cache: a memory of answers it has already computed.

Counting calls with and without a cache
from functools import lru_cache calls = 0 def fib_slow(n): global calls calls += 1 return n if n < 2 else fib_slow(n - 1) + fib_slow(n - 2) fib_slow(20) print("without cache:", calls, "calls") @lru_cache(maxsize=None) def fib_fast(n): return n if n < 2 else fib_fast(n - 1) + fib_fast(n - 2) print(fib_fast(20)) print(fib_fast.cache_info())
Output
without cache: 21891 calls
6765
CacheInfo(hits=18, misses=21, maxsize=None, currsize=21)

The plain version makes 21,891 calls to answer fib_slow(20). The cached one computes each of the 21 distinct inputs once, and every repeat is a lookup: misses=21 means new computations and hits=18 means answers reused. For large inputs the difference is between milliseconds and years.

⚠️
Use with care: caching only makes sense for functions whose answer depends solely on their arguments. If a function reads a global or the clock, a cached answer may be stale.
What does partial(power, exponent=2) return?
A new function that takes the remaining argument (base) and calls power(base, exponent=2).
Why is fib_slow(20) so wasteful?
It solves the same smaller problems again and again: fib_slow(18) is computed inside both fib_slow(19) and fib_slow(20), and so on down. The cache remembers each result.
Try it. Change 20 to 30 in fib_fast and watch how the hits and misses grow. Then try fib_slow(30) if you are patient: it makes over 2 million calls.
Recap
  • partial(f, ...) builds a simpler function with some arguments already filled in.
  • reduce(f, items) folds a sequence into one value by combining pairs.
  • @lru_cache makes a function remember its answers, which is a big saving for repeated calls, especially recursion.
3.13 — Using Python's Standard Library: math, random, datetime, collections

You now know how to write functions, so it is time to use the ones already written. Python comes with a huge collection of ready-made code called the standard library, sometimes described as "batteries included". It is organised into modules: each module is a file of related functions and values. Nothing in a module is available until you ask for it with an import statement, because Python keeps its everyday vocabulary small on purpose.

Three ways to import
import, from-import and as
import math print(math.sqrt(16), math.pi) from math import sqrt, ceil print(sqrt(25), ceil(4.1)) import math as m print(m.floor(4.9))
Output
4.0 3.141592653589793
5.0 5
4

import math brings in the whole module, and you reach its contents with a dot: math.sqrt. This shows where each name comes from. from math import sqrt copies just that name into your program, so you write sqrt(25) with no prefix. import math as m gives the module a shorter nickname, and it is the origin of the famous import numpy as np. Avoid from math import *, which dumps every name in and can silently overwrite yours. The most common import mistakes are these two:

Using a module you did not importread-only
print(math.sqrt(16))
What Python says
Traceback (most recent call last):
  File "<exec>", line 1, in <module>
NameError: name 'math' is not defined. Did you forget to import 'math'
Asking a module for a name it does not haveread-only
from math import sqroot
What Python says
Traceback (most recent call last):
  File "<exec>", line 1, in <module>
ImportError: cannot import name 'sqroot' from 'math' (unknown location). Did you mean: 'sqrt'?

The first is a NameError: math is just an unknown word until you import it. The second tells you the module exists but has no such name, which is nearly always a typo.

random: chance you can repeat

The random module produces numbers that look unpredictable. A computer generates them with a formula that starts from a seed, a number that fixes the starting point. Give the same seed and you get the same sequence every time. This is exactly what you want when you must reproduce an experiment, so machine learning code sets seeds all the time.

random with and without a seed
import random random.seed(42) print([random.randint(1, 6) for _ in range(5)]) random.seed(42) print([random.randint(1, 6) for _ in range(5)]) random.seed(7) print(random.choice(["red", "green", "blue"])) cards = [1, 2, 3, 4, 5] random.shuffle(cards) print(cards)
Output
[6, 1, 1, 6, 3]
[6, 1, 1, 6, 3]
green
[5, 1, 3, 4, 2]

The first two lines are identical because the seed was reset to 42 in between. randint(1, 6) picks a whole number from 1 to 6, including both ends. choice picks one item from a list, and shuffle reorders a list in place. Without the seed lines, every run would differ.

datetime: dates without the arithmetic headaches

Days per month, leap years and weekdays are painful to compute by hand. The datetime module does it for you. A date holds a year, month and day. A timedelta is a length of time, and you can add or subtract it. We use fixed dates here so the answers never change; date.today() gives the real current date.

Dates and durations
from datetime import date, timedelta start = date(2024, 3, 15) print(start, "->", start.strftime("%A, %d %B %Y")) print("in 30 days:", start + timedelta(days=30)) end = date(2024, 12, 25) gap = end - start print("days until:", gap.days)
Output
2024-03-15 -> Friday, 15 March 2024
in 30 days: 2024-04-14

collections: better containers

The collections module adds specialised containers. Counter counts how often each item appears, which used to need a loop and an if. defaultdict is a dictionary that creates a missing entry for you, using the type you give it.

Counter and defaultdict
from collections import Counter, defaultdict words = "the cat and the hat and the bat".split() counts = Counter(words) print(counts.most_common(2)) print(counts["the"], counts["dog"]) groups = defaultdict(list) for w in words: groups[w[0]].append(w) print(dict(groups))
Output
[('the', 3), ('and', 2)]
3 0
{'t': ['the', 'the', 'the'], 'c': ['cat'], 'a': ['and', 'and'], 'h': ['hat'], 'b': ['bat']}
Why do machine-learning scripts often call random.seed(...) at the top?
So that random choices come out the same on every run. Then you can reproduce a result, share it, and tell whether a change to your code caused a difference.
What is the difference between import math and from math import sqrt?
The first lets you write math.sqrt(...) with the module name in front; the second lets you write sqrt(...) directly, but only for the names you listed.
Try it. Use date(2025, 1, 1).weekday() (Monday is 0) and Counter("mississippi").most_common(1), and explain each result to yourself.
Recap
  • import module gives access via module.name; from module import name gives the bare name; as renames.
  • The standard library is a big set of modules: math, random, datetime, collections and many more.
  • random.seed(n) makes random numbers repeatable, which matters for reproducible experiments.
  • A missing import causes NameError; a wrong name inside a real module causes ImportError.
3.14 — How import Finds Modules, Writing Your Own, and __main__

A module is nothing magical: it is a Python file. When you write import math, Python looks for something called math, runs that file once from top to bottom, and hands you a module object whose contents you reach with a dot. Everything you learned about functions applies, because a module is mostly a collection of them.

How Python finds a module

Python does not search your whole disk. It checks, in order: whether it has already imported the module (a remembered list called sys.modules), then the folders in the list sys.path. That list starts with the folder of your own script, then the standard library, then installed packages such as NumPy. The first match wins. If nothing matches, you get an error:

A module that does not existread-only
import mathh
What Python says
Traceback (most recent call last):
  File "<exec>", line 1, in <module>
ModuleNotFoundError: No module named 'mathh'

Because your own folder is searched first, a file of yours named random.py would hide the real random module, and a file called math.py would break every import math. Do not name your files after standard modules.

Where import looks
 import shapes_tools
     1. already in sys.modules?   -> yes: reuse it (no re-run)
     2. your script's folder?     -> shapes_tools.py found: run it
     3. the standard library?     -> (checked if step 2 failed)
     4. installed packages?       -> numpy, pandas, sklearn...
     5. none of the above         -> ModuleNotFoundError
Your own folder comes first, which is why your own files can be imported, and also why they can accidentally hide a standard module.
Writing your own module

Any .py file is a module. The example below first writes a small file called shapes_tools.py into this page's private file space (reading and writing files is Chapter 5, so treat those three lines as setup), then imports it exactly as you would import math.

Create a module file and import it
import sys, importlib source = '''def area(width, height): return width * height print("shapes_tools loaded, its __name__ is", __name__) ''' with open("shapes_tools.py", "w") as f: f.write(source) importlib.invalidate_caches() sys.modules.pop("shapes_tools", None) import shapes_tools print(shapes_tools.area(3, 4)) import shapes_tools print("second import did nothing new")
Output
shapes_tools loaded, its __name__ is shapes_tools
12
second import did nothing new
What Python does, line by line
  • The with open(...) lines create the file shapes_tools.py in the current folder, which is on sys.path. The next two lines clear Python's memory of any earlier import, so you can re-run the block.
  • import shapes_tools finds that file, runs it once from top to bottom, and creates the module object. The def runs (creating area) and the print runs, so you see the loading message, with __name__ set to the module's own name.
  • shapes_tools.area(3, 4) calls the function through the dot, giving 12.
  • The second import finds shapes_tools in sys.modules and reuses it. The file is not run again, so there is no second loading message.
The __name__ guard

Notice the strange value printed above: the module's __name__ was the string "shapes_tools". Python sets a special variable __name__ in every file. When the file is imported, __name__ is the module's name. When the file is run directly as the main program, __name__ is the string "__main__". That difference lets one file be both a reusable module and a runnable script, by guarding the script part:

The __main__ guard
import runpy, sys, importlib source = '''def area(width, height): return width * height def main(): print("area of 3 x 4 =", area(3, 4)) print("file loaded, __name__ =", __name__) if __name__ == "__main__": main() ''' with open("shapes_guarded.py", "w") as f: f.write(source) importlib.invalidate_caches() sys.modules.pop("shapes_guarded", None) print("--- imported as a module ---") import shapes_guarded print("--- run as a script ---") runpy.run_path("shapes_guarded.py", run_name="__main__")
Output
--- imported as a module ---
file loaded, __name__ = shapes_guarded
--- run as a script ---
file loaded, __name__ = __main__
area of 3 x 4 = 12

When imported, the guard is False, so main() is skipped, and other programs can use area without triggering a demo. When run as a script, the guard is True and main() runs. Without the guard, importing the file would print and run everything every time, which is rarely what the importer wants. In your own projects you will write this guard at the bottom of nearly every script. A real project grows by placing several module files in a folder with an __init__.py file, called a package, which lets you write imports such as from myproject import data. This in-browser console cannot show a multi-file folder, but the rules are the same.

What is __name__ inside a file that is run directly, and what is it when the file is imported?
"__main__" when run directly. The module's own name (for example "shapes_tools") when imported.
Why might a file you name random.py cause strange errors?
Python searches your own folder first, so import random would load your file instead of the standard module, and the real functions such as randint would be missing.
Try it. Change the guarded module so that main() also prints area(5, 6). Then re-run and notice that the import still prints only the loading line.
Recap
  • A module is a .py file; import finds it via sys.modules and sys.path, runs it once and gives you a module object.
  • Your own folder is searched first: never name your files after standard modules.
  • __name__ is "__main__" when a file runs directly and the module name when imported, so if __name__ == "__main__": guards script-only code.
  • A folder of modules with an __init__.py is a package.
Chapter 3 Summary and What You Can Now Do
  • Why functions: copy-pasted logic is hard to fix and hides intent. A function is a named block you write once (DRY) and call many times.
  • Define versus call: def name(params): writes the function and runs nothing; name(args) runs it. Without parentheses you only name it.
  • Parameters and arguments: parameters are in the definition, arguments in the call. Match by position or by keyword (name=value), positional first.
  • The call stack: every call gets a private frame, and only the top frame runs. A traceback is the stack, read bottom-up.
  • return versus print: return hands a value back; print only displays. No return means None. return a, b gives a tuple you can unpack.
  • Defaults and star-arguments: x=4 makes a parameter optional. Never use a list as a default; use None. *args collects a tuple, **kwargs a dictionary.
  • Scope (LEGB): names are local to the function; lookup goes Local, Enclosing, Global, Built-in. Prefer return over global.
  • Recursion: a function that calls itself needs a base case, and each call gets its own frame.
  • lambda: a one-expression, nameless function, mostly used as key= for sorted, max and min.
  • Docstrings and type hints: document what a function does and what it takes and returns. Hints are not enforced.
  • Closures and nonlocal: a returned inner function remembers the outer variables; nonlocal lets it change them.
  • functools: partial pre-fills arguments, reduce folds items into one value, @lru_cache remembers answers.
  • The standard library: import math, from math import sqrt, import x as y; random.seed for repeatable randomness, plus datetime and collections.
  • Modules: a module is a .py file found through sys.modules and sys.path. Use if __name__ == "__main__": so a file is both importable and runnable.

What you can now do. You can turn any repeated block of code into a function with clear inputs and a returned result. You can read a traceback to see who called whom, and predict where a variable is visible. You can use a large part of the standard library, write your own module, and explain the machinery behind every import numpy as np you will meet in later chapters.
