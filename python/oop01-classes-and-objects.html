Classes & Objects

So far you have used the data types Python gave you: numbers, strings, lists, dictionaries. In this chapter you learn to invent your own. A class lets you bundle the facts about a thing (a pet, a bank account, a book) together with the actions it can perform, so one program can keep hundreds of them without getting tangled. We go slowly, one idea at a time, and every idea starts with the problem it solves.

1.1 — Why Classes Exist: The Problem With Loose Data

Imagine you volunteer at a small dog shelter and you want to write a Python program that keeps track of the dogs. Every dog has a name, an age and a breed. You already know how to store things: variables, lists and dictionaries. So let us try, using only what you learned in Chapters 1 to 4, and let us pay close attention to where it hurts. Feeling the pain first is the best way to understand why the new tool exists.

Our first attempt uses parallel lists. That means one list for each fact, where position 0 in every list belongs to the first dog, position 1 to the second dog, and so on. The lists only "know" they belong together because you remember it.

Attempt 1: three parallel lists
names = ["Rex", "Milo", "Luna"] ages = [3, 5, 2] breeds = ["Beagle", "Pug", "Husky"] for i in range(len(names)): print(names[i], "is", ages[i], "years old and is a", breeds[i])

This works. Now watch what happens when the shelter wants the dogs in alphabetical order. You sort the names, because that is the list you are looking at. Nothing tells Python that the other two lists must follow along.

Attempt 1: sorting breaks the link
names = ["Rex", "Milo", "Luna"] ages = [3, 5, 2] breeds = ["Beagle", "Pug", "Husky"] names.sort() # names is now ['Luna', 'Milo', 'Rex'] for i in range(len(names)): print(names[i], "is", ages[i], "years old and is a", breeds[i])
The lists after names.sort(): each column no longer describes one dog
BEFORE names.sort()
  position   0       1       2
  names      Rex     Milo    Luna
  ages       3       5       2
  breeds     Beagle  Pug     Husky

AFTER names.sort()
  position   0       1       2
  names      Luna    Milo    Rex
  ages       3       5       2
  breeds     Beagle  Pug     Husky

Column 0 now says: Luna, 3, Beagle   (wrong!)

Read the output carefully. Luna is now described as a three-year-old Beagle, but Luna is really a two-year-old Husky. Python did exactly what you asked, and the program silently lies. Nobody sees an error message, so nobody notices. This is the worst kind of bug.

The obvious fix is to keep everything about one dog together in a dictionary, which you met in Chapter 4. One dictionary per dog, and a list of those dictionaries. This is much better, and it is how a lot of real code works. But it still has three weak spots.

Attempt 2: one dictionary per dog
dog1 = {"name": "Rex", "age": 3, "breed": "Beagle"} dog2 = {"name": "Milo", "age": 5, "breed": "Pug"} dog3 = {"nmae": "Luna", "age": 2, "breed": "Husky"} # typo in the key! def describe(pet): return pet["name"] + " is " + str(pet["age"]) + " years old" print(describe(dog1)) print(describe(dog2)) try: print(describe(dog3)) except KeyError as error: print("KeyError:", error)
💡
A first look at try / exceptSome examples in this chapter wrap a risky line in try: and except SomeError as error:. Read it as "attempt this line. If Python complains with that kind of error, do not crash: print the error's message instead." That lets one page show you the real error message and then carry on. You do not need to write these yourself yet, because Chapter 5 teaches them properly. Your job is just to read the message it prints.

Weak spot one: nothing enforces the shape. Every dictionary is free to have different keys. One typo ("nmae") creates a dog with no name, and the mistake only shows up later, far from where you made it, as a KeyError. Weak spot two: the data and the actions are strangers. The function describe lives in a separate place from the dictionaries it works on. Python has no idea that describe is meant for dogs only. Weak spot three: names collide. In a bigger program you will also want to describe bank accounts and books. Each needs its own describe, but a function name can only mean one thing at a time.

Attempt 2: the function does not know what it is for
def describe(pet): return pet["name"] + " is " + str(pet["age"]) + " years old" def describe(account): # a second describe, for bank accounts return "Account owner: " + account["owner"] dog = {"name": "Rex", "age": 3} try: print(describe(dog)) except KeyError as error: print("KeyError:", error)

The second def describe quietly replaced the first one, so asking it to describe a dog now fails. You could invent awkward names like describe_dog and describe_account, but the real problem remains: the thing and the things you can do with it are not stored together.

💡
What we actually wantA way to say "here is a kind of thing called a Dog. Every Dog has a name, an age and a breed, and every Dog knows how to describe itself." Once that is written down in one place, Python can create as many dogs as we like, and every one of them has the right shape and the right abilities built in.

That wish has a name: a class. A class is a description of a kind of thing, written once. An object is one actual thing made from that description. The rest of this chapter teaches you, step by step, how to write classes and how to use the objects they create. Just to show you where we are heading, here is a tiny class. Do not worry about understanding every line yet. We take each word apart slowly in sections 1.2 to 1.5, and by the end you will be writing classes like this without effort.

A small taste of what is coming
class Dog: def __init__(self, name, age): self.name = name self.age = age def describe(self): return f"{self.name} is {self.age} years old" rex = Dog("Rex", 3) luna = Dog("Luna", 2) print(rex.describe()) print(luna.describe())

Notice what changed. There is no way to make a dog without a name and an age, because the class demands them. The describe action belongs to dogs and travels with them. And rex and luna are two separate dogs that cannot get mixed up, because each one carries its own facts. Writing programs this way is called object-oriented programming, or OOP for short. It is not magic and it is not a new language. It is a way of organising the variables and functions you already know, so that a program with hundreds of moving parts stays understandable.

✏️ Try it: In the parallel-lists example, sort ages instead of names and predict what the output will look like before you run it. Then change one dictionary key in the dictionaries example and see where the error appears.
🧠 Check yourself
In the parallel lists example, why did sorting names produce wrong output without any error message?
Python treats the three lists as unrelated. Sorting one of them moves its items but leaves the other two untouched, so positions no longer line up. Nothing in the code says that the lists belong together, so Python has nothing to complain about.
Name one thing a class gives you that a plain dictionary does not.
Any one of: a guaranteed shape (every object gets the same facts when it is created), actions stored together with the data, or a clear name for the kind of thing. All three were the weak spots of dictionaries.
📌 Recap
  • Parallel lists rely on you remembering which positions belong together, and sorting or deleting one list silently breaks the link.
  • Dictionaries keep one thing's facts together, but they do not enforce which keys exist and do not carry actions with them.
  • A class describes a kind of thing once; an object is one actual thing made from it.
  • OOP means organising a program around such objects: data and actions kept together.
1.2 — The Blueprint Idea: Classes and Objects

Before you write any code, we need one picture in your head. Think about how a house is built. An architect draws a blueprint: a plan that says "this house has three bedrooms, one kitchen and a red door". The blueprint is not a house. You cannot sleep in a blueprint, and you cannot paint a blueprint's walls. But once you own a blueprint you can build a house from it, and then another, and another. Every house follows the same plan, yet each one is a separate building. If the owner of the second house repaints the door blue, the first house keeps its red door.

Python works the same way. A class is the blueprint: a description of a kind of thing. An object is a house built from the blueprint: one actual thing that lives in your program's memory. Another word for an object made from a class is an instance. When someone says "rex is an instance of Dog", they mean "rex is one actual dog built from the Dog blueprint". You can also picture a cookie cutter. The cutter is the class. Each cookie is an object. One cutter, as many cookies as you like, and biting the ear off one cookie does not change the others.

One blueprint, many separate objects
        +------------------+
        |  class Dog        |    the blueprint,
        |  "what a Dog is" |    written ONCE
        +---------+--------+
                  |
        Dog() builds three objects
       +----------+----------+
       |          |          |
       v          v          v
   +--------+ +--------+ +--------+
   |  rex   | |  milo  | |  luna  |
   +--------+ +--------+ +--------+
   three real objects, separate from each other

Now the smallest possible class. The word class starts the definition. Then comes the name. By strong convention class names start with a capital letter (Dog, BankAccount), which is how you can tell a class from an ordinary variable at a glance. After the colon comes an indented block, exactly like a function body or an if block. Our class has nothing to say yet, so we write the keyword pass, which means "do nothing here, I am not finished".

The smallest class
class Dog: pass rex = Dog() milo = Dog() print(type(rex)) print(isinstance(rex, Dog)) print(rex is milo)

Three new things appeared. Writing Dog(), with round brackets, calls the class like a function, and the result is a brand-new object. type(rex) asks "what kind of thing is this?" and Python answers with the class name. isinstance(rex, Dog) asks a yes-or-no question: "was rex built from Dog?" And rex is milo asks whether the two names point at the very same object. The answer is False, because calling Dog() twice built two separate objects.

What Python does, line by line

  • Python reads class Dog: and its block. It creates the class object Dog, the blueprint, and stores it under the name Dog. At this moment no dog exists yet. There is only a plan for dogs.
  • Python runs rex = Dog(). The brackets tell it to build a new object from the blueprint. It sets aside a fresh spot in memory for one empty dog.
  • The name rex is attached to that object. Think of a name as a sticky label. The label is not the dog, it just points at it.
  • Python runs milo = Dog() and builds a second, different object. The label milo goes on this one. The two objects share a blueprint but nothing else.

There is a small surprise hiding here. You have been using classes since Chapter 1 without knowing it. Numbers, strings, lists and dictionaries are all classes that Python ships with, and the values you create are objects built from them.

You have used classes all along
print(type(5)) print(type("hello")) print(type([1, 2, 3])) names = list() # calling the class list builds an empty list print(names, type(names)) print("hello".upper()) # a method of the str class, used on one str object print(isinstance(5, int), isinstance("hi", int))

So list is a class, [1, 2, 3] is an object made from it, and .append and .upper are actions that come with those classes. What is new in this chapter is that you write the blueprint. You decide what a Dog, a BankAccount or a Playlist is.

There are two mistakes nearly every beginner makes in the first hour. The first is forgetting the round brackets. The name Dog on its own is the blueprint. Dog() is a dog. If you write rex = Dog you have not built anything, you have just given a second label to the blueprint.

Mistake 1: forgetting the brackets
class Dog: pass rex = Dog # no brackets: this is the blueprint, not a dog print(rex) print(type(rex)) print(isinstance(rex, Dog)) real_rex = Dog() # brackets: this is a dog print(type(real_rex)) print(isinstance(real_rex, Dog))

The tell-tale sign is the output <class '__main__.Dog'> and the type <class 'type'>. Python is saying "this is a class", not a dog. The second mistake is a typing slip in the class line itself. Python will refuse to read the file at all and reports a SyntaxError (a sentence Python cannot understand) or an IndentationError (the block is missing or badly lined up). We can show the exact messages safely by asking Python to compile the broken text and catch the complaint.

Mistake 2: the two most common typing slips
try: compile("class Dog\n pass", "<demo>", "exec") except SyntaxError as error: print("SyntaxError:", error.msg) try: compile("class Dog:\nrex = 1", "<demo>", "exec") except SyntaxError as error: print(type(error).__name__ + ":", error.msg)

The first message says expected ':': you forgot the colon after Dog. The second says expected an indented block after class definition on line 1: a class needs at least one indented line, and pass is the perfect placeholder when you have nothing else to write yet. When you see an error like this in real code, Python also prints the line number and draws a caret under the spot it was reading. Start your search at that line, and look one line above it too.

✅
Naming habitClass names use CapitalizedWords (Dog, LibraryBook). Variable names for objects use lowercase (rex, my_book). Python does not force this, but every Python programmer expects it, and it lets you tell blueprints from things at a glance.

What is the difference between Dog and Dog()?

📌 Recap
  • A class is a blueprint written once; an object (or instance) is one actual thing built from it.
  • class Dog: followed by an indented block defines a class; pass is a placeholder for an empty block.
  • Dog() builds a new object each time it is called; type(x) and isinstance(x, Dog) tell you what an object is.
  • int, str, list and dict are classes too, so you have been using objects since Chapter 1.
1.3 — Attributes: Facts That Belong to an Object

Right now our dogs are empty shells. rex = Dog() builds a dog, but the dog has no name, no age and no breed. We need somewhere to store facts about each dog. Python's answer is the attribute: a variable that belongs to one object instead of floating around loose in your program. You reach it with a dot: rex.name means "the name that belongs to rex". Read the dot as "'s". So rex.name reads as "rex's name".

A good picture is a labelled folder. Each object is its own folder. Inside are tabs with labels (name, age) and each tab holds one value. Your loose variables such as total or count are papers lying on the desk. Attributes are papers filed inside a specific folder, and two folders can each have a tab called name holding different values without any confusion.

To create an attribute you simply assign to it. There is no separate "declare" step. The first assignment brings the attribute into existence, and later assignments change its value.

Setting and reading attributes
class Dog: pass rex = Dog() rex.name = "Rex" rex.age = 3 milo = Dog() milo.name = "Milo" milo.age = 5 print(rex.name, "is", rex.age) print(milo.name, "is", milo.age)

Each object keeps its own values. Changing one dog does not touch the other, exactly like repainting one house does not repaint its neighbour.

Attributes are separate for each object
class Dog: pass rex = Dog() rex.age = 3 milo = Dog() milo.age = 5 rex.age = rex.age + 1 # Rex has a birthday milo.age += 2 # += works on attributes too print("rex:", rex.age) print("milo:", milo.age)
Two objects, each with its own attributes
rex  --->  +-------------------+
           | name : "Rex"      |
           | age  : 4          |
           +-------------------+

milo --->  +-------------------+
           | name : "Milo"     |
           | age  : 7          |
           +-------------------+

label      an object with its own attributes

How does Python remember all this? Every object carries a hidden dictionary that maps attribute names to values. You can look at it with the built-in function vars(). This should feel familiar from Chapter 4, because rex.name is a friendlier way of writing something much like rex_dict["name"].

Peeking inside an object with vars()
class Dog: pass rex = Dog() print(vars(rex)) # nothing stored yet rex.name = "Rex" print(vars(rex)) rex.age = 3 print(vars(rex)) print(vars(rex)["name"], rex.name)

What Python does when it sees rex.name = "Rex"

  • It follows the label rex to find the object.
  • It looks in that object's hidden dictionary (the one vars(rex) shows) for a key called "name".
  • It does not find one, so it adds the entry "name": "Rex". If the key had existed, the value would simply be replaced.
  • Later, print(rex.name) performs the same lookup in the other direction: find the object, look up "name", hand back the value.

Because there is no declaration step, Python does not stop you from giving different objects different attributes. That flexibility is the source of the first common mistake. If you ask for an attribute that was never set, Python raises an AttributeError.

Mistake: asking for an attribute that does not exist
class Dog: pass rex = Dog() rex.name = "Rex" rex.age = 3 luna = Dog() luna.name = "Luna" # we forgot to set luna.age print(luna.name) try: print(luna.age) except AttributeError as error: print("AttributeError:", error) print(hasattr(luna, "age"), hasattr(rex, "age")) print(getattr(luna, "age", "unknown"))

Without the try, a tiny program that reads the missing attribute stops with a short traceback. Read it from the bottom up: the last line names the problem, and the line 6 above it points at the code that caused it. (The console on this page shows only the final line of an error to keep things short. In a saved file on your own computer you see the whole traceback, as below.)

What an unhandled AttributeError looks like
class Dog: pass luna = Dog() luna.name = "Luna" print(luna.age) Traceback (most recent call last): File "demo.py", line 6, in <module> print(luna.age) ^^^^^^^^ AttributeError: 'Dog' object has no attribute 'age'

The message is precise. 'Dog' object tells you the kind of thing you asked, and no attribute 'age' tells you what was missing. Two tools help here: hasattr(obj, "age") answers True or False, and getattr(obj, "age", "unknown") returns a fallback value instead of failing.

The second mistake is quieter. A typo in an attribute name does not raise any error when you assign, because assignment is allowed to create new attributes. Python cannot tell "a new attribute" from "a misspelt one".

Mistake: a typo silently creates a new attribute
class Dog: pass rex = Dog() rex.name = "Rex" rex.age = 3 rex.agee = 4 # oops: meant rex.age print(rex.age) # still 3 print(vars(rex)) # the typo is visible here

Now put the two problems together and you can see why doing this by hand is fragile. Every dog needs the same three assignment lines. If you forget one, or misspell one, functions that expect a full dog fail later, far from the mistake. It is exactly the "nothing enforces the shape" weakness we met with dictionaries in section 1.1.

Why setting attributes by hand is fragile
class Dog: pass def describe(dog): return dog.name + " is " + str(dog.age) rex = Dog() rex.name = "Rex" rex.age = 3 print(describe(rex)) luna = Dog() luna.name = "Luna" # forgot age try: print(describe(luna)) except AttributeError as error: print("AttributeError:", error)

What we want is a way to make the class itself insist "every Dog must be given a name and an age at the moment it is built". That is the job of the special method __init__, and it is the subject of the next section.

✏️ Try it: In the first example, add a breed attribute to rex only, then print vars(rex) and vars(milo) side by side. Notice that the two dogs now have different attributes and Python is perfectly happy.
🧠 Check yourself
If rex.age is 3 and you run rex.age = 4, does milo.age change?
No. Each object has its own attributes, so the assignment changes only what is stored inside rex.
You wrote rex.nmae = "Rex" by accident. Does Python raise an error on that line? What happens later when you read rex.name?
No error on the assignment: assigning creates a new attribute called nmae. Later, rex.name raises AttributeError: 'Dog' object has no attribute 'name', because name was never set.
📌 Recap
  • An attribute is a variable stored inside one object and reached with a dot: rex.name.
  • Assigning to obj.attr creates the attribute if it is new, or replaces its value if it exists.
  • vars(obj) shows an object's attributes as a dictionary; each object has its own.
  • A missing attribute raises AttributeError: 'Dog' object has no attribute 'age'; a misspelt assignment creates a stray attribute silently.
  • Setting attributes by hand after creation is repetitive and easy to get wrong, which is why we need __init__.
1.4 — __init__ and self, Very Slowly

This is the section that trips up more beginners than any other, so we will go slowly and look at it from several sides. Take your time. If something feels strange on the first pass, that is normal, and by the end of the section you will have seen every piece working.

Start from the pain in section 1.3. To build one proper dog you had to write Dog() and then three separate assignments, and forgetting any one of them left a broken dog. What we want is to write Dog("Rex", 3) and get back a dog that is complete from the very first moment. The tool for that is a special function called __init__. It is short for "initialise", which means "get something ready to use". Python calls it automatically, right after it builds a new empty object, so it is the perfect place to fill in the object's starting facts.

Now the part that confuses people: the word self. Imagine a form that a shelter fills in for every new dog. The form has blanks for name and age. The form itself is the same for every dog, but the person filling it in needs to know which dog they are writing about right now. self is that "which dog". It is the object that is being set up, handed to __init__ so the function knows where to store the facts. Here is another way to think of it. When Rex says "my name is Rex" and Milo says "my name is Milo", both dogs use the same word, "my", and it points at whoever is speaking. Inside a class, self plays the role of "my", or "this very object".

Your first __init__
class Dog: def __init__(self, name, age): self.name = name self.age = age rex = Dog("Rex", 3) milo = Dog("Milo", 5) print(rex.name, rex.age) print(milo.name, milo.age)

Compare this with the version in section 1.3. There are no loose assignments after creation, and the dogs are complete at birth. In self.name = name the left side is an attribute stored on the object, and the right side is the parameter that arrived when you called Dog(...). They happen to share a spelling, but they are two different things. This is the most common source of confusion, so hold on to it.

Instead of just trusting me, let us catch self in the act. In the next example, __init__ saves self into a list. Afterwards we compare the saved item with the dog we got back. If self really is the new object, they must be the very same thing.

Proof: self IS the new object
created = [] class Dog: def __init__(self, name): print("__init__ is running for", name) created.append(self) # save the object that self points at self.name = name rex = Dog("Rex") print("Dog() call finished") print(created[0] is rex) print(type(created[0]).__name__)

Notice the order of the printed lines: the message from inside __init__ appears before "Dog() call finished". You never called __init__ yourself. Python called it for you, in the middle of Dog("Rex"). And created[0] is rex is True, so self and rex are two names for one object. We can also watch the object fill up.

Watching the object fill up
class Dog: def __init__(self, name, age): print("at the start:", vars(self)) self.name = name print("after name: ", vars(self)) self.age = age print("at the end: ", vars(self)) rex = Dog("Rex", 3) print("rex has:", vars(rex))

What Python does, line by line, for rex = Dog("Rex", 3)

  • Python sees that you are calling a class (Dog followed by brackets), with two arguments: "Rex" and 3.
  • It builds a new, empty object of type Dog. It has no attributes yet, which is why vars(self) printed {}.
  • It looks up __init__ in the class and calls it, passing the new object as the first argument. The remaining arguments follow: self is the new object, name is "Rex", age is 3.
  • The body runs. self.name = name stores "Rex" inside the new object, and self.age = age stores 3.
  • __init__ finishes. It does not return anything, and it should not try to. Python hands the finished object back to you, and the label rex is attached to it.
How the call matches the definition, piece by piece
rex = Dog( "Rex", 3 )       what you write

__init__( self , name  , age )   what Python runs
            |      |       |
            |     "Rex"    3
            |
    the new, empty object
    (Python passes it in for you)

This picture explains the biggest puzzle: **why does self appear in the definition but not in the call?** Because you never pass it. Python passes it for you. The definition lists three parameters (self, name, age), but the call supplies only two, and Python quietly provides the first. Once you know this, the error messages you will meet stop being mysterious. Watch how the counting works in these three typical slips.

Mistake 1: passing the wrong number of arguments
class Dog: def __init__(self, name, age): self.name = name self.age = age try: Dog("Rex") # one argument is missing except TypeError as error: print("TypeError:", error) try: Dog("Rex", 3, "Beagle") # one argument too many except TypeError as error: print("TypeError:", error)

The first message is Dog.__init__() missing 1 required positional argument: 'age'. It is telling you exactly which piece you forgot to supply. The second is Dog.__init__() takes 3 positional arguments but 4 were given. This one looks off by one: you gave three arguments but Python says four. That is because it counts self, which it filled in for you. Whenever a message about __init__ or a method seems to be off by one, remember that self is being counted.

Mistake 2: forgetting self in the definition
class Dog: def __init__(name, age): # self is missing! name = name age = age try: Dog("Rex", 3) except TypeError as error: print("TypeError:", error)

Here the definition has only two parameters but Python still passes three things (the new object plus your two arguments). The message Dog.__init__() takes 2 positional arguments but 3 were given is the signature of a forgotten self. The fix is to put self first, every time.

Mistake 3: forgetting "self." when storing
class Dog: def __init__(self, name, age): name = name # a plain local variable; it vanishes when __init__ ends self.age = age rex = Dog("Rex", 3) print(vars(rex)) try: print(rex.name) except AttributeError as error: print("AttributeError:", error)

Without self. in front, name = name creates a normal local variable that disappears the moment __init__ finishes. The object never receives it. This bug is sneaky because __init__ runs without any complaint. The clue appears later, as an AttributeError. Whenever an attribute is "missing" from an object you know you created properly, check that you wrote self. in front of it inside __init__.

One more trap concerns the name of the method itself. It needs two underscores on each side. If you type only one, Python does not treat it as special, and your class ends up with no initialiser at all.

Mistake 4: _init_ is not __init__
class Dog: def _init_(self, name): # only one underscore each side self.name = name try: Dog("Rex") except TypeError as error: print("TypeError:", error)

Dog() takes no arguments is the message to remember. It means "this class has no __init__, so it does not know what to do with the arguments you gave it". Finally, an initialiser can also set up attributes that are not passed in at all, and parameters can have default values just as in ordinary functions from Chapter 3.

Defaults and starting values
class Dog: def __init__(self, name, age=1): self.name = name self.age = age self.tricks = [] # every new dog starts with an empty list self.is_hungry = True puppy = Dog("Pip") # age is left out, so 1 is used adult = Dog("Rex", 4) print(vars(puppy)) print(vars(adult))

The word self is only a convention. Python would accept def __init__(this, name). But every Python programmer writes self, and so should you, because it makes your code instantly readable to everyone else.

  • self is the object being set up. Python passes it in for you, so it appears in the def but never in the call.

1.5 — Methods: Actions That Belong to an Object

So far our dogs carry facts, but they cannot do anything. Back in section 1.1 we wrote describe(pet) as a loose function far away from the data it used, and Python had no idea the two belonged together. A method fixes that. A method is simply a function that is written inside a class, so it belongs to the objects built from that class. You call it with a dot, just like you reach an attribute: rex.bark() means "Rex, do your bark action".

Think of a remote control. The remote and the television are separate boxes, but each remote is paired with one television: press "volume up" on your remote and only your television gets louder. A method is like that button. The function bark lives in the class, but when you write rex.bark() Python pairs it with rex, so the action happens to Rex and not to some other dog.

Here is the smallest example. The only difference from an ordinary function is that it sits inside the class and its first parameter is self. It is exactly the same self you met in __init__: the object the method was called on.

Your first method
class Dog: def __init__(self, name, age): self.name = name self.age = age def bark(self): print(f"{self.name} says Woof!") rex = Dog("Rex", 3) milo = Dog("Milo", 5) rex.bark() milo.bark()

The same method produced two different messages. That works because self is different each time: inside the first call it is Rex, inside the second it is Milo. Now for the claim that makes methods far less mysterious: rex.bark() is just a shorter way of writing Dog.bark(rex). You take the function from the class and hand it the dog explicitly.

rex.bark() is Dog.bark(rex)
class Dog: def __init__(self, name): self.name = name def bark(self): print(f"{self.name} says Woof!") rex = Dog("Rex") rex.bark() # the short way Dog.bark(rex) # the long way: same function, dog passed by hand print(type(Dog.bark).__name__) # a plain function stored in the class print(type(rex.bark).__name__) # the same function, paired with rex print(rex.bark.__self__ is rex) # the pairing remembers its dog

Those last three lines show what the dot really does. Dog.bark is an ordinary function that lives in the class. rex.bark is what Python builds when you use the dot on an object: a bound method, meaning "this function, already tied to rex". When you add the brackets and call it, Python passes rex in as self for you. That is why you never write self in the call and why the definition needs it.

What Python does, line by line, for rex.bark()

  • Python follows the label rex to the object and looks for something called bark among the object's own attributes (the ones vars(rex) shows). It finds nothing there.
  • It then looks in the object's class, Dog, and finds the function bark. Methods are stored once in the class, not copied into every object.
  • Because you used the dot on an object, Python ties the function to rex, creating the bound method.
  • The brackets call it. Python passes the object as the first argument, so the call really is Dog.bark(rex) and self is rex.
  • The body runs. self.name reads the name stored inside rex, and the message is printed.
A method call is a function call with the object slipped in first
what you write:     rex.add_trick("sit")
                            |
                Python rewrites it as
                            v
what really runs:   Dog.add_trick(rex, "sit")

def add_trick( self , trick ):
      self = rex ,  trick = "sit"

Methods can do three kinds of jobs, and it helps to name them. Some read the object's state and give something back. Some change the state. Some take extra arguments beyond self. Here is one of each on our dog.

Methods that read, change, and take arguments
class Dog: def __init__(self, name, age): self.name = name self.age = age self.tricks = [] def describe(self): # reads state, returns a string return f"{self.name} is {self.age} and knows {len(self.tricks)} tricks" def birthday(self): # changes state self.age += 1 def add_trick(self, trick): # changes state, uses an argument self.tricks.append(trick) rex = Dog("Rex", 3) print(rex.describe()) rex.birthday() rex.add_trick("sit") rex.add_trick("roll over") print(rex.describe()) print(vars(rex))

Notice that vars(rex) shows only the attributes (name, age, tricks). The methods are not in there, because they live once in the class. Methods can also call each other, using self to reach a sibling method, exactly like they use self to reach an attribute.

Methods calling other methods through self
class Dog: def __init__(self, name): self.name = name self.tricks = [] def add_trick(self, trick): self.tricks.append(trick) def show_off(self): for trick in self.tricks: print(f"{self.name} does: {trick}") self.celebrate() # calling another method def celebrate(self): print(f"Good dog, {self.name}!") rex = Dog("Rex") rex.add_trick("sit") rex.add_trick("shake") rex.show_off()

The difference between printing and returning is a classic beginner stumbling block, and it works the same as with ordinary functions from Chapter 3. A method that only prints hands back None. If you try to use that result as text, Python complains.

Mistake: printing is not returning
class Dog: def __init__(self, name): self.name = name def bark(self): print("Woof!") # prints, returns nothing def speak(self): return "Woof!" # returns a value we can reuse rex = Dog("Rex") result = rex.bark() print("bark() returned:", result) print(rex.name + " says " + rex.speak()) try: print(rex.name + " says " + rex.bark()) except TypeError as error: print("TypeError:", error)

Look closely at the output. The second Woof! was printed by the method while Python was still working out the sentence, and only then did the + fail because the method handed back None instead of text. When the goal is to use the answer somewhere else (store it, add it to a sentence, test it), return it. When the goal is only to show something to a person, print it. Most methods in real programs return values or change state, and leave printing to the outer program.

Three more mistakes come up constantly with methods. All are easy to fix once you can read the message.

Mistake: forgetting the brackets (no error!)
class Dog: def __init__(self, age): self.age = age def birthday(self): self.age += 1 rex = Dog(3) rex.birthday # no brackets: the method is looked at, not called print(rex.age) # still 3 rex.birthday() # brackets: now it runs print(rex.age)
Mistake: leaving self out of the method definition
class Dog: def __init__(self, name): self.name = name def bark(): # no self here print("Woof!") rex = Dog("Rex") try: rex.bark() except TypeError as error: print("TypeError:", error)

The message Dog.bark() takes 0 positional arguments but 1 was given is the same off-by-one family as before. You wrote no parameters, but Python passed one: the object. The third mistake happens inside the method body. If you use a bare name such as name, Python looks for an ordinary variable and not for the object's attribute.

Mistake: using an attribute without self
class Dog: def __init__(self, name): self.name = name def bark(self): print(name + " says Woof!") # should be self.name rex = Dog("Rex") try: rex.bark() except NameError as error: print("NameError:", error)

NameError: name 'name' is not defined reads as "I looked for a plain variable called name and found none". Inside a method, every fact about the object goes through self.: self.name, self.age, self.tricks. That one habit prevents most method bugs.

  • A method is a function defined inside a class; self is its first parameter and receives the object it was called on.
  • rex.bark() is the same as Dog.bark(rex); the dot creates a bound method tied to rex.
  • Methods can read state, change state, take extra arguments and call other methods through self.

1.6 — Instance Attributes vs Class Attributes

Until now every attribute lived inside one object and was set with self.something = .... That fits facts that belong to a single dog: its name, its age, its list of tricks. But some facts do not belong to one dog at all. Every dog in the shelter is the same species. The shelter also wants to know how many dogs have been registered in total. Writing self.species = "Canis familiaris" into every single dog would repeat the same fact hundreds of times, and changing it later would mean visiting every dog. We need a place for facts that belong to the kind of thing, not to any one thing.

That place is a class attribute: a variable written directly in the class body, outside any method. The ordinary attributes you set with self. are called instance attributes, because an instance is one object. The classroom analogy fits well. The rules poster on the wall belongs to the whole class and every student can read it. Each student's notebook belongs to that student alone.

A class attribute is shared by every object
class Dog: species = "Canis familiaris" # class attribute: written in the class body def __init__(self, name): self.name = name # instance attribute: one per dog rex = Dog("Rex") milo = Dog("Milo") print(rex.species) print(milo.species) print(Dog.species) # also reachable through the class itself

Both dogs can read species, yet neither one stores it. To see who really owns what, look at where Python keeps each attribute. Object attributes live in the object's own dictionary. Class attributes live in the class's dictionary.

Where each attribute really lives
class Dog: species = "Canis familiaris" def __init__(self, name): self.name = name rex = Dog("Rex") print("name" in vars(rex), "species" in vars(rex)) print("species" in vars(Dog)) print(rex.species) # found anyway

What Python does, line by line, for rex.species

  • Python follows the label rex to the object and looks in the object's own dictionary. There is no species there.
  • It does not give up. It looks in the object's class, Dog, and finds species there.
  • It returns that value. If the class did not have it either, you would get an AttributeError.
  • So the rule is: object first, then class. The first place that has the name wins.
Lookup order: the object first, then its class
rex.species
    |
    v
+--------------------+
| name : "Rex"       |   1) look in the object:
| (no species)       |      not there
+---------+----------+
          | not found: try the class
          v
+------------------------------+
| class Dog                    |
| species : "Canis familiaris" |
+------------------------------+
2) found: ONE copy, shared by every dog

Changing the class attribute changes what every object sees, because they all read the same single copy. But there is a subtle twist. If you assign through an object (rex.species = ...), Python does not modify the class. It creates a brand-new instance attribute on rex, which then hides the class attribute for that one dog only. Programmers call this shadowing.

Changing it through the class vs through an object
class Dog: species = "Canis familiaris" rex = Dog() milo = Dog() Dog.species = "Canis lupus familiaris" # changes the shared copy print(rex.species, "|", milo.species) rex.species = "wolf" # creates a NEW attribute on rex only print(rex.species, "|", milo.species) print(vars(rex)) del rex.species # del deletes rex's own species print(rex.species)

Class attributes are also handy for a shared counter. Here the shelter numbers the dogs as they arrive. We change the counter through the class name Dog.count, so every dog updates the one shared value.

A shared counter
class Dog: count = 0 # how many dogs exist def __init__(self, name): self.name = name Dog.count += 1 # update the shared number rex = Dog("Rex") milo = Dog("Milo") luna = Dog("Luna") print(Dog.count) print(rex.count) # every dog sees the same shared value

Now the first mistake. Suppose you write self.count += 1 instead of Dog.count += 1. It looks almost identical, but it does something quite different. Python first reads self.count (finding the class value 0), adds one, and then stores the answer on self, creating a new instance attribute. The shared counter never moves.

Mistake: self.count += 1 does not update the shared counter
class Dog: count = 0 def __init__(self, name): self.name = name self.count += 1 # creates an instance attribute! rex = Dog("Rex") milo = Dog("Milo") print("Dog.count:", Dog.count) print("rex.count:", rex.count) print(vars(rex))

The second mistake is the nastiest bug in this chapter, so read carefully. You saw in Chapter 4 that a list is mutable: you can change it in place, and every name pointing at that same list sees the change. Now imagine a dog's tricks list written as a class attribute. There is only one list, and every dog shares it.

Mistake: a mutable class attribute is shared by everyone
class Dog: tricks = [] # ONE list, shared by all dogs def __init__(self, name): self.name = name def add_trick(self, trick): self.tricks.append(trick) # changes the shared list in place rex = Dog("Rex") milo = Dog("Milo") rex.add_trick("sit") print("rex:", rex.tricks) print("milo:", milo.tricks) # Milo never learned anything! print(rex.tricks is milo.tricks)

Milo "knows" a trick he was never taught, because rex.tricks and milo.tricks are two labels on the same list. is confirms it. The fix is to create the list inside __init__, so every dog builds its own new list.

The fix: create the list inside __init__
class Dog: def __init__(self, name): self.name = name self.tricks = [] # a NEW list for each dog def add_trick(self, trick): self.tricks.append(trick) rex = Dog("Rex") milo = Dog("Milo") rex.add_trick("sit") print("rex:", rex.tricks) print("milo:", milo.tricks) print(rex.tricks is milo.tricks)
The shared-list bug and its fix
BUG: tricks written in the class body
  rex  --+
         +--> Dog.tricks --> ["sit"]
  milo --+    one list, two owners

FIX: tricks created in __init__
  rex  --> tricks --> ["sit"]
  milo --> tricks --> []
           two lists, one each

Here is a rule of thumb you can rely on. Ask: "Could two objects of this class sensibly hold different values for this?" If yes (name, age, tricks, balance) it is an instance attribute, set in __init__. If it is a constant or shared fact (a species, a maximum, a counter of all objects) it can be a class attribute. And when in doubt, or when the value is a list or dictionary, use self. in __init__.

No. Assigning through rex creates a new instance attribute on rex only, which shadows the class attribute for that one dog. milo.sound still finds the class value "Woof".
Why is tricks = [] in the class body a bug, but self.tricks = [] in __init__ correct?
The class-body version creates a single list that every object shares, so appending through one dog changes them all. self.tricks = [] runs once per object and builds a separate list each time.
📌 Recap
  • A class attribute is written in the class body and shared by all instances; an instance attribute is set with self. and belongs to one object.
  • Lookup goes object first, then class. Assigning through an object creates an instance attribute that shadows the class one.
  • Use ClassName.count += 1 (not self.count += 1) to change a shared value.
  • Never put a mutable value (list, dict) in the class body when each object needs its own; create it in __init__.
1.7 — Objects Are References: Two Names, One Object

Here is a small program that surprises almost everyone the first time. You make a dog, give it a second name, rename the dog through the second name, and then look at it through the first name. Try to predict the output before you run it.

A surprise: changing a dog through a second name
class Dog: def __init__(self, name, age): self.name = name self.age = age a = Dog("Rex", 3) b = a # "copy" the dog? b.name = "Max" b.age += 1 print(a.name, a.age) print(b.name, b.age) print(a is b)

Rex became Max even though we only touched b. If this reminds you of lists in Chapter 4, good: it is the very same idea. A variable does not contain an object. A variable is a label attached to an object that lives somewhere else in memory. Writing b = a does not build a second dog. It sticks a second label onto the same dog. Another way to see it: you are sharing a link to one online document, not emailing separate copies. Anyone who edits through the link changes the one document. The technical word for this is a reference: the name refers to the object.

b = a puts a second label on the same object
before:        a ---> +----------------+
                      | name : "Rex"   |
                      | age  : 3       |
                      +----------------+

after b = a:   a ---+
                    +--> (same object)
               b ---+

one object, two labels:  a is b  ->  True

What Python does, line by line, for b = a

  • Python evaluates the right side, a, and finds the object that label points at.
  • It does not copy that object. It attaches the new label b to the same object.
  • b.name = "Max" follows the label b, arrives at the one shared object, and changes its name.
  • a.name follows the label a, arrives at that same object, and reads the new value, "Max".

That leads to a question: how do you ask "are these the same object" versus "do these look alike"? Python has two different tools. The word is asks: "are these two labels on the very same object?" The operator == asks: "are these equal?" For objects you write yourself, == behaves like is unless you teach the class otherwise (that is a topic for the next chapter). Lists, on the other hand, already know how to compare their contents.

is asks "same object?", == asks "equal?"
class Dog: def __init__(self, name): self.name = name x = Dog("Rex") y = Dog("Rex") # a separate dog with identical data z = x # another label on x print(x is y, x == y) # two objects: not the same, not equal (by default) print(x is z, x == z) # one object list1 = [1, 2] list2 = [1, 2] print(list1 is list2, list1 == list2) # lists compare by contents

Python can show each object's identity number with id(), but the number changes from run to run and machine to machine, so we never print it in lessons. Comparing with is gives the same information reliably. Functions behave the same way. When you pass an object into a function, the function receives another label for the same object, so changing its attributes changes the original. Reassigning the parameter to something new, however, only moves the function's own label.

Passing an object to a function
class Dog: def __init__(self, name, age): self.name = name self.age = age def celebrate(dog): dog.age += 1 # changes the shared object def replace(dog): dog = Dog("Stranger", 9) # moves the LOCAL label only rex = Dog("Rex", 3) celebrate(rex) print(rex.name, rex.age) replace(rex) print(rex.name, rex.age) # unchanged: still Rex

Objects also live inside containers. A list of dogs holds references to dogs, not copies. Looping over the list gives you the real dogs, so changing them changes the ones in the list. A dictionary can hold dogs as values, which gives you a fast way to look one up by name.

Objects inside lists and dictionaries
class Dog: def __init__(self, name, age): self.name = name self.age = age shelter = [Dog("Rex", 3), Dog("Milo", 5), Dog("Luna", 2)] for dog in shelter: dog.age += 1 # each loop variable is a label on a real dog print([dog.age for dog in shelter]) by_name = {dog.name: dog for dog in shelter} by_name["Luna"].age = 10 print(shelter[2].age) # the same Luna, seen through the list

Now the classic trap, again from Chapter 4. Multiplying a list repeats the reference, not the object. If you write [Dog("Pup")] * 3, you do not get three puppies. You get one puppy listed three times.

Mistake: [Dog("Pup")] * 3 is one dog three times
class Dog: def __init__(self, name): self.name = name self.tricks = [] litter = [Dog("Pup")] * 3 litter[0].tricks.append("sit") print([d.tricks for d in litter]) print(litter[0] is litter[1]) # the fix: build a NEW dog for each slot litter = [Dog(f"Pup{i}") for i in range(3)] litter[0].tricks.append("sit") print([d.tricks for d in litter]) print(litter[0] is litter[1])

Sometimes you really do want a second, independent dog based on an existing one. There are three ways. The most explicit is to build a new object from the old one's values. The standard library module copy offers copy.copy (a shallow copy: a new object whose attributes point at the same inner values) and copy.deepcopy (a deep copy: a new object with its own copies of everything inside it as well). The difference matters as soon as an attribute is itself a list.

Copying an object: shallow vs deep
import copy class Dog: def __init__(self, name): self.name = name self.tricks = [] rex = Dog("Rex") rex.tricks.append("sit") shallow = copy.copy(rex) deep = copy.deepcopy(rex) print(shallow is rex, deep is rex) # both are new objects print(shallow.tricks is rex.tricks) # shallow shares the inner list print(deep.tricks is rex.tricks) # deep has its own list shallow.tricks.append("roll over") print(rex.tricks) # affected by the shallow copy print(deep.tricks) # not affected
Shallow copy shares inner lists; deep copy does not
shallow = copy.copy(rex)
  rex     -> [ tricks ]--+
                         +--> ["sit"]  shared!
  shallow -> [ tricks ]--+

deep = copy.deepcopy(rex)
  rex     -> [ tricks ] ----> ["sit"]
  deep    -> [ tricks ] ----> ["sit"]  own copy

One last reference-related error deserves a mention because you will meet it constantly. A function that searches for a dog often returns None when it finds nothing. None is not a dog. Asking it for .name fails with a message you can now read easily.

Mistake: the "object" is actually None
class Dog: def __init__(self, name): self.name = name def find_dog(dogs, wanted): for dog in dogs: if dog.name == wanted: return dog # falls off the end: returns None shelter = [Dog("Rex"), Dog("Milo")] found = find_dog(shelter, "Luna") print(found) try: print(found.name) except AttributeError as error: print("AttributeError:", error)

'NoneType' object has no attribute 'name' means "the thing you called .name on is None". The bug is not on that line. It is earlier, where the function returned nothing. Check for None before you use a result from a search: if found is not None:.

Why can [Dog("Pup")] * 3 cause trouble?

📌 Recap
  • A variable is a label pointing at an object; b = a adds a second label, it does not copy the object.
  • is asks "same object?"; == asks "equal?", and for your own classes == matches is until you teach it otherwise.
  • Functions and containers receive references, so changing an object's attributes through them changes the original.
  • Use copy.copy, copy.deepcopy or a fresh constructor call when you truly need an independent object.
1.8 — Designing a Class: From Idea to Working Code

You now know every mechanical piece: class, __init__, self, attributes and methods. The next hurdle is different. Faced with a blank file and a task, how do you decide what the class should contain? Beginners often freeze here, or they cram everything into one giant function. There is a simple, reliable method: describe the thing in plain English and mark the words.

Write one or two sentences about the thing. Underline the nouns. A noun that names the kind of thing becomes a class. A noun that names a fact about it becomes an attribute. Then underline the verbs: the things it can do become methods. Finally ask three questions. What must be supplied when it is created (those become __init__ parameters)? What should start at a default value (an empty list, a zero)? What should each method give back or change?

From a sentence to a class design
"A bank account has an owner and a balance.
 You can deposit, withdraw, and ask for a
 summary of what happened."

account ......... class BankAccount
owner ........... attribute  self.owner
balance ......... attribute  self.balance
what happened ... attribute  self.history
deposit ......... method  deposit(amount)
withdraw ........ method  withdraw(amount)
summary ......... method  summary()

Let us build this account in four visible steps, running the program after each one. Building small and testing as you go is how experienced programmers work. It keeps every mistake close to the line that caused it. Step 1 is the bare minimum: an owner, a balance and a way to add money.

Step 1: owner, balance, deposit
class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self.balance = balance def deposit(self, amount): self.balance += amount acct = BankAccount("Asha", 100) acct.deposit(50) print(acct.owner, acct.balance)

Step 2 adds withdraw. Here a class earns its keep, because the rule lives right next to the data. You cannot take out more than you have. The method checks, and reports success or failure by returning True or False. It does not print, because the code that called it should decide what to say to the customer.

Step 2: withdraw with a safety check
class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self.balance = balance def deposit(self, amount): self.balance += amount def withdraw(self, amount): if amount > self.balance: return False # refuse: not enough money self.balance -= amount return True acct = BankAccount("Asha", 100) print(acct.withdraw(30), acct.balance) # allowed print(acct.withdraw(500), acct.balance) # refused, balance unchanged

What Python does, line by line, for acct.withdraw(500) in step 2

  • Python finds withdraw in the class and calls BankAccount.withdraw(acct, 500). So self is acct and amount is 500.
  • The if compares 500 with self.balance, which is 70 at that moment. The test is true.
  • return False runs immediately. The rest of the method is skipped, so self.balance is never changed.
  • The caller receives False and can decide what to print. If the test had been false, the balance would have dropped and True would come back.

Step 3 keeps a history. A new attribute, history, starts as an empty list inside __init__ (remember the lesson of section 1.6). Every deposit and every successful withdrawal appends a small tuple describing what happened.

Step 3: a history list
class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self.balance = balance self.history = [] def deposit(self, amount): self.balance += amount self.history.append(("deposit", amount)) def withdraw(self, amount): if amount > self.balance: return False self.balance -= amount self.history.append(("withdraw", amount)) return True acct = BankAccount("Asha", 100) acct.deposit(50) acct.withdraw(30) acct.withdraw(999) print(acct.history)

Step 4 adds a summary method that turns all of that into a readable report. Notice that it returns a string, so the caller can print it, save it or put it in an email.

Step 4: summary()
class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self.balance = balance self.history = [] def deposit(self, amount): self.balance += amount self.history.append(("deposit", amount)) def withdraw(self, amount): if amount > self.balance: return False self.balance -= amount self.history.append(("withdraw", amount)) return True def summary(self): rows = [f" {kind}: {amount}" for kind, amount in self.history] return "\n".join([f"{self.owner}: balance {self.balance}"] + rows) acct = BankAccount("Asha", 100) acct.deposit(50) acct.withdraw(30) print(acct.summary())

Because each account carries its own balance and its own history, two accounts never interfere with each other. That is the payoff for everything in the chapter so far.

Two accounts, fully independent
class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self.balance = balance self.history = [] def deposit(self, amount): self.balance += amount self.history.append(("deposit", amount)) asha = BankAccount("Asha", 100) ben = BankAccount("Ben") asha.deposit(50) ben.deposit(10) print(asha.owner, asha.balance, len(asha.history)) print(ben.owner, ben.balance, len(ben.history))

Two mistakes are especially common while designing. The first: inside one method, calling another method of the same class without self.. Python looks for a plain function with that name and finds none.

Mistake: calling a sibling method without self
class BankAccount: def __init__(self, owner): self.owner = owner self.balance = 0 def deposit(self, amount): self.balance += amount def bonus(self): deposit(10) # should be self.deposit(10) acct = BankAccount("Asha") try: acct.bonus() except NameError as error: print("NameError:", error)

The second is a design weakness rather than an error message. Nothing stops code outside the class from writing acct.balance = -1000 and skipping withdraw and its safety check entirely. Python allows it. In the next chapter (OOP 2) you will learn how to guard attributes so the rules cannot be bypassed. For now, the discipline is: change state through methods.

Here is a second, quite different design so the pattern sinks in. A Playlist has a name and songs. You can add a song, remove a song and ask for the total length. Each song is a (title, minutes) tuple. The nouns (playlist, name, songs) gave us the attributes and the verbs (add, remove, total) gave us the methods. In total_minutes, sum(minutes for title, minutes in self.songs) is a comprehension without the square brackets: it adds up each song's minutes.

A second design: Playlist
class Playlist: def __init__(self, name): self.name = name self.songs = [] def add_song(self, title, minutes): self.songs.append((title, minutes)) def remove_song(self, title): for song in self.songs: if song[0] == title: self.songs.remove(song) return True return False def total_minutes(self): return sum(minutes for title, minutes in self.songs) mix = Playlist("Road trip") mix.add_song("Sunrise", 3) mix.add_song("Highway", 4) print(mix.total_minutes(), mix.remove_song("Sunrise"), mix.remove_song("Nope")) print(mix.songs, mix.total_minutes())

Notice how the two classes have the same shape: a few facts set in __init__, and a handful of short methods, each doing one job. When a method grows long or does several unrelated things, split it. When two facts always travel together and have their own behaviour, they might deserve a class of their own. Chapter OOP 4 shows how classes can contain each other.

1.9 — Debugging Objects: Looking Inside When Things Go Wrong

Every programmer spends a large share of their time working out why something does not behave. That is not a sign that you are doing it wrong. It is the job. With objects, bugs usually fall into a few families: an attribute is missing or misspelt, a method was not called, two names point at one object, or a value is of a different type than you assumed. The skill is to look inside the object instead of guessing. This section gives you the tools and a checklist.

The first thing every beginner tries is print(rex). Let us see what that shows for an object of your own class.

What print(obj) shows by default
class Dog: def __init__(self, name): self.name = name rex = Dog("Rex") text = str(rex) print(text.startswith("<__main__.Dog object at 0x")) print(text.split(" at ")[0])

I have not printed the whole line, because it contains a memory address (the 0x... number), and that number is different every time you run the program. On your computer, print(rex) produces something like the reference block below, with a different number.

print(rex) with no special method
<__main__.Dog object at 0x7f3a2c1b5d90>

Python is saying: "an object of class Dog, defined in the main program, stored at this memory address". That is honest but not helpful, because it says nothing about Rex. The reason is that you have not told Python how a dog should present itself as text, so it falls back to a default. In OOP 2 you will learn the special method __str__, which lets you write print(rex) and see Dog(Rex, age 3). For now, use the better tools below.

What Python does, line by line, for print(rex)

  • print needs text, so Python asks the object to turn itself into a string.
  • Python looks in the class Dog for instructions on how. There are none.
  • It uses the default: the class name plus the object's memory address.
  • That text is printed, and it tells you the type and nothing about the contents.

The tool you will reach for most is vars(obj). It returns a dictionary of everything stored inside the object, and you have used it all chapter. A second built-in, dir(obj), lists every name the object can respond to, including methods and Python's own special names. It is long, so it helps to filter out names that begin with two underscores.

vars() and dir(): what does this object have?
class Dog: def __init__(self, name, age): self.name = name self.age = age def bark(self): print("Woof!") rex = Dog("Rex", 3) print(vars(rex)) print([n for n in dir(rex) if not n.startswith("__")]) print(hasattr(rex, "bark"), hasattr(rex, "color")) print(type(rex).__name__, isinstance(rex, Dog))

Read the results together. vars shows the facts stored in this object (name and age). dir also shows bark, which lives in the class. hasattr answers yes-or-no questions, and type and isinstance confirm what kind of object you are holding. When a value is not what you expected, print vars right before the line that fails.

Now a genuine detective story. This dog is supposed to age by a year on birthday(). It does not, and no error appears. Watch how vars reveals the culprit.

Detective work: the birthday that does nothing
class Dog: def __init__(self, name, age): self.name = name self.age = age def birthday(self): age = self.age + 1 # bug hides here rex = Dog("Rex", 3) rex.birthday() print(vars(rex)) # age is still 3 print(rex.birthday()) # None: it returns nothing

The method computed age, a plain local variable, and threw it away when the method ended. The attribute self.age was never touched, exactly like the missing self. in section 1.4. The fix is self.age = self.age + 1 or, shorter, self.age += 1. The lesson is the method: *look at the state (vars) before and after the suspect call*.

Another subtle clash appears when an attribute and a method share a name. An instance attribute set in __init__ is found before the class's method with the same name. That hides the method, and calling it fails with an unusual message.

Mistake: an attribute and a method with the same name
class Dog: def __init__(self, age): self.age = age # instance attribute called age def age(self): # method also called age: hidden by the attribute return self.age rex = Dog(3) print(vars(rex)) try: rex.age() except TypeError as error: print("TypeError:", error)

'int' object is not callable means "you put brackets after something that is a number". Python found the attribute age (the number 3) first, and you cannot call a number. The fix is to give them different names, such as an attribute age and a method describe_age() or get_age().

Often the bug is not in the method you called but in a method it called. The traceback lists every function that was active when the error happened, oldest first. You read it from the bottom: the last line says what went wrong, and the entry just above it says where. Here is what a saved file would show when we accidentally pass a string instead of a number to withdraw.

Reading a traceback that passes through a method
Traceback (most recent call last): File "bank.py", line 12, in <module> print(acct.withdraw("50")) ^^^^^^^^^^^^^^^^^^^ File "bank.py", line 7, in withdraw if amount > self.balance: ^^^^^^^^^^^^^^^^^^^^^ TypeError: '>' not supported between instances of 'str' and 'int'

Read it bottom-up. The error is a TypeError: you compared a str with an int. It happened at line 7, inside withdraw, on the if amount > self.balance line. The entry above says who called withdraw: line 12 of the main program, where we wrote "50" in quotes. So the cause is the call site, even though the error fired inside the method. We can ask Python for the names of those entries directly, which is handy when a real traceback scrolls past too fast.
