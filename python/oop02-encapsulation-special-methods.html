2.1 — The Problem: Anyone Can Break Your Object

In OOP 1 you learned that a class is a blueprint and an object is one thing built from that blueprint. You learned that __init__ sets up a new object, that self means "the object I am working on", and that a method is a function that lives inside a class. The data an object remembers is stored in attributes, such as self.balance. Here is a small bank account class that uses all of those ideas. Run it first, so we are starting from the same place. (Every runnable block in this chapter is complete on its own, so you can run any of them in any order.)

A simple Account, as you built it in OOP 1
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def deposit(self, amount): self.balance = self.balance + amount def show(self): print(f"{self.owner} has {self.balance} coins") asha = Account("Asha", 100) asha.deposit(50) asha.show()

This works, and for a moment it feels finished. The trouble is what the class does not do. It never checks anything. A real bank account has rules: a balance cannot be a piece of text, a deposit cannot be negative, and you cannot casually reach in and rewrite the balance. Our class knows none of these rules, and Python will not enforce rules that we did not write. Watch how much nonsense it accepts.

Nothing stops bad data
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def deposit(self, amount): self.balance = self.balance + amount asha = Account("Asha", 100) asha.balance = -999 # a negative balance? print(asha.balance) asha.balance = "lots" # text instead of a number? print(asha.balance) asha.balance = 100 asha.deposit(-500) # a negative deposit is really a withdrawal print(asha.balance)

Every one of those lines ran without a single error. Python is not being careless. From its point of view, asha.balance = -999 is a perfectly legal instruction: "put the value -999 into the attribute called balance". Python has no idea that a bank balance should never be negative. Only you know that, so only you can teach the class to care.

   Outside code                         The Account object
  ┌───────────────┐                    ┌──────────────────────┐
  │ asha.balance  │ ─── writes any ──► │ owner   = "Asha"     │
  │   = -999      │      value,        │ balance = -999   ???  │
  │ asha.balance  │      any time      │                      │
  │   = "lots"    │                    └──────────────────────┘
  └───────────────┘                    Nobody checks anything.
An object with no rules is like a house with no front door

Why this hurts: the bug shows up far from the cause

The worst part is not the bad value itself. It is that the damage appears somewhere else, later. Imagine that a hundred lines after asha.balance = -999, another part of the program calculates interest. It multiplies the balance by 0.05 and prints a friendly message. The message is wrong, and when you go hunting for the reason you will search the interest code, which is perfectly fine. The real culprit is a single line far away that nobody thought about.

The bug appears far from the cause
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def deposit(self, amount): self.balance = self.balance + amount asha = Account("Asha", 100) asha.balance = -999 # somewhere, long ago... # ...a hundred lines later, in a different part of the program: interest = asha.balance * 0.05 print(f"Interest earned: {interest}")

The program happily prints Interest earned: -49.95, a negative amount of interest that no bank would ever pay. Nothing crashed, so nothing pointed at the real cause.

Programmers call a statement that must always be true about an object an invariant. "The balance is a number that is never below zero" is an invariant of a bank account. A class that cannot protect its invariants is like a bank that leaves the vault door open and hopes that everyone is polite. This chapter is about teaching your classes to protect themselves, and then about making them pleasant to use.

The quiet typo problem

There is one more trap, and every beginner meets it. Suppose you make a small spelling mistake while updating an attribute.

A typo silently creates a brand-new attribute
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def deposit(self, amount): self.balance = self.balance + amount asha = Account("Asha", 100) asha.balnce = 500 # typo: "balnce", not "balance" print(asha.balance) print(vars(asha))

There was no error at all. The real balance is still 100, and the object quietly grew a new attribute named balnce. The built-in function vars() shows an object's attributes as a dictionary, and you can see both spellings living side by side. Python lets you attach a new attribute to almost any object at any moment, which is flexible, but it also means that a typo becomes a silent bug instead of a loud crash.

What Python does when you write asha.balance = -999
  • Python works out the value on the right-hand side of the =. Here that is the number -999.
  • It finds the object that asha points to (the Account you built).
  • It stores the value in that object's attribute dictionary under the name "balance". If the name already exists it is replaced; if not, a new attribute is created.
  • It does not ask the class whether the value is sensible. There is no step where a rule could say no. That missing step is the whole problem.
🧠 Check yourself
After asha.balnce = 500 (a typo), what does asha.balance still equal, and why is there no error?
It still equals 100. Assigning to an attribute that does not exist yet simply creates it, so Python treats balnce as a new, legitimate attribute.
Name one rule ("invariant") a bank account should always obey.
For example: the balance is a number, the balance is never negative, or deposits must be positive. Any true-at-all-times rule about the account counts.
✏️ Try it
Change -999 to -1 and run the "bad data" block again. Then invent your own nonsense value, such as None or a list [1, 2], and see whether Python complains. It will not. That silence is exactly what we will fix.
✅ Recap
  • Python does not check what you store in an attribute, so acct.balance = -999 is accepted.
  • An invariant is a rule that must always be true about an object, such as "balance is never negative".
  • Bad values cause bugs far away from the line that created them, which makes them painful to find.
  • A misspelled attribute name silently creates a new attribute instead of raising an error.
  • The next sections teach a class to guard its own data.
2.2 — Encapsulation: A Front Door for Your Data

Last section we saw the problem: anyone can write anything into an attribute. Your first instinct might be to leave a polite note in the code, like # please do not change balance directly. Try that idea in your head. Would it stop a teammate who is in a hurry, or you, three months from now, when you have forgotten the note? Comments are for humans, and humans forget. We need a stronger idea.

That idea is called encapsulation. The word sounds heavy, but the picture is simple. Think about a vending machine. You do not open the back and rearrange the snacks. You use the front panel: put in coins, press a button, take your snack. The messy insides (the motor, the coin counter, the stock) are sealed away, and the machine only allows the few actions it was designed for. Encapsulation means the same thing for objects: keep the data inside the object, and let the outside world touch it only through a small set of methods, the front door. Those methods are called the object's public interface. Everything behind the door is the object's private business.

   Outside code                    Account object
                              ┌──────────────────────────────┐
   acct.deposit(50)  ───────► │  deposit()    withdraw()     │
   acct.get_balance() ──────► │  get_balance()               │
                              │  ┌────────────────────────┐  │
   acct._balance = -999 ─ ✗─► │  │  _balance = 100        │  │
   (please don't!)            │  └────────────────────────┘  │
                              └──────────────────────────────┘
Encapsulation: the outside talks to the front door, not to the data

Here is where Python is different from some other languages, and it is worth understanding honestly. Languages such as Java have a private keyword that the computer really enforces. Python takes a more trusting attitude, often summed up as "we are all consenting adults here". Python gives you naming conventions instead of locks. There are three levels, and you tell them apart by how many underscores (_) a name starts with.

  • Public: a normal name such as balance or owner. It is part of the front door. Anyone may use it.
  • Protected (by convention): a name with one leading underscore, such as _balance. It means "this is internal, please do not touch it from outside". Python does not stop you. It is a signpost, not a wall.
  • Private (name mangling): a name with two leading underscores, such as __balance. Python does something extra here, which we will look at closely in a moment.

Let us start with the single underscore. It changes nothing about how Python runs your code. It only tells other programmers (and tools such as editors) that the attribute is an internal detail.

One underscore is a signpost, not a lock
class Account: def __init__(self, owner, balance): self.owner = owner self._balance = balance # internal: use the methods instead def get_balance(self): return self._balance asha = Account("Asha", 100) print(asha.get_balance()) # the polite way, through the front door print(asha._balance) # works, but you were asked not to asha._balance = -999 # Python does not stop you... print(asha.get_balance()) # ...so the convention is only as good as your team

So the single underscore is a promise between programmers. That is a surprisingly powerful thing. Almost every Python library you will ever use follows it, so when you read code and see _something, you instantly know "this is internal, I should not depend on it". Now the double underscore, which goes one step further.

Two underscores: Python rewrites the name
class Account: def __init__(self, owner, balance): self.owner = owner self.__balance = balance # two underscores def get_balance(self): return self.__balance # works inside the class asha = Account("Asha", 100) print(asha.get_balance()) try: print(asha.__balance) # from the outside... except AttributeError as error: print("AttributeError:", error)

The outside access failed with AttributeError: 'Account' object has no attribute '__balance'. That looks like real privacy. But read the message carefully: it says the attribute does not exist under that name. It does not say the data is gone. Let us look inside the object with vars(), the tool from the last section.

Name mangling: the data is still there
class Account: def __init__(self, owner, balance): self.owner = owner self.__balance = balance asha = Account("Asha", 100) print(vars(asha)) print(asha._Account__balance) # the "mangled" name works fine asha._Account__balance = -999 # so this still works too print(asha._Account__balance)
What Python does with self.__balance inside class Account
  • While reading the class body, Python notices a name that starts with two underscores and does not end with two underscores.
  • It rewrites that name by adding an underscore and the class name in front: __balance becomes _Account__balance. This rewriting is called name mangling.
  • The attribute is stored in the object under the mangled name, which is exactly what vars(asha) displayed.
  • Code outside the class that writes asha.__balance is not rewritten, so it looks for a name that was never stored, and you get the AttributeError.

This is the honest truth about "private" in Python: name mangling is not security. It is a way to avoid accidental collisions. Its real purpose appears in OOP 3, when a class and its child classes might both want an attribute with the same name, and mangling keeps them from trampling each other. Anyone who really wants the data can still write _Account__balance, and that is fine, because they clearly did it on purpose.

⚠️
Common mistakeDo not use two underscores on both sides, like __balance__. Names that start and end with two underscores (__init__, __str__) are reserved by Python for special behaviour, and they are never mangled. You will meet many of them later in this chapter.

So which one should I use?

Use the single underscore almost every time. It is simple, everyone understands it, and it is easy to debug because the attribute keeps its normal name. Reach for double underscores only when you are building classes meant to be extended and need to prevent clashes. Whichever you choose, the important part is what you do next: you provide methods that guard the data. That is what the next two sections build.

🧠 Check yourself
You write self._balance = 100 inside __init__. Can code outside the class read and change acct._balance? Should it?
Yes, it can, because Python does not enforce anything. It should not: the underscore is a signal that the attribute is internal and the outside should use the class's methods.
Inside class Account, you store self.__pin = 1234. What is the real attribute name stored on the object?
_Account__pin. Python mangles it by putting an underscore and the class name in front.
✏️ Try it
Add a second private attribute, self.__nickname = "Rainy day fund", then print vars(asha). Predict the exact key name before you run it. Then read the nickname from outside using the mangled name.
✅ Recap
  • Encapsulation means keeping data inside an object and letting outside code use it only through a public interface of methods.
  • name is public, _name is a "please do not touch" signpost, and __name is mangled to _ClassName__name.
  • Name mangling protects against accidental clashes, not against determined people. It is not security.
  • In everyday Python, prefer a single underscore and a set of well-behaved methods.
2.3 — Validation: Methods That Say No

We now know where the front door is. The next question is what the doorman should do when someone tries to walk through with something silly, such as a deposit of -50. There are two tempting but weak answers. One is to do nothing and carry on. The other is to print an error message and carry on. Try the second one and see why it is not enough.

The weak answer: print a complaint and carry on
class Account: def __init__(self, owner, balance): self.owner = owner self._balance = balance def deposit(self, amount): if amount <= 0: print("Deposit must be positive") # just a message... else: self._balance += amount asha = Account("Asha", 100) asha.deposit(-50) print("Balance is now", asha._balance) print("Deposit accepted!") # this line has no idea anything went wrong

The method printed a complaint, but the rest of the program cannot see it. The line that follows happily announces "Deposit accepted!", which is false. A message printed to the screen is only for a human watching. The code that called deposit received no signal at all. We need a way for a method to say "I refuse, and I am stopping everything until someone deals with this."

Python has exactly that, and it is a statement called raise. When Python runs raise, it immediately stops the current method, creates an exception (an object that describes what went wrong) and sends it back up to whoever called the method. If nobody deals with it, the program stops and prints a report called a traceback. Think of a bank teller who cannot process your request. A good teller does not mutter and carry on; they stamp the form REJECTED and hand it back with a reason. raise is that stamp. The reason is the text you pass in.

Python has many built-in kinds of exception. You need only two for now. ValueError means "this is the right kind of thing, but the value is unacceptable" (a negative deposit). TypeError means "this is the wrong kind of thing entirely" (the text "ten" where a number belongs). Here is the smallest possible example.

raise in its smallest form
def check_age(age): if age < 0: raise ValueError("age cannot be negative") return age print(check_age(30)) # fine try: check_age(-5) # this raises... except ValueError as error: # ...and this catches it print("Caught:", error)

The try and except lines are worth a quick explanation, even though Chapter 5 studies them in depth. Python runs the indented lines under try. If one of them raises a ValueError, Python jumps straight to the except ValueError as error: line, and the error object is available under the name error. Printing it shows the message you wrote. If nothing goes wrong, the except part is skipped. That is all you need for now: try this, and if that specific error happens, do this instead.

Now let us give our Account real rules. We validate in __init__ too, because a bad account should never come into existence.

An Account that refuses bad input
class Account: def __init__(self, owner, balance=0): if balance < 0: raise ValueError("Opening balance cannot be negative") self.owner = owner self._balance = balance def deposit(self, amount): if amount <= 0: raise ValueError("Deposit must be positive") self._balance += amount def get_balance(self): return self._balance asha = Account("Asha", 100) asha.deposit(50) print(asha.get_balance()) for bad in (-20, 0): try: asha.deposit(bad) except ValueError as error: print("Refused:", error) print(asha.get_balance())
What happens when asha.deposit(-20) runs
  • Python calls deposit with self as Asha's account and amount as -20.
  • The if amount <= 0: test is true, so Python runs the raise line.
  • raise builds a ValueError object that carries the text "Deposit must be positive".
  • The method stops on the spot. The line self._balance += amount never runs, so the balance is safe.
  • The error travels back to the caller. Our try/except catches it and prints the message.

Now the withdrawal, which has one extra rule: you cannot take out more than you have. We also make the message useful, because a message that says exactly what was wrong (and with which numbers) saves a lot of debugging time.

withdraw: a rule with a helpful message
class Account: def __init__(self, owner, balance=0): self.owner = owner self._balance = balance def withdraw(self, amount): if amount <= 0: raise ValueError("Withdrawal must be positive") if amount > self._balance: raise ValueError(f"Cannot withdraw {amount}: only {self._balance} available") self._balance -= amount asha = Account("Asha", 100) asha.withdraw(30) print(asha._balance) try: asha.withdraw(500) except ValueError as error: print("Refused:", error)

Notice how much the message helps. "Refused" alone would leave you guessing; the message tells you the amount you asked for and the amount actually available. Here we caught the error to keep the console tidy. What if nobody catches it? Then the program stops, and Python prints a traceback. Below is the same class, with the last call left unprotected, saved in a file called bank.py and run as a normal script. Read a traceback from the bottom up. The last line names the error type and its message. The lines above it are the trail of calls that led there, ending with the line that raised it, so you can see where the refusal happened.

Reference only — bank.py (the same class, but the failing call is not caught)
class Account: def __init__(self, owner, balance=0): self.owner = owner self._balance = balance def withdraw(self, amount): if amount <= 0: raise ValueError("Withdrawal must be positive") if amount > self._balance: raise ValueError(f"Cannot withdraw {amount}: only {self._balance} available") self._balance -= amount asha = Account("Asha", 100) asha.withdraw(30) print(asha._balance) asha.withdraw(500)

Three mistakes beginners make with validation

Mistake 1: forgetting the word raise. Writing ValueError("...") on its own line builds an error object and then throws it away. There is no error and no protection, and it is very easy to miss.

Mistake: building an error but not raising it
class Account: def __init__(self, owner, balance=0): self.owner = owner self._balance = balance def deposit(self, amount): if amount <= 0: ValueError("Deposit must be positive") # forgot raise! self._balance += amount asha = Account("Asha", 100) asha.deposit(-50) print(asha._balance) # 50: the bad deposit went through

Mistake 2: changing the data before checking it. If you subtract first and validate afterwards, then by the time the error is raised the damage is already done, and the object is left in a broken state even though you "refused" the request. The rule of thumb is check first, change afterwards.

Mistake: modifying before validating
class Account: def __init__(self, owner, balance=0): self.owner = owner self._balance = balance def withdraw(self, amount): self._balance -= amount # changed too early! if self._balance < 0: raise ValueError("Insufficient funds") asha = Account("Asha", 100) try: asha.withdraw(500) except ValueError as error: print("Refused:", error) print(asha._balance) # -400: refused, but still damaged

Mistake 3: believing this is enough. Our methods now guard the front door well, yet asha._balance = -999 still works, because the attribute is still an ordinary one that anyone can assign to. Validation inside methods protects only the people who use the methods. To guard attribute assignment itself we need a tool that runs code whenever an attribute is read or written. That tool is the next section.

🧠 Check yourself
What is the difference between print("Deposit must be positive") and raise ValueError("Deposit must be positive") inside deposit?
print only shows text to a human and the program carries on as if nothing happened. raise stops the method, so the balance is never changed, and it signals the caller so the caller can react (or the program stops with a traceback).
In withdraw, why check amount > self._balance before doing self._balance -= amount?
If you subtract first, the balance is already wrong by the time you notice the problem. Checking first means a refused request leaves the object untouched.

✅ Recap
  • Printing a complaint does not tell the calling code anything. raise does: it stops the method and sends an exception back.
  • ValueError means "right kind of thing, bad value". TypeError means "wrong kind of thing".
  • try: ... except ValueError as error: catches the exception and lets you read its message.
  • Check first, change afterwards, so a refused request leaves the object unharmed.
  • Read tracebacks from the bottom: the last line has the error type and message.
2.4 — @property: Guarded Attributes That Look Like Plain Ones

Our Account now has a front door, but the door is a little awkward. To read the balance we must write asha.get_balance(), and to change it we would need a matching set_balance(...) method. Imagine adding 10 coins the "front door" way: asha.set_balance(asha.get_balance() + 10). Compare that with the natural version, asha.balance += 10. Programmers coming from other languages write getter and setter methods everywhere, and the code fills up with noise. Python offers something better, and it also solves a second problem that you may not have noticed yet.

Suppose you shipped version 1 of the class with a plain public attribute balance, and other people's code (maybe 200 lines of it) already contains acct.balance = 50 and print(acct.balance). Now you want validation. If you rename things to _balance and set_balance(), you break every one of those 200 lines. What you want is to keep the outside looking exactly the same while changing the inside. Python's tool for this is the property.

To use it we need one small piece of new vocabulary. A decorator is a line that starts with @ and sits directly above a def. It wraps the function below it and changes how it behaves. You do not need to know how decorators are built. You only need to know that @property above a method turns that method into something you read like an attribute, without parentheses. Think of a light switch on the wall. You flip it like any switch, but behind the plate there is wiring that decides what really happens.

The smallest property: a read-only balance
class Account: def __init__(self, owner, balance): self.owner = owner self._balance = balance @property def balance(self): return self._balance asha = Account("Asha", 100) print(asha.balance) # no parentheses! print(vars(asha)) # the data lives in _balance print(type(Account.balance)) # balance is a property object on the class
What Python does when it reads asha.balance
  • Python has to find something called balance. The object itself does not store one: the vars() line shows it holds only owner and _balance.
  • On the class Account, however, there is a balance, and it is a property object (the type() line printed <class 'property'>).
  • Because it is a property, Python calls the method you decorated, passing asha in as self.
  • Whatever that method returns (self._balance, here 100) becomes the value of asha.balance.
    asha.balance                      what really runs
   ┌─────────────┐   Python sees     ┌────────────────────────────┐
   │ looks like  │   a property on   │ def balance(self):         │
   │ plain data  │ ────────────────► │     return self._balance   │
   └─────────────┘   the class       └────────────────────────────┘
A property is a method wearing an attribute's clothes

Because we wrote only the reading part, the property is read-only. If someone tries to overwrite it, Python refuses, and this is protection we got for free.

Read-only means assignment is refused
class Account: def __init__(self, owner, balance): self.owner = owner self._balance = balance @property def balance(self): return self._balance asha = Account("Asha", 100) try: asha.balance = -999 except AttributeError as error: print("AttributeError:", error) print(asha.balance)

Sometimes you do want assignment to be allowed, as long as it follows the rules. For that you add a second method with the same name, decorated with @balance.setter. The setter runs whenever someone writes asha.balance = something, and it gets the new value as its argument. That is the perfect place to validate.

A property with a validating setter
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance # goes through the setter! @property def balance(self): return self._balance @balance.setter def balance(self, value): if value < 0: raise ValueError("Balance cannot be negative") self._balance = value asha = Account("Asha", 100) asha.balance = 250 # allowed, so the setter runs print(asha.balance) try: asha.balance = -999 except ValueError as error: print("Refused:", error) try: Account("Ben", -1) # even the starting value is checked except ValueError as error: print("Refused:", error)

Look closely at __init__. It says self.balance = balance, with no underscore, so the assignment goes through the setter and the starting value is validated with the same rule. One rule, written once, guards every way in. The actual data is stored in _balance, the "behind the door" attribute, and only the setter writes to it.

Properties that compute their answer

A property does not have to return a stored value. It can work something out each time you ask. This is useful when a piece of information should always agree with the data it comes from. The trouble with storing such a value is that it goes stale. Watch what happens.

Stored copies go stale, computed properties do not
class StaleAccount: def __init__(self, balance): self.balance = balance self.status = "empty" if balance == 0 else "active" # stored once class Account: def __init__(self, balance): self.balance = balance @property def status(self): # worked out fresh each time return "empty" if self.balance == 0 else "active" old, new = StaleAccount(0), Account(0) old.balance = 500 new.balance = 500 print("stored: ", old.status) print("computed:", new.status)

The stored version still says "empty" even though there are 500 coins in it, because nothing updated the copy. The computed property cannot go out of date, since it reads the balance every time. A good rule for properties: keep them cheap and unsurprising. Reading asha.status should feel like reading an attribute, not like starting a long calculation.

Why properties keep old code working

Here is the payoff we promised. The class below stores money as whole cents internally, which avoids the tiny rounding errors that fractions can cause. That is a big change to the inside. But look at the code that uses it: it is the same code that worked with the plain version.

The inside changes, the outside code does not
class Account: def __init__(self, balance): self._cents = round(balance * 100) # new internal format @property def balance(self): return self._cents / 100 @balance.setter def balance(self, value): if value < 0: raise ValueError("Balance cannot be negative") self._cents = round(value * 100) # --- old client code, written before the change, still works --- acct = Account(10.5) acct.balance = acct.balance + 0.25 print(acct.balance) print(vars(acct))

Common mistakes

Mistake 1: calling a property with parentheses. A property already produces the value, so asha.balance() tries to call the number 100 as if it were a function.

Mistake: parentheses after a property
class Account: def __init__(self, balance): self._balance = balance @property def balance(self): return self._balance asha = Account(100) try: asha.balance() except TypeError as error: print("TypeError:", error)

Mistake 2: the setter writes to the property's own name. Inside the setter you must store into _balance. If you write self.balance = value, that assignment triggers the setter again, which assigns again, forever. Python stops this with a RecursionError. We show this one for reading only, because an endless chain of calls is heavy for Python running inside a browser tab.

Reference only — Mistake: the setter calls itself
class Account: @property def balance(self): return self._balance @balance.setter def balance(self, value): self.balance = value # should be self._balance! try: Account().balance = 5 except RecursionError as error: print("RecursionError:", error)
What it prints
RecursionError: maximum recursion depth exceeded

Mistake 3: using @balance.setter before the property exists. The getter must come first, otherwise Python has no balance to attach the setter to and reports NameError: name 'balance' is not defined.

🧠 Check yourself
You define @property def area(self) and then call shape.area(). What error do you get, and why?
A TypeError such as 'int' object is not callable (or 'float'...). The property already ran and gave you the value, and you then tried to call that value like a function.
A class has a property balance with a getter only. What happens on acct.balance = 5?

✅ Recap
  • @property turns a method into something you read without parentheses, so guarded data still looks like a plain attribute.
  • A getter alone makes the property read-only. Add @name.setter to allow validated assignment.
  • Store the real data in _name and let the property named name guard it. Writing self.name = ... in __init__ sends the starting value through the setter too.
  • Computed properties are always fresh, so they never go stale like a stored copy.
  • Properties let you change the inside of a class without breaking any code that uses it.
2.5 — __str__ and __repr__: Teaching Your Object to Introduce Itself

Your Account is safe now, but try to look at one. Print it, the way you would print a number or a string, and see what comes out.

The default way Python shows your object
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance asha = Account("Asha", 100) text = str(asha) print(text[:28]) # the start of the text print(text.endswith(">")) # ends with a closing bracket

That is not friendly. Python printed something like <__main__.Account object at 0x7f3a2c1b5d90>. The long number at the end is a memory address, the place in the computer's memory where the object lives. It is different on every run, which is why the block above prints only the beginning of the text. This tells you a class exists and nothing at all about which account it is. It is even worse in a list of accounts, where you would see a row of such addresses. When you are hunting a bug, this is painful.

Python lets you fix it, using special methods. These are methods whose names start and end with two underscores, such as __init__, which you already know. Programmers nickname them dunder methods (short for "double underscore"). You almost never call a special method yourself. You define it, and Python calls it for you at the right moment. That is why your class can behave like Python's own types.

There are two special methods for turning an object into text, and they have different audiences. Think of a party. __str__ is the name tag: short, friendly, meant for the guests (your users). __repr__ is the passport: precise, unambiguous, meant for the person who has to identify you exactly (you, the developer, while debugging). Both must return a string.

__str__: the friendly version
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def __str__(self): return f"{self.owner}'s account: {self.balance} coins" asha = Account("Asha", 100) print(asha) # print calls __str__ print(f"Hello, {asha}!") # so do f-strings print(str(asha)) # and str()
What Python does for print(asha)
  • print needs text to display, so it asks for str(asha).
  • str() looks on the class Account for a method named __str__.
  • It finds ours and calls it with asha as self.
  • Our method returns the string "Asha's account: 100 coins", and print shows it.
  • If we had not written __str__, Python would fall back to __repr__, and if that is missing too, to the ugly default from before.

Now a surprise that trips up almost everyone. What happens when our accounts are inside a list? We only wrote __str__, so you might expect the friendly text.

Surprise: lists show the developer version
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def __str__(self): return f"{self.owner}'s account: {self.balance} coins" accounts = [Account("Asha", 100), Account("Ben", 40)] print(accounts[0]) # friendly: uses __str__ print(str(accounts)[:30]) # the list uses __repr__ for its items

When Python prints a list, it shows each item using repr, because a list display is developer-oriented and must be unambiguous. Since we did not write __repr__, we get the ugly default again inside the list. So the two methods each have their own job. Here is the rule of thumb for what each one does:

   What you write              What Python calls
   ─────────────────────────   ─────────────────────────
   print(x)                    __str__    friendly text
   f"{x}"                      (falls back to __repr__
   str(x)                       if there is no __str__)

   repr(x)                     __repr__   precise text
   f"{x!r}"                    (also what a Python shell
   x inside a list or dict      shows when you type x)
Who calls which special method

What should a good __repr__ look like? The best convention is to make it look like the code that would create the object. Then when you see it in a debugging message, you can read exactly what it is, and even copy it into your code. For our account that is Account('Asha', 100), with quotes around the name so you can tell text from numbers. To get those quotes we use a tool called !r inside an f-string, which means "show this value using its repr". Compare the two ways of showing the same string.

str vs repr on simple values, and the !r shortcut
name = "Asha" print(str(name), repr(name)) # Asha 'Asha' print(2, "2") # look identical... print(repr(2), repr("2")) # ...but repr tells them apart print(f"{name} {name!r}") # !r inside an f-string print(repr("line1\nline2")) # repr even shows hidden characters

Now we can give the class both methods. __repr__ is the precise one, and __str__ is the friendly one.

Both special methods on Account
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def __repr__(self): return f"Account({self.owner!r}, {self.balance!r})" def __str__(self): return f"{self.owner}'s account: {self.balance} coins" accounts = [Account("Asha", 100), Account("Ben", 40)] print(accounts[0]) # friendly print(repr(accounts[0])) # precise print(accounts) # lists use repr

To keep the examples short we have left out the validation you wrote earlier. In your finished class all of it is still there. Notice that a different kind of question is being answered by each: print(asha) answers "what would I tell a customer?", while repr(asha) answers "what exactly is this object?". If you can only write one of the two, write __repr__. When __str__ is missing, Python quietly uses __repr__ instead, but it never works the other way round.

Only __repr__ is enough
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance def __repr__(self): return f"Account({self.owner!r}, {self.balance!r})" asha = Account("Asha", 100) print(asha) # falls back to __repr__ print([asha])

Common mistakes

Mistake 1: printing inside __str__ instead of returning. Python needs the method to give back a string. If you print and return nothing, the method returns None, and Python complains with a message that names the problem clearly.

Mistake: __str__ must return, not print
class Account: def __init__(self, owner): self.owner = owner def __str__(self): print(f"Account of {self.owner}") # prints, but returns None asha = Account("Asha") try: print(asha) except TypeError as error: print("TypeError:", error)

Notice that the line "Account of Asha" did appear, because our method printed it before returning. Then Python complained. Read the message: __str__ returned non-string (type NoneType). It tells you which method broke the rule and what it returned instead. The fix is always to replace print(...) with return ....

Mistake 2: misspelling the special name. If you write __str or _str_ or __string__, Python does not raise any error. It just never calls the method, because it looks for the exact name __str__. If your custom text is not showing up, check the underscores first.

🧠 Check yourself
You print a list of Account objects and see <__main__.Account object at 0x...> for every item, even though the class has __str__. What is missing?
__repr__. A list displays its items with repr, so __str__ is not used there. Adding a __repr__ fixes the list display.
What should repr(Account("Asha", 100)) ideally look like?
Like the code that creates it: Account('Asha', 100). Using !r puts the quotes around the name automatically.
✏️ Try it
Add a third attribute currency to the account (for example "coins"), put it in both methods, and print one account and a list of two. Then delete the __repr__ and predict what the list looks like before you run it.
✅ Recap
  • A special (dunder) method has a name like __str__. You define it, and Python calls it at the right moment.
  • __str__ is the friendly text for users: used by print(), str() and f-strings. __repr__ is the precise text for developers: used by repr(), inside lists, and by !r.
  • A good __repr__ looks like the constructor call, such as Account('Asha', 100).
  • Both methods must return a string. If only one is defined, define __repr__, since __str__ falls back to it.
2.6 — Equality and Ordering: When Are Two Objects "the Same" or "Bigger"?

So far our objects can hold data safely and describe themselves. Next we want to compare them, the way you compare numbers. Our bank needs a proper way to talk about amounts of money, so we introduce a small new class, Money, which stores an amount in whole cents (so Money(1250) means 12.50). This class will keep growing for the rest of the chapter. First, let us see what Python does when we try to compare two of them.

The problem: equal amounts are not "equal", and cannot be sorted
class Money: def __init__(self, cents): self._cents = cents def __repr__(self): return f"Money({self._cents})" a = Money(500) b = Money(500) print(a == b) # same amount, yet... try: print(sorted([Money(900), Money(100)])) except TypeError as error: print("TypeError:", error)

Two identical 5-dollar amounts are reported as not equal, and sorting fails with TypeError: '<' not supported between instances of 'Money' and 'Money'. To see why, we need two ideas that beginners often mix up. Identity asks "are these two names pointing at the very same object?", and Python checks that with is. Equality asks "do these two objects count as the same value?", and Python checks that with ==. Think of two five-dollar notes in your pocket. They have equal value, but they are two different pieces of paper. By default, == on your own objects behaves exactly like is: it only says "yes" for one and the same piece of paper.

Identity (is) versus equality (==) by default
class Money: def __init__(self, cents): self._cents = cents a = Money(500) b = Money(500) c = a # c is another name for the SAME object print("a is b:", a is b) # different objects print("a == b:", a == b) # default == means "is" print("a is c:", a is c) # same object print("a == c:", a == c)
      a ───────► ┌───────────────┐          b ───────► ┌───────────────┐
      c ───────► │ Money  _cents │                     │ Money  _cents │
                 │        = 500  │                     │        = 500  │
                 └───────────────┘                     └───────────────┘
   a is c  → True   (one object)          a is b  → False   (two objects)
   a == b  → False by default. We can teach Python to say True.
Two objects with equal contents, and one object with two names

To change what == means, we write the special method __eq__. Python calls it whenever you write a == b, passing the left object as self and the right object as other. It must return True or False.

__eq__ decides what "equal" means
class Money: def __init__(self, cents): self._cents = cents def __eq__(self, other): return self._cents == other._cents a, b, c = Money(500), Money(500), Money(750) print(a == b) # True: same amount print(a == c) # False: different amount print(a is b) # still False: they are two objects print(a != c) # != works automatically

That works until someone compares a Money with something that is not a Money. Our method reaches for other._cents, and a plain number has no such attribute, so the comparison crashes instead of simply answering "no". The polite fix is to check the type first, and to answer with the special value NotImplemented. This is not an error. It is Python's way for a method to say: "I do not know how to compare with that; let Python try something else". Python then falls back to its default answer, which for == is False.

Comparing with something that is not Money
class Careless: def __init__(self, cents): self._cents = cents def __eq__(self, other): return self._cents == other._cents class Money: def __init__(self, cents): self._cents = cents def __eq__(self, other): if not isinstance(other, Money): return NotImplemented return self._cents == other._cents try: Careless(500) == 500 except AttributeError as error: print("AttributeError:", error) print(Money(500) == 500) # False, no crash

The function isinstance(other, Money) asks "is other a Money object (or a child of Money)?". It returns True or False. We will use this guard again in the next few sections.

The hash catch: equality changes how sets and dicts see your object

There is a consequence you must know about. Python sets and dictionary keys store objects using a number called a hash, a kind of label that tells Python which "drawer" an object belongs in. Objects that are equal must have the same hash, otherwise the drawers would not work. So when you write your own __eq__, Python takes away the automatic hash by setting __hash__ to None, and it refuses to guess a new one. You then have to say how the hash is worked out.

Defining __eq__ removes the hash until you add one
class Money: def __init__(self, cents): self._cents = cents def __eq__(self, other): if not isinstance(other, Money): return NotImplemented return self._cents == other._cents try: {Money(500), Money(500)} except TypeError as error: print("TypeError:", error) Money.__hash__ = lambda self: hash(self._cents) # the fix, in one line print(len({Money(500), Money(500), Money(750)})) # duplicates collapse

In a real class you write the fix inside the class as a method, def __hash__(self): return hash(self._cents). The one-line version above only makes it easy to see in a short example. The value you hash must be the same data that __eq__ compares. There is also a safety rule: only hash an object whose data does not change. If a Money were changed while sitting in a set, Python would look in the wrong drawer and never find it again. That is why our Money has no setter.

Ordering: making < and sorted() work

For ordering we write __lt__ ("less than"). Python calls it for a < b. And if you write a > b, Python is clever enough to flip it around and call b.__lt__(a). But <= and >= are not filled in for you.

Only __lt__: some comparisons work, some do not
class Money: def __init__(self, cents): self._cents = cents def __eq__(self, other): return self._cents == other._cents def __lt__(self, other): return self._cents < other._cents a, b = Money(100), Money(900) print(a < b, a > b) try: print(a <= b) except TypeError as error: print("TypeError:", error)

Writing __le__, __gt__ and __ge__ by hand is boring. Python's standard library has a shortcut, a decorator called functools.total_ordering. You write __eq__ and __lt__, place @total_ordering above the class, and it fills in the other three comparisons. Now sorted(), min(), max() and .sort() all work on your own objects.

total_ordering completes the set
from functools import total_ordering @total_ordering class Money: def __init__(self, cents): self._cents = cents def __eq__(self, other): return self._cents == other._cents def __lt__(self, other): return self._cents < other._cents def __repr__(self): return f"Money({self._cents})" prices = [Money(900), Money(100), Money(450)] print(sorted(prices)) print(min(prices), max(prices)) print(Money(100) <= Money(100), Money(100) >= Money(900))
What Python does for sorted(prices)
  • sorted needs to know which of two items comes first, so it repeatedly asks item1 < item2.
  • For each question Python calls item1.__lt__(item2), which our class answers by comparing the two _cents values.
  • It uses the answers to arrange the list from smallest to largest and returns a new list. Our Money objects did not change.

Common mistake: using is to compare values. is is for asking "same object?", and it is what you want for None (if x is None). To ask "same value?", use ==. In the code above Money(100) is Money(100) would be False, even though they are equal.

🧠 Check yourself
You define __eq__ on a class and later put two objects into a set. Python raises TypeError: unhashable type. What is the fix?
Define __hash__ too, computed from the same data that __eq__ compares, for example return hash(self._cents).
What does returning NotImplemented from __eq__ mean?
"I do not know how to compare with that kind of object." It is not an error. Python tries the other side, and if nothing can answer it falls back to the default (False for ==).
✏️ Try it
In the last block, add Money(450) a second time to the prices list. Print sorted(prices) and len(set(prices)). Predict the second answer first (you will need __hash__ for the set to work: add it inside the class).
✅ Recap
  • is asks "same object?". == asks "same value?". By default == on your own classes means is.
  • __eq__ defines equality. Return NotImplemented for objects of an unknown type.
  • Defining __eq__ removes the automatic hash. Add __hash__ (from the same data) if the objects must live in sets or be dict keys.
  • __lt__ plus @functools.total_ordering gives you every comparison, so sorted, min and max just work.
2.7 — Container Behaviour: Objects That Work With len(), [ ] and for

A bank has many accounts, so let us build a class that holds them: a Bank. Inside, it keeps the accounts in a list (a private one, by the rules of encapsulation). Now try to use the Bank the way you use an ordinary list.

The problem: a Bank is not a list
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance class Bank: def __init__(self): self._accounts = [] def open_account(self, owner, balance): self._accounts.append(Account(owner, balance)) bank = Bank() bank.open_account("Asha", 100) bank.open_account("Ben", 40) for action in (lambda: len(bank), lambda: bank[0], lambda: [a for a in bank]): try: action() except TypeError as error: print("TypeError:", error)

Three ordinary things all failed: len(bank), bank[0] and looping with for. The messages say it plainly. The Bank "has no len()", is "not subscriptable" (which is Python's phrase for "you cannot use square brackets on it") and is "not iterable" (you cannot loop over it). The only workaround is to reach inside with for a in bank._accounts, which breaks the front-door rule we worked so hard on in 2.2. We want the outside to say len(bank) and for a in bank, while the list stays hidden.

Python makes this possible with the same trick as in the last section. Built-in tools such as len() do not look inside your object. They ask it, by calling a special method. If your class has the method, the tool works. This idea is called duck typing, from the saying "if it walks like a duck and quacks like a duck, it is a duck". Python does not care what class you are. It only cares whether you have the right methods. Think of a plug and a socket: if your plug has the right shape, it fits.

Here are the four special methods for a container, each linked to the syntax it powers.

   What you write       Python calls                 Returns
   ──────────────────   ──────────────────────────   ─────────────
   len(bank)       ──►  bank.__len__()               a number
   bank[0]         ──►  bank.__getitem__(0)          the item
   for a in bank   ──►  bank.__iter__()              an iterator
   "Asha" in bank  ──►  bank.__contains__("Asha")    True / False
Container syntax and the method behind each

Let us add them one at a time, starting with the easiest: __len__. It simply returns how many things the container holds. As a bonus, an empty container then counts as "false" in an if, just like an empty list.

__len__ gives you len() (and emptiness checks)
class Bank: def __init__(self): self._accounts = [] def open_account(self, owner): self._accounts.append(owner) def __len__(self): return len(self._accounts) bank = Bank() print(len(bank)) print("empty" if not bank else "has accounts") bank.open_account("Asha") bank.open_account("Ben") print(len(bank)) print("empty" if not bank else "has accounts")

Next is __getitem__, which powers the square brackets. Python passes whatever you wrote between the brackets as an argument. Because we can hand that argument straight to the inner list, we get negative positions and slices (like [0:2]) without writing any extra code.

__getitem__ gives you [ ] and slices
class Bank: def __init__(self, names): self._accounts = list(names) def __getitem__(self, position): return self._accounts[position] bank = Bank(["Asha", "Ben", "Chen"]) print(bank[0]) print(bank[-1]) print(bank[0:2]) try: bank[10] except IndexError as error: print("IndexError:", error)

The error for a position that does not exist comes from the inner list, and it is the same message you already know. Now for the star of this section: __iter__, which powers for loops. An iterator is an object that hands out items one at a time and remembers where it is. The simplest way to produce one is to ask the inner list for its own with iter(...).

__iter__ gives you for loops and everything built on them
class Bank: def __init__(self, balances): self._balances = list(balances) def __iter__(self): return iter(self._balances) bank = Bank([100, 40, 250]) for balance in bank: print("balance:", balance) print(list(bank)) print(sum(bank), max(bank), sorted(bank)) print([b * 2 for b in bank])
What Python does for for balance in bank:
  • Python calls iter(bank), which calls our bank.__iter__().
  • Our method returns an iterator over the inner list.
  • Python asks that iterator for the next item, over and over, and puts each item into the variable balance before running the loop body.
  • When the iterator has no more items it signals "finished" and the loop ends quietly. You never see this signal.

Notice the bonus in the last two lines of the block. Once a class can be iterated, everything in Python that consumes iterables works on it: list(), sum(), max(), sorted(), and list comprehensions. You wrote one small method and got all of those.

One small tool appears in the next block. The built-in any(...) looks at a series of true/false answers and gives back True as soon as one of them is true (and False if none is). Written as any(a.owner == owner for a in accounts), it means "is there at least one account whose owner matches?".

The fourth method is __contains__, which powers the word in. Without it, Python falls back to looping through the container and comparing each item. That fallback works, but defining __contains__ lets you decide what "contains" means. For a Bank, it is natural to ask "is there an account for this owner?".

__contains__ gives you the word in
class Account: def __init__(self, owner, balance): self.owner = owner self.balance = balance class Bank: def __init__(self, accounts): self._accounts = list(accounts) def __contains__(self, owner): return any(a.owner == owner for a in self._accounts) bank = Bank([Account("Asha", 100), Account("Ben", 40)]) print("Asha" in bank) print("Zed" in bank) print("Zed" not in bank)

Now let us assemble the pieces into one tidy class. The list stays private, and a validated method is the only way in. The outside world gets a natural, list-like feel.

A complete Bank: private list, natural syntax
class Account: def __init__(self, owner, balance): self.owner, self.balance = owner, balance def __repr__(self): return f"Account({self.owner!r}, {self.balance})" class Bank: def __init__(self): self._accounts = [] def open_account(self, owner, balance): if owner in self: raise ValueError(f"{owner} already has an account") self._accounts.append(Account(owner, balance)) def __len__(self): return len(self._accounts) def __getitem__(self, i): return self._accounts[i] def __iter__(self): return iter(self._accounts) def __contains__(self, owner): return any(a.owner == owner for a in self._accounts) bank = Bank() bank.open_account("Asha", 100) bank.open_account("Ben", 40) print(len(bank), bank[0], "Ben" in bank) print(sum(a.balance for a in bank))

Look at if owner in self inside open_account. The Bank uses its own __contains__ to check for duplicates. Your special methods are ordinary parts of your class, and your own code can use them.

Common mistakes

Mistake 1: __iter__ must return an iterator, not the list itself. It is very tempting to write return self._accounts. Python then complains, because a list is iterable (you can loop over it) but is not an iterator (it does not hand out items on its own). The tool that turns one into the other is iter().

Mistake: returning the list from __iter__
class Bank: def __init__(self): self._items = [1, 2, 3] def __iter__(self): return self._items # should be iter(self._items) try: for item in Bank(): print(item) except TypeError as error: print("TypeError:", error)

Mistake 2: forgetting the return. A __len__ that computes the length but never returns it gives back None, and len(bank) fails with 'NoneType' object cannot be interpreted as an integer. As with __str__, these methods must give back their answer.

🧠 Check yourself
Which special method makes for account in bank: work, and what must it return?
__iter__, and it must return an iterator, for example iter(self._accounts). Returning the list itself gives TypeError: iter() returned non-iterator of type 'list'.
A class defines only __len__. Which of these work on it: len(x), x[0], for i in x, bool(x)?
len(x) works, and bool(x) works too (it is False when the length is 0). x[0] needs __getitem__ and for i in x needs __iter__ (or __getitem__).
✏️ Try it
In the "complete Bank" block, add a fifth account and print bank[-1], bank[1:] and [a.owner for a in bank]. Then try to open a second account for "Asha" inside a try/except ValueError and print the message.
✅ Recap
  • Built-in tools ask your object for behaviour through special methods, so a class with the right methods "fits the plug". This is duck typing.
  • __len__ powers len() (and empty checks), __getitem__ powers [ ] and slices, __iter__ powers for and everything built on it, and __contains__ powers in.
  • __iter__ must return an iterator, so use iter(self._items).
  • A container can keep its data private and still feel like a built-in list.
2.8 — Operator Overloading: Making + and * Mean Something

Our Money class can be printed, compared and sorted. The next natural thing to do with money is add it up. Let us try the obvious thing and see what Python says.

The problem: + does not know about Money
class Money: def __init__(self, cents): self._cents = cents def __repr__(self): return f"Money({self._cents})" def add(self, other): # the "method" workaround return Money(self._cents + other._cents) a, b, c = Money(500), Money(250), Money(100) try: a + b except TypeError as error: print("TypeError:", error) print(a.add(b).add(c)) # works, but reads badly

The error is unsupported operand type(s) for +: 'Money' and 'Money'. An operand is one of the things an operator works on, so this message reads "Python does not know how to put a plus between two Money objects". We could make do with a method like a.add(b).add(c), but compare that with a + b + c. The second one is how you would write it on paper, and it is much easier to read once the sums get longer.

Here is the idea. You already use + with different meanings for different types, and nobody is confused by it. For numbers it adds. For strings it joins. For lists it glues them together. Each type decides for itself what + means. This ability to give operators a meaning for your own classes is called operator overloading.

+ already means different things for different types
print(2 + 3) # numbers: add print("ab" + "cd") # strings: join print([1, 2] + [3]) # lists: concatenate print("ha" * 3) # strings: repeat print([0] * 4) # lists: repeat

The rule behind it is simple, and it is the same pattern as the last two sections: a + b is a shortcut for a.__add__(b). Python asks the left-hand object to do the work. If we define __add__ on Money, the plus sign starts working.

__add__ makes + work (and the originals stay untouched)
class Money: def __init__(self, cents): self._cents = cents def __add__(self, other): if not isinstance(other, Money): return NotImplemented return Money(self._cents + other._cents) def __str__(self): return f"${self._cents // 100}.{self._cents % 100:02d}" a, b = Money(500), Money(250) total = a + b print(total) print(a, b) # a and b did not change print(total is a, total is b) # total is a brand-new object
What Python does for a + b
  • Python sees + with a Money on the left, so it calls a.__add__(b), passing b as other.
  • Our method checks that other is a Money. If it were not, it would return NotImplemented (more on that shortly).
  • It builds a new Money holding the sum of the two amounts and returns it.
  • That returned object becomes the value of the whole expression a + b. Neither a nor b was modified, exactly like 2 + 3 does not change the 2 or the 3.

Returning a new object is an important habit. Money behaves like a number: if you add 5 dollars to 3 dollars you get 8 dollars, and the 5 and the 3 are still 5 and 3. Now we add the other operators a Money needs. Subtraction must refuse to produce a negative amount, and multiplication by a plain whole number is handy for prices times quantities.

__sub__ and __mul__
class Money: def __init__(self, cents): self._cents = cents def __sub__(self, other): if not isinstance(other, Money): return NotImplemented if other._cents > self._cents: raise ValueError("Money cannot be negative") return Money(self._cents - other._cents) def __mul__(self, count): if not isinstance(count, int): return NotImplemented return Money(self._cents * count) def __repr__(self): return f"Money({self._cents})" price = Money(250) print(price - Money(100)) print(price * 3) try: Money(100) - price except ValueError as error: print("ValueError:", error)

There is a catch with multiplication. price * 3 works, because the Money is on the left. But people also write 3 * price, with the number first. Now Python asks the integer 3 to multiply, and the integer says "I do not know what a Money is". Python does not give up yet. It then tries the right-hand object using a reflected method, whose name begins with r: __rmul__. (The "r" stands for "right-hand side".) So 3 * price becomes price.__rmul__(3). For multiplication, order does not matter, so we can reuse the same method.

__rmul__ handles the number-first version
class Money: def __init__(self, cents): self._cents = cents def __mul__(self, count): return Money(self._cents * count) def __repr__(self): return f"Money({self._cents})" price = Money(250) try: print(3 * price) except TypeError as error: print("TypeError:", error) Money.__rmul__ = Money.__mul__ # the fix (normally written inside the class) print(3 * price)

NotImplemented: the polite "not my job"

You saw return NotImplemented several times. It is not an error. It means "I cannot handle this combination; ask someone else". Python then tries the other object's reflected method, and if nobody can help it raises a clean TypeError that names both types. That is much better than crashing with a confusing message from inside your method.

Returning NotImplemented gives a clean error
class Money: def __init__(self, cents): self._cents = cents def __add__(self, other): if not isinstance(other, Money): return NotImplemented return Money(self._cents + other._cents) try: Money(500) + 5 except TypeError as error: print("TypeError:", error)

A catch with sum(), and truthiness with __bool__

Python's sum() starts counting from the number 0, so on a list of Money objects the very first step is 0 + Money(...). The integer 0 does not know what to do, and Money has no reflected __radd__, so it fails. The simple fix is to tell sum to start from a zero Money instead.

sum() needs a Money to start from
class Money: def __init__(self, cents): self._cents = cents def __add__(self, other): return Money(self._cents + other._cents) def __repr__(self): return f"Money({self._cents})" prices = [Money(500), Money(250), Money(100)] try: sum(prices) except TypeError as error: print("TypeError:", error) print(sum(prices, Money(0))) # second argument = starting value

The last special method here is __bool__. Python calls it when it needs a true/false answer, for example in if price:. Without it, every object counts as true. For money it is natural to say that zero is "false", so if not balance: reads as "if there is no money".

__bool__ makes zero money falsy
class Money: def __init__(self, cents): self._cents = cents def __bool__(self): return self._cents != 0 def __add__(self, other): return Money(self._cents + other._cents) wallet = Money(0) print(bool(wallet), bool(Money(5))) if not wallet: print("The wallet is empty") wallet += Money(300) # += falls back to __add__ print(bool(wallet))

Notice wallet += Money(300). We never wrote __iadd__, so Python quietly rewrites it as wallet = wallet + Money(300), which uses our __add__ and simply points the name wallet at the new object.

When operators help, and when they confuse

Operator overloading is a power tool. Use it when the meaning is obvious to anyone who reads it: adding Money to Money, adding two 2D vectors, multiplying a price by a quantity. A good test is to ask, "would someone guess what this does without reading the class?". Avoid clever tricks. If bank + account opened a new account, or playlist << song appended a song, readers would have to hunt through the class to learn the trick. A plainly named method such as bank.open_account(...) says what it does. Also keep operators consistent: + should not secretly change the left operand, and it should not print things or talk to files. Operators should behave like the mathematical ones people already know.

  • a + b means a.__add__(b), a * b means a.__mul__(b), and so on. Return a new object rather than changing the operands.

2.9 — @classmethod and @staticmethod: Other Doors Into a Class

Our Money takes a number of cents, so Money(1250) means 12.50. That is convenient for the class but not for people. Real programs receive money as text, for example the string "12.50" typed into a form or read from a file. Let us look at what the caller has to do today.

The problem: converting text to Money by hand
class Money: def __init__(self, cents): self._cents = cents def __repr__(self): return f"Money({self._cents})" text = "19.99" print(Money(int(float(text) * 100))) # looks right, but is it? print(Money(round(float(text) * 100))) # the safer version

The first line quietly produced 1998 cents instead of 1999. Decimal fractions like 19.99 cannot be stored perfectly as floats, so 19.99 times 100 comes out as 1998.9999999999998, and int() chops the fraction off. The second line fixes it with round. The real problem is bigger: every caller now has to know this trick, and they will all write it slightly differently.

The natural home for that knowledge is the class itself. But a class only has one __init__, and we cannot give it two different meanings ("cents" and "text"). Stuffing both into one __init__ with lots of if isinstance(...) tests makes it messy. The clean answer is an alternative constructor: an extra function, attached to the class, whose whole job is to build an object from a different starting point. Python has a special kind of method for this, the class method.

A class method is a method that belongs to the class rather than to one particular object. You mark it with the decorator @classmethod, and its first parameter is not self but cls, which is the class itself (here, Money). Think of a house with a front door and a side door: Money(1250) is the front door and Money.from_string("12.50") is a side door, and both lead to the same kind of object. Note that you call it on the class, before any Money exists.

A classmethod as an alternative constructor
class Money: def __init__(self, cents): self._cents = cents def __repr__(self): return f"Money({self._cents})" @classmethod def from_string(cls, text): dollars, _, cents = text.strip().lstrip("$").partition(".") cents = (cents + "00")[:2] # "5" -> "50", "" -> "00" return cls(int(dollars) * 100 + int(cents)) print(Money.from_string("12.50")) print(Money.from_string("$19.99")) print(Money.from_string("7")) print(Money.from_string("0.5"))
What Python does for Money.from_string("12.50")
  • Python sees the method is a classmethod, so it automatically passes the class Money as cls, and "12.50" as text. No object exists yet.
  • The method splits the text at the dot into dollars ("12") and cents ("50"), using only whole-number arithmetic, so no float errors can creep in. (The string method partition(".") cuts a string at the first dot and gives back three pieces: the part before, the dot itself, and the part after. We name the middle piece _, the usual way to say "I will not use this".)
  • cls(1250) is exactly the same as writing Money(1250): it runs __init__ and builds a new object.
  • The new object is returned to the caller.

Why write cls(...) and not simply Money(...)? Because cls always means "the class this method was called on". If you later create a child class of Money (a topic for OOP 3), Child.from_string("1.00") will correctly build a Child, while a hard-coded Money(...) would build the wrong kind of object. Getting into the habit costs nothing.

Class methods are also handy for small named helpers. Remember the sum(prices, Money(0)) trick from the last section? A zero() classmethod reads better.

Named constructors read like English
class Money: def __init__(self, cents): self._cents = cents def __add__(self, other): return Money(self._cents + other._cents) def __repr__(self): return f"Money({self._cents})" @classmethod def zero(cls): return cls(0) @classmethod def from_dollars(cls, dollars): return cls(round(dollars * 100)) prices = [Money.from_dollars(19.99), Money.from_dollars(5)] print(sum(prices, Money.zero()))

The second decorator of this section is @staticmethod. A static method is a plain function that happens to live inside the class because it belongs to the same topic. It receives neither self nor cls, since it does not need to know about any particular object or even the class. Think of a toolbox labelled "Money tools": a tape measure in it is related to the job, but it does not depend on any particular piece of money. A good example is a checker that says whether a piece of text looks like an amount.

A staticmethod: a related helper that needs no object
class Money: def __init__(self, cents): self._cents = cents @staticmethod def looks_like_money(text): digits = text.strip().lstrip("$").replace(".", "", 1) return digits.isdigit() print(Money.looks_like_money("12.50")) print(Money.looks_like_money("abc")) print(Money(5).looks_like_money("$3")) # also callable on an object

        Money(5).value()                             (self = that object)

   class method          @classmethod                needs the CLASS itself,
        Money.zero()     def zero(cls):              usually to build objects
                                                     (cls = Money)
   static method         @staticmethod               needs neither: a helper
        Money.looks_like_money("3")                  that lives here for
                         def looks_like_money(t):    tidiness only
The three kinds of method: what each one receives

Here is a rule of thumb to choose between them. Ask what the method needs. If it needs the data of one particular object, it is an instance method (the normal kind, with self). If it needs the class itself, usually to create new objects, make it a class method (with cls). If it needs neither, and is only related to the topic, make it a static method, or ask whether it should just be an ordinary function outside the class. When in doubt, start with a normal instance method.

Common mistakes

Mistake 1: forgetting the decorator. Without @classmethod, Python treats the method as an ordinary one and, when you call it on the class, hands your argument to cls and finds text missing.

Mistake: no @classmethod decorator
class Money: def __init__(self, cents): self._cents = cents def from_string(cls, text): # decorator forgotten return cls(int(text) * 100) try: Money.from_string("5") except TypeError as error: print("TypeError:", error)

Mistake 2: calling an instance method on the class. Money.value() has no object to use as self, so Python reports Money.value() missing 1 required positional argument: 'self'. Either create an object first (Money(5).value()) or, if the method truly needs no object, it probably should not be an instance method.

Chapter Summary — What You Can Now Do

You started this chapter with an Account that accepted any nonsense and printed as <__main__.Account object at 0x...>. You now know how to build classes that protect themselves and behave like Python's own types. Here is the whole toolbox, in the order you learned it.

  • Encapsulation: keep data behind a front door. name is public, _name is a "please do not touch" signpost, and __name is mangled to _ClassName__name (a guard against accidents, not security).
  • Validation: methods check their input and raise ValueError (bad value) or TypeError (wrong kind) with a helpful message. Check first, change afterwards.
  • Properties: @property makes a guarded attribute look plain, @name.setter validates assignment, and computed properties never go stale. They let you change a class's inside without breaking the code that uses it.
  • Text: __str__ is the friendly text for print and f-strings. __repr__ is the precise text, ideally shaped like the constructor call, and it is what lists show.
  • Comparison: __eq__ defines == (return NotImplemented for foreign types), __hash__ must match it for sets and dict keys, and __lt__ with @total_ordering gives you sorting, min and max.
  • Containers: __len__, __getitem__, __iter__ and __contains__ make your class work with len(), [ ], for and in.
  • Operators: __add__, __sub__, __mul__, __rmul__ and __bool__ make +, -, * and if work. Return new objects, and use operators only when their meaning is obvious.
  • Method kinds: instance methods use self, @classmethod methods use cls and build objects, @staticmethod methods use neither.
