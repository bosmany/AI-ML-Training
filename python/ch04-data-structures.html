Chapter 4:
Data Structures

Real datasets don't arrive as five neat variables — they arrive as thousands of records, each with several fields, often nested inside each other. This chapter covers the four containers Python gives you to hold that data: lists, tuples, dicts, and sets — and the shape you'll see constantly once you start loading real data: lists of dictionaries.

4.1 — Why We Need Collections: One Name for Many Values

Until now every value you stored had its own name: one variable, one number. That works for a handful of values. Watch what happens when a small study group of four learners each has a quiz score and we want the average.

Four values, four names
score_asha = 72 score_ben = 85 score_chen = 60 score_dana = 91 total = score_asha + score_ben + score_chen + score_dana print("Average:", total / 4)
Output
Average: 77.0

It runs, and the answer is right. Now picture a fifth learner joining. You must add a new variable, edit the total line, and change the 4 in the division. Miss any one of those three edits and the program quietly gives a wrong answer. With four hundred learners this approach is impossible: nobody writes four hundred variable names by hand, and you often do not even know how many values you will receive until the program runs.

What we want is a collection: a single object that holds many values together, under one name. Think of a shelf with labelled slots, or a lunch box with compartments. You carry one box, and still reach any compartment when you need it. Python has four built-in collections, and this chapter teaches all four: the list, the tuple, the dict (short for dictionary), and the set.

Here is the smallest possible example. The same four scores, now in one list. A list is written with square brackets, and the values inside are separated by commas.

The same problem with a list
scores = [72, 85, 60, 91] print(scores) print("How many:", len(scores)) print("Average:", sum(scores) / len(scores)) scores.append(78) print("After a fifth learner:", sum(scores) / len(scores))
Output
[72, 85, 60, 91]
How many: 4
Average: 77.0
After a fifth learner: 77.2
What Python does, line by line
  • scores = [72, 85, 60, 91] builds one list object holding four numbers and gives it the name scores.
  • len(scores) asks the list how many items it holds. It answers 4, so we never type the count ourselves.
  • sum(scores) adds every item: 72 + 85 + 60 + 91 = 308. Dividing by 4 gives 77.0.
  • scores.append(78) adds a fifth item to the end. The list grows.
  • The last line uses the same two functions again. No other line changed, yet the answer is now 77.2, because len and sum look at whatever is in the list right now.

That is the whole idea. The code is written once and works for any number of values. Every chapter from here on relies on it: a dataset is a collection of rows, a model config is a collection of settings, a vocabulary is a collection of words.

The four collections at a glance

Do not memorise this table yet. Read it once so the names feel familiar, and come back after each section. Two words need explaining. Ordered means every item has a fixed position you can count from. Mutable means you can change the collection after you have made it (add, remove, replace items). The opposite, immutable, means it is frozen once created.

Your program receives an unknown number of quiz scores each day. Why is a list a better fit than one variable per score?
Because a list has a single name whatever its size, and functions like len and sum adapt to however many items it holds. With separate variables you would have to edit the code every time the count changed.
Which of the four collections cannot hold the same value twice?
The set. Adding a value that is already inside changes nothing. (Dict keys are also unique, but dict values can repeat.)

Recap
  • A collection holds many values under one name, so code does not depend on how many values there are.
  • Python has four built-in collections: list, tuple, dict and set.
  • Ordered means items have positions; mutable means the collection can be changed after it is created.
  • len(collection) counts the items; sum(list) adds a list of numbers.
4.2 — Reaching Inside a List: Indexing and Slicing

A list is only useful if you can get at the items inside it. Suppose the study group scores are [72, 85, 60, 91, 78] and you want the first score, the last score, and the top three. You do not want to loop through the list for that. Python lets you point at a single item by its position, called an index.

Here is the part that surprises every beginner: counting starts at 0, not 1. Think of a row of houses where the number tells you how many steps to walk from the first house. The first house is zero steps away, the second is one step away. An index is exactly that: the distance from the start. Python also lets you count from the end, using negative numbers, where -1 is the last item.

One list, two ways to number it
 values     :    72    85    60    91    78
 index      :     0     1     2     3     4      (from the left)
 negative   :    -5    -4    -3    -2    -1      (from the right)
Every item has two valid addresses. scores[0] and scores[-5] are the same item, and so are scores[4] and scores[-1].
Indexing with positive and negative numbers
scores = [72, 85, 60, 91, 78] print(scores[0]) print(scores[1]) print(scores[-1]) print(scores[-2]) print(len(scores))
Output
72
85
78
91
5
What Python does, line by line
  • scores[0] is zero steps from the start, so it is the first item, 72.
  • scores[1] is one step from the start: 85.
  • scores[-1] counts from the end. The last item is 78.
  • scores[-2] is one step back from the end: 91.
  • len(scores) is 5, but the largest valid index is 4. A list of length n has indexes 0 to n - 1.
The sad path: an index that does not exist

What if you ask for a position past the end? Python refuses loudly instead of guessing. This is the real message from running the code below.

Asking for position 5 in a list of fiveread-only
scores = [72, 85, 60, 91, 78] print(scores[5])
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
IndexError: list index out of range

Read the last line first. The name IndexError says what kind of problem it is, and the text after the colon says what happened: the index was out of range. The line above it, line 2, tells you which line of your code failed. The fix is almost always an off-by-one: the last item of a five-item list is scores[4], or safer, scores[-1]. The negative form never needs you to know the length.

Slicing: taking a piece of the list

A slice copies a run of items into a new list. You write two numbers with a colon between them: scores[1:4] means "start at index 1, stop before index 4". The stop index is excluded. That feels odd at first, but it has a payoff: the slice [a:b] always has exactly b - a items, and scores[:2] plus scores[2:] rebuilds the whole list with no overlap.

Slice numbers point at the lines BETWEEN items
        +----+----+----+----+----+
        | 72 | 85 | 60 | 91 | 78 |
        +----+----+----+----+----+
 cut :  0    1    2    3    4    5

 scores[1:4]  -> cut at 1, cut at 4 -> [85, 60, 91]
Picture the numbers as cut marks between the boxes. A slice keeps everything between two cuts, which is why the stop position is never included.
Slices: start, stop, step
scores = [72, 85, 60, 91, 78] print(scores[1:4]) print(scores[:2]) print(scores[2:]) print(scores[-2:]) print(scores[::2]) print(scores[::-1]) print(scores[10:20]) print(scores)
Output
[85, 60, 91]
[72, 85]
[60, 91, 78]
[91, 78]
[72, 60, 78]
[78, 91, 60, 85, 72]
[]
[72, 85, 60, 91, 78]
What Python does, line by line
  • scores[1:4] keeps items at index 1, 2 and 3: [85, 60, 91].
  • scores[:2] leaves the start out, so it starts at the beginning: the first two items.
  • scores[2:] leaves the stop out, so it runs to the end.
  • scores[-2:] is the last two items, a handy way to say "the most recent two".
  • scores[::2] adds a third number, the step: take every second item. scores[::-1] uses a step of -1, which walks backwards and gives a reversed copy.
  • scores[10:20] is far beyond the end, yet there is no error. Slices are forgiving and simply return an empty list.
  • The last line prints the original: slicing never changes scores. It builds a new list each time.

Notice the contrast. A single index past the end raises IndexError, but a slice past the end quietly returns fewer items or none. That forgiving behaviour is convenient, and also a place where bugs hide, because a typo in a slice number does not shout.

Because a list is mutable, you can also change one item by assigning to its index. Assigning to a position that does not exist raises the same IndexError, since there is nothing there to replace.

Replacing an item by index
scores = [72, 85, 60, 91, 78] scores[2] = 65 print(scores) scores[-1] = scores[-1] + 2 print(scores)
Output
[72, 85, 65, 91, 78]
[72, 85, 65, 91, 80]

The same indexing and slicing rules work on strings, because a string is also an ordered row of items (its characters). "python"[0] is "p" and "python"[-3:] is "hon".

For scores = [72, 85, 60, 91, 78], what are scores[1:3] and scores[-3:-1]?
scores[1:3] is [85, 60] (indexes 1 and 2). scores[-3:-1] is [60, 91]: it starts at the third-from-last item and stops before the last one.
A list has 8 items. Which index is the last one, and what does items[8] do?
The last index is 7 (or -1). items[8] raises IndexError: list index out of range.
Try it. In the slice block, change [1:4] to [0:5], then to [1:1]. What does an empty slice look like? Try scores[::-2] too and explain the result.
Recap
  • An index is a position counted from 0; negative indexes count from the end (-1 is the last).
  • A valid index for a list of length n runs from -n to n - 1; anything else raises IndexError.
  • A slice [start:stop:step] builds a new list and excludes the stop position.
  • Slices never raise IndexError and never change the original list.
4.3 — Changing a List: In-Place Methods versus New Lists

Lists are mutable, so Python gives them methods that change them. A method is a function that belongs to an object and is called with a dot, like scores.append(95). Before we meet the full toolbox, look at a bug that catches almost everyone in their first week. We want the scores sorted from highest to lowest, so we write the natural thing.

The most common list bug
scores = [72, 85, 60, 91, 78] scores = scores.sort(reverse=True) print(scores)
Output
None

The output is None. The sorted list vanished. To see why, we need one idea: Python operations come in two flavours.

The first flavour changes the object itself, in place, and returns nothing useful (Python returns the special value None, which means "no value"). It is like tidying your own desk: the desk is now tidy, and there is nothing to hand to anyone. The second flavour leaves the original alone and hands back a new object, like photocopying a page and then tidying the copy. You now hold two pages.

scores.sort() is the tidy-the-desk kind. It reorders scores and returns None. Our line scores = scores.sort(...) sorted the list correctly, and then immediately overwrote the name scores with the None that sort returned. The sorted list lost its only name and was thrown away. The built-in function sorted(scores) is the photocopy kind: it returns a new sorted list.

In place versus a new list
scores = [72, 85, 60, 91, 78] ranked = sorted(scores, reverse=True) print("ranked :", ranked) print("original:", scores) result = scores.sort() print("sort() returned:", result) print("original now :", scores)
Output
ranked  : [91, 85, 78, 72, 60]
original: [72, 85, 60, 91, 78]
sort() returned: None
original now   : [60, 72, 78, 85, 91]
What Python does, line by line
  • sorted(scores, reverse=True) builds a brand-new list, highest first, and stores it under ranked.
  • The first two prints show that scores is untouched: still in its original order.
  • scores.sort() reorders the list itself (lowest first this time). It returns None, which we captured in result to prove the point.
  • The final prints show None for the result, and the original list now sorted. One call, one visible effect, no return value.
⚠️
Rule of thumb: if a list method changes the list, it returns None. Do not write x = x.sort(), x = x.append(5) or x = x.reverse(). Call the method on its own line, or use the returning version (sorted(x), reversed, slicing) when you need a new list.

append versus extend, and two sad paths

append adds one item, whatever it is. extend adds each item of another list. If you append a list, you get a list inside a list, which is rarely what you wanted.

append adds one thing, extend adds many
a = [1, 2] a.append([3, 4]) print(a, len(a)) b = [1, 2] b.extend([3, 4]) print(b, len(b))
Output
[1, 2, [3, 4]] 3
[1, 2, 3, 4] 4

4.4 — Two Names, One List: Aliasing versus Copying

Here is a plan that sounds reasonable. You want to keep a backup of the scores before changing them, so you write backup = scores. Then you change scores. Watch what happens to the backup.

A backup that is not a backup
scores = [72, 85, 60] backup = scores scores.append(99) scores[0] = 0 print("scores:", scores) print("backup:", backup) print("same object?", scores is backup)
Output
scores: [0, 85, 60, 99]
backup: [0, 85, 60, 99]
same object? True

The backup changed too, and it did not need to be touched. The last line, scores is backup, is True. To see why, we need the truth about what a variable really is.

A common picture is that a variable is a box with the value inside. For numbers and short text that picture is good enough. For collections it is misleading. A better picture: the list lives somewhere in memory, and a variable is a name tag stuck onto it. Writing backup = scores does not build a second list. It sticks a second name tag on the same list. Two tags, one object. This is called aliasing: two names for the same thing.

Aliasing: two name tags on one list
  BEFORE                          AFTER  scores.append(99)

  scores --+                      scores --+
           |                               |
           v                               v
        +----------------+             +--------------------+
        | 72 | 85 | 60   |             | 72 | 85 | 60 | 99  |
        +----------------+             +--------------------+
           ^                               ^
           |                               |
  backup --+                      backup --+

  ONE list, TWO names: changing it through one name shows up through the other.
Assignment copies the name tag, never the list. is asks "are these two names on the same object?".
What Python does, line by line
  • scores = [72, 85, 60] creates a list in memory and sticks the name scores on it.
  • backup = scores finds the object that scores points to and sticks a second name on that same object. No new list is made.
  • scores.append(99) changes the one shared list. Both names see it because both point to it.
  • scores[0] = 0 also edits the shared list, so backup shows the 0 too.
  • scores is backup compares identity, "is it literally the same object?", and answers True.
Making a real copy

When you want an independent list, ask for a copy explicitly. There are three common spellings and they all do the same thing: build a new list holding the same items.

Three ways to copy, and proof they are independent
scores = [72, 85, 60] backup1 = scores.copy() backup2 = list(scores) backup3 = scores[:] scores.append(99) print("scores :", scores) print("backups:", backup1, backup2, backup3) print(scores is backup1) print(scores == backup1)
Output
scores : [72, 85, 60, 99]
backups: [72, 85, 60] [72, 85, 60] [72, 85, 60]
False
False

The two comparison lines show a difference worth remembering. == asks "do these hold equal contents?", and is asks "are these the very same object?". After scores.append(99) the contents differ, so == is False. A fresh copy made before any change would be == to the original, yet still not is the original.

The same trap inside functions

Aliasing also happens when you pass a list to a function. The parameter is a new name tag stuck onto the list you passed in, so a function that changes it changes the caller's list. Sometimes that is what you want, and sometimes it is a surprise. A careful function copies first.

A function that changes its input, and one that does not
def add_bonus_in_place(values): for i in range(len(values)): values[i] = values[i] + 5 def with_bonus(values): return [v + 5 for v in values] scores = [72, 85, 60] print(with_bonus(scores), scores) add_bonus_in_place(scores) print(scores)
Output
[77, 90, 65] [72, 85, 60]
[77, 90, 65]

The first function builds and returns a new list, so scores is untouched after it. The second one edits the list it was given, so scores itself changed. When you write your own functions, pick one style and say which in the name or in a comment.

Numbers and text do not behave this way

If aliasing is real, why did it never bite you with plain numbers? Because numbers and strings are immutable: nothing can change them in place. The line a = a + 1 builds a new number and moves the tag, so a second name pointing at the old number is unaffected. Aliasing only causes trouble for mutable objects: lists, dicts and sets.

A copy that is only one layer deep

One more trap, and it matters as soon as collections hold other collections. copy() and [:] make a shallow copy: a new outer list, but the items inside are still the same objects. If those items are themselves lists, both outer lists share them.

Shallow copy: the inner lists are still shared
import copy groups = [["Asha", "Ben"], ["Chen"]] shallow = groups.copy() deep = copy.deepcopy(groups) groups[0].append("Dana") print("groups :", groups) print("shallow:", shallow) print("deep :", deep)
Output
groups : [['Asha', 'Ben', 'Dana'], ['Chen']]
shallow: [['Asha', 'Ben', 'Dana'], ['Chen']]
deep   : [['Asha', 'Ben'], ['Chen']]

shallow shows Dana because its first item is the very same inner list. copy.deepcopy copies every layer, so deep is fully independent. You will not need deepcopy often, but when a nested structure changes "by itself", shared inner objects are the usual cause.

After a = [1, 2], b = a, b.append(3), what is a?
[1, 2, 3]. b = a created no new list, so b.append(3) changed the one list both names point to.
How do you get a list that is safe to change without affecting the original?
Copy it: new = old.copy(), list(old) or old[:]. If the list contains other lists or dicts and you plan to change those, use copy.deepcopy(old).

Recap
  • A variable is a name tag on an object, and b = a puts a second tag on the same object.
  • With mutable objects this is aliasing: changing through one name shows through the other. is tests for it.
  • Make an independent list with .copy(), list(x) or x[:].
  • Copies are shallow: inner collections are still shared. Use copy.deepcopy when you need full independence.
4.5 — Tuples: Fixed Records and Unpacking

Some groups of values belong together and should never change. A point on a map is an x and a y. A colour is red, green and blue. If you store a point as a list, nothing stops a bug from quietly changing it later. A tuple is Python's answer: an ordered collection that is immutable, sealed once it is created. Think of a sealed envelope with two items inside. You can read what is in it, but you cannot swap an item.

A tuple is written with round brackets. Reading works exactly like a list, with indexes and slices from section 4.2. Changing does not work at all.

A tuple can be read but not changed
point = (3, 4) print(point[0], point[1]) print(point[-1]) print(len(point)) print(point + (5,)) print(point)
Output
3 4
4
2
(3, 4, 5)
(3, 4)

Reading is fine. The + line builds a new tuple (3, 4, 5) and leaves point alone, in the same spirit as slicing: a new object rather than a change. Now the sad path, with the real error message.

Trying to change a tupleread-only
point = (3, 4) point[0] = 10
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
TypeError: 'tuple' object does not support item assignment

TypeError means "you used this kind of object in a way it does not support". The message spells it out: a tuple does not support item assignment. There is no fix that keeps it a tuple. If you need a changeable version, build a new tuple with the changed value, or use a list.

⚠️
The one-item trap: (5) is just the number 5 in brackets. A tuple of one item needs a trailing comma: (5,). In fact it is the commas that make a tuple, not the brackets: x = 1, 2 is also a tuple.
Unpacking: giving each part its own name

Indexing a record as point[0] and point[1] is hard to read. Unpacking lets you split a tuple into separate variables in one line, matching values to names by position. It works on lists too.

Unpacking in four everyday situations
point = (3, 4) x, y = point print("x =", x, "y =", y) a, b = 1, 2 a, b = b, a print("swapped:", a, b) def min_and_max(values): return min(values), max(values) low, high = min_and_max([72, 85, 60, 91]) print("low", low, "high", high) pairs = [("Asha", 72), ("Ben", 85)] for name, score in pairs: print(name, "scored", score)
Output
x = 3 y = 4
swapped: 2 1
low 60 high 91
Asha scored 72
Ben scored 85
What Python does, line by line
  • x, y = point matches the first value to x and the second to y. Two names, two values.
  • a, b = b, a first builds the tuple (2, 1) from the right side, then unpacks it into a and b. That is how Python swaps two variables without a temporary third one.
  • return min(values), max(values) sends back a tuple. That is what "a function returning two values" really is. low, high = ... unpacks it on the other side.
  • In the loop, each item of pairs is a tuple. for name, score in pairs unpacks it as the loop takes it, so we get name and score directly instead of pair[0] and pair[1].
When the counts do not match

Unpacking demands an exact match. Three values into two names is an error, and so are two values into three names.

Too many valuesread-only
a, b = (1, 2, 3)
What Python says
Traceback (most recent call last):
  File "<exec>", line 1, in <module>
ValueError: too many values to unpack (expected 2)
Not enough valuesread-only
a, b, c = (1, 2)
What Python says
Traceback (most recent call last):
  File "<exec>", line 1, in <module>
ValueError: not enough values to unpack (expected 3, got 2)

Both messages come from ValueError: the type is right, the count is wrong. Read them as a receipt. "Expected 2" is how many names you wrote. The first message tells you there were too many values; the second tells you how many really arrived ("got 2") so you can compare with the 3 names. Section 4.13 shows a way to soak up any extra values with a star.

Why bother with a tuple at all?

Three reasons. It signals intent: a reader who sees (3, 4) knows the two values are a fixed pair. It is safe: nobody can change it by mistake. And, as section 4.7 shows, only immutable things can be used as dictionary keys, so a tuple can be a key where a list cannot. Functions in libraries you will meet later, such as the split of a dataset into training and test parts, return tuples for exactly these reasons.

What is type((7)) and what is type((7,))?
(7) is just the int 7, so its type is int. (7,) has the trailing comma, so it is a tuple.
x, y, z = [1, 2] fails. Which error, and why?

4.6 — Dictionaries: Looking Things Up by Name

Lists find things by position: "give me item number 3". But often you do not know the position, you know the name. Look at how awkward it gets when we keep names and phone numbers in two parallel lists.

Two lists that must stay in step

Output

It works, but only while the two lists are perfectly aligned. Sort one list and forget the other, or delete a name and not its number, and every answer after that is wrong without any error message. What we want is what a paper phone book gives us: you look up a name, and the book hands you a number. You never think about page positions.

That is a dictionary, or dict. It stores key-value pairs: each key (the name you look up) is tied to a value (the thing you get back). A dict is written with curly brackets, and each pair is key: value, separated by commas.

Which values can be keys? Hashable ones

Try to use a list as a key and Python refuses.

If a key could change after being stored, its fingerprint would change, and the dict would look in the wrong place forever. So dict keys must be hashable, meaning immutable.

4.8 — Sets: Unique Items, Fast Membership, and Comparing Groups

Two questions come up all the time with data. "Which distinct values are in here?" and "Is this value in the collection?" A list can answer both, but awkwardly. Here is the first one: a list of pet labels with repeats, and we want the distinct kinds.

Removing duplicates the hard way
labels = ["cat", "dog", "cat", "bird", "dog", "cat"] unique = [] for label in labels: if label not in unique: unique.append(label) print(unique)
Output
['cat', 'dog', 'bird']

It works, but it is a lot of code for a simple idea. A set is a collection that holds each value at most once, so duplicates disappear by design. Think of a guest list at a door: writing a name that is already on the list changes nothing. A set is written with curly brackets and no colons (a dict has colons), or built from any collection with set(...).

Sets remove duplicates automatically
labels = ["cat", "dog", "cat", "bird", "dog", "cat"] kinds = set(labels) print(len(labels), "labels,", len(kinds), "kinds") print(sorted(kinds)) kinds.add("fish") kinds.add("cat") print(sorted(kinds)) kinds.discard("dog") kinds.discard("zebra") print(sorted(kinds)) print("cat" in kinds)
Output
6 labels, 3 kinds
['bird', 'cat', 'dog']
['bird', 'cat', 'dog', 'fish']
['bird', 'cat', 'fish']
True
What Python does, line by line
  • set(labels) walks the list and keeps one copy of each value: three kinds from six labels.
  • We print sorted(kinds). A set has no order, so its own print order can differ between runs. sorted gives a list in a predictable order.
  • add("fish") inserts a new value. add("cat") does nothing, since "cat" is already inside. No error, no duplicate.
  • discard("dog") removes it. discard("zebra") does nothing because it was never there. (remove("zebra") would raise a KeyError.)
  • "cat" in kinds answers True. Membership tests are what sets are best at.
⚠️
Two traps. An empty pair of curly brackets {} makes an empty dict, not a set. Write set() for an empty set. And sets have no positions, so kinds[0] fails with TypeError: 'set' object is not subscriptable.
Why sets are fast: a speed intuition

Asking "is x in this list?" makes Python check the items one by one until it finds it, or reaches the end. With a million items that is up to a million checks. A set uses the hash idea from section 4.7: it computes a fingerprint from the value and jumps straight to where that value would be stored. The work barely grows as the collection grows. Compare a pile of unsorted cards, where you must flip through everything, with a labelled filing cabinet where you go to the right drawer at once. We can measure this without a stopwatch by counting the checks a list needs.

Counting how many checks a list search makes
def list_checks(items, target): checks = 0 for item in items: checks += 1 if item == target: break return checks small = list(range(100)) large = list(range(100000)) print("small list, last value:", list_checks(small, 99)) print("large list, last value:", list_checks(large, 99999)) large_set = set(large) # built once, up front print("set lookup, one hash jump ->", 99999 in large_set)
Output
small list, last value: 100
large list, last value: 100000
set lookup, one hash jump -> True

The list needed 100 checks for the small list and 100,000 for the large one: cost grows in step with size. The set lookup is one jump either way. (Building the set costs time once, so a set pays off when you ask many membership questions, not just one.) Programmers write this as "list lookup is proportional to the size, set lookup is roughly constant".

Sorting records: why sorted() needs a key

To rank learners by score we might try sorted(learners). Python has no idea how to put two dicts in order: is one "smaller" than another? It refuses, and says so.

Sorting dicts directlyread-only

What Python says

The message says < is not supported between two dicts. Sorting works by comparing pairs of items, and dicts cannot be compared. We must tell sorted what to compare. That is the job of the key= argument: a function that receives one item and returns the value to sort by. Here is that function written the ordinary way.

A key function, written normally
def get_score(learner): return learner["score"] learners = [ {"name": "Asha", "score": 72}, {"name": "Ben", "score": 85}, {"name": "Chen", "score": 60}, ] ranked = sorted(learners, key=get_score, reverse=True) for rank, learner in enumerate(ranked, start=1): print(rank, learner["name"], learner["score"])

2 Asha 72
3 Chen 60

Note that key=get_score has no brackets. We hand over the function itself and let sorted call it. It calls get_score once for each learner, gets 72, 85 and 60, sorts the learners by those numbers, and reverse=True puts the highest first. enumerate(ranked, start=1) numbers the results from 1 instead of 0. Because we only need this tiny function once, Python offers a shortcut.

A lambda is a small function without a name, written on one line: lambda learner: learner["score"]. Read it as "given a learner, give back its score". The word before the colon is the parameter, and whatever follows the colon is the returned value. It is exactly the same function as get_score, just written in place.

The same ranking with a lambda
learners = [ {"name": "Asha", "group": "A", "score": 72}, {"name": "Ben", "group": "B", "score": 85}, {"name": "Chen", "group": "A", "score": 60}, {"name": "Dana", "group": "B", "score": 91}, ] by_score = sorted(learners, key=lambda learner: learner["score"], reverse=True) print([l["name"] for l in by_score]) best = max(learners, key=lambda learner: learner["score"]) print(best["name"]) by_group = sorted(learners, key=lambda l: (l["group"], -l["score"])) print([l["name"] for l in by_group])

Dana
['Asha', 'Chen', 'Dana', 'Ben']

Three variations in one block. max accepts the same key=, and returns the whole best record. The last sort uses a tuple as the key: Python compares tuples position by position, so this orders by group first, and inside each group by highest score (the minus sign flips the numbers so bigger scores come first). Just like with a list of numbers, sorted builds a new list and .sort(key=...) reorders in place and returns None.

p is the parameter (one item from the list), and p["age"] is the value the lambda returns for it. It is a function that reads the "age" field of whatever it is given.

 |-- "course"   -> dict
 |                  |-- "title" -> "Intro"
 |                  '-- "tags"  -> list ["python", "data"]
 '-- "learners" -> list
                    |-- [0] dict: "name" -> "Asha", "scores" -> dict
                    '-- [1] dict: "name" -> "Ben",  "scores" -> dict
Every step down the tree is either a key (for a dict) or an index (for a list). The kind of bracket you write must match the kind of container you are stepping into.

The trick to reading a long chain is to go one step at a time, left to right, asking at each step "what is this now?". Let the computer show you.

Walking down one step at a time
response = { "learners": [ {"name": "Asha", "scores": {"quiz1": 72, "quiz2": 80}}, {"name": "Ben", "scores": {"quiz1": 85, "quiz2": 78}}, ], } step1 = response["learners"] step2 = step1[1] step3 = step2["scores"] step4 = step3["quiz2"] for step in (step1, step2, step3, step4): print(type(step).__name__, "->", step)
Output
list -> [{'name': 'Asha', 'scores': {'quiz1': 72, 'quiz2': 80}}, {'name': 'Ben', 'scores': {'quiz1': 85, 'quiz2': 78}}]
dict -> {'name': 'Ben', 'scores': {'quiz1': 85, 'quiz2': 78}}
dict -> {'quiz1': 85, 'quiz2': 78}
int -> 78
What Python does, line by line
  • response["learners"] looks up a key in a dict. The result is a list of two dicts.
  • step1[1] indexes that list. The result is the dict for Ben.
  • step2["scores"] looks up a key in Ben's dict. The result is another dict.
  • step3["quiz2"] looks up a key in that inner dict. The result is a plain int, 78, and we have arrived.
  • Written in one go: response["learners"][1]["scores"]["quiz2"]. It is the same four steps.
When the path is wrong

Two errors cover most nested-data mistakes. Using a key on a list, or a missing key at the wrong level. The messages point straight at the problem if you read the type names.

A string key used on a listread-only
learners = [{"name": "Asha"}, {"name": "Ben"}] print(learners["name"])
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>

A key that lives one level deeperread-only
learner = {"name": "Asha", "scores": {"quiz1": 72}} print(learner["quiz1"])
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
KeyError: 'quiz1'

The first message says a list needs integer positions, not a text key: you skipped the step [0] that picks which learner. The second is a plain KeyError, because "quiz1" is inside "scores", not at the top. In both cases, print the value one step earlier and look at its type. For optional parts chain .get with an empty dict as the fallback: learner.get("scores", {}).get("quiz3", 0) returns 0 instead of crashing.

From JSON text to Python and back

The standard library module json converts between JSON text (a string) and Python objects. json.loads(text) builds dicts and lists from text; json.dumps(obj) goes the other way. JSON writes true, false and null where Python writes True, False and None, and the module handles that translation.

JSON text to dict and back
import json text = '{"name": "Asha", "passed": true, "scores": [72, 80], "note": null}' data = json.loads(text) print(data) print(data["scores"][1], data["passed"], data["note"]) data["scores"].append(91) print(json.dumps(data))
Output
{'name': 'Asha', 'passed': True, 'scores': [72, 80], 'note': None}
80 True None
{"name": "Asha", "passed": true, "scores": [72, 80, 91], "note": null}
For d = {"a": [10, 20, {"b": 5}]}, how do you reach the 5?
d["a"][2]["b"]: key "a" gives the list, index 2 gives the inner dict, key "b" gives 5.
data["items"]["price"] raises TypeError: list indices must be integers or slices, not str. What is the likely cause?
data["items"] is a list, not a dict. You need an index first, for example data["items"][0]["price"].
Try it. In the walk-down block, change step1[1] to step1[0] and "quiz2" to "quiz1". Predict the four printed lines. Then change [1] to [5] and read the error.
Recap
  • Collections nest: dicts hold lists, lists hold dicts, dicts hold dicts. JSON is that same shape written as text.
  • Read a chain like d["a"][0]["b"] left to right, one step at a time; use a key for a dict and an index for a list.
  • TypeError: list indices must be integers means you used a key on a list; a KeyError usually means the wrong level.
  • json.loads(text) turns JSON text into Python data and json.dumps(obj) turns it back into text.
4.12 — The collections Module: Counter, defaultdict, namedtuple

Two jobs come up again and again: counting how often things occur, and grouping items under a label. You can do both with a plain dict, as in section 4.7, but the code repeats the same "does the key exist yet?" dance. Python's standard module collections (a module is a ready-made toolbox you load with import) has small tools that remove the dance. Here is the manual way once more, for grouping learners by their group.

Grouping by hand
learners = [("Asha", "A"), ("Ben", "B"), ("Chen", "A")] groups = {} for name, group in learners: if group not in groups: groups[group] = [] groups[group].append(name) print(groups)
Output
{'A': ['Asha', 'Chen'], 'B': ['Ben']}

It works, but the if guard is noise. Three tools solve three related problems.

Counter: how many of each?

Counter takes any collection and returns a dict-like object mapping each item to how often it appears. It behaves like a dict, with a few extras such as most_common. Looking up an item that never appeared gives 0 instead of a KeyError.

Counter
from collections import Counter answers = ["red", "blue", "red", "green", "red", "blue"] counts = Counter(answers) print(counts) print(counts["red"], counts["purple"]) print(counts.most_common(2)) print(Counter("banana"))
Output
Counter({'red': 3, 'blue': 2, 'green': 1})
3 0
[('red', 3), ('blue', 2)]
Counter({'a': 3, 'n': 2, 'b': 1})
defaultdict: a dict that creates missing values

defaultdict(list) is a dict with a rule: when you look up a key that is missing, it creates the value by calling the function you gave (list builds an empty list) and stores it. That removes the if guard from the grouping code above.

defaultdict
from collections import defaultdict learners = [("Asha", "A"), ("Ben", "B"), ("Chen", "A")] groups = defaultdict(list) for name, group in learners: groups[group].append(name) print(dict(groups)) totals = defaultdict(int) for name, points in [("Asha", 3), ("Ben", 5), ("Asha", 4)]: totals[name] += points print(dict(totals))
Output
{'A': ['Asha', 'Chen'], 'B': ['Ben']}
{'Asha': 7, 'Ben': 5}
What Python does, line by line
  • defaultdict(list) makes an empty dict that knows how to create a list on demand.
  • For ("Asha", "A") the code reads groups["A"]. The key is missing, so the dict quietly creates [], stores it, and hands it back. Then .append("Asha") fills it.
  • ("Chen", "A") finds the key already there and just appends.
  • defaultdict(int) creates 0 for a missing key (int() returns 0), so totals[name] += points works on the first visit.
⚠️
Side effect: merely reading a missing key from a defaultdict adds it. If you only want to peek, use key in d or d.get(key).
namedtuple: a tuple with field names

A plain tuple ("Asha", 72) makes you remember that position 1 is the score. A namedtuple is a tuple whose parts also have names. You define the shape once, then create records that read like learner.score. It stays immutable, and it is lighter than a dict.

namedtuple
from collections import namedtuple Learner = namedtuple("Learner", ["name", "score"]) asha = Learner("Asha", 72) print(asha) print(asha.name, asha.score) print(asha[1]) name, score = asha print(name, score)
Output
Learner(name='Asha', score=72)
Asha 72
72
Asha 72
A namedtuple cannot be changedread-only
from collections import namedtuple Learner = namedtuple("Learner", ["name", "score"]) asha = Learner("Asha", 72) asha.score = 80
What Python says
Traceback (most recent call last):
  File "<exec>", line 4, in <module>
AttributeError: can't set attribute

AttributeError tells you there is no way to set that attribute: the record is frozen, just like the tuple it is built on. To "change" one, build a new one: asha._replace(score=80).

You want to count how often each word appears in a list of words. Which tool?
Counter(words). It counts in one line, and counts.most_common(3) gives the top three.
Why is Counter(...)["missing"] safe but {}["missing"] not?
A Counter returns 0 for items it has never seen, because a count of "not there" is naturally 0. A plain dict raises KeyError.
Try it. In the Counter block, feed it list("mississippi") and read the most common letters. Then change most_common(2) to most_common() with no number.
Recap
  • Counter(items) counts occurrences; .most_common(n) lists the top n as (item, count) tuples.
  • defaultdict(list) creates an empty list for any missing key, which removes the if key not in d guard when grouping.
  • namedtuple gives a tuple named fields (record.score) and stays immutable.
  • All three come from from collections import ....
4.13 — Star and Double-Star: Splitting and Merging

Section 4.5 showed that plain unpacking needs an exact match of counts. But often you want the first item and "everything else", or the first and last and you do not care how many are in between. Without a special tool you would write first = scores[0] and rest = scores[1:] on two lines. Python has a one-line answer: put a * in front of one name, and that name soaks up all the leftover items as a list.

Star-unpacking a list
scores = [72, 85, 60, 91, 78] first, *rest = scores print(first, rest) *most, last = scores print(most, last) first, *middle, last = scores print(first, middle, last) winner, *others = ["Dana"] print(winner, others)
Output
72 [85, 60, 91, 78]
[72, 85, 60, 91] 78
72 [85, 60, 91] 78
Dana []
What Python does, line by line
  • first, *rest = scores gives first one item, and rest everything remaining, always as a list.
  • *most, last = scores works from the other side: last takes the final item and most takes all before it.
  • first, *middle, last = scores takes both ends and puts the inside in middle.
  • With a one-item list, others becomes an empty list []. The starred name can hold zero items.

The rules are short. You may use only one starred name per line, and the other names still need a value each. Both mistakes give real errors.

Two stars are ambiguousread-only
a, *b, *c = [1, 2, 3, 4]
What Python says
Traceback (most recent call last):
  File "<exec>", line 1
SyntaxError: multiple starred expressions in assignment
Not enough values for the plain namesread-only
first, *middle, last = [1]
What Python says
Traceback (most recent call last):
  File "<exec>", line 1, in <module>
ValueError: not enough values to unpack (expected at least 2, got 1)

The first is a SyntaxError, caught before the program even starts: with two stars, Python could not decide where one ends and the other begins. The second is a ValueError. The plain names first and last each need one item, and the list has only one.

Star in the other direction: spreading items out

The star also works when you build something. [*a, *b] spreads the items of a and b into one new list, and print(*items) passes each item as a separate argument.

Spreading with *
morning = ["Asha", "Ben"] evening = ["Chen"] everyone = [*morning, "Dana", *evening] print(everyone) print(*everyone) print(everyone)
Output
['Asha', 'Ben', 'Dana', 'Chen']
Asha Ben Dana Chen
['Asha', 'Ben', 'Dana', 'Chen']
Double star: merging dicts

Two stars ** do the same job for dicts, spreading every key: value pair. {**a, **b} builds a new dict from a, then b. When both have the same key, the later one wins. That is the standard way to say "start from the defaults, then apply my changes", and it does not touch either original.

Merging and overriding a dict
defaults = {"epochs": 10, "lr": 0.1, "shuffle": True} overrides = {"lr": 0.01} merged = {**defaults, **overrides} print(merged) print(defaults) tweaked = {**defaults, "epochs": 50} print(tweaked)
Output
{'epochs': 10, 'lr': 0.01, 'shuffle': True}
{'epochs': 10, 'lr': 0.1, 'shuffle': True}
{'epochs': 50, 'lr': 0.1, 'shuffle': True}
What Python does, line by line
  • **defaults spreads three pairs into the new dict.
  • **overrides spreads one pair. The key "lr" already exists, so its value is replaced by 0.01. Later wins.
  • defaults is unchanged, which proves the merge built a new dict.
  • {**defaults, "epochs": 50} mixes spreading and a written pair: a copy of defaults with one field changed.

Because {**d} builds a new dict, it is also a quick way to copy one, with the same shallow limits you met in section 4.4: inner lists or dicts are still shared. On newer Python versions defaults | overrides does the same as {**defaults, **overrides}. The double star also works in function calls: if settings = {"a": 1, "b": 2} then f(**settings) means f(a=1, b=2).

What are head and tail after head, *tail = "abc"?
head is "a" and tail is ["b", "c"]. A string unpacks into its characters, and the starred name is always a list.
For {**{"x": 1, "y": 2}, **{"y": 9}}, what is the result?
{"x": 1, "y": 9}. The second dict is spread last, so its "y" replaces the first.
Try it. Add a third dict called cli = {"epochs": 3} and merge all three in the order defaults, overrides, cli. Which value of epochs wins, and what happens if you change the order?
Recap
  • first, *rest = items gives the leftovers to the starred name, always as a list (possibly empty); only one star is allowed.
  • [*a, *b] builds a list from two lists, and f(*items) passes items as separate arguments.
  • {**a, **b} merges dicts into a new one; on a clash the later dict wins.
  • Merging copies only one layer: inner collections are still shared.
4.1 — Lists in Depth: Mutable, Ordered Collections

You've used lists since Chapter 1. A list is mutable — you can change it after creating it — and ordered — items keep the position you put them in. Its methods change the list in place and usually return None, which is a common source of confusion.

List methods — building and reordering a scores list
scores = [72, 85, 60, 91, 78] scores.append(95) # adds to the end — modifies scores in place print(scores) scores.remove(60) # removes the FIRST 60 it finds print(scores) scores.sort(reverse=True) # sorts in place, highest first print(scores) print(f'Top score: {scores[0]}') last = scores.pop() # removes AND returns the last item print(f'Removed: {last}, remaining: {scores}')
⚠️
Beginner trap: scores = scores.sort() sets scores to None! .sort() reorders the list in place and returns nothing. Just call scores.sort() on its own line — don't reassign it.
4.2 — Tuples: Immutable, Ordered Collections

A tuple looks like a list but uses () instead of [], and once created, it cannot be changed. Use a tuple when a value shouldn't ever be modified — coordinates, a fixed record, a return value made of several parts.

Tuples and unpacking
point = (3, 4) x, y = point # unpacking — x=3, y=4 print(f'x={x}, y={y}') # point[0] = 5 # <-- TypeError! tuples don't support item assignment # Unpacking a list of tuples in a loop — a very common ML pattern records = [('alice', 28, 'Hubli'), ('bob', 34, 'Pune')] for name, age, city in records: print(f'{name} is {age} from {city}')
💡
Why this matters in ML: a dataset row is often naturally a tuple — fixed fields, in a fixed order, that shouldn't change once loaded. Functions that return multiple values (like train_test_split() in sklearn) return them as a tuple.
4.3 — Dictionaries: Key-Value Pairs

A dict maps keys to values. It's the single most-used data structure in real ML code — model configs, API responses, and JSON files are all, fundamentally, dicts.

Building and reading a model config
model_config = {'name': 'ResNet50', 'epochs': 50, 'lr': 0.001} print(model_config['epochs']) # 50 — direct access by key print(model_config.get('batch_size', 32)) # 32 — .get() returns a default instead of crashing # model_config['batch_size'] # <-- this would raise a KeyError! the key doesn't exist yet model_config['batch_size'] = 32 # adding a new key is just an assignment for key, value in model_config.items(): print(f'{key}: {value}')
⚠️
Real bug that kills real ML pipelines: config['batch_size'] raises KeyError the instant that key is missing — and it WILL be missing sometimes, from an incomplete config file or an old dataset version. config.get('batch_size', 32) never crashes; it just uses your default.
4.4 — Sets: Unique, Unordered Collections

A set holds only unique values, with no guaranteed order, and supports fast mathematical operations: union, intersection, difference. Use it to deduplicate, or to compare two collections of things.

Comparing feature sets between two model versions
model_a_features = {'age', 'income', 'education', 'city'} model_b_features = {'age', 'income', 'job_title'} common = model_a_features & model_b_features # intersection — in BOTH only_a = model_a_features - model_b_features # difference — in A but not B combined = model_a_features | model_b_features # union — in EITHER # sorted() gives a stable, printable order — sets themselves have none print(f'Common: {sorted(common)}') print(f'Only in A: {sorted(only_a)}') print(f'All features: {sorted(combined)}') # A classic use: removing duplicate labels raw_labels = ['cat', 'dog', 'cat', 'bird', 'dog', 'cat'] unique_labels = set(raw_labels) print(f'Unique classes: {sorted(unique_labels)}')
4.5 — The Shape of Real Data: Lists of Dictionaries

This is the pattern you'll see everywhere once you start loading real datasets — CSV rows, API responses, JSON files. Each record is a dict, and the whole dataset is a list of them.

A tiny dataset, ML-shaped
candidates = [ {'name': 'Alice', 'skills': ['Python', 'SQL'], 'score': 0.92}, {'name': 'Bob', 'skills': ['Java'], 'score': 0.75}, ] for c in candidates: print(f"{c['name']}: {c['score']:.0%} — skills: {', '.join(c['skills'])}")
4.6 — Sorting Complex Structures

You already met sorted(..., key=lambda ...) in Chapter 3. It works exactly the same way on a list of dicts — the lambda just picks which field to sort by.

Ranking candidates by score
candidates = [ {'name': 'Alice', 'score': 0.92}, {'name': 'Bob', 'score': 0.75}, {'name': 'Carol', 'score': 0.81}, ] ranked = sorted(candidates, key=lambda c: c['score'], reverse=True) for i, c in enumerate(ranked, start=1): print(f'#{i}: {c["name"]} — {c["score"]:.0%}')
⭐
enumerate(ranked, start=1) — the optional start argument you haven't seen yet lets ranks begin at 1 instead of 0. Small thing, very commonly used for leaderboards and reports.
4.7 — Nested Dicts: The JSON Shape

Config files and API responses often nest a dict inside a dict. Accessing a nested value just means chaining the keys: data['train']['accuracy'].

A nested dataset-stats structure
dataset_stats = { 'train': {'size': 8000, 'accuracy': 0.91}, 'val': {'size': 1000, 'accuracy': 0.87}, 'test': {'size': 1000, 'accuracy': 0.85}, } for split, stats in dataset_stats.items(): print(f"{split}: {stats['size']} samples, {stats['accuracy']:.0%} accuracy") # Direct nested access — chain the keys: print(f"Test accuracy specifically: {dataset_stats['test']['accuracy']:.0%}")
4.8 — The collections Module: Counter, defaultdict, namedtuple

The built-in collections module gives you three specialized containers that solve extremely common data-wrangling problems in one line instead of five. You'll reach for these constantly once you're working with real, messy data.

Counter — counting things without a manual loop
from collections import Counter, defaultdict, namedtuple # Counter: count occurrences of each item — one line instead of a manual dict+loop skill_mentions = ['python', 'sql', 'python', 'ml', 'sql', 'python'] counts = Counter(skill_mentions) print(counts) # Counter({'python': 3, 'sql': 2, 'ml': 1}) print(counts.most_common(1)) # [('python', 3)] — the single most common item, as a list of tuples
defaultdict — grouping without checking "does this key exist yet?"
candidates = [ {'name': 'Alice', 'city': 'Hubli'}, {'name': 'Bob', 'city': 'Pune'}, {'name': 'Eve', 'city': 'Hubli'}, ] # Without defaultdict you'd need: if city not in groups: groups[city] = [] groups = defaultdict(list) # any missing key auto-creates an empty list for c in candidates: groups[c['city']].append(c['name']) print(dict(groups)) # {'Hubli': ['Alice', 'Eve'], 'Pune': ['Bob']}
namedtuple — a lightweight, immutable record with named fields
Candidate = namedtuple('Candidate', ['name', 'score']) alice = Candidate('Alice', 0.92) print(alice.name, alice.score) # access by NAME, not index — reads like a dict, immutable like a tuple print(alice) # Candidate(name='Alice', score=0.92) — a readable repr for free
⭐
When to reach for which: Counter for "how many of each," defaultdict for "group these by some key," namedtuple when a plain tuple's record[0]/record[1] access gets hard to read and you want record.name instead — without the overhead of a full class.
4.9 — Star- and Dict-Unpacking

Plain unpacking (x, y = point) requires an exact count match. Star-unpacking lets one variable soak up "everything else," and dict-unpacking (**) lets you merge or override dictionaries without writing a loop.

Star-unpacking — first, rest, and last
scores = [72, 85, 60, 91, 78] first, *rest = scores print(f'first={first}, rest={rest}') # first=72, rest=[85, 60, 91, 78] *most, last = scores print(f'most={most}, last={last}') # most=[72, 85, 60, 91], last=78 first, *middle, last = scores print(f'first={first}, middle={middle}, last={last}')
Dict-unpacking — merging and overriding configs
base_config = {'epochs': 50, 'lr': 0.001, 'batch_size': 32} overrides = {'lr': 0.01} # a per-experiment override # Later keys win — overrides['lr'] replaces base_config['lr'] merged = {**base_config, **overrides} print(merged) # {'epochs': 50, 'lr': 0.01, 'batch_size': 32}
💡
Why this matters in ML: {**default_config, **experiment_overrides} is the standard one-liner for "start from defaults, then apply just what this run changes" — you'll see it in almost every training script.
Chapter 4 Summary
  • Lists are mutable and ordered. Methods like .sort() and .append() change the list in place and return None — never reassign their result.
  • Tuples are immutable and ordered — use them for fixed records, and for unpacking multiple values at once.
  • Dicts map keys to values. Use .get(key, default) instead of [key] whenever the key might not exist.
  • Sets hold unique values and support & (intersection), - (difference), | (union).
  • Lists of dicts are the shape of real datasets. Nested dicts are the shape of real configs and JSON.
  • sorted(data, key=lambda x: x['field']) ranks any list of dicts by any field.
  • collections gives you Counter (count things), defaultdict (group things), and namedtuple (a lightweight named record). Star-unpacking (first, *rest = ...) and dict-unpacking ({**a, **b}) merge and split structures without a manual loop.
