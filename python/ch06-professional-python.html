6.1 — Virtual Environments and pip: One Toolbox Per Project

Before any new Python feature, one habit. So far every program you wrote used only what comes with Python. Real programs also use packages: code that other people wrote and shared, such as pandas or numpy. A tool called pip (Python's package installer) downloads a package and puts it where Python can find it. That sounds harmless until you have two projects on the same computer.

The problem: one shelf, two projects

Imagine Project A is a report script written last year. It needs version 1.0 of a package called tablelib. Today you start Project B, and it needs version 2.0 of the same package. Python keeps one copy of each package name per installation, like one shelf with one slot per name. Watch what happens if we model that shelf with a dictionary (the real thing is a folder, but the idea is identical).

One shared shelf: installing replaces the old version
installed = {} # ONE shelf for the whole computer def install(name, version): installed[name] = version # a new version REPLACES the old one install("tablelib", "1.0") # for Project A print("Project A needs 1.0. The shelf holds", installed["tablelib"]) install("tablelib", "2.0") # Project B asks for the newer one print("Project A needs 1.0. The shelf holds", installed["tablelib"])
Output
Project A needs 1.0. The shelf holds 1.0
Project A needs 1.0. The shelf holds 2.0
What Python does, line by line
  • installed = {} creates an empty shelf. There is exactly one, shared by everything.
  • install("tablelib", "1.0") puts the pair tablelib -> 1.0 on the shelf. Project A is happy.
  • install("tablelib", "2.0") writes to the same key. A dictionary key holds one value, so 2.0 replaces 1.0. Nothing warns you.
  • The last print shows 2.0. Project A, which was never touched, now runs against a version it was not written for and may crash. Programmers call this dependency hell.
The idea: give every project its own shelf

A virtual environment (people say venv) is a private folder that holds its own copy of the Python program and its own shelf of packages. Project A gets one, Project B gets another, and they cannot disturb each other. The analogy is a workshop where each job has its own toolbox on its own bench. Borrowing a screwdriver from another bench is not allowed, so nobody ever returns a bent one. Here is the same toy, with one shelf per project.

One shelf per project
shelves = {"project_a": {}, "project_b": {}} # a separate shelf each def install(project, name, version): shelves[project][name] = version install("project_a", "tablelib", "1.0") install("project_b", "tablelib", "2.0") print("A has:", shelves["project_a"]) print("B has:", shelves["project_b"])
Output
A has: {'tablelib': '1.0'}
B has: {'tablelib': '2.0'}
Try it. Add a second package, for example install("project_a", "plotlib", "3.1"), and print both shelves again. Project B's shelf must not change.
What a venv really looks like on disk

A venv is not magic. It is an ordinary folder, and you can open it. This is the real layout that python -m venv .venv creates (the name .venv is a convention; the leading dot hides the folder in most file browsers). Everything Python needs for this one project lives inside it.

Inside a project folder after: python -m venv .venv

|-- requirements.txt       <- the shopping list (you keep this)
`-- .venv/                 <- the private toolbox (created for you)
    |-- pyvenv.cfg         <- a note: "made from /usr/bin python"
    |-- bin/               <- commands (Scripts\ on Windows)
    |   |-- python         <- this project's own python
    |   |-- pip            <- this project's own pip

The two parts to remember: bin/ holds the commands, site-packages/ holds the installed packages. Delete .venv and you lose only the toolbox, never your own code.

  • source .venv/bin/activate runs a small script that puts .venv/bin at the front of your shell's search path (the list of folders it looks in for commands). That is all activation is. The (.venv) in your prompt is a reminder that it is on.

The file you share: requirements.txt

You send the shopping list, and they build a fresh toolbox from it: python3 -m venv .venv, activate, then pip install -r requirements.txt (-r means "read the list from this file"). Commit requirements.txt to git and keep .venv out of git.

Common mistake: installing without a venv

The most common slip is forgetting to activate, so pip tries to install into the system Python. Many modern Linux systems refuse, on purpose, to protect the tools the operating system itself uses. This is the real message from a lab machine.

Read it as a friendly instruction, not a failure: the last two lines say exactly what to do. Create a venv, activate it, and run the same pip install again. On systems that do not refuse, the install silently goes global, which is worse, because the mess builds up unseen.

Two projects both use pandas, but different versions. Where do the two copies live?
In two different site-packages folders, one inside each project's .venv. That is the whole point: each project has its own shelf, so the versions never fight.
You delete the .venv folder by accident. What did you lose, and how do you get it back?
Only the installed packages and the private Python copy. Your own code is untouched. Rebuild it with python3 -m venv .venv, activate it, and pip install -r requirements.txt. This is why the shopping list is kept in git.
Recap
  • A package is shared code; pip installs it; without isolation two projects can demand different versions of one name.
  • A virtual environment is a folder (.venv) with its own Python and its own site-packages shelf.
  • Activating only puts .venv/bin first on your search path, so python and pip mean this project's copies.
  • pip freeze > requirements.txt writes the shopping list; pip install -r requirements.txt rebuilds the environment anywhere.
6.2 — Custom Exceptions: Errors That Have a Name

From here the chapter follows one small program that checks score records, like {"name": "Asha", "score": 0.92}. Each section adds one professional tool to it. We start with what happens when a record is bad. You have seen Python stop with errors such as ValueError. An exception is Python's way of saying "something went wrong here": it stops the normal flow and travels backwards up the chain of function calls looking for code that will deal with it.

The problem: two different mistakes, one label

Suppose a function reads a score from text. There are two ways it can fail. The text may not be a number at all ("abc"), or it may be a number outside the allowed range 0 to 1 ("1.7"). Both are reasonably called ValueError, so the caller cannot tell them apart.

Two different problems, both ValueError
def read_score(text): value = float(text) # "abc" fails here if not 0 <= value <= 1: raise ValueError("score must be between 0 and 1") # "1.7" fails here return value for text in ["abc", "1.7"]: try: read_score(text) except ValueError as error: print("Problem:", error)
Output
Problem: could not convert string to float: 'abc'
Problem: score must be between 0 and 1

To react differently (ask the user to retype the first, clamp the second) you would have to inspect the message text, which is fragile: fix a typo in the message and your code silently changes behaviour. We want the type of the error to carry the meaning.

Quick refresher: try / except

A try block says "attempt this". If a line inside raises an exception, Python skips the rest of the block and jumps to the matching except. If nothing goes wrong, the except is skipped. Either way the program continues afterwards.

try / except in one picture
try: print("step 1") number = int("abc") # raises ValueError right here print("step 2 (never reached)") except ValueError as error: print("handler ran:", error) print("the program keeps going")
Output
step 1
handler ran: invalid literal for int() with base 10: 'abc'
the program keeps going
The idea: give your problem its own name

A custom exception is a new error type you define yourself. It is a class that inherits from Exception (inheritance from OOP Part 3: the new class *is-a* Exception). You need no body at all, because the name is the message. Think of the coloured tags in a hospital: a red tag means something specific, and the staff know who to call without reading a long note.

The smallest custom exception
class ScoreOutOfRange(Exception): pass # the name alone carries the meaning try: raise ScoreOutOfRange("1.7 is not between 0 and 1") except ScoreOutOfRange as error: print("Caught:", error) print("Its type:", type(error).__name__)
Output
Caught: 1.7 is not between 0 and 1
Its type: ScoreOutOfRange
What Python does, line by line
  • class ScoreOutOfRange(Exception): pass builds a new type. It has every ability of a normal exception because it inherits them.
  • raise ScoreOutOfRange("...") creates an object of that class, with the text stored inside, and starts the exception travelling.
  • Python leaves the try block immediately and compares the exception's type with the except line. It is a ScoreOutOfRange, so the handler runs.
  • error is the exception object. Printing it shows the text you passed in. type(error).__name__ gives the class name as a string.
Using it: distinct problems, distinct handlers

Now the two mistakes from the start can be different types, and the caller chooses what to catch. To keep the family organised, define one base class for all validation problems and let the specific ones inherit from it. Then code that only cares that *something* failed validation can catch the parent, and code that cares about one case can catch the child. The specific error can also carry data, stored by __init__.

A small family of exceptions
          Exception          (Python's own base class)
              |
       ValidationError       (ours: "record not acceptable")
        /            \
ScoreOutOfRange   MissingName
(has .name, .score)

except ScoreOutOfRange -> catches only the left child
except ValidationError -> catches BOTH children (and itself)
An except clause for a class also catches every class below it in the family tree.
A base class, two children, and extra data
class ValidationError(Exception): """Base class: every 'record is not acceptable' problem.""" class ScoreOutOfRange(ValidationError): def __init__(self, name, score): super().__init__(f"{name}: score {score} is not between 0 and 1") self.name = name self.score = score class MissingName(ValidationError): pass def validate(record): if not record.get("name"): raise MissingName("record has no name") if not 0 <= record["score"] <= 1: raise ScoreOutOfRange(record["name"], record["score"]) return record records = [{"name": "Asha", "score": 0.9}, {"name": "Ben", "score": 1.4}, {"name": "", "score": 0.5}] for record in records: try: validate(record) print("ok:", record["name"]) except ScoreOutOfRange as error: print("out of range, the bad score was", error.score) except ValidationError as error: print("some other validation problem:", error)
Output
ok: Asha
out of range, the bad score was 1.4
some other validation problem: record has no name
What Python does, line by line
  • Asha: validate passes both checks and returns. The try block finishes, so no except runs and ok: Asha prints.
  • Ben: the score check fails and raise ScoreOutOfRange("Ben", 1.4) runs. Its __init__ calls super().__init__(...) to store the message, and keeps name and score as attributes.
  • Python checks the except clauses from top to bottom. ScoreOutOfRange matches the first, so it runs and reads error.score.
  • The third record has an empty name, so MissingName is raised. It is not a ScoreOutOfRange, so the first clause is skipped. It is a ValidationError through inheritance, so the second clause catches it.
Common mistakes, with the real messages

Mistake 1: forgetting to inherit from Exception. A class that inherits from nothing is an ordinary class, and Python refuses to raise it.

Not an exception classread-only
class BadScore: pass raise BadScore()
What Python says
Traceback (most recent call last):
  File "<exec>", line 4, in <module>
TypeError: exceptions must derive from BaseException

Read the last line first: exceptions must derive from BaseException. "Derive" means inherit. Add (Exception) after the class name and the error disappears.

Mistake 2: putting the parent except first. Nothing crashes, which is exactly why it is dangerous. Python takes the first matching clause, and the parent matches everything, so the specific handler below it can never run.

The wrong order silently hides the specific handler
class ValidationError(Exception): pass class MissingName(ValidationError): pass try: raise MissingName("no name") except ValidationError: print("generic handler ran") except MissingName: print("specific handler ran (you will never see this)")
Output
generic handler ran

The rule: most specific first, most general last. Swap the two clauses and re-run to see the difference.

Mistake 3: catching too much. except Exception: catches nearly every error, including your own typos. Here the variable name is misspelled, which is a bug, but the handler hides it and reports a false story.

An over-broad except swallows a real bug
def average(values): total = sum(values) return totl / len(values) # typo: 'totl' instead of 'total' try: print(average([1, 2, 3])) except Exception: print("could not compute the average")
Output
could not compute the average

The real problem is a NameError from the typo, and you would never know. Catching your own named exception avoids this: a typo raises NameError, which your except ScoreOutOfRange correctly ignores, so the bug shows up loudly. That is the practical payoff of naming errors.

What happens if nobody catches it? Then the exception travels all the way up and Python prints a traceback: the chain of calls, ending with the error. Read it from the bottom.

An uncaught custom exceptionread-only
class ScoreOutOfRange(Exception): pass def validate(score): if score > 1: raise ScoreOutOfRange(f"{score} is above 1") return score validate(1.7)
What Python says
Traceback (most recent call last):
  File "<exec>", line 9, in <module>
  File "<exec>", line 6, in validate
ScoreOutOfRange: 1.7 is above 1

The bottom line names the type and the message. The lines above show where it happened (validate, line 6) and who called it (<module>, line 9). A good exception name plus a clear message usually tells you the fix without opening the code.

Which one is better for a caller who wants to handle a bad score differently from a missing name: two ValueErrors with different messages, or two custom exception classes? Why?
Two custom classes. The caller can write one except clause per class. With two ValueErrors the caller would have to read the message text to tell them apart, and any rewording of a message would break that code.
You write except ValidationError: above except MissingName: where MissingName inherits from ValidationError. Which handler runs when a MissingName is raised?
The ValidationError one, because a MissingName is a ValidationError and Python uses the first matching clause. Put the specific handler first.
Try it. In the family example, add a class BlankScore(ValidationError): pass, raise it when record["score"] is None, and add a record with "score": None to see the general handler catch it.
Recap
  • An exception's type should say what went wrong; define your own with class Name(Exception): pass.
  • Group related errors under one base class: except Parent catches every child too.
  • Put the most specific except first; Python uses the first one that matches.
  • An uncaught exception ends in a traceback whose last line is TypeName: message. Never hide bugs with a broad except Exception:.
6.3 — Context Managers: Cleanup That Cannot Be Forgotten

Some actions come in pairs: open a file, close it. Lock a door, unlock it. Start a timer, stop it. The second half is cleanup, and it is easy to skip by accident. In this section you will see why, meet the fix that Python offers (the with statement), and then build your own.

The problem: an error jumps over the cleanup

Our score program prints "open report" when it starts and "close report" when it ends. Look at what happens when a bad value appears in the middle. Dividing by a score of 0 raises ZeroDivisionError, and Python leaves the function on the spot.

Cleanup skipped when an error strikes
def summarise(scores): print("open report") total = 0 for score in scores: total += 100 / score # a score of 0 raises ZeroDivisionError print("close report") # never reached if the loop fails return total try: summarise([5, 0]) except ZeroDivisionError: print("error was handled by the caller")
Output
open report
error was handled by the caller
What Python does, line by line
  • summarise([5, 0]) prints open report, then starts the loop.
  • score = 5 works: 100 / 5 is 20. score = 0 fails: dividing by zero raises ZeroDivisionError.
  • Python abandons the function immediately. The line print("close report") is skipped, so the report is left open.
  • The caller's except handles the error, and the program carries on with a report that was never closed. In real programs that means a file left open, a lock still held, or a connection never returned.

The classic fix is try / finally. Code in a finally block runs no matter what: after success, after an error, even after a return.

try / finally always runs the cleanup
def summarise(scores): print("open report") try: total = 0 for score in scores: total += 100 / score return total finally: print("close report") # runs on success AND on failure try: summarise([5, 0]) except ZeroDivisionError: print("error was handled by the caller")
Output
open report
close report
error was handled by the caller

That works, but it has a weakness: every place that opens something must remember to write the same try / finally dance. One forgotten finally and you are back to the bug.

The idea: the door that closes itself

A context manager is an object that knows how to set something up and how to clean it up, so you never have to write the cleanup yourself. You use it with the with statement. Picture a door with an automatic closer: you walk through (setup), do your business, and the door shuts behind you (cleanup) even if you trip on the way out. You have used one before without the name.

with open(...) closes the file for you
with open("scores.txt", "w") as f: f.write("Asha,92\n") print("inside the with block, closed?", f.closed) print("after the with block, closed?", f.closed)
Output
inside the with block, closed? False
after the with block, closed? True

f.closed tells you whether the file is closed. It is False inside the block and True right after, and you never wrote f.close(). The with statement did it, and would have done it even if an error had stopped the block halfway.

Writing your own with @contextmanager

Python makes it easy to build your own from an ordinary function. You add the @contextmanager decorator (a decorator is a label placed above a function that changes how it behaves; section 6.5 explains how they work, so for now just copy the shape) and put one yield in the middle. Think of yield as a bookmark: the function stops at that line, hands control to the body of the with block, and when the block ends Python comes back and continues from the bookmark.

The smallest useful context manager
from contextlib import contextmanager @contextmanager def stage(name): print("START", name) # setup: runs before the block try: yield # <- the with-block runs here finally: print("END", name) # cleanup: always runs after with stage("validation"): print("checking the records") print("after the with statement")
Output
START validation
checking the records
END validation
after the with statement
What happens around the yield
  with stage("validation"):          stage() function
  ---------------------------        ---------------------------
                                     print("START validation")
                                     try:
       (paused here)  <------------      yield
  print("checking the records")   -->  (resumes here when block ends)
                                     finally:
                                         print("END validation")
  print("after the with ...")
The function is split in two by yield: everything above it is the entrance, everything below it is the exit. The with body runs in the gap.
What Python does, line by line
  • with stage("validation"): calls stage("validation"). Because of @contextmanager, the function does not run yet; Python sets it up to run in two halves.
  • Python enters the context: it runs stage from its first line up to the yield. That prints START validation.
  • At the yield, stage pauses and the indented with body runs: checking the records prints.
  • When the body finishes (normally or by an error), Python resumes stage after the yield. The finally block prints END validation.
  • Only then does the line after the with run, printing after the with statement.
The sad path: an error inside the block

The whole point is that cleanup still happens when the body fails. Here the body raises an error. Watch that END still prints, and that the error is not swallowed: it continues upward to the caller's except.

Cleanup runs even when the body fails
from contextlib import contextmanager @contextmanager def stage(name): print("START", name) try: yield finally: print("END", name) try: with stage("validation"): print("checking the records") raise ValueError("bad record found") print("this line is skipped") except ValueError as error: print("caller saw:", error)
Output
START validation
checking the records
END validation
caller saw: bad record found

The order is the lesson: START, the body, END, and only then the caller's message. The exit half runs first as the exception passes through, then the exception carries on.

Handing a value to the block with yield

yield can also pass an object to the with body, and as name receives it. This is exactly what open does when it gives you the file object.

yield hands a value to "as"
from contextlib import contextmanager @contextmanager def collect_problems(): problems = [] try: yield problems # the block receives this list as "found" finally: print("problems collected:", len(problems)) with collect_problems() as found: found.append("Ben: score 1.4") found.append("no name") print("the list outlives the block:", found)
Output
problems collected: 2
the list outlives the block: ['Ben: score 1.4', 'no name']
Common mistakes, with the real messages

Mistake 1: leaving out try / finally. It looks fine, and it works until the first error. Then the cleanup lines are skipped, exactly like the very first example.

No try/finally: the END line is lost on error
from contextlib import contextmanager @contextmanager def stage(name): print("START", name) yield print("END", name) # skipped if the body raises try: with stage("validation"): raise ValueError("boom") except ValueError: print("caller handled it, but END never printed")
Output
START validation
caller handled it, but END never printed

Mistake 2: forgetting the @contextmanager line. Without it, stage is a plain generator function, and with does not know what to do with it.

Missing @contextmanagerread-only
def stage(name): print("START", name) yield print("END", name) with stage("validation"): print("body")
What Python says
Traceback (most recent call last):
  File "<exec>", line 6, in <module>
TypeError: 'generator' object does not support the context manager protocol

The message says the object does not follow the context manager protocol, meaning the two set-up-and-tear-down hooks that with looks for (section 6.4 names them). The fix is to add @contextmanager above the def.

Mistake 3: two yields. A context manager must pause exactly once.

Two yieldsread-only
from contextlib import contextmanager @contextmanager def two(): yield 1 yield 2 with two(): print("body")
What Python says
body
Traceback (most recent call last):
  File "<exec>", line 8, in <module>
  File "/lib/python312.zip/contextlib.py", line 149, in __exit__
    raise RuntimeError("generator didn't stop")
RuntimeError: generator didn't stop

Python resumed the function after the first yield expecting it to finish, but it paused again. One yield, one pause, one cleanup.

What does with stage("x"): do with the lines above the yield and the lines below it?
The lines above run first, as setup, before the with body. The lines below run after the body finishes, as cleanup, even if the body raised an error (provided they are inside a finally).
Why is try/finally around the yield important?
Without it, an exception in the with body is thrown into the function at the yield, and the lines after the yield are skipped, so the cleanup never runs. finally guarantees it does.
Try it. Change the body of the first stage example to print(1 / 0). Predict the order of the three messages (START, END, and the error) before you run it.
Recap
  • Cleanup that sits after risky code is skipped when an error jumps out; try / finally guarantees it.
  • A context manager bundles setup and cleanup; the with statement runs both for you.
  • With @contextmanager, code above the single yield is the entrance, code below it (inside finally) is the exit.
  • yield value hands something to the as name. Missing @contextmanager, or two yields, gives a clear TypeError or RuntimeError.
6.4 — Class-Based Context Managers: __enter__ and __exit__

The @contextmanager function from 6.3 is short, but it has a limit: everything lives inside one function that runs once. Sometimes you want a real object that keeps facts about the visit (how many problems it saw, when it started) and has methods you can call inside the block. For that, Python lets any class become a context manager.

The problem: state and decisions

Imagine you want a helper that counts problems during validation and, when the block ends, prints a summary, and also decides whether some errors should be quietly tolerated. With the function style you can fake the counting with a list (as in 6.3), but the object is awkward to reuse and there is no natural place to decide about the error that ended the block. A class has both: attributes for the state, and a hook that receives the error.

The idea: check-in and check-out

Think of a hotel front desk. On arrival you check in (__enter__): the desk hands you a key. On departure you check out (__exit__): the desk collects the key, and asks whether anything was broken during your stay, so it can decide how to respond. Any class that defines these two special methods (dunder methods, like the ones in OOP Part 2) can be used after with. Together the pair is called the context manager protocol.

What with Stage("validation") as s: really does
1. build the object     obj = Stage("validation")
2. check in             s = obj.__enter__()  ("as" gets this)
3. run the body         ... your code, may use s ...
4. check out, ALWAYS    obj.__exit__(exc_type, exc_value, tb)

No error in the body:  the three arguments are None, None, None
Error in the body:     they describe the error. If __exit__
                       returns True the error is swallowed;
                       False (or nothing) lets it continue up.
The smallest class-based context manager
class Stage: def __init__(self, name): self.name = name def __enter__(self): print("START", self.name) return self # this becomes the "as" value def __exit__(self, exc_type, exc_value, traceback): print("END", self.name) return False # False: do not hide any error with Stage("validation") as s: print("checking the records, stage is called", s.name)
Output
START validation
checking the records, stage is called validation
END validation
What Python does, line by line
  • Stage("validation") runs __init__, which stores the name. Nothing is printed yet.
  • with calls __enter__. It prints START validation and returns self, so s now refers to the Stage object.
  • The body runs. It can use s, and it does: s.name is validation.
  • The body ends, and with calls __exit__ with three Nones (no error). It prints END validation.
  • __exit__ returned False, which only matters when an error happened. Here it changes nothing.
What __exit__ receives

The three parameters of __exit__ describe an error if there was one: its class, its value (the exception object, whose text you can print), and the traceback. If the body finished cleanly, all three are None. Let us look at both cases with a class that only reports what it receives.

Looking at the three arguments
class Peek: def __enter__(self): return self def __exit__(self, exc_type, exc_value, traceback): print("exit got:", exc_type, "|", exc_value, "| traceback given:", traceback is not None) return False with Peek(): print("body 1 runs fine") try: with Peek(): raise ValueError("bad record") except ValueError: print("caller saw the error too")
Output
body 1 runs fine

exit got: <class 'ValueError'> | bad record | traceback given: True
caller saw the error too
Swallowing an error on purpose: return True

If __exit__ returns True, Python treats the error as handled and the program continues after the with block as if nothing happened. That is powerful and risky, so a careful manager swallows only the errors it understands. This one tolerates our own ValidationError family from 6.2 and lets everything else through.

Tolerate only one kind of error
class ValidationError(Exception): pass class Tolerate: def __enter__(self): return self def __exit__(self, exc_type, exc_value, traceback): if exc_type is not None and issubclass(exc_type, ValidationError): print("tolerated:", exc_value) return True # swallow it return False # anything else continues upward with Tolerate(): raise ValidationError("Ben: score 1.4") print("execution continues after the with block") try: with Tolerate(): print(10 / 0) except ZeroDivisionError: print("a different error was NOT swallowed")
Output
tolerated: Ben: score 1.4
execution continues after the with block
a different error was NOT swallowed
What Python does, line by line
  • The first body raises ValidationError. Python calls __exit__ with that class, that object and a traceback.
  • issubclass(exc_type, ValidationError) is True (a class is a subclass of itself), so we print a note and return True. The error vanishes, and the next line after the with runs.
  • The second body raises ZeroDivisionError. This time the issubclass test is False, so __exit__ returns False.
  • Returning False lets the error keep travelling. The outer try catches it and prints its message.
A class earns its keep when it remembers things

Here the object counts problems during the block and reports at the end. Because it is an object, you can still read its attributes after the block is over.

State that survives the block
class Tally: def __init__(self): self.problems = 0 def __enter__(self): return self def add(self, note): self.problems += 1 print("problem noted:", note) def __exit__(self, exc_type, exc_value, traceback): print("summary:", self.problems, "problem(s)") return False with Tally() as tally: tally.add("Ben: score 1.4") tally.add("missing name") print("after the block, tally.problems is still", tally.problems)
Output
problem noted: Ben: score 1.4
problem noted: missing name
summary: 2 problem(s)
after the block, tally.problems is still 2

Mistake 1: defining only one of the two methods. with needs both. Python tells you which is missing, in brackets at the end.

Mistake 2: the wrong parameters on __exit__. Python passes three arguments besides self. Forgetting them gives an error that counts them for you.

__exit__ without the three parametersread-only
class Stage: def __enter__(self): return self def __exit__(self): print("bye") with Stage(): print("body")

Mistake 3: forgetting return self in __enter__. The with still runs, but as receives None, because a function with no return gives back None.

When does Python call __exit__, and what are its three arguments if the body finished without an error?
Always: when the body ends normally, after an error, or after a return inside the block. With no error the three arguments are all None.

  • __exit__(self, exc_type, exc_value, traceback) always runs; all three are None when there was no error.

  • Use a class when the manager keeps state or must decide about the error; use @contextmanager for quick, stateless wraps.
6.5 — Decorators, Step 1: Functions Are Values

Decorators have a reputation for being confusing. The reason is that they need three smaller ideas at once, and most explanations show all three in one go. We will go slowly: in 6.5 and 6.6 we learn the two ideas underneath, in 6.7 we build a decorator, in 6.8 we polish it, and in 6.9 we add settings to it. If you get lost, go back one section. Each step is small.

The problem: the same extra lines, everywhere

Our validator has two functions, and we want a trace line printed each time either one is called, so we can see what the program is doing. The obvious way is to paste the lines into both.

The copy-paste version
def validate(record): print("calling validate") # trace line (copy 1) return record["score"] >= 0 def total(a, b): print("calling total") # trace line (copy 2) return a + b print(validate({"name": "Asha", "score": 0.9})) print(total(2, 3))
Output
calling validate
True
calling total
5

It works, but with fifty functions you would edit fifty bodies, and to change the wording you would edit them all again. We would like to say the trace behaviour once and attach it to any function from outside, without touching the function's own code. To do that, we first need to see that Python lets us treat a function like any other piece of data.

The idea: a function is a value you can carry around

In Chapter 3 you saw that def builds a function object and attaches a name to it. The name is just a label, like a sticky note on a box. That means you can stick a second label on the same box, put the box in a list, hand the box to another function, or return it from one. Writing the name without parentheses refers to the box. Writing it with parentheses opens the box and runs it.

One function, two labels
def say_hello(): print("hello") greet = say_hello # no parentheses: a second label, NOT a call print("type:", type(greet).__name__) print("same box:", greet is say_hello) greet() # parentheses: run it say_hello()
Output
type: function
same box: True
hello
hello
What Python does, line by line
  • def say_hello() builds the function object and attaches the label say_hello. Nothing prints, because defining never runs the body.
  • greet = say_hello has no parentheses, so Python does not run anything. It looks up the object behind say_hello and attaches a second label greet to it.
  • type(greet).__name__ says function; greet is say_hello says True, the two labels point at exactly the same object.
  • greet() and say_hello() each run the same body, so hello is printed twice.
Handing a function to another function

If a function is a value, it can be an argument. This is how sorted(names, key=len) works: you hand len (not len(...)) to sorted, and sorted calls it for you. Here we write our own.

A function that receives a function
def apply_twice(action, value): once = action(value) # 'action' is whichever function we were given return action(once) def add_ten(n): return n + 10 def shout(text): return text.upper() + "!" print(apply_twice(add_ten, 5)) print(apply_twice(shout, "hi"))
Output
25
HI!!

apply_twice has no idea whether it was given add_ten or shout. It just calls whatever is in action. That is the first ingredient of a decorator: a function that takes a function.

Handing a function back

A function can also return a function. The second ingredient is a function that builds a new function and gives it back.

A function that returns a function
def make_greeter(greeting): def greeter(name): return greeting + ", " + name return greeter # returns the box, without calling it hello = make_greeter("Hello") morning = make_greeter("Good morning") print(hello("Asha")) print(morning("Ben"))
Output
Hello, Asha
Good morning, Ben

Notice something odd. greeter uses the variable greeting, but make_greeter finished running before hello("Asha") was called. How does hello still know the greeting? That is exactly the question of the next section. For now, just notice that it works.

Common mistake: calling when you meant to refer

Adding parentheses by habit is the classic slip. greet = say_hello() does not attach a label. It runs say_hello and labels its result. That result is None, because the function does not return anything.

Parentheses that should not be thereread-only
def say_hello(): print("hello") greet = say_hello() # runs it now, greet becomes None greet()
What Python says
hello
Traceback (most recent call last):
  File "<exec>", line 5, in <module>
TypeError: 'NoneType' object is not callable

The output hello appears first (from the accidental call), then the error. Read the error as: "you tried to call something, but it is None, and None cannot be called". "Callable" means "can be followed by parentheses". Whenever you see 'NoneType' object is not callable, look for a name that should have been a function but is None, often from stray parentheses or a missing return.

What is the difference between greet = say_hello and greet = say_hello()?
The first attaches another label to the same function object. The second runs the function immediately and labels whatever it returns, which is None if the function has no return.
In sorted(names, key=len), why is it len and not len()?
sorted needs the function itself, to call it once per item. len() would run right now with no argument and fail. Passing len hands over the box; sorted opens it later.
Try it. Make a list steps = [add_ten, shout] and loop for step in steps: printing step.__name__. You just stored functions in a list.
Recap
  • def creates a function object; the name is only a label. f refers to it, f() runs it.
  • A function can be passed to another function and returned from one.
  • These are the two ingredients of a decorator: something that takes a function, and something that hands a function back.
  • 'NoneType' object is not callable usually means stray parentheses or a missing return.
6.6 — Decorators, Step 2: Closures, Functions That Remember

At the end of the last section a small mystery was left: hello("Asha") still knew the word "Hello", even though make_greeter had already finished. Chapter 3 introduced this as a closure. Here we look at it again slowly, because it is the engine inside every decorator.

The problem: the outer function is gone, the value is still needed

When a function finishes, its local variables normally disappear, like notes written on a whiteboard that gets wiped. But the inner function was written inside the outer one and refers to one of those variables. If Python wiped the whiteboard, greeter would break the moment it was called. Python avoids that with a simple rule.

The idea: the inner function packs a backpack

When an inner function is created and uses a variable from the function around it, Python attaches a small backpack to the inner function and puts a copy of the reference to that variable inside it. The backpack travels with the function wherever it goes. Two calls of the outer function make two inner functions, each with its own backpack.

Each inner function carries its own backpack
def make_multiplier(factor): def multiply(x): return x * factor # 'factor' comes from the outer function return multiply double = make_multiplier(2) triple = make_multiplier(3) print(double(10), triple(10)) print("double's backpack holds:", double.__closure__[0].cell_contents) print("triple's backpack holds:", triple.__closure__[0].cell_contents)
Output
20 30
double's backpack holds: 2
triple's backpack holds: 3
Two calls, two backpacks
make_multiplier(2)  builds  double
                            = [ multiply ] + backpack { factor: 2 }
make_multiplier(3)  builds  triple
                            = [ multiply ] + backpack { factor: 3 }

make_multiplier has finished and its whiteboard is wiped, but
each multiply function still carries its own factor.
__closure__ is the real name of the backpack; .cell_contents opens one pocket.
What Python does, line by line
  • make_multiplier(2) runs. Inside it, multiply is defined and notices that it uses factor, so Python records factor = 2 in a backpack attached to multiply.
  • return multiply hands the function back and make_multiplier finishes. Its normal local variables are gone, but the backpack survives inside the returned function.
  • The same happens for make_multiplier(3), producing a different function with a different backpack. The two do not interfere.
  • double(10) runs x * factor with x = 10 and factor taken from double's backpack: 20. triple(10) gives 30.
Changing a remembered value needs nonlocal

A closure can also change what is in its backpack, but Python needs to be told. Without the word nonlocal, an assignment inside the inner function is read as making a brand-new local variable, which does not exist yet at the moment you try to add to it.

Assigning without nonlocalread-only
def make_counter(): count = 0 def step(): count = count + 1 # Python sees an assignment: 'count' is local here return count return step counter = make_counter() counter()
What Python says
Traceback (most recent call last):
  File "<exec>", line 9, in <module>
  File "<exec>", line 4, in step
UnboundLocalError: cannot access local variable 'count' where it is not associated with a value

Read it as: "inside step, count is being assigned, so it is a local variable, but you read it before giving it a value." The fix is one line: write nonlocal count first, which tells Python "this name lives in the outer function's backpack".

nonlocal lets the closure update its backpack
def make_counter(): count = 0 def step(): nonlocal count count = count + 1 return count return step counter = make_counter() print(counter(), counter(), counter()) other = make_counter() print("a second counter starts fresh:", other())
Output
1 2 3
a second counter starts fresh: 1

Every decorator that keeps a tally (calls made, results cached) uses this pattern. Now we have both ingredients: functions can be passed around, and an inner function remembers what it was built with.

After double = make_multiplier(2) runs, the function make_multiplier has finished. Where is the number 2 stored?
In double's backpack, its __closure__. Python keeps the variable alive for exactly as long as a function that uses it exists.
Why do two counters made with make_counter() not share their count?
Each call to make_counter() creates a new count variable and a new inner function with its own backpack pointing at that variable.
Try it. Print double.__closure__[0].cell_contents before and after calling double(10). The backpack does not change when you call the function, because multiply only reads factor.
Recap
  • An inner function can use variables from the function around it.
  • Python keeps those variables alive in a closure (a backpack) attached to the inner function.
  • Each call of the outer function builds a new inner function with its own backpack.
  • To reassign a remembered variable, declare it with nonlocal; otherwise you get UnboundLocalError.
6.7 — Decorators, Step 3: Your First Decorator

We now have the two ingredients, so the recipe is short. A decorator is a function that takes a function, builds a new function around it (using a closure to remember the original), and returns the new one. The analogy is a gift wrapper. The gift inside is unchanged, but the wrapper adds something on the way in and out.

Building it by hand, no special syntax

Here is the trace idea from 6.5 as a decorator. The wrapper prints a line, calls the original function, prints the result, and passes it on. We apply it by hand first, so nothing is hidden.

A decorator applied by hand
def log_call(func): def wrapper(*args, **kwargs): print("calling", func.__name__, "with", args, kwargs) result = func(*args, **kwargs) print("got back", result) return result return wrapper def add(a, b): return a + b add = log_call(add) # replace the label 'add' with the wrapped version print(add(3, 5))
Output
calling add with (3, 5) {}
got back 8
8

*args, **kwargs (from Chapter 3) means "accept any positional and keyword arguments and pass them all along". It lets one wrapper fit a function with any parameters.

The @ syntax is a shortcut for exactly that line

Writing add = log_call(add) under every function is tedious, so Python offers a shorthand: put @log_call on the line above the def. It means precisely the same thing. Nothing more happens.

@log_call above def add(...) == add = log_call(add) below it
BEFORE decoration          AFTER decoration

add --> [ original add ]   add --> [ wrapper ]
                                      |
                                      +-- backpack: func =
                                          [ original add ]

The label "add" now points at the wrapper. The original still
exists, but only the wrapper (via its backpack) can reach it.
Decoration time versus call time

This is the part that trips almost everyone, so let us make it visible. There are two different moments. Decoration time is when Python reads the def line and applies the decorator, exactly once. Call time is every later moment you call the function. The prints below carry labels so you can see which is which.

Two moments, clearly labelled
def log_call(func): print("[decoration time] wrapping", func.__name__) def wrapper(*args, **kwargs): print("[call time] calling", func.__name__, "with", args) result = func(*args, **kwargs) print("[call time] result is", result) return result return wrapper print("about to define add") @log_call def add(a, b): return a + b print("definition finished; add is now called:", add.__name__) print("about to call add twice") add(3, 5) add(10, 20)
Output
about to define add
[decoration time] wrapping add
definition finished; add is now called: wrapper
about to call add twice
[call time] calling add with (3, 5)
[call time] result is 8
[call time] calling add with (10, 20)
[call time] result is 30
What Python does, in order
  • def log_call(func): builds the decorator function. The body does not run.
  • print("about to define add") runs.
  • Python reaches @log_call and def add. It builds the original add function object, then immediately runs log_call(add). This is decoration time: [decoration time] wrapping add prints, wrapper is built (its backpack holds func = the original add), and log_call returns it.
  • Python attaches the label add to what log_call returned, the wrapper. The original is no longer reachable by name. That is why add.__name__ says wrapper.
  • add(3, 5) is call time. It runs wrapper(3, 5): prints the call line, calls the remembered original with the same arguments, prints [call time] result is 8, and returns 8.
  • add(10, 20) does step 5 again. The decoration line is not printed a second time, because decoration happened once, when the def was read.

Keep this picture: decoration happens once, at definition, and swaps the label. Calling happens many times and goes through the wrapper.

Common mistakes, with the real messages

Mistake 1: forgetting return wrapper. The decorator then returns None, so the label add is attached to None.

The decorator forgets to return the wrapperread-only
def log_call(func): def wrapper(*args, **kwargs): return func(*args, **kwargs) # no "return wrapper" here @log_call def add(a, b): return a + b print(add(3, 5))
What Python says
Traceback (most recent call last):
  File "<exec>", line 10, in <module>
TypeError: 'NoneType' object is not callable

Same message as in 6.5, and the same reading: add is None now. Whenever a decorated function suddenly "is not callable", check that the decorator returns something.

Mistake 2: forgetting return result inside the wrapper. Nothing crashes. The wrapper runs the original but throws its answer away, so every call quietly returns None.

The wrapper swallows the result
def log_call(func): def wrapper(*args, **kwargs): result = func(*args, **kwargs) print("done") # missing: return result return wrapper @log_call def add(a, b): return a + b print("add(3, 5) gives:", add(3, 5))
Output
done
add(3, 5) gives: None

Mistake 3: a wrapper that does not accept the arguments. If the wrapper is written def wrapper():, it cannot receive what the caller passes.

The wrapper has no parametersread-only
def log_call(func): def wrapper(): return func() return wrapper @log_call def add(a, b): return a + b add(3, 5)
What Python says
Traceback (most recent call last):
  File "<exec>", line 10, in <module>
TypeError: log_call.<locals>.wrapper() takes 0 positional arguments but 2 were given

"takes 0 positional arguments but 2 were given" points at the wrapper, not at add. Because the wrapper is what the label now points at, it is what the caller actually talks to. The fix is def wrapper(*args, **kwargs):.

A decorator can keep state

Because wrapper is a closure, it can also count things. Here is a decorator that counts how many times a function was called, using nonlocal from 6.6.

A decorator with memory
def count_calls(func): calls = 0 def wrapper(*args, **kwargs): nonlocal calls calls += 1 print(func.__name__, "has been called", calls, "time(s)") return func(*args, **kwargs) return wrapper @count_calls def validate(record): return record["score"] >= 0 validate({"name": "Asha", "score": 0.9}) validate({"name": "Ben", "score": -1})
Output
validate has been called 1 time(s)
validate has been called 2 time(s)
Python reads @log_call above def add. When does log_call run: when add is defined, or every time add is called?
When add is defined, once. What runs on every call is the wrapper that log_call returned.
After decoration, what does the name add refer to?
The wrapper function returned by the decorator. The original is kept alive inside the wrapper's backpack as func.
Try it. Delete the print("[decoration time] ...") line and count how many labelled lines you expect. Then put it back and add a third call add(1, 1). How many times does the decoration line print now?
Recap
  • A decorator is a function that takes a function and returns a wrapper function; @name above a def means f = name(f).
  • Decoration time happens once, when the def is read. Call time happens on every call and goes through the wrapper.
  • The wrapper uses *args, **kwargs to accept anything and must return the original's result.
  • Common errors: forgetting return wrapper ('NoneType' object is not callable) or a wrapper with the wrong parameters (takes 0 positional arguments).
6.8 — Decorators, Step 4: functools.wraps and Stacking

Our decorator works, but it left a small problem behind. It also has a natural next question: what if you put two decorators on one function? Both are short.

The problem: the wrapper steals the identity

You saw it a moment ago: after decoration, add.__name__ is wrapper. The same happens to the docstring, the text in triple quotes that describes a function. That matters in real life, because error messages, logs and help() use these attributes. Everything would say wrapper, which tells a human nothing.

The wrapper hides the original identity
def log_call(func): def wrapper(*args, **kwargs): return func(*args, **kwargs) return wrapper @log_call def add(a, b): """Add two numbers.""" return a + b print("name:", add.__name__) print("doc:", add.__doc__)
Output
name: wrapper
doc: None
The idea: copy the name tag onto the wrapper

The standard library has a helper for exactly this: functools.wraps. You put @wraps(func) on the wrapper, and it copies the original's name, docstring and a few other attributes onto it. It also stores the original as wrapper.__wrapped__, so you can still reach the unwrapped version when you need it. Think of it as sewing the original's name tag onto the wrapper coat.

The same decorator with @wraps
from functools import wraps def log_call(func): @wraps(func) def wrapper(*args, **kwargs): return func(*args, **kwargs) return wrapper @log_call def add(a, b): """Add two numbers.""" return a + b print("name:", add.__name__) print("doc:", add.__doc__) print("original still reachable:", add.__wrapped__(2, 3))
Output
name: add
doc: Add two numbers.
original still reachable: 5

Make @wraps(func) a habit: every decorator you write from now on should have it on its wrapper. It costs one line and saves you from confusing logs. (Notice that wraps(func) has parentheses and an argument, so it is a decorator that takes an argument. Section 6.9 shows how those are built.)

Stacking: which one runs first?

You can put several decorators on one function. The rule that surprises people: they are applied from the bottom up (the one closest to the def first), so the top decorator ends up on the outside. Here two decorators each wrap a string in tags, so the nesting order is visible in the result.

Two decorators on one function
def bold(func): def wrapper(): return "<b>" + func() + "</b>" return wrapper def italic(func): def wrapper(): return "<i>" + func() + "</i>" return wrapper @bold @italic def word(): return "hello" print(word())
Output
<b><i>hello</i></b>
What Python does, line by line
  • Python builds the original word, then applies the bottom decorator first: word = italic(word). Now word is an italic wrapper around the original.
  • Then it applies the top one to that result: word = bold(word). So word is a bold wrapper around the italic wrapper around the original.
  • On the call, the outermost wrapper runs first (bold), which calls the next (italic), which calls the original, and then the tags are added on the way out, italic first.
  • So the result reads <b><i>hello</i></b>: the last decorator applied (the top one) is the outermost layer, like the outer skin of an onion.
What two things does @wraps(func) fix for the decorated function?
Its __name__ and its __doc__ (and a few related attributes) are copied from the original onto the wrapper, so logs, error messages and help() show the real name instead of wrapper.
With @bold above @italic, which decorator is applied to the function first?
@italic, the one nearest the def. Decorators are applied from the bottom up, so bold ends up as the outer layer.
Try it. Swap the order of @bold and @italic in the stacking example and predict the new output before running it.
Recap
  • Without help, a decorated function's __name__ and __doc__ become those of wrapper.
  • Put @wraps(func) (from functools) on the wrapper to copy the original's identity; __wrapped__ reaches the original.
  • Stacked decorators apply bottom-up, so the top decorator is the outermost layer.
6.9 — Decorators, Step 5: Decorators That Take Settings

So far @log_call has no settings: it is just a name. Real decorators often need a setting, like @retry(times=3) (try up to three times) or @log_call("MATH") (a label for the log lines). This is the last layer of the topic, and it feels harder only because there is one more nesting level. If 6.7 is clear, this is a small step.

The problem: a decorator receives only the function

The decorator from 6.7 has room for exactly one input, the function. There is nowhere to put a setting. And what happens if you try to write the parentheses anyway, hoping for the best?

Adding parentheses to a plain decoratorread-only
def log_call(func): def wrapper(*args, **kwargs): return func(*args, **kwargs) return wrapper @log_call() def add(a, b): return a + b
What Python says
Traceback (most recent call last):
  File "<exec>", line 6, in <module>
TypeError: log_call() missing 1 required positional argument: 'func'

This tells us how Python reads @something(...). It first calls something(...) with what is in the parentheses, and only then applies whatever comes back to the function below. Here log_call() was called with nothing, but it demands func, hence the error. So for @log_call("MATH") to work, log_call("MATH") must return a real decorator. We need a function that builds decorators.

The idea: a decorator factory

Compare with a tailor. A plain decorator is a ready-made coat: you hand it your function and it wraps it. A decorator factory is the tailor: you hand over your measurements (the setting) and receive a coat made to fit (the decorator), and then you put the coat on the function. So there are three functions nested one inside the other:

Three layers, three moments
def label_calls(label):          <- 1 FACTORY: gets the setting
    def decorator(func):         <- 2 DECORATOR: gets the function

What Python does, in order
  • Python reads @label_calls("MATH"). Before it can decorate anything it must evaluate the expression after the @, so it calls label_calls("MATH"). That prints [1: factory runs].
  • The factory returns decorator, whose backpack now holds label = "MATH".
  • Python applies that returned decorator to the function: decorator(add). This prints [2: decorator runs]. It builds wrapper (backpack: label and func) and returns it.
  • The name add is now attached to wrapper. All of steps 1 to 3 happened at definition time, once, before definition done printed.
  • add(3, 5) is call time: only wrapper runs. It prints [3: call time] MATH -> add (3, 5), calls the original and returns 8. The second call prints another [3: call time] line. Steps 1 and 2 never run again.
A useful one: @retry

Here is the classic use. Some operations fail now and then (a network request, a busy file), and trying again a few times often helps. @retry(times=3) wraps any function so that a failure is retried, and only after the last attempt does the error escape. We add @wraps from 6.8 as a good habit. The attempts dictionary just makes the function fail twice and then succeed, so you can watch it work.

@retry(times=3): a decorator with a setting
from functools import wraps def retry(times): def decorator(func): @wraps(func) def wrapper(*args, **kwargs): last_error = None for attempt in range(1, times + 1): try: return func(*args, **kwargs) except ValueError as error: last_error = error print("attempt", attempt, "failed:", error) raise last_error return wrapper return decorator state = {"calls": 0} @retry(times=3) def flaky(): state["calls"] += 1 if state["calls"] < 3: raise ValueError("not ready yet") return "success" print(flaky())
Output
attempt 1 failed: not ready yet
attempt 2 failed: not ready yet
success
What Python does, line by line
  • At definition, retry(3) runs and returns decorator, which is applied to flaky. flaky is now the wrapper, and times = 3 sits in its backpack.
  • flaky() runs wrapper. The loop starts with attempt = 1. The original raises ValueError, the except catches it, prints a line and remembers the error.
  • Attempt 2 fails the same way. Attempt 3 finds state["calls"] is 3, so the original returns "success", and return inside the loop leaves the whole wrapper with that value.
  • If all three had failed, the loop would end, and raise last_error would throw the last error to the caller, the honest result after trying hard.

Now the sad path, so you can see the end of the story. Same decorator, but a function that never succeeds. To keep this block short, the decorator is written compactly.

When every attempt fails
def retry(times): def decorator(func): def wrapper(*args, **kwargs): for attempt in range(1, times + 1): try: return func(*args, **kwargs) except ValueError as error: print("attempt", attempt, "failed:", error) last_error = error raise last_error return wrapper return decorator @retry(times=2) def always_broken(): raise ValueError("still broken") try: always_broken() except ValueError as error: print("gave up. Common mistake: forgetting the parentheses

The mirror image of the first error: the decorator is a factory, but you write it like a plain decorator. Then @retry passes the function in as the times setting, and the factory returns its inner decorator instead of a wrapper.

6.10 — Generators: Producing Values One at a Time

Until now, a function either returned one value or built a whole list. Both have a cost when the data is big. Suppose the validator must look at a million records. A function that collects them all into a list must hold every one in memory at the same moment, even if you only need to look at them one by one. A generator is a function that hands out its values one at a time, on demand, and never stores the whole collection.

The problem: building everything up front

Here is how much memory the two approaches use for the squares of the numbers below a million. sys.getsizeof reports the size of an object in bytes. We only print the comparison, because the exact byte counts depend on the machine.

A list holds everything; a generator holds almost nothing
import sys as_list = [n * n for n in range(1_000_000)] # a million values, all stored as_generator = (n * n for n in range(1_000_000)) # a recipe for a million values print("list is much bigger:", sys.getsizeof(as_list) > 1000 * sys.getsizeof(as_generator)) print("both give the same total:", sum(as_list) == sum(as_generator))
Output
list is much bigger: True
both give the same total: True

The second line uses a generator expression, which we meet properly in 6.11. The point for now: the generator gives the same answers without ever holding a million numbers at once. The analogy is a recipe versus a finished feast. The list is the feast: everything cooked and sitting on the table. The generator is the recipe: it makes the next dish only when someone asks for it.

The idea: yield is a pause button

Inside a function, the word yield works like return with a difference. return ends the function for good. yield hands a value out and then pauses the function right there, remembering its variables and the exact line. The next time someone asks for a value, it un-pauses and continues from that line. (This is the same bookmark idea you met with @contextmanager in 6.3. That decorator is built on generators.) A function that contains yield is called a generator function, and calling it gives back a generator object.

A generator that shows its pauses
def count_up(limit): print(" (starting)") n = 1 while n <= limit: print(f" (about to yield {n})") yield n print(f" (resumed after {n})") n += 1 print(" (finished)") gen = count_up(2) print("created the generator. Has the body run yet?") print("first next() gives:", next(gen)) print("second next() gives:", next(gen)) try: next(gen) except StopIteration: print("third next(): the generator is finished (StopIteration)")
Output
created the generator. Has the body run yet?
  (starting)
  (about to yield 1)
first next() gives: 1
  (resumed after 1)
  (about to yield 2)
second next() gives: 2
  (resumed after 2)
  (finished)
third next(): the generator is finished (StopIteration)
What Python does, line by line
  • gen = count_up(2) does not run the body. You get a generator object back, ready but not started. That is why nothing was printed by the function yet.
  • The first next(gen) starts the body. It prints (starting), sets n = 1, prints (about to yield 1), and reaches yield n. The generator pauses and hands out 1.
  • The second next(gen) un-pauses right after the yield. It prints (resumed after 1), adds one to n, loops, prints (about to yield 2) and pauses again with 2.
  • The third next(gen) resumes, prints (resumed after 2), n becomes 3, the while condition is now false, so the body runs off its end and prints (finished).
  • Running off the end raises StopIteration, Python's signal for "no more values". A for loop catches this signal silently, which is how it knows to stop.
A generator alternates between running and paused
caller says:   next()      next()      next()
generator:     run,        resume,     resume,
               yield 1     yield 2     run off the end
               (pause)     (pause)     -> StopIteration

Between calls it is paused: position and variables are kept.
Between two next() calls the generator does nothing and costs nothing, but it remembers where it was and the value of every local variable.
A for loop does the next() calls for you

You rarely call next yourself. A for loop, list(...) and sum(...) all ask the generator for one value after another until StopIteration.

Generators work anywhere an iterable does
def high_scores(scores): for score in scores: if score >= 80: yield score scores = [92, 75, 81, 60, 88] for s in high_scores(scores): print("high score:", s) print("as a list:", list(high_scores(scores)))
Output
high score: 92
high score: 81
high score: 88
as a list: [92, 81, 88]
Common mistakes, with the real messages

Mistake 1: using a generator twice. A generator is a one-way stream, like water running through a pipe. Once its values have been taken they are gone, and the second pass finds it empty. Nothing crashes, which makes this easy to miss.

A generator is used up after one pass
def high_scores(scores): for score in scores: if score >= 80: yield score gen = high_scores([92, 75, 81, 60, 88]) print("first pass: ", list(gen)) print("second pass:", list(gen))
Output
first pass:  [92, 81, 88]
second pass: []

If you need the values twice, either call the generator function again to get a fresh generator, or store the result once with list(...).

Mistake 2: treating it like a list. A generator does not store its items, so it cannot answer "give me item 0" or "how many are there?".

Indexing a generatorread-only
def high_scores(scores): for score in scores: if score >= 80: yield score gen = high_scores([92, 75, 81, 60, 88]) print(gen[0])
What Python says
Traceback (most recent call last):
  File "<exec>", line 7, in <module>
TypeError: 'generator' object is not subscriptable
Asking a generator for its lengthread-only
def high_scores(scores): for score in scores: if score >= 80: yield score gen = high_scores([92, 75, 81, 60, 88]) print(len(gen))
What Python says
Traceback (most recent call last):
  File "<exec>", line 7, in <module>

Both messages say the same thing in different words: a generator has no stored items to index or count. Convert it with list(gen) first if you really need that, at the cost of holding everything in memory again.

Mistake 3: next() past the end. Calling next on a finished generator raises StopIteration, as in the trace above. A for loop handles it for you, but a bare next does not.

What is the difference between return and yield inside a function?
return ends the function and gives one final value. yield hands out a value and pauses the function, remembering where it was, so it can continue from that point when asked for the next value.
You call gen = count_up(3) and print nothing else. Does the body of count_up run?
No. Calling a generator function only creates the generator object. The body starts running at the first next(gen), or when a for loop or list() asks for a value.
Try it. In count_up, change limit to 3 and add a for value in count_up(3): print(value) loop after the gen lines. Watch how the for loop drives the same pauses.
Recap
  • A generator function contains yield; calling it returns a generator object and runs nothing yet.
  • yield hands out a value and pauses the function; the next next() resumes right after it.
  • Reaching the end raises StopIteration, which for loops catch to stop cleanly.
  • A generator holds one value at a time (memory-friendly), is used up after one pass, and cannot be indexed or measured with len().
6.11 — Generators in Practice: Pipelines and Generator Expressions

Now we put generators to work. There are three payoffs: the validator can hand out only good records, several generators can be chained into an assembly line, and a short one-line form lets you write simple ones in a single expression.

Our validator, as a generator

Recall validate from 6.2, which raises an error for a bad record. We want a function that goes through many records and hands out only the valid ones, printing a note for each rejected one instead of crashing. That is a natural generator: yield for the good ones, except for the bad ones.

valid_records: yield the good ones, report the bad ones
class ValidationError(Exception): pass def validate(record): if not 0 <= record["score"] <= 1: raise ValidationError(record["name"] + ": score " + str(record["score"])) return record def valid_records(raw): for record in raw: try: yield validate(record) except ValidationError as error: print("skipped:", error) raw = [{"name": "Asha", "score": 0.9}, {"name": "Ben", "score": 1.4}, {"name": "Chen", "score": 0.6}, {"name": "Dana", "score": -0.2}] names = [record["name"] for record in valid_records(raw)] print("passed:", names, "count:", len(names))
Output
skipped: Ben: score 1.4
skipped: Dana: score -0.2
passed: ['Asha', 'Chen'] count: 2
What Python does, line by line
  • valid_records(raw) creates the generator. The list comprehension then asks it for values one by one.
  • For Asha, validate returns the record, so yield hands it out. The comprehension keeps its name, then asks again and the generator resumes after the yield.
  • For Ben, validate raises ValidationError. The generator's own except catches it and prints skipped: .... No yield happens, so the loop moves on to Chen without the caller noticing anything.
  • After Dana is skipped the loop ends, the generator finishes, and the comprehension stops. The caller received only the two valid records.
Pipelines: an assembly line, one item at a time

Generators shine when chained. Each stage takes an iterable, does one small job, and yields its results to the next stage. Because every stage is lazy, an item travels through the whole line before the next item enters. Picture a car factory: one car moves through every station while the next waits at the door, rather than all cars piling up at station one. The prints below show the interleaving.

A three-stage pipeline
def read_scores(texts): for text in texts: print(" read", text) yield text def to_number(items): for text in items: print(" convert", text) yield float(text) def only_passing(numbers): for value in numbers: if value >= 0.5: print(" keep", value) yield value pipeline = only_passing(to_number(read_scores(["0.9", "0.2", "0.7"]))) for value in pipeline: print("received", value)
Output

  convert 0.9
  keep 0.9
received 0.9
  read 0.2
  convert 0.2
  read 0.7
  convert 0.7
  keep 0.7
received 0.7
One item at a time flows through every stage
texts -> read_scores -> to_number -> only_passing -> for loop

"0.9": read, convert, keep, RECEIVED
"0.2": read, convert, (dropped: 0.2 < 0.5)
"0.7": read, convert, keep, RECEIVED

The line never holds all the data: at most one item in flight.

Read the output: for 0.9 you see read, convert, keep, received, in that order, before 0.2 even starts. That is laziness at work. With a file of millions of lines, this pipeline uses the memory of one line.

Generator expressions: the one-line form

A list comprehension [x for x in data if ...] builds a whole list. Change the square brackets to round brackets and you get a generator expression: the same syntax, but lazy. When it is the only argument of a function, you can even drop the extra pair of brackets. Here is a real advantage of being lazy: next can stop after the first match, without checking the rest.

A generator expression stops early
checked = 0 def is_bad(score): global checked checked += 1 return score > 1 scores = [0.5, 0.6, 0.7, 1.5] + [0.5] * 996 # 1000 scores, first bad one is 4th all_bad = [s for s in scores if is_bad(s)] # list comprehension: checks ALL print("list version checked", checked, "scores") checked = 0 first_bad = next(s for s in scores if is_bad(s)) # generator expression: stops at first print("generator version checked", checked, "scores; first bad is", first_bad) print("total with sum():", sum(s for s in scores if s <= 1))
Output
list version checked 1000 scores
generator version checked 4 scores; first bad is 1.5
total with sum(): 499.8

The first version checked all 1000. The second stopped as soon as it found one, after only 4. And in sum(s for s in ...) we wrote no extra brackets, because the expression is the function's only argument.

What does the difference between [x for x in data] and (x for x in data) mean for memory and for how much work is done?
The square-bracket form builds the entire list immediately, using memory for every item. The round-bracket form is a generator expression: it makes each item only when asked, so it uses almost no memory and can stop early.
In the pipeline above, does to_number convert 0.7 before 0.9 has been received by the for loop?
No. Each item flows through every stage before the next one starts. 0.9 is read, converted, kept and received first, and only then does the line start on 0.2.

Recap
  • A generator can filter and repair as it goes: yield for good items, try/except around the bad ones.
  • Chained generators form a pipeline: one item moves through every stage before the next begins.
  • (expression for x in data) is a lazy generator expression; [...] builds the whole list.
  • Laziness saves memory and lets you stop early, but the result is single-use.
6.12 — Logging, Part 1: print() That Grows Up

Every beginner debugs with print. It is fine for twenty lines. In a real program that runs for hours on a server, you cannot watch the screen, and print starts to hurt. This section shows the problems, and the standard-library answer, the logging module.

The problem: prints you can never switch off

While developing, you scatter prints to see what is happening: "checking Asha", "score is 0.9". When you are done, you must find and delete them all, or they clutter the real output forever. And if the bug comes back next month, you must write them all again. A common workaround is a flag, which shows the next problem: all messages look the same, so an important one ("disk is full") hides among the chatter.

The print-with-a-flag workaround
DEBUG = True def validate(record): if DEBUG: print("checking", record["name"]) ok = 0 <= record["score"] <= 1 if not ok: print("PROBLEM: bad score for", record["name"]) # no way to tell it from debug chatter return ok validate({"name": "Asha", "score": 0.9}) validate({"name": "Ben", "score": 1.4})
Output
checking Asha
checking Ben
PROBLEM: bad score for Ben

Two things are missing: importance (how serious is this message?) and a single switch (show me only what matters, without editing code).

The idea: every message has a level

The logging module gives each message a level, a label of importance, and lets you choose a threshold once, at the top of the program. Think of a newspaper: the front page carries only major news, and the inside pages carry the small stories. You decide how deep to read today. There are five standard levels, each with a number. A higher number means more serious.

Setting the threshold to a level means "show this level and everything above it". Threshold INFO shows INFO, WARNING, ERROR and CRITICAL, and hides DEBUG. Here it is with all five messages. (We pass force=True for a reason explained below.)

import logging logging.basicConfig(level=logging.DEBUG, format="%(levelname)s: %(message)s", force=True) logging.debug("checking record 1") logging.info("validation started") logging.warning("score close to the limit") logging.error("record 2 rejected") logging.critical("cannot open the database")

  • logging.basicConfig(...) sets up the simplest possible logging: one destination (the screen), a threshold (level=logging.DEBUG) and a format.
  • The format string %(levelname)s: %(message)s is a template. %(levelname)s is replaced by the level's name and %(message)s by your text.
  • Each call, such as logging.warning("..."), creates a record with that level. Python compares the level number with the threshold.
  • The threshold is DEBUG (10), so every level (10, 20, 30, 40, 50) is at least 10, and all five lines are printed.

Common mistakes, with the real behaviour

Mistake 1: expecting INFO to show by default. If you never configure logging, the threshold is WARNING. Your info and debug messages disappear without any error, which is confusing until you know the rule. (force=True with no level is the default configuration.)

The default threshold hides INFO
import logging logging.basicConfig(force=True) # defaults: threshold WARNING logging.info("validation started") # silently dropped logging.warning("disk almost full") # shown, with the default format

Mistake 2: calling basicConfig twice. Without force=True, the second call is quietly ignored, so your change of threshold or format never takes effect.

The second basicConfig is ignored
import logging logging.basicConfig(level=logging.DEBUG, format="FIRST: %(message)s", force=True) logging.basicConfig(level=logging.ERROR, format="SECOND: %(message)s") # ignored! logging.info("did the second call change anything?")

If the output had followed the second call, nothing would print (INFO is below ERROR) and the format would say SECOND. Instead you see the first configuration still in charge.

6.13 — Logging, Part 2: Loggers, Handlers and Formatters

basicConfig is a shortcut that builds three parts for you. To send different messages to different places, you need to know the parts. There are only three, and each has one job.

The problem: one destination is not enough

On a server you want everything, including DEBUG detail, saved in a file for later investigation. But you only want serious messages to appear on the screen where an operator is watching. With basicConfig there is one destination and one threshold, so you cannot have both.

The idea: reporter, desks and house style

Imagine a newsroom. A logger is the reporter: your code says logger.info(...) and the reporter writes down a report. A handler is a delivery desk: one sends reports to the screen, another to a file, another over the network. Each desk has its own filter ("we only take WARNING and above"). A formatter is the house style: it decides how each line looks. One reporter can feed many desks, and each desk has its own style.

The path of one log message

        v

        v                           v

A message must pass the logger's level first, then each handler's own level. That is why the logger is usually set to DEBUG (accept all) and the handlers do the filtering.
One logger, two desks, two styles

What Python does, line by line
  • getLogger("training") fetches (or creates) the logger named training. Asking for the same name anywhere in the program returns the same logger.
  • setLevel(DEBUG) lets every message into the system. Two handlers are then attached, each with its own level and its own Formatter.
  • logger.debug(...) passes the logger (10 >= 10). The console desk rejects it (10 < 30), the file desk accepts it. So the debug line appears only in the saved text.
  • logger.warning(...) and logger.error(...) pass both desks. Each desk formats the line in its own style, which is why the console lines are short and the saved lines include the logger name.
  • The StringIO object stands in for a file so you can see the result. Real code would write logging.FileHandler("app.log") instead of the second StreamHandler.

The two lines at the top show the console desk. The block after --- what the 'file' received --- shows the other desk got everything, including the debug and info lines that were kept off the screen. Same logger calls, two audiences.

Loggers have names, and the name shows where a message came from

It is a convention to make one logger per module with logging.getLogger(__name__), so every line says which file it came from. Names use dots to form families, and a message also travels up to the parent logger's handlers (that is called propagation). It is handy, and also the source of the classic "my messages print twice" problem below.

Common mistakes, with the real behaviour

Mistake 1: adding the same handler again. Running set-up code twice (or once per function call) attaches a second handler, and every message is delivered once per handler.

Two identical handlers: every line appears twice
import logging logger = logging.getLogger("dup_demo") logger.handlers.clear() logger.propagate = False logger.setLevel(logging.INFO) for _ in range(2): # imagine this set-up code ran twice handler = logging.StreamHandler() handler.setFormatter(logging.Formatter("%(message)s")) logger.addHandler(handler) logger.info("validation started") print("handlers attached:", len(logger.handlers))
Output
validation started
validation started
handlers attached: 2

The fix is to configure a logger once, or guard with if not logger.handlers: before adding.

Mistake 2: the logger's level is stricter than the handler's. The message is stopped at the first gate and never reaches the handler, however permissive the handler is.

The logger gate stops the message first
import logging logger = logging.getLogger("gate_demo") logger.handlers.clear() logger.propagate = False logger.setLevel(logging.WARNING) # the reporter only writes WARNING and up handler = logging.StreamHandler() handler.setLevel(logging.DEBUG) # the desk would accept anything... handler.setFormatter(logging.Formatter("%(levelname)s | %(message)s")) logger.addHandler(handler) logger.debug("this never reaches the handler") logger.warning("this one does")
Output
WARNING | this one does

Mistake 3: messages printed twice because of propagation. If the root logger has a handler (from basicConfig) and your named logger has its own, the message goes to your handler and then up to the root's handler too.

Propagation duplicates a message
import logging logging.basicConfig(level=logging.INFO, format="ROOT: %(message)s", force=True) logger = logging.getLogger("prop_demo") logger.handlers.clear() logger.setLevel(logging.INFO) handler = logging.StreamHandler() handler.setFormatter(logging.Formatter("OWN: %(message)s")) logger.addHandler(handler) logger.info("validation started") # delivered twice logger.propagate = False # the fix: stop it travelling upward logger.info("validation finished") # delivered once
Output
OWN:  validation started
ROOT: validation started
OWN:  validation finished
The validator with real logging

Finally, our validator, written the professional way: one logger per module, INFO for progress, WARNING for records that are rejected.

The validator, now logging
import logging logging.basicConfig(level=logging.INFO, format="%(levelname)s [%(name)s] %(message)s", force=True) logger = logging.getLogger("validator") def validate(record): if not 0 <= record["score"] <= 1: logger.warning("rejected %s: score %s", record["name"], record["score"]) return False logger.info("accepted %s", record["name"]) return True records = [{"name": "Asha", "score": 0.9}, {"name": "Ben", "score": 1.4}] passed = [r["name"] for r in records if validate(r)] logger.info("%d of %d records passed", len(passed), len(records))
Output
INFO [validator] accepted Asha
WARNING [validator] rejected Ben: score 1.4
INFO [validator] 1 of 2 records passed

Notice the %s placeholders: instead of building the text with an f-string, you give the logger a template and the values separately. The logger builds the final text only if the message passes the level check, so hidden DEBUG lines cost almost nothing.

A logger is set to WARNING and its handler is set to DEBUG. Does an INFO message get printed? Which gate stops it?
No. The logger's level is checked first, and INFO (20) is below WARNING (30), so the message never reaches the handler. Both gates must pass.
What is the job of a formatter, compared with a handler?
A handler decides where a message goes (screen, file, network) and which levels it accepts. A formatter decides how the line looks (which fields, in which order).
Try it. In the two-desks example, change the console handler's level to logging.INFO and predict which extra line appears on the screen before you run it.
Recap
  • A logger creates messages, a handler sends them to a destination, a formatter lays out the line.
  • A message must pass the logger's level, then each handler's level, so use handlers to split audiences.
  • Name loggers with getLogger(__name__); configure each once to avoid duplicates; use propagate = False to stop double printing.
  • Prefer logger.info("x %s", value) over f-strings; the text is only built if the message is used.
6.14 — Testing, Part 1: unittest, a Safety Net for Your Code

You have been testing your code all along: you run it, look at the output, and think "yes, that looks right". That is a manual test, and it has two weaknesses. You forget to do it, and you check only the cases you thought of at that moment. Automated tests fix both: they are small programs that check your functions for you, in a fraction of a second, every time.

The problem: a change breaks something far away

Imagine the validator's is_valid function was written last month and worked. Today you "simplify" it, run your one favourite example, and it still looks fine. But you have quietly broken a case you did not check: a score of exactly 1.0.

A quiet break that one example does not catch
def is_valid(score): return 0 <= score < 1 # the old version was: 0 <= score <= 1 print("Asha (0.9):", is_valid(0.9)) # looks fine
Output
Asha (0.9): True

Nothing warns you that 1.0 is now rejected. A test suite would have told you at once, because it remembers all the cases you cared about. The analogy is a smoke detector: you do not stare at the ceiling every minute, you install a device that shouts when something is wrong.

The idea: a test states what you expect

A test is a tiny function that calls your code with a known input and states the answer you expect. The smallest test needs no library. Python has an assert statement: assert condition does nothing if the condition is true, and stops with an AssertionError if it is false.

assert: silent when true, loud when falseread-only
def is_valid(score): return 0 <= score < 1 assert is_valid(0.5) # fine, nothing printed print("first check passed") assert is_valid(1.0) # expected True, but the function says False print("never reached")
What Python says
first check passed
Traceback (most recent call last):
  File "<exec>", line 6, in <module>
AssertionError

That is the seed of testing. The trouble is that the first failed assert stops everything, so you learn about one problem at a time. unittest, which comes with Python, runs all your checks and gives a report.

Your first unittest

A test lives in a class that inherits from unittest.TestCase (inheritance again, from OOP Part 3). Each check is a method whose name starts with test. Inside, you call self.assertEqual(actual, expected) and friends. To keep the report deterministic in this lesson, the helper run sends unittest's chatter to a hidden buffer and prints only the counts.

A test class with two tests
import io import unittest def is_valid(score): return 0 <= score <= 1 class TestIsValid(unittest.TestCase): def test_middle_score_is_valid(self): self.assertTrue(is_valid(0.5)) def test_upper_edge_is_valid(self): self.assertTrue(is_valid(1.0)) def run(case): suite = unittest.defaultTestLoader.loadTestsFromTestCase(case) result = unittest.TextTestRunner(stream=io.StringIO()).run(suite) print("ran:", result.testsRun, "| failures:", len(result.failures), "| errors:", len(result.errors)) for test, report in result.failures: print("FAILED", test._testMethodName, "->", report.strip().splitlines()[-1]) run(TestIsValid)
Output
ran: 2 | failures: 0 | errors: 0
What Python does, line by line
  • class TestIsValid(unittest.TestCase) makes a test collection. Inheriting gives it assertTrue, assertEqual and many more.
  • The loader scans the class and collects every method whose name starts with test. Each becomes one test.
  • The runner creates a fresh TestIsValid object for each test, calls the method, and records: passed, failed (an assertion was false) or errored (some other exception).
  • result holds the counts. Both checks pass, so failures and errors are 0.

Now break the function on purpose, as we did earlier, and watch the safety net catch it. assertEqual is more informative than assertTrue, because it shows both values.

The safety net catches the broken edge case

Read the failure line: AssertionError: False != True says the function returned False where the test expected True. The test name, test_upper_edge_is_valid, tells you which rule broke, before you have opened the function. That is why test names should read like sentences.

Testing the sad path: assertRaises

Good tests also check that bad input fails in the right way. assertRaises is a context manager (6.3): the with block must raise the named exception, or the test fails. We reuse our custom exception from 6.2.

assertRaises, and setUp for fresh data
import io import unittest class ScoreOutOfRange(Exception): pass def check(score): if not 0 <= score <= 1: raise ScoreOutOfRange(f"{score} is out of range") return score class TestCheck(unittest.TestCase): def setUp(self): self.good = 0.75 # runs before EACH test: fresh data def test_good_score_passes_through(self): self.assertEqual(check(self.good), 0.75) def test_high_score_raises(self): with self.assertRaises(ScoreOutOfRange): check(1.7) result = unittest.TextTestRunner(stream=io.StringIO()).run( unittest.defaultTestLoader.loadTestsFromTestCase(TestCheck)) print("ran:", result.testsRun, "| passed:", result.wasSuccessful())
Output
ran: 2 | passed: True
🚫
Never call unittest.main() in this consoleunittest.main() ends by calling sys.exit(), which raises SystemExit and looks like a crash here. Use TextTestRunner(...).run(...) as in these examples. In a real terminal script, unittest.main() is what you would normally write at the bottom of the file.
Common mistakes

Mistake 1: a test method that does not start with test. The loader ignores it. Nothing fails, so you believe you are protected when you are not. Here the count reveals the problem: ran: 0.

A test that silently never runs
import io import unittest class TestIsValid(unittest.TestCase): def upper_edge_is_valid(self): # missing the "test" prefix! self.assertEqual(1 + 1, 3) # would fail, if it ran result = unittest.TextTestRunner(stream=io.StringIO()).run( unittest.defaultTestLoader.loadTestsFromTestCase(TestIsValid)) print("ran:", result.testsRun, "| passed:", result.wasSuccessful())
Output
ran: 0 | passed: True

"Passed: True" here means nothing, because no test ran. Always glance at the number of tests run. Mistake 2: a test that checks the wrong thing (for example expecting the result you *hope* for instead of computing it independently). A test is only as good as the expected value you write down by hand.

Why must a test method's name start with test?
The loader collects only methods starting with test. Any other name is treated as a helper and is never run, so a mis-named test gives false confidence.
What is the difference between a failure and an error in the unittest report?
A failure means an assertion was false (your code returned the wrong answer). An error means some other exception was raised while the test ran (for example a typo, or a crash inside your function).
Try it. In the failing example, change < back to <= in is_valid and re-run. The report should return to failures: 0. Then add a third test for a negative score.
Recap
  • An automated test states an expected result; it catches broken behaviour the moment you change code.
  • With unittest, a class inherits TestCase, each test_... method makes checks such as assertEqual, assertTrue, assertRaises.
  • setUp builds fresh data before every test; assertRaises (a context manager) checks the sad path.
  • A method not named test... is silently skipped, so always read how many tests ran.
6.15 — Testing, Part 2: pytest (Reference)

unittest is always available, but many teams prefer pytest, a third-party package (pip install pytest, inside a venv from 6.1). It does the same job with less writing. The problem: unittest has ceremony

6.16 — pyproject.toml: The ID Card of a Project

By now a project has code, a venv, tests and a requirements.txt. One more file ties it together. When you want other people, or other programs, to install and run your project, you need one place that says who it is, what version it is, what it needs, and how it is built. That place is pyproject.toml.

The problem: information scattered everywhere

Without it, the project's name lives in your head, the dependencies in requirements.txt, and "how do I start this tool?" in a README that nobody reads. Every tool (pip, test runners, build tools) has to guess. Think of an ID card: one small card that answers the standard questions about a person, in a standard layout, so any official can read it. pyproject.toml is that card for a Python project, and every modern tool knows where to look.

The idea: a settings file in TOML

TOML is a simple text format for settings: [section] headings and key = value lines. Strings go in double quotes, lists in square brackets. Python 3.11 and newer can read it with the standard-library module tomllib, so we can explore the format for real, even in this browser.

Reading a pyproject-style file with tomllib
import tomllib text = """ [project] name = "score-tool" version = "0.1.0" description = "Check score records" dependencies = ["pandas>=2.0", "requests"] """ data = tomllib.loads(text) print(type(data).__name__) print("name:", data["project"]["name"]) print("first dependency:", data["project"]["dependencies"][0]) print("how many dependencies:", len(data["project"]["dependencies"]))
Output
dict
name: score-tool
first dependency: pandas>=2.0
how many dependencies: 2
What Python does, line by line
  • tomllib.loads(text) parses the text and returns a normal Python dictionary. TOML is just a friendly way to write nested dictionaries.
  • [project] becomes the key "project", whose value is another dictionary holding name, version, and so on.
  • dependencies = [...] becomes a Python list of strings, so data["project"]["dependencies"][0] is the first one.
  • So any tool that wants to know your project's name reads data["project"]["name"]. That is all a settings file is.

Reading a value like "pandas>=2.0": it is a requirement, a package name plus a rule about versions. >=2.0 means "version 2.0 or newer". A bare name accepts any version.

The three sections you need
The shape of a small pyproject.toml

What "package.module:function" means

In [project.scripts], the text on the right of the = says where the function lives: the part before the colon is a module path, the part after is a function name. When you install the project, pip creates a small launcher program named check-scores that imports that module and calls that function. We can imitate the launcher with the standard library to see it is not magic.

  • getattr(module, "sqrt") fetches the attribute named sqrt from the module: the function itself, uncalled (functions are values, 6.5).

You started this chapter with a program that only worked on your laptop. You now have the toolkit that lets a program be shared, trusted and maintained. The list below gives one line per section, with the idea to remember.

  • 6.1 Virtual environments and pip. A venv is a private folder with its own Python and its own site-packages shelf. Activate it, pip install into it, and share a requirements.txt shopping list.

  • 6.10 and 6.11 Generators. yield pauses a function and hands out one value at a time, so big data fits in memory. Chain generators into pipelines and use (x for x in data) for the lazy one-liner. A generator is used up after one pass.
  • 6.12 and 6.13 Logging. Levels (DEBUG, INFO, WARNING, ERROR, CRITICAL) plus a threshold replace scattered prints. Loggers create messages, handlers choose the destination, formatters choose the look.
