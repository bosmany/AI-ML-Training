2.1 — Conditions: Questions Python Can Answer with True or False

So far, every program you wrote in Chapter 1 ran the same way every time: top to bottom, every line, no questions asked. That is fine for a calculator, but a real program has to react to what it sees. Look at what happens when the code cannot decide anything.

A program that cannot decide
accuracy = 0.55 print("Model accepted for deployment!") print("Its accuracy was", accuracy)
Output
Model accepted for deployment!
Its accuracy was 0.55

The model got 55% of its answers right, and the program cheerfully accepted it anyway. There was no step where the code asked "is this good enough?". To fix that, we need a way to ask a question and get an answer the program can act on.

That question is called a condition: any expression that Python can answer with exactly one of two values, True or False. Think of a light switch. The switch is either on or off, and everything a program decides is built from that. In Chapter 1 you met the type bool (short for boolean, named after the mathematician George Boole) and the comparison operators. Here is the full set again, because every decision in this chapter uses one of them.

Notice that == uses two equal signs. A single = means "store this value in that name" (assignment). A double == means "are these two things equal?". Mixing them up is the most common beginner slip, and we will meet the error message for it in section 2.2.

The smallest possible conditions

What Python does, line by line
  • accuracy = 0.94 stores the float 0.94 under the name accuracy.
  • accuracy > 0.9: Python looks up accuracy, gets 0.94, compares it with 0.9, and produces the value True. Then print shows it.
  • accuracy == 0.94 compares equality and gives True. accuracy != 1.0 asks "are they different?" and also gives True.
  • type(...) of a comparison result is bool. A comparison is not a special kind of thing. It is an ordinary value you can store in a variable, print, or pass around.
Comparison chaining: asking two questions at once

In maths you write 0 <= x <= 1 to say "x is between 0 and 1". Python lets you write exactly that. It is called comparison chaining, and it saves you from repeating the middle value. Python reads it as two comparisons joined together: 0 <= x and x <= 1, and the whole chain is True only if both hold. This is perfect for checking that an accuracy, which must be a fraction from 0 to 1, is a sensible number.

Chained comparisons
accuracy = 0.94 broken = 1.4 print(0 <= accuracy <= 1) print(0 <= accuracy and accuracy <= 1) print(0 <= broken <= 1) print(0.9 < accuracy < 0.95)
Output
True
True
False
True

The first two lines give the same answer, one written short and one written long. The third line is the sad path: 1.4 is not a possible accuracy, so the chain is False. In the last line the value 0.94 sits in a narrow band between 0.9 and 0.95, so it is True.

Two traps to know about early

Strings are compared exactly. Capital letters matter, and so do spaces. Floats are only approximate. Computers store decimals like 0.1 in binary, where they cannot be written exactly, so tiny errors creep in. Never trust == between two computed floats. Instead, ask whether they are close.

Case matters, and floats are slightly off
print("Cat" == "cat") print("cat" == "cat ") print(0.1 + 0.2) print(0.1 + 0.2 == 0.3) print(abs((0.1 + 0.2) - 0.3) < 0.000001)
Output
False

False
True

The last line shows the safe habit: subtract, take the absolute distance with abs, and check it is smaller than a tiny tolerance. You will see this pattern again whenever a training loop checks "has the loss stopped changing?".

What is the value of 5 > 3 > 1?
True. Python reads it as 5 > 3 and 3 > 1, and both parts are True. The chain runs left to right, one neighbouring pair at a time.
Why does 0.1 + 0.2 == 0.3 print False?
The sum is stored as 0.30000000000000004, a hair away from 0.3, because 0.1 and 0.2 cannot be stored exactly in binary. Compare with a tolerance instead.

Recap
  • A condition is an expression that Python answers with True or False.
  • Comparison operators are ==, !=, >, <, >=, <=, plus in. Remember = stores, == asks.
  • Chaining such as 0 <= x <= 1 means "both comparisons are true".
  • Compare strings exactly, and compare computed floats with a tolerance.
2.2 — if and else: Running Code Only When a Condition Holds

Back to the model that was accepted with 55% accuracy. We want the "accepted" message to appear only when the accuracy is good enough. Python's tool for that is the if statement. It works like a sign on a door: "If it is raining, take an umbrella." When the condition is True, Python runs the lines that belong to the if. When it is False, Python skips them and moves on.

The smallest possible if
accuracy = 0.55 if accuracy >= 0.9: print("Model accepted!") print("Report finished.")
Output
Report finished.
What Python does, line by line
  • Line 1 stores 0.55 in accuracy.
  • Line 3 evaluates the condition accuracy >= 0.9. That is 0.55 >= 0.9, which is False.
  • Because it is False, Python skips the indented line 4. Nothing is printed for it.
  • Line 5 is not indented, so it does not belong to the if. It always runs, and prints "Report finished."
How indentation defines a block

The lines that belong to an if are called its block. Python does not use curly braces or an "end" keyword to mark a block. It uses indentation, which means the empty space at the start of a line. The if line ends with a colon, and every line that is pushed in by four spaces below it is inside the block. The first line that goes back to the left edge is outside it. In Python, indentation is not decoration. It is part of the grammar.

How Python reads a block
if accuracy >= 0.9:            <- header, ends with a colon
    print("Accepted")           <- 4 spaces: INSIDE the block
    print("Saving model...")    <- 4 spaces: INSIDE the block
print("Report finished.")       <- 0 spaces: block is over
Everything indented under the colon runs only when the condition is True. The first line back at the left edge runs no matter what.
Adding an else: the other road

Often you want a second action for the False case. Add else: at the same indentation as the if. Exactly one of the two blocks runs, never both and never neither.

The two roads of if / else
                accuracy >= 0.9 ?
                 /            \
            True                False
             |                    |
    print("Accepted")      print("Rejected")
              \                  /
               print("Report finished.")
A condition is a fork in the road. Both roads join up again afterwards.
if with else
accuracy = 0.55 if accuracy >= 0.9: print("Accepted") print("Saving model...") else: print("Rejected: accuracy is only", accuracy) print("Keep training.") print("Report finished.")
Output
Rejected: accuracy is only 0.55
Keep training.
Report finished.

Three lines. The if block is skipped, so Python runs the two lines of the else block ("Rejected: accuracy is only 0.55" and "Keep training.") and then the unindented "Report finished." line.

The colon says "a block starts here". The indentation says exactly which lines are in it. Without both, Python cannot know where the conditional part ends.

  • The colon opens a block and indentation (four spaces) says which lines are inside it.
  • Exactly one branch of an if/else runs, then Python continues after it.
  • Read errors by their last line: expected ':', expected an indented block, unexpected indent, unindent does not match.
2.3 — Truthiness: How Python Decides "Yes" or "No" for Any Value

Until now our conditions were comparisons like accuracy >= 0.9, which produce a clean True or False. But real programs also need to ask simpler questions: "Did the user type a name?" or "Do we have any data yet?". Written the long way, those checks are clumsy.

The long way to ask "is it empty?"
name = "" if len(name) > 0: print("Hello,", name) else: print("No name was given.")
Output
No name was given.

Python offers a shortcut. When you put any value where a condition is expected, Python quietly converts it to True or False first. The result is called the value's truthiness. Values that turn into True are truthy, and values that turn into False are falsy. Think of a box: an empty box counts as "no", and a box with anything in it counts as "yes".

The rule is short. A value is falsy if it is a zero (the integer 0 or the float 0.0), if it is empty (the string "", the list [], the dictionary {}; lists and dictionaries are containers, values that hold other values, and you will meet them in section 2.7 and Chapter 4), if it is False itself, or if it is None. None is Python's way of saying "no value at all". It is what you use for something that has not been filled in yet, such as a score that has not been measured. Everything else is truthy.

The falsy club: everything outside it is truthy
FALSY (act like False)
  False    0    0.0    ""    []    {}    None

TRUTHY (act like True)
  True    1    -3    0.001    "hi"    " "    "0"    "False"
  [0]    [[]]   (not empty inside)    ...anything else
Ask "is it zero, empty, or nothing?". If yes, it is falsy. If not, it is truthy.

You can see what Python decides by asking bool(value), which performs the conversion and shows the answer.

Asking Python for the truthiness of values
print("bool(0) ->", bool(0)) print("bool(0.0) ->", bool(0.0)) print("bool('') ->", bool('')) print("bool([]) ->", bool([])) print("bool(None) ->", bool(None)) print("bool(42) ->", bool(42)) print("bool(-0.5) ->", bool(-0.5)) print("bool('hi') ->", bool('hi')) print("bool([0, 1]) ->", bool([0, 1]))
Output

bool(0.0)      -> False
bool('')       -> False
bool([])       -> False
bool(None)     -> False
bool(42)       -> True
bool(-0.5)     -> True
bool('hi')     -> True
bool([0, 1])   -> True
The surprising cases

Truthiness is about emptiness, not about meaning. Python does not read the text. The string "False" is a non-empty string, so it is truthy. The string "0" is truthy for the same reason. A string containing one space is truthy, and so is a list that holds a single zero, because the list itself is not empty.

Values that look false but are truthy
print(bool("False")) print(bool("0")) print(bool(" ")) print(bool([0])) print(bool([[]])) print(bool(-1))
Output
True
True
True
True
True
True
What Python does for if name:
  • Python evaluates the expression after if. Here it is just the variable name, which holds "".
  • It converts that value with the truthiness rules. An empty string is falsy, so the condition counts as False.
  • The if block is skipped and the else block runs.
The short way
name = "" if name: print("Hello,", name) else: print("No name was given.")
Output
No name was given.
The trap: zero is falsy, but zero can be a real answer

Truthiness is handy, and it can also hide a bug. Suppose a model scored exactly 0.0 on a test, a real and very bad result. If your code asks if score:, the zero counts as falsy, and the program claims there is no score at all. When you mean "was a value provided?", compare with None explicitly. Use is None or is not None, because there is only ever one None object and is checks for exactly that.

Zero is a score, None is a missing score
score = 0.0 if score: print("if score: recorded", score) else: print("if score: no score yet <-- wrong!") if score is not None: print("is not None: recorded", score) else: print("is not None: no score yet") score = None print(score is None)
Output
if score:            no score yet  <-- wrong!
is not None:         recorded 0.0
True
Is [[]] truthy or falsy, and why?
Truthy. It is a list containing one item (an empty list). The outer list is not empty, so it counts as True. Only a list with zero items is falsy.
What would if score: do when score is 0.0, and how do you fix it if 0.0 is a valid result?
It treats the score as missing (falsy). Write if score is not None: to ask only whether a value was provided.
Try it. Add your own print(bool(...)) lines. Predict first: bool("no"), bool(0.1 - 0.1), bool(" ".strip()). The last one is worth thinking about, because .strip() removes spaces from both ends.
Recap
  • Any value can be used as a condition. Zero, empty things, None and False are falsy; everything else is truthy.
  • Truthiness checks emptiness, not meaning: "False" and "0" are truthy strings.
  • Use if items: to ask "is there anything in it?".
  • Use is None or is not None when 0 or an empty value is a legitimate answer.
2.4 — Combining Conditions with and, or, not

A model is rarely "good" for one reason alone. It needs high accuracy and low loss. Here is what that looks like with only the tools you have so far: one if tucked inside another.

Two checks the clumsy way
accuracy = 0.94 loss = 0.08 if accuracy > 0.9: if loss < 0.1: print("Ready to deploy") else: print("Not ready") else: print("Not ready")
Output
Ready to deploy

The "Not ready" message is written twice, and the logic is hard to read. Python has three small words that glue conditions together. Think of them as everyday English. To enter a concert you need a ticket and an ID. To pay you can use cash or a card. Someone at the door saying "not under 18" flips the meaning of a check.

The same check with and
accuracy = 0.94 loss = 0.08 has_gpu = False print(accuracy > 0.9 and loss < 0.1) print(accuracy > 0.99 or loss < 0.1) print(not has_gpu) if accuracy > 0.9 and loss < 0.1: print("Ready to deploy") else: print("Not ready")
Output

What Python does for accuracy > 0.9 and loss < 0.1
  • Work out the left side: 0.94 > 0.9 is True.
  • Work out the right side: 0.08 < 0.1 is True.
  • Combine them: True and True is True, so the if block runs.
Which one goes first? Precedence and parentheses

When you mix them, Python has an order, called precedence: not is applied first, then and, then or. This is like multiplication before addition in maths. The safest habit is to add parentheses to say what you mean, so the reader does not have to remember the rules.

Precedence, and parentheses that change the answer
print(True or False and False) print((True or False) and False) print(not True or True) print(not (True or True))
Output
True
False
True
False

Line 1 is True or (False and False), which is True or False, so True. Line 2 groups the other way and gets False. Same symbols, different answer.

The classic mistake: x == "a" or "b"

In English you say "if the label is cat or dog". In Python, writing label == "cat" or "dog" does not mean that. It means (label == "cat") or "dog", and a non-empty string like "dog" is always truthy, so the whole thing is always true.

The condition that is always True
label = "bird" if label == "cat" or "dog": print("wrongly accepted:", label) if label == "cat" or label == "dog": print("never printed for bird") if label in ["cat", "dog"]: print("never printed for bird") else: print("bird is not a cat or a dog")
Output
wrongly accepted: bird
bird is not a cat or a dog

The fix is to repeat the full comparison on each side of or, or to use in with a list of choices, which is shorter and easier to extend. (A list is a row of values in square brackets, like ["cat", "dog"]. Section 2.7 explains lists properly.)

What is not (5 > 3 and 2 > 4)?
Inside the parentheses: True and False is False. Then not False is True.
Why is if answer == "yes" or "y": a bug?
Python reads it as (answer == "yes") or "y". The string "y" is truthy, so the condition is always true. Write answer == "yes" or answer == "y", or answer in ["yes", "y"].
Try it. In the "same check with and" block, change loss to 0.5 and predict which of the three prints and the if/else result change before you run it.
Recap
  • and needs both sides True. or needs at least one. not flips the answer.
  • Precedence is not, then and, then or. Use parentheses to show your intent.
  • Write each comparison in full: x == 1 or x == 2, or use x in [1, 2].
2.5 — Short-Circuiting: Python Stops as Soon as It Knows

Imagine checking the average score of a batch. If the batch is empty, the count is zero, and dividing by zero is impossible. What happens if we just write the check and hope?

Dividing by zeroread-only
total = 0.0 count = 0 print(total / count > 0.5)
What Python says
Traceback (most recent call last):
  File "<exec>", line 4, in <module>
    print(total / count > 0.5)
           ~~~~~~^~~~~~~
ZeroDivisionError: float division by zero

We want "if there is at least one item and the average is above 0.5". If count is 0 we should never attempt the division at all. Luckily Python already behaves that way. It reads and and or from left to right and stops as soon as the answer is certain. This is called short-circuiting, like an electrician cutting the power before it reaches the last bulb.

The reasoning is plain. For A and B, if A is False the whole thing must be False, whatever B is, so Python skips B. For A or B, if A is True the whole thing must be True, so Python skips B.

Where Python stops
A and B
  A is False ?  --> stop. Result is False.
  A is True ?   --> look at B. Result is B.

A or B
  A is True ?   --> stop. Result is True.
  A is False ?  --> look at B. Result is B.
The left side is always evaluated. The right side is evaluated only if the left side did not already decide the answer.

To watch this happen, we need a helper that announces itself when it runs. Below, check is a tiny function: it prints a message and hands back the value you gave it. Functions are the topic of Chapter 3, so for now just read it as "a mini-command that prints its label, then returns the value". Every time you see checking ... in the output, that side of the expression was evaluated.

A visible trace of short-circuiting
def check(label, value): print(" checking", label) return value print("and, left is False:") print(check("left", False) and check("right", True)) print("and, left is True:") print(check("left", True) and check("right", True)) print("or, left is True:") print(check("left", True) or check("right", False))
Output
and, left is False:
  checking left
False
and, left is True:
  checking left
  checking right
True
or, left is True:
  checking left
True
Reading the trace
  • In the first test, left is False, so the and cannot possibly be True. right is never checked, which is why "checking right" is missing.
  • In the second test, left is True, so Python has to look at right to decide. Both lines appear.
  • In the third test, or already has a True on the left, so it stops. Again "checking right" never appears.
Using it as a safety guard

Now the problem from the start has a clean fix. Put the safe check on the left. If it fails, the risky division on the right never runs. The order matters: swapping the two sides would crash again.

A guard that prevents the crash
total = 0.0 count = 0 if count != 0 and total / count > 0.5: print("Good average") else: print("No data, or average too low") count = 4 total = 3.0 if count != 0 and total / count > 0.5: print("Good average:", total / count)
Output
No data, or average too low
Good average: 0.75
and / or hand back a value, not always True or False

One more detail. When and or or finishes, it returns the operand that decided the result, not a fresh True or False. For or that is the first truthy value it meets, which gives a compact way to supply a default. For and it is the first falsy value, or the last value if all are truthy.

What and / or actually return
print("" or "anonymous") print("Asha" or "anonymous") print(0 and 99) print(5 and 99)
Output
anonymous
Asha
0
99

The first line shows the default idea: an empty name is falsy, so or moves on to the next choice. Use it with care, as section 2.3 warned. score or 0.5 would wrongly replace a real score of 0.0.

What does check("left", False) or check("right", True) print, and what value does the expression return?
It prints both "checking left" and "checking right", because or with a False left side must look at the right side. The value returned is True, the right side's value.
Why is total / count > 0.5 and count != 0 unsafe?
Python evaluates the left side first, so the division happens before the count != 0 guard is checked. With count at 0 it crashes. Put the guard on the left.
Try it. Add print(check("left", 0) and check("right", 1)) to the trace block. Predict what is printed and which value comes back before running.
Recap
  • Python evaluates and / or left to right and short-circuits: it stops once the answer is known.
  • Put the cheap or safe check on the left, for example count != 0 and total / count > 0.5.
  • and / or return one of their operands, so name or "anonymous" gives a default for an empty string.
2.6 — elif Chains, Ordering Mistakes, and Nested Decisions

An if/else gives you two roads. Real reports often need more: a report card with grades A, B, C and F. You might try one if per grade. Let us see what that does to a model with an accuracy of 0.96, which deserves an A.

Separate ifs: every one gets a vote
accuracy = 0.96 if accuracy >= 0.95: grade = "A" if accuracy >= 0.85: grade = "B" if accuracy >= 0.70: grade = "C" print("Grade:", grade)
Output
Grade: C

The model earned an A and got a C. Each if here is an independent question. Python asked all three, all three were True, and each one overwrote grade in turn. The last answer won. What we want is a single chain in which the first match ends the conversation. That is what elif (short for "else if") does.

An elif chain is a ladder
   accuracy >= 0.95 ?  --yes-->  grade = "A"  --> done
        | no
   accuracy >= 0.85 ?  --yes-->  grade = "B"  --> done
        | no
   accuracy >= 0.70 ?  --yes-->  grade = "C"  --> done
        | no
   else               -------->  grade = "F"  --> done
Python climbs down the ladder from the top and steps off at the first True condition. Conditions below it are never even evaluated.
The same grading with elif
accuracy = 0.96 if accuracy >= 0.95: grade = "A" elif accuracy >= 0.85: grade = "B" elif accuracy >= 0.70: grade = "C" else: grade = "F" print(f"Accuracy {accuracy:.0%} -> Grade {grade}")
Output
Accuracy 96% -> Grade A
What Python does, line by line
  • Test accuracy >= 0.95. It is 0.96 >= 0.95, which is True, so grade becomes "A".
  • Because a branch ran, Python skips every remaining elif and the else. It jumps straight to the print.
  • With accuracy = 0.83 the first test is False, the second (>= 0.85) is False, and the third (>= 0.70) is True, so the grade is "C".
The ordering mistake

Because the first True condition wins, order matters. Put the most demanding test first. If you list the easiest one at the top, it catches everything below it and the stricter tests can never be reached.

Wrong order: the easy test steals every case
accuracy = 0.96 if accuracy >= 0.70: grade = "C" elif accuracy >= 0.85: grade = "B" elif accuracy >= 0.95: grade = "A" else: grade = "F" print(f"Accuracy {accuracy:.0%} -> Grade {grade}")
Output
Accuracy 96% -> Grade C

Nothing crashes, and that is what makes this bug dangerous. The program runs and prints a plausible but wrong answer. Whenever you write a chain, check it with one value from every band, including the values exactly on a border. Also note the last part of the chain: else has no condition of its own. It catches everything the tests above did not.

Decisions inside decisions

You can put an if inside the block of another if. This is called nesting, and it is the right tool when the second question only makes sense after the first one is answered. Here, we only care about overfitting once the accuracy looks good. Overfitting means a model that has memorised its training data: it does well on training examples but worse on new ones.

Nested conditions: detecting overfitting
train_loss = 0.12 val_loss = 0.31 accuracy = 0.91 if accuracy > 0.9: if val_loss > train_loss * 1.5: print("High accuracy, but OVERFITTING") else: print("High accuracy and generalizing well") else: print("Accuracy too low: keep training")
Output
High accuracy, but OVERFITTING

Each level of nesting adds four more spaces, and every block must stay lined up. Deep nesting gets hard to read fast. Often you can flatten it with and. The check "accuracy above 0.9 and validation loss more than 1.5 times training loss" says the same as the two nested lines, in one condition.

With accuracy = 0.90, which grade does the correct elif ladder give, and why?
B. The first test 0.90 >= 0.95 is False, and the second 0.90 >= 0.85 is True. Border values matter: >= includes the boundary.
In the nested overfitting example, what prints if accuracy = 0.8?
"Accuracy too low: keep training". The outer if is False, so the inner question is never asked.
Try it. In the wrong-order block, change accuracy to 0.6. What is printed? Then reorder the chain (0.95 first) and confirm the 0.96 case gives an A.
Recap
  • Use elif for more than two roads. Python takes the first True branch and skips the rest.
  • Separate if statements are independent questions and can all run.
  • Put the strictest condition first. A wrong order runs without errors but gives wrong answers.
  • Nest an if only when the second question depends on the first, and flatten with and when you can.

First we need a way to hold six numbers under one name. A list is an ordered collection of values written in square brackets and separated by commas: [0.82, 0.61, 0.45]. You will study lists properly in Chapter 4. For now, you only need to know that a list can be walked through, item by item.

2.8 — range(): Counting for the Loop

Sometimes you have no list at all. You just want to do something five times, such as "train for five epochs". An epoch is one full pass of a model over its training data. To count without typing a list by hand, Python offers range, which hands out whole numbers on demand.

range hands out numbers
print(list(range(5))) for epoch in range(5): print("Training epoch", epoch)
Output
[0, 1, 2, 3, 4]
Training epoch 0
Training epoch 1

Training epoch 4

Two surprises in that output. The counting starts at 0, not 1, and it ends at 4, not 5. Both are deliberate. range(5) produces exactly five numbers, and computers count from zero. The wrapper list(...) is only there to display the numbers, because a range is produced lazily and does not show itself when printed.

The three forms of range

range(stop) counts from 0 up to, but not including, stop. range(start, stop) begins where you say. range(start, stop, step) jumps by step each time, and a negative step counts downwards. The rule to memorise is "the start is included, the stop is excluded".

The stop value is never produced
range(2, 7)        ->  2  3  4  5  6       (7 is NOT included)
                       ^           ^
                    start       stop - 1

range(0, 10, 3)    ->  0  3  6  9          (next would be 12)

range(5, 0, -1)    ->  5  4  3  2  1       (0 is NOT included)
How many numbers do you get? For a step of 1 it is stop minus start. So range(2, 7) gives 5 numbers.
Different forms of range
print(list(range(2, 7))) print(list(range(0, 10, 3))) print(list(range(5, 0, -1))) print(list(range(5, 0))) print(len(range(2, 7)))

[2, 3, 4, 5, 6]

The fourth line is a sad path. The default step is +1, and you cannot climb from 5 up to 0, so Python gives you an empty range. It does not complain. The block of a loop over it would run zero times.

Off-by-one traps

An off-by-one error means being wrong by exactly one: one iteration too many or too few. It is the number one range mistake. If a person says "epochs 1 to 5", they mean five epochs numbered 1, 2, 3, 4, 5. The obvious code range(1, 5) stops one short.

The classic off-by-one

How to avoid it
  • Decide what the first and last numbers should be, for example 1 and 5.
  • Make the stop one larger than the last number you want: range(1, 6).
  • Check the count with stop - start: 6 - 1 = 5 numbers. If that is not the count you wanted, adjust.

Only whole numbers are allowed in a range. Python reports a clear error if you slip in a float.

What does list(range(3, 8, 2)) produce?
[3, 5, 7]. It starts at 3, adds 2 each time (3, 5, 7), and stops before reaching 9, which is past the stop of 8.
You want to print the numbers 10, 9, 8, ..., 1. Which range call do you need?

Recap

  • Start is included, stop is excluded. Count = stop - start when the step is 1.
  • A range that cannot reach the stop is empty, not an error.
  • Off-by-one errors: to include the last number, add 1 to the stop.
2.9 — Loop Patterns: Accumulator, Counter, Flag, Best-So-Far

A loop that only prints is not very useful. The real power comes when a loop builds up an answer as it goes. Say we want the average of six losses, without any built-in help. A loop visits one number at a time, so it has to remember what it has seen. The trick is a variable created before the loop that each iteration updates. Four such shapes appear in almost every program you will write, so they are worth learning by name.

The four loop patterns
ACCUMULATOR (running total)      COUNTER (how many?)
  total = 0                        n = 0
  for x in data:                   for x in data:
      total += x                       if cond:
                                           n += 1

  found = False                    best = float("inf")
  for x in data:                   for x in data:

          found = True                     best = x
Every pattern has the same skeleton: set up a starting value before the loop, update it inside the loop, use it after the loop.
The accumulator

An accumulator is a variable that collects a running result, like the total on a shop till. It starts at 0. Each iteration adds the current item: total += x is a shortcut for total = total + x.

An accumulator, with the state shown
losses = [0.82, 0.61, 0.45, 0.30] total = 0 for loss in losses: total += loss print(f"added {loss:.2f} -> total is now {total:.2f}") print("Average:", round(total / len(losses), 4))

The total column carries information from one iteration to the next. That is how a loop "remembers". After the loop, dividing by len(losses), which is the number of items, gives the average.

The counter, the flag, and best-so-far

A counter is an accumulator that adds 1 whenever a condition is met, so it counts things. A flag is a bool that starts False and is switched to True when something happens, so afterwards you can ask "did it ever happen?". A best-so-far variable remembers the smallest or largest value seen. To start a search for the minimum, we need a number bigger than any real value. float("inf") is Python's "infinity", larger than every number, so the first real value always beats it.

Counter, flag and best-so-far in one loop
accuracies = [0.72, 0.81, 0.79, 0.95, 0.66] good_count = 0 found_perfect = False best = float("inf") worst = 0 for acc in accuracies: if acc >= 0.8: good_count += 1 if acc == 1.0: found_perfect = True if acc < best: best = acc if acc > worst: worst = acc print("Models at 80% or better:", good_count) print("Any perfect model?", found_perfect) print("Lowest:", best, "Highest:", worst)
Output

Lowest: 0.66 Highest: 0.95
What Python does, line by line
  • Before the loop, four variables are set to safe starting values. They are the "memory" of the loop.
  • For each accuracy, three or four independent if checks may update them. Note the independent ifs: we want every check to run, not just the first.
  • After the loop, the variables hold the final answers: 2 good models, no perfect one, lowest 0.66, highest 0.95.
Two classic mistakes

Resetting the accumulator inside the loop. If total = 0 is written inside the block, it goes back to zero every iteration, so only the last item survives. Never creating it at all gives a clear error.

Initialising in the wrong place
losses = [0.82, 0.61, 0.45] for loss in losses: total = 0 total += loss print("Total should be 1.88, got:", total)
Output
Total should be 1.88, got: 0.45
Forgetting to create the accumulatorread-only

What Python says

    running_total += loss
    ^^^^^^^^^^^^^

The error message names the missing variable. running_total += loss needs an existing running_total to add to, so create it before the loop. (If you run this in the page console right after another block that created a variable with the same name, no error appears, because the console remembers earlier runs. That is why this example uses a fresh name.)

Which starting value would you give a counter, and which one an accumulator that multiplies numbers together?
A counter starts at 0. A product accumulator starts at 1, because multiplying by 1 changes nothing, whereas starting at 0 would make the answer 0 forever.
Why does the best-so-far example start best at float("inf") instead of 0?
Every real accuracy is below infinity, so the first one always replaces it. Starting at 0 would never be beaten by a smaller number, so the minimum would stay wrongly at 0.

Recap
  • Most loops build an answer: set a starting value before the loop, update it inside, read it after.
  • Accumulator total += x, counter n += 1 under an if, flag found = True, best-so-far with float("inf") as the initial minimum.
  • Initialise outside the loop. Inside the loop it resets each time; missing altogether it raises NameError.
2.10 — while Loops: Repeating Until the Condition Changes

A for loop needs to know its material in advance: a list, or a range(5). But often you do not know how many rounds you need. "Keep training until the loss is small enough" could take 7 rounds or 700. You would have to guess a number for range, and guessing wrong wastes time or stops too early.

A while loop repeats as long as its condition stays True. Before every round, Python asks the condition again. It is like stirring paint: while it is still lumpy, keep stirring, and stop the moment it is smooth. You do not count the stirs in advance.

The smallest while loop

2.11 — Infinite Loops, and Choosing Between for and while

Here is the danger of while. If the condition never becomes False, the loop never ends. This is an infinite loop, and the program appears to freeze. A for loop over a list cannot do this, since the list runs out. A while loop can, because you are in charge of making the condition change.

Below is a loop that forgot to shrink the loss. To keep this page safe, we added an emergency exit that stops the loop after 5 rounds. The break line is explained in the next section: it means "leave the loop right now".

An infinite loop, caught by a safety exit
loss = 0.9 rounds = 0 while loss > 0.1: rounds += 1 print("round", rounds, "loss is still", loss) if rounds == 5: print("Emergency exit: the loss never changes!") break
Output
round 1 loss is still 0.9
round 2 loss is still 0.9
round 3 loss is still 0.9
round 4 loss is still 0.9
round 5 loss is still 0.9
Emergency exit: the loss never changes!

Without the last three lines, this program would print forever. The condition loss > 0.1 never changes, because nothing in the block touches loss.

Three common causes
Why loops do not end
1. Variable never updated
     while loss > 0.1:
         epochs += 1          <- loss is never touched

2. Updated in the wrong direction
     while loss > 0.1:
         loss = loss + 0.1    <- moves away from 0.1

3. Condition can be skipped over
     while count != 10:
         count += 3           <- 0, 3, 6, 9, 12, ...
In every case the condition stays True forever. Ask yourself: what changes each round, and does it move toward making the condition False?

The third cause is sneaky. Counting by 3 from 0 goes 0, 3, 6, 9, 12. It jumps over 10, so count != 10 is always True. Using < instead of != is safer: count < 10 stops even when you overshoot.

The skipped-over condition
count = 0 rounds = 0 while count != 10: count += 3 rounds += 1 if rounds == 6: print("Stuck: count is", count, "and never equals 10") break print("Safe version:") count = 0 while count < 10: count += 3 print("Stopped with count =", count)
Output
Stuck: count is 18 and never equals 10
Safe version:
Stopped with count = 12
How to stop a runaway loop

In a terminal, press Ctrl+C. Python interrupts the program and prints KeyboardInterrupt. On this course page, Python runs inside your browser tab, so a truly infinite loop freezes the tab, and the only cure is to reload the page (your saved progress is kept). Prevention is far better. Put a limit in the condition, so the loop has two ways to end: "the goal is reached" or "the budget of rounds is used up".

Prevention: a maximum number of rounds
loss = 0.9 epoch = 0 max_epochs = 50 while loss > 0.1 and epoch < max_epochs: epoch += 1 loss = loss * 0.99 print("Stopped at epoch", epoch, "with loss", round(loss, 3))
Output
Stopped at epoch 50 with loss 0.545
for or while? A simple rule
QuestionUse
Do I have a list, a string, or a known count (range(n))?for
Do I know beforehand how many rounds I need?for
Do I repeat until something happens, with an unknown number of rounds?while
Is the stopping rule a condition on a changing value, such as loss below a goal?while

Both can do most jobs, but for is safer, because it is bounded by its data. Choose for whenever you can, and while when the stopping point depends on something that changes during the loop. Real training code often uses both: a for over epochs with a break when the model has stopped improving, which is exactly the mini project.

What is the very first thing to check when a while loop never ends?
Whether something inside the block changes a variable used by the condition, and in the right direction so the condition can eventually become False.
Why is while count < 10 safer than while count != 10 when counting by 3?
Counting by 3 jumps over 10 (9, then 12). With <, the value 12 makes the condition False and the loop ends. With !=, the condition is True forever.
Try it. In the prevention block, change 0.99 to 1.0 so the loss never shrinks. Confirm that the loop still ends, by the epoch limit.
Recap
  • A while loop that never makes its condition False is an infinite loop.
  • Causes: not updating, updating the wrong way, or a != test that gets skipped over.
  • Stop a runaway with Ctrl+C in a terminal; reload the page here. Better: add a maximum-rounds limit to the condition.
  • Use for when you have data or a known count, and while when you repeat until something happens.
2.12 — break and continue: Skipping and Stopping

Real data is messy. A sensor fails and leaves a gap. A form is submitted half empty. In Python, a missing value is often None (section 2.3). Watch what happens when a loop tries to add up scores that contain one.

A missing value breaks the loopread-only
scores = [0.9, 0.85, None, 0.77] total = 0 for s in scores: total += s
What Python says
Traceback (most recent call last):
  File "<exec>", line 5, in <module>
    total += s
TypeError: unsupported operand type(s) for +=: 'float' and 'NoneType'

The loop crashed at the third item, because you cannot add nothing to a number. What we want is "if this item is missing, skip it and move on". That is the job of continue, one of two keywords that let you steer a loop from the inside.

continue means "abandon the rest of this round and go straight to the next item". Picture a factory conveyor belt. A damaged part arrives, a worker pulls it off, and the belt carries on. break is the emergency stop: "leave the loop entirely, right now". The rest of the items are never looked at.

continue skips a round
scores = [0.9, 0.85, None, 0.77, None, 0.95] valid = [] for s in scores: if s is None: print("skipping a missing value") continue valid.append(s) print("Valid scores:", valid)
Output
skipping a missing value
skipping a missing value
Valid scores: [0.9, 0.85, 0.77, 0.95]
What Python does with the None items
  • For 0.9, the test s is None is False, so the continue is not run. The next line appends 0.9 to the list valid. The .append method adds an item to the end of a list.
  • For the first None, the test is True. Python prints the message, and continue sends it straight to the next item, so the append line is skipped.
  • The loop carries on until the list is used up. Only real numbers were appended.
break stops the search
valid = [0.9, 0.85, 0.77, 0.95, 0.60] for i in range(len(valid)): print("checking index", i) if valid[i] < 0.8: print("First low score:", valid[i], "at index", i) break print("Search finished")
Output
checking index 0
checking index 1
checking index 2
First low score: 0.77 at index 2
Search finished

Only three indexes were checked. Once the first score below 0.8 was found, break ended the loop, and indexes 3 and 4 were never touched. That saves work when the list is huge. The valid[i] notation picks the item at position i, counting from 0, just like range.

continue versus break
continue                            break
--------                            -----
for item in items:                  for item in items:
    ...                                 ...
    continue  ---+                      break  -----------+
    ...          | skipped              ...              | skipped, and
    ...          |                      ...              | all later items
  <--------------+                    <-- loop is over ---+
  go to the NEXT item                 continue after the loop
continue ends only this round. break ends the whole loop.
Using them in a while loop, and the trap

Both keywords work in while loops too. Here we simulate training and skip a few "corrupted" epochs, whose numbers we keep in a set. A set, written in curly braces like {2, 4}, is a collection that is quick to ask "is this in there?" with in. There is a trap: continue jumps back to the condition immediately, so any line after it is skipped, including a counter update. Update the counter before the continue.

continue and break inside while
corrupted = {2, 4} epoch = 0 while epoch < 10: epoch += 1 if epoch in corrupted: print("epoch", epoch, "corrupted, skipping") continue print("epoch", epoch, "trained") if epoch == 5: print("Enough training, stopping") break
Output

epoch 2 corrupted, skipping
epoch 3 trained
epoch 4 corrupted, skipping

If epoch += 1 had come after the continue, epoch 2 would be found corrupted, continue would jump back without adding 1, and the loop would meet epoch 2 forever. That is an infinite loop, made by a misplaced line.

What does the loop for i in range(5): if i == 3: continue; print(i) print?
It prints 0, 1, 2, 4. When i is 3, continue skips the print and moves to the next number. This is the same idea as the quiz question at the end of the chapter.
What is the difference between break and continue?
continue skips the rest of the current round and carries on with the next item. break ends the loop completely.

Recap
  • continue skips the rest of this round, and the loop carries on with the next item.
  • break leaves the loop immediately; nothing after it in the block runs, and the remaining items are never visited.
  • Both are usually inside an if, so they trigger only on a special case.
  • In a while loop, update the counter before continue, or the loop may never end.
2.13 — Nested Loops: A Loop Inside a Loop

Machine-learning engineers often try every combination of settings. Say two learning rates (how big a step the model takes when it learns) and three batch sizes (how many examples it looks at per step). That is 2 x 3 = 6 combinations. Writing six separate lines is tedious, and adding a fourth batch size means editing more lines.

A loop can contain another loop. This is called nesting. Think of a clock: for each hour, the minute hand goes all the way round the dial. The outer loop picks one learning rate. For each one, the inner loop runs through all the batch sizes from start to end before the outer loop moves on.

The smallest nested loop
for lr in [0.1, 0.01]: for batch_size in [16, 32, 64]: print("learning rate", lr, "batch size", batch_size)
Output

learning rate 0.01 batch size 64

              +---------+---------+---------+

              +---------+---------+---------+
The numbers show the order of the prints. The inner loop sweeps along a row; the outer loop moves down to the next row.
What Python does, line by line
  • The outer loop sets lr = 0.1. The inner loop then runs completely: 16, 32, 64. That gives prints (1), (2) and (3).
  • The inner loop is finished, so control goes back to the outer loop, which sets lr = 0.01.
  • The inner loop starts again from its beginning and runs completely once more, giving (4), (5) and (6).
  • The outer list is used up, so the whole thing ends.
Counting the work

  • break and continue affect only the innermost loop.

2.14 — enumerate() and zip(): Position and Parallel Lists

Two situations come up constantly. First, you want the position of each item as well as the item, for example "epoch 3 had loss 0.45". Second, you have two lists that belong together, like a model's predictions and the true answers. Here is the awkward way to solve the first one.

Tracking the position by hand
losses = [0.82, 0.61, 0.45] position = 0 for loss in losses: print("epoch", position, "loss", loss) position += 1
Output
epoch 0 loss 0.82
epoch 1 loss 0.61
epoch 2 loss 0.45

It works, but you must remember to create and update position yourself, and forgetting either is a bug. range(len(losses)) avoids that, yet forces you to write losses[i] everywhere. Python has a tool designed for exactly this: enumerate. It hands you a pair for each item: the position first, then the value. Think of numbering the seats in a cinema as people walk in.

enumerate
losses = [0.82, 0.61, 0.45] for i, loss in enumerate(losses): print("index", i, "->", loss) for epoch, loss in enumerate(losses, start=1): print("epoch", epoch, "->", loss)
Output
index 0 -> 0.82
index 1 -> 0.61
index 2 -> 0.45
epoch 1 -> 0.82
epoch 2 -> 0.61
epoch 3 -> 0.45

The second loop passes start=1 so the numbering begins at 1, which is friendlier for epochs. In for i, loss in ..., the two names on the left take the two parts of each pair. This is called unpacking: a pair such as (0, 0.82) is split into i = 0 and loss = 0.82.

What Python does, line by line
  • enumerate(losses) prepares pairs: (0, 0.82), (1, 0.61), (2, 0.45).
  • On the first round the pair (0, 0.82) is unpacked into i and loss.
  • The block runs with those values, then the next pair is taken. The bookkeeping is done for you.

The second helper is zip. Just like the zipper on a jacket, it pulls two sides together, tooth by tooth: the first item of each list, then the second of each, and so on. This is how you compare predictions against targets, the correct answers.

zip walks two lists together
predictions = [1, 0, 1, 1, 0] targets = [1, 0, 0, 1, 0] for p, t in zip(predictions, targets): print("predicted", p, "actual", t, "match:", p == t)
Output
predicted 1 actual 1 match: True
predicted 0 actual 0 match: True
predicted 1 actual 0 match: False
predicted 1 actual 1 match: True
predicted 0 actual 0 match: True
Both at once, and the sad path

Combine them when you need the sample number too: enumerate(zip(a, b)) gives pairs whose second half is itself a pair, so we unpack as i, (p, t). The parentheses mirror the shape of the data. Then add the accumulator from section 2.9 to count the correct answers.

enumerate and zip together
predictions = [1, 0, 1, 1, 0] targets = [1, 0, 0, 1, 0] correct = 0 for i, (p, t) in enumerate(zip(predictions, targets)): if p == t: correct += 1 print("sample", i, "correct") else: print("sample", i, "WRONG") print("Accuracy:", correct / len(targets))
Output
sample 0 correct
sample 1 correct
sample 2 WRONG
sample 3 correct
sample 4 correct
Accuracy: 0.8
The shape of enumerate(zip(a, b))
predictions = [1, 0, 1]     targets = [1, 0, 0]

zip(predictions, targets)
    ->  (1, 1)   (0, 0)   (1, 0)
enumerate( zip(...) )
    ->  (0, (1, 1))   (1, (0, 0))   (2, (1, 0))

The names on the left of in must have the same shape as the data: an index, then a pair.

Sad path 1: unequal lengths. zip stops silently when the shorter list is used up, so extra items are dropped without any error. Sad path 2: a wrong unpacking shape. If you write two names but each item is a single number, Python cannot split it.

zip stops at the shorter list

The message says Python cannot unpack a "non-iterable float object". In plain words, a single number is not a pair, so it cannot be split into two names. The fix is enumerate(losses), which supplies the pairs.

What does for i, x in enumerate(["a", "b"], start=10) give for i on each round?
10, then 11. The start value only changes the counting, not which item you get.

  • zip(a, b) walks two lists in parallel, pair by pair, and stops at the shorter one.
  • Write for i, (p, t) in enumerate(zip(a, b)) when you need both, with names shaped like the data.
  • Unpacking a, b = pair splits a pair into two names.
2.15 — List and Dict Comprehensions: A Loop That Builds a Collection

A very common job is "make a new list from an old one". Say we have raw exam-style scores from 0 to 100 and want only the passing ones (60 or more). You already know how to do it with the tools from this chapter: create an empty list, loop, test, append.

Building a list with a loop
raw_scores = [45, 78, 92, 33, 88, 61, 95] passing = [] for s in raw_scores: if s >= 60: passing.append(s) print("Passing:", passing)
Output
Passing: [78, 92, 88, 61, 95]

That is four lines for a very small idea. Python has a compact form, the list comprehension, which puts the whole recipe inside square brackets. It is not a new kind of loop. It is a shorter way of writing the loop above, and it gives exactly the same result.

The same thing as a comprehension
raw_scores = [45, 78, 92, 33, 88, 61, 95] passing = [s for s in raw_scores if s >= 60] print("Passing:", passing)
Output
Passing: [78, 92, 88, 61, 95]
The loop and the comprehension, side by side
LOOP
  passing = []
  for s in raw_scores:
      if s >= 60:
          passing.append(s)

COMPREHENSION
  passing = [ s   for s in raw_scores   if s >= 60 ]
             (1)  (2)                   (3)

  (1) what to put in the new list
  (2) where the items come from
  (3) optional filter: keep only if True
Read it as English: "s, for each s in raw_scores, if s is at least 60". The pieces are the same as in the loop, just rearranged.
What Python does, line by line
  • It starts with an empty new list, which you never have to create yourself.
  • It takes each s from raw_scores, one by one, just like a for loop.
  • It evaluates the if test. If it is False, the item is dropped. If it is True, the expression at the front (here just s) is appended.
  • When the source is used up, the finished list is stored in passing.
Filter, transform, or both

The front part can do work on each item. That is a transform. Dividing every score by 100 rescales scores to the range 0 to 1, a common preparation step in machine learning. Leaving out the if keeps all items. Using both gives "transform the ones that pass".

Three shapes of comprehension
raw_scores = [45, 78, 92, 33, 88, 61, 95] normalized = [s / 100 for s in raw_scores] print("Normalized:", normalized) passing_normalized = [s / 100 for s in raw_scores if s >= 60] print("Passing, normalized:", passing_normalized) nums = [1, 2, 3, 4, 5, 6] even_squares = [n * n for n in nums if n % 2 == 0] print("Even squares:", even_squares)
Output
Normalized: [0.45, 0.78, 0.92, 0.33, 0.88, 0.61, 0.95]
Passing, normalized: [0.78, 0.92, 0.88, 0.61, 0.95]
Even squares: [4, 16, 36]

The % sign gives the remainder after division, so n % 2 == 0 is a test for even numbers. In the last line, only 2, 4, 6 pass the test, and each is squared before being kept.

Dict comprehensions

A dictionary stores pairs of a label and a value, written {label: value}; Chapter 4 covers it fully. A dict comprehension builds one the same way. You write key: value at the front. Here the front part uses a small a if condition else b expression to pick the word "pass" or "fail".

A dict comprehension
raw_scores = [45, 78, 92, 33] grades = {s: ("pass" if s >= 60 else "fail") for s in raw_scores} print(grades) print(grades[78])
Output
{45: 'fail', 78: 'pass', 92: 'pass', 33: 'fail'}
pass

Common mistake: putting else in the filter position. The filter at the end of a comprehension only decides whether to keep an item, so it has no else. If you want a different value for the other case, that choice goes at the front, in the a if condition else b form.

else at the end of a comprehensionread-only
raw_scores = [45, 78, 92] labels = ["pass" for s in raw_scores if s >= 60 else "fail"]
What Python says
  File "<exec>", line 2
    labels = ["pass" for s in raw_scores if s >= 60 else "fail"]
                                                    ^^^^
SyntaxError: invalid syntax
The correct way: the choice goes at the front
raw_scores = [45, 78, 92] labels = ["pass" if s >= 60 else "fail" for s in raw_scores] print(labels)
Output
['fail', 'pass', 'pass']

When should you keep the plain loop? Whenever the body needs several statements, or when a comprehension would be hard to read out loud. Readability is the goal, not fewer lines.

Rewrite result = [] / for n in [1,2,3]: / result.append(n * 10) as a comprehension.
result = [n * 10 for n in [1, 2, 3]], which gives [10, 20, 30]. The expression is the appended value, and the for part stays the same.
What does [x for x in [5, 8, 12] if x > 100] give?
An empty list, []. No item passes the test, and that is not an error.

Recap
  • A comprehension builds a new list in one line: [expression for item in source if test].
  • It is the same recipe as a loop with append. Read it aloud as English.
  • Front part = transform, if at the end = filter, a if c else b at the front = choose between two values.
  • {key: value for ...} builds a dictionary. Keep a plain loop when the body gets complicated.
2.16 — Set and Generator Comprehensions, and Nested Comprehensions

The same for ... if recipe works with other brackets, and each choice of bracket changes what you get. Square brackets build a list, curly braces without a colon build a set, and round brackets build a generator. First the problem: a list of labels with repeats, and you want to know which different labels exist.

The unique labels, the long way
labels = ["cat", "dog", "cat", "bird", "dog", "cat"] unique = [] for label in labels: if label not in unique: unique.append(label) print(unique)
Output
['cat', 'dog', 'bird']

A set is a collection that keeps only one copy of each value and does not care about order. A set comprehension uses curly braces, and duplicates disappear on their own. Because a set has no fixed order, wrap it in sorted(...) when you want the same printed order every time.

Set comprehension
labels = ["cat", "dog", "cat", "bird", "dog", "cat"] unique_labels = {label for label in labels} print(sorted(unique_labels)) print(len(unique_labels), "different labels") lengths = {len(label) for label in labels} print(sorted(lengths))
Output
['bird', 'cat', 'dog']
3 different labels
[3, 4]

The last two lines show a set of word lengths: "cat" and "dog" both have length 3, so 3 appears once, next to 4 for "bird".

Generator expressions: values on demand

A generator expression has round brackets. Instead of building the whole list at once, it prepares a recipe and hands out one value at a time when something asks. This matters for big data: a list of ten million items fills memory, while a generator holds only one item at a time. It fits naturally with functions that read values one by one, such as sum, max and min.

A generator feeding sum
scores = [45, 78, 92, 33, 88] print(sum([s for s in scores if s >= 60])) print(sum(s for s in scores if s >= 60)) print(max(s / 100 for s in scores))
Output
258
258
0.92

Both sum lines give 258. The first builds a temporary list, the second does not. When a generator is the only thing inside a function call, its own brackets can be left out, as in sum(s for ...).

A generator is single-use, like a ticket that is stamped once. After it has handed out all its values, it is empty. Asking again gives nothing, and no error.

A generator is used up after one pass
scores = [45, 78, 92] gen = (s for s in scores) print(type(gen)) print(list(gen)) print(list(gen))
Output
<class 'generator'>
[45, 78, 92]
[]
What Python does, line by line
  • Line 2 creates the generator, but computes nothing yet. It is a recipe.
  • list(gen) asks for every value. The generator produces 45, 78, 92, and is now used up.
  • The second list(gen) finds nothing left, so it returns an empty list.
Nested comprehensions

A comprehension can have two for parts, to walk a list of lists and flatten it. The important rule: the for parts are written in the same order as the nested loops would be, the outer one first.

Nested loops versus nested comprehension
LOOPS
  flat = []
  for batch in batches:          <- outer
      for item in batch:         <- inner
          flat.append(item)

COMPREHENSION
  flat = [ item   for batch in batches   for item in batch ]
                  (outer first)          (inner second)
Read the for parts left to right, and it is the same order as reading the loops top to bottom.
Flattening a list of lists
batches = [[1, 2], [3, 4, 5], [6]] flat_loop = [] for batch in batches: for item in batch: flat_loop.append(item) print(flat_loop) flat = [item for batch in batches for item in batch] print(flat)
Output
[1, 2, 3, 4, 5, 6]
[1, 2, 3, 4, 5, 6]

Common mistake: the order of the two for parts reversed. Then batch is used before it has been created.

The for parts in the wrong orderread-only
batches = [[1, 2], [3, 4, 5], [6]] flat = [item for item in batch for batch in batches]
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
    flat = [item for item in batch for batch in batches]
                              ^^^^^
NameError: name 'batch' is not defined

Deeply nested comprehensions become puzzles. If you cannot read one aloud in a single breath, write the loops out instead.

What is the difference between [x for x in data] and {x for x in data}?
The first is a list and keeps every item in order, including repeats. The second is a set: duplicates vanish, and the order is not guaranteed.
Why does the second list(gen) in the example print []?
A generator is single-use. The first list(gen) consumed all its values, so nothing is left for the second.

Recap
  • [...] builds a list, {...} (no colon) builds a set that removes duplicates, (...) builds a lazy generator.
  • Use sorted(a_set) for a predictable print order.
  • A generator hands out values on demand, saves memory with sum, max and friends, and can be used only once.
  • In a nested comprehension the for parts go in the same order as the nested loops: outer first.
2.17 — for...else and the Walrus Operator

Two smaller tools finish the chapter. Both remove a bit of clutter you have already met. The first clutter is the flag from section 2.9 in a search: a variable that says "did I find it?". To search a list of accuracies for a model at or above 95%, the flag version needs three extra ideas: create the flag, set it, test it afterwards.

A search with a flag
accuracies = [0.72, 0.81, 0.79, 0.85] found = False for acc in accuracies: if acc >= 0.95: print("Found a model above 95%!") found = True break if not found: print("No model reached 95% accuracy.")
Output
No model reached 95% accuracy.

Python lets a loop have its own else block, and its meaning is not what the word suggests. The else of a loop runs only if the loop finished without hitting break. Read it as "no break happened". It turns "search, and do something if not found" into one structure. Think of looking for your keys in every pocket: if you never stop early (never break), you end up at the else: "keys not found".

for...else, with a miss and with a hit
accuracies = [0.72, 0.81, 0.79, 0.85] for acc in accuracies: if acc >= 0.95: print("Found a model above 95%!") break else: print("No model reached 95% accuracy.") accuracies.append(0.97) for acc in accuracies: if acc >= 0.95: print("Found a model above 95%!", acc) break else: print("(not printed: a break happened)")
Output
No model reached 95% accuracy.
Found a model above 95%! 0.97
What Python does, line by line
  • First search: no value passes the test, so break never runs. The loop ends naturally and Python runs the else block.
  • accuracies.append(0.97) adds a fifth value at the end of the list.
  • Second search: the fifth value passes, break runs, and Python skips the else block entirely.

The else lines up with for, not with the if inside it. That is the classic slip: an else indented under the if means something quite different, "for this one item, it did not pass", and would print at every non-matching item.

Which else is which?
for acc in accuracies:
    if acc >= 0.95:
        ...
        break
    else:         <- belongs to the IF: runs for every item that
        ...          fails the test
else:             <- belongs to the FOR: runs once, only if no
    ...              break happened
The indentation tells Python which statement an else belongs to.
The walrus operator :=

The second bit of clutter is computing something twice. Suppose you want to print the number of scores, but only when there are many of them. The plain way asks for len(scores) in the test and again in the message. The walrus operator :=, named because it looks like a walrus lying on its side, assigns a value and also uses it in the same expression. It is a normal = that can live inside a condition.

Assign and test at the same time
scores = [0.9, 0.8, 0.7, 0.95, 0.6] n = len(scores) if n > 3: print("Plain way, n =", n) if (count := len(scores)) > 3: print("Walrus way, count =", count)
Output
Plain way, n = 5
Walrus way, count = 5

Both do the same. In the walrus form, Python computes len(scores), stores the result in count, and compares that result with 3, all in one line. The parentheses around the assignment are needed here. The count name stays available afterwards, just like any variable.

The walrus inside a while condition
readings = [12, 45, 99, 7, 150] i = 0 while i < len(readings) and (r := readings[i]) < 100: print("Reading:", r) i += 1 print("Stopped at position", i, "because", readings[i], "is too big")
Output
Reading: 12
Reading: 45
Reading: 99
Reading: 7
Stopped at position 4 because 150 is too big

This loop reads values until one reaches 100. The walrus grabs readings[i] once, tests it, and lets the block use it as r. Thanks to short-circuiting from section 2.5, readings[i] is only reached when i < len(readings) holds, so we never index past the end.

Common mistake: a bare walrus statement. As a stand-alone line, := is not allowed. Use plain = there.

A walrus on its own lineread-only
count := 5
What Python says
  File "<exec>", line 1
    count := 5
          ^^
SyntaxError: invalid syntax

Use the walrus sparingly. When it makes a line harder to read than two simple lines, use the two lines.

In a for...else, when does the else block run?
Only when the loop finishes all its items without executing a break. It also runs when the loop had nothing to visit at all.
What does if (n := len(items)) > 3: do that if len(items) > 3: does not?
It also stores the length in n, so the block can use n without computing len(items) again.
Try it. Change the reading 99 to 199 in the last block. Where does the loop stop now?
Recap
  • The else of a for loop runs only if the loop finished without a break. It replaces the "found" flag in searches.
  • The else must line up with for. Under the if it means something different.
  • := (walrus) assigns a value and uses it in one expression, for example if (n := len(x)) > 3:.
  • Both tools are optional; use them when they make code shorter and clearer.
Chapter 2 Summary
  • Conditions (2.1) are questions Python answers with True or False. Use == to compare, 0 <= x <= 1 for ranges, and a tolerance for computed floats.
  • if / else (2.2) runs a block only when the condition holds. The colon and four-space indentation define the block.
  • Truthiness (2.3): zero, empty things, None and False are falsy; everything else is truthy. Use is None when 0 is a real value.
  • and / or / not (2.4) combine conditions; precedence is not, and, or. Short-circuiting (2.5) stops as soon as the answer is known, so put guards on the left.
  • elif chains (2.6) take the first True branch, so put the strictest test first. Nest only when the second question depends on the first.
  • for loops (2.7) repeat over a collection; trace them with a table. range (2.8) includes the start and excludes the stop.
  • Loop patterns (2.9): accumulator, counter, flag and best-so-far, each created before the loop.
  • while loops (2.10, 2.11) repeat until the condition is False. Make sure the block changes it, add a maximum-rounds limit, and prefer for when you have data or a known count.
  • break and continue (2.12): stop the loop, or skip to the next round. Nested loops (2.13) run the inner loop fully for each outer round.
  • enumerate() and zip() (2.14) give positions and walk lists in parallel; zip stops at the shorter list.
  • Comprehensions (2.15, 2.16) are compact loops that build a list, dict, set or generator. for...else and := (2.17) remove a search flag and a repeated calculation.
