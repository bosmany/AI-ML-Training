OOP Part 5:
Building, Testing & Debugging a Real Program

You now know every building block of object-oriented Python. This last OOP chapter is about doing the real thing: planning a program with several classes, building it in safe stages, proving it works with automatic tests, recognising the classic bugs before they bite, and reshaping a messy script into clean classes without breaking it. It also shows you how to read classes other people wrote, which is what you will do all the time from here on.

5.1 — From a Written Idea to a Plan of Classes

Welcome to the last chapter of the object-oriented track. Here is a very short recap, because everything below leans on it. A class is a blueprint and an object is one thing built from it, keeping its own facts in attributes. A method is a function that belongs to a class and works on one object through self. Encapsulation means a class keeps its details tidy behind a few clear methods. Inheritance (class Child(Parent)) lets one class start from another, and composition lets an object hold other objects as parts. In this chapter you will use all of that on a program with several classes that cooperate, and you will learn how to plan it, test it, debug it and reshape it.

Real programs start as a few sentences from a person, not as classes. Someone says: "Our small library lends books to members. Each book has a title and an author. A member has a name and may borrow at most two books at a time. A book can be on loan to only one member at a time. Every loan lasts 14 days. If a book comes back after its due day, the member owes a fine of 25 cents for each late day." Your job is to turn those sentences into code. The mistake almost everyone makes first is to start typing.

The problem first. Here is what typing without a plan often looks like: plain dictionaries and functions, with each fact stored wherever it was convenient at the moment. Run it and read the last line.

Starting to code with no plan
books = {"Dune": None, "Emma": None} # title -> who has it (None = on the shelf) loans_of = {"Asha": []} # member name -> titles they hold def checkout(title, name): books[title] = name loans_of[name].append(title) def checkout_at_desk(title, name): # written a week later, in a hurry books[title] = name # forgot to update loans_of checkout("Dune", "Asha") checkout_at_desk("Emma", "Asha") print(books) print(loans_of) book_says = sum(1 for who in books.values() if who == "Asha") print("Asha's list says", len(loans_of["Asha"]), "but the books say", book_says)

The program disagrees with itself. The same fact ("Asha holds Emma") is stored in two places, and one code path updated only one of them. Nothing crashed, so nobody noticed. Now imagine adding the two-book limit: which of the two functions would you put it in? Both? Only one? The honest answer is "I do not know where this rule lives", and that confusion is exactly what planning removes.

The idea. Before writing code, answer four questions on paper. They are old, simple and surprisingly effective. First, what are the things? Underline the nouns in the requirement. Second, what does each thing know? That is its data, which will become attributes. Third, what can each thing do? Those are actions, which will become methods. Fourth, who talks to whom? When one object needs help from another, write that down. Programmers call a table with these answers a CRC card: Class, Responsibility, Collaborators. Think of a team on a sports field. Each player has one job, and the plan says who passes the ball to whom.

Not every noun becomes a class. In our story the nouns are library, book, title, author, member, name, loan, day and fine. A title is just text, so it becomes an attribute of Book. The same goes for author and name. A day is a number. The fine is a number that can be worked out from other facts, so we will compute it rather than store it. That leaves four real things: Library, Book, Member, Loan. A loan is easy to miss, because it is a noun hiding in the sentence "every loan lasts 14 days". It is the record that links one member, one book and one due day, and it is the natural home for the fine.

Each card is one class. "Knows" becomes attributes, "does" becomes methods, and "works with" tells you which objects will hold references to each other.

You can even keep the cards as data, which is handy for printing a plan and checking it against the story. This block is not the program itself. It is the plan, written in Python so that you can see the shape.

The plan as data
cards = { "Book": {"knows": ["title", "author", "its loan"], "does": ["say if it is on the shelf"]}, "Member": {"knows": ["name", "list of loans"], "does": ["say if it may borrow more"]}, "Loan": {"knows": ["book", "due day"], "does": ["work out the fine"]}, "Library": {"knows": ["all its books"], "does": ["check out", "take back"]}, } for name, card in cards.items(): print(name) for part in ("knows", "does"): print(" ", part + ":", ", ".join(card[part]))

The last planning step is to give every rule in the requirement exactly one home. A rule with no home gets forgotten. A rule with two homes gets copied, and the copies drift apart, just like the two dictionaries above. Ask of each rule: which object has the facts needed to enforce it?

Every rule gets exactly one owner
rules = [ ("A member may hold at most two books", "Member (it knows its own loans)"), ("A book is on loan to one person only", "Library (it can look at the book before lending)"), ("Every loan lasts 14 days", "Library (it is the lending policy)"), ("Late returns cost 25 cents per day", "Loan (it knows the due day)"), ] for rule, owner in rules: print(f"{rule:<38} -> {owner}")
  • Read the requirement and underline every noun. Cross out the ones that are just plain values (title, name, day).
  • For each thing that is left, write what it knows (attributes) and what it does (methods).
  • Draw arrows between things that need each other. Those arrows are the "works with" column.
  • Give each rule in the story one owner: the object that already holds the facts the rule needs.
  • Only now start coding, one small class at a time. The next section does exactly that.
Who holds a reference to whom
  Library ──── has many ────► Book
     │                         ▲
     │ has many               │ points at
     ▼                         │
  Member ──── has many ───► Loan ─────────┘
A Member holds a list of Loans. Each Loan points at one Book. The Library holds all the Books. Arrows show "holds a reference to", which is the composition you learned in OOP 4.

Common mistakes. The first is defining classes in the wrong order. Python runs a file from top to bottom, and a name must exist before the line that uses it runs. This matters most in default values, which are evaluated the moment the def line is read:

Mistake: using a class before it is defined
try: class Loan: def __init__(self, owner=Member("nobody")): # runs while reading this line self.owner = owner except NameError as error: # catch the error so we can print it print("NameError:", error)

The try and except lines are a safety net that you will learn properly in the next section: Python runs the indented code under try, and if that code raises a NameError, it jumps to the except block instead of crashing the page. Without the net, you would see a traceback whose last line is the same message: NameError: name 'Member' is not defined. Read tracebacks from the bottom: the last line names the missing word, and the lines above show where Python was when it noticed. The fix is to define Member first, or (better) not to build objects in default values at all. The second common mistake is inventing classes that have nothing to do:

Mistake: a class with no job
class Title: def __init__(self, text): self.text = text class Book: def __init__(self, title): self.title = Title(title) # a whole object just to hold a string book = Book("Dune") print(book.title.text) # awkward: why not book.title?

A class earns its place when it has data that belongs together and behaviour, or rules to guard. A single string with no behaviour is just a string. If you are not sure, start with the plain value; promoting it to a class later is easy.

Check yourself: In the requirement, "the member owes a fine". Should fine be an attribute stored on Member, or something else?
Better to compute it. A fine depends on the due day and today's day, so store the due day (on the Loan) and calculate the fine when asked. A stored fine could go out of date.
Check yourself: Why do we write "Loan" as its own class instead of storing a due day directly on Book?
The due day belongs to one borrowing, not to the book forever. A book is lent many times. The Loan is the short-lived record of who borrowed which book and when it is due.
Try it: Change the story: "Members may also reserve a book that is on loan." Add a card for it on paper (or as a new entry in the cards dictionary): is Reservation a new class, or an attribute of Book? Write down what it knows and what it does.

Recap

  • Turn a written requirement into classes by asking: what are the things, what does each know, what can each do, who talks to whom.
  • Plain values (titles, names, numbers) stay attributes. Records that link things, like a Loan, are easy to miss.
  • A CRC card (Class, Responsibility, Collaborators) is a tiny table for one class.
  • Give every rule exactly one owner, so it is stored and enforced in one place.
  • Define classes before use, and do not create classes that have no job.
5.2 — Build It in Stages

You have a plan. The temptation now is to write all four classes in one go and hope. Resist it. The reliable way to build anything with several parts is to add one small piece at a time and run the program after every piece. If something breaks, you know it was the last thing you added, because everything before it was already working. This is called building in stages (or "increments"), and it turns a scary big job into a chain of small, checkable ones.

The problem first. Suppose you had written 150 lines across four classes and pressed Run for the first time, and the screen filled with red. Which of the 150 lines is wrong? You would be searching in the dark. The stages below each add just one idea, and each ends with a short demonstration that prints something, so you can see it work before moving on.

💡
How to run the stages: The stage blocks below build on each other, like a story told in order. When you press ▶ Run the console remembers the classes you defined, so run Stage 1, then Stage 2, and so on. If you jump ahead you will see NameError: name 'Book' is not defined. That message just means "run an earlier stage first".

Stage 1: the book and the shelf. We begin with the smallest useful thing: books that can sit on a Library shelf and be listed. A book starts with no loan, which we record as None (Python's word for "nothing here"). A Book can say whether it is on the shelf.

Stage 1: Book and Library
class Book: def __init__(self, title, author): self.title = title self.author = author self.loan = None # None means "on the shelf" def is_available(self): return self.loan is None class Library: def __init__(self): self.books = {} # title -> Book def add_book(self, title, author): self.books[title] = Book(title, author) def titles_on_shelf(self): return [b.title for b in self.books.values() if b.is_available()] lib = Library() lib.add_book("Dune", "Herbert") lib.add_book("Emma", "Austen") print(lib.titles_on_shelf())
  • Library() creates an object whose books attribute is an empty dictionary.
  • Each add_book call builds a Book and stores it under its title, so we can find it fast later.
  • titles_on_shelf() loops over the stored books and keeps the titles of those whose is_available() is True.
  • Both loans are None, so both titles are listed: ['Dune', 'Emma'].

Stage 2: members and loans. Now we add the two classes that record borrowing. A Loan ties one book to a due day. A Member keeps a list of loans. We also teach the Library to check_out a book. Note that the current day is passed in as a number (today). The program never asks a real clock. That choice matters: a program that reads the real clock gives a different answer every day, which makes it very hard to test. With a passed-in day, "day 1" is always day 1. (A real system would use dates, but the idea is identical.) We must redefine Library in full because we are adding a method to it.

Stage 2: Loan, Member and a first check_out
class Loan: def __init__(self, book, due_day): self.book = book self.due_day = due_day class Member: def __init__(self, name): self.name = name self.loans = [] class Library: LOAN_DAYS = 14 # one shared setting for every loan def __init__(self): self.books = {} def add_book(self, title, author): self.books[title] = Book(title, author) def check_out(self, title, member, today): book = self.books[title] loan = Loan(book, today + self.LOAN_DAYS) book.loan = loan member.loans.append(loan) return loan lib = Library() lib.add_book("Dune", "Herbert") asha = Member("Asha") loan = lib.check_out("Dune", asha, today=1) print(loan.due_day, loan.book.title, asha.loans[0] is loan) print(lib.books["Dune"].is_available())

What Python does, line by line, inside check_out("Dune", asha, today=1): it looks up the Book object in self.books. It builds a Loan pointing at that book with a due day of 1 + 14 = 15. It stores the loan in two places, on the book (book.loan) and in the member's list, and hands the loan back to the caller. The printed True for asha.loans[0] is loan proves the member and the caller hold the very same object, not copies.

After Asha checks out Dune on day 1
  asha ─► Member                    lib ─► Library
          name  = "Asha"                    books = { "Dune" ─┐ }
          loans = [ ─────┐ ]                                 │
                         ▼                                    ▼
                   ┌──────────────┐      ┌─────────────────────────┐
                   │ Loan         │      │ Book                    │
                   │ due_day = 15 │      │ title = "Dune"          │
                   │ book ────────┼─────►│ author = "Herbert"      │
                   └──────────────┘◄─────┤ loan ───────────────────┘
                                         └─────────────────────────┘
Three objects, several arrows. The Loan and the Book point at each other, and the Member and the Library each keep an arrow to the same objects. Nothing is copied.

Stage 3: the rules. Right now the Library will happily lend the same book twice, and lend a member ten books. Let us see the sad path before fixing it, because the failure is exactly what the rules exist to prevent.

Sad path: nothing stops a double loan
ben = Member("Ben") lib.check_out("Dune", ben, today=2) # Dune is already with Asha! print(asha.loans[0].book is ben.loans[0].book) print(len(ben.loans), len(asha.loans))

Both Asha and Ben now "hold" the same book. We need the Library to refuse. To refuse in Python we raise an error: a way of saying "stop, this cannot be done" that immediately leaves the current function and travels back up to whoever called it. Python already has many error types (ValueError, KeyError). We want one that means "the library rules were broken", so we create our own. Because you know inheritance, this is one short line: class LibraryError(Exception): pass builds a new kind of error that is a kind of Exception, so Python treats it like any other. The word pass means "nothing else to add".

Raising an error would crash the program if nobody dealt with it. The tool for dealing with it is try / except, and the idea takes two lines: try this code, and except (if that particular error happens) run this other code instead of crashing. Here is Stage 3 with the rules, and a demonstration that catches the refusals so we can print them.

Stage 3: the Library enforces its rules
class LibraryError(Exception): pass class Member: MAX_LOANS = 2 def __init__(self, name): self.name = name self.loans = [] def can_borrow(self): return len(self.loans) < self.MAX_LOANS class Library: LOAN_DAYS = 14 def __init__(self): self.books = {} def add_book(self, title, author): self.books[title] = Book(title, author) def check_out(self, title, member, today): if title not in self.books: raise LibraryError(f"no such book: {title}") book = self.books[title] if not book.is_available(): raise LibraryError(f"{title} is already on loan") if not member.can_borrow(): raise LibraryError(f"{member.name} has too many books") loan = Loan(book, today + self.LOAN_DAYS) book.loan = loan member.loans.append(loan) return loan

That block only defines classes, so it prints nothing. The next block uses them. Read the try / except pairs slowly: each one attempts something that should be refused and prints the refusal message.

Stage 3 in action: catching the refusals
lib = Library() for title in ["Dune", "Emma", "Ulysses"]: lib.add_book(title, "various") asha, ben = Member("Asha"), Member("Ben") lib.check_out("Dune", asha, today=1) lib.check_out("Emma", asha, today=1) for attempt in [("Dune", ben), ("Ulysses", asha), ("Missing", ben)]: try: lib.check_out(attempt[0], attempt[1], today=2) except LibraryError as error: print("Refused:", error) print(len(asha.loans), len(ben.loans))

Three refusals, three different reasons, and afterwards Asha still has exactly two loans and Ben none. The failed attempts changed nothing, because every check happens before the first change. That ordering is a habit worth keeping: check everything first, change things last. If we had appended the loan first and checked the limit afterwards, a refused checkout could leave half its work behind.

Stage 4: overdue fines. The last rule: a late return costs 25 cents per day. A Loan knows its due day, so it can work out its own fine when told today's day. We also add give_back to the Library, which removes the loan from both places and returns the fine. Again, today is passed in, so we can test a return on any day we like without waiting.

Stage 4: fines for late returns
class Loan: FEE_PER_DAY = 0.25 def __init__(self, book, due_day): self.book = book self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day) def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY class Library(Library): # keep everything from Stage 3, add give_back def give_back(self, title, member, today): book = self.books[title] loan = book.loan member.loans.remove(loan) book.loan = None return loan.fine(today) lib = Library() lib.add_book("Dune", "Herbert") asha = Member("Asha") lib.check_out("Dune", asha, today=1) # due on day 15 print("fine on day 15:", lib.give_back("Dune", asha, today=15)) lib.check_out("Dune", asha, today=20) # due on day 34 print("fine on day 39:", lib.give_back("Dune", asha, today=39))

Returning on day 15 (exactly the due day) costs nothing (it prints 0.0), because max(0, 15 - 15) is 0. Returning on day 39 is five days late, so the fine is 5 x 0.25 = 1.25. Notice we wrote class Library(Library): a new class that inherits from the old one and adds a method. It works, but each stage would stack another layer on top. In a real file you would edit the original class instead, and we will do that from now on. Here is the full story on one screen, as a scripted "day at the library".

Stage 5: a scripted day at the library
lib = Library() for title, author in [("Dune", "Herbert"), ("Emma", "Austen"), ("Ulysses", "Joyce")]: lib.add_book(title, author) ben = Member("Ben") lib.check_out("Emma", ben, today=3) print("due:", ben.loans[0].due_day) print("on shelf:", sorted(b.title for b in lib.books.values() if b.is_available())) print("fine on time:", lib.give_back("Emma", ben, today=17)) lib.check_out("Ulysses", ben, today=20) print("late fine:", lib.give_back("Ulysses", ben, today=40)) print("Ben holds", len(ben.loans), "books")

Common mistakes. Three errors are very common while building in stages, and you can reproduce all of them. The first is forgetting to pass the day:

Mistake: forgetting an argument
try: lib.check_out("Dune", ben) except TypeError as error: print("TypeError:", error)

Python says the method is missing 1 required positional argument: 'today'. Read it literally: you gave two of the three things it needs (self is filled in for you). The second is forgetting self. when a method calls another method of the same class:

Mistake: calling a sibling method without self.
class SloppyLoan: def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day) def fine(self, today): return days_late(today) * 0.25 # BUG: should be self.days_late(today) try: print(SloppyLoan(15).fine(20)) except NameError as error: print("NameError:", error)

The message name 'days_late' is not defined is Python telling you it looked for a plain function called days_late and found none. Methods are reached through the object: self.days_late(today). The third is passing the day as text:

Mistake: a day that is text, not a number
loan = Loan(lib.books["Dune"], 15) try: print(loan.fine("20")) except TypeError as error: print("TypeError:", error)

You cannot subtract a number from text, and Python says so: unsupported operand type(s) for -: 'str' and 'int'. Convert at the edge of the program (int("20")) so that the classes only ever see numbers.

Check yourself: In Stage 3, why do all the if ... raise checks come before Loan(...) and book.loan = loan?
So a refused checkout changes nothing. If the program modified the book or the member first and then discovered a rule was broken, it would leave half-finished changes behind.
Check yourself: The fine is 0.25 per day late. Where in the code would you change it to 0.50, and how many places must you edit?
One place: the constant FEE_PER_DAY = 0.25 on Loan. Everything else reads it through self.FEE_PER_DAY.
Try it: Change Member.MAX_LOANS to 3 in Stage 3, re-run Stage 3 and its demonstration, and check that Asha can now borrow a third book. Then change LOAN_DAYS and check that the due day moves with it.

Recap

  • Build in stages: add one small piece, run it, print something, then move on. A failure points at the last thing you added.
  • Pass the current day in to methods instead of reading a real clock, so results are repeatable.
  • raise LibraryError(...) refuses an action, and try / except catches the refusal so the program can carry on.
  • Check every rule first, change state last, so a refusal leaves no half-done work.
  • Read a traceback from its last line. A missing argument, a missing self. and text used as a number each have a very recognisable message.
5.3 — Why Test? Automatic Tests With unittest

By now you have a small library program that seems to work. "Seems" is the important word. How do you know it works, and how will you know it still works after you change it next week? Most beginners answer with the method they already use: run it, print a few things and look. That works, right up to the point where it stops working. This section shows what goes wrong with checking by eye, and then teaches Python's built-in tool for checking automatically: unittest.

The problem first. Here is the Loan class from the last section, checked the way a beginner checks: print a few results and read them.

Checking by eye
class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day) def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY loan = Loan(15) for today in [10, 15, 16, 20, 40]: print("day", today, "fine", loan.fine(today))

Is this right? You have to remember, or work out, what each line should say: day 10 is early so 0.0, day 15 is the due day so 0.0, and so on. Nothing tells you. The program cannot flag a wrong number, because it does not know what the right number is. Now imagine 40 such lines, and a change made three weeks later. You would have to re-read every line and re-do the arithmetic in your head, and after a while you would stop looking carefully. Checking by eye does not scale, and it hides mistakes exactly when you are tired.

The idea. Write down the expected answer once, in code, and let the computer compare. A test is a tiny piece of code that runs part of your program and says what should be true. If it is true, nothing happens. If it is false, the test complains loudly. Think of a spell-checker: you do not re-read the whole essay hunting for typos; the tool underlines the wrong ones. Python already has a keyword for the simplest version, assert: assert condition does nothing when the condition is true and raises an AssertionError when it is false. You may add a message after a comma.

The smallest test: assert
class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day) def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY loan = Loan(15) assert loan.fine(15) == 0 assert loan.fine(16) == 0.25 print("two asserts passed") try: assert loan.fine(20) == 2.0, "fine for 5 days late should be 1.25" except AssertionError as error: print("AssertionError:", error)

The first two asserts passed silently, and we printed a line to prove we got there. The third one says the fine for five days late should be 2.0, which is wrong (it is 1.25), so it raised an AssertionError carrying our message. Without the try / except wrapper, the program would have stopped right there, and any later assert would never have run. That is the weakness of bare asserts: the first failure hides all the others, and you get no summary. The unittest module fixes both problems.

Your first unittest. A test in unittest is a method inside a class that inherits from unittest.TestCase. The method's name must start with test. Inside it you call assertion methods such as self.assertEqual(actual, expected). Then two lines at the bottom find every test in your class and run them. Those two lines are the same every time, so treat them as a small incantation for now.

A first TestCase
import sys, unittest class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day) def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY class LoanTests(unittest.TestCase): def test_no_fine_on_the_due_day(self): self.assertEqual(Loan(15).fine(15), 0) def test_no_fine_when_early(self): self.assertEqual(Loan(15).fine(10), 0) def test_five_days_late(self): self.assertEqual(Loan(15).fine(20), 1.25) suite = unittest.defaultTestLoader.loadTestsFromTestCase(LoanTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

Read the output. Each test gets a line ending in ok. Then a dashed line, Ran 3 tests in 0.001s (the time will differ on your machine, which is normal), and finally the word OK on a line of its own. That last word is the verdict: every test passed. Notice also that the tests ran in alphabetical order, not the order we wrote them. That is a hint about something important: tests must never depend on each other or on running in a particular order.

  • Python reads the LoanTests class. Because it inherits from TestCase, the loader knows it holds tests.
  • The loader collects every method whose name starts with test: three of them here.
  • For each test, the runner calls the method. Each assertEqual(a, b) checks a == b.
  • If a method finishes without an assertion failing, the test passes (ok). Otherwise it is reported as FAIL.
  • At the end the runner prints a summary: how many ran, and OK or FAILED.
💡

What a failing test looks like. A test suite is only useful if you can read its complaints. Below, we have introduced a bug on purpose: days_late forgot the max(0, ...) guard, so a book returned early would get a negative fine. Run it.

import sys, unittest class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return today - self.due_day # BUG: forgot max(0, ...) def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY class LoanTests(unittest.TestCase): def test_no_fine_on_the_due_day(self): self.assertEqual(Loan(15).fine(15), 0) def test_no_fine_when_early(self): self.assertEqual(Loan(15).fine(11), 0) def test_five_days_late(self): self.assertEqual(Loan(15).fine(20), 1.25) suite = unittest.defaultTestLoader.loadTestsFromTestCase(LoanTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

Start at the line that says AssertionError. The number on the left of != is what your code returned, and the right is what the test expected. The line above it points at the exact assertion in your test.

A different word appears when the code itself crashes:

An ERROR is not a FAIL
import sys, unittest class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day) def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY class LoanTests(unittest.TestCase): def test_typo(self): self.assertEqual(Loan(15).fine_amount(20), 1.25) # no such method suite = unittest.defaultTestLoader.loadTestsFromTestCase(LoanTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

Here the test asked for fine_amount, a method that does not exist, so Python raised AttributeError before the assertion could even compare anything. unittest reports that as an error (ERROR), separate from a failure (FAIL). The rule of thumb: a FAIL means the code ran and gave the wrong answer; an ERROR means the code (or the test) broke. Read the last line of the traceback in both cases.

Setting up fresh objects with setUp. Most tests need an object to poke at. Building it in every test is repetitive, and sharing one object between tests is dangerous, because one test's changes leak into the next. The method setUp solves both: the runner calls it before every single test, so each test starts with a brand-new object.

setUp: a fresh Member for every test
import sys, unittest class Member: MAX_LOANS = 2 def __init__(self, name): self.name = name self.loans = [] def can_borrow(self): return len(self.loans) < self.MAX_LOANS class MemberTests(unittest.TestCase): def setUp(self): self.member = Member("Asha") # a brand-new Member before EVERY test def test_starts_with_no_loans(self): self.assertEqual(self.member.loans, []) def test_new_member_can_borrow(self): self.assertTrue(self.member.can_borrow()) def test_full_member_cannot_borrow(self): self.member.loans = ["a", "b"] # changes only THIS test's member self.assertFalse(self.member.can_borrow()) suite = unittest.defaultTestLoader.loadTestsFromTestCase(MemberTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

The third test changed self.member.loans, yet the first test (which ran earlier, alphabetically) and the second still saw an empty list, because each got its own Member. This is the same idea as the "shared mutable thing" bugs you will meet in section 5.5, only here the runner protects you.

What the runner does for each test

   ┌──────────┐    ┌───────────────┐    ┌──────────────────────────┐

"Arrange, act, assert" is a handy way to shape one test: build what you need, do one thing, then check the result.

The assertions you will use most. All of them are methods on self, and each produces a helpful message when it fails.

Testing that the right error happens. Rules are not only about what works; they are also about what must be refused. assertRaises is used with the keyword with: the indented block underneath must raise the named error, and if it does not, the test fails. Adding as ctx lets you look at the error afterwards through ctx.exception, for example to check its message.

assertRaises: the third loan must be refused
import sys, unittest class LibraryError(Exception): pass class Member: MAX_LOANS = 2 def __init__(self, name): self.name = name self.loans = [] def take(self, loan): if len(self.loans) >= self.MAX_LOANS: raise LibraryError(f"{self.name} has too many books") self.loans.append(loan) class MemberTests(unittest.TestCase): def test_third_loan_is_refused(self): member = Member("Asha") member.take("a") member.take("b") with self.assertRaises(LibraryError) as ctx: member.take("c") self.assertEqual(str(ctx.exception), "Asha has too many books") self.assertEqual(len(member.loans), 2) suite = unittest.defaultTestLoader.loadTestsFromTestCase(MemberTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

Now the sad path: what if the limit check were missing? The test should catch that, and it does, with a very readable message.

The same test catching a missing rule
import sys, unittest class LibraryError(Exception): pass class Member: def __init__(self, name): self.name = name self.loans = [] def take(self, loan): # BUG: the limit check is missing self.loans.append(loan) class MemberTests(unittest.TestCase): def test_third_loan_is_refused(self): member = Member("Asha") for book in ["a", "b"]: member.take(book) with self.assertRaises(LibraryError): member.take("c") suite = unittest.defaultTestLoader.loadTestsFromTestCase(MemberTests) unittest.TextTestRunner(stream=sys.stdout).run(suite)

AssertionError: LibraryError not raised says exactly what happened: the third take quietly succeeded. A test suite is a safety net that catches things that "seem fine" when you look at the output.

Common mistakes. Two traps catch almost everyone. The first is comparing floating-point numbers with assertEqual. Computers store decimals like 0.1 in binary, which cannot represent them exactly, so tiny errors appear:

Mistake: assertEqual on decimals
import sys, unittest class FloatTests(unittest.TestCase): def test_exact(self): self.assertEqual(0.1 + 0.2, 0.3) def test_close_enough(self): self.assertAlmostEqual(0.1 + 0.2, 0.3) suite = unittest.defaultTestLoader.loadTestsFromTestCase(FloatTests) unittest.TextTestRunner(stream=sys.stdout).run(suite)

The exact comparison failed with 0.30000000000000004 != 0.3, while assertAlmostEqual allows for the tiny rounding difference. (Our library fines happen to be multiples of 0.25, which are exact, but use assertAlmostEqual whenever the numbers come from real arithmetic.) The second trap is a test that never runs:

Mistake: a method whose name does not start with test
import sys, unittest def fine(days_late): return days_late * 0.25 class FineTests(unittest.TestCase): def check_five_days(self): # BUG: name does not start with "test" self.assertEqual(fine(5), 999) suite = unittest.defaultTestLoader.loadTestsFromTestCase(FineTests) unittest.TextTestRunner(stream=sys.stdout).run(suite)

The output says Ran 0 tests and NO TESTS RAN. The method check_five_days holds a wrong assertion (it expects 999), yet nothing complained, because the loader only collects methods starting with test. Whenever a suite looks suspiciously quiet, look at the "Ran N tests" count and check it matches the number you wrote.

Check yourself: A test suite prints Ran 4 tests and OK, but you wrote five test methods. What is the most likely reason?
One method's name does not start with test, so it was never collected. Rename it and run again. The count in "Ran N tests" is worth checking.
Check yourself: What is the difference between FAIL and ERROR in the output?
FAIL: the code ran but an assertion was false (wrong answer). ERROR: some other exception escaped, such as AttributeError (something broke before the check).
Try it: In the "A first TestCase" block, add a fourth test called test_one_day_late that expects Loan(15).fine(16) to equal 0.25. Then change FEE_PER_DAY to 0.5 in the class and watch two tests fail. Change it back and watch them pass again.

Recap

  • Checking by eye does not scale; a test writes the expected answer down once and lets the computer compare.
  • A unittest test is a method starting with test in a class that inherits unittest.TestCase.
  • Output: ok per test, then Ran N tests and OK or FAILED. A FAIL is a wrong answer, an ERROR is a crash.
  • setUp gives every test a fresh object; assertRaises checks that an error is raised; assertAlmostEqual handles decimals.
  • If the "Ran N tests" number is lower than you expect, a test name is wrong.
5.4 — Testing Classes Well

Knowing how to write a test is only half the skill. The other half is knowing what to test and how to shape tests so they help you instead of becoming a chore. A good test suite is like a good smoke alarm: it goes off when there is a real problem, it stays quiet otherwise, and you trust it. A bad one goes off at random, or never. This section gives you five habits that keep your tests trustworthy.

Habit 1: test behaviour, not internals. The problem first. Suppose a colleague tidies up Member: instead of a list called loans it now keeps a private set of titles, because a set is faster to search. Nothing the rest of the program relies on has changed, but look at what happens to two different styles of test.

Tests that poke at the insides break for no good reason
import sys, unittest class Member: # version 2: the insides changed def __init__(self, name): self.name = name self._titles = set() # was a list called `loans` def take(self, title): self._titles.add(title) def loan_count(self): return len(self._titles) def holds(self, title): return title in self._titles class BrittleTests(unittest.TestCase): # pokes at the insides def test_take(self): m = Member("Asha") m.take("Dune") self.assertEqual(m.loans, ["Dune"]) class BehaviourTests(unittest.TestCase): # uses only the public methods def test_take(self): m = Member("Asha") m.take("Dune") self.assertEqual(m.loan_count(), 1) self.assertTrue(m.holds("Dune")) for case in (BrittleTests, BehaviourTests): suite = unittest.defaultTestLoader.loadTestsFromTestCase(case) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

The first test failed with AttributeError: 'Member' object has no attribute 'loans', even though Member still does its job perfectly. That test reached inside the object and depended on a detail (a list named loans). The second test only used the class's public doors, loan_count() and holds(), so it survived the change. The idea: a test should describe what the object promises (its behaviour), not how it happens to be built today. Then you can improve the insides freely and the tests tell you whether you broke a promise. This is encapsulation from OOP 2 paying off in a new place.

Habit 2: one idea per test. Here is a single test that checks four things at once, run against a version of Loan with a hidden bug (an accidental "grace day").

One test, four assertions: the first failure hides the rest
import sys, unittest class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day - 1) # BUG: an accidental grace day def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY class FineTests(unittest.TestCase): def test_everything_about_fines(self): loan = Loan(15) self.assertEqual(loan.fine(10), 0) self.assertEqual(loan.fine(15), 0) self.assertEqual(loan.fine(16), 0.25) self.assertEqual(loan.fine(20), 1.25) suite = unittest.defaultTestLoader.loadTestsFromTestCase(FineTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

It failed at fine(16), and that is all we learn. The assertion after it, fine(20), never ran, so we do not know whether it is also broken. Now the same checks as four small tests, each with a name that reads like a sentence:

Four small tests: the full picture
import sys, unittest class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day - 1) # BUG: an accidental grace day def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY class FineTests(unittest.TestCase): def test_early_return_costs_nothing(self): self.assertEqual(Loan(15).fine(10), 0) def test_on_the_due_day_costs_nothing(self): self.assertEqual(Loan(15).fine(15), 0) def test_one_day_late(self): self.assertEqual(Loan(15).fine(16), 0.25) def test_five_days_late(self): self.assertEqual(Loan(15).fine(20), 1.25) suite = unittest.defaultTestLoader.loadTestsFromTestCase(FineTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

Now the report tells a story: early returns and due-day returns are fine, but one day late and five days late are wrong. That pattern says "the first late day is being forgiven", which points straight at an off-by-one in days_late. Small, well-named tests give you a diagnosis, not just an alarm. A good test name says what should happen: test_on_the_due_day_costs_nothing is far more useful than test2.

When many checks share the same shape and differ only in their numbers, writing a separate method for each is heavy. self.subTest(...) lets one loop run many cases and still report each failing case separately, labelled with the values you give it.

subTest: a table of cases, reported one by one
import sys, unittest class Loan: FEE_PER_DAY = 0.25 def __init__(self, due_day): self.due_day = due_day def days_late(self, today): return max(0, today - self.due_day - 1) # BUG: grace day def fine(self, today): return self.days_late(today) * self.FEE_PER_DAY class BoundaryTests(unittest.TestCase): def test_days_around_the_due_day(self): cases = [(14, 0), (15, 0), (16, 0.25), (17, 0.5)] # (today, expected fine) for today, expected in cases: with self.subTest(today=today): self.assertEqual(Loan(15).fine(today), expected) suite = unittest.defaultTestLoader.loadTestsFromTestCase(BoundaryTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

The report lists (today=16) and (today=17) as separate failures and the others passed. Notice the choice of cases: the day before the due day, the due day itself, and the days just after. That leads to habit 3.

Habit 3: test the edges. Bugs love boundaries, the places where behaviour changes. Programmers use a simple checklist of three kinds of edge. Empty: what happens with no data (an empty library, an empty list)? Boundary: the exact value where a rule flips (the due day itself, the second book when the limit is two, the third book). Invalid: input that should be refused (a blank name, a negative number). Middle-of-the-road cases rarely fail; edge cases often do. This block covers one of each.

Empty, boundary and invalid cases
import sys, unittest class Member: def __init__(self, name): if not name.strip(): raise ValueError("a member needs a name") self.name = name self.loans = [] class Library: def __init__(self): self.books = {} def titles_on_shelf(self): return sorted(self.books) class EdgeCaseTests(unittest.TestCase): def test_empty_library_lists_nothing(self): self.assertEqual(Library().titles_on_shelf(), []) def test_blank_name_is_refused(self): with self.assertRaises(ValueError): Member(" ") def test_normal_name_is_accepted(self): self.assertEqual(Member("Asha").name, "Asha") suite = unittest.defaultTestLoader.loadTestsFromTestCase(EdgeCaseTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

Habit 4: keep the outside world out of your tests. Some code talks to things you do not control: it sends emails, writes files, reads the clock, calls a website. Tests that do those things are slow, unpredictable and can have side effects (imagine your test suite emailing real people). The remedy uses composition from OOP 4: the Library does not send email itself; it is given a notifier object with a send method. In the real program we hand it a real one. In a test we hand it a fake: a tiny stand-in that has the same send method but only remembers what it was asked to send.

The real notifier does real work (here it prints)
class PrintNotifier: # the real thing: talks to the outside world def send(self, message): print("EMAIL SENT:", message) class Library: LOAN_DAYS = 14 def __init__(self, notifier): self.notifier = notifier self.on_loan = {} # title -> due day def check_out(self, title, who, today): if title in self.on_loan: raise ValueError(f"{title} is already on loan") due = today + self.LOAN_DAYS self.on_loan[title] = due self.notifier.send(f"{who}: {title} is due on day {due}") return due lib = Library(PrintNotifier()) lib.check_out("Dune", "Asha", today=1)
A fake notifier: same shape, no side effects
import sys, unittest class Library: LOAN_DAYS = 14 def __init__(self, notifier): self.notifier = notifier self.on_loan = {} def check_out(self, title, who, today): if title in self.on_loan: raise ValueError(f"{title} is already on loan") due = today + self.LOAN_DAYS self.on_loan[title] = due self.notifier.send(f"{who}: {title} is due on day {due}") return due class FakeNotifier: # a stand-in that just remembers messages def __init__(self): self.sent = [] def send(self, message): self.sent.append(message) class NotificationTests(unittest.TestCase): def setUp(self): self.fake = FakeNotifier() self.lib = Library(self.fake) def test_checkout_sends_one_reminder(self): self.lib.check_out("Dune", "Asha", today=1) self.assertEqual(self.fake.sent, ["Asha: Dune is due on day 15"]) def test_refused_checkout_sends_nothing(self): self.lib.check_out("Dune", "Asha", today=1) with self.assertRaises(ValueError): self.lib.check_out("Dune", "Ben", today=2) self.assertEqual(len(self.fake.sent), 1) suite = unittest.defaultTestLoader.loadTestsFromTestCase(NotificationTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)
Real and fake plug into the same socket
  Library ── notifier ──► PrintNotifier   (real: sends the email)
                     or
  Library ── notifier ──► FakeNotifier    (test: stores messages in a list)

  Library only calls  notifier.send(message).
  It cannot tell the difference, so the same code runs in both worlds.
This is the same "swap a part" idea as the strategy pattern in OOP 4. Because we pass the day in and pass the notifier in, the tests need no clock and no network.
  • setUp builds a fresh FakeNotifier and a Library that holds it, before each test.
  • The first test checks out one book. The Library calls self.notifier.send(...), which is really the fake's method, so the message lands in fake.sent.
  • The test compares fake.sent with the exact expected list.
  • The second test does a legal checkout, then an illegal one wrapped in assertRaises, and checks that only one message exists: a refused checkout must not notify anybody.

Habit 5: keep tests independent. Every test must set up what it needs and must not care what ran before it. The most common way to break this is sharing one object between tests. Here the shared member is created once at the top of the file:

Mistake: state shared between tests
import sys, unittest class Member: MAX_LOANS = 2 def __init__(self, name): self.name = name self.loans = [] def can_borrow(self): return len(self.loans) < self.MAX_LOANS shared = Member("Asha") # BUG: one member shared by every test class SharedStateTests(unittest.TestCase): def test_a_can_borrow_when_empty(self): self.assertTrue(shared.can_borrow()) def test_b_fill_up(self): shared.loans.extend(["x", "y"]) self.assertFalse(shared.can_borrow()) def test_c_can_borrow_when_empty(self): self.assertTrue(shared.can_borrow()) suite = unittest.defaultTestLoader.loadTestsFromTestCase(SharedStateTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

The third test is identical to the first, but it failed: AssertionError: False is not true, because the second test filled up the shared member first. In the alphabetical order the runner uses, it worked by luck for two of the three. Failures that depend on order are miserable to debug. The fix is setUp: create the Member there so that every test gets its own. Read that failure message carefully, too: False is not true is what assertTrue says when it is given a false value.

The last trap is a test that can never fail. It is worse than having no test, because it gives false confidence.

Mistake: a test that can never fail
import sys, unittest class Member: MAX_LOANS = 2 def __init__(self, name): self.name = name self.loans = ["a", "b"] # the member is FULL def can_borrow(self): return len(self.loans) < self.MAX_LOANS class SneakyTests(unittest.TestCase): def test_full_member_can_borrow(self): member = Member("Asha") self.assertTrue(member.can_borrow) # forgot the () -> can never fail def test_full_member_cannot_borrow(self): member = Member("Asha") self.assertFalse(member.can_borrow()) suite = unittest.defaultTestLoader.loadTestsFromTestCase(SneakyTests) unittest.TextTestRunner(stream=sys.stdout, verbosity=2).run(suite)

The first test says a full member can borrow, which is wrong, yet it passed. The culprit is member.can_borrow without brackets: that is the method object itself, and an object is always "truthy", so assertTrue is satisfied whatever the method would return. A good habit is to break the code on purpose once and check that your test notices. If a test still passes on broken code, it is not protecting anything.

Check yourself: A colleague renames a private attribute inside Loan. Fifteen tests fail, though nothing about how Loan behaves changed. What was likely wrong with those tests?
They tested internals (a specific attribute name) instead of behaviour (results of public methods). Rewrite them to call public methods and check what they return or raise.
Check yourself: For a rule "a member may hold at most two books", which three cases would you test?
Boundary and beyond: a member with one book can borrow (below the limit), a member with exactly two cannot (at the limit), and taking a third is refused (invalid). An empty member is the "empty" edge.
Try it: Add a third test to the notifier suite: test_message_mentions_the_due_day, which checks that fake.sent[0] contains the text "day 15" using self.assertIn("day 15", self.fake.sent[0]).

Recap

  • Test behaviour through public methods, not internal attributes, so you can change the insides safely.
  • One idea per test, with a name that reads like a sentence. Use subTest for tables of similar cases.
  • Test the edges: empty, boundary and invalid inputs. That is where bugs live.
  • Replace the outside world (email, files, clocks) with a small fake that is passed in.
  • Keep tests independent with setUp, and check that a test can really fail.
5.5 — The Bug Catalogue: Eight Classic Object Bugs

Every language has its famous traps, and object-oriented Python has about eight that catch nearly everyone. They are not signs of being a bad programmer. They are places where Python behaves in a way that makes perfect sense once you know the rule, but surprises you until you do. Learning them now, on purpose, means that when one appears in your own program at 11pm, you will recognise it in seconds. Each bug below follows the same pattern: the symptom you would see, a reproduction you can run, the reason, and the fix.

A good way to use this section: read the symptom, cover the explanation, and try to guess the cause before you scroll. Most of these bugs come from one underlying fact that you met in OOP 1 and OOP 4: names are arrows to objects, and two arrows can point at the same object.

Bug 1: a shared mutable class attribute. Symptom: you add a book to Asha's loans and Ben's loans grow too. Cause: a list was written directly in the class body. A value defined there belongs to the class, which exists once, so every object reaches the same list.

Bug 1: the list lives on the class
class BuggyMember: loans = [] # ONE list, owned by the class itself def __init__(self, name): self.name = name asha = BuggyMember("Asha") ben = BuggyMember("Ben") asha.loans.append("Dune") print("Ben's loans:", ben.loans) print("same list object:", asha.loans is ben.loans) class Member: # the fix: each object makes its own list def __init__(self, name): self.name = name self.loans = [] asha, ben = Member("Asha"), Member("Ben") asha.loans.append("Dune") print("Ben's loans now:", ben.loans)
One list, many owners
  BuggyMember (the class)
     └─ loans ───────────────► [ "Dune" ]  ◄──────────┐
                                    ▲                  │
  asha ─► Member(name="Asha")  ──── reads class ───────┤
  ben  ─► Member(name="Ben")   ──── reads class ───────┘

  Fixed: self.loans = [] inside __init__ gives EACH object its own list.
Ask of every attribute: should this belong to the class (one shared setting, like a constant) or to each object (its own facts)? Lists and dictionaries almost always belong to each object.

Bug 2: forgetting super().__init__(). Symptom: a subclass object is missing attributes its parent should have set, and you get an AttributeError far from the cause. Cause: when a child class defines its own __init__, Python uses only that one, and the parent's __init__ never runs unless you call it.

Bug 2: the parent never got to set its part
class Book: def __init__(self, title, author): self.title = title self.author = author class EBook(Book): def __init__(self, title, author, size_mb): self.size_mb = size_mb # BUG: never called super().__init__ ebook = EBook("Dune", "Herbert", 3) print(vars(ebook)) try: print(ebook.title) except AttributeError as error: print("AttributeError:", error) class FixedEBook(Book): def __init__(self, title, author, size_mb): super().__init__(title, author) # let the parent set up its part self.size_mb = size_mb print(vars(FixedEBook("Dune", "Herbert", 3)))

The first vars shows only size_mb: the title and author were never stored. The rule is simple: if a child defines __init__, call super().__init__(...) first (or at least early), passing what the parent needs.

Bug 3: changing an argument the caller still owns. Symptom: you change something inside an object and a list in a completely different part of the program changes. Cause: self.loans = loans does not copy the list; it stores a second arrow to the caller's list.

Bug 3: storing the caller's own list
class Member: def __init__(self, name, loans): self.name = name self.loans = loans # keeps the CALLER's list, not a copy mine = ["Dune"] asha = Member("Asha", mine) asha.loans.append("Emma") print("caller's own list is now:", mine) class SafeMember: def __init__(self, name, loans): self.name = name self.loans = list(loans) # a private copy mine = ["Dune"] asha = SafeMember("Asha", mine) asha.loans.append("Emma") print("caller's list still:", mine)

The fix is to make a private copy at the door with list(loans) (or loans.copy()). The same care applies in the other direction: if a method returns self.loans directly, callers can change your internal list, so return a copy there too. Numbers, strings and tuples cannot be changed in place, so this bug only applies to lists, dictionaries and sets.

Bug 4: a list as a default argument. Symptom: brand-new objects start out already containing items that some other object added. Cause: default values are created once, when Python reads the def line (recall the NameError in 5.1 that came from the same rule), not each time you call the function. The single default list is then shared by every call that does not pass its own.

Bug 4: one default list for every object
class Member: def __init__(self, name, loans=[]): # ONE list, made when def ran self.name = name self.loans = loans asha = Member("Asha") ben = Member("Ben") asha.loans.append("Dune") print("Ben's loans:", ben.loans) print(Member.__init__.__defaults__) class FixedMember: def __init__(self, name, loans=None): self.name = name self.loans = [] if loans is None else list(loans) asha, ben = FixedMember("Asha"), FixedMember("Ben") asha.loans.append("Dune") print("Ben's loans now:", ben.loans)

The line (['Dune'],) is Python showing you the stored defaults: the very list that Asha changed. The standard fix is a stand-in: use None as the default, and build the list inside the function when the caller did not give one. This pattern, x = [] if x is None else list(x), is worth memorising.

Bug 5: __eq__ without __hash__. Symptom: you teach a class what "equal" means, and suddenly you cannot put its objects in a set or use them as dictionary keys. Cause: sets and dictionaries find things using a number called a hash, and a rule says equal objects must have equal hashes. When you define __eq__, Python removes the default __hash__ rather than risk breaking that rule.

Bug 5: equal, but unhashable
class Book: def __init__(self, title): self.title = title def __eq__(self, other): return isinstance(other, Book) and self.title == other.title print(Book("Dune") == Book("Dune")) try: shelf = {Book("Dune")} except TypeError as error: print("TypeError:", error) class HashableBook(Book): def __hash__(self): return hash(self.title) # equal books must hash equally shelf = {HashableBook("Dune"), HashableBook("Dune"), HashableBook("Emma")} print(len(shelf))

The message is TypeError: unhashable type: 'Book'. The fix defines __hash__ from the same fields that __eq__ compares, here the title, so two books with the same title hash the same and the set keeps one of them. (Dataclasses from OOP 4 with frozen=True do this for you.) Only do this for objects whose compared fields do not change while they sit in a set.

Bug 6: changing a list while looping over it. Symptom: a loop that removes items skips some of them, with no error at all. Cause: the loop walks the list by position. When you remove item 0, the items shift left, and the loop moves on to position 1, stepping over the item that just slid into position 0.

Bug 6: removing while looping skips items
class Member: def __init__(self, due_days): self.loans = list(due_days) # each loan is just its due day here def return_overdue(self, today): for due in self.loans: if due < today: self.loans.remove(due) # BUG: changing the list we loop over asha = Member([5, 6, 7, 30]) asha.return_overdue(today=10) print("left after returning overdue:", asha.loans) class FixedMember(Member): def return_overdue(self, today): self.loans = [due for due in self.loans if due >= today] asha = FixedMember([5, 6, 7, 30]) asha.return_overdue(today=10) print("fixed:", asha.loans)

Three overdue loans (5, 6, 7) and only two were removed: the 6 was skipped. The safe options are to loop over a copy (for due in list(self.loans)) or, cleaner, to build the new list you want with a comprehension, as the fix does. Rule of thumb: never add to or remove from a collection while iterating over it.

Bug 7: circular references that walk in both directions. Symptom: RecursionError: maximum recursion depth exceeded. Our library has a natural cycle: a Member holds Loans and each Loan holds its Member. Python handles such cycles fine in memory. The trouble comes when a method follows the arrows in both directions forever, such as a describe() that asks the other side to describe itself.

Bug 7: describe() ping-pongs forever
class Member: def __init__(self, name): self.name = name self.loans = [] def describe(self): return self.name + " holds " + ", ".join(l.describe() for l in self.loans) class Loan: def __init__(self, member, title): self.member = member self.title = title member.loans.append(self) # the two objects now point at each other def describe(self): return f"{self.title} (borrowed by {self.member.describe()})" # goes back! asha = Member("Asha") Loan(asha, "Dune") try: print(asha.describe()) except RecursionError as error: print("RecursionError:", error)
Bug 7 fixed: only walk one way
class Member: def __init__(self, name): self.name = name self.loans = [] def describe(self): return self.name + " holds " + ", ".join(l.describe() for l in self.loans) class Loan: def __init__(self, member, title): self.member = member self.title = title member.loans.append(self) def describe(self): return f"{self.title} (due soon)" # do not walk back to the member asha = Member("Asha") loan = Loan(asha, "Dune") print(asha.describe()) print(loan.member.loans[0] is loan) # the cycle still exists, and is harmless
A cycle, and where the loop happens
  Member.describe() ──► Loan.describe() ──► Member.describe() ──► Loan.describe() ...
        │                     ▲
        └───── loans ─────────┘  and  Loan.member points back
  Fix: Loan.describe() stops at the data it owns (title). It does not call back.
Decide which direction is the "owner". The Member describes its Loans; a Loan just states its own facts. Any code that walks a cycle (describing, copying, saving as JSON) needs a stopping rule like this.

Bug 8: inheritance chains that are too deep. Symptom: nobody, including you, can say what a method will do without opening five files. Cause: each level of inheritance can override or add to the one above. Here is a chain of six classes where the answer to "how many days can I borrow this?" is scattered across three of them.

Bug 8: who decided loan_days is 7?
class Item: loan_days = 14 class Book(Item): pass class Fiction(Book): loan_days = 21 class Novel(Fiction): pass class SciFiNovel(Novel): loan_days = 7 class SignedSciFiNovel(SciFiNovel): pass kind = SignedSciFiNovel print([c.__name__ for c in kind.__mro__ if c is not object]) print("loan_days is", kind.loan_days) for c in kind.__mro__: if "loan_days" in vars(c): print("...set by", c.__name__) # The flatter design: one class, and the differences live in data LOAN_DAYS = {"fiction": 21, "scifi": 7} class FlatBook: def __init__(self, title, genre): self.title, self.genre = title, genre def loan_days(self): return LOAN_DAYS.get(self.genre, 14) print(FlatBook("Dune", "scifi").loan_days())

The second half shows a flatter design: one class, and the differences live as ordinary data in a dictionary. It can grow a new genre with one line. The advice from OOP 4 applies: keep inheritance shallow (two or three levels), and reach for composition or plain data when the difference is only a number or a setting. __mro__ ("method resolution order") is the list of classes Python searches, in order, and it is your map when you must read a deep tree.

Recap

  • Names are arrows: two names can point at one list. Most of these bugs are that one fact in disguise.
  • Put per-object lists in __init__, copy lists you receive, and use None instead of [] as a default.
  • A child class that defines __init__ must call super().__init__(...).
  • Define __hash__ alongside __eq__ if objects go in sets or dictionary keys.
  • Do not change a list while looping over it, do not let methods bounce between two objects forever, and keep inheritance shallow.
5.6 — Refactoring: Reshaping Code Without Breaking It

Programs rarely start in the shape they should end in. Many useful scripts begin as a handful of functions passing dictionaries around, because that was the quickest way to get an answer. Then the script grows, and one day it is hard to change. The fix is refactoring: changing how the code is organised without changing what it does. From outside, nothing is different. Inside, it is tidier and safer to extend. Think of reorganising a kitchen: you still cook the same meals, but now the knives are where you expect them.

The problem first. Here is the kind of code that makes people want to refactor: a "playlist" stored as a dictionary of dictionaries. Notice how easily a typo slips in, and how Python reacts.

Dictionaries everywhere: the typo problem
playlist = {"name": "Road trip", "songs": []} playlist["songs"].append({"title": "Sunrise", "seconds": 200}) playlist["songs"].append({"title": "Highway", "secs": 250}) # typo: "secs" try: total = sum(song["seconds"] for song in playlist["songs"]) except KeyError as error: print("KeyError:", error) try: playlist["Songs"].append({}) # typo: capital S except KeyError as error: print("KeyError:", error)

The first typo ("secs") was accepted silently when the song was added, and blew up only later when we summed the seconds, far from the mistake. The second typo failed immediately, but with a message that only says KeyError: 'Songs'. A dictionary has no idea which keys are allowed; a class does, because its attributes are written down in one place (__init__) and misspelling one raises AttributeError right at the mistake. Rules, too (like "a song must have a positive length") end up scattered in whichever function happened to run first.

The idea: safety net first, then small steps. Refactoring has one golden rule: never restructure code that has no tests, because without tests you cannot know whether you changed the behaviour. So the order is always (1) write tests that pin down what the code does today, (2) make one small structural change, (3) run the tests, (4) repeat. If the tests go red, you know exactly which small change did it, and you can undo it. Another rule: do not add features while refactoring. Structure changes and behaviour changes must never be mixed in one step, or a red test will not tell you which one caused it.

Here are the tests, written first, against the old function-based style. They describe the behaviour we must keep: totals, the longest song, an empty playlist, a text description and one refusal. This block only defines them (and a small run_tests helper); nothing prints yet. As in section 5.2, run the blocks of this section in order, because the console remembers what you defined.

Step 0a: the safety net, written first
import sys, unittest def run_tests(case): suite = unittest.defaultTestLoader.loadTestsFromTestCase(case) return unittest.TextTestRunner(stream=sys.stdout).run(suite) class PlaylistTests(unittest.TestCase): def setUp(self): self.pl = new_playlist("Road trip") add_song(self.pl, "Sunrise", 200) add_song(self.pl, "Highway", 250) def test_total_seconds(self): self.assertEqual(total_seconds(self.pl), 450) def test_longest_song(self): self.assertEqual(longest(self.pl), "Highway") def test_longest_of_empty_playlist_is_none(self): self.assertIsNone(longest(new_playlist("Empty"))) def test_describe(self): self.assertEqual(describe(self.pl), "Road trip: 2 songs, 7m30s") def test_bad_length_is_refused(self): with self.assertRaises(ValueError): add_song(self.pl, "Silence", 0)

Now the starting code: a working script of plain functions and dictionaries. The last line runs the safety net. Each dot is one passing test, and there should be five.

Step 0b: the procedural baseline (tests pass)
def new_playlist(name): return {"name": name, "songs": []} def add_song(pl, title, seconds): if seconds <= 0: raise ValueError("a song needs a positive length") pl["songs"].append({"title": title, "seconds": seconds}) def total_seconds(pl): return sum(s["seconds"] for s in pl["songs"]) def longest(pl): if not pl["songs"]: return None return max(pl["songs"], key=lambda s: s["seconds"])["title"] def describe(pl): minutes, secs = divmod(total_seconds(pl), 60) return f"{pl['name']}: {len(pl['songs'])} songs, {minutes}m{secs:02d}s" run_tests(PlaylistTests)
The refactoring ladder: tests stay green on every rung
  Step 0   dicts + functions                      tests: 5 pass
     │
  Step 1   a Playlist class holds the data        tests: 5 pass   (same tests!)
     │
  Step 2   a Song class holds one song + its rule tests: 5 pass
     │
  Step 3   behaviour moves into methods           tests: 5 pass
     │        (old functions stay as thin wrappers)
  Step 4   retire the wrappers, update the tests  tests: 5 pass
The test class from Step 0a is not touched until the very last step. As long as it stays green, the outside behaviour has not changed.

Step 1: a class for the data. We introduce Playlist to own the name and the list of songs. Each function still exists with the same name and the same arguments; only the insides change from pl["songs"] to pl.songs. new_playlist now returns a Playlist instead of a dictionary. The tests never notice, because they only call the functions.

Step 1: data moves into a Playlist class
class Playlist: def __init__(self, name): self.name = name self.songs = [] # still a list of dicts, for now def new_playlist(name): return Playlist(name) def add_song(pl, title, seconds): if seconds <= 0: raise ValueError("a song needs a positive length") pl.songs.append({"title": title, "seconds": seconds}) def total_seconds(pl): return sum(s["seconds"] for s in pl.songs) def longest(pl): if not pl.songs: return None return max(pl.songs, key=lambda s: s["seconds"])["title"] def describe(pl): minutes, secs = divmod(total_seconds(pl), 60) return f"{pl.name}: {len(pl.songs)} songs, {minutes}m{secs:02d}s" run_tests(PlaylistTests)

Step 2: a class for one song. Songs are still dictionaries inside the playlist. We add a Song class, and, following the planning rule of section 5.1, the "positive length" rule now lives with the thing it protects. Only the functions that touch songs change. The playlist class from Step 1 is unchanged, so we do not repeat it here.

Step 2: a Song class owns its own rule
class Song: def __init__(self, title, seconds): if seconds <= 0: raise ValueError("a song needs a positive length") self.title = title self.seconds = seconds def add_song(pl, title, seconds): pl.songs.append(Song(title, seconds)) # the rule moved into Song def total_seconds(pl): return sum(s.seconds for s in pl.songs) def longest(pl): if not pl.songs: return None return max(pl.songs, key=lambda s: s.seconds).title run_tests(PlaylistTests)

The ValueError now comes from Song.__init__, called inside add_song, yet the test that expects the error from add_song still passes: same behaviour, better home.

Step 3: behaviour into methods. The functions total_seconds(pl), longest(pl) and describe(pl) all take a playlist as their first argument. That is the classic sign that they want to be methods of the class they operate on. We move them into Playlist, and to keep the tests green we leave the old function names behind as one-line wrappers that forward to the methods. Before you look at the correct version, here is a realistic slip during this very step, and how the safety net catches it.

Step 3 with a slip: the tests catch it
class Playlist: def __init__(self, name): self.name = name self.songs = [] def add(self, title, seconds): self.songs.append(Song(title, seconds)) def total_seconds(self): return sum(s.seconds for s in self.songs) def longest(self): if not self.songs: return None return max(self.songs, key=lambda s: s.seconds).title def describe(self): secs, minutes = divmod(self.total_seconds(), 60) # slip: swapped names return f"{self.name}: {len(self.songs)} songs, {minutes}m{secs:02d}s" def new_playlist(name): return Playlist(name) def add_song(pl, title, seconds): pl.add(title, seconds) def total_seconds(pl): return pl.total_seconds() def longest(pl): return pl.longest() def describe(pl): return pl.describe() run_tests(PlaylistTests)

One test failed and the message shows the exact difference: '30m07s' versus '7m30s'. We had swapped the names in secs, minutes = divmod(...) while moving the code. Because the change was small and the tests ran straight away, the cause is obvious. Had we moved everything and only then run the tests, we would have been hunting. The failing lines marked - and + show what we got and what we expected, respectively. Here is the fixed step.

Step 3: behaviour lives in methods (tests pass)
class Playlist: def __init__(self, name): self.name = name self.songs = [] def add(self, title, seconds): self.songs.append(Song(title, seconds)) def total_seconds(self): return sum(s.seconds for s in self.songs) def longest(self): if not self.songs: return None return max(self.songs, key=lambda s: s.seconds).title def describe(self): minutes, secs = divmod(self.total_seconds(), 60) return f"{self.name}: {len(self.songs)} songs, {minutes}m{secs:02d}s" def new_playlist(name): return Playlist(name) def add_song(pl, title, seconds): pl.add(title, seconds) def total_seconds(pl): return pl.total_seconds() def longest(pl): return pl.longest() def describe(pl): return pl.describe() run_tests(PlaylistTests)
  • Each method has the same body as its old function, with pl replaced by self.
  • Each old function name still exists, but its body is a single call: def total_seconds(pl): return pl.total_seconds().
  • The unchanged tests call the wrappers, which call the methods. So we have proven the methods behave exactly as the old functions did.

Step 4: retire the wrappers. Now the old function names have served their purpose, and new code should call the methods directly. This is the only moment the tests change, and they change in the most mechanical way: total_seconds(pl) becomes pl.total_seconds(), and nothing else. We delete the wrappers and run the updated tests. The very last lines show what happens to any code still using the old names.

Step 4: the wrappers are gone, the tests use methods
class PlaylistMethodTests(unittest.TestCase): # the ONE deliberate change to the tests def setUp(self): self.pl = Playlist("Road trip") self.pl.add("Sunrise", 200) self.pl.add("Highway", 250) def test_total_seconds(self): self.assertEqual(self.pl.total_seconds(), 450) def test_longest_song(self): self.assertEqual(self.pl.longest(), "Highway") def test_longest_of_empty_playlist_is_none(self): self.assertIsNone(Playlist("Empty").longest()) def test_describe(self): self.assertEqual(self.pl.describe(), "Road trip: 2 songs, 7m30s") def test_bad_length_is_refused(self): with self.assertRaises(ValueError): self.pl.add("Silence", 0) del new_playlist, add_song, total_seconds, longest, describe # retire the wrappers run_tests(PlaylistMethodTests) try: describe(Playlist("x")) except NameError as error: print("old API is gone:", error)

We started with a bundle of functions passing dictionaries around, and finished with two small classes that each protect their own rules, with the same five tests proving the behaviour never changed. Notice how few risky moments there were: at every step there was a working program and a green test run to return to.

Common mistakes. The classic error is refactoring without a safety net, then wondering whether something subtle changed. The second is doing several rungs of the ladder in one go: when a test fails you are back to searching in the dark. The third is quietly "improving" behaviour as you go (a nicer message, a new option). If you spot a bug or a feature while refactoring, write it down and finish the current step first. The fourth is leaving the wrappers around forever: two ways to do everything is its own kind of mess, so schedule their removal.

Recap

  • Refactoring changes the structure of code without changing its behaviour.
  • Write tests first, change one small thing, run the tests, repeat. Never mix refactoring with new features.
  • Functions that all take the same object as their first argument usually want to become methods of that object's class.
  • Thin wrappers keep old callers and old tests working while you move code; remove them at the end.
  • A small step plus an immediate test run makes a slip easy to find.
5.7 — Saving and Loading Objects

Objects live in your computer's memory, and memory is wiped the moment the program ends. A real program needs to keep things: the library's books, the members, who has what. That means turning objects into something that can be stored or sent (saving, sometimes called serialising) and turning it back into objects later (loading). This section teaches the standard, safe recipe. We will stay in memory here, and Chapter 5 will show how to put the same text into a real file.

The problem first. The most common way to store structured data is JSON, a plain-text format made of dictionaries, lists, strings, numbers, true/false and null. Python's json module converts between those and text. It knows only those basic types. Watch what happens when we hand it one of our own objects:

json does not know our classes
import json class Book: def __init__(self, title, author): self.title = title self.author = author book = Book("Dune", "Herbert") try: print(json.dumps(book)) except TypeError as error: print("TypeError:", error) print(json.dumps({"title": book.title, "author": book.author}))

TypeError: Object of type Book is not JSON serializable says it plainly: JSON has no idea what a Book is. The last line shows the way out. If we describe the book with a plain dictionary, JSON handles it perfectly.

The idea: two small methods. Give the class a method that produces the plain dictionary (to_dict) and a second method that builds an object from such a dictionary (from_dict). Think of packing a suitcase and unpacking it: to_dict packs the object flat, from_dict unpacks it into a fresh object. The unpacking method is written as a classmethod. A class method receives the class itself as its first argument (conventionally named cls) instead of an object, and you mark it with the line @classmethod above the def. That is exactly what we need, because when we load we do not have an object yet: we call Book.from_dict(data) on the class and it returns a new one. Inside, cls(...) is the same as writing Book(...), but it also works for subclasses.

to_dict, from_dict and a round trip through JSON text
import json class Book: def __init__(self, title, author): self.title = title self.author = author def to_dict(self): return {"title": self.title, "author": self.author} @classmethod def from_dict(cls, data): return cls(data["title"], data["author"]) book = Book("Dune", "Herbert") text = json.dumps(book.to_dict()) print(text, type(text).__name__) data = json.loads(text) print(data, type(data).__name__) copy = Book.from_dict(data) print(type(copy).__name__, copy.title, copy is book)
  • book.to_dict() returns a plain dictionary of the book's facts.
  • json.dumps(...) turns the dictionary into one line of text (a str). This is what you would save or send.
  • json.loads(text) turns the text back into a dictionary. It is a dict, not a Book: the class information was not stored.
  • Book.from_dict(data) builds a brand-new Book from the dictionary. It has the same facts, but it is a different object, so copy is book is False.
The save / load round trip
  Book object ──to_dict()──► dict ──json.dumps()──► text (str)
                                                       │  save it, send it
  Book object ◄─from_dict()── dict ◄─json.loads()──── text (str)
Only plain values (text, numbers, lists, dictionaries, None) travel. The methods and the class name stay in your code, which is why from_dict is needed on the way back in.

Objects that hold objects. For a Library that holds many books, the recipe repeats: the outer to_dict asks each inner object for its own dictionary, and the outer from_dict calls the inner from_dict for each piece. Each class packs and unpacks only its own level, which keeps the code simple. We also store a "version": 1 so that a future program can tell which layout it is reading.

A Library saves its Books, and loads them again
import json class Book: def __init__(self, title, author, due_day=None): self.title, self.author, self.due_day = title, author, due_day def to_dict(self): return {"title": self.title, "author": self.author, "due_day": self.due_day} @classmethod def from_dict(cls, data): return cls(data["title"], data["author"], data["due_day"]) class Library: def __init__(self): self.books = {} def to_dict(self): return {"version": 1, "books": [b.to_dict() for b in self.books.values()]} @classmethod def from_dict(cls, data): lib = cls() for item in data["books"]: book = Book.from_dict(item) lib.books[book.title] = book return lib lib = Library() lib.books["Dune"] = Book("Dune", "Herbert", due_day=15) lib.books["Emma"] = Book("Emma", "Austen") text = json.dumps(lib.to_dict()) print(text) restored = Library.from_dict(json.loads(text)) print(sorted(restored.books), restored.books["Dune"].due_day, restored.books["Emma"].due_day)

Notice how the references from earlier chapters change shape when saved: inside memory, objects point at each other with arrows, but text has no arrows. So we save names or ids (here, titles) and rebuild the arrows while loading. If a Member had held Loan objects that point at Books, we would save the loan as a dictionary containing the book's title, and on loading look that title up in the rebuilt library.

Is a loaded object "the same"? A round trip should preserve the facts. It does not preserve identity, and unless you wrote __eq__, Python's == compares identity too:

Same facts, different object
import json class Book: def __init__(self, title, author, due_day=None): self.title, self.author, self.due_day = title, author, due_day def to_dict(self): return {"title": self.title, "author": self.author, "due_day": self.due_day} @classmethod def from_dict(cls, data): return cls(data["title"], data["author"], data["due_day"]) original = Book("Dune", "Herbert", due_day=15) restored = Book.from_dict(json.loads(json.dumps(original.to_dict()))) print(restored.to_dict() == original.to_dict()) # same facts... print(restored is original) # ...but a different object print(restored == original) # no __eq__ yet, so == says no

That is why a good round-trip test compares the two dictionaries (restored.to_dict() == original.to_dict()), or you give the class an __eq__ as in OOP 2. It is also a fine test to keep in your suite: save, load, and check nothing was lost.

Common mistakes. Data that arrives from outside a program can be wrong: a field missing, or text that is not valid JSON at all. Your loading code should say what is wrong, in plain words. This block feeds three inputs to the same loop: one missing a field, one fine, and one that is not JSON.

Loading defensively: clear errors for bad data
import json class Book: def __init__(self, title, author): self.title, self.author = title, author @classmethod def from_dict(cls, data): for key in ("title", "author"): if key not in data: raise ValueError(f"saved book is missing {key!r}") return cls(data["title"], data["author"]) for text in ['{"title": "Dune"}', '{"title": "Dune", "author": "Herbert"}', '{title: Dune}']: try: book = Book.from_dict(json.loads(text)) print("loaded", book.title) except json.JSONDecodeError as error: print("not valid JSON:", error) except ValueError as error: print("bad data:", error)

Without the checks, the first input would give a bare KeyError: 'author', which does not say that the saved data was at fault. Notice we caught json.JSONDecodeError first, then ValueError. When you have several except blocks, Python picks the first one that matches. Order matters here because JSONDecodeError is itself a kind of ValueError, so it must come first or the more general one would swallow it.

Why you never load pickled data you did not create. Python has another saving tool called pickle. It stores almost any Python object with no to_dict needed, which sounds wonderful. The catch is how loading works: a pickle is really a small program that tells Python which functions to call to rebuild the object, and pickle.loads obeys it. Here is a harmless demonstration that uses print as the "function to call".

A pickle can run code while loading (harmless demo)
import pickle class Sneaky: def __reduce__(self): # tells pickle: "to rebuild me, call print with this argument" return (print, ("this code ran while LOADING the data",)) data = pickle.dumps(Sneaky()) print("about to load...") pickle.loads(data) print("loaded. Any function could have been called instead of print.")

Our Sneaky class told pickle "to rebuild me, call print", and the message appeared during loading. A hostile file could name a far more dangerous function, such as one that deletes files or steals passwords. That is why the rule is simple: never unpickle data from anyone you do not fully trust, and prefer JSON for anything that crosses a boundary (files that others can edit, the network, uploads). JSON can only ever produce plain data, and your own from_dict decides what to do with it.

Check yourself: Why is from_dict a @classmethod and not an ordinary method?
An ordinary method needs an existing object to be called on. When loading, no object exists yet. A class method is called on the class (Book.from_dict(data)) and builds a new object with cls(...).
Check yourself: A class has an attribute created = datetime.date(...) or a set of tags. Can you pass those straight to json.dumps?
No. JSON has no date type and no set type. In to_dict, convert them to plain values (for example a text like "2025-01-31" and a list of tags), and convert back in from_dict.
Try it: Add a Member class with name and a list of loaned titles, give it to_dict and from_dict, and check that Member.from_dict(json.loads(json.dumps(member.to_dict()))).loans equals the original list.

Recap

  • JSON only understands basic types, so give classes to_dict() and a from_dict() classmethod.
  • Saving turns objects into text; loading builds new objects with the same facts. Arrows between objects become names or ids.
  • Each class packs and unpacks only its own level and delegates the rest to the classes it holds.
  • Validate incoming data and raise clear errors. Put except blocks for the more specific error first.
  • Never load pickle data you did not create: loading can run arbitrary code. Prefer JSON.
5.8 — Reading Other People's Classes

Until now you have mostly read code that you wrote, in the order that you wrote it. Professional programming is different: most of the time you are reading code written by someone else, or by yourself six months ago, and it is being used through classes you did not design. Learning to size up an unfamiliar class quickly is one of the most valuable skills you can build. It also removes the fear of libraries: every library you will ever use is, at heart, a collection of classes doing what you have learned in this track.

The problem first. Someone hands you a class called Thermostat and says "use it". You could read every line, but real classes can have hundreds. Or you could open a page of documentation, which may not exist. The faster way is to ask the objects themselves. Python has built-in tools that let you look inside any object while the program runs. There is a good reading order too, and it follows the structure you already know from OOP 1.

The idea: a reading order. First look at the attributes: what does an object of this class know? Then the public methods: what can it do? Then the special (dunder) methods: how does it behave with print, ==, len and loops? Only after those, if needed, read the bodies of the methods that matter. This is the same trio as a CRC card from section 5.1 (knows, does, works with), read in reverse.

A reading order for an unfamiliar class
  1. Attributes        vars(obj)               what it KNOWS
  2. Public methods    dir(obj) minus "_" names  what it can DO
  3. Special methods   __init__, __repr__ ...   how it BEHAVES with Python
  4. Base classes      Class.__mro__            what it INHERITS
  5. Docs and hints    help(), signature()      what the author SAID
  6. Method bodies     only the ones you need   HOW it does it
You often only need steps 1 to 3 to be able to use a class well.

Three built-in tools cover the first three steps. vars(obj) gives a dictionary of the object's own attributes (its __dict__, which you saw in OOP 1). dir(obj) lists every name the object can reach, including inherited ones and the special ones with double underscores. Because that list is long, we filter it: names that do not start with an underscore, and that are callable (can be called like a function). Attributes and methods starting with a single underscore are, by convention, private details.

The first three steps on a Thermostat
class Thermostat: """Keeps a room at a target temperature.""" MAX = 30 def __init__(self, room, target=20): self.room = room self.target = target self._history = [] def set_target(self, degrees): """Change the target; refuses values above MAX.""" if degrees > self.MAX: raise ValueError("too hot") self._history.append(self.target) self.target = degrees def undo(self): """Go back to the previous target.""" self.target = self._history.pop() def __repr__(self): return f"Thermostat({self.room!r}, target={self.target})" t = Thermostat("Kitchen") t.set_target(23) print(vars(t)) # 1. attributes first print([n for n in dir(t) if not n.startswith("_") and callable(getattr(t, n))]) # 2. public methods print([n for n, v in vars(Thermostat).items() if n.startswith("__") and callable(v)]) # 3. special methods print(t)
  • vars(t) shows the attributes: room, target, and _history (private by the underscore convention, so we can ignore it). It also reveals that set_target(23) saved the old target 20 in that history.
  • The filtered dir(t) shows only two public methods: set_target and undo. The class also has MAX = 30, a plain value, which is why we filtered by callable.
  • Looking at the special methods defined on the class itself, we see __init__ (how it is built) and __repr__ (how it prints).
  • Printing t uses that __repr__, so we know it will look like Thermostat('Kitchen', target=23).

What the author said: help, docstrings and signatures. A docstring is a string placed as the first line inside a class or function; Python stores it so tools can show it. help(thing) prints it nicely, and the inspect module (part of Python's standard library) can also report a function's signature: its names and defaults for the arguments.

help, docstrings and signatures
class Thermostat: """Keeps a room at a target temperature.""" MAX = 30 def set_target(self, degrees): """Change the target; refuses values above MAX.""" self.target = degrees print(Thermostat.__doc__) help(Thermostat.set_target) import inspect print(inspect.signature(Thermostat.set_target)) print(inspect.getdoc(Thermostat.set_target))

When a library gives you a class with no documentation, help and inspect.signature are often the fastest way to learn how to call it. (In a normal file, inspect.getsource(obj) can even print the code itself. It cannot do that for code typed into this page's console, because the code is not stored in a file.)

We can put all this together in a small tool that summarises any object, following the reading order. Write it once and you can point it at classes for the rest of your career.

A little class inspector
import inspect class Thermostat: """Keeps a room at a target temperature.""" MAX = 30 def __init__(self, room, target=20): self.room = room self.target = target def set_target(self, degrees): """Change the target; refuses values above MAX.""" self.target = degrees def undo(self): """Go back to the previous target.""" self.target = 20 def __repr__(self): return f"Thermostat({self.room!r})" def inspect_object(obj): cls = type(obj) print("class:", cls.__name__, "| bases:", [b.__name__ for b in cls.__bases__]) print("about:", inspect.getdoc(cls)) print("attributes:", vars(obj)) for name, fn in inspect.getmembers(cls, inspect.isfunction): if not name.startswith("_"): print("method:", name + str(inspect.signature(fn)), "-", inspect.getdoc(fn)) print("special:", [n for n, v in vars(cls).items() if n.startswith("__") and callable(v)]) inspect_object(Thermostat("Hall"))

This is a "class card" generated by the program itself, from the real object, so it can never go out of date. If you had a large class from a library you had never seen, this output would tell you in ten lines what it knows and what it can do.

Classes that look magical are still classes. Very soon you will meet libraries such as FastAPI, Pydantic and SQLAlchemy. They look strange because their classes contain almost no code: just names with type hints and no __init__. Yet objects of those classes somehow validate data or save to a database. The secret is that a base class does the work, by reading the class's annotations, using exactly the tools of this section. To take the mystery out, here is a miniature version. The base class reads self.__annotations__ (the dictionary of annotated names and their types) and builds the object from them.

A miniature 'model' class: the trick behind those libraries
class Model: """A tiny base class that builds objects from type annotations.""" def __init__(self, **values): for name, kind in self.__annotations__.items(): if name not in values: raise TypeError(f"missing field: {name}") setattr(self, name, kind(values[name])) # convert to the declared type def __repr__(self): fields = ", ".join(f"{n}={getattr(self, n)!r}" for n in self.__annotations__) return f"{type(self).__name__}({fields})" class Item(Model): name: str price: float item = Item(name="Pen", price="1.5") # the text "1.5" becomes 1.5 print(item) print(Item.__annotations__) try: Item(name="Pen") except TypeError as error: print("TypeError:", error)

The class Item contains only two annotated names, yet Item(name="Pen", price="1.5") works, converts the text "1.5" to the number 1.5, and complains when a field is missing. Everything happened in the parent Model, using inheritance (OOP 3), setattr and a special method (OOP 2). Real libraries do much more, but the shape is identical. You are not expected to learn them here. Common mistakes. Two tools have surprises. vars() only works on objects that keep their attributes in a __dict__. It fails on numbers and on classes that use __slots__ (a way to save memory by declaring a fixed set of attributes). Read the error, and note the alternative for slots classes:

Mistake: vars() on an object without a __dict__
try: print(vars(5)) except TypeError as error: print("TypeError:", error) class Point: __slots__ = ("x", "y") def __init__(self, x, y): self.x, self.y = x, y p = Point(1, 2) try: print(vars(p)) except TypeError as error: print("TypeError:", error) print({name: getattr(p, name) for name in Point.__slots__})

The message vars() argument must have __dict__ attribute tells you exactly what is missing. For a __slots__ class, loop over Class.__slots__ and use getattr, as in the last line. The other surprise is that dir() output is long and mixes your names with Python's inherited ones. Always filter it, as we did, or you will drown in __class__, __delattr__ and dozens more.

  • help(), docstrings and inspect.signature show what the author documented, without opening the source.

5.9 — Debugging Habits, Where Next, and a Self-Check

You now have a toolbox: planning, staged building, tests, a catalogue of classic bugs, safe refactoring, saving data and reading unfamiliar classes. This last section ties them together into a routine that works whenever a program misbehaves, shows it on one complete example, and then gives you a checklist to measure yourself honestly against.

A debugging routine. Beginners often debug by changing things at random until the error goes away, which is slow and can hide the real problem. Professionals follow a short routine instead. First, read the message: the last line of a traceback or the a != b line of a failed test usually names the symptom. Second, reproduce it small: shrink the failing situation to the fewest lines that still go wrong. Third, look at the real state: print vars(obj) instead of guessing what an object contains. Fourth, form one guess and check it, changing one thing at a time. Fifth, keep a test that fails before the fix and passes after, so the bug can never quietly return.

The five-step debugging routine
  1. READ      the last line of the traceback / the "a != b" message
  2. SHRINK    the smallest example that still goes wrong
  3. LOOK      vars(obj), type(x), print the real values
  4. GUESS     one cause at a time, then check it
  5. PIN       a test that fails before the fix and passes after
Random changes feel busy but teach you nothing. Each step of this routine narrows the search.

The problem first: a bug that hides in plain sight. Below is a small library. After a book is returned, the test says it should be free again. Run it and read the last line of the failure.

A test fails: step 1, read the message
import sys, unittest class Book: def __init__(self, title): self.title = title self.loan_due = None class Library: def __init__(self): self.books = {} def add(self, title): self.books[title] = Book(title) def check_out(self, title, today): self.books[title].loan_due = today + 14 def give_back(self, title): book = self.books[title] book.loan_due == None # the bug hides on this line class ReturnTests(unittest.TestCase): def test_book_is_free_after_return(self): lib = Library() lib.add("Dune") lib.check_out("Dune", 1) lib.give_back("Dune") self.assertIsNone(lib.books["Dune"].loan_due) suite = unittest.defaultTestLoader.loadTestsFromTestCase(ReturnTests) unittest.TextTestRunner(stream=sys.stdout).run(suite)

The message is AssertionError: 15 is not None. In plain words: after returning the book, loan_due is still 15, when the test expected None. That already tells us the return did not clear the loan. There is no need to read the whole program. We look at the state (step 3) of a single book before and after the suspicious line.

Steps 2 and 3: shrink it, then look at the real state
class Book: def __init__(self, title): self.title = title self.loan_due = None lib_books = {"Dune": Book("Dune")} lib_books["Dune"].loan_due = 15 book = lib_books["Dune"] print("before:", vars(book)) # step 3: look at the real state book.loan_due == None # the buggy line: compares, changes nothing print("after ==:", vars(book)) book.loan_due = None # the fix: one = assigns print("after =:", vars(book))

The printout settles it. After the line book.loan_due == None the book is unchanged, because that line compares and throws the answer away. Two equals signs ask a question; one equals sign changes something. Now the fix is one character, and the test from step 1 is the proof (step 5):

Step 5: the fix, with the test still in place
import sys, unittest class Book: def __init__(self, title): self.title = title self.loan_due = None class Library: def __init__(self): self.books = {} def add(self, title): self.books[title] = Book(title) def check_out(self, title, today): self.books[title].loan_due = today + 14 def give_back(self, title): self.books[title].loan_due = None # fixed: assignment class ReturnTests(unittest.TestCase): def test_book_is_free_after_return(self): lib = Library() lib.add("Dune") lib.check_out("Dune", 1) lib.give_back("Dune") self.assertIsNone(lib.books["Dune"].loan_due) suite = unittest.defaultTestLoader.loadTestsFromTestCase(ReturnTests) unittest.TextTestRunner(stream=sys.stdout).run(suite)
