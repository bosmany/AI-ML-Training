41.1 — Assembling the App With APIRouter

A single main.py with 20+ routes gets unreadable fast. APIRouter lets you split routes into separate files by feature — a candidates router, an auth router — each defined independently, then wired together with app.include_router(...). Everything you learned about a single route (path params, Pydantic bodies, Depends()) works identically on a router; only the assembly step changes.

🎬
Reference code — run it in the Colab notebook, not here
Every code block in this chapter needs a real FastAPI/Starlette install, so there's no "▶ Run" button.
Colab / real Python — splitting routes into a router
# routers/candidates.py from fastapi import APIRouter, Depends router = APIRouter() @router.get("/health") def health(): return {"status": "ok"} # main.py from fastapi import FastAPI from routers import candidates app = FastAPI(title="Candidate Scoring API v2") app.include_router(candidates.router, prefix="/candidates", tags=["candidates"])
⭐
The prefix is applied to every route in the router — /health inside candidates.router actually becomes /candidates/health once included. tags= just groups routes together in the auto-generated docs.
41.2 — Candidate Scoring API v2 — Putting It All Together

A real project's file layout mirrors this split: a thin main.py that only creates the app and includes routers, a models.py for Pydantic/SQLAlchemy models, an auth.py for the OAuth2/JWT dependency from Ch 39, and a database.py for the async session dependency from Ch 38.

from fastapi import APIRouter, Depends, BackgroundTasks from sqlalchemy.ext.asyncio import AsyncSession router = APIRouter() @router.post("", response_model=CandidateOut, status_code=201) async def create_candidate( candidate: CandidateIn, background_tasks: BackgroundTasks, db: AsyncSession = Depends(get_db), # Ch 38 current_user: str = Depends(get_current_user), # Ch 39 ): saved = await save_candidate(db, candidate) background_tasks.add_task(send_welcome_email, saved.name) # Ch 40 return saved
⭐
Nothing here is new. Every piece — Depends(), the async DB session, the auth dependency, the background task — is a concept you already exercised in an earlier chapter. This route just uses all of them at once, which is exactly what a real production endpoint looks like.
41.3 — A Full Test Suite

Real test suites are organized by feature (mirroring the router split) and share setup through pytest fixtures — a fresh in-memory database per test, a TestClient instance, a helper that returns an authenticated header. This avoids copy-pasting the same 5 lines of setup into every test function.

Colab / real Python — reference-only pytest structure
# test_candidates.py import pytest from fastapi.testclient import TestClient @pytest.fixture def auth_headers(client): token = login_as_test_user(client) return {"Authorization": f"Bearer {token}"} def test_create_candidate_requires_auth(client): response = client.post("/candidates", json={"name": "Grace", "score": 0.9}) assert response.status_code == 401 def test_create_candidate_succeeds(client, auth_headers): response = client.post("/candidates", json={"name": "Grace", "score": 0.9}, headers=auth_headers) assert response.status_code == 201
💡
The Colab notebook runs the equivalent of this with plain assert statements instead of a real pytest CLI invocation (which needs a real filesystem/process) — the logic and coverage are identical, only the runner differs.
41.4 — Dockerizing the App

You've containerized a trained model before, back in Chapter 31.3 — this is the exact same idea applied to a full API instead of a single serialized model. The Dockerfile installs dependencies, copies the code, and declares the startup command.

Terminal / real project — reference only, no Run button
# Dockerfile FROM python:3.12-slim WORKDIR /app COPY requirements.txt . RUN pip install -r requirements.txt COPY . . CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"] # build and run: # docker build -t candidate-api-v2 . # docker run -p 8000:8000 candidate-api-v2
⭐
Same pattern as Ch 31, one difference: the CMD runs uvicorn serving a whole app with routers/DB/auth, instead of one script wrapping a single model — the container itself doesn't care about that difference at all.
41.5 — Where To Deploy It

Reference only — no exercise here, just orientation for after this course. Once you have a Dockerfile, several low-cost/free options exist to actually put your API on the internet:

OptionWhat it's good for
Render / RailwayPoint at your GitHub repo, it builds your Dockerfile and gives you a public URL — simplest path for a portfolio project
Fly.ioDeploys your container close to users globally; a bit more configuration, more control
A bare VM (EC2, a VPS)Install Docker yourself, docker run your image behind a reverse proxy (nginx) — most control, most setup work
💡
All three run the exact same container. The Dockerfile is the actual deliverable — where you run it is a separate, later decision, and switching providers later doesn't require touching your application code.

💼 FastAPI & Backend API Interview Prep

12 questions commonly asked in backend/API engineering interviews, covering everything across this module. Click a question to reveal the answer. Not graded — this is here so you walk into an interview room prepared.

What is dependency injection, and why does FastAPI's Depends() matter?▶
Dependency injection means a function declares what it needs (a DB session, the current user) as parameters, and something external provides them, instead of the function constructing them itself. Depends() lets FastAPI build that value for you — including running its own validation/auth logic — before your route body runs, and lets the same dependency (e.g. get_current_user) be reused, tested, and overridden (e.g. with a fake user in tests) across many routes without duplicating code.
What's the difference between a path parameter and a query parameter, and when do you use each?▶
A path parameter identifies a specific resource and is part of the URL structure itself (/candidates/5 — this candidate, specifically). A query parameter modifies or filters a request and is optional by convention (/candidates?min_score=0.8 — filter this collection). Rule of thumb: if removing it changes WHICH resource you mean, it's a path param; if it changes HOW you view/filter a resource, it's a query param.
What does it mean for an HTTP method to be idempotent, and which methods are expected to be?▶
Idempotent means calling it multiple times with the same input produces the same end state as calling it once. GET, PUT, and DELETE are expected to be idempotent (PUT-ing the same full resource twice leaves it in the same state; deleting an already-deleted resource is still "gone"). POST is NOT idempotent by convention — posting the same "create a candidate" request twice creates two candidates.
How does FastAPI generate interactive API docs automatically?▶
It introspects your route decorators, function type hints, and Pydantic models at import time to build an OpenAPI schema (a JSON spec describing every route, parameter, and response shape), then serves that schema through a bundled Swagger UI (/docs) and ReDoc (/redoc) page — no separate documentation-writing step, the docs can't drift out of sync with the code because they're generated FROM it.
What's the practical difference between a 401 and a 403 response?▶
401 Unauthorized: you haven't proven who you are (missing or invalid credentials) — "log in first." 403 Forbidden: the server knows exactly who you are, but you don't have permission for this specific action — "you're logged in, but you can't do this." Returning 403 instead of 401 (or vice versa) is a common interview trip-up.
When does it actually matter whether a FastAPI route handler is async def vs plain def?▶
It matters when your route does I/O (a DB query, an outbound HTTP call): an async def route that properly awaits async I/O lets the event loop serve other requests while waiting, giving much better concurrency under load. A plain def route is run in a threadpool by FastAPI automatically, which is fine for CPU-bound or purely synchronous work — but mixing a blocking synchronous call INSIDE an async def route (e.g. calling a non-async DB driver without awaiting) blocks the entire event loop and hurts every other in-flight request, not just that one.
How would you version a REST API as it evolves?▶
Most common: a version prefix in the URL path (/v1/candidates, /v2/candidates), implemented in FastAPI as two separate routers mounted at different prefixes — lets you run both versions side by side while clients migrate. Less common alternatives: a custom request header, or content negotiation via the Accept header. Path versioning wins on simplicity and discoverability, which is usually worth more than its slight URL "impurity."
What is the N+1 query problem, and how would you avoid it with SQLAlchemy?▶
It happens when you fetch a list of N parent rows, then loop over them issuing one extra query per row to fetch related data (e.g. each candidate's applications) — N+1 total queries instead of 2. Fixed by eager-loading the relationship up front, e.g. SQLAlchemy's selectinload() or joinedload(), which fetches the related rows in one extra query (or one JOIN) instead of one query per parent row.
Why is using an ORM generally safer against SQL injection than writing raw SQL?▶
An ORM like SQLAlchemy parameterizes query values by default — user input is passed as a bound parameter to the database driver, never string-concatenated into the SQL text, so it can never be interpreted as SQL syntax. Raw SQL is only unsafe when you build it via string formatting/concatenation with user input; raw SQL using the driver's own parameterized-query placeholders (? or %s) is equally safe — the danger is string-building, not "raw SQL" itself.
What is CORS middleware, and when do you actually need it?▶
Browsers block a web page's JavaScript from calling an API on a different origin (domain/port/protocol) unless that API explicitly allows it via CORS response headers. You need FastAPI's CORSMiddleware whenever your API is called directly from browser JavaScript running on a different origin than the API itself (e.g. a React app on localhost:3000 calling an API on localhost:8000). You do NOT need it for server-to-server calls, mobile apps, or Postman/curl — CORS is a browser-enforced rule, not a general network security feature.
How do you test an endpoint that depends on the currently authenticated user, without a real login flow in every test?▶
FastAPI supports dependency overrides: app.dependency_overrides[get_current_user] = lambda: "test-user" replaces the real dependency with a fake one for the duration of the test, so you never need to actually generate and pass a real JWT in most tests — reserve a real login+token flow for the handful of tests specifically checking the auth mechanism itself.
What's the difference between horizontal and vertical scaling for a deployed API, and which does Docker make easier?▶
Vertical scaling: give the same single instance more CPU/RAM — simple, but has a hard ceiling and a single point of failure. Horizontal scaling: run more copies of the same instance behind a load balancer — better fault tolerance and near-unlimited headroom, but requires the app to be stateless (no in-memory session state tied to one process). Docker makes horizontal scaling dramatically easier: since the container is a self-contained, reproducible unit, spinning up 10 identical copies is just running the same image 10 times.
