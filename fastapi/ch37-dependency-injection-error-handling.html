Chapter 37:
Dependency Injection & Error Handling

Chapter 36 built single endpoints. Real APIs repeat setup logic (pagination, filtering, auth checks) across dozens of routes, and they need consistent, predictable error responses instead of unhandled tracebacks. FastAPI's Depends() system shares logic between endpoints without copy-pasting it, and its exception-handling hooks turn any error — expected or custom — into a clean, structured HTTP response.

37.1 — Depends(): Sharing Logic Across Endpoints

Plenty of endpoints need the same setup: pagination, an auth check, a database session. Writing that logic inside every route function duplicates it everywhere and duplicates every future bug fix too. A dependency is just a normal function; wrapping a parameter in Depends(that_function) tells FastAPI to call it first and pass its return value in.

🎬
Reference code — run it in the Colab notebook, not here
Every code block in this chapter needs a real FastAPI/Starlette install, so there's no "▶ Run" button. Read it, then open the notebook linked above to actually execute it.
Colab / real Python — a shared pagination dependency
from fastapi import FastAPI, Depends app = FastAPI() def get_pagination(skip: int = 0, limit: int = 10): return {"skip": skip, "limit": limit} @app.get("/candidates") def list_candidates(pagination: dict = Depends(get_pagination)): return {"pagination": pagination, "results": []}
⭐
FastAPI calls get_pagination() for you on every request to this route, using the same query-parameter parsing rules from Chapter 36 — ?skip=10&limit=5 flows straight into the dependency, which flows straight into pagination.
37.2 — Class-Based Dependencies

A dependency doesn't have to be a plain function — any callable works, including a class. FastAPI calls the class like a function (i.e. constructs an instance), so its __init__ parameters are parsed exactly like a function's would be. This is useful when several related query parameters belong together as one object.

Colab / real Python — a class-based dependency
class CommonQueryParams: def __init__(self, q: str | None = None, skip: int = 0, limit: int = 10): self.q = q self.skip = skip self.limit = limit @app.get("/candidates/search") def search_candidates(commons: CommonQueryParams = Depends(CommonQueryParams)): return {"q": commons.q, "skip": commons.skip, "limit": commons.limit}
37.3 — HTTPException

When a lookup fails inside a route, raise fastapi.HTTPException instead of letting a plain KeyError escape as an unhandled 500. FastAPI catches it and converts it into a clean JSON error response with the status code and detail message you chose.

Colab / real Python — a clean 404 instead of a crash
from fastapi import FastAPI, HTTPException CANDIDATES = {1: {"name": "Alice", "score": 0.92}} @app.get("/candidates/{candidate_id}") def get_candidate(candidate_id: int): if candidate_id not in CANDIDATES: raise HTTPException(status_code=404, detail="Candidate not found") return CANDIDATES[candidate_id]
💡
Requesting /candidates/999 now returns a real, structured 404 — {"detail": "Candidate not found"} — instead of a 500 crash from an unhandled KeyError.
37.4 — Custom Exception Classes & Handlers

HTTPException is fine for simple cases, but it couples your business logic directly to HTTP concerns. A cleaner pattern for larger apps: raise a plain, framework-agnostic Python exception from your domain logic, then register an @app.exception_handler(...) that converts it into an HTTP response in exactly one place.

Colab / real Python — a custom exception with a registered handler
from fastapi import FastAPI, Request from fastapi.responses import JSONResponse class CandidateNotFoundError(Exception): def __init__(self, candidate_id: int): self.candidate_id = candidate_id @app.exception_handler(CandidateNotFoundError) def candidate_not_found_handler(request: Request, exc: CandidateNotFoundError): return JSONResponse( status_code=404, content={"error": f"Candidate {exc.candidate_id} not found"}, )
⭐
Now any function anywhere can raise CandidateNotFoundError(id) — a database layer, a service class, a background task — without importing FastAPI or knowing about HTTP status codes at all. The handler is the only place that translates "not found" into a 404.
⚠️
Register exception handlers (and middleware) before the app handles its first request. Starlette builds and caches its handler stack on the first call, so a handler added afterwards is silently ignored — you get a plain-text 500 Internal Server Error instead of your JSON. In a normal main.py this never bites, because everything is registered at import time. It does bite in a notebook that keeps adding to one app across cells — which is why the Colab notebook builds a fresh app for this section.
37.5 — Sub-Dependencies

Dependencies can depend on other dependencies — FastAPI resolves the whole chain automatically. This is how larger apps compose small, single-purpose dependencies (get the DB session → get the current user from a token → check the user is an admin) into one route parameter.

Colab / real Python — a dependency that depends on another
def get_pagination(skip: int = 0, limit: int = 10): return {"skip": skip, "limit": limit} def get_sorted_pagination(pagination: dict = Depends(get_pagination), sort_by: str = "score"): return {**pagination, "sort_by": sort_by} @app.get("/candidates") def list_candidates(query: dict = Depends(get_sorted_pagination)): return query
37.6 — Status Code Cheat-Sheet

Picking the right status code is part of designing a clean API. The ones you'll use constantly:

CodeMeaningWhen to use it
200OKA successful GET, PUT, or PATCH
201CreatedA successful POST that created a new resource
204No ContentA successful DELETE — nothing to return
400Bad RequestThe request itself is malformed, independent of any specific field
401UnauthorizedNo valid credentials were supplied at all
403ForbiddenCredentials were valid, but this user isn't allowed to do this
404Not FoundThe requested resource (by id, by path) doesn't exist
422Unprocessable EntityPydantic validation failed — FastAPI raises this automatically
500Internal Server ErrorAn unhandled exception — a bug, not a client mistake
37.7 — Testing With Dependency Overrides

Tests shouldn't depend on a real database or a real third-party service just to exercise route logic. app.dependency_overrides[original] = replacement swaps out any dependency for a test double, for the lifetime of the TestClient — the route code itself never changes.

Colab / real Python — overriding a dependency in tests
from fastapi.testclient import TestClient def override_get_pagination(): return {"skip": 0, "limit": 2} app.dependency_overrides[get_pagination] = override_get_pagination client = TestClient(app) response = client.get("/candidates") assert response.status_code == 200 assert response.json()["pagination"]["limit"] == 2 app.dependency_overrides.clear() # always clean up after the test
🚫
Always clear overrides after a test — app.dependency_overrides is shared, mutable state on the app object. Leaving an override in place leaks into every test that runs after it in the same process.
Chapter 37 Summary
  • Depends() shares setup logic across endpoints — functions or classes both work as dependencies.
  • Dependencies can depend on other dependencies — FastAPI resolves the whole chain for you.
  • HTTPException turns a failed lookup into a clean, structured error response instead of a crash.
  • Custom exceptions + @app.exception_handler keep business logic decoupled from HTTP status codes.
  • app.dependency_overrides swaps a real dependency for a test double, without touching route code.
