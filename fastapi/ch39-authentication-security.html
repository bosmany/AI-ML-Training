39.1 — Authentication vs. Authorization

Authentication answers "who are you?" — proving identity, usually with a username/password exchanged for a token. Authorization answers "what are you allowed to do?" — once identity is known, deciding whether this user can create a candidate, delete one, or only read. This chapter builds authentication (login → token) and uses it for a simple authorization rule: only a logged-in recruiter may write, anyone may read.

🚫
Never store a plaintext password, ever. If the database is ever breached (backup leak, SQL injection, a misconfigured bucket), plaintext passwords hand over every user's real password immediately — and since people reuse passwords across sites, that breach cascades everywhere else too. Store only a one-way hash.
39.2 — Password Hashing

A hash is a one-way function: easy to compute forward, computationally infeasible to reverse. The bcrypt package implements a strong, slow-by-design password hash that's deliberately expensive to brute-force. bcrypt.gensalt() generates a random salt for every hash and hashpw embeds it in the result, so two users with the same password still get different hashes. You never decrypt a hash to check a password — bcrypt.checkpw re-hashes the login attempt with the stored salt and compares.

Older FastAPI tutorials reach for passlib (hashing) and python-jose (JWTs). Neither is actively maintained any more, and passlib crashes on a fresh install alongside current bcrypt with a confusing "password cannot be longer than 72 bytes" error. If you meet them in an older codebase, the calls map directly onto the libraries below. This chapter uses the underlying, actively maintained libraries directly: bcrypt and PyJWT.

🎬

Colab / real Python — hashing and verifying a password
import bcrypt def hash_password(plain: str) -> str: return bcrypt.hashpw(plain.encode(), bcrypt.gensalt()).decode() def verify_password(plain: str, hashed: str) -> bool: return bcrypt.checkpw(plain.encode(), hashed.encode()) hashed = hash_password("s3cret-password") print(hashed) # looks like $2b$12$... — never the original string print(verify_password("s3cret-password", hashed)) # True print(verify_password("wrong-guess", hashed)) # False
💡
fake_users_db in this chapter stores only hashed_password, never the raw password — exactly like a real database table would. bcrypt works on bytes, so the helpers .encode() the password going in; the hash is .decode()d to a plain str so it fits a database text column or a JSON field, and .encode()d back to bytes when verifying.
⚠️
bcrypt only looks at the first 72 bytes of a password. Older releases silently ignored everything after byte 72, so two long passwords sharing a 72-byte prefix were treated as identical. Current bcrypt refuses instead: hashpw raises ValueError: password cannot be longer than 72 bytes. In a real app, enforce a maximum password length at the API boundary (a Pydantic Field(max_length=...), like the validation from Chapter 36) so a user gets a clean 422 rather than a 500.
39.3 — OAuth2PasswordBearer & the Token Flow Shape

FastAPI's OAuth2PasswordBearer(tokenUrl="token") declares two things at once: (1) protected routes should expect an Authorization: Bearer <token> header, and (2) the interactive docs should show a login form that POSTs to /token. The /token route itself accepts OAuth2PasswordRequestForm — a username + password submitted as form data, not JSON (this is the OAuth2 "password flow" spec, not a FastAPI-specific choice).

Colab / real Python — declaring the token scheme and the login route
from fastapi import FastAPI, Depends, HTTPException from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm app = FastAPI() oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token") fake_users_db = { "recruiter1": {"username": "recruiter1", "hashed_password": hash_password("hunter2")} } @app.post("/token") def login(form_data: OAuth2PasswordRequestForm = Depends()): user = fake_users_db.get(form_data.username) if not user or not verify_password(form_data.password, user["hashed_password"]): raise HTTPException(status_code=401, detail="Incorrect username or password") # token creation shown in 39.4
39.4 — Creating & Verifying JWTs

A JWT (JSON Web Token) is a signed, self-contained string encoding a payload — here, who the user is (sub) and when the token expires (exp). jwt.encode (from the PyJWT package, imported as jwt) signs the payload with a secret key; jwt.decode verifies the signature and expiry, raising a jwt.InvalidTokenError if either is invalid. The server never has to look the token up anywhere — the signature alone proves it wasn't tampered with.

Colab / real Python — encoding and decoding a JWT
import jwt from datetime import datetime, timedelta, timezone SECRET_KEY = "dev-only-secret-change-in-production" ALGORITHM = "HS256" payload = {"sub": "recruiter1", "exp": datetime.now(timezone.utc) + timedelta(minutes=30)} token = jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM) print(token) # three dot-separated base64 segments: header.payload.signature decoded = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM]) print(decoded["sub"]) # 'recruiter1'
⭐
A JWT is signed, not encrypted. Anyone can base64-decode the payload and read it — never put a raw password or secret inside one. The signature only proves it wasn't altered since the server issued it.
💡
Three PyJWT details worth knowing. (1) jwt.encode returns a str. (2) The sub claim must be a string — jwt.decode rejects a token whose sub is, say, an integer user id, so store str(user.id). (3) Build exp from a timezone-aware datetime.now(timezone.utc); datetime.utcnow() is deprecated. And always pass algorithms=[...] to decode — it stops an attacker choosing the verification algorithm for you.
39.5 — The get_current_user Dependency

This is the piece every protected route will share: decode the bearer token, and either return the identified user or raise HTTPException(401). FastAPI's Depends() means this function runs automatically before the route body — the route never sees a request without a valid token.

Colab / real Python — the shared auth dependency
import jwt from fastapi import Depends, HTTPException, status def get_current_user(token: str = Depends(oauth2_scheme)): try: payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM]) username = payload.get("sub") if username is None: raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token") return username except jwt.InvalidTokenError: raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token")
💡
jwt.InvalidTokenError is the base class of every PyJWT decode failure — ExpiredSignatureError, InvalidSignatureError, DecodeError and the rest are all subclasses, so one except clause turns an expired, tampered or malformed token into the same clean 401.
39.6 — Protecting Endpoints

Adding current_user: str = Depends(get_current_user) as a parameter is the entire mechanism — FastAPI runs the dependency first. If it raises, the route body never executes and the caller gets a clean 401. If it succeeds, current_user is available inside the route, already verified.

Colab / real Python — a protected write endpoint
@app.post("/candidates", response_model=CandidateOut, status_code=201) def create_candidate(candidate: CandidateIn, current_user: str = Depends(get_current_user)): new_id = max(CANDIDATES) + 1 CANDIDATES[new_id] = candidate.model_dump() return {"id": new_id, **candidate.model_dump()}
💡
GET routes stay open — only POST/PUT/DELETE gain the Depends(get_current_user) parameter, matching the "anyone can read, only a logged-in recruiter can write" rule from 39.1.
39.7 — Testing Authenticated Endpoints

Testing auth with TestClient takes two calls: first POST real form data to /token and pull the token out of the response, then send that token as an Authorization header on the protected call. Nothing about this is mocked — it's the exact same JWT a real client would receive and send.

Colab / real Python — logging in, then calling a protected route
from fastapi.testclient import TestClient client = TestClient(app) login_response = client.post("/token", data={"username": "recruiter1", "password": "hunter2"}) token = login_response.json()["access_token"] response = client.post( "/candidates", json={"name": "Frank", "score": 0.70}, headers={"Authorization": f"Bearer {token}"} ) assert response.status_code == 201 no_auth_response = client.post("/candidates", json={"name": "Ghost", "score": 0.5}) assert no_auth_response.status_code == 401
🚫
Always test the unhappy path too. A protected endpoint that only gets tested WITH a valid token could be silently accepting every request — the no_auth_response call above is what actually proves the protection works.
Chapter 39 Summary
  • Authentication (who you are) vs. authorization (what you can do) — this chapter builds login and uses it to gate writes.
  • Password hashing (bcrypt.hashpw / bcrypt.checkpw, with a per-hash salt and a 72-byte input limit) means a database breach never exposes real passwords.
  • OAuth2PasswordBearer + a /token route accepting OAuth2PasswordRequestForm is the standard login shape FastAPI expects.
  • JWTs (PyJWT's jwt.encode/decode) are signed, not encrypted — self-contained proof of identity with a built-in expiry.
  • get_current_user as a shared Depends() is the one dependency every protected route reuses — tested by proving both the authorized AND unauthorized paths.
