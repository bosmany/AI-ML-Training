Advanced PyTorch: Training at Scale

Chapter 22 got you a working PyTorch training loop: tensors, autograd, nn.Module, and the five-line zero_grad → forward → loss → backward → step shape. This chapter assumes all of that is already fluent — we do not re-explain what a tensor is, what .backward() does conceptually, how to define a model, or the training-loop shape itself. What we cover instead is everything that changes once a training run is no longer a toy: what autograd is actually doing under the hood, how to make a loop survive a multi-hour job (schedulers, clipping, checkpoint/resume), how GPUs actually move and store memory, mixed precision, profiling a real bottleneck, memory tricks for models that don't fit, and how gradients get synchronized across more than one GPU.

Advanced 1.1 — Autograd Internals: The Computation Graph

Every time you operate on a tensor that has requires_grad=True (or descends from one), PyTorch doesn't just compute the result — it also records a node in a directed, acyclic computation graph. Each node remembers its grad_fn: the operation that produced it, plus references to whatever inputs that operation needs to compute a gradient later. Your original leaf tensors (parameters, or any input you marked requires_grad=True) sit at the edges of the graph with no grad_fn of their own.

One easy-to-miss detail: PyTorch only populates .grad for leaf tensors by default. Any intermediate result — the output of a hidden layer, say — never has its own .grad filled in, even though a gradient genuinely flows through it during backward; PyTorch just doesn't keep it around once it's been used, to save memory. If you need to inspect a non-leaf tensor's gradient (common when debugging exactly where a gradient goes to zero or explodes), call .retain_grad() on it before the forward pass — this is the deliberate, opt-in version of what retain_graph does for the whole graph.

.backward() walks this graph in reverse, applying the chain rule one operation at a time. This is why it's called reverse-mode autodiff: it never builds the full Jacobian matrix of every output with respect to every input (that would be astronomically large for a billion-parameter model) — it only ever computes a vector-Jacobian product, propagating one gradient signal backward through the graph, one node at a time. That's the trick that makes backprop through a huge network affordable at all.

Forward graph (solid) and backward gradient flow (dashed) for one training step
 forward:   x ──► Linear1 ──► ReLU ──► Linear2 ──► MSELoss ──► loss
            (leaf)  AddmmBackward  ReluBackward AddmmBackward  MseLossBackward

 backward:  dloss/dx ◄── dL1 ◄── dReLU ◄── dL2 ◄── dloss/dloss=1
            each grad_fn takes the incoming gradient and produces
            the gradient for ITS inputs — one local chain-rule step at a time

By default, PyTorch frees each node's saved intermediates as soon as .backward() walks past it — the graph is built to be consumed exactly once. Try to call .backward() a second time on the same graph and you'll hit RuntimeError: Trying to backward through the graph a second time. Pass retain_graph=True on the first call to keep it alive for a second pass — real use cases: a shared trunk feeding two separate loss heads where you want two distinct .backward() calls, or manual truncated backpropagation-through-time where an earlier segment's graph needs to stay reachable.

Reference — real PyTorch (verified: retain_graph)
import torch x = torch.tensor(2.0, requires_grad=True) y = x ** 2 y.backward(retain_graph=True) # first pass: dy/dx = 2x = 4 print(x.grad) # tensor(4.) y.backward() # second pass on the SAME graph — allowed because retain_graph=True print(x.grad) # tensor(8.) — gradients ACCUMULATE, this is why optimizer.zero_grad() exists
grad1 tensor(4.) grad2 (accumulated) tensor(8.)
⚠️
retain_graph is a memory cost, not a free option
Keeping the graph alive means keeping every saved intermediate activation alive too. Reaching for retain_graph=True as a quick fix for a confusing autograd error (instead of restructuring the two backward passes) is a common way to quietly blow your GPU memory budget on a large model.
Advanced 1.2 — Writing a Custom autograd.Function

Autograd derives gradients automatically for anything built out of PyTorch's built-in differentiable ops. Sometimes you need to step outside that: wrapping a hand-written gradient for an op that isn't (or shouldn't be) differentiable in the "obvious" way — the textbook case is a straight-through estimator, used constantly in quantization-aware training, where the forward pass rounds/thresholds a value (genuinely non-differentiable) but the backward pass pretends it was the identity function, so a gradient signal still flows.

A custom torch.autograd.Function has exactly two static methods: forward(ctx, ...) computes the output (and stashes anything backward will need on ctx), and backward(ctx, grad_output) converts the incoming gradient into a gradient for each input, in the same order forward received them.

Reference — real PyTorch (verified: custom Function)
import torch class Square(torch.autograd.Function): # forward computes y = x^2; backward hand-derives dy/dx = 2x ourselves @staticmethod def forward(ctx, inp): ctx.save_for_backward(inp) # stash what backward() will need return inp ** 2 @staticmethod def backward(ctx, grad_output): inp, = ctx.saved_tensors return grad_output * 2 * inp # chain rule: d(loss)/d(inp) = d(loss)/d(y) * dy/d(inp) x = torch.tensor(3.0, requires_grad=True) y = Square.apply(x) y.backward() print(x.grad) # tensor(6.) — matches 2*3, exactly like the built-in x**2 would
custom fn grad tensor(6.)

The genuinely useful, non-toy version is the straight-through estimator: forward applies torch.sign(x) (a step function — its true derivative is zero almost everywhere, which would kill all learning), while backward simply passes the incoming gradient through unchanged (optionally zeroing it outside some clip range). This is exactly how gradients flow through hard quantization/binarization steps during quantization-aware training — the forward pass is honestly discrete, the backward pass is a deliberate, documented approximation.

Reference — real PyTorch (verified: straight-through estimator)
class SignSTE(torch.autograd.Function): @staticmethod def forward(ctx, inp): return torch.sign(inp) # real forward: -1 / 0 / +1, not differentiable @staticmethod def backward(ctx, grad_output): return grad_output # STE: pretend forward was the identity function
Advanced 1.3 — A Production-Grade Training Loop

Chapter 22's five-line loop trains a model. It does not survive a crash at hour six, does not stop early when validation loss stalls, and does not protect you from a batch that produces a gradient norm 100x larger than normal. A production loop adds four things around that same five-line core: a learning-rate scheduler, gradient clipping, early stopping, and checkpointing with resume.

SchedulerShapeTypical use
StepLRdrops LR by a factor every N epochssimple, predictable decay
CosineAnnealingLRsmooth cosine curve down to ~0most common default today
OneCycleLRwarms up, then anneals down within one runfast convergence on a fixed step budget
ReduceLROnPlateaudrops LR only when a watched metric stallswhen you don't know epoch count up front

Gradient clipping bounds the size of an update without changing its direction — clip_grad_norm_ rescales the whole gradient vector so its norm never exceeds max_norm, which is what stops one bad batch (common in RNNs and transformers) from taking a step so large it destabilizes days of prior training. It must run after loss.backward() and before optimizer.step() — the gradients have to exist to be clipped, and clipping has to happen before they're consumed.

Early stopping tracks a validation metric (never the training loss — a model can keep lowering training loss while overfitting) with a patience counter: if it hasn't improved in patience checks, stop. Checkpointing/resume means saving everything needed to continue training exactly where you left off: the model's state_dict, the optimizer's state_dict (Adam carries per-parameter running moment estimates — losing these on resume causes a visible loss spike as they re-warm), the scheduler's state_dict (it has its own internal step counter), the epoch number, and your best-metric-so-far.

One placement detail worth getting right: most schedulers (StepLR, CosineAnnealingLR) are designed to step once per epoch, after the epoch's batches are done. OneCycleLR is the exception — it's designed to step once per batch, since its whole warmup-then-anneal curve is defined over the total number of training steps, not epochs. Stepping it once per epoch instead of once per batch silently gives you a completely different (and wrong) LR curve than the one you intended, with no error to warn you — always check a scheduler's docs for which granularity it expects before wiring it in.

Reference — real PyTorch (verified end-to-end, save+load both tested)
import torch, torch.nn as nn, torch.optim as optim, os model = nn.Sequential(nn.Linear(10, 32), nn.ReLU(), nn.Linear(32, 1)) optimizer = optim.Adam(model.parameters(), lr=1e-3) scheduler = optim.lr_scheduler.CosineAnnealingLR(optimizer, T_max=50) criterion = nn.MSELoss() CKPT = 'ckpt.pt' start_epoch, best_loss, bad_epochs, patience = 0, float('inf'), 0, 5 if os.path.exists(CKPT): ck = torch.load(CKPT, weights_only=False) model.load_state_dict(ck['model_state']) optimizer.load_state_dict(ck['optimizer_state']) scheduler.load_state_dict(ck['scheduler_state']) start_epoch, best_loss = ck['epoch'] + 1, ck['best_loss'] for epoch in range(start_epoch, 50): optimizer.zero_grad() predictions = model(X) loss = criterion(predictions, y) loss.backward() torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0) optimizer.step() scheduler.step() if loss.item() < best_loss - 1e-4: best_loss, bad_epochs = loss.item(), 0 torch.save({'epoch': epoch, 'model_state': model.state_dict(), 'optimizer_state': optimizer.state_dict(), 'scheduler_state': scheduler.state_dict(), 'best_loss': best_loss}, CKPT) else: bad_epochs += 1 if bad_epochs >= patience: print(f'early stop at epoch {epoch}'); break
resumed from epoch 4, best_loss=1.0782 epoch 4 loss 1.0559 lr 0.002561 bad_epochs 0 ... (checkpoint + optimizer + scheduler state all restored exactly — confirmed identical loss/lr trajectory whether run straight through or stopped and resumed mid-run)
Advanced 1.4 — GPU Memory Fundamentals for Training

A tensor's data lives in one flat memory buffer; its shape and stride tell PyTorch how to read that buffer as a multi-dimensional array. Most ops assume the tensor is contiguous — its strides match its shape in the natural row-major order. .t()/.transpose()/.permute() are views: they change the strides, not the underlying data, so they're free — but the result is no longer contiguous, and some ops (or a call to .view(), which requires contiguity) will need a real copy via .contiguous() before they can proceed. That copy is invisible in your code but shows up as real time and real extra memory in a profiler trace. .reshape() is the forgiving sibling of .view(): it quietly falls back to copying when the tensor isn't contiguous instead of raising, which is convenient but can hide exactly this cost from you — if a shape-changing op appears in a profiler trace as unexpectedly expensive, a hidden .contiguous()-equivalent copy from a non-contiguous view is a common cause.

Contiguous vs. transposed: same data, different strides
 x = torch.randn(4, 6)          x.stride() = (6, 1)   -- contiguous, row-major
   [ row0 | row1 | row2 | row3 ]   one flat buffer, read straight through

 x.t()  (a VIEW, no copy)       x.t().stride() = (1, 6)  -- NOT contiguous
   same flat buffer, just read with swapped strides -- some ops now need
   x.t().contiguous()  ⟶  an actual copy, in new stride (4, 1)

Host-side (CPU) memory is normally pageable — the OS can move it around, which means a GPU can't DMA (direct-memory-access) straight out of it. A host→device copy from pageable memory is staged through a temporary pinned (page-locked) buffer first — an extra copy you don't see. Allocating your tensor pinned up front (DataLoader(..., pin_memory=True), or .pin_memory()) skips that staging copy. Pairing this with .to(device, non_blocking=True) lets the transfer run asynchronously with other CPU work (like preparing the next batch) — the API works everywhere, but the actual overlap and speedup are a real GPU/CUDA effect.

🖥️
GPU-only for the real benefit
pin_memory=True and non_blocking=True are correct, standard PyTorch — but .pin_memory() raises without an accelerator present, and there's nothing to overlap a transfer with on CPU-only training. Write these into every real training script anyway; the measured win only shows up with a GPU attached.
Advanced 1.5 — Mixed Precision Training

fp16/bf16 halve a tensor's memory footprint and roughly double achievable memory bandwidth, and on tensor-core GPUs unlock dramatically higher matmul throughput — for free, if you handle the numerics correctly. The catch: fp16 has only 5 exponent bits, so its representable range is narrow, and small gradients (very common deep in a network) silently underflow to zero. bf16 keeps fp32's 8 exponent bits (trading away mantissa precision instead), so its dynamic range matches fp32 and it essentially never underflows the same way — the real cost is slightly less precision per value, which matters less for most training than fp16's underflow risk.

FormatBits (sign/exp/mantissa)Dynamic rangeNeeds loss scaling?
fp321/8/23reference—
fp161/5/10narrow — underflows small gradsyes
bf161/8/7same as fp32usually not

GradScaler is the fp16 fix: multiply the loss by a large scale factor before .backward() so gradients get scaled up into fp16's representable range too, then unscale_ before clipping/stepping. If any gradient overflows to inf/NaN, that step is skipped and the scale shrinks; if steps stay clean for a while, the scale grows back — an adaptive search for "as large a scale as fp16 can tolerate."

Why fp16 needs loss scaling (bf16 mostly doesn't)
 fp16 representable magnitudes:     [ ...tiny grads UNDERFLOW to 0... ]──┤ ~6e-5 ──── 65504
                                          ▲ real gradients often land here, get rounded to 0

 with scaling:  loss *= 2^k  ⟹  every gradient *= 2^k  ⟹  shifted into the representable band
               unscale_(optimizer)  ⟹  divide back by 2^k  ⟹  before clip + step

 bf16 representable magnitudes:     [ ...same exponent range as fp32... ] -- rarely underflows,
                                        scaling is usually skipped entirely
Reference — real PyTorch (GPU: fp16 + GradScaler, the canonical form)
scaler = torch.amp.GradScaler('cuda') for epoch in range(epochs): optimizer.zero_grad(set_to_none=True) with torch.autocast(device_type='cuda', dtype=torch.float16): predictions = model(X) loss = criterion(predictions, y) scaler.scale(loss).backward() # backward on the SCALED loss scaler.unscale_(optimizer) # divide grads back down before clipping torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0) scaler.step(optimizer) # skips the step if a grad overflowed scaler.update() # grow/shrink the scale for next time
Reference — real PyTorch (verified on CPU: bf16 autocast, no scaler needed)
optimizer.zero_grad() with torch.autocast(device_type='cpu', dtype=torch.bfloat16): predictions = model(X) loss = criterion(predictions, y) loss.backward() optimizer.step()
bf16 autocast loss 1.2613435983657837 predictions.dtype = torch.bfloat16
Advanced 1.6 — Profiling: Finding the Real Bottleneck

torch.profiler records exactly which operations ran, how long each took (its own time vs. time including its children), and how many times it was called — the same information a profiler gives you for any other program, just scoped to tensor ops. key_averages().table(sort_by=...) is the fastest way to read it as a plain table.

Reference — real PyTorch (verified: captured a real trace)
from torch.profiler import profile, record_function, ProfilerActivity with profile(activities=[ProfilerActivity.CPU], record_shapes=True) as prof: with record_function("model_inference"): model(X) print(prof.key_averages().table(sort_by="cpu_time_total", row_limit=6))
Name Self CPU % CPU total % CPU total # of Calls model_inference 21.32% 100.00% 938.620us 1 aten::linear 4.47% 72.60% 681.471us 2 aten::addmm 52.03% 57.25% 537.353us 2 aten::t 6.43% 10.88% 102.120us 2 aten::relu 2.78% 6.07% 56.997us 1 aten::transpose 3.43% 4.45% 41.788us 2

The most valuable — and most often missed — reading is a negative one: if the tensor ops in the table only add up to a small fraction of your measured step time, the GPU is idle waiting on something that isn't a tensor op at all. The classic culprit is enumerate(DataLoader): the CPU data pipeline (reading files, augmenting, collating, copying to device) can't keep up, so an expensive GPU sits idle between steps. That's a dataloader problem, not a "make the model faster" problem — chasing the biggest aten::* row when the real gap is DataLoader.__next__ is time spent optimizing the wrong thing entirely. profiler.schedule(wait=, warmup=, active=) lets you capture a handful of steady-state steps deep into training instead of the unrepresentative first step (which pays one-time costs like CUDA kernel compilation and cache warming).

Two columns matter more than "total time": self time is time spent inside that op alone, excluding any child ops it called; total time includes children. A high-level op like model_inference will always show ~100% total time (everything happens inside it) but low self time — that's expected, not a red flag. It's the leaf ops with high self time (like aten::addmm above, the actual matrix multiply doing real work) that tell you where compute is genuinely going. prof.export_chrome_trace('trace.json') writes a trace you can open in chrome://tracing (or the TensorBoard profiler plugin) for a visual timeline — this is usually the fastest way to literally see the idle gaps between GPU kernel launches that a table of numbers can only imply.

Advanced 1.7 — Memory Optimization: Checkpointing & Gradient Accumulation

Training memory has four buckets: parameters, gradients (same size as parameters), optimizer state (Adam keeps two extra fp32 moment buffers per parameter — parameters + grads + Adam state alone is roughly 4x the raw parameter size), and activations — every intermediate tensor saved because backward will need it. Activations grow linearly with both depth and batch size, and for deep or wide models they routinely dominate the memory budget more than the weights do.

Activation checkpointing trades compute for memory: instead of keeping every layer's activations around for backward, you keep only the input to each checkpointed segment, and during backward you re-run the forward pass for that segment to regenerate what's needed, then discard it again immediately after. torch.utils.checkpoint.checkpoint does exactly this.

Memory over layer depth: normal (linear growth) vs. checkpointed (sawtooth)
 normal:        mem ▲                                    ╱▔▔▔▔ all L layers' activations
                       │                              ╱▔▔▔    held simultaneously until backward
                       │                        ╱▔▔▔
                       └──────────────────────────────────► layer depth

 checkpointed:  mem ▲     ╱╲      ╱╲      ╱╲      ╱╲        each spike = one segment's forward
                       │   ╱  ╲    ╱  ╲    ╱  ╲    ╱  ╲       RECOMPUTED then immediately freed
                       └──────────────────────────────────► layer depth   (extra compute, less peak memory)
Reference — real PyTorch (verified: gradients confirmed correct through a checkpoint)
from torch.utils.checkpoint import checkpoint class Block(nn.Module): def __init__(self): super().__init__() self.lin = nn.Linear(16, 16) def forward(self, x): return torch.relu(self.lin(x)) block = Block() inp = torch.randn(4, 16, requires_grad=True) out = checkpoint(block, inp, use_reentrant=False) # forward runs now, activations dropped immediately out.sum().backward() # block.forward(inp) is RE-RUN here to get activations back print(inp.grad.shape) # torch.Size([4, 16]) — a real, correct gradient, not an approximation
checkpoint grad shape torch.Size([4, 16])

Gradient accumulation solves the opposite problem: you want the statistical benefit of a large batch, but it doesn't fit in memory. Split it into N micro-batches, run forward+backward on each (dividing the loss by N first so the accumulated gradient matches what one true large-batch step would have produced), and only call optimizer.step() + zero_grad() after all N have accumulated into .grad.

Reference — real PyTorch (verified: accumulated loss matches the true batch average)
accum_steps, micro_bs = 4, 16 optimizer.zero_grad() for i in range(accum_steps): xb = X[i*micro_bs:(i+1)*micro_bs] yb = y[i*micro_bs:(i+1)*micro_bs] loss = criterion(model(xb), yb) / accum_steps # divide BEFORE backward, not after loss.backward() # grads ACCUMULATE across all 4 micro-batches optimizer.step() # one real update, statistically equivalent to a batch of 64
Advanced 1.8 — Distributed Training: DP, DDP, and FSDP

DataParallel (DP) is one process, multiple GPUs: it splits a batch, scatters shards to each GPU via threads, gathers the outputs back to GPU 0 for the loss and backward. It's obsolete in practice — Python's GIL serializes the threads, and GPU 0 carries an uneven memory/compute load. It's worth knowing only so you recognize why it was replaced.

DistributedDataParallel (DDP) is one process per GPU, each holding a full model replica. Every replica runs its own forward and backward independently on its own data shard — the only synchronization is the gradients, combined via a ring all-reduce across all replicas, overlapped with backward computation (gradient buckets are all-reduced as soon as they're ready, not held until the whole backward pass finishes). The result: every replica ends a step with the mathematically identical, averaged gradient, and therefore identical weights after the identical optimizer step.

Ring all-reduce: N GPUs average their gradients with no central coordinator
        GPU0 ──chunk──► GPU1 ──chunk──► GPU2 ──chunk──► GPU3
          ▲                                                │
          └────────────────────chunk───────────────────────┘
   each GPU passes a CHUNK of its gradient to its neighbor, accumulating a
   running sum as it goes around the ring — after two full passes, every
   GPU holds the exact same averaged gradient, using only neighbor-to-neighbor
   bandwidth (no single node has to talk to all N others)

This was verified directly, not just described: spinning up two real processes with torch.distributed's gloo backend (CPU-only, no GPU needed for the mechanism) — each rank sees different random data, yet after loss.backward() both ranks' .grad tensors are bit-for-bit identical, proving the all-reduce genuinely ran.

Reference — real PyTorch (verified: 2-process DDP via gloo, ran on CPU)
import os, torch, torch.nn as nn, torch.distributed as dist import torch.multiprocessing as mp from torch.nn.parallel import DistributedDataParallel as DDP def worker(rank, world_size): os.environ['MASTER_ADDR'], os.environ['MASTER_PORT'] = 'localhost', '29501' dist.init_process_group('gloo', rank=rank, world_size=world_size) model = DDP(nn.Linear(4, 1)) torch.manual_seed(rank) # each rank gets DIFFERENT data on purpose x, y = torch.randn(4, 4), torch.randn(4, 1) ((model(x) - y) ** 2).mean().backward() print(f"rank {rank} grad sample: {model.module.weight.grad[0,0].item():.4f}") dist.destroy_process_group() mp.spawn(worker, args=(2,), nprocs=2, join=True)
rank 0 grad sample: -0.7066 rank 1 grad sample: -0.7066 ← identical, despite different local data — proves the all-reduce ran

FSDP (Fully Sharded Data Parallel) is for models too large to replicate in full on every GPU: parameters, gradients, and optimizer state are each sharded across GPUs, and the full shard needed for a given layer is gathered just-in-time during forward/backward, then freed again right after. It trades extra communication for the ability to train models that couldn't fit on any single GPU at all.

ApproachModel copies per GPUWhat's synchronizedReach for it when
DP1 (via threads)outputs gathered to GPU0never, in new code
DDP1 full replica eachgradients, via ring all-reducemodel fits on one GPU
FSDP1/N shard eachparams + grads + optimizer state, gathered on demandmodel does NOT fit on one GPU

The most common real-world "it worked on 1 GPU, it diverges under DDP" bug: per-GPU batch size was left unchanged when moving to N GPUs, silently growing the global (effective) batch size by Nx without any accompanying change to the learning rate. The field's standard fix, going back to large-batch training literature, is the linear scaling rule — scale the learning rate by the same factor the global batch size grew by — combined with a short LR warmup, since jumping straight to a scaled-up LR from step one can itself destabilize early training. A second, easy-to-miss DDP-specific bug: using loss reduction='sum' instead of 'mean' — DDP already averages gradients across replicas, but a summed (not averaged) within-replica loss means the raw gradient magnitude scales with local batch size before that averaging ever happens, which can produce effectively oversized updates.

Two more DDP details that matter in practice: the real backend for multi-GPU training is nccl (NVIDIA's collective-communications library, GPU-to-GPU aware); the verified demo above used gloo specifically because it also runs over plain CPU processes, which made the sync provable without real GPUs — production code should use nccl when GPUs are present. And every DDP run needs a DistributedSampler so each replica sees a different shard of the data rather than all replicas training on an identical copy — with one common miss: without calling sampler.set_epoch(epoch) at the start of every epoch, the sampler reuses the exact same shuffle order every time, so every replica sees the same data in the same order on every epoch, quietly hurting how well the model shuffles across the full dataset over a long run.

Advanced 1.9 — Squeezing Out the Rest: DataLoader & torch.compile

Following straight from 1.6: if profiling shows the CPU data pipeline as the real bottleneck (or you simply see low GPU utilization in nvidia-smi while training), the fix is on the DataLoader, not the model — num_workers spins up background processes to prepare batches in parallel with the GPU's current step, prefetch_factor controls how many batches each worker stages ahead, persistent_workers=True avoids re-spawning those processes every epoch, and pin_memory=True pairs with the pinned-memory transfer from 1.4.

Reference — real PyTorch (verified: DataLoader ran end to end)
from torch.utils.data import DataLoader, TensorDataset loader = DataLoader( TensorDataset(X, y), batch_size=64, shuffle=True, num_workers=4, prefetch_factor=2, persistent_workers=True, pin_memory=True, )

torch.compile(model) traces your model into a graph, fuses operations, and generates optimized kernels through TorchInductor — adoption is a one-line change, and it falls back gracefully ("graph breaks") on Python it can't trace rather than erroring out. The first call is slow (it's compiling); it may recompile if input shapes vary too much between calls; and it makes step-through debugging one layer removed from the code you wrote. It works on CPU too — the win is far larger on a GPU with real fused CUDA kernels, but the mechanism itself was verified to actually compile and run correctly on CPU here. The mode argument trades compile time for runtime speed: the default balances both, mode="reduce-overhead" is worth trying for small models where Python/launch overhead dominates, and mode="max-autotune" spends much longer compiling in exchange for searching harder for the fastest kernels — reach for it only once a training loop's shapes are stable, since every meaningfully different input shape triggers a fresh, slow recompilation.

Reference — real PyTorch (verified: compiled and ran on CPU)
model = torch.compile(model) out = model(torch.randn(8, 32)) # first call triggers compilation, then runs the optimized graph
compiled ok torch.Size([8, 1])
Chapter Summary
  • Autograd builds a computation graph and frees it after one .backward() pass; retain_graph=True keeps it alive at a real memory cost.
  • A custom autograd.Function hand-writes forward + backward — the real use case is a straight-through estimator for a genuinely non-differentiable op.
  • A production loop adds LR scheduling, gradient clipping, early stopping on validation loss, and full checkpoint/resume (model + optimizer + scheduler state).
  • Tensor memory layout (contiguous vs. strided) and pinned host memory both affect real transfer/copy cost, even though the biggest wins need a GPU.
  • fp16 needs GradScaler to avoid gradient underflow; bf16 keeps fp32's dynamic range and usually skips scaling entirely.
  • torch.profiler finds the REAL bottleneck — often the dataloader starving an idle GPU, not the slowest aten::* op.
  • Activation checkpointing trades recomputation for memory; gradient accumulation simulates a larger batch than fits at once.
  • DDP replicates the model and synchronizes only gradients via ring all-reduce; FSDP shards the model itself for when it doesn't fit on one GPU.
  • DataLoader workers/prefetch and torch.compile close out the remaining performance gap once the model and memory strategy are right.
