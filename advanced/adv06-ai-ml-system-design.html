6.1 — Same Framework, Nine New Boxes

What this chapter does and does not do

sr01 gave you a framework and the plumbing every distributed system needs: requirements and estimation (sr01 §1.2–1.3), caching (§1.4), databases and replication (§1.5), sharding (§1.6), queues (§1.7), rate limiting (§1.8), load balancing (§1.9), API design (§1.10), observability (§1.11) and failure modes (§1.12). Its Case Study 5 walked through an ML model-serving platform in detail: dynamic batching, replica sizing from throughput math, sticky canary routing by hashing the user id, and a failure-mode table. None of that is repeated below — it is cited by section number, exactly as a senior design doc cites prior art instead of re-deriving it.

What's different about ML systems is not the plumbing, it's what flows through the plumbing: a "row" is a feature vector that must be computed the same way at training time and at serving time; a "cache" holds a feature or an embedding that goes stale on its own schedule, unrelated to how often it's read; a "deploy" ships a model whose bad behavior is silent — the service returns 200 with a confident, wrong number, and only a delayed, incomplete label tells you it happened. This chapter designs nine systems where that difference is the whole problem: recommendation, search/ranking, fraud detection, feature stores, training platforms, model serving, RAG, high-scale LLM inference, and ML monitoring.

6.2 — Recommendation Systems: Candidate Generation + Ranking

Requirements

Functional: given a user and a context, return a ranked list of items in real time. Non-functional: a strict end-to-end latency budget (typically 100–200 ms p99), high throughput at low marginal cost per request, and feature freshness — a user who just watched something should see the effect within seconds, not the next day's batch job. Assumption: a catalog too large to score exhaustively (millions of items) per request.

Architecture: two stages, not one

No system scores every item for every request — the catalog is too large and the latency budget too small. Candidate generation narrows millions of items to a few hundred cheaply (an approximate-nearest-neighbor search over embeddings, or simple rules like "same category, recently popular"). Ranking then applies an expensive, accurate model to just those candidates. This is the same shape as search engines (6.3) and it exists purely to fit an expensive model inside a latency budget.

Splitting a 100 ms budget between retrieval and ranking
total_budget_ms = 100 retrieval_ms = 30 # ANN search over the embedding index (candidate generation) feature_fetch_ms = 8 # online feature store read for the candidates (see 6.5) ranking_base_ms = 10 # fixed cost of one ranking-model batch call ranking_per_item_ms = 0.6 # marginal cost per candidate scored remaining = total_budget_ms - retrieval_ms - feature_fetch_ms - ranking_base_ms max_candidates = int(remaining / ranking_per_item_ms) print(f"Total p99 latency budget: {total_budget_ms} ms") print(f"Candidate generation (ANN retrieval): {retrieval_ms} ms") print(f"Feature fetch for candidates: {feature_fetch_ms} ms") print(f"Ranking model fixed cost: {ranking_base_ms} ms") print(f"Remaining for per-candidate ranking: {remaining} ms") print(f"Max candidates the ranker can afford to score: {max_candidates}")
Total p99 latency budget: 100 ms Candidate generation (ANN retrieval): 30 ms Feature fetch for candidates: 8 ms Ranking model fixed cost: 10 ms Remaining for per-candidate ranking: 52 ms Max candidates the ranker can afford to score: 86

This is the same batching arithmetic as sr01 §1.17's batch_time(b) = 20 + 2 * b — a fixed cost plus a per-item cost — applied to a ranking model instead of a generic accelerator call. The output (86 candidates) is the actual design constraint: the candidate-generation stage must return a short-list under 86, not "as many good candidates as possible."

Feature freshness, and why it's the hard part

The ranking model's best features are usually recency signals: what did this user just click, add to cart, or skip. A feature computed by last night's batch job is already stale by the time it's read, and recommendations visibly ignore what the user just did — the classic complaint "I already bought that, why is it still recommended." The fix is the same online/offline split as 6.5's feature store: recent-interaction features are written to the online store within seconds of the event (a streaming job, not a nightly batch), while slow-moving features (long-term taste profile) stay on the cheaper batch path.

⚠️
Common mistakes Scoring the whole catalog "to be safe" and blowing the latency budget. Treating candidate generation as a solved, one-time step instead of its own tunable trade-off (recall vs. latency). Shipping a ranking model with training data assembled from batch features while serving reads mostly-fresh online features — different distributions, same training-serving skew problem as 6.5.
Recap
  • Two-stage retrieval-then-rank exists to fit an expensive model inside a fixed latency budget — split the budget like sr01's batching math, not by guesswork.
  • Freshness is the differentiator: recent-interaction features need a streaming write path, not a nightly batch.
6.3 — Search & Ranking: The Relevance Pipeline

Requirements and architecture

Search shares recommendation's two-stage shape (6.2) with one addition: a query. Retrieval narrows the corpus using lexical match (inverted index, BM25) and/or semantic match (embedding similarity, the same ANN index as 6.2 and RAG's retrieval in 6.8). Ranking then reorders the short-list with a model that can afford to look at query-document interaction features retrieval couldn't (click history for this query, freshness, authority signals).

Learning-to-rank, at the level a system designer needs

A ranking model can be trained three ways. Pointwise predicts a relevance score per document independently (simplest, treats ranking as regression/classification — misses that what matters is relative order). Pairwise trains on "document A should rank above document B" pairs (directly optimizes order, but pair counts explode with list length). Listwise optimizes a whole ranked list against a ranking metric directly (closest to what you actually want, most expensive to train). As a system designer you rarely implement the loss function yourself — the decision that matters is what pairs or lists you can mine from click logs at your traffic volume, because pairwise and listwise approaches are only as good as the implicit-feedback data behind them.

💡
Reused, not re-taught Measuring whether a ranking is actually good — recall@k, MRR, nDCG — is covered with real runnable code in adv04: Evaluation Beyond Accuracy. This section is architecture; that chapter is measurement.

  • Pointwise/pairwise/listwise is a data-availability decision as much as a modeling one.

6.4 — Fraud & Anomaly Detection: Scoring in Milliseconds, Learning in Months

Requirements

Functional: score every transaction in real time; allow, hold for review, or block. Non-functional: a latency budget tight enough to sit inline in a checkout path (tens of milliseconds, not sr01 Case Study 5's 150 ms — fraud scoring usually shares the request path with payment authorization, which has its own budget); very high recall on rare events; every decision auditable. The twist that makes this different from every other pattern in this chapter: the ground-truth label (a confirmed chargeback or a confirmed-legitimate transaction) can take weeks to arrive, while the fraud pattern itself can drain accounts in minutes.

Fraud-scoring data flow
 transaction ─► streaming feature engine ─► fraud model ─► rule engine overlay ─► allow / hold / block
                (velocity: count/sum per        (score)      (hard limits,             │
                 card in a sliding window)                    regulatory rules)        │
                                                                                        ▼
 outcome (chargeback, weeks later) ◄── case review (hours) ◄── held/blocked queue ◄─────┘
      │                                       │
      └──────────────────► labels for retraining, arriving at two very different speeds

Deep dive 1: velocity features must be O(1), not O(history)

The single most useful fraud feature is a velocity aggregate: "how many transactions has this card made in the last 10 minutes," "what's the sum of amounts in the last hour." The naive implementation rescans the card's whole history on every transaction. That's fine for a demo and catastrophic in production, because the cost grows with how much history a card has — exactly the accounts an attacker is trying to drain fast accumulate the most history the fastest.

Naive rescan vs. a sliding-window deque, same event stream
from collections import deque def make_stream(n, gaps): t, out = 0.0, [] for i in range(n): t += gaps[i % len(gaps)] out.append(t) return out gaps = [1, 2, 1, 3, 1, 1, 2, 5, 1, 2] # seconds between transactions, repeating pattern stream = make_stream(2000, gaps) window = 600 # 10-minute velocity window, in seconds def naive_velocity(history, now, window): return sum(1 for t in history if now - t <= window) naive_work = 0 history = [] for now in stream: naive_work += len(history) # comparisons this call makes _ = naive_velocity(history, now, window) history.append(now) windowed_work = 0 dq = deque() for now in stream: while dq and now - dq[0] > window: dq.popleft() windowed_work += 1 dq.append(now) windowed_work += 1 print(f"Events processed: {len(stream)}") print(f"Naive rescan: {naive_work:,} comparisons total ({naive_work / len(stream):.1f} per event, growing with history)") print(f"Sliding window: {windowed_work:,} operations total ({windowed_work / len(stream):.1f} per event, flat)") print(f"Naive is {naive_work / windowed_work:.0f}x more work over this run")
Events processed: 2000 Naive rescan: 1,999,000 comparisons total (999.5 per event, growing with history) Sliding window: 3,684 operations total (1.8 per event, flat) Naive is 543x more work over this run

The deque version amortizes to roughly two operations per event forever, regardless of how long the card has been active. This is a streaming-aggregation problem, not a database problem: production systems do this with a windowed stream processor (the ML-specific version of "you already know Kafka" — here the consumer keeps per-key sliding-window state under a strict latency SLA, not just routing events), sharded by card or account id so each key's state lives on one node.

Deep dive 2: the feedback-loop delay problem

A brand-new fraud pattern starts today. The complete, trustworthy label — a chargeback — is typically confirmed 30 to 90 days later. If that's your only signal, you find out your model missed a new pattern about two months after it started, by which point the damage is done and the pattern has likely evolved. The mitigation is not "wait faster," it's using a faster, incomplete proxy label alongside the slow, complete one: a small fraction of transactions get manually reviewed by an analyst within a day, and that review flag — while it only covers a sample — is available almost immediately.

Two label sources for the same new fraud pattern: coverage over time
n_events = 200 event_day = [i * 14 / n_events for i in range(n_events)] # a new fraud pattern spread over 14 days chargeback_delay = [30 + (i % 61) for i in range(n_events)] # ground truth: 30-90 days later analyst_flagged = [(i % 20 == 0) for i in range(n_events)] # only 5% get a fast manual review analyst_delay = 1 # review flag lands the next day def coverage(as_of_day, ready_fn): ready = sum(1 for i in range(n_events) if ready_fn(i, as_of_day)) return ready / n_events def chargeback_ready(i, as_of): return event_day[i] + chargeback_delay[i] <= as_of def analyst_ready(i, as_of): return analyst_flagged[i] and event_day[i] + analyst_delay <= as_of print(f"{'Day':>4} {'Chargeback coverage':>20} {'Analyst-flag coverage':>22}") for day in (7, 14, 30, 45, 60, 90): cb = coverage(day, chargeback_ready) an = coverage(day, analyst_ready) print(f"{day:>4} {cb:>19.0%} {an:>21.0%}")
Day Chargeback coverage Analyst-flag coverage 7 0% 2% 14 0% 5% 30 0% 5% 45 18% 5% 60 46% 5% 90 88% 5%

At day 30 the "authoritative" label source still knows nothing, while the analyst-flag signal has been sitting at its 5% ceiling since day 14 — incomplete, but present. Neither label alone is enough: the fast one is a biased sample (only what got reviewed), the slow one is unbiased but useless for same-week decisions. Production systems use the fast signal to trigger investigation and tighten rules immediately, and the slow signal as the eventual, authoritative retraining input — the same "label-free early warning vs. matured ground truth" split as mp04 §4.7, applied one layer earlier, before labels exist at all.

Scaling, reliability, cost, security

Scaling: shard streaming aggregation state by account/card id, same principle as sr01 §1.6's shard-key-from-dominant-query rule. Reliability: when the model service is unhealthy, decide explicitly whether to fail open (allow, accept fraud risk) or fail closed (block, accept false-positive/customer-friction risk) — this is a business decision to make in advance, not an accident of whatever the circuit breaker (sr01 §1.12) defaults to. Cost: the real trade-off is false positives (blocked legitimate customers, support cost, churn) against false negatives (fraud losses) — a ranking/threshold decision, not a pure accuracy one; adv04 covers choosing that threshold properly. Security: transaction data is PII and payment data; tokenize card numbers before they reach the feature pipeline, and keep the fraud model's audit log (which version scored which transaction) for regulatory dispute handling.

RiskEffectMitigation
Streaming aggregator falls behindVelocity features become stale exactly when an attack is acceleratingBackpressure + shed low-priority feature updates before dropping the scoring path itself
Only using mature labelsNew fraud pattern invisible for 30–90 daysFast proxy labels (analyst review, disputes) as an early-warning layer, per above
Rule engine and model disagree silentlyOne overrides the other with no record of whyLog both scores and the final decision; alert when the overlay overrides the model above a rate threshold
Recap
  • Velocity features need O(1) sliding-window state, sharded by key — not a rescan, ever.
  • The feedback loop is the defining constraint: pair a fast, incomplete label with a slow, complete one.
  • Fail-open vs. fail-closed on model outage is a business decision made in the design doc, not a default.
6.5 — Feature Stores & Real-Time Inference: One Row, Two Clocks

Requirements

Functional: serve the same feature value whether it's read during training (a batch job, over months of history) or during inference (a single low-latency lookup, right now). Non-functional: online reads in single-digit milliseconds at the combined QPS of every model that shares the store; offline reads that can scan years of history without touching the online path. This is the real-time inference platform pattern and the feature-store pattern folded into one, because "online feature serving" is the feature store's read path.

Feature store architecture
 batch jobs / streaming jobs ──► OFFLINE STORE (Parquet/warehouse, adv05) ──► training pipeline
                                       │  materialize (point-in-time correct)
                                       ▼
                                 ONLINE STORE (low-latency KV, ms reads)
                                       ▲
 request ─► API gateway ─► model service ── reads features at request time

Deep dive 1: sizing the online store like any other read-heavy service

The online store is read by every model that uses it, so its capacity plan sums across models — the same estimation discipline as sr01 §1.3, applied to feature reads instead of API requests.

Capacity for a shared online feature store
import math models = [ ("ranker", 2000, 40), # (name, request QPS, features read per request) ("fraud", 3000, 15), ("ads", 1500, 25), ] ops_per_replica = 50_000 # a single online-store replica's sustained read ops/sec target_util = 0.6 total_ops = sum(qps * feats for _, qps, feats in models) replicas = math.ceil(total_ops / (ops_per_replica * target_util)) for name, qps, feats in models: print(f"{name:<8} {qps:>5} req/s x {feats:>2} features = {qps * feats:>7,} reads/s") print(f"Total feature reads/sec: {total_ops:,}") print(f"Replicas at {target_util:.0%} utilisation: {replicas}") util_if_one_dies = total_ops / (ops_per_replica * (replicas - 1)) print(f"Utilisation if one replica dies: {util_if_one_dies:.0%}")
ranker 2000 req/s x 40 features = 80,000 reads/s fraud 3000 req/s x 15 features = 45,000 reads/s ads 1500 req/s x 25 features = 37,500 reads/s Total feature reads/sec: 162,500 Replicas at 60% utilisation: 6 Utilisation if one replica dies: 65%

Six replicas survive one loss at 65% — comfortably under saturation, the same "lose-a-zone" check sr01 §1.3 recommends for any capacity plan. Every new model that onboards to the shared store adds its row to this table; the store's capacity plan should be re-run at onboarding time, not discovered in an incident.

Deep dive 2: point-in-time correctness, or why the offline metric lied

A feature pipeline that computes "total purchases so far" by aggregating all data available today, and joins it onto historical training rows, leaks the future into the past: a customer's post-churn silence becomes a feature that predicts the churn that already happened. adv05 covers the SQL pattern for doing this correctly (point-in-time joins); here's why it matters enough to design around. Compare a feature computed correctly (only data available as of each row's label snapshot) against the same feature computed the leaky way (all data, including what happened after).

Point-in-time feature vs. a leaky all-time aggregate
# customer: (purchases BEFORE the label snapshot, purchases AFTER it, churned label) customers = { "c1": (5, 0, 1), "c2": (4, 6, 0), "c3": (6, 0, 1), "c4": (3, 5, 0), "c5": (4, 0, 1), "c6": (7, 7, 0), "c7": (5, 0, 1), "c8": (6, 6, 0), } def point_in_time_count(before, after): return before # only what was known as of the label snapshot def leaky_count(before, after): return before + after # what a naive "total purchases so far" job computes TODAY threshold = 7 print(f"{'cust':<5}{'correct(PIT)':>13}{'leaky(all-time)':>17}{'label':>7}") for name, (b, a, y) in customers.items(): print(f"{name:<5}{point_in_time_count(b,a):>13}{leaky_count(b,a):>17}{y:>7}") def accuracy(fn): correct = 0 for b, a, y in customers.values(): pred = 1 if fn(b, a) <= threshold else 0 correct += (pred == y) return correct / len(customers) print(f"Accuracy predicting churn at count <= {threshold}, point-in-time feature: {accuracy(point_in_time_count):.0%}") print(f"Accuracy predicting churn at count <= {threshold}, leaky all-time feature: {accuracy(leaky_count):.0%}")
cust correct(PIT) leaky(all-time) label c1 5 5 1 c2 4 10 0 c3 6 6 1 c4 3 8 0 c5 4 4 1 c6 7 14 0 c7 5 5 1 c8 6 12 0 Accuracy predicting churn at count <= 7, point-in-time feature: 50% Accuracy predicting churn at count <= 7, leaky all-time feature: 100%

100% offline accuracy, and the feature is unusable in production: at serving time "after" doesn't exist yet, so the online store cannot produce the leaky value at all — the model was trained on a feature it can never see live. This is the sharpest version of training-serving skew, and it's exactly why a feature store enforces one definition per feature, computed identically by whichever path (batch or streaming) fills the online store, rather than letting each model's training pipeline invent its own aggregation logic.

Reliability and failure modes

When the online store is slow or down, sr01 §1.17's mitigation applies directly: timeout, serve default/last-known feature values, and degrade to a simpler model rather than fail the request. Never let a feature-store outage take down every model that reads it — that turns one dependency into every team's incident.

RiskEffectMitigation
Point-in-time leakageGreat offline metric, broken/impossible in productionOne materialization job, one definition per feature, enforced point-in-time joins (adv05)
Online/offline definition driftSame feature name, two different computations — the classic silent skewShared feature registry: the definition lives once, both paths read it
Online store outageEvery dependent model degrades at oncePer-feature default values, timeout, fall back to a simpler model (sr01 §1.12)
Recap
  • Size the online store by summing every model's (QPS x features/request), same discipline as sr01 §1.3.
  • Point-in-time correctness isn't a nicety — a leaky feature can show 100% offline accuracy while being physically impossible to serve.
  • One feature, one definition, shared by the batch and streaming write paths — that's what "store" means here.
6.6 — ML Training Platforms: Scheduling Around Interruption

Requirements and architecture

A training platform's job is unglamorous: accept a training job, put it on a machine with the right accelerator, track what ran with what code/data/hyperparameters, and get out of the way. You already know job schedulers and priority queues in general; what's ML-specific is that jobs run for hours to weeks on the most expensive, least available hardware in the fleet, which makes spot/preemptible instances the default cost lever, not an edge case — and every job on spot capacity can be reclaimed with only minutes of notice. Experiment tracking (which run produced which model, with which config) is already covered in mlops ch32; distributed training mechanics (DDP/FSDP) are in adv01. The platform-design question here is narrower: how do you keep a multi-day job cheap on interruptible capacity without losing days of progress?

Deep dive: checkpoint interval is a real optimization, not a formality

Checkpoint too rarely and a preemption loses hours of compute. Checkpoint too often and the checkpoint-write overhead itself (serializing a multi-gigabyte model to durable storage) becomes the cost. Given a job's known interruption pattern, there is an interval that minimizes total wasted time.

Checkpoint interval vs. total time lost to preemption
job_length = 600 # minutes of training if nothing ever interrupted it preemption_ticks = [47, 133, 210, 340, 401, 522] # spot reclaim notices, minute marks (deterministic) checkpoint_cost = 0.6 # minutes to write a checkpoint, roughly fixed size def last_checkpoint_before(t, interval): return (t // interval) * interval print(f"{'Checkpoint every':>16} {'#checkpoints':>12} {'Overhead (min)':>15} {'Rework lost (min)':>18} {'Total waste (min)':>18}") best = None for interval in (5, 15, 30, 60, 120): n_checkpoints = job_length // interval overhead = n_checkpoints * checkpoint_cost rework = sum(t - last_checkpoint_before(t, interval) for t in preemption_ticks) waste = overhead + rework if best is None or waste < best[1]: best = (interval, waste) print(f"{interval:>15}m {n_checkpoints:>12} {overhead:>15.1f} {rework:>18} {waste:>18.1f}") print(f"Best checkpoint interval here: every {best[0]} minutes ({best[1]:.1f} minutes of total waste)")
Checkpoint every #checkpoints Overhead (min) Rework lost (min) Total waste (min) 5m 120 72.0 8 80.0 15m 40 24.0 48 72.0 30m 20 12.0 63 75.0 60m 10 6.0 213 219.0 120m 5 3.0 333 336.0 Best checkpoint interval here: every 15 minutes (72.0 minutes of total waste)

The shape is U-shaped, not monotonic: 5-minute checkpoints waste more time writing checkpoints than 15-minute ones ever lose to rework, and 60+ minute intervals lose enormous rework time to the same six preemptions. The right interval depends on your cloud's actual preemption rate (available from its spot-interruption history) and your checkpoint's real write cost — re-run this arithmetic per job family rather than picking a round number.

Scheduling and scaling notes

Priority queues for job scheduling work exactly like any other priority queue (sr01's queueing ideas in §1.7 apply directly) with one addition: a "resume" job (recovering from preemption) should generally jump the queue ahead of new jobs, since it represents sunk cost that gets more expensive the longer it waits. Mix spot and on-demand pools deliberately: time-insensitive sweeps and hyperparameter search run well on spot; a launch-blocking final training run may be worth on-demand's cost premium for its lower interruption risk.

Recap
  • Spot/preemptible capacity is the default cost lever for training, which makes checkpoint interval a real, computable optimization, not a formality.
  • Resume jobs should generally preempt new jobs in the scheduler's priority order — they're recovering sunk cost.
  • Experiment tracking and distributed-training mechanics live in mlops ch32 and adv01 respectively; this section is the scheduling layer around both.
6.7 — Model-Serving Platforms: Beyond sr01's Case Study

What sr01 §1.17 already covered, and what's new

sr01's Case Study 5 designed a single-model serving platform: dynamic batching, replica sizing from throughput math, sticky canary routing by hashing the user id, and a failure-mode table (cold start, autoscaling lag, bad model versions, feature-store slowness, noisy neighbors, input drift). That's not repeated here. Three things it didn't cover: serving many models on shared infrastructure, autoscaling on the metric that actually reflects load, and the operational difference between a canary and a shadow deployment.

Multi-model serving platform
 client ─► router ─► shared GPU pool (many small models, bin-packed together)
                   └► isolated pool (one large/critical model, its own quota)
 autoscaler watches: queue depth per pool, NOT cpu%
 rollout: shadow (compare, zero user risk) ─► canary (small % real traffic) ─► promote/rollback (mp04 §4.9)

Multi-model serving: a platform serving many teams' models has to decide, per model, shared pool (several small models bin-packed onto the same accelerators, cheaper, but one model's traffic spike steals capacity from another — the "noisy neighbor" row in sr01's own failure table) or an isolated pool (guaranteed capacity, more expensive, reserved for models where sr01's noisy-neighbor mitigation — quotas — isn't enough because the blast radius of starvation is unacceptable, e.g. checkout-path fraud scoring).

Deep dive: autoscale on queue depth, not CPU

A GPU-bound serving replica can be completely saturated — a growing backlog, climbing latency — while its CPU utilization sits flat and low, because the CPU is just shuttling batches to and from the accelerator that's doing the real work. An autoscaler watching CPU never fires. One watching queue depth per replica catches the exact moment work is arriving faster than it's being drained.

CPU-based vs. queue-depth-based autoscaling, same traffic spike
arrivals = [140, 140, 140, 140, 140, # normal 420, 420, 420, 420, 420, 420, # a 6-minute spike (3x) 140, 140, 140, 140, 140] # back to normal capacity_per_replica = 60 # requests/min one GPU replica can actually finish def run(scale_signal, threshold, start_replicas=3, max_replicas=8, cooldown=2): replicas, backlog, last_scale, peak_backlog, scale_events = start_replicas, 0, -99, 0, [] for minute, arrived in enumerate(arrivals): backlog = max(0, backlog + arrived - capacity_per_replica * replicas) peak_backlog = max(peak_backlog, backlog) signal = scale_signal(backlog, replicas) if signal > threshold and replicas < max_replicas and minute - last_scale >= cooldown: replicas += 1 last_scale = minute scale_events.append(minute) return peak_backlog, replicas, scale_events # "CPU-bound" policy: the GPU does the real work, so CPU sits at a flat, low, uninformative number cpu_peak, cpu_replicas, cpu_events = run(lambda backlog, replicas: 35, threshold=70) # cpu% never crosses 70 # Queue-depth policy: scale on backlog per replica, the thing that actually reflects load queue_peak, queue_replicas, queue_events = run(lambda backlog, replicas: backlog / replicas, threshold=20) print(f"CPU-based autoscaler : peak backlog {cpu_peak:>5} requests, ended at {cpu_replicas} replicas, scaled at minutes {cpu_events}") print(f"Queue-depth autoscaler : peak backlog {queue_peak:>5} requests, ended at {queue_replicas} replicas, scaled at minutes {queue_events}")
CPU-based autoscaler : peak backlog 1440 requests, ended at 3 replicas, scaled at minutes [] Queue-depth autoscaler : peak backlog 900 requests, ended at 7 replicas, scaled at minutes [5, 7, 9, 11]

The CPU-based policy never scales at all — its signal is flat by construction — and the backlog just keeps growing for the whole spike. The queue-depth policy starts reacting one minute after the spike begins (respecting a 2-minute cooldown between scale-ups, same pattern as mp04 §4.8's hysteresis, applied to scaling instead of alerting) and caps the damage at a lower peak. The lesson generalizes beyond GPUs: autoscale on the metric that's causally downstream of the thing you actually care about (user-facing latency), not on whatever's easiest to read off the node.

Canary vs. shadow: a genuine either/or, not two names for the same thing

mp04 §4.9 already gives you the mechanics of both and an automated promote/hold/rollback decision from agreement rate and service metrics — reused here, not repeated. The design decision this platform has to make is which one to use first, and they are not interchangeable: shadow serves the new model a copy of real traffic and discards its answers, so it costs zero user risk but never confirms real user impact. Canary actually serves a small slice of users, so it measures real impact but at real (small, bounded) risk. New model architectures or anything with a severe cost-of-error should shadow first; once shadow shows parity with the baseline, canary measures the thing shadow can't.

Recap
  • Shared pools save cost and create noisy-neighbor risk; isolated pools cost more and remove it — pick per model, not platform-wide.
  • Autoscale on queue depth for accelerator-bound workloads; a flat CPU metric is not "healthy," it's uninformative.
  • Shadow proves parity at zero risk; canary measures real impact at bounded risk — use shadow first for anything new or high-stakes, promote to canary once it's earned it.

6.8 — RAG at Production Scale: Ingestion, Freshness, Vector-DB Trade-offs

Requirements and architecture

A RAG platform's extra requirement beyond the LLM app patterns you already know is keeping the retrieval corpus current without re-embedding everything on every change, and choosing a vector store whose trade-offs match your scale and freshness needs. The LLM call itself (fine-tuning, prompting, serving) is adv02's and adv03's job; this section is the pipeline in front of it.

RAG ingestion + query paths
 source docs ─► chunker ─► embedder (workers) ─► vector DB ◄── freshness lag = batch cadence, not compute
                                                     │
 query ─► embed ─► ANN search (top-k) ─► rerank ─► prompt assembly ─► LLM (adv02/adv03) ─► answer

Deep dive: freshness is an architecture decision, not a compute problem

Teams often assume re-indexing is expensive because embedding is "an ML workload." At real throughput it usually isn't the bottleneck — the ingestion cadence is.

Embedding compute cost vs. batch-cadence staleness
corpus_size = 5_000_000 throughput_per_worker = 800 # docs/sec a single embedding worker can process workers = 10 daily_change_rate = 50_000 # docs added or edited per day total_throughput = throughput_per_worker * workers full_reindex_hours = corpus_size / total_throughput / 3600 delta_minutes = daily_change_rate / total_throughput / 60 print(f"Total embedding throughput: {total_throughput:,} docs/sec across {workers} workers") print(f"Full corpus re-index: {full_reindex_hours:.2f} hours") print(f"Daily delta (new/edited docs) takes: {delta_minutes:.1f} minutes of embedding compute") print(f"Nightly-batch ingestion worst-case staleness: up to 24.0 hours for a doc edited right after the batch") print(f"Streaming/micro-batch ingestion (every 5 min) worst-case staleness: up to {5 + delta_minutes:.1f} minutes")
Total embedding throughput: 8,000 docs/sec across 10 workers Full corpus re-index: 0.17 hours Daily delta (new/edited docs) takes: 0.1 minutes of embedding compute Nightly-batch ingestion worst-case staleness: up to 24.0 hours for a doc edited right after the batch Streaming/micro-batch ingestion (every 5 min) worst-case staleness: up to 5.1 minutes

The actual embedding work for a day's changes is six seconds. The 24-hour staleness in the nightly-batch design comes entirely from when the job runs, not from how long it takes — so if freshness matters (a support-bot RAG system answering from docs that change hourly), the fix is a scheduling change (micro-batch every few minutes) that costs almost nothing extra in compute, not a bigger cluster.

Vector database trade-offs, and monitoring reuse

ChoiceGood fit whenCost
Managed vector DB (dedicated service)Fast to ship, need hybrid lexical+semantic search out of the boxPer-query and storage pricing, less control over index internals

Whichever you choose, the freshness SLO from this section and the retrieval-quality metrics (recall@k, faithfulness, hallucination checks) from adv04 are what you monitor — reuse mp04's four-layer discipline (§4.1) rather than inventing a separate "RAG health" dashboard: retrieval latency and error rate are service health, corpus staleness is a data-quality signal, and answer faithfulness is the model-performance layer, just measured differently than a classifier's accuracy.

Recap
  • Freshness is usually a scheduling decision, not a compute one — check the arithmetic before assuming you need more embedding capacity.
  • Pick a vector store by scale and operational appetite, not by defaulting to whichever is trending.
  • Monitor RAG with the same four layers as any other model — retrieval metrics and faithfulness are the model-performance layer's ML-specific content.
6.9 — High-Scale LLM Inference: Load Balancing Across GPU Replicas

Requirements and what's reused

adv03 (LLM Inference & Serving at Scale) covers the mechanics this platform runs on: continuous/dynamic batching, the KV cache and its memory footprint, quantization for inference, and what engines like vLLM do differently. All reused here by name, not repeated. What's platform-specific at high scale is what happens across replicas: routing requests to them, and surviving GPU-specific failure modes sr01 §1.9's generic load balancing didn't anticipate.

LLM inference platform, request routing
 client ─► global LB ─► region ─► request router (least-outstanding-work, not round robin)
                                      ├─ replica A (long generation in flight)
                                      ├─ replica B (idle) ◄── new short request lands HERE
                                      └─ replica C
 KV-cache aware: prefer a replica that already holds this prompt's cached prefix, when possible

Deep dive: why round robin fails harder here than in sr01 §1.9

sr01 §1.9 taught round robin and least-loaded/power-of-two-choices as general load-balancing strategies, for workloads where request service time is roughly uniform. LLM generation service time is not uniform — a one-line chat reply might take 300 ms, a long generation 4+ seconds — and round robin has no idea which replica just got assigned the long one. It keeps sending traffic there anyway, creating head-of-line blocking behind whichever replica drew the unlucky long request.

Round robin vs. least-outstanding-work under highly variable generation lengths
import numpy as np n_replicas = 4 n_requests = 30 arrival_gap = 150 # ms between arrivals # service time per request, in ms: mostly short replies, a few long generations (high variance) pattern = [300, 280, 320, 4200, 300, 260, 310, 4600, 290, 300, 330, 4100, 280, 300, 310] service_times = [pattern[i % len(pattern)] for i in range(n_requests)] arrivals = [i * arrival_gap for i in range(n_requests)] def round_robin(free_at, arrival, counter): r = counter[0] % n_replicas counter[0] += 1 return r def least_loaded(free_at, arrival, counter): return min(range(n_replicas), key=lambda r: free_at[r]) def simulate(assign_fn): free_at = [0] * n_replicas counter = [0] total_time = [] for arrival, svc in zip(arrivals, service_times): r = assign_fn(free_at, arrival, counter) start = max(free_at[r], arrival) finish = start + svc free_at[r] = finish total_time.append(finish - arrival) return total_time rr = simulate(round_robin) ll = simulate(least_loaded) rr_p50, rr_p95 = np.percentile(rr, [50, 95]) ll_p50, ll_p95 = np.percentile(ll, [50, 95]) print(f"Round robin : p50 {rr_p50:>6.0f} ms, p95 {rr_p95:>7.0f} ms, worst {max(rr):>7.0f} ms") print(f"Least loaded : p50 {ll_p50:>6.0f} ms, p95 {ll_p95:>7.0f} ms, worst {max(ll):>7.0f} ms") print(f"p95 improvement from least-loaded routing: {(1 - ll_p95/rr_p95):.0%}")
Round robin : p50 310 ms, p95 11565 ms, worst 11700 ms Least loaded : p50 1585 ms, p95 5741 ms, worst 6820 ms p95 improvement from least-loaded routing: 50%

Round robin's median is actually a little better (most requests land on an otherwise-idle replica by luck), but its p95 and worst case are catastrophic — one long generation poisons every request queued behind it on that replica. Least-loaded routing trades a bit of median latency (it deliberately balances load, which sometimes means a short request waits slightly behind other work) for roughly half the p95 and a much safer worst case. For a latency SLA measured at p95 or p99 (the honest way to promise anything, per sr01 §1.11), that trade is almost always worth taking. A further, adv03-specific refinement is KV-cache-aware routing: when a request continues a conversation, routing it back to the replica that already holds that prompt's cached prefix avoids recomputing it, which matters more as context windows grow.

Failure modes specific to GPU replicas

RiskEffectMitigation
KV-cache exhaustionToo many long/concurrent sequences exceed replica memory, OOM or forced evictionTrack KV-cache usage per replica (adv03) as its own scaling and admission-control signal
Slow replica warmupA multi-GB model takes minutes to load; sr01 §1.17's cold-start risk, worse the bigger the modelWarm spares; never scale a latency-critical pool to zero
Spot preemption mid-generationAn in-flight generation is lost, user sees a failure or a truncated answerIdempotent client retry with the same request id; route retries to a fresh replica, not the reclaimed one

Recap
  • adv03 supplies the per-replica mechanics (batching, KV cache, quantization); this section is what happens across replicas.
  • Highly variable LLM service times make least-loaded/least-outstanding routing far more valuable than in sr01's general case — round robin's tail is the failure mode to design against.
  • KV-cache usage and replica warmup are GPU-specific failure signals a generic load balancer doesn't know to watch.
6.10 — ML Monitoring Platforms: One Pane for Many Models

What mp04 already covers, and the platform question it leaves open

mp04 gives you the statistics for monitoring one model well: the four-layer framework (§4.1), percentiles and burn rate (§4.2–4.3), PSI/KS drift tests (§4.5–4.6), matured-cohort accuracy (§4.7), hysteresis alerting (§4.8), and canary/shadow rollout decisions (§4.9). None of that is repeated here. The platform question is what happens when you have not one model but hundreds, owned by different teams, at a combined prediction volume too large to log in full: how do you watch all of it in one place without either drowning every team in noise or bankrupting the logging budget?

Monitoring platform, many models to one pane
 1000s of model instances ─► sampled logs + metrics (reservoir, bounded per-model cost)
                                     │
                                     ▼
                           central metrics/drift store (mp04's stats, computed per model)
                                     │
                       alert routing table (model owner, not one generic on-call)
                         ├─ search-ml   ├─ risk-ml   ├─ ads-ml   ├─ platform-ml

Deep dive 1: you cannot log everything, so sample deliberately

A single busy model can produce tens of millions of predictions a day; a platform serving hundreds of models cannot afford to store every feature vector for every one of them, and doesn't need to — mp04's drift tests and slice analysis (adv04) work fine on a representative sample. Reservoir sampling keeps a fixed-size, uniformly representative sample from a stream of unknown/unbounded length, which is exactly the "how much can I afford to log" problem at platform scale.

Reservoir sampling: a fixed logging budget regardless of traffic
import random random.seed(7) def reservoir_sample(stream, k): sample = [] for i, item in enumerate(stream): if i < k: sample.append(item) else: j = random.randint(0, i) # Algorithm R if j < k: sample[j] = item return sample n_events = 200_000 # one day's predictions for one busy model, scaled down for this demo k = 500 # fixed logging budget per model, regardless of traffic stream = range(n_events) sample = reservoir_sample(stream, k) print(f"Stream size: {n_events:,} predictions, reservoir cap: {k}") print(f"Sample size kept: {len(sample)}") print(f"Storage if you logged everything: {n_events:,} rows/model/day") print(f"Storage with the reservoir: {k:,} rows/model/day, a {n_events / k:.0f}x reduction") print(f"Sample still spans the full stream (min id {min(sample)}, max id {max(sample)}) -- not just the tail")
Stream size: 200,000 predictions, reservoir cap: 500 Sample size kept: 500 Storage if you logged everything: 200,000 rows/model/day Storage with the reservoir: 500 rows/model/day, a 400x reduction Sample still spans the full stream (min id 218, max id 199491) -- not just the tail

A fixed per-model cap means the platform's total storage cost scales with the number of models, not with their combined traffic — the difference between a monitoring budget that's predictable and one that grows without bound as any single model gets popular. The same cap-and-sample idea applies to the metrics themselves: compute mp04's drift scores on the reservoir sample, not the full stream, and they stay statistically valid at a fraction of the compute.

Deep dive 2: route the alert to the model's owner, not one shared pager

A platform-wide dashboard is only a "pane of glass" if the alerts it fires reach the right people. A drift alert on the fraud team's model and one on the recommendation team's model have nothing to do with each other and should never page the same generic on-call — that's how alert fatigue (mp04 §4.8) turns into organizational alert fatigue.

Routing alerts from many models to their owning teams
owners = {"ranker": "search-ml", "fraud-v3": "risk-ml", "ads-ctr": "ads-ml", "chat-llm": "platform-ml"} # (model, layer, severity) as raised by the four monitoring layers from mp04 4.1 alerts = [ ("ranker", "data_quality", "ticket"), ("fraud-v3", "service_health","page"), ("ads-ctr", "data_drift", "ticket"), ("chat-llm", "service_health","page"), ("fraud-v3", "data_drift", "page"), ("ranker", "model_perf", "ticket"), ("ads-ctr", "data_drift", "ticket"), ] def route(model, layer, severity): owner = owners.get(model, "platform-ml") # unknown model falls back to the platform team channel = "infra-oncall" if layer == "service_health" and severity == "page" else owner return channel routed = [route(m, l, s) for m, l, s in alerts] for (model, layer, sev), dest in zip(alerts, routed): print(f"{model:<9} {layer:<14} {sev:<7} -> {dest}") from collections import Counter counts = Counter(routed) print("Alerts per destination:", dict(sorted(counts.items())))
ranker data_quality ticket -> search-ml fraud-v3 service_health page -> infra-oncall ads-ctr data_drift ticket -> ads-ml chat-llm service_health page -> infra-oncall fraud-v3 data_drift page -> risk-ml ranker model_perf ticket -> search-ml ads-ctr data_drift ticket -> ads-ml Alerts per destination: {'ads-ml': 2, 'infra-oncall': 2, 'risk-ml': 1, 'search-ml': 2}

Notice the one deliberate exception: service_health pages go to infra on-call regardless of model, because an unhealthy service is an infra problem first — everything else routes to the model's own team, since only they know whether a drift score means "retrain" or "expected, ignore." Building this table (and keeping it current as models are onboarded) is most of what separates a real monitoring platform from a dashboard nobody trusts enough to act on.

Reliability and cost

Monitoring must never sit in the serving request path — collect metrics and samples asynchronously (fire-and-forget or a local buffer flushed off the critical path), so a monitoring outage degrades observability, never predictions. Cardinality is the platform's real cost driver: every (model x version x feature) combination is a distinct time series, and that count multiplies fast across hundreds of models with dozens of features and frequent version churn — track cardinality itself as a metric, and prune retired model versions' series on a schedule.

Recap
  • mp04 supplies the per-model statistics; this section is what it takes to run those statistics for hundreds of models without the cost or the alert-noise exploding.
  • Reservoir sampling bounds logging cost per model regardless of traffic, and keeps the sample statistically representative.
  • Route every alert to its model's owning team by default; only service-health pages should ever go to a shared on-call.

6.11 — Choosing Among Patterns

These patterns compose, they don't compete

A real product rarely needs exactly one of these nine. A shopping app's recommendation system (6.2) reads from the same feature store (6.5) that its fraud model (6.4) reads from, both served by the same multi-model platform (6.7), all watched by one monitoring platform (6.10). A support chatbot's RAG pipeline (6.8) runs its generation through the same high-scale LLM inference platform (6.9) that a separate internal tool also calls. The design skill is recognizing which of these boxes you already need shared infrastructure for, versus which one is genuinely a new system.

If your hardest constraint is......you're mostly designing
Latency budget shared with payment/checkoutFraud detection (6.4) — the feedback-loop delay is the real design driver
Serving many teams' models on one accelerator budgetModel serving (6.7) — isolation vs. sharing, autoscaling signal
Same feature value must match in training and at inferenceFeature store (6.5) — point-in-time correctness is non-negotiable
Response time dominated by a variable-length generationHigh-scale LLM inference (6.9) — routing strategy matters more than raw capacity
Watching correctness (not just uptime) across many models cheaplyML monitoring (6.10) — sampling and alert routing, not more dashboards

The review checklist, extended for one ML-specific question

Run sr01 §1.18's review checklist (numbers, single points of failure, state, consistency, retries, overload, operations, cost and team) on any of these designs unchanged — it still applies in full. Add exactly one ML-specific question, because it's the one a purely-infra reviewer will forget to ask: "how would we know if this were silently wrong, and how long would that take?" Every pattern in this chapter answers that question differently — a fraud model's answer takes weeks (6.4), a feature store's answer might be "never, if the leak also breaks the offline metric the same way" (6.5) — and a design doc that can't answer it at all is not finished.

Recap
  • These nine patterns are shared infrastructure that compose in a real product, not nine independent systems to pick one of.
  • Identify your hardest constraint first; it usually points at which pattern you're actually designing.
  • Reuse sr01 §1.18's review checklist in full, and add one question: how would you know if this were silently wrong?

Why: Chargebacks ARE the ground-truth label, and they're slow — the classic fraud feedback-loop delay from section 6.4. Waiting for them means finding out about a new pattern two months late. A fast, incomplete proxy (analyst review, disputes) gives an earlier, if partial, signal.
Question 2 of 5
A churn model shows 100% accuracy offline using a "total purchases so far" feature, computed by a nightly job over all available history. In production it performs far worse. What's the most likely cause?
Why: Section 6.5's demo shows exactly this: an all-time aggregate that includes post-label data hits 100% offline accuracy and is physically impossible to serve online, since the future data doesn't exist yet at inference time. The fix is enforcing point-in-time joins, not more replicas or a simpler model.
Question 3 of 5
A GPU-bound model-serving replica's CPU utilization sits flat at 35% through a 3x traffic spike, while its request backlog grows for six straight minutes. What does this tell you about the autoscaler?
Why: Section 6.7's simulation shows a CPU-based policy never scaling at all while backlog climbs to 1,440 requests, because the CPU is just shuttling batches to the accelerator doing the real work. Queue depth is the causally correct signal for GPU-bound serving.
Question 4 of 5
An LLM-serving platform routes requests round robin across 4 replicas. Generation lengths vary hugely (300 ms to 4.6 seconds). Predict the effect compared with least-outstanding-work routing.
Why: Section 6.9's simulation gets exactly this result: round robin's p50 is better (310 ms) but its p95/worst are catastrophic (11,565 / 11,700 ms); least-loaded trades some median latency for roughly half the p95. Highly variable service time is what makes this matter far more than in sr01's general load-balancing case.
Question 5 of 5
A platform monitors 400 models. Every drift, data-quality and performance alert currently pages the same shared on-call rotation. What's the right fix, per section 6.10?
Why: A shared pager for hundreds of unrelated models is how mp04's per-model alert fatigue becomes organization-wide alert fatigue. Section 6.10 routes each alert to the model's owning team by a lookup table, keeping the shared on-call for service-health pages only. Logging everything is also the wrong fix — it ignores the reservoir-sampling cost lesson from the same section.
