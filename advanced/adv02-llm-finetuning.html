2.1 — SFT: What Fine-Tuning Actually Changes

Chapter 29.5 taught prompting — zero-shot, few-shot, chain-of-thought — and Chapter 28.2 taught reusing a frozen pretrained model as-is via pipeline(). Both leave the model's weights untouched: you're steering behavior entirely through the text you send at inference time. Supervised Fine-Tuning (SFT) is different in kind, not degree: you run real gradient steps against the model's own weights, using your own dataset of (prompt, response) pairs, so the desired behavior gets baked into the parameters. Ask the fine-tuned model something with a bare prompt and no instructions, and it still responds the way you trained it to — because the update lives in the weights, not in whatever text happened to precede the request.

This has a real cost: labeled data to curate, GPU time to spend, and careful evaluation to avoid overfitting a small dataset (exactly the warning ch28.5 gave). So the decision rule practicing engineers actually use is: reach for prompting/RAG first — it's free to iterate on, instantly reversible, and often gets you 90% of the way there. Reach for SFT when (a) you need a fixed output format, tone, or vocabulary the model won't reliably hold no matter how the prompt is engineered, (b) you have enough real labeled pairs for the task, or (c) the behavior needs to be cheap per-request — no re-sending a long system prompt or a stack of few-shot examples on every call, which is real latency and real token cost at scale. SFT still starts from a pretrained checkpoint (the transfer-learning idea from ch28.1) — you are never training a language model from nothing.

Two failure modes are specific to SFT and worth naming up front. Overfitting a small SFT set looks like training loss dropping nicely while held-out perplexity gets worse — the model is memorizing your handful of examples' exact phrasing rather than learning the underlying task; more data, fewer epochs, a lower learning rate, and dropout on the adapter (Section 2.5) all push back against it. Catastrophic forgetting is the model quietly losing general capability it had before fine-tuning because the SFT set only reinforces one narrow behavior — a model fine-tuned hard on customer-support replies can lose its ability to write working code, even though nothing in the recipe was "about" code. Section 2.8 covers the concrete check: eval on a small general-capability held-out set, not only your task's own metric. Also distinguish two shapes of SFT in the wild: single-task fine-tuning (this chapter's running example — one narrow behavior, a small focused dataset) versus instruction-tuning (a large, diverse mixture of many tasks phrased as instructions, the recipe behind general-purpose chat models) — the mechanics (datasets, LoRA, evaluation) are identical; only the data's scale and diversity differ.

2.2 — Real Fine-Tuning Data: the datasets Library

HuggingFace's datasets library is the standard way to load, transform, and feed real fine-tuning data — it's Arrow-backed (columnar, memory-mapped, so a dataset far bigger than RAM still works), and it plugs directly into Trainer or a manual training loop. For a small SFT dataset you already have in Python, skip disk formats entirely and build it in memory:

Colab / real Python — building and tokenizing an SFT dataset
from datasets import Dataset from transformers import AutoTokenizer tok = AutoTokenizer.from_pretrained("gpt2") tok.pad_token = tok.eos_token # GPT-2 has no pad token by default; reuse eos # SFT data: (prompt, response) pairs — neutral, task-shaped examples data = { "prompt": [ "Summarize: Asha finished the report early.", "Classify sentiment: I love this product", "Classify sentiment: This is terrible", ], "response": [ "Asha completed the report ahead of schedule.", "positive", "negative", ], } ds = Dataset.from_dict(data) def tokenize_fn(example): text = example["prompt"] + " -> " + example["response"] + tok.eos_token out = tok(text, truncation=True, max_length=64, padding="max_length") out["labels"] = out["input_ids"].copy() # causal LM: labels == input_ids return out tokenized = ds.map(tokenize_fn, remove_columns=ds.column_names) print(tokenized[0].keys()) # dict_keys(['input_ids','attention_mask','labels'])
✅
Verified real output — this exact code was run in a CPU-only venv: dict_keys(['input_ids', 'attention_mask', 'labels']). .map() applies tokenize_fn row-by-row (or in batches with batched=True for speed on larger datasets) and remove_columns drops the original text columns once you only need token IDs.

The toy dataset above is small enough to build by hand in a Python dict — a real instruction-tuning run instead pulls a genuine labeled dataset straight off the Hub with load_dataset("dataset-name") (real-world examples include broad instruction-following sets like Alpaca-style or Dolly-style collections, or a narrower, task-specific set you curated yourself for single-task fine-tuning). The mechanics don't change between the two: load_dataset returns the same Dataset/DatasetDict object Dataset.from_dict does, so the exact same tokenize_fn and .map() call from above applies whether the underlying data is three toy rows or three hundred thousand real ones — only the dataset's SIZE changes whether batched mapping and streaming (mentioned below) are worth the extra complexity.

For collation (batching variable-length examples together), DataCollatorForLanguageModeling(tok, mlm=False) handles causal-LM padding and label-masking automatically instead of the fixed padding="max_length" above — fixed-length padding wastes compute on short examples but keeps every batch the same shape (simpler for a first pass); dynamic padding is the standard choice once throughput matters. Always hold out a validation split (ds.train_test_split(test_size=0.1)) before training — the k-fold/train-val-test mechanics themselves are Chapter 19/33's job, not repeated here.

One detail the simplified tokenize_fn above glosses over: real SFT recipes usually mask the PROMPT portion of labels with -100 (PyTorch's cross-entropy "ignore this position" value), so the loss only scores the model's ability to predict the RESPONSE tokens, not the prompt tokens it was simply given. Without masking, the model spends some of its limited gradient signal "learning" to predict text it will always be handed anyway, which is wasted capacity on a small SFT set. In practice: tokenize the prompt alone first to get its length, tokenize the full prompt + response text, then set labels[:prompt_len] = -100 before training. For multi-turn chat-style data (system/user/assistant turns), the same masking idea applies per-turn via the tokenizer's chat template — datasets.map(), batched with batched=True for real throughput, or a streaming IterableDataset for corpora too large to fit in memory, are the two knobs to reach for as data size grows; the toy dataset in this chapter is small enough that neither is needed yet.

2.3 — Why Full Fine-Tuning Is Usually Wasteful

Training with Adam in mixed precision needs more than just the model's weights in memory. The commonly-used rule of thumb is about 16 bytes per trainable parameter: fp16 weights (2 bytes) + fp16 gradients (2 bytes) + an fp32 master copy of the weights (4 bytes) + Adam's fp32 first moment (4 bytes) + Adam's fp32 second moment (4 bytes) = 16 bytes/param, before a single activation is stored. Full fine-tuning means every one of the model's parameters is trainable, so that 16x multiplier applies to the WHOLE model:

Model sizeTotal paramsfp16 weights onlyFull fine-tune (~16 B/param)
7B7,000,000,00014 GB~112 GB
13B13,000,000,00026 GB~208 GB

112–208 GB (before activations) doesn't fit on any single consumer or even most datacenter GPUs — that's the entire reason PEFT (Parameter-Efficient Fine-Tuning) exists as a family of methods: freeze the base model, add a small number of new trainable parameters, and get most of the quality gain of full fine-tuning at a tiny fraction of the memory. The 16-bytes/param figure isn't a worst case either — some production setups also keep an EMA (exponential moving average) copy of the weights for a smoother final checkpoint, pushing the real number higher still. LoRA is the technique that won this family; a few earlier relatives are worth knowing the names of even without a deep dive: adapters insert small trainable bottleneck layers between existing frozen layers (extra depth, so extra inference latency unless removed); prefix-tuning prepends trainable "virtual tokens" to the input at every layer instead of touching any weight; BitFit trains only the bias terms. LoRA won out because its adapter can be mathematically merged back into the original weight matrices after training — meaning, unlike adapters or prefix-tuning, a LoRA-tuned model has exactly zero extra inference latency once merged (Section 2.5).

2.4 — LoRA: Low-Rank Adapters

LoRA's insight: instead of learning a full update ΔW to a weight matrix W (shape d_out × d_in), freeze W entirely and learn ΔW as the product of two small matrices, ΔW = B·A, where B is d_out × r and A is r × d_in, with rank r chosen tiny (commonly 4–64) relative to d_in/d_out. The forward pass becomes h = Wx + (B·A)x; B is initialized to all zeros so training starts as a no-op identical to the frozen model, and A is initialized with small random values.

LoRA rank decomposition — frozen weight + trainable low-rank update
 Frozen pretrained weight               Trainable LoRA adapter
 ┌─────────────────────┐                ┌───┐      ┌──────────────────┐
 │                     │                │ B │      │        A          │
 │   W   (d_out x d_in) │       +        │(d_out│  x   │   (r x d_in)     │
 │      FROZEN          │                │ x r) │      │   r << d_in,d_out │
 │                     │                └───┘      └──────────────────┘
 └─────────────────────┘                zero-init         small-random-init

              h = W x + (B A) x     ◄── only B and A get gradients
              at inference: merge into W' = W + B A  (zero extra latency)

The parameter savings are the whole point — for a d_in = d_out = 4096 projection (a realistic attention-projection shape in a 7B-class model) with r = 8: full_params = 4096×4096 = 16,777,216 vs. lora_params = 8×4096 + 8×4096 = 65,536 — about 256x fewer trainable parameters for that layer. The numpy demo below shows the mechanism is real, not hand-waving: when the actual needed update genuinely is low-rank, a rank-r LoRA reconstructs it exactly through gradient descent alone.

Reference numpy — LoRA reconstructing a low-rank update via gradient descent
import numpy as np np.random.seed(0) d_in, d_out, r = 8, 8, 2 # the "true" weight update a fine-tune would need to learn (constructed rank-2) B_true = np.random.randn(d_out, r) * 0.5 A_true = np.random.randn(r, d_in) * 0.5 delta_W_true = B_true @ A_true # LoRA parameterization, trained from scratch with plain gradient descent B = np.zeros((d_out, r)) # zero-init, matches real LoRA A = np.random.randn(r, d_in) / np.sqrt(d_in) # small-random-init lr = 0.5 for step in range(2000): delta_W = B @ A diff = delta_W - delta_W_true grad_B = (2/diff.size) * diff @ A.T grad_A = (2/diff.size) * B.T @ diff B -= lr*grad_B; A -= lr*grad_A print("reconstruction error:", np.mean((B@A - delta_W_true)**2)) full_params = d_in*d_out lora_params = r*d_in + r*d_out print(f"full={full_params}, lora={lora_params}, ratio={lora_params/full_params:.3f}")
reconstruction error: 1.01e-30 full=64, lora=32, ratio=0.500

Real fine-tuning updates aren't exactly low-rank — but the LoRA paper's empirical finding (and the reason it works so well in practice) is that they're well-approximated by a low-rank update, so a small r captures most of the useful signal at a fraction of the parameters.

Two practical choices come up on every real LoRA setup. Where to apply it: the common default is attention projections only (query/value, or query/key/value/output — see 2.5's target_modules), which already captures most of the quality gain at the lowest parameter cost; also targeting the feed-forward/MLP projections adds more trainable parameters and can close a further quality gap on harder tasks, at a proportionally higher (but still tiny relative to full fine-tuning) memory cost. How to pick the rank r: start small (8–16), train, and evaluate on a held-out set — only raise r if the model is clearly underfitting the task (training loss won't drop further even with more steps); Exercise 4 works through a real table showing this exact diminishing-returns pattern, where quadrupling r barely moves perplexity once the right modules are already covered. Going needlessly high defeats the entire point of using LoRA in the first place — the parameter-efficiency IS the feature, not a side effect.

2.5 — Configuring LoRA With peft

HuggingFace's peft library wraps this into LoraConfig + get_peft_model(). The field that actually trips people up is target_modules: it must match the REAL module names inside the specific architecture you're wrapping — BERT-family models expose separate query/key/value Linear layers, but GPT-2 fuses all three into a single Conv1D layer named c_attn, and Llama-family models use q_proj/k_proj/v_proj/o_proj. Always check model.named_modules() first rather than copying a target list from a tutorial for a different architecture — it's a two-line, always-correct way to answer "what is this specific model's attention projection actually called":

Colab / real Python — discovering the real target_modules names
names = set() for n, m in model.named_modules(): if m.__class__.__name__ in ("Linear","Conv1D"): names.add(n.split(".")[-1]) print(names)
{'c_fc', 'c_proj', 'c_attn', 'lm_head'}

On this GPT-2-shaped model, that confirms c_attn is the (only) fused attention projection — c_fc/c_proj belong to the feed-forward block (Section 2.4's "attention-only vs. also MLP" trade-off), and lm_head is the output projection, not usually LoRA-adapted.

Colab / real Python — LoraConfig on a GPT-2-style model
from peft import LoraConfig, get_peft_model, TaskType lora_cfg = LoraConfig( r=8, lora_alpha=16, lora_dropout=0.05, target_modules=["c_attn"], # GPT-2's fused QKV projection task_type=TaskType.CAUSAL_LM, ) peft_model = get_peft_model(model, lora_cfg) peft_model.print_trainable_parameters()
trainable params: 8,192 || all params: 6,846,080 || trainable%: 0.1197

lora_alpha scales the adapter's contribution (ΔW is applied as (alpha/r)·B·A) — a common convention is alpha = 2×r. lora_dropout regularizes the tiny adapter against overfitting a small SFT set. Once training is done, model.merge_and_unload() folds B·A back into W, so a served, merged model has zero extra inference latency versus the original — this connects directly to Adv 3's serving content.

A few more LoraConfig fields worth knowing rather than leaving at their defaults: bias controls whether bias terms are also trained ("none" is the usual choice — biases are a tiny fraction of parameters, not worth the extra bookkeeping); modules_to_save lists any modules that should be fully trained (not LoRA-adapted) alongside the frozen base — the classic case is a freshly-added classification head, which has no pretrained weights to preserve and needs real gradients, not a low-rank update on top of random init. And note the deliberate choice NOT to always merge: a single frozen base model can host many different LoRA adapters simultaneously (one per customer, one per task) if you keep them unmerged and swap which adapter is active per request — a multi-tenant serving pattern Adv 3 picks up.

2.6 — QLoRA: Quantize the Frozen Base, Keep the Adapters Full Precision

QLoRA adds one more idea on top of LoRA: quantize the FROZEN base model's weights down to 4 bits (HuggingFace/bitsandbytes' NF4 format — a data type tuned for the roughly-normal distribution of trained neural network weights, plus "double quantization" that also quantizes the per-block scale constants for a further small savings). Only the frozen base gets quantized; the LoRA adapters you actually train still compute in bf16/fp16 full precision, so the parameters that are learning don't inherit the quantization's rounding error — bitsandbytes implements the CUDA kernels that dequantize each 4-bit block on the fly during the matmul, transparently to the rest of the model.

Reference-only — needs a real CUDA GPU, shown as correct syntax
from transformers import BitsAndBytesConfig, AutoModelForCausalLM bnb_cfg = BitsAndBytesConfig( load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16, # LoRA adapters compute in bf16 ) base = AutoModelForCausalLM.from_pretrained(model_id, quantization_config=bnb_cfg, device_map="auto") peft_model = get_peft_model(base, lora_cfg) # same LoraConfig as 2.5
⚠️
Needs a real GPU — bitsandbytes' 4-bit kernels require CUDA; this cannot be executed or verified on this CPU-only box. The syntax above is correct and matches bitsandbytes 0.4x/transformers 5.x usage.

"Double quantization" is worth unpacking briefly since it's easy to gloss over: NF4 quantizes each small block of weights (e.g. 64 values) to 4-bit codes plus one fp32 scale constant per block — but storing a full fp32 scale per 64 values is itself non-trivial overhead at model scale, so QLoRA quantizes THOSE scale constants too (to 8-bit), shaving roughly another 0.4 bits per parameter off the total. It's a small optimization on its own, but it's representative of why QLoRA needed real engineering, not just "cast to int4" — naive 4-bit quantization of a full model without this care measurably hurts quality; NF4 plus double quantization is tuned specifically to keep a quantized frozen base close to its fp16 quality. In practice, this combination is exactly what lets a single 24 GB consumer GPU fine-tune models in the 13B–33B range that would otherwise need multiple datacenter GPUs.

Be honest with yourself about the trade-off, though: quantizing the frozen base to 4-bit is not entirely free — the original QLoRA paper's own benchmarks show it recovering the large majority of full-precision fine-tuning quality, not literally all of it, and the residual gap varies by task and model. The right default stance is the same one this whole chapter has been building toward: try the cheaper option (LoRA on an fp16 base) first if it fits your GPU at all, and reach for QLoRA specifically when the fp16 base genuinely doesn't fit — not as a default "smaller is always fine" assumption. Section 2.8's before/after evaluation habit is exactly how you'd catch a real quality regression if one shows up.

2.7 — GPU Memory Budgeting, Worked

Putting 2.3–2.6 together into one explicit budget (weights + optimizer states only — activation memory is separate, scales with batch size × sequence length × hidden size × layer count, and is exactly what gradient checkpointing, covered in Adv 1, is for):

Method7B model13B modelWhy
Full fine-tune (fp16+fp32 Adam)~112 GB~208 GB16 B/param × ALL params
LoRA (fp16 frozen base + r=8-16 adapters)~14.2 GB~26.2 GB2 B/param base (frozen, no optimizer) + ~16 B/param on ~0.1-0.5% of params
QLoRA (4-bit NF4 frozen base + same adapters)~4.1 GB~7.2 GB~0.5 B/param base (quantized) + same tiny adapter overhead
Peak weights+optimizer memory by method (7B model, 1 char ≈ 2 GB)
 Full fine-tune   ████████████████████████████████████████████████████  ~112 GB
 LoRA             ███████                                                 ~14.2 GB
 QLoRA            ██                                                     ~4.1 GB

This is exactly why LoRA makes a single-GPU (16-24 GB) fine-tune of a 7B model realistic, and why QLoRA is the technique the original paper used to fine-tune models as large as 65B on a single 48 GB GPU. Numbers are back-of-envelope (a "16 bytes/param" and "~0.5 bytes/param for 4-bit" rule of thumb) — real deployments still need headroom for activations, the tokenizer/embedding tables, and framework overhead.

Activation memory is the piece deliberately left out of the table above, and it deserves its own back-of-envelope: roughly, activation memory scales with batch_size × sequence_length × hidden_size × num_layers (times a small constant for the intermediate tensors kept per layer for backprop). Doubling either your batch size or your sequence length roughly doubles activation memory — which is why long-context fine-tuning is disproportionately expensive even with LoRA/QLoRA already shrinking the weights+optimizer side of the budget. Gradient checkpointing (Adv 1) trades this off directly: instead of storing every layer's activations for the backward pass, it recomputes them on the fly, cutting activation memory substantially at the cost of roughly one extra forward pass per training step — a trade worth making whenever activation memory, not weights, is the binding constraint.

Mapped onto real hardware SKUs (DevOps-experienced readers will already know these from provisioning, not re-explained here): a 16 GB card (e.g. a T4) is enough for LoRA on a 7B model but not full fine-tuning of anything past a small model; a 24 GB consumer or datacenter card (e.g. an RTX 4090 or an A10) comfortably fits QLoRA on 13B–33B models, or LoRA on 7B with real headroom for activations; an 80 GB card (an A100/H100) is where full fine-tuning of a 7B model finally becomes possible on a single GPU, and where LoRA on models in the tens of billions of parameters has real room to spare. None of this changes the provisioning mechanics you already know — it changes which model sizes are even worth trying to fit before reaching for multi-GPU sharding.

2.8 — Evaluating a Fine-Tuned Model

Perplexity is the standard first metric for a causal LM: perplexity = exp(mean cross-entropy loss) over held-out examples — lower is better, and it directly reflects how "surprised" the model is by the real next tokens. Always measure it on a held-out split never used for training or checkpoint selection (the same discipline as any other held-out eval, ch19/ch33 — not repeated here).

Colab / real Python — before/after perplexity on the tiny SFT run from 2.5
import math, torch def eval_loss(m, tokenized_ds): m.eval() total, n = 0.0, 0 with torch.no_grad(): for ex in tokenized_ds: ids = torch.tensor([ex["input_ids"]]); labels = torch.tensor([ex["labels"]]) out = m(input_ids=ids, labels=labels) total += out.loss.item(); n += 1 return total/n before = eval_loss(peft_model, tokenized) print(f"before: loss={before:.3f} ppl={math.exp(before):.1f}") # ... train (2.5's loop, or Trainer) ... after = eval_loss(peft_model, tokenized) print(f"after: loss={after:.3f} ppl={math.exp(after):.1f}")
before: loss=10.140 ppl=25337.4 after: loss=8.922 ppl=7496.0

That's a real captured run: a tiny (6.8M-parameter, randomly-initialized) 2-layer GPT-2-shaped model, LoRA-tuned for 30 epochs on 8 toy examples, on CPU, in under 30 seconds — perplexity drops by more than 3x. For task-shaped outputs (like the sentiment examples above), also track a task metric directly — exact-match / accuracy on held-out prompts — rather than perplexity alone; the full rigor of calibration, slicing, and LLM-as-judge evaluation is Adv 4's job (referenced, not repeated here).

Two more evaluation habits catch problems perplexity alone misses. First, actively check for the catastrophic forgetting named in Section 2.1: run the SAME before/after comparison on a small held-out set of GENERAL prompts unrelated to the fine-tuning task — if general perplexity got noticeably worse while task perplexity improved, the fine-tune is trading away capability you didn't intend to touch, and the fix is usually less aggressive training (fewer epochs, lower learning rate, or a lower LoRA rank) rather than more data on the narrow task. Second, don't trust a single run: the same config trained with a different random seed can land at a meaningfully different final metric on a small dataset — reporting one number from one run risks mistaking noise for a real improvement, which is precisely the discipline Adv 7 (multiple seeds, confidence intervals, the multiple-comparisons trap) covers in depth.

2.9 — Checkpointing Strategy for Long Fine-Tune Runs

The general mechanics of checkpointing and resuming a PyTorch training run (optimizer state, step count, RNG state) are Adv 1's job — referenced, not repeated. What's specific to LoRA: peft_model.save_pretrained(dir) saves ONLY the adapter weights — typically a few MB, versus gigabytes for a full model checkpoint — so you can afford to checkpoint far more often than a full fine-tune ever could. To resume or serve, reload the frozen base once and reattach the adapter: PeftModel.from_pretrained(base_model, adapter_dir).

The same "only the adapter is small" property extends to the optimizer state itself: since Adam's momentum and variance are only tracked for the trainable (adapter) parameters, resuming a LoRA run means restoring optimizer state sized to a few tens of thousands to a few million numbers, not billions — the general resume mechanics from Adv 1 apply unchanged, they're simply operating over a dramatically smaller state to begin with. This is one more instance of the same theme running through this whole chapter: LoRA doesn't need a special-cased version of every piece of standard training infrastructure, it just makes every piece of that infrastructure cheaper by shrinking what's trainable.

💡
Keep more than just "last" — save the N most recent checkpoints AND the best-eval checkpoint (load_best_model_at_end in Trainer, or the manual equivalent: track best eval loss, save separately). A long run can regress or diverge late; cheap adapter-only checkpoints make it free to fall back.

The disk-cost difference is concrete, not just theoretical: for a 7B-parameter base model, a single full fp16 checkpoint is ~14 GB, so checkpointing every few hundred steps over a long run quickly becomes a real storage-management problem on its own. A LoRA adapter targeting the attention projections at rank 8–16, by contrast, is typically only a few megabytes to a few tens of megabytes — cheap enough to checkpoint every eval step, keep dozens of them around, and even version them like ordinary small config files. Whatever experiment tracker records these runs' metrics over time is a separate concern already covered in `mlops-practice/mp02` (referenced, not repeated) — this section is specifically about what gets written to disk and how often, not about the dashboard that watches it.

2.10 — The Full Pipeline

Sections 2.1–2.9 chain into one pipeline — this is exactly what the Project below builds end to end:

Treat the whole thing as a loop, not a one-shot script: run the pipeline once end to end with a small, cheap config (small rank, attention-only target_modules, a quick eval), look at the before/after numbers honestly, and only then decide what's worth changing — more data if the model is clearly underfitting even the training set, a higher rank or wider target_modules if held-out perplexity plateaus well above the baseline while training loss keeps dropping (a sign the adapter itself is the bottleneck, not the data), or QLoRA specifically if the NEXT experiment's base model no longer fits in GPU memory at all. Each iteration is cheap precisely because the pieces that matter — the adapter checkpoint, the eval script, the before/after comparison — are all small and fast by construction; that fast loop is the entire practical argument for PEFT methods over full fine-tuning, independent of the raw memory math in Section 2.3.

Advanced 2 Summary
  • SFT updates the model's own weights on your (prompt, response) pairs — unlike prompting, the behavior survives a bare prompt with no instructions.
  • datasets.map() builds and tokenizes real fine-tuning data; causal-LM labels are just the input IDs shifted internally by the loss function.
  • Full fine-tuning costs roughly 16 bytes/parameter (fp16 weights+grads + fp32 master+Adam m+v) — infeasible for 7B+ models on a single GPU.
  • LoRA freezes W and learns ΔW = B·A at rank r << d — real ~256x parameter savings on a typical projection shape, verified with a real GPT-2-shaped fine-tune (perplexity 25337 → 7496).
  • QLoRA quantizes the frozen base to 4-bit NF4 (GPU-only) while adapters stay full precision — ~4.1 GB vs. ~112 GB for a 7B model's full fine-tune.
  • Checkpoint adapters, not the full model — a few MB, so frequent + best-eval checkpoints are essentially free.
