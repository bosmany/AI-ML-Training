5.1 — The ML-Specific Slice of Data Engineering

Every one of the tools in this chapter — SQL, Spark, columnar files, lakes, ETL — already has a job description outside ML, and you already know that job description. What changes when the consumer is a model rather than a report is time semantics: a BI dashboard is allowed to ask "what does the data look like right now," but a training pipeline must ask "what did the data look like at the exact instant each historical prediction would have been made" — get that wrong and you get a model that looks brilliant offline and falls apart in production, for reasons that have nothing to do with the model itself. That single distinction is the thread running through this whole chapter: window functions computed the wrong way, joins that grab tomorrow's feature value, a nightly batch job that silently disagrees with the streaming job serving live traffic — every one of these is the same underlying failure (using information the model would not have had) wearing a different data-engineering costume.

We will build on mlops-practice/mp01 (reproducibility, data-quality gates, leakage and train/serve skew) and mp04 (monitoring and drift) rather than re-deriving them — both get referenced by section number below instead of repeated. What's new here is the data-engineering machinery that either causes those failures or prevents them: real SQL window functions, point-in-time joins, Parquet internals, PySpark's DataFrame API, medallion lakes, and the batch/streaming trade-off.

Concretely, that means this chapter is organized around a single pipeline you will actually build in the project: raw events land somewhere cheap (bronze), get computed into row-per-entity features using the window-function and point-in-time techniques in §5.2-§5.3, get stored in a format chosen for how ML actually reads data rather than how a report does (§5.5-§5.6), and get promoted through a quality gate you already know how to write (§5.9, reusing mp01) into a shape a training job or an online feature store can consume. The batch-vs-streaming decision in §5.10 is where that whole pipeline meets the clock, and is usually the single design decision with the largest blast radius if it's made implicitly instead of on purpose.

5.2 — Window Functions for Feature Computation

You already know GROUP BY collapses rows; a window function instead keeps every row and attaches a value computed over a window of related rows — OVER (PARTITION BY ... ORDER BY ...). For ML feature engineering this is the workhorse: "this customer's running total," "the average of their last 3 orders," "how long since their previous visit" are all one-line window-function expressions, computed once in the warehouse instead of as a slow Python loop. The examples below run on a real, in-process SQLite database (Pyodide has no server-based SQL engine, but SQLite's window-function support is the genuine ANSI SQL syntax, not an imitation) — the query text is exactly what you would run against Postgres, Snowflake or BigQuery.

Running total and rolling average with real SQL window functions
import sqlite3 con = sqlite3.connect(':memory:') cur = con.cursor() cur.executescript(""" CREATE TABLE txns (customer_id TEXT, txn_time INTEGER, amount REAL); """) rows = [ ('c1', 1000, 100.0), ('c1', 1050, 50.0), ('c1', 1100, 200.0), ('c2', 1010, 30.0), ('c2', 1060, 70.0), ] cur.executemany("INSERT INTO txns VALUES (?,?,?)", rows) con.commit() q = """ SELECT customer_id, txn_time, amount, SUM(amount) OVER (PARTITION BY customer_id ORDER BY txn_time ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total, AVG(amount) OVER (PARTITION BY customer_id ORDER BY txn_time ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS rolling_avg_2 FROM txns ORDER BY customer_id, txn_time """ for row in cur.execute(q): print(row)

Two more window functions earn their keep in almost every feature table. ROW_NUMBER() gives each row a rank inside its partition — the standard way to compute "which visit number is this" or to de-duplicate down to "the latest row per key." LAG() reaches back to the previous row in the same partition — the standard way to compute "seconds since the previous event" without a self-join.

ROW_NUMBER() and LAG() for per-user sequence features
import sqlite3 con = sqlite3.connect(':memory:') cur = con.cursor() cur.executescript("CREATE TABLE page_views (user_id TEXT, ts INTEGER, page TEXT);") rows = [ ('u1', 1000, 'home'), ('u1', 1050, 'search'), ('u1', 1200, 'product'), ('u2', 1010, 'home'), ('u2', 1400, 'product'), ] cur.executemany("INSERT INTO page_views VALUES (?,?,?)", rows) con.commit() q = """ SELECT user_id, ts, page, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY ts) AS view_number, ts - LAG(ts) OVER (PARTITION BY user_id ORDER BY ts) AS seconds_since_prev FROM page_views ORDER BY user_id, ts """ for row in cur.execute(q): print(row)
⭐
Why compute features in SQL instead of pandas. The window-function query runs once, in the warehouse, next to the data — no network transfer of the full history, and the exact same query (parameterized by an "as of" date) can back-fill years of training data or compute today's feature for serving. A Python loop over rows re-implements what the query planner already does correctly and in parallel.
5.3 — Point-in-Time-Correct Joins

This is the sharpest edge in ML data engineering and the natural sequel to the leakage checklist in mp01 §1.7: mp01 taught you to detect a feature that "wouldn't exist yet" at prediction time; a point-in-time join is how you build a feature table so that failure mode cannot happen in the first place. A feature store keeps a history of feature values (a customer's credit score as of several different dates), and building training data means joining each historical event to the feature value that was true at that event's time — not the latest one, which would leak the future into the past.

Naive "latest" join (leaks future feature values) vs a real point-in-time join
import sqlite3 con = sqlite3.connect(':memory:') cur = con.cursor() cur.executescript(""" CREATE TABLE feature_snapshots (customer_id TEXT, as_of_date TEXT, credit_score INTEGER); CREATE TABLE events (event_id INTEGER, customer_id TEXT, event_time TEXT, label INTEGER); """) cur.executemany("INSERT INTO feature_snapshots VALUES (?,?,?)", [ ('c1', '2024-01-01', 600), ('c1', '2024-01-15', 650), ('c1', '2024-02-01', 700), ('c2', '2024-01-01', 580), ('c2', '2024-01-20', 610), ]) cur.executemany("INSERT INTO events VALUES (?,?,?,?)", [ (1, 'c1', '2024-01-10', 0), (2, 'c1', '2024-01-20', 1), (3, 'c1', '2024-02-15', 0), (4, 'c2', '2024-01-05', 0), ]) con.commit() # WRONG: joins every event to the customer's LATEST snapshot -> leaks future feature values wrong = """ SELECT e.event_id, e.event_time, f.as_of_date, f.credit_score FROM events e JOIN (SELECT customer_id, MAX(as_of_date) AS as_of_date FROM feature_snapshots GROUP BY customer_id) latest ON latest.customer_id = e.customer_id JOIN feature_snapshots f ON f.customer_id = latest.customer_id AND f.as_of_date = latest.as_of_date ORDER BY e.event_id """ print('-- naive join (leaks future feature values) --') for row in cur.execute(wrong): print(row) # CORRECT: joins each event to the most recent snapshot AS OF (<=) that event's own time correct = """ SELECT e.event_id, e.event_time, (SELECT f.as_of_date FROM feature_snapshots f WHERE f.customer_id = e.customer_id AND f.as_of_date <= e.event_time ORDER BY f.as_of_date DESC LIMIT 1) AS as_of_date, (SELECT f.credit_score FROM feature_snapshots f WHERE f.customer_id = e.customer_id AND f.as_of_date <= e.event_time ORDER BY f.as_of_date DESC LIMIT 1) AS credit_score FROM events e ORDER BY e.event_id """ print('-- point-in-time-correct join --') for row in cur.execute(correct): print(row)

Look at event 1 (2024-01-10): the naive join hands it a credit score of 700 — a value that would not exist for another three weeks. The point-in-time join correctly hands it 600, the score that was actually on file that day. This is exactly the mechanism feature stores like Feast or Tecton sell as their headline feature ("point-in-time correct training data generation") — now you know what is actually happening underneath: a correlated subquery (or, at scale, an ASOF JOIN / a window function with a range frame) keyed on "most recent snapshot not after this event."

The correlated subquery above is correct but does not scale as written — for every one of millions of events it re-scans that customer's snapshot history, which is fine for a demo and a query planner's worst nightmare on a real feature store. Two things make it fast in practice: an index (or, in a columnar table, a sort order) on (customer_id, as_of_date) so "most recent row not after X" is a range-bounded lookup instead of a full scan, and, where the SQL dialect supports it, a native ASOF JOIN (DuckDB, kdb+, and increasingly Spark/Flink via window joins) that implements exactly this "nearest preceding row" semantics as a first-class join type instead of a correlated subquery. The concept — join to what was true, not what is true — is identical at every scale; only the execution strategy changes.

⚠️
This is also why "offline AUC 0.99, coin flip in production" so often traces back here. A naive latest-value join makes every historical feature artificially accurate — the model is effectively told the answer. mp01 §1.7 gave you the debugging checklist (split strategy, feature availability, label timing, train/serve stats); this section is the fix for the specific "feature availability" bullet when your features come from a snapshot table.
5.4 — PySpark for ML Data Prep: DataFrame API, Lazy Evaluation, When You Need It

You already know Spark exists and roughly what it is for (distributed compute over a cluster). The part that actually matters day to day for ML data prep is the DataFrame API's laziness: every .filter(), .select() or .groupBy() call just builds a plan — nothing runs until an action (.show(), .collect(), .write) forces it. That matters because Spark's optimizer (Catalyst) can rewrite the whole plan before executing it once — pushing filters down before expensive joins, pruning columns you never select — which a pandas script, executing eagerly line by line, cannot do for you.

Real PySpark DataFrame API — reference only, needs a JVM this sandbox does not have
from pyspark.sql import SparkSession from pyspark.sql import functions as F spark = SparkSession.builder.appName("feature-prep").getOrCreate() orders = spark.read.parquet("s3://lake/bronze/orders/") # nothing read yet — lazy daily = (orders .filter(F.col("country") == "US") # still lazy: just adds a step to the plan .groupBy("customer_id", "order_date") .agg(F.count("*").alias("order_count"), F.sum("amount").alias("total_amount"))) daily.explain() # shows the OPTIMIZED plan, still nothing executed daily.write.partitionBy("order_date").parquet("s3://lake/silver/daily_features/") # the ACTION
⚠️
Reference-only. PySpark needs a JVM and a cluster (or at least local mode with Java installed); neither exists in this sandbox. The DataFrame API calls above are real, correct syntax — the exercises exercise the same transformation logic for real in pandas, and section 5.10's exercise is explicit about which parts are simulated versus genuinely executed.

The honest decision rule, since "just use Spark" is not free — a cluster, serialization overhead, and a genuinely different debugging experience: reach for Spark when a single machine's RAM cannot hold the data (tens to hundreds of GB and up), when the job is naturally embarrassingly parallel across many files, or when you are already inside a Spark-based platform (Databricks, EMR) and the incremental cost of one more job is near zero. Stay on pandas or polars (a modern, multi-threaded, single-machine DataFrame library with a similar lazy-execution story to Spark, without the cluster) when the data fits comfortably in memory on one box — which, for most feature-engineering jobs on a single company's tabular data, it does. Partitioning is the other half of "when you need it": Spark shines specifically because it can read only the file partitions a filter touches and process the rest in parallel across executors — which is exactly the Parquet partitioning story in the next two sections, and the reason Spark and Parquet are almost always mentioned in the same sentence.

The operational gotcha DevOps experience does not automatically cover is the shuffle: any operation that needs rows from different partitions to meet — a groupBy on a column other than the current partition key, a join on a non-partitioned column — forces Spark to redistribute data across the cluster over the network, which is almost always the slowest part of a job and the first thing to check when a Spark job is "just slow." repartition(n) triggers a full shuffle to rebalance into n partitions (useful before a big join); coalesce(n) merges partitions without a shuffle (useful only to reduce partition count, e.g. before writing fewer, larger output files). And because the DataFrame API is lazy, an expensive computation reused by two downstream steps gets recomputed twice unless you explicitly .cache() or .persist() it — the Spark equivalent of memoization, and a common first fix for "why is this job doing the same join four times."

5.5 — Parquet: Why Columnar Beats CSV for ML Data

A CSV is row-oriented: every value for row 1, then every value for row 2. Parquet is columnar: every value for column A stored together, then every value for column B — which pays off twice for ML workloads. First, reading only the three columns your feature needs out of a 200-column table touches only those columns' bytes, not the whole file. Second, a column of repeated values (a country code, a boolean flag) compresses far better sitting next to only its own kind than interleaved with unrelated numbers and strings. Parquet also stores the schema and per-column statistics (min/max) in the file itself, so a query engine can sometimes skip whole row groups without reading them at all.

Real CSV vs Parquet: file size, and reading only the column you need
import pandas as pd, numpy as np, os import fastparquet # pandas' Parquet engine in this browser (no pyarrow build in Pyodide) rng = np.random.default_rng(0) n = 20_000 df = pd.DataFrame({ 'user_id': rng.integers(1, 5000, n), 'country': rng.choice(['US', 'EU', 'APAC', 'LATAM'], n), 'amount': rng.uniform(5, 500, n).round(2), 'is_fraud': rng.integers(0, 2, n), }) df.to_csv('/tmp/orders_size.csv', index=False) df.to_parquet('/tmp/orders_size.parquet', engine='fastparquet') csv_bytes = os.path.getsize('/tmp/orders_size.csv') parquet_bytes = os.path.getsize('/tmp/orders_size.parquet') print(f"rows: {n}") print(f"CSV size: {csv_bytes:,} bytes") print(f"Parquet size: {parquet_bytes:,} bytes") print(f"Parquet is {csv_bytes / parquet_bytes:.1f}x smaller on this dataset") only_country = pd.read_parquet('/tmp/orders_size.parquet', engine='fastparquet', columns=['country']) print('columns actually read:', only_country.columns.tolist())
🧠
Honest numbers, not marketing numbers. On this synthetic, fairly random dataset Parquet comes out roughly 1.5-2x smaller than CSV — real, but modest, because random floats and evenly split categories barely compress. Real production tables with repetitive categorical columns, sorted timestamps and low-cardinality flags routinely see 5-10x. The columns=[...] argument is the more universally reliable win: it is a genuine columnar read, not an estimate.
⚠️
Why fastparquet and not pyarrow here. Pyodide (Python-in-the-browser) has no pyarrow build, so every Parquet example in this chapter uses engine='fastparquet', a pure-Python/Cython Parquet implementation — genuinely reading and writing the real file format. In a normal venv or production job, engine='pyarrow' (pandas' default when installed) is the more common choice and slightly faster; the file format and the lessons here are identical either way.
5.6 — Partitioning Schemes and Real Partition Pruning

A partitioned Parquet "table" is really just a directory tree: orders/country=US/part.0.parquet, orders/country=EU/part.0.parquet, and so on — the partition column's value is encoded in the folder name and dropped from the file itself. Partition pruning means a query that filters on the partition column never opens the folders it doesn't need — the query planner reads folder names, not file contents, to decide what to skip. The proof below is deliberately adversarial: we corrupt the US partition's file so that opening it would crash, then filter for EU only and show the read still succeeds — the only way that's possible is if the US file was never opened at all.

directory layout after partitioning by country
orders/
├── country=US/
│   └── part.0.parquet      (only US rows, no "country" column inside)
├── country=EU/
│   └── part.0.parquet      (only EU rows)
└── country=APAC/
    └── part.0.parquet      (only APAC rows)
Proving partition pruning: read succeeds even though one partition's file is corrupted
import pandas as pd, numpy as np, glob import fastparquet df = pd.DataFrame({ 'order_id': range(1, 13), 'country': ['US']*4 + ['EU']*4 + ['APAC']*4, 'amount': np.round(np.random.default_rng(0).uniform(10, 500, 12), 2), }) df.to_parquet('/tmp/pq_prune_demo', engine='fastparquet', partition_cols=['country']) # sabotage the US partition file so opening it would raise an error for f in glob.glob('/tmp/pq_prune_demo/country=US/*.parquet'): with open(f, 'wb') as fh: fh.write(b'not a real parquet file at all') try: eu_only = pd.read_parquet('/tmp/pq_prune_demo', engine='fastparquet', filters=[('country', '==', 'EU')]) print('read succeeded despite corrupted US partition -> real pruning') print('rows:', len(eu_only), 'countries:', eu_only['country'].unique().tolist()) except Exception as e: print('read FAILED (touched the corrupted file):', type(e).__name__)

The design question is which column(s) to partition by, and it only has one right answer per table: partition by whatever your queries actually filter on most often, and remember that partition order matters for nested directories — a query that filters only on the inner column still has to open every outer folder to reach it. Over-partitioning is a real failure mode too (too many tiny files hurts more than it helps); a common rule of thumb is to keep each partition file in the tens-to-hundreds of MB range, not kilobytes. Exercise 2 has you measure this trade-off with real numbers instead of taking it on faith.

5.7 — Data Lakes: Bronze, Silver, Gold

A data warehouse wants clean, modeled, schema-enforced tables — great for BI, awkward for ML, which routinely needs the messy raw event before anyone decided how to model it (the exact wording of a support ticket, a raw clickstream, an un-deduplicated log). A data lake — object storage plus a table format like Parquet, Delta or Iceberg — stores data at whatever stage it's in and lets you choose how clean to make it, which is why ML platforms are usually built lake-first with a warehouse layered on top for BI. The medallion architecture is the standard way to organize that: three named zones, each a real Parquet dataset, each stricter than the last.

medallion architecture: bronze → silver → gold
BRONZE (raw)              SILVER (cleaned)              GOLD (feature-ready)
────────────────          ─────────────────             ────────────────────
raw JSON/CSV/logs   -->   deduplicated                   business-level
as-ingested, no      |    schema-enforced         -->    aggregates &
schema guarantees    |    types fixed, joined            ML feature tables
append-only, cheap   |    quality-gated                  (what 5.10's
to re-derive from    |    (mp01 §1.5/§1.6 checks)         project reads)

Bronze is the source of truth you can always replay from if a downstream bug corrupts silver or gold — this is why it is append-only and never overwritten. Silver is where the data-quality gate from mp01 belongs (schema checks, range checks, dedup) — reference that section rather than re-deriving it; nothing new to add here except that in a lake, that gate is usually itself a scheduled job writing a new, clean Parquet dataset rather than a one-off script. Gold is shaped for a specific consumer — for ML that usually means a feature table, one row per (entity, timestamp), ready for the point-in-time join in §5.3. The project in this chapter builds exactly this: bronze → quality gate → silver.

"Lake vs warehouse" is not a fight ML wins outright — it's a fight over what gets stored before anyone has decided on a schema. A warehouse (Snowflake, BigQuery, Redshift) wants a schema up front and gives you strong governance, fast SQL and a mature BI ecosystem in exchange; that is exactly what you want for the gold layer and for anyone doing dashboards. It is a poor fit for the bronze layer of an ML platform because ML teams routinely want to keep raw, unstructured or semi-structured data (full request payloads, images, un-parsed logs, a new event type nobody has modeled yet) on the chance a future feature idea needs it, without a schema migration for every experiment. A lake — cheap object storage plus a table format — happily stores all of that at bronze, then gets schema and quality enforced only once, at the silver boundary, which is precisely why medallion architecture and "ML platforms are lake-first" tend to be mentioned in the same breath: the lake buys the freedom to capture everything now and decide what it means later, without ever losing the ability to reprocess from scratch.

5.8 — ETL vs ELT for ML Pipelines

ETL (Extract, Transform, Load) transforms data in a separate compute layer — a Spark job, a Python script — before it ever lands in the warehouse or lake. ELT (Extract, Load, Transform) loads the raw data first and transforms it in place, usually with SQL running inside the warehouse itself (dbt is the tool most associated with this style). Neither is universally correct; the trade-off that matters for ML specifically is reproducibility of the raw layer. ELT's "load first, transform later" habit is a natural fit for the bronze zone in §5.7 — you always have the untouched raw data to re-run a fixed transform against, which matters enormously when you discover a bug in a feature definition six months after the affected models shipped. ETL pipelines that transform-then-load often never persist the pre-transform data at all, which is fine for a dashboard nobody will re-derive and painful for a model you need to explain or retrain.

ETL vs ELT, and where each keeps the "replay from raw" option
ETL:  source --> [transform in Spark/Python] --> warehouse table
                          (raw form often discarded after this step)

ELT:  source --> lake/warehouse (raw, bronze) --> [transform in SQL/dbt] --> silver/gold
                        ^ always here to re-run a fixed transform against

In practice most real ML platforms run both: an ELT-style bronze landing zone for replayability, with an ETL-style Spark or pandas job doing the heavier feature computation (joins, window functions, point-in-time correctness) that plain SQL-in-the-warehouse would make awkward. Pick based on where the transform is cheapest to run and where you need the ability to rewind, not based on which acronym sounds more modern.

5.9 — Data Validation and Versioning, Briefly

Both of these are fully covered already and get referenced rather than repeated. Validation — schema checks, range/domain checks, the pass/fail quality-gate report, pydantic for row-level contracts, and where pandera and Great Expectations fit — is mp01 §1.5, §1.6 and §1.8; the only new thing worth saying here is where that gate sits in a lake: as the bronze-to-silver transform in §5.7, run once per landing batch, blocking promotion to silver on failure exactly as mp01 describes. Versioning — DVC's pointer-file-in-git model for large datasets — is mp01 §1.8; the lake-specific addition is that a table format like Delta or Iceberg gives you the same "time travel" property natively (query the table as it existed at a past commit) without a separate tool, which is why newer lake platforms increasingly skip DVC for anything that's already a lake table.

5.10 — Batch vs Streaming for ML Features

The question is simple to state and expensive to get wrong: does this feature need to reflect an event from the last few seconds, or is "as of last night" good enough? Fraud scoring at the moment of a card swipe needs the last few seconds; a weekly churn-propensity feature does not. The mistake that creates real production incidents is treating this as a performance question ("streaming is faster") when it is really a correctness question — the two computation paths are different code, running at different times, and mp01 §1.7 already named the failure mode this produces: train/serve skew. The runnable example below is the specific, batch/streaming-flavored version of that failure: the same logical feature, computed two honestly-implemented ways, giving two different numbers with zero bugs anywhere.

Same feature, two pipelines: a late-arriving event splits batch from streaming
import pandas as pd # One customer's purchases; event_time = when it happened, arrival_time = when the pipeline saw it events = pd.DataFrame({ 'customer_id': ['c1', 'c1', 'c1', 'c1'], 'event_time': [480, 610, 700, 705], 'amount': [40.0, 15.0, 22.0, 60.0], 'arrival_time': [480, 610, 700, 1440], # the 60.0 purchase arrives a full day late }) # STREAMING: closes its window at minute 720 using only what had ARRIVED by then window_close = 720 streaming_seen = events[events['arrival_time'] <= window_close] streaming_feature = streaming_seen['amount'].sum() # BATCH: a nightly job that scans the full day AFTER every event has arrived batch_feature = events['amount'].sum() print(f"streaming feature (as of minute {window_close}): {streaming_feature}") print(f"batch feature (full day, computed next morning): {batch_feature}") print(f"same feature name, different value: {streaming_feature != batch_feature}") print(f"gap: {batch_feature - streaming_feature}")

Nobody wrote a bug. The streaming job correctly reported what it knew at the time; the batch job correctly reported the full day once everything settled. If training data comes from the batch feature and serving reads the streaming feature (a very common real setup — batch for backfill and training, streaming for low-latency serving), the model trains on a systematically different distribution than it serves on. The fix is not "pick one architecture forever" — it is to make the discrepancy visible and bounded: log both the streaming and eventual-batch value for the same logical feature, monitor their gap the way mp04 §4.7 monitors prediction drift under delayed labels, and set an explicit, documented tolerance instead of discovering the gap from a metrics regression three weeks later.

Typical freshnesshours to a dayseconds
Infra complexitylowerhigher (Kafka/Flink-class systems)
Good fitweekly/monthly aggregates, backfills, training datafraud scoring, bidding, live inventory

Chapter Summary
  • The ML-specific twist on data engineering is always about time: what did the data look like at the exact moment a historical prediction was made.
  • SQL window functions (OVER, ROW_NUMBER, LAG) compute per-row features once, in the warehouse, instead of in a slow Python loop.
  • A point-in-time join is how a feature store builds leakage-free training data — join to the snapshot as of the event, never the latest one.
  • PySpark's DataFrame API is lazy so its optimizer can rewrite the whole plan; reach for it (or polars) only once single-machine pandas genuinely runs out of RAM.
  • Parquet is columnar (read only the columns you need, compress better) and partitioned directories give real, provable partition pruning.
  • Medallion bronze → silver → gold keeps a replayable raw layer, applies the mp01 quality gate once at silver, and ships feature tables as gold.
  • Batch vs streaming is a correctness decision, not a speed decision — mismatched batch-trained / streaming-served features are a textbook source of train/serve skew.
