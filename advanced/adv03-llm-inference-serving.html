3.1 — Why Naive One-Request-at-a-Time Serving Wastes the GPU

A GPU running LLM decode spends almost all of its time moving weights from memory to compute units, not computing on them — decode is memory-bandwidth bound, not compute bound. Concretely: generating the next token for one sequence reads every weight in the model once, does a tiny amount of arithmetic with each one, and throws most of the GPU's compute capacity away idle. Generating the next token for 16 sequences at once reads the same weights once and does 16x the arithmetic with them — almost free, because the GPU had that headroom sitting unused. Serve requests one at a time under real concurrent traffic and you are not being "safe" or "simple", you are leaving most of an expensive card idle while a queue of paying users piles up behind it.

This is not a hypothetical. Here is the same idea as a deterministic simulation you can run: 500 requests arrive as a Poisson process (mean 3ms apart), and each GPU pass costs a mostly-fixed overhead plus a small per-token term that grows only slightly with batch size — the shape argued for above. Naive serialized service collapses under this load (the arrival rate exceeds what one-at-a-time can drain); windowed batching keeps up easily.

GPU-queueing simulation: naive vs. windowed batching
import numpy as np rng = np.random.default_rng(7) N = 500 mean_interarrival_ms = 3.0 arrivals = np.cumsum(rng.exponential(mean_interarrival_ms, size=N)) FIXED_MS, PER_TOK_MS, TOKENS, GROWTH = 8.0, 0.35, 24, 0.03 def pass_cost_ms(batch_size): # cost of ONE GPU pass over `batch_size` sequences: mostly-fixed overhead # + a per-token term that grows only a little with batch size (decode is # memory-bandwidth bound, so the weights move through the chip once per # step no matter how many sequences ride along) return FIXED_MS + PER_TOK_MS * TOKENS * (1 + GROWTH * (batch_size - 1)) def simulate_naive(arrivals): # one GPU, one request at a time -- a real queue behind a single server finish, prev_finish, cost = np.zeros(len(arrivals)), 0.0, pass_cost_ms(1) for i, a in enumerate(arrivals): start = max(a, prev_finish) finish[i] = prev_finish = start + cost return finish - arrivals def simulate_batched(arrivals, window_ms=12.0, cap=16): # collect whoever arrives within `window_ms`, or `cap` requests, then run ONE pass latencies, i, n, gpu_free_at = np.zeros(len(arrivals)), 0, len(arrivals), 0.0 while i < n: window_start = arrivals[i] j = i while j < n and arrivals[j] <= window_start + window_ms and (j - i) < cap: j += 1 batch = arrivals[i:j] dispatch = max(window_start + window_ms, gpu_free_at, batch[-1]) finish = dispatch + pass_cost_ms(len(batch)) latencies[i:j] = finish - batch gpu_free_at = finish i = j return latencies lat_naive = simulate_naive(arrivals) lat_batched = simulate_batched(arrivals) def summarize(name, lat): p50, p95, p99 = np.percentile(lat, [50, 95, 99]) thpt = len(lat) / (arrivals[-1] + lat[-1]) * 1000.0 print(f"{name}: p50={p50:.1f}ms p95={p95:.1f}ms p99={p99:.1f}ms throughput={thpt:.1f} req/s") summarize("naive ", lat_naive) summarize("batched", lat_batched)
naive : p50=3350.6ms p95=6327.6ms p99=6580.4ms throughput=61.0 req/s batched: p50=108.8ms p95=229.6ms p99=243.3ms throughput=277.1 req/s

3.2 — Continuous / Dynamic Batching

There are three batching strategies worth naming precisely, because "batching" alone is ambiguous and interviewers (and production incidents) care about which one you mean:

  • Static batching: collect exactly N requests, run them together for their entire generation, and only start the next batch once every sequence in the current one has finished. The GPU idles for every sequence that finishes early while waiting for the slowest one.
  • Windowed / dynamic batching: collect whoever arrives within a fixed time window (or until a size cap), run one pass, repeat. Section 3.1's simulation used this. Better than static, but still wastes a moment waiting out the window, and a batch is still fixed once dispatched.
  • Continuous batching (the real technique behind vLLM, TGI, TensorRT-LLM): decode proceeds one step at a time across whichever sequences are currently live. The instant any sequence finishes, its slot is freed and the very next queued request fills it — on the next decode step, not at the end of anyone else's generation. No one waits for a window and no one waits for the slowest sequence in an old batch.
Slot occupancy over time: static batching (wait for the whole batch) vs. continuous
static batching, 4 slots, requests finish at different lengths:
  slot1 [A------------done]                    [E----done]
  slot2 [B--done]           (slot idles, waiting for the batch)
  slot3 [C----------done]   (slot idles, waiting for the batch)
  slot4 [D----------------------done]
                                              ^ ALL slots stall until D finishes

continuous batching, same 4 slots:
  slot1 [A------------done][E----done]
  slot2 [B--done][F--------done]
  slot3 [C----------done][G-done]
  slot4 [D----------------------done][H--...
                    ^ each slot refills the instant it frees, no group wait

The simulation below makes this concrete with a GPU that can hold 8 sequences at once, 60 requests with varying (unknown-in-advance) output lengths arriving in a somewhat bursty pattern. "Static" only admits new sequences once every current slot is empty; "continuous" fills any free slot immediately. The metric that matters is GPU utilization: the fraction of decode steps where a slot was actually doing useful work.

Continuous vs. static batching: slot occupancy simulation
import numpy as np rng = np.random.default_rng(3) N_REQUESTS = 60 CAPACITY = 8 # how many sequences the GPU can hold at once lengths = rng.integers(3, 20, size=N_REQUESTS) # decode steps each request still needs arrivals = np.sort(rng.integers(0, 40, size=N_REQUESTS)) def run(mode): queue = sorted(zip(arrivals.tolist(), lengths.tolist()), key=lambda r: r[0]) qi = 0 slots = [None] * CAPACITY # remaining steps for the sequence in this slot, or None step, busy_steps, total_steps, completed = 0, 0, 0, 0 while completed < N_REQUESTS: can_admit = any(s is None for s in slots) if mode == "static": can_admit = can_admit and all(s is None for s in slots) # wait for the WHOLE batch to finish if can_admit: for k in range(CAPACITY): if slots[k] is None and qi < len(queue) and queue[qi][0] <= step: slots[k] = queue[qi][1] qi += 1 busy = sum(1 for s in slots if s is not None) if busy: busy_steps += busy total_steps += 1 for k in range(CAPACITY): if slots[k] is not None: slots[k] -= 1 if slots[k] == 0: slots[k] = None completed += 1 elif qi < len(queue): step = queue[qi][0] continue step += 1 return step, busy_steps / (total_steps * CAPACITY) steps_cont, util_cont = run("continuous") steps_stat, util_stat = run("static") print(f"Continuous batching: finished at step {steps_cont}, GPU utilization {util_cont:.1%}") print(f"Static batching: finished at step {steps_stat}, GPU utilization {util_stat:.1%}") print(f"Speedup from continuous batching: {steps_stat/steps_cont:.2f}x fewer steps to drain the same {N_REQUESTS} requests")
Continuous batching: finished at step 93, GPU utilization 85.1% Static batching: finished at step 154, GPU utilization 51.4% Speedup from continuous batching: 1.66x fewer steps to drain the same 60 requests

Notice the mechanism is exactly the same shape as an OS scheduler filling a fixed number of CPU cores as processes exit and new ones arrive — if you already reason about run queues and context switches, continuous batching is that idea applied to GPU decode slots instead of CPU cores.

3.3 — The KV Cache: What It Stores and Why It Grows Linearly

ch25's attention math recomputes, for every new token, the dot product between that token's query and the keys of every previous token. Recomputing the keys and values for all previous tokens on every single step would make generation quadratic in sequence length for no reason — those keys and values never change once computed. So every real serving system caches them: for each attention layer, for each sequence, it stores one K vector and one V vector per token already generated. That is the KV cache. Each new decode step computes K/V for only the one new token, appends it to the cache, and attends over everything stored so far. This is why the cache grows linearly with sequence length: every generated token adds exactly one more K/V pair, per layer, forever, for as long as that sequence stays alive on the GPU.

KV cache growth, one layer, one sequence
step 1 ("The"):     cache = [K1,V1]
step 2 ("The cat"): cache = [K1,V1][K2,V2]
step 3 (" sat"):    cache = [K1,V1][K2,V2][K3,V3]
                     ...
step N:              cache = [K1,V1]...[KN,VN]   <- N pairs, growing by 1 every step

memory per sequence = num_layers x seq_len x 2 (K and V) x num_kv_heads x head_dim x dtype_bytes

Multiply that out across every layer and every sequence in flight and it stops being a rounding error — it is routinely the single largest consumer of GPU memory during serving, larger than the model's own weights once sequences get long or batches get wide. The function below computes it exactly, and applies it to a few realistic shapes, including grouped-query attention (GQA): modern models (Llama-3, Mistral, and others) use far fewer "KV heads" than "query heads" — several query heads share one K/V head — specifically to shrink this cache. The GQA row below uses 8 KV heads instead of 32 query heads, same everything else.

KV-cache memory calculator, several real-ish model shapes
def kv_cache_bytes(batch_size, seq_len, num_layers, num_kv_heads, head_dim, dtype_bytes=2): """Bytes needed to hold K and V for `batch_size` sequences of length `seq_len`.""" per_token_per_layer = 2 * num_kv_heads * head_dim * dtype_bytes # 2 = one K, one V per_sequence = per_token_per_layer * num_layers * seq_len return per_sequence * batch_size GiB = 1024 ** 3 # "Llama-2-7B"-shaped model: 32 layers, 32 heads, head_dim 128, no GQA, fp16 cache configs = [ ("7B-class, seq=2048, batch=1", dict(batch_size=1, seq_len=2048, num_layers=32, num_kv_heads=32, head_dim=128)), ("7B-class, seq=4096, batch=8", dict(batch_size=8, seq_len=4096, num_layers=32, num_kv_heads=32, head_dim=128)), ("13B-class, seq=4096, batch=8", dict(batch_size=8, seq_len=4096, num_layers=40, num_kv_heads=40, head_dim=128)), ("7B-class w/ GQA (8 kv heads), same load", dict(batch_size=8, seq_len=4096, num_layers=32, num_kv_heads=8, head_dim=128)), ] for name, cfg in configs: b = kv_cache_bytes(**cfg) print(f"{name}: {b/GiB:.2f} GiB")
7B-class, seq=2048, batch=1: 1.00 GiB 7B-class, seq=4096, batch=8: 16.00 GiB 13B-class, seq=4096, batch=8: 25.00 GiB 7B-class w/ GQA (8 kv heads), same load: 4.00 GiB

Read the last two rows together: a bigger model (13B vs. 7B) costs more KV cache because it has more layers and more KV heads, but switching from full multi-head attention to GQA on the same 7B model cuts the cache by exactly the ratio of KV heads (32/8 = 4x here), independent of model size. That is why almost every serving-oriented model released since 2023 ships with GQA or a variant of it (or its more aggressive cousin, multi-query attention, which uses a single shared KV head) — it is a direct, controllable lever on the thing that actually limits how many concurrent sequences a GPU can hold.

3.4 — Quantization for Inference

Weights are normally stored in fp16 or bf16 (2 bytes each). Quantization stores them in fewer bits — int8 (1 byte) or int4 (half a byte) — by picking a scale factor and rounding every value onto a small integer grid. This shrinks the model's memory footprint proportionally (int8 is half the size of fp16, int4 is a quarter), which matters for exactly the reasons this chapter cares about: a smaller model leaves more GPU memory for the KV cache (more concurrent sequences), and since decode is memory-bandwidth bound (3.1), moving fewer bytes per weight often makes the whole forward pass faster too, not just smaller.

None of that is free. Rounding to a coarser grid introduces error, and how much error depends entirely on how carefully you choose the scale. The naive version below picks one scale for an entire weight matrix (per-tensor, symmetric quantization) and quantizes a real matrix at three bit-widths, measuring the actual reconstruction error at each one:

Naive per-tensor quantization: memory savings vs. real error
import numpy as np rng = np.random.default_rng(42) W = rng.normal(0, 0.02, size=(4096, 4096)).astype(np.float32) # one real weight matrix def quantize(W, bits): qmax = 2 ** (bits - 1) - 1 scale = np.abs(W).max() / qmax q = np.round(W / scale).clip(-qmax - 1, qmax) return q * scale, scale # dequantized weights, and the scale used def report(name, bits, bytes_per_elem): dq, scale = quantize(W, bits) rel_err = np.abs(dq - W).mean() / np.abs(W).mean() size_mb = W.size * bytes_per_elem / (1024 ** 2) print(f"{name}: scale={scale:.6f} mean_rel_error={rel_err:.4f} size={size_mb:.1f}MB") report("fp16 (baseline)", 16, 2.0) report("int8 ", 8, 1.0) report("int4 ", 4, 0.5) fp16_mb, int8_mb, int4_mb = (W.size * b / (1024 ** 2) for b in (2.0, 1.0, 0.5)) print(f"Memory vs fp16: int8={fp16_mb/int8_mb:.1f}x smaller, int4={fp16_mb/int4_mb:.1f}x smaller")
fp16 (baseline): scale=0.000003 mean_rel_error=0.0001 size=32.0MB int8 : scale=0.000837 mean_rel_error=0.0131 size=16.0MB int4 : scale=0.015177 mean_rel_error=0.2378 size=8.0MB Memory vs fp16: int8=2.0x smaller, int4=4.0x smaller

int8 here is a modest, usually-safe 1.3% mean relative error — this is why int8 weight quantization is close to a default choice in production. int4 jumps to nearly 24% with this naive per-tensor approach, which is why nobody ships naive int4 in practice. Real int4 methods (GPTQ, AWQ, and similar) instead use a separate scale per small group of weights (e.g. every 128 values) and calibrate the scale against a small sample of real activations, which recovers most of that lost accuracy at the same 4-bit footprint. The honest summary: int8 is close to "free" (a real speed/memory win for a small, usually-imperceptible quality cost); int4 is a genuine trade-off that needs a smarter method and a quality check on your own task before you trust it in production.

📌
Weights vs. the KV cacheQuantization is usually discussed as "shrink the weights", but the KV cache from 3.3 can be quantized too (fp8 or int8 KV cache is common in serving engines) — and because the KV cache, not the weights, is often the binding memory constraint at long context or large batch, quantizing it can buy you more concurrent sequences than quantizing the weights does.
3.5 — What vLLM / TensorRT-LLM Actually Do Differently

Handed off to a naive serving loop, each sequence's KV cache is usually allocated as one contiguous block sized for the worst case — the model's maximum context length — because nobody knows in advance how long a given generation will actually run. Most requests finish far short of that maximum, so most of the reserved memory sits empty for the sequence's entire lifetime, and worse, it cannot be reused by anyone else because it is contiguous and reserved. This is the real memory-fragmentation problem PagedAttention (the core idea in vLLM) solves: instead of one big reservation, the KV cache is split into small fixed-size blocks (or "pages" — literally the same idea as OS virtual-memory paging), allocated to a sequence one block at a time as it actually grows, and returned to a shared pool the instant the sequence finishes. Non-contiguous physical blocks are stitched together with a per-sequence block table, exactly like a page table maps virtual addresses to physical frames.

Contiguous worst-case reservation vs. paged, grow-as-you-go allocation
naive contiguous (reserve MAX_SEQ_LEN per sequence, always):
  seq A [############----------------------------]  (used -- wasted)
  seq B [########------------------------------]
  seq C [##################################----]
                     ^ wasted space cannot be handed to anyone else

paged (16-token blocks, grow on demand, free on completion):
  seq A [#][#][#]                        <- 3 blocks, exactly what it has used
  seq B [#][#]                           <- 2 blocks
  seq C [#][#][#][#][#][#][#][#][#][#]   <- grows, one block at a time
  free pool: [ ][ ][ ][ ][ ]...           <- reclaimed the instant any sequence ends

The simplified allocator below is a real, runnable version of the same mechanism: it compares how many blocks a naive contiguous scheme must reserve up front for 40 sequences of unknown length, against the true peak concurrent usage a paged allocator would need (sequences growing and freeing blocks independently). This is the actual reason PagedAttention increases achievable batch size — not a faster attention kernel, a better memory allocator.

Toy paged KV-cache allocator vs. naive contiguous reservation
import numpy as np rng = np.random.default_rng(11) BLOCK = 16 # tokens per page (one "PagedAttention" block) MAX_SEQ_LEN = 512 # the worst case any single request could reach N = 40 actual_lengths = rng.integers(20, 400, size=N) # real, unknown-in-advance output lengths # --- naive contiguous allocation: reserve MAX_SEQ_LEN for every sequence up front --- naive_blocks_reserved = N * (-(-MAX_SEQ_LEN // BLOCK)) # ceil-div x N naive_blocks_used = sum(-(-int(L) // BLOCK) for L in actual_lengths) # --- paged allocation: grow one block at a time, free on completion --- paged_peak_concurrent = 0 for L in range(1, MAX_SEQ_LEN + 1): total_blocks_now = sum(-(-L // BLOCK) for seq_len in actual_lengths if L <= seq_len) paged_peak_concurrent = max(paged_peak_concurrent, total_blocks_now) waste_naive = 1 - naive_blocks_used / naive_blocks_reserved print(f"Naive contiguous: reserves {naive_blocks_reserved} blocks up front, actually needs {naive_blocks_used} -> {waste_naive:.1%} wasted") print(f"Paged allocator: peak concurrent usage is only {paged_peak_concurrent} blocks (grows/frees per sequence)") print(f"Memory headroom gained by paging: {naive_blocks_reserved / paged_peak_concurrent:.2f}x more sequences fit in the same memory")
Naive contiguous: reserves 1280 blocks up front, actually needs 579 -> 54.8% wasted Paged allocator: peak concurrent usage is only 338 blocks (grows/frees per sequence) Memory headroom gained by paging: 3.79x more sequences fit in the same memory

Put together with 3.2's continuous batching, this is the whole story of what a real serving engine (vLLM, TensorRT-LLM, TGI) does that a hand-rolled Hugging Face generate() loop does not: continuous, iteration-level admission of new sequences, plus paged, non-contiguous KV-cache memory management, plus (usually) a custom fused attention kernel that reads the paged block table directly. 3.6 — Latency vs. Throughput: A Genuine Trade-off

You already reason about p50/p95/p99 for ordinary services (sr01 § observability). The same percentiles matter here, but the lever that moves them is different: batch window size. A tiny window dispatches almost immediately, batches stay small, and if the arrival rate exceeds what small batches can drain, latency explodes from queueing (exactly what happened to "naive" in 3.1). A window that is too generous keeps every request waiting the full window even when the GPU could have started sooner, and keeps adding latency long after throughput has stopped improving. There is a real optimum, and it depends on your traffic, not a universal constant.

The sweep below runs the same simulator as 3.1/3.2 across five window sizes against one fixed, moderately loaded traffic pattern (mean arrival gap 4ms, so roughly 250 req/s of demand):

Sweeping batch window size: latency keeps rising, throughput plateaus
import numpy as np FIXED_MS, PER_TOK_MS, TOKENS, GROWTH, CAP = 8.0, 0.35, 24, 0.03, 32 def pass_cost_ms(batch_size): return FIXED_MS + PER_TOK_MS * TOKENS * (1 + GROWTH * (batch_size - 1)) def simulate(window_ms, mean_interarrival_ms=4.0, n=800, seed=5): rng = np.random.default_rng(seed) arrivals = np.cumsum(rng.exponential(mean_interarrival_ms, size=n)) latencies, i, gpu_free_at = np.zeros(n), 0, 0.0 while i < n: window_start = arrivals[i] j = i while j < n and arrivals[j] <= window_start + window_ms and (j - i) < CAP: j += 1 batch = arrivals[i:j] dispatch = max(window_start + window_ms, gpu_free_at, batch[-1]) finish = dispatch + pass_cost_ms(len(batch)) latencies[i:j] = finish - batch gpu_free_at = finish i = j p50, p95, p99 = np.percentile(latencies, [50, 95, 99]) throughput = n / (arrivals[-1] + latencies[-1]) * 1000.0 return p50, p95, p99, throughput print(f"{'window_ms':>10} {'p50_ms':>8} {'p95_ms':>8} {'p99_ms':>8} {'throughput':>12}") for w in [2, 8, 20, 50, 100]: p50, p95, p99, thpt = simulate(w) print(f"{w:>10} {p50:>8.1f} {p95:>8.1f} {p99:>8.1f} {thpt:>12.1f}")
window_ms p50_ms p95_ms p99_ms throughput 2 3001.1 5494.1 5756.5 91.4 8 732.6 1355.3 1421.1 181.8 20 29.9 38.2 38.7 266.3 50 47.4 69.7 70.7 267.5 100 74.3 121.8 123.7 260.2

Read this as two regimes. At 2ms and 8ms, the window is too small to form batches big enough to keep up with 250 req/s of demand — the server is overloaded, and both latency and (effective) throughput are bad; this is the same collapse as naive serving, just with training wheels on. Somewhere around 20ms the batch is finally big enough to comfortably clear the incoming rate, and latency drops off a cliff. Past that point (50ms, 100ms), throughput has essentially plateaued (the GPU is compute-saturated at its batch cap) while latency keeps climbing for no further benefit — pure waste. The right window is the smallest one that clears your load: bigger buys you nothing but tail latency.

The trade-off, stated precisely
  • Below the "just enough" window: both latency and throughput are bad (overload, not a trade-off).
  • At the "just enough" window: near-best latency AND near-peak throughput — this is usually the right operating point.
  • Above it: throughput is flat, latency keeps growing — a real trade-off with no upside past this point.
  • The "just enough" point depends on arrival rate, so it must be re-tuned (or auto-tuned) as traffic changes, not hardcoded once.
3.7 — Cost Optimization

Once throughput is measured in tokens/second, cost per token is one division away, and it makes the value of batching concrete in dollars instead of just percentiles. Reusing the two real, captured throughput numbers from section 3.1's benchmark:

Cost per 1M tokens: naive vs. windowed batching, on-demand vs. spot
on_demand_per_hr = 2.50 # one mid-range inference GPU, on-demand spot_per_hr = 0.90 # the same class of GPU, spot / preemptible # throughput figures captured from the real FastAPI benchmark in section 3.1 throughput_tok_s = {"naive (batch=1)": 1462.4, "windowed batching": 9857.0} for name, tok_s in throughput_tok_s.items(): tokens_per_hour = tok_s * 3600 cost_od = on_demand_per_hr / (tokens_per_hour / 1_000_000) cost_spot = spot_per_hr / (tokens_per_hour / 1_000_000) print(f"{name}: {tok_s:.0f} tok/s -> ${cost_od:.3f} per 1M tokens on-demand, ${cost_spot:.3f} on spot") naive_cost = on_demand_per_hr / (throughput_tok_s["naive (batch=1)"] * 3600 / 1_000_000) batch_cost = on_demand_per_hr / (throughput_tok_s["windowed batching"] * 3600 / 1_000_000) print(f"Batching cuts cost per 1M tokens by {naive_cost/batch_cost:.1f}x on the same GPU")
naive (batch=1): 1462 tok/s -> $0.475 per 1M tokens on-demand, $0.171 on spot windowed batching: 9857 tok/s -> $0.070 per 1M tokens on-demand, $0.025 on spot Batching cuts cost per 1M tokens by 6.7x on the same GPU

You already know spot/preemptible instances trade a reclaim risk for a large discount for stateless, restartable workloads. LLM serving complicates that trade a little: a request mid-generation on a reclaimed instance loses its KV cache and its partial output, so spot capacity is a genuinely good fit for batch/offline workloads (bulk summarization, embedding a large corpus, overnight evaluation runs — all restartable at the request level) and a much worse fit for interactive, user-facing chat traffic with a tight latency SLA, where a mid-response reclaim is a visible failure, not a retriable background job. A common real pattern: run the latency-sensitive tier on-demand (or reserved) with the smallest safe batch window from 3.6, and route batch/offline traffic to a separate, spot-backed pool with a large batch window tuned purely for throughput. This is also where the DevOps instinct to "autoscale on CPU" needs updating: the signal that matters for a GPU inference pool is queue depth (how many requests are waiting for a batch slot) and KV-cache headroom, not CPU utilization, which barely moves on a GPU-bound service — adv06 goes deeper on this at the platform-design level.

Question 1 of 5
Section 3.1's real benchmark showed windowed batching beating naive serving on BOTH throughput (6.7x) AND latency (p95 654.6ms → 101.8ms), not the classic "batching trades latency for throughput" story. What actually explains this?
Why: Naive's own per-request GPU time is tiny (about 16ms); its huge measured latency is almost entirely queueing behind the single-GPU lock at high concurrency. Batching serves ~13 requests per pass, draining the same load far faster, so the queue barely forms. Section 3.6 shows the more familiar trade-off (bigger window, more latency, flat throughput) once the server is no longer overloaded.
Question 2 of 5
A team switches a 7B-class model from full multi-head attention (32 KV heads) to grouped-query attention with 8 KV heads, everything else unchanged. What happens to KV-cache memory, and why?
Why: kv_cache_bytes = 2 x num_kv_heads x head_dim x dtype_bytes x num_layers x seq_len x batch_size — num_kv_heads appears as a direct linear factor, so cutting it from 32 to 8 cuts the cache by exactly that ratio (4x), independent of model size or sequence length, matching the worked example in 3.3.
Question 3 of 5
In section 3.2's slot-occupancy simulation, continuous batching finished the same 60 requests in 93 steps at 85.1% GPU utilization, while static batching took 154 steps at 51.4%. What is continuous batching actually doing differently?
Why: Static batching only admits new sequences once every slot in the current batch is empty, so a slot with a short sequence sits idle until the longest sequence in that batch finishes. Continuous batching refills a slot on the very next decode step after it frees, which is why it reaches far higher utilization and finishes sooner with the same GPU.
Question 4 of 5
What does PagedAttention (the core idea behind vLLM) actually change, compared to a naive Hugging Face-style serving loop?
Why: The attention math is exactly the same; what changes is the allocator. Reserving a worst-case contiguous block per sequence wastes most of that memory most of the time (3.5's simulation: 54.8% waste) and cannot be reclaimed early. Paged, block-based allocation grows and frees per sequence, which is why it fits more concurrent sequences in the same memory — a memory-management win, not an attention-algorithm win.
Question 5 of 5
A serving team has one GPU pool. Traffic is a mix of interactive chat (tight p95 SLA) and a nightly bulk-summarization job (no user waiting). Using this chapter's vocabulary, what is the best design?
Why: Mixing the two workloads in one pool forces a single batch-window choice that is wrong for at least one of them (3.6). Separating them lets each pool run at its own optimum: chat gets the smallest safe window (low tail latency) on stable capacity, and the bulk job gets a large window plus spot pricing (3.7) since a reclaim there is a cheap retry, not a user-visible failure. Quantization (3.4) is a separate, complementary lever, not a substitute for this design choice.
