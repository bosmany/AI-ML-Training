Concurrency & Performance

Mid-level engineers make code correct. Senior engineers make it correct under load, under failure and under a stopwatch. This chapter teaches the two skills that separate those levels: reasoning about many things happening at once (races, locks, queues, retries, the event loop, backpressure) and making programs faster by measurement instead of instinct (profilers, complexity, memory, and a disciplined optimise loop). Real threads cannot run in a browser, so you will use deterministic simulations that make every interleaving visible and repeatable.

2.1 — Concurrency vs Parallelism: Waiting vs Computing

Picture a service that builds a dashboard by calling three internal APIs. Each call spends 100 ms waiting on the network and almost no time computing. Called one after another, the page takes about 300 ms. Everyone on the team says "make it concurrent", and someone adds a thread pool. A month later a different endpoint, which hashes 50 MB of uploads, gets the same treatment. It does not get faster at all. Same fix, opposite result. The reason is that the two endpoints are limited by different things, and seniors ask "what is this program actually waiting for?" before they reach for any tool.

Concurrency is about *structure*: arranging a program so that many tasks are in progress at the same time, even if only one of them is executing at any instant. Parallelism is about *execution*: several tasks really running at the same instant on separate CPU cores. Concurrency needs a way to switch between tasks while one of them waits. Parallelism needs more than one core.

Here is the everyday picture. A single cook with three pots on the stove is concurrent: while the pasta water heats (waiting), the cook chops onions (working). One person, three dishes in flight, no extra speed from a second cook. Three cooks each chopping their own onions is parallel. Adding a second cook only helps when there is real chopping to do. For dishes that are mostly waiting for water to boil, one cook is enough.

That gives the vocabulary you will use for the rest of the chapter. A task is I/O-bound when most of its time is spent waiting (network, disk, database, another service). It is CPU-bound when most of its time is spent computing (hashing, parsing, image resizing, number crunching). Concurrency helps I/O-bound work because waits can overlap. Parallelism helps CPU-bound work because computation can be split across cores. Getting this match wrong is the most common concurrency mistake in code review.

We cannot start real threads inside a browser tab, and real thread timing is not repeatable anyway. So this chapter uses a deterministic simulation: tasks are strings where C is one tick of computing (needs a core) and W is one tick of waiting (needs no core). A tiny scheduler runs them tick by tick and prints a timeline. # means computing, . means waiting, and a space means "ready but no core free".

Tick-by-tick timeline: sequential vs concurrent
def simulate(tasks, cores=1, sequential=False): pos = [0] * len(tasks) rows = [''] * len(tasks) tick = 0 while any(pos[i] < len(tasks[i]) for i in range(len(tasks))): active = [i for i in range(len(tasks)) if pos[i] < len(tasks[i])] if sequential: active = active[:1] # only one task at a time used = 0 for i in range(len(tasks)): if i not in active: rows[i] += ' ' if pos[i] == 0 else '' elif tasks[i][pos[i]] == 'W': rows[i] += '.'; pos[i] += 1 # waiting needs no core elif used < cores: rows[i] += '#'; pos[i] += 1; used += 1 else: rows[i] += ' ' # ready, but no core free tick += 1 return tick, rows io_tasks = ['CWWWC', 'CWWWC', 'CWWWC'] for label, kw in [('sequential ', dict(sequential=True)), ('concurrent 1core', dict(cores=1))]: ticks, rows = simulate(io_tasks, **kw) print(f'{label}: {ticks} ticks') for name, row in zip('ABC', rows): print(f' {name} |{row}|')
Output (real Pyodide run)
sequential : 15 ticks A |#...#| B | #...#| C | #...#| concurrent 1core: 7 ticks A |#...#| B | #...#| C | #...#|

Read the output slowly. In the sequential run, task B does not even start until A has finished all five ticks, so the total is 15. In the concurrent run on one core, all three tasks are in flight. While A waits (.), B and C use the core. The core is only needed for the two C ticks at each end of a task, and each task is delayed by one or two ticks at the start while it queues for the core (the spaces). The three tasks finish in 7 ticks instead of 15. One core, no parallelism, a wall time more than halved. That is concurrency paying off on I/O-bound work.

  • The scheduler builds a list of unfinished tasks (active). In sequential mode it keeps only the first one.
  • For each task it looks at the next step. A W step always advances, because waiting needs no core.
  • A C step advances only if a core is still free this tick (used < cores). Otherwise the task stays put and shows a space.
  • One loop pass is one tick. The number of passes is the wall-clock time.

Now the sad path. Change the tasks to pure computing and give the scheduler more cores. The interesting comparison is one core versus several.

CPU-bound work: concurrency does not help, cores do
def ticks_for(tasks, cores): # simple ideal model: each core runs one 'C' tick per tick, tasks need only cores pos = [0] * len(tasks) tick = 0 while any(p < len(t) for p, t in zip(pos, tasks)): used = 0 for i, t in enumerate(tasks): if pos[i] < len(t) and used < cores: pos[i] += 1; used += 1 tick += 1 return tick cpu_tasks = ['CCCC', 'CCCC', 'CCCC'] for cores in (1, 2, 3): print(f'{cores} core(s): {ticks_for(cpu_tasks, cores)} ticks')
Output (real Pyodide run)
1 core(s): 12 ticks 2 core(s): 8 ticks 3 core(s): 4 ticks

With one core, interleaving three CPU-bound tasks still costs 12 ticks: there is one core's worth of work and nothing to overlap. Only extra cores reduce the wall time. Notice that two cores give 8 ticks, not 6: a task cannot be split across cores in this model, so with three tasks on two cores the third must wait for a free core and runs alone. Three cores give the full 4. This is why "just add threads" fails for the hashing endpoint. In CPython, threads have an extra handicap for CPU-bound Python code, which section 2.2 explains.

Common mistakeTreating "concurrent" and "parallel" as synonyms in a design review. If someone says "we made it concurrent, so it should be 4x faster on this 4-core box", ask whether the task waits or computes. If it computes, concurrency alone gives 1x.
Check yourself: A batch job resizes 10,000 images (each takes 20 ms of pure CPU) on a 4-core machine. Is it I/O-bound or CPU-bound, and what would a good speedup look like?
CPU-bound. Spreading the work over 4 cores (parallelism) can approach 4x in the best case, for example 200 s down to about 50 s. Overlapping waits (concurrency) gives nothing because there are no waits.

Recap
  • Concurrency overlaps waiting; parallelism uses several cores at once. They are different tools for different bottlenecks.
  • First question for any slow program: is it I/O-bound or CPU-bound?
  • Concurrency on CPU-bound work gives no speedup; more workers than waits also gives none.
  • A deterministic tick simulation makes scheduling behaviour visible and repeatable, and the rest of this chapter uses it.
2.2 — The GIL: What It Does, What It Does Not Do

A teammate runs a CPU-heavy function in four threads on a four-core laptop and reports "threads made it slower". Another teammate says "Python has a GIL, so threads are useless." Both statements are half right, and acting on the wrong half causes real bugs. Below is the experiment with real threads. It cannot run in your browser tab, so it is a reference block: the output was captured from a real CPython 3.12 run on a multi-core Linux machine.

⚠️
Reference-only blockReal threading and multiprocessing cannot start inside the browser (you will see the exact error in a moment). The code is shown with a real captured run. Your own timings will differ, but the shape of the result (CPU-bound threads about 1x, I/O-bound threads about Nx) will not.
Real threads: CPU-bound vs I/O-bound (captured output)reference only
import threading, time def burn(n): # pure-Python CPU work total = 0 for i in range(n): total += i * i return total def run_threads(target, args, count=4): threads = [threading.Thread(target=target, args=args) for _ in range(count)] t0 = time.perf_counter() for t in threads: t.start() for t in threads: t.join() return time.perf_counter() - t0 def sequential(target, args, count=4): t0 = time.perf_counter() for _ in range(count): target(*args) return time.perf_counter() - t0 cpu_seq = sequential(burn, (2_000_000,)) cpu_thr = run_threads(burn, (2_000_000,)) io_seq = sequential(time.sleep, (0.2,)) io_thr = run_threads(time.sleep, (0.2,)) print(f"CPU-bound: sequential {cpu_seq:.2f}s, 4 threads {cpu_thr:.2f}s, speedup {cpu_seq/cpu_thr:.2f}x") print(f"I/O-bound: sequential {io_seq:.2f}s, 4 threads {io_thr:.2f}s, speedup {io_seq/io_thr:.2f}x")
Real output captured on this machine (CPython 3.12.3, Linux)
CPU-bound: sequential 0.27s, 4 threads 0.26s, speedup 1.03x I/O-bound: sequential 0.80s, 4 threads 0.20s, speedup 3.95x

Four threads doing pure-Python computation finished no sooner than the same work done sequentially (a speedup near 1x, sometimes below it), while four threads that wait finished about four times faster. That pattern is the GIL at work.

The idea

The Global Interpreter Lock (GIL) is a mutex inside CPython, the standard Python interpreter. A mutex is a lock that only one holder can own at a time. Before a thread may execute Python bytecode it must own the GIL, so at any instant only one thread is running Python code, whatever the number of cores. CPython has this lock because its memory management (reference counting, where every object counts how many names point at it) is not thread-safe on its own. One big lock made the interpreter and its C extensions simple and fast in the single-threaded case.

The analogy is a shared microphone at a meeting. Many people can be in the room (many threads), but only the person holding the microphone can speak (run Python). Holding it while waiting for an answer would be wasteful, so a thread that starts a blocking operation such as reading a socket, sleeping, or waiting on a file hands the microphone back. That is why the I/O-bound half of the experiment scaled: sleeping threads do not hold the GIL. Long computations inside C libraries such as numpy or hashlib also release it, so those can use several cores from threads.

A thread that keeps running Python bytecode does not hold the lock forever. CPython asks it to give the lock up after a switch interval, 5 milliseconds by default, so other threads get a turn. You can read it, and you can also see that the browser cannot start real threads:

What the GIL does not do

This is the misconception that causes production incidents: the GIL does not make your code thread-safe. It guarantees that the interpreter's own data structures stay consistent (two threads cannot corrupt a list's internals). It says nothing about *your* invariants. A thread can lose the GIL between any two bytecode instructions, and most useful operations are several instructions. Ask Python to show you the instructions behind counter += 1:

One line of Python is several steps
import dis counter = 0 def bump(): global counter counter += 1 steps = [i.opname for i in dis.get_instructions(bump) if i.opname not in ('RESUME', 'RETURN_CONST', 'RETURN_VALUE')] print(steps) print('steps that touch the shared value:', len(steps))
Output (real Pyodide run)
['LOAD_GLOBAL', 'LOAD_CONST', 'BINARY_OP', 'STORE_GLOBAL'] steps that touch the shared value: 4

Read it as: load the current value, load 1, add, store the result. If thread A loads 5, loses the GIL, thread B loads 5 and stores 6, then A resumes and stores its own 6, one increment vanished. The GIL never prevented that because the lock was legitimately handed over between two instructions. Section 2.4 reproduces exactly this, deterministically.

  • Load: the thread reads counter (5) into its private evaluation stack.
  • Compute: it adds 1 on its private stack (6). Nothing shared has changed yet.
  • Switch: after the switch interval, the interpreter may pause this thread and let another one run.
  • Store: when it resumes, it writes its stale 6 over whatever the other thread stored.

Free-threaded Python (3.13 and later)

CPython 3.13 shipped an optional free-threaded build in which the GIL is disabled (PEP 703). It is a separate build (official installers offer it as an option; on Linux distributions it usually appears as a separate executable such as python3.13t), not a runtime switch on the normal build. You can check what you have with sys._is_gil_enabled() (added in 3.13), or sysconfig.get_config_var("Py_GIL_DISABLED"), and free-threaded builds can still be run with the GIL turned on via PYTHON_GIL=1 or -X gil=1. In 3.13 the free-threaded build was experimental. PEP 779 set the criteria for promoting it, and from Python 3.14 the free-threaded build is officially supported but still optional; making it the default is a separate, later decision.

Two caveats matter for planning. First, single-threaded code runs somewhat slower on the free-threaded build (the CPython docs quote an average overhead of roughly 1 to 8 percent depending on platform). Second, an extension module that has not declared support for free threading can make the interpreter re-enable the GIL when you import it, with a warning. The larger lesson is the one above: removing the GIL removes a safety net that was hiding your own races, never one that made them impossible. Code that is correct only "because of the GIL" gets *more* fragile, so learn the locking habits in this chapter regardless of which build you run.

Recap
  • The GIL lets one thread run Python bytecode at a time; it is released during blocking I/O and in many C libraries.
  • CPU-bound pure-Python threads do not scale; I/O-bound threads do; processes sidestep the GIL at the cost of copying data.
  • The GIL protects the interpreter's internals, not your invariants: x += 1 is several steps.
  • Free-threaded builds (3.13 experimental, 3.14 supported, optional) remove the lock but not the need for locks in your own code.
2.3 — Threads vs Processes vs asyncio: A Decision Table

A design review asks: "the nightly job calls 2,000 partner endpoints, unpacks each response, and hashes the payload. Threads, processes or asyncio?" The junior answer is whichever one the engineer used last time. The senior answer starts with two measurements (how long does one task wait, and how long does it compute?) and ends with a table. This section gives you the table and the reasons behind each row, so you can defend the choice instead of recalling it.

The three tools differ in who decides when to switch tasks and what each task costs. A thread is an operating-system unit of execution inside one process. The OS pauses and resumes threads whenever it likes (pre-emptive scheduling), and every thread shares the process's memory. A process is a separate program instance with its own memory and its own GIL, so processes run on different cores at once, but data must be copied between them (serialised, in Python by pickling). A coroutine under asyncio is a function that can pause itself at an await. One thread runs them all, and a task only yields control when it chooses to (cooperative scheduling).

To make the trade-offs concrete, here is a toy cost model. It is deliberately simple: tasks wait io milliseconds then compute cpu milliseconds; threads overlap waits but the GIL serialises compute; processes spread compute across cores but pay start-up and copying cost; asyncio overlaps every wait but computes on one thread. The numbers are invented, but the ranking they produce is the real one.

A toy wall-time model for the three tools
import math def wall_ms(strategy, n, io, cpu, cores=4, workers=8): """n tasks, each waits `io` ms then computes `cpu` ms.""" if strategy == 'sequential': return n * (io + cpu) if strategy == 'threads': # waits overlap; GIL serialises compute return math.ceil(n / workers) * io + n * cpu if strategy == 'processes': # compute spreads over cores; pay overhead w = min(workers, cores) return math.ceil(n / w) * (io + cpu) + 40 + 2 * n if strategy == 'asyncio': # all waits overlap; compute is serial return io + n * cpu raise ValueError(strategy) workloads = { 'call 100 APIs (io=100, cpu=1)': (100, 100, 1), 'hash 100 files (io=1, cpu=100)': (100, 1, 100), 'mixed (io=50, cpu=50)': (100, 50, 50), } for name, (n, io, cpu) in workloads.items(): print(name) for s in ('sequential', 'threads', 'processes', 'asyncio'): print(f' {s:<10} {wall_ms(s, n, io, cpu):>7} ms')

Recap
  • Choose by the task's profile: waits go to asyncio or threads, pure-Python compute goes to processes, array maths goes to numpy.

  • Every option needs a limit (pool size, semaphore) tied to what the downstream system can handle.

2.4 — Race Conditions and Check-Then-Act Bugs

Two requests arrive at the same moment to reserve the last seat on a flight. Each handler runs if seats > 0: seats -= 1. Both see one seat, both proceed, and the flight is now sold at -1. The code is correct for every single request in isolation, it passes every unit test, and it fails only under load, once in a while, with no stack trace. That is a race condition: the result depends on the relative timing of operations that the programmer assumed would not overlap.

The pattern behind most races is check-then-act: you check a condition, and then you act on it, but the world can change between the two steps, so you act on stale information. The same shape appears as read-modify-write (x = x + 1), "if the file does not exist, create it", "if the row is missing, insert it", and "if the cache has no entry, compute and store one".

Analogy: two people editing the same paragraph in a shared document, each having downloaded a copy. Both change the paragraph, both upload, and the second upload silently overwrites the first. Nobody made a mistake with their own copy; the mistake is that the read and the write were not one indivisible step.

Real threads make this hard to study, because the bad interleaving might happen once in a million runs. So we take control of the timing. Each simulated thread is a Python generator: a function that pauses at every yield. A yield marks a place where a real thread could be pre-empted. A schedule such as 'ABAB' says who runs the next step. Now the interleaving is an input, not luck.

Lost update: two increments, two schedules

The bad interleaving ABAB, step by step
   time ->        1            2            3            4
   thread A    read n (0)                write n = 1
   thread B                  read n (0)                write n = 1
   shared n        0            0            1            1     expected 2
                   ^ both threads hold the same stale copy of 0
  • Schedule AABB runs A completely, then B completely. B reads 1 and writes 2. Correct.
  • Schedule ABAB lets A read 0, then B read 0 (a stale value, because A has not written yet).
  • A writes 1. Then B writes 1, overwriting A's result. Two increments happened; the counter moved once. This is a lost update.
  • Nothing crashed and nothing raised. Races corrupt data silently, which is why they are expensive.

How likely is the bad ordering? Instead of guessing, enumerate every possible interleaving and count the outcomes. This is what model checkers do, and it is a great habit for reasoning about small critical sections.

A bug that fails in 4 of 6 abstract orderings is a bug, however rarely you observe it.

Check-then-act in the seat example

Now the seat reservation. The broken buyer checks in step 1 and acts in step 2. The fixed buyer does both in a single step, which is what a lock (next section) or an atomic database statement such as UPDATE seats SET n = n - 1 WHERE n > 0 gives you.

The last seat: broken and fixed
from itertools import permutations from collections import Counter def buyer(store, atomic): if atomic: if store['seats'] > 0: # check and act: ONE step store['seats'] -= 1 yield else: ok = store['seats'] > 0 # step 1: check yield if ok: store['seats'] -= 1 # step 2: act on a stale answer yield def explore(atomic): steps = 1 if atomic else 2 results = Counter() for sched in set(permutations('A' * steps + 'B' * steps)): store = {'seats': 1} gens = {'A': buyer(store, atomic), 'B': buyer(store, atomic)} for who in sched: next(gens[who]) results[store['seats']] += 1 return dict(sorted(results.items())) print('broken (check, then act):', explore(atomic=False)) print('fixed (one atomic step):', explore(atomic=True))

The keys are the final seat counts and the values are how many orderings ended there. The broken version can end at -1 (oversold); the fixed version never does. In the fixed version, the second buyer sees 0 seats and correctly gets nothing.

The same bug with a different symptom

Not every check-then-act bug oversells. Sometimes the stale check produces an exception. Two cleanup jobs both check whether an order exists and delete it. Both see it, the first deletes it, and the second one crashes.

2.5 — Locks, Deadlock and Lock Ordering

Section 2.4 ended with "make check and act one indivisible step". The standard tool for that is a lock (also called a mutex, short for mutual exclusion): an object that at most one thread can hold at a time. Code between acquiring and releasing it is a critical section, and while one thread is inside, every other thread that wants the lock waits. A lock turns a multi-step operation into something that behaves like a single step, as far as other lock-holders can tell.

Locks fix races and create a new class of bug. Suppose a payments service moves money between two accounts and, to be safe, locks both. Thread A transfers from account X to account Y, so it locks X and then Y. At the same moment thread B transfers from Y to X, so it locks Y and then X. A holds X and waits for Y. B holds Y and waits for X. Neither can ever proceed, and neither will ever release what it holds. This is a deadlock, and it is quiet: no exception, no log line, just requests that never return.

The analogy is two cars on a one-lane bridge meeting in the middle, each waiting for the other to reverse. Deadlock needs four ingredients (the Coffman conditions): mutual exclusion (locks are exclusive), hold-and-wait (a thread keeps what it has while asking for more), no pre-emption (you cannot take a lock away from its holder), and circular wait (a cycle of threads each waiting for the next). Remove any one and deadlock is impossible. The practical one to remove is circular wait.

A wait-for cycle
     Thread A  --- holds --->  Lock X
        |                        ^
     wants                     wants
        v                        |
     Lock Y   <--- holds ---  Thread B

   A waits for B (who holds Y), B waits for A (who holds X):
   the arrows form a cycle, so neither thread can ever continue.

First, the basic behaviour of a lock, using the real threading.Lock. Locks work fine in a browser, because a single thread is enough to observe how they behave: acquire(blocking=False) returns immediately with True or False instead of waiting.

What a lock does when it is already held
import threading lock = threading.Lock() print('first acquire :', lock.acquire(blocking=False)) print('second acquire :', lock.acquire(blocking=False)) # already held print('with timeout :', lock.acquire(timeout=0.01)) # waits 10 ms, gives up lock.release() try: lock.release() # releasing twice except RuntimeError as e: print('RuntimeError:', e) rlock = threading.RLock() # re-entrant lock print('RLock twice by same thread:', rlock.acquire(), rlock.acquire()) try: with lock: raise ValueError('boom') except ValueError: pass print('locked after an exception inside `with`?', lock.locked())
Output (real Pyodide run)
first acquire : True second acquire : False with timeout : False RuntimeError: release unlocked lock RLock twice by same thread: True True locked after an exception inside `with`? False

Four lessons are hiding in that output. A plain Lock is not re-entrant: the same thread asking twice would wait forever for itself (the second acquire returned False only because we asked for non-blocking). An RLock lets the owning thread re-acquire. Releasing an unheld lock raises RuntimeError: release unlocked lock. And with lock: releases even when the body raises, which is why you should almost never call acquire() and release() by hand: an exception between them leaves the lock held forever, and every later caller freezes.

To watch a deadlock without hanging your browser, we use a small kernel. Each simulated thread is a generator that yields one request at a time: ('acquire', 'X') or ('release', 'X'). The kernel follows a schedule; if the thread whose turn it is asks for a lock somebody else holds, that thread is blocked and loses the turn. After the schedule ends, if every unfinished thread is blocked, that is a deadlock.

A deadlock, caught in the act
def transfer(first, second): yield ('acquire', first) yield ('acquire', second) yield ('release', second) yield ('release', first) def run(programs, schedule): pending = {n: next(g) for n, g in programs.items()} owner, done, trace = {}, set(), [] for who in schedule: if who in done: continue op, lock = pending[who] if op == 'acquire': if lock in owner: continue # blocked, loses the turn owner[lock] = who else: del owner[lock] trace.append(f'{who} {op} {lock}') try: pending[who] = next(programs[who]) except StopIteration: done.add(who) left = [n for n in programs if n not in done] blocked = {n: pending[n][1] for n in left if pending[n][0] == 'acquire' and pending[n][1] in owner} return (bool(left) and len(blocked) == len(left)), trace, blocked, owner programs = {'A': transfer('X', 'Y'), 'B': transfer('Y', 'X')} # opposite order dead, trace, blocked, owner = run(programs, 'ABABABAB') print('deadlock:', dead) print('trace :', trace) print('waiting :', blocked, ' holding:', owner)
Output (real Pyodide run)
deadlock: True trace : ['A acquire X', 'B acquire Y'] waiting : {'A': 'Y', 'B': 'X'} holding: {'X': 'A', 'Y': 'B'}
  • A acquires X (turn 1). B acquires Y (turn 2). Both first locks are taken.
  • A wants Y, but B holds it, so A is blocked. B wants X, but A holds it, so B is blocked.
  • Every remaining turn is skipped. The waiting dictionary is the wait-for cycle from the diagram: A wants Y (held by B), B wants X (held by A).

Did the schedule cause this, or the code? Both, and the distinction matters. A different schedule, such as all of A and then all of B, never deadlocks. The bug lives in the code (two paths taking the same locks in opposite orders), and the schedule is just the trigger. So we ask the kernel about all 256 schedules of length 8, and compare the original with the fix.

The fix: a global lock order

If every thread acquires locks in the same global order, a cycle cannot form: a cycle would need some thread to hold a "later" lock while waiting for an "earlier" one, and the rule forbids that. In code the rule is small: sort the locks before taking them, using a stable key such as an account id. It requires no cleverness, only discipline, plus a comment that says why.

Lock ordering removes the cycle
from itertools import product def transfer(first, second, ordered): if ordered: first, second = sorted((first, second)) # the whole fix yield ('acquire', first) yield ('acquire', second) yield ('release', second) yield ('release', first) def deadlocked(ordered, schedule): progs = {'A': transfer('X', 'Y', ordered), 'B': transfer('Y', 'X', ordered)} pending = {n: next(g) for n, g in progs.items()} owner, done = {}, set() for who in schedule: if who in done: continue op, lock = pending[who] if op == 'acquire': if lock in owner: continue owner[lock] = who else: del owner[lock] try: pending[who] = next(progs[who]) except StopIteration: done.add(who) left = [n for n in progs if n not in done] return bool(left) and all(pending[n][0] == 'acquire' and pending[n][1] in owner for n in left) for ordered in (False, True): bad = sum(deadlocked(ordered, s) for s in product('AB', repeat=8)) print('ordered' if ordered else 'unordered', '-> deadlocks in 256 schedules:', bad)
Output (real Pyodide run)
unordered -> deadlocks in 256 schedules: 128 ordered -> deadlocks in 256 schedules: 0

Half of all schedules deadlock the unordered version, and none deadlock the ordered one. That is a proof by exhaustion for this small case, which is far stronger than "ran it 100 times and it was fine".

Other defences and habits

  • Keep critical sections short. Do the slow work (network calls, disk, heavy computation) outside the lock; hold it only to read and update shared state. A lock held during a 2-second HTTP call serialises every caller behind that call.
  • Never call unknown code while holding a lock. A callback might take another lock in the wrong order or wait on you.
  • Use timeouts as a safety net. lock.acquire(timeout=5) turns "hang forever" into an error you can log and alert on. It does not fix the design, but it makes deadlocks visible.
  • Prefer not sharing. A queue (next section), an immutable snapshot or per-thread data with a final merge removes whole categories of locking.
  • Beware the cousins. Livelock: threads keep reacting to each other and make no progress (two people stepping aside in a corridor forever). Starvation: one thread never gets the lock because others keep winning it. Both are cured by design (ordering, fairness, backoff with jitter), not by more locks.

2.6 — Queues and the Producer–Consumer Pattern

After section 2.5 you might conclude that concurrency means locks everywhere. Seniors conclude the opposite: the best lock is the one you do not need. A common way to avoid sharing is to stop passing *shared variables* between workers and pass *messages* instead. The tool is the queue: a first-in, first-out line where one side puts items in and the other side takes them out. A well-built queue does its own locking internally, so the workers on either side never touch each other's data.

The problem it solves shows up in any pipeline. A web handler receives uploads faster than a worker can resize them. If the handler calls the resizer directly, the request waits for it. If it appends to a shared list that a worker polls, you need a lock, a polling loop with sleep, and a way to shut down. A queue gives all three in one object. This is the producer–consumer pattern: producers create work items, consumers process them, and the queue between them absorbs bursts and lets each side run at its own pace.

Analogy: the ticket rail in a restaurant kitchen. Waiters (producers) clip tickets on the rail and walk away. Cooks (consumers) take the oldest ticket when they are free. Waiters never wait for a particular cook, and cooks never hunt for orders. If the rail fills up, waiters have to slow down, and that will be section 2.10.

Producer-consumer pipeline
   producers                 queue (FIFO)                 consumers
   +----------+        +---+---+---+---+---+---+        +-----------+
   | P1 web   |--put-->| j1| j2| j3| j4| j5| j6 |--get-->| C1 worker |
   | P2 cron  |--put-->+---+---+---+---+---+---+--get-->| C2 worker |
   +----------+          ^ maxsize bounds this           +-----------+
                         | full: put() blocks or fails
   shutdown: one sentinel (None) per consumer ->  [..., None, None]

Python's queue.Queue is the thread-safe standard-library version. Its behaviour can be observed from a single thread, so here is the whole API in a browser-safe block. Watch the two exceptions: Empty when you ask a queue with nothing in it for an item without waiting, and Full when you put into a bounded queue that has no room.

The queue.Queue API in one thread
import queue q = queue.Queue(maxsize=2) q.put('a'); q.put('b') print('size:', q.qsize(), '| full:', q.full()) try: q.put_nowait('c') # no room, and we refuse to wait except queue.Full as e: print('Full raised:', type(e).__name__) print('get:', q.get(), q.get()) # first in, first out try: q.get_nowait() except queue.Empty as e: print('Empty raised:', type(e).__name__) # task_done / join: how a queue knows the WORK is finished, not just taken q2 = queue.Queue() for n in range(3): q2.put(n) for _ in range(3): item = q2.get() if item != 1: # forgot task_done() for item 1 q2.task_done() print('unfinished tasks:', q2.unfinished_tasks)
Output (real Pyodide run)
size: 2 | full: True Full raised: Full get: a b Empty raised: Empty unfinished tasks: 1

The last two lines show the classic bug. get() removes an item, but task_done() is what tells the queue that the work on it is complete. queue.join() blocks until every item has been marked done. If a consumer skips task_done() (often because an exception happened first), join() waits forever. The safe pattern is try: process(item) finally: q.task_done().

Now the pattern in motion. The simulation below has one producer and two consumers, each advancing one step per turn, so the scheduling is fully deterministic. A None sentinel (sometimes called a poison pill) tells a consumer "there is no more work, exit". You need one sentinel per consumer.

Producer and two consumers, with sentinels
from collections import deque q = deque() log = [] def producer(jobs, consumers): for j in jobs: q.append(j) log.append(f'P put {j}') yield for _ in range(consumers): q.append(None) # one sentinel per consumer log.append('P put STOP') yield def consumer(name): while True: if not q: yield # empty: wait one turn continue job = q.popleft() if job is None: log.append(f'{name} stops') return log.append(f'{name} starts {job}') yield # working takes a turn log.append(f'{name} finishes {job}') yield actors = [producer(['j1', 'j2', 'j3', 'j4'], 2), consumer('C1'), consumer('C2')] while actors: for a in list(actors): try: next(a) except StopIteration: actors.remove(a) print('\n'.join(log))
Output (real Pyodide run)

  • Each round gives every actor one turn: the producer puts one item, then C1, then C2 each try to take one. Handling a job takes one turn, so while C1 is busy with j1, C2 picks up j2.
  • C1 and C2 split the jobs between them without either knowing the other exists. Neither touches the other's data; the queue is the only shared thing.
  • After the four jobs the producer puts two STOP markers, one for each consumer, and each consumer exits when it reads one.
  • If the producer put only one sentinel, the second consumer would wait on an empty queue forever. That hang is the most common shutdown bug.

The same pattern with asyncio

Coroutines use the same shape with asyncio.Queue. The difference is that await queue.get() pauses the coroutine instead of blocking a thread. Top-level await works in this page's Python, so no asyncio.run is needed. The workers loop forever, so the main code waits with queue.join() and then cancels them.

That "every item exactly once" property is what the queue gives you inside one process. Across machines (SQS, RabbitMQ, Kafka) the guarantee usually weakens to "at least once", which is why the next section is about idempotency.

2.7 — Idempotency and Retries

A checkout service calls a payment provider. The provider charges the card, but the network drops the response. The service sees a timeout. Did the charge happen? It cannot know: the request might have been lost before arriving, or processed and its answer lost on the way back. From the caller's side both look identical. If it retries, it might charge twice. If it gives up, it might have taken money for nothing. Every distributed system faces this ambiguity, and the answer is the same everywhere: make the operation safe to repeat, then retry freely.

An operation is idempotent if doing it several times leaves the world in the same state as doing it once. "Set the address to X" is idempotent. "Add 10 to the balance" is not. The HTTP methods PUT and DELETE are defined as idempotent, POST is not (chapter SF 1 covered why). For operations that are naturally non-idempotent, such as charging a card or creating an order, you make them idempotent with an idempotency key: a unique token that the client generates once per logical operation and sends with every attempt. The server remembers the result for each key and returns it again instead of repeating the work.

Analogy: a numbered ticket at a bakery. If you wave your ticket a second time because you are unsure the clerk heard you, the clerk looks at the number, sees your order is already being handled, and does not bake another loaf.

First, see the failure. A scripted flaky network drops the response on the first attempt (the server did the work, the client never hears back), so the naive client retries.

Naive retry charges twice

Two details make this production-grade rather than a toy. First, store a fingerprint of the request next to the key and reject a reuse with different content, because that is a client bug you want to hear about. Second, the "have I seen this key?" step is itself a check-then-act. Two retries arriving at the same instant can both see the key missing and both charge. In a real system the key insertion must be atomic: a unique constraint in the database (INSERT ... ON CONFLICT DO NOTHING, then read the winner), or a lock, done before the work starts. Keys also need an expiry, so the store does not grow forever.

Retrying well

Idempotency makes a retry safe. It does not make it wise. Three rules keep retries from making an outage worse. Retry only transient failures (timeouts, connection resets, HTTP 429, 502, 503, 504), never permanent ones (400, 401, 403, 404, 422), because repeating a wrong request just fails again. Wait between attempts with exponential backoff (the delay doubles each time up to a cap). And add jitter (randomness) so that a thousand clients that failed together do not all retry together.

Backoff with jitter, on a virtual clock
import random def delays(attempts, base=0.1, cap=2.0, jitter=True, rng=None): out = [] for n in range(attempts): ceiling = min(cap, base * 2 ** n) # 0.1, 0.2, 0.4, 0.8, 1.6, 2.0 ... out.append(rng.uniform(0, ceiling) if jitter else ceiling) return out print('no jitter :', [round(d, 2) for d in delays(6, jitter=False)]) print('jittered :', [round(d, 2) for d in delays(6, rng=random.Random(7))]) # 100 clients fail at t=0 and retry after their first backoff def retry_times(jitter, seed=1): rng = random.Random(seed) return [delays(1, base=1.0, jitter=jitter, rng=rng)[0] for _ in range(100)] for jitter in (False, True): times = retry_times(jitter) buckets = {} for t in times: buckets[int(t * 10)] = buckets.get(int(t * 10), 0) + 1 # 100 ms buckets print('jitter' if jitter else 'no jitter', '-> busiest 100 ms bucket:', max(buckets.values()), 'of 100 retries')
Output (real Pyodide run)

Without jitter all 100 clients come back at the same instant: a thundering herd, which can knock a recovering service over again. With jitter the retries spread across the whole window and the busiest 100 ms slice holds 16 of the 100 retries instead of all of them.

Retries multiply

The most expensive retry bug is invisible in any single service. If each layer makes up to 3 attempts (the first try plus 2 retries), a failure at the bottom is attempted 3 x 3 x 3 = 27 times when three services are stacked. At the moment the bottom service is weakest, it is hit with the most traffic. Seniors limit retries to one layer (usually the outermost or the one closest to the failing call), cap the total with a retry budget (for example "at most 10% extra requests"), and set a deadline on the whole operation.

2.8 — asyncio Internals: The Event Loop, Tasks and await

Most mid-level engineers can write async def and await, and many have shipped an asyncio service. The ones who get paged at night are usually the ones who never learned what the machinery underneath actually does. Symptoms: "the whole service froze while one request was slow", "my background job never ran", "why is it not faster with await?". All three have one root cause, which is a misunderstanding of what await does.

A coroutine is a function defined with async def. Calling it does not run it; it returns a coroutine object, a paused computation. The event loop is a scheduler running in one thread. It keeps a ready queue of tasks that can run right now and a heap of timers for tasks that are sleeping, and it asks the operating system which sockets are ready. A task wraps a coroutine and registers it with the loop. await something means: "if something is not finished, pause me, let the loop run other tasks, and resume me when it is". That pause is the only moment other tasks get to run.

Analogy: one waiter serving twenty tables. The waiter never stands beside a table waiting for the kitchen (that would freeze the room). He takes an order, goes to the next table, and returns when the kitchen rings the bell. But if he decides to personally chop an onion for five minutes, every table waits, because there is only one waiter.

One turn of the event loop
        +---------------------------------------------------------------+
        |                      while running:                           |
        |  1. run every callback in the READY queue (each task runs     |
        |     until its next `await` that has to wait, then pauses)     |
        |  2. find the earliest TIMER (sleep, timeout): how long to wait |
        |  3. ask the OS: which sockets are ready? (wait up to step 2)  |
        |  4. move finished I/O and expired timers into the READY queue |
        +---------------------------------------------------------------+
                                     v repeat
   a task that never reaches an `await` (a blocking call) freezes steps 1-4

The best way to demystify a loop is to write a toy one. Below, each task is a generator that yields ('sleep', seconds), which plays the role of await asyncio.sleep(seconds). The loop uses a heap of (wake-up time, task) pairs and a virtual clock that jumps straight to the next wake-up. A real loop does the same, except that it really waits, and it also watches sockets.

A 15-line event loop
import heapq now = [0] def task(name, steps, delay): for i in range(steps): print(f't={now[0]:>2} {name} step {i}') yield delay # like: await asyncio.sleep(delay) def run(tasks): heap, n = [], 0 for t in tasks: heapq.heappush(heap, (0, n, t)); n += 1 while heap: when, _, t = heapq.heappop(heap) # earliest wake-up first now[0] = when # jump the virtual clock try: delay = next(t) # run until the next await except StopIteration: continue # task finished heapq.heappush(heap, (when + delay, n, t)); n += 1 run([task('A', 3, 2), task('B', 2, 3)]) print('total virtual time:', now[0])
Output (real Pyodide run)
t= 0 A step 0 t= 0 B step 0 t= 2 A step 1 t= 3 B step 1 t= 4 A step 2 total virtual time: 6
  • At t=0 both tasks start. A prints, then yields "wake me in 2". B prints, then yields "wake me in 3".
  • The loop pops the earliest wake-up: A at t=2, then B at t=3, then A at t=4, and so on. It never busy-waits; the clock simply jumps.
  • Nothing runs in parallel. The tasks interleave only at their yield (in real code, await) points.
  • Total time is 6, not the 12 that running them one after another would need. That is the whole benefit of asyncio for waiting workloads.

Now the real thing, under the real loop of this page. First: does await alone give concurrency? No. Awaiting coroutines one after another runs them one after another. Concurrency appears only when several tasks exist at the same time, for example through asyncio.gather or asyncio.create_task. Each job below yields to the loop with await asyncio.sleep(0) ("let others run, then resume me"), which makes the interleaving deterministic.

await in sequence vs gather

Coroutine, task, and the two classic mistakes

A bare coroutine object does nothing until something awaits it or wraps it in a task. asyncio.create_task(coro) schedules the coroutine on the loop right away, and the task starts running the next time the current one pauses. Two mistakes follow from this, and both come with real messages. The first is calling asyncio.run() from code that is already inside a running loop (typical in notebooks and in this browser page): it refuses.

Two real asyncio mistakes
import asyncio, inspect async def fetch(): await asyncio.sleep(0.01) return 'data' c = fetch() # the call did NOT run the body print('calling fetch() gives a', type(c).__name__, '- done?', inspect.getcoroutinestate(c)) c.close() # tidy up so Python does not warn coro = fetch() try: asyncio.run(coro) # illegal inside a running loop except RuntimeError as e: print('RuntimeError:', e) coro.close() t = asyncio.create_task(fetch()) # scheduled now, runs at our next await print('task done right after create_task?', t.done()) print('awaited result:', await t, '| done:', t.done())
Output (real Pyodide run)

The second classic mistake is not shown as a run because it is silent: writing fetch() without await in normal code means the body never runs, and Python only complains later with RuntimeWarning: coroutine 'fetch' was never awaited. Treat that warning as an error in your test suite. A related trap: keep a reference to any task you create with create_task. The loop holds tasks only weakly, so a task nobody references can be garbage-collected before it finishes.

Where control really changes hands

One more fact separates people who understand asyncio from people who use it. await does not always yield. If the awaited thing is already finished, or is a coroutine that never actually waits on anything, the loop is never given control. Awaiting a pure-computation coroutine ten thousand times is just a function call ten thousand times, and no other task runs meanwhile. Only real suspension points (asyncio.sleep, network reads, queue.get() on an empty queue, lock.acquire() under contention, await asyncio.sleep(0)) hand the loop back. This is why long CPU loops in async code freeze everything, which section 2.9 demonstrates.

Check yourself: Three await fetch() calls in a row, each waiting 100 ms. Roughly how long does it take, and what is the smallest change that makes it about 100 ms?
About 300 ms, because each await finishes before the next starts. Wrap them so they run together: await asyncio.gather(fetch(), fetch(), fetch()) (or three create_task calls followed by awaiting each).
Check yourself: Can two coroutines in one event loop change the same variable at the same instant?
No: only one task runs at a time and it is only interrupted at an await. Races are still possible if a check and an act are separated by an await (section 2.9 and the exercises), but they are much rarer than with threads.

Recap
  • A coroutine is a paused function; a task schedules it; the event loop runs ready tasks and sleeps until the next timer or ready socket.
  • await pauses the current task only when the awaited thing has to wait. That pause is the only time other tasks run.
  • await a(); await b() is sequential; gather or create_task makes tasks concurrent.
  • Keep references to tasks, never call asyncio.run inside a running loop, and treat "never awaited" warnings as bugs.
2.9 — asyncio in Production: Blocking Calls, Cancellation, Timeouts and TaskGroup

Section 2.8 explained the loop. This section covers the four situations that turn an asyncio prototype into an incident: a blocking call inside a coroutine, cancellation that goes wrong, missing timeouts, and errors that vanish or leave orphan tasks. Each has a small, reproducible demonstration.

Blocking the loop

Because one thread runs every task, any call that does not await stops the world. time.sleep(0.3) inside an async def does not pause that coroutine politely; it freezes the entire loop for 0.3 seconds, so every other request stalls too. The same is true of requests.get, a big json.loads, a synchronous database driver, or a 2-second CPU loop. To see it, run a heartbeat task that records a timestamp every 10 ms, then compare the worst gap between ticks when the work is a blocking call versus an awaited one.

A heartbeat shows the loop freezing

Output (real Pyodide run)

The heartbeat could not tick during the blocking call, because it never got a turn. The fixes, in order of preference: use an async library for the I/O; push unavoidable blocking or CPU work to an executor (await loop.run_in_executor(pool, fn) or await asyncio.to_thread(fn)); or split long loops with await asyncio.sleep(0). Cancellation

When a request times out, a client disconnects or a program shuts down, tasks are cancelled: task.cancel() makes the task's current await raise asyncio.CancelledError. This is not an ordinary error. It is the mechanism by which the loop tells a task to stop, so the rule is: clean up in finally, and if you catch CancelledError, re-raise it. Swallowing it makes the task uncancellable, which breaks timeouts and clean shutdown in ways that are painful to trace.

What a cancelled task sees
import asyncio log = [] async def worker(): try: log.append('start') await asyncio.sleep(10) log.append('never reached') except asyncio.CancelledError: log.append('caught cancel, cleaning up') raise # ALWAYS re-raise finally: log.append('finally runs') t = asyncio.create_task(worker()) await asyncio.sleep(0) # let the worker start and reach its await t.cancel() try: await t except asyncio.CancelledError: log.append('caller sees CancelledError') print(log) print('task.cancelled():', t.cancelled())

Timeouts

Every call that leaves your process needs a timeout. Without one, a slow dependency turns into a pile of stuck tasks, held connections and eventually memory exhaustion. In Python 3.11 and later, async with asyncio.timeout(seconds): puts a deadline on a whole block; the older asyncio.wait_for(coro, seconds) does the same for one awaitable. Both work by cancelling the inner work and raising the built-in TimeoutError.

A timeout is a cancellation with a deadline

gather versus TaskGroup

Running several tasks together raises a question: what happens when one fails? asyncio.gather re-raises the first exception, but the other tasks are not cancelled; they run on in the background, unsupervised, which is a slow leak of orphan work. A TaskGroup (Python 3.11+) is structured: the block does not exit until all its tasks finish, and if one fails the others are cancelled, then all errors are raised together as an ExceptionGroup, which you catch with except*.

gather leaves survivors, TaskGroup cancels them
import asyncio async def slow(log): try: await asyncio.sleep(0.05); log.append('slow finished') except asyncio.CancelledError: log.append('slow cancelled'); raise async def boom(): await asyncio.sleep(0.01) raise ValueError('boom') log = [] try: await asyncio.gather(slow(log), boom()) except ValueError as e: log.append(f'gather raised {e}') await asyncio.sleep(0.1) # give the orphan time to finish print('gather :', log) log = [] try: async with asyncio.TaskGroup() as tg: tg.create_task(slow(log)); tg.create_task(boom()) except* ValueError as eg: log.append(f'group raised {[str(e) for e in eg.exceptions]}') print('TaskGroup:', log) results = await asyncio.gather(boom(), asyncio.sleep(0, 'ok'), return_exceptions=True) print('return_exceptions=True:', results)
Output (real Pyodide run)
gather : ['gather raised boom', 'slow finished'] TaskGroup: ['slow cancelled', "group raised ['boom']"] return_exceptions=True: [ValueError('boom'), 'ok']

With gather, the slow task finished after the error was already reported: work nobody is waiting for. With TaskGroup, it was cancelled promptly and the failure surfaced once. Prefer TaskGroup for new code. Use gather(return_exceptions=True) when you genuinely want "run all of them and give me every outcome", for example a fan-out where partial results are acceptable.

Races still exist in asyncio

Cooperative scheduling reduces races but does not remove them. If a check and its act are separated by an await, another task can run in between. The remedy is an asyncio.Lock (or restructuring so the check and act have no await between them).

2.10 — Backpressure: What Happens When Producers Outrun Consumers

Section 2.6 gave you a queue between producers and consumers, and left one question open: what if the producers are faster? On a Monday morning a batch upload sends 5,000 jobs per minute to a worker that finishes 3,000. If the queue is unbounded, nothing fails immediately. The queue just grows, latency grows with it (each new job waits behind everything queued before it), memory grows, and eventually the process is killed or the jobs are so stale that nobody wants the results. The system did not crash under load; it collapsed slowly and silently.

Backpressure is any mechanism by which a slow consumer signals a fast producer to slow down, so that work in flight stays bounded. It is the difference between a system that degrades gracefully and one that dies. You already use it: TCP's receive window makes a sender pause, and an HTTP 429 Too Many Requests with a Retry-After header says "not now". Analogy: a highway on-ramp meter light. Letting every car in at once jams the highway for everyone; releasing one car per few seconds keeps traffic flowing.

Start with the failure. A producer adds 5 items per tick; the consumer removes 3 per tick.

Unbounded queue: depth and wait grow forever
arrive, serve = 5, 3 queue = 0 print('tick queue depth wait for a new item (ticks)') for tick in range(1, 9): queue += arrive queue -= min(queue, serve) print(f'{tick:>4} {queue:>11} {queue / serve:>10.1f}')
Output (real Pyodide run)
tick queue depth wait for a new item (ticks) 1 2 0.7 2 4 1.3 3 6 2.0 4 8 2.7 5 10 3.3 6 12 4.0 7 14 4.7 8 16 5.3

The depth rises by 2 every tick without limit, and the wait for the newest item follows it. There is a relationship behind this, Little's Law: the average number of items in a system (L) equals the arrival rate (lambda) times the average time an item spends in the system (W), so L = lambda x W. If 100 requests per second arrive and each takes 200 ms end to end, about 20 requests are in flight at any moment. Turn it around: if you cap the items in flight at 20, then at that latency you can accept at most 100 per second, and anything above must wait or be turned away. A bounded queue enforces that cap.

A bounded queue forces a decision when it is full. There are three honest options, and choosing consciously is a design decision, not an implementation detail.

  • Block the producer (the producer waits until there is room). Nothing is lost; the producer slows to the consumer's speed. Right for in-process pipelines and batch jobs.
  • Shed load (drop the newest item, or the oldest, and tell the caller with a 429 or 503). Right for user-facing requests where a late answer is worthless and a fast "try later" is better.
  • Spill or scale: buffer to disk or a durable broker, or add consumers. Right when the burst is temporary or the work must not be lost, at the price of cost and complexity.
A bounded queue pushes back
   producer  --put-->  [ j j j j j j ]  --get-->  consumer
   (fast)              maxsize = 6                 (slow)
       ^                    |
       |     queue full:    |
       +--- BLOCK (wait)  or  REJECT (429) or  DROP (shed) ---+
   depth stays <= 6, so memory and wait time stay bounded
Block versus shed load with a bounded queue

Both policies keep the queue at 6 or below. block loses nothing but forces the producer to wait (and in a real service that waiting propagates upstream to whoever called the producer). shed keeps the producer moving at full speed and discards what does not fit. Neither is universally right; the mistake is not choosing.

The producer runs ahead by at most the queue's size. The depth never exceeds 2, whatever the speeds. The same idea limits how many tasks run at once: a semaphore is a counter that lets at most N holders in. This is how you honour a rule such as "the partner allows 3 concurrent calls" while still starting 20 tasks.

A semaphore caps concurrency
import asyncio sem = asyncio.Semaphore(3) active = peak = 0 async def call(i): global active, peak async with sem: # at most 3 inside at once active += 1 peak = max(peak, active) await asyncio.sleep(0.01) # the remote call active -= 1 await asyncio.gather(*(call(i) for i in range(20))) print('tasks started: 20 | peak concurrency:', peak)
Output (real Pyodide run)
tasks started: 20 | peak concurrency: 3

Why you must leave headroom

One more fact makes backpressure urgent well before a system is "full". In a simple queueing model, the average time an item spends in the system is 1 / (service rate - arrival rate). Latency does not rise gently with load; it rises like a hockey stick.

Latency versus utilisation (M/M/1 model)
service_rate = 100 # requests per second the worker can finish for load in (0.5, 0.7, 0.8, 0.9, 0.95, 0.99): arrival = load * service_rate avg_ms = 1000 / (service_rate - arrival) print(f'utilisation {load:>4.0%}: average time in system {avg_ms:>6.0f} ms')
Output (real Pyodide run)
utilisation 50%: average time in system 20 ms utilisation 70%: average time in system 33 ms utilisation 80%: average time in system 50 ms utilisation 90%: average time in system 100 ms utilisation 95%: average time in system 200 ms utilisation 99%: average time in system 1000 ms

At 50 percent utilisation an item spends 20 ms in the system; at 90 percent, 100 ms; at 99 percent, a full second. This is why capacity plans aim for 60 to 70 percent at peak, and why a service at 95 percent "seems fine" until a small burst makes it unusable. It is a model with idealised assumptions, but the shape is real.

Retrying rejected requests immediately (a rejected client that retries instantly becomes the load; use backoff, section 2.7). Watching CPU only, when the leading indicators are queue depth and the age of the oldest item.
Check yourself: Arrival rate is 200 requests per second and each request spends 250 ms in the system. By Little's Law, how many requests are in flight on average?

Check yourself: When would you drop load instead of blocking the producer?
When the producer is a user-facing caller for whom a late answer is useless: a fast 429 or 503 lets the caller retry elsewhere and protects the rest of the system. Blocking suits pipelines where every item must eventually be processed.

Recap
  • Unbounded queues turn overload into slow collapse (growing memory and latency); bound every queue.
  • When full, choose deliberately: block, shed (429/503) or spill/scale.
  • Little's Law (L = lambda x W) links in-flight work, throughput and latency; semaphores and pool sizes are how you cap in-flight work.
  • Latency explodes as utilisation approaches 100 percent, so leave headroom and watch queue depth and oldest-item age.
2.11 — Profiling: Measure Before You Change Anything

A teammate spends a week rewriting a parsing function in a faster style. The endpoint gets 1.5 percent faster, because parsing was 3 percent of the request. The real cost was a database call inside a loop, visible to anyone who had looked. This is the standard performance story: programmers are bad at guessing where time goes, and a profiler is the instrument that replaces guessing. Donald Knuth's remark that "premature optimisation is the root of all evil" is about exactly this: optimise the measured hotspot, not the code that merely looks slow.

A profiler measures where a program spends time (or memory). There are three tools you need, each answering a different question.

ToolQuestion it answersCost and where to use it
timeitHow long does this small snippet take?Micro-benchmarks, comparing two implementations
cProfile (deterministic)Which functions are called how often, and where does the time go?Adds overhead (about 2x); use on a representative run, in development
tracemallocWhich lines allocate memory, and how much?Memory hunting; adds overhead
py-spy (sampling)What is a running process doing right now?Very low overhead; attach to production, no code change

timeit: comparing small alternatives

timeit runs a snippet many times and reports the total. Two habits matter. Use repeat and take the minimum: noise from the operating system only ever makes a run slower, so the fastest run is the best estimate of the true cost. And compare relative results ("about 100 times slower") rather than trusting an absolute number from someone else's machine. The block prints only the comparison, because absolute times differ between machines.

timeit: list versus set membership
import timeit n = 20_000 data_list = list(range(n)) data_set = set(data_list) target = n - 1 # worst case for the list scan t_list = min(timeit.repeat(lambda: target in data_list, repeat=5, number=200)) t_set = min(timeit.repeat(lambda: target in data_set, repeat=5, number=200)) print('list membership at least 20x slower than set:', t_list / t_set >= 20)
Output (real Pyodide run)
list membership at least 20x slower than set: True

The list has to compare against elements one by one (linear, O(n)); the set hashes the key and jumps straight to it (constant, O(1) on average). Section 2.12 returns to why.

cProfile: which function is the problem?

cProfile records every function call and how long it took. The table it prints has five columns worth knowing. ncalls: how many times the function was called. tottime: time spent inside the function itself, excluding functions it called. cumtime: time including everything it called. percall: the corresponding time divided by ncalls. The last column names the function. Sorting by cumulative shows the call path from the top; sorting by tottime shows where the time is actually burnt.

To keep this page's output identical for every reader, the block below replaces the wall clock with a virtual clock: each unit of work adds a fixed number of microseconds to a counter that cProfile uses as its timer. Everything else (the call counts, the function ranking, the way to read the table) is exactly what you see with a real clock. In real use you omit the timer argument.

cProfile on a slow report (deterministic virtual clock)
import cProfile, pstats, io clock = [0] # a virtual clock in microseconds (must be int) def timer(): return clock[0] def parse(rows): out = [] for r in rows: out.append(r.split(',')) clock[0] += 200 # pretend each row costs 200 us return out def dedupe(items): kept = [] for it in items: for k in kept: # linear scan for every item: O(n^2) clock[0] += 30 # pretend each comparison costs 30 us if k == it: break else: kept.append(it) return kept def render(items): clock[0] += 500 * len(items) # pretend each output line costs 500 us return '\n'.join(','.join(i) for i in items) def report(rows): return render(dedupe(parse(rows))) rows = [f'id{i % 40},x' for i in range(120)] pr = cProfile.Profile(timer=timer, timeunit=1e-6) pr.runcall(report, rows) buf = io.StringIO() st = pstats.Stats(pr, stream=buf).sort_stats('cumulative') st.print_stats('parse|dedupe|render|report') print(buf.getvalue())
Output (real Pyodide run)
368 function calls (328 primitive calls) in 0.117 seconds Ordered by: cumulative time List reduced from 10 to 4 due to restriction <'parse|dedupe|render|report'> ncalls tottime percall cumtime percall filename:lineno(function) 1 0.000 0.000 0.117 0.117 <exec>:29(report) 1 0.073 0.073 0.073 0.073 <exec>:14(dedupe) 1 0.024 0.024 0.024 0.024 <exec>:7(parse) 1 0.020 0.020 0.020 0.020 <exec>:25(render)
  • report has a cumtime of 0.117 s (the whole run) but a tottime of about 0: it does no work itself, it only calls three others. That is the shape of a coordinator function.
  • dedupe has a tottime of 0.073 s, about 62 percent of the total. It calls no other slow function, so its own body is the hotspot. That is where to look first.
  • parse and render are 20 and 17 percent. Even making them infinitely fast would save at most 38 percent; making dedupe fast is worth at least as much and far more if its cost drops from quadratic to linear.
  • Every function was called once, so this is not a "called too often" problem. The cost per call is the issue (an O(n^2) scan). If ncalls were 100,000 for a cheap function, the fix would be to call it less.

That last point is a general diagnostic. High tottime with few calls means the function's algorithm is expensive. High ncalls with tiny percall means the call count is the problem (a query in a loop, a function recomputed for the same input). High cumtime but low tottime means the time is in what it calls, so go down the call path.

tracemalloc: which line allocates?

Time is not the only resource. tracemalloc snapshots memory allocations and can tell you which source line holds the most. The block reports only the line number and a threshold, because byte sizes differ between platforms (a 32-bit WebAssembly build uses smaller pointers than your laptop).

tracemalloc points at the heavy line

py-spy and flame graphs (reference only)

Deterministic profilers slow the program down, which makes them awkward in production and can distort what they measure. A sampling profiler such as py-spy instead peeks at the program's call stack about 100 times per second from outside the process. Functions that appear in many samples are where the time goes. It needs no code changes and adds little overhead, so you can point it at a live, misbehaving service. It also works on programs that hang (py-spy dump prints every thread's current stack).

⚠️
Reference-only blockpy-spy is a separate tool that attaches to an operating-system process, so it cannot run in a browser tab. The commands are the standard ones; nothing here produces output on this page.
py-spy: the three commands to rememberreference only
pip install py-spy py-spy top --pid 12345 # live, like `top`, but for Python functions py-spy dump --pid 12345 # one-shot: what is every thread doing RIGHT NOW? py-spy record -o profile.svg --pid 12345 --duration 30 # 30 s of samples -> flame graph py-spy record -o profile.svg -- python app.py # profile a program from start to finish

The most useful output is the flame graph. Each box is a function; a box's width is the share of samples in which it appeared; a box sits on top of the function that called it. So the picture reads from the bottom (entry point) upward (callees), and wide boxes are where the time is. The horizontal order is alphabetical, not chronological, so never read the left-to-right direction as "first to last".

Reading a flame graph (the report profiled above)
   +-------+-------------------------+--------+
   | parse |         dedupe          | render |   <- callees: box width = time share
   +-------+-------------------------+--------+
   |                 report                   |   <- entry point: always 100% wide
   +------------------------------------------+

   Look for:
   * a wide box with nothing on top   -> that function's own code is hot (dedupe)
   * a wide box with many narrow ones -> the time is in its callees; go up
   * many narrow boxes of one name    -> the call count is the problem
   * left-to-right order is alphabetical, NOT chronological
⚠️
Common mistakesProfiling with toy data (the hotspot is often data-size dependent). Trusting one timing run instead of the minimum of several. Profiling with a debugger or other tools attached. Optimising the function that is easiest to understand instead of the one at the top of the profile. Comparing an old absolute time on your laptop to a new one on CI.
Check yourself: A function has ncalls=250,000, tottime=1.9 s, percall=0.0000076 s. What is the likely fix?
The per-call cost is tiny; the number of calls is the problem. Reduce the calls (batch, cache, hoist out of a loop), rather than micro-optimising the function body.
Check yourself: Why take the minimum of several timeit repeats instead of the mean?
Interference (other processes, garbage collection, CPU frequency) only adds time, never removes it, so the fastest run is the closest to the code's true cost. The mean mixes in the noise.

Recap
  • Profile first: timeit for snippets, cProfile for call-level cost, tracemalloc for memory, py-spy for live processes.
  • Read the table: high tottime with few calls means an expensive algorithm; high ncalls means call less; high cumtime with low tottime means look at the callees.
  • In a flame graph, wide boxes with nothing above them are the hotspot; left-to-right order carries no meaning.
  • Use minimums of repeated runs, realistic data, and relative rather than absolute numbers.
