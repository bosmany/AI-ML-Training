Chapter 12:
Pandas Fundamentals

NumPy handles numbers in arrays. Pandas handles TABLES — rows and columns, with labels, mixed types, and missing values — which is what almost every real dataset actually looks like. This is the tool you'll use to load, inspect, filter, and summarize data for the rest of this course.

12.1 — DataFrame: The Spreadsheet Inside Python

A DataFrame is a table: rows and named columns, like a spreadsheet. A Series is a single column (or row) of it. Remember Chapter 4's "list of dicts" pattern? A DataFrame is that same idea, but built for fast, convenient bulk operations.

Creating a DataFrame from a dict of lists
import pandas as pd data = { 'name': ['Alice', 'Bob', 'Carol'], 'score': [92, 75, 81], 'city': ['Hubli', 'Pune', 'Mumbai'], } df = pd.DataFrame(data) print(df) # pandas prints a nicely formatted table print(f'Shape: {df.shape}') # (3, 3) — 3 rows, 3 columns print(f'Columns: {list(df.columns)}')
12.2 — Reading a Real CSV File

Chapter 5 parsed CSVs manually with the csv module. Pandas does the whole thing — including type conversion — in one line: pd.read_csv(). The running example for the rest of this chapter is a real, 1,500-row e-commerce orders dataset (plus a 50-row customers lookup table) — generated once with a fixed seed so it's exactly reproducible, then written to a real CSV and read back exactly like any file you'd download.

Generating this chapter's dataset, writing it, reading it back — and verifying it
import numpy as np import pandas as pd rng = np.random.default_rng(42) # fixed seed -> identical data every run n_customers, n_orders = 50, 1500 first_names = 12.3 — Indexing: .loc vs .iloc

.iloc selects by integer POSITION (like a list index). .loc selects by LABEL (the actual index value, or column name) — for a default DataFrame these often look the same, but they mean different things and diverge the moment your index isn't a simple 0,1,2....

.loc and .iloc side by side
import pandas as pd df = pd.DataFrame({'name': ['Alice','Bob','Carol'], 'score': [92,75,81]}) print(df.iloc[1]) # the 2nd ROW by POSITION — Bob's row print(df.loc[1, 'name']) # the value at index label 1, column 'name' — 'Bob' print(df['score']) # a whole column, as a Series print(df.head(2)) # first 2 rows

Every Series/DataFrame operation lines rows up by INDEX LABEL, not position — arithmetic between two objects with different indexes silently produces NaN wherever the labels don't both exist, instead of an error. The same risk applies to DataFrames, not just Series.

Index misalignment: arithmetic aligns by LABEL, not position
import pandas as pd a = pd.Series([10, 20, 30], index=['x','y','z']) b = pd.Series([1, 2, 3], index=['y','z','w']) # only y, z overlap with a misaligned = a + b print(misaligned) print(f'NaN count: {misaligned.isna().sum()}') # FIX 1 — you actually meant label-based alignment: fill the non-overlapping labels instead of dropping to NaN label_fix = a.add(b, fill_value=0) print(f'label-aware fix: {label_fix.tolist()}') # FIX 2 — you actually meant POSITIONAL alignment (e.g. after independently filtering two frames): reset both first positional_fix = a.reset_index(drop=True) + b.reset_index(drop=True) print(f'positional fix: {positional_fix.tolist()}')
🚫
Real output: x and w become NaN — 2 of 4 result rows — because each only exists in ONE of the two Series; no error, no warning. a.add(b, fill_value=0) treats a missing label as 0 instead of NaN ([10.0, 21.0, 32.0, 3.0]) — correct when the labels genuinely mean different things and a missing one should count as zero. .reset_index(drop=True) on both sides instead aligns by POSITION ([11, 22, 33]) — correct when the index labels are incidental (e.g. left over from independently filtering two different DataFrames) and you actually meant "1st with 1st, 2nd with 2nd." Picking the wrong one of these two fixes silently produces a plausible-looking but wrong number — know which kind of alignment your data actually needs.
12.4 — Filtering Rows

Same boolean-masking idea from Chapter 11, applied to a DataFrame: df[condition] keeps only the matching rows. Combine conditions the same way — & / |, each side in parentheses.

Filtering a DataFrame
import pandas as pd df = pd.DataFrame({ 'name': ['Alice','Bob','Carol','Dave'], 'score': [92,75,81,60], 'dept': ['Sales','Eng','Sales','Eng'], }) qualified = df[df['score'] >= 80] print(f'Qualified: {list(qualified["name"])}') sales_high = df[(df['dept'] == 'Sales') & (df['score'] >= 80)] print(f'Sales & qualified: {list(sales_high["name"])}')

.query() is a readable alternative to boolean masking — the condition is a plain string, so no repeating df[...] for every column, and no bare &/| operator-precedence surprises.

Same filter, .query() style — on the real orders data
import pandas as pd orders = pd.read_csv('orders.csv') # from 12.2 — already on disk in this session boolean_style = orders[(orders['product_category'] == 'Electronics') & (orders['quantity'] >= 3)] query_style = orders.query("product_category == 'Electronics' and quantity >= 3") print(f'boolean-mask rows: {len(boolean_style)}') print(f'query rows: {len(query_style)}') print(f'identical: {boolean_style.equals(query_style)}')
💡
Real output: both return exactly 259 rows, and are identical. Use whichever reads more clearly for the condition at hand — .query() tends to win once you're combining 3+ conditions.

One filtering mistake is common enough to have its own name: chained assignment — trying to filter AND assign in one bracketed expression.

Chained assignment: looks reasonable, doesn't do what it looks like
import pandas as pd orders = pd.read_csv('orders.csv') sample = orders.head(5).copy() # WRONG: two separate lookups chained together. This does NOT raise — it WARNS, then silently does nothing. sample[sample['quantity'] > 2]['quantity'] = 999 print(f'after chained assignment (still unchanged!): {sample["quantity"].tolist()}') # RIGHT: a single .loc call — one lookup, an unambiguous write target sample.loc[sample['quantity'] > 2, 'quantity'] = 999 print(f'after .loc fix: {sample["quantity"].tolist()}')
🚫
Real output: the chained-assignment line prints a ChainedAssignmentError warning explaining that "this never works to update the original DataFrame," and then execution continues normally — no exception, no crash. The data prints completely unchanged ([3, 3, 2, 3, 2]) right after a line that looked like it should have changed it. That silence is what makes this mistake dangerous: your code runs, nothing looks wrong, and the bug is a value that's quietly stale everywhere downstream. The .loc version afterward is the fix — one lookup, one unambiguous write target, and it genuinely changes the data ([999, 999, 2, 999, 2]).
12.5 — Sorting

.sort_values('column') sorts a DataFrame by any column, ascending by default.

Ranking by score
import pandas as pd df = pd.DataFrame({'name': ['Alice','Bob','Carol'], 'score': [92,75,81]}) ranked = df.sort_values('score', ascending=False) print(f'Ranked: {list(ranked["name"])}') # highest score first
12.6 — GroupBy: Aggregating by Category

.groupby('column') splits a DataFrame into groups sharing a value, so you can aggregate each group separately — "average score PER department," not just overall.

Average score by department
import pandas as pd df = pd.DataFrame({ 'name': ['Alice','Bob','Carol','Dave','Eve'], 'dept': ['Sales','Eng','Sales','Eng','Sales'], 'score': [85,72,91,68,77], }) avg_by_dept = df.groupby('dept')['score'].mean() print(avg_by_dept) print(f'Sales average: {avg_by_dept["Sales"]:.4f}') # value_counts() — how many rows per category print(df['dept'].value_counts())
⭐
groupby is the pandas analogue of NumPy's axis=0 aggregation — instead of collapsing by position (rows/columns), it collapses by CATEGORY. Same mental move as Chapter 11, applied to labeled data.

One aggregation per group is often not enough — .agg() computes SEVERAL at once, on the real orders data.

Multiple aggregations per group, in one call
import pandas as pd orders = pd.read_csv('orders.csv') price_stats = orders.groupby('product_category')['unit_price'].agg(['mean', 'count']) print(price_stats.round(4))
💡
Real output: Electronics has the highest average unit price (258.01) across 436 orders — one .agg([...]) call replaces writing .mean() and .count() as two separate groupby calls.
12.7 — Merging: Inner, Left, Right, and Outer

A merge (also called a join) combines two DataFrames using a shared key column — exactly like joining tables in SQL. The four kinds differ only in which UNMATCHED rows they keep: inner keeps only rows with a match on both sides; left keeps every left row (filling unmatched right columns with NaN); right is the mirror image; outer keeps everything from both sides.

All four join types, same real data, one lookup subset
import pandas as pd orders = pd.read_csv('orders.csv') customers = pd.read_csv('customers.csv') # deliberately only a SUBSET of customers, so unmatched rows actually occur some_customers = customers[customers['customer_id'] <= 25][['customer_id', 'customer_name']] inner = orders.merge(some_customers, on='customer_id', how='inner') left = orders.merge(some_customers, on='customer_id', how='left') right = orders.merge(some_customers, on='customer_id', how='right') outer = orders.merge(some_customers, on='customer_id', how='outer') print(f'inner: {len(inner)} left: {len(left)} right: {len(right)} outer: {len(outer)}') print(f'unmatched rows in left join (NaN customer_name): {left["customer_name"].isnull().sum()}')
💡
Real output: inner: 775 left: 1500 right: 775 outer: 1500. Only 25 of 50 customers are in the lookup, but ALL 1,500 orders (from all 50 customers) are on the left — so left keeps all 1,500, with 725 rows getting NaN for customer_name (orders from the 25 EXCLUDED customers). inner/right drop those unmatched 725, leaving 775. outer matches left here because every included customer already has at least one order.

The most common real merge bug isn't picking the wrong join type — it's an unexpected duplicate key, which silently multiplies rows instead of erroring.

A duplicate key silently multiplies rows
import pandas as pd orders_small = pd.DataFrame({'order_id': [1,2,3], 'customer_id': [10,20,20]}) lookup_dup = pd.DataFrame({'customer_id': [10,20,20], 'name': ['Ann','Ben','Ben2']}) # 20 appears TWICE — maybe a duplicated data-entry row merged = orders_small.merge(lookup_dup, on='customer_id', how='inner') print(f'orders_small rows: {len(orders_small)} -> merged rows: {len(merged)}') print(merged)
🚫
Real output: 3 orders become 5 merged rows — orders 2 and 3 (both customer_id=20) each matched BOTH duplicate lookup rows, producing every combination. No error, no warning — the row count just quietly grows. The fix: before merging on a key, check lookup_df['key'].duplicated().sum() is 0 (or that a merge's output row count matches your expectation), rather than discovering the inflation downstream in a wrong aggregate.
12.8 — Pivot and Pivot Table

.pivot_table() reshapes long data into a wide summary grid: one column's values become new COLUMN HEADERS, another becomes an aggregated VALUE — the pandas equivalent of a spreadsheet pivot table.

Total quantity sold, by category (rows) and payment method (columns)
import pandas as pd orders = pd.read_csv('orders.csv') pt = orders.pivot_table( values='quantity', index='product_category', columns='payment_method', aggfunc='sum', fill_value=0, # fill_value: a real category/method combo with zero orders becomes 0, not NaN ) print(pt)
📊
Real output: a 5×4 grid — every (category, payment method) combination's total quantity, at a glance. The same result via groupby would need .groupby(['product_category','payment_method'])['quantity'].sum().unstack() — pivot_table is the direct, more readable route to this exact shape.
12.9 — apply() vs Vectorized Operations

.apply() runs a Python function once per row (or column) — flexible, but it's a Python-level loop underneath, with all of Chapter 11's loop overhead. If the same computation can be written as a vectorized expression, that's almost always faster, and often more readable too.

Row-wise apply() vs a vectorized expression — same result, timed fairly
import pandas as pd import timeit orders = pd.read_csv('orders.csv') def apply_version(): return orders.apply(lambda row: row['quantity'] * row['unit_price'], axis=1) def vectorized_version(): return orders['quantity'] * orders['unit_price'] print(f'results match: {(apply_version().values == vectorized_version().values).all()}') apply_times = timeit.repeat(apply_version, repeat=5, number=3) vec_times = timeit.repeat(vectorized_version, repeat=5, number=3) print(f'apply best-of-5: {min(apply_times):.4f}s vectorized best-of-5: {min(vec_times):.6f}s')
⚠️
Real output: results match: True, apply best-of-5 ~0.0125s, vectorized best-of-5 ~0.000094s — about 130x faster (exact numbers will differ on your machine, same methodology as Chapter 11's timing). axis=1 apply is the most common "unnecessary apply": it reconstructs a full row (a Series) for every single row just to read two of its values, when orders['quantity'] * orders['unit_price'] does the identical computation in one vectorized pass. Reach for .apply() only when the logic genuinely can't be expressed as column-level vector operations.
12.10 — Datetime: Parsing, Extraction, Filtering, and Resampling

A date read from CSV is just a STRING until you tell pandas otherwise. pd.to_datetime() converts it to a real datetime dtype — unlocking .dt accessors, correct chronological comparisons, and resampling (aggregating into fixed time buckets like "per month").

String dates sort wrong; real datetimes sort right
import pandas as pd messy_dates = pd.Series(['2023-1-5', '2023-10-2', '2023-2-1']) # inconsistent formatting, still valid dates print(f'sorted as STRINGS (wrong): {sorted(messy_dates.tolist())}') # '2023-10-2' sorts before '2023-2-1' — alphabetically "1" < "2" print(f'sorted as real dates: {sorted(pd.to_datetime(messy_dates)).__str__()}')
🚫
Real output: as strings, October ('2023-10-2') sorts BEFORE February ('2023-2-1') — alphabetical comparison, not chronological, because '1' < '2' as characters. Once converted with pd.to_datetime(), the same values sort correctly: January, February, October. Always check df['date_col'].dtype after loading a CSV — if it says object instead of datetime64, every date comparison and sort on it is silently comparing text.
Real datetime extraction, filtering, and monthly resampling
import pandas as pd orders = pd.read_csv('orders.csv') print(f'dtype before conversion: {orders["order_date"].dtype}') orders['order_date'] = pd.to_datetime(orders['order_date']) print(f'dtype after conversion: {orders["order_date"].dtype}') # extraction via the .dt accessor orders['order_month'] = orders['order_date'].dt.month # filtering: real chronological comparison, not string comparison q1_2023 = orders[(orders['order_date'] >= '2023-01-01') & (orders['order_date'] < '2023-04-01')] print(f'Q1 2023 orders: {len(q1_2023)}') # resample: aggregate into calendar-month buckets — needs a DatetimeIndex monthly = orders.set_index('order_date').resample('ME')['quantity'].sum() print(f'January 2023 total quantity: {monthly.iloc[0]}')
📅
Real output: dtype goes from object to datetime64[us]; Q1 2023 has 193 orders; January 2023's total quantity sold is 191. resample('ME') ("month end") only works once the index is a real DatetimeIndex — it's doing the exact same "bucket, then aggregate" idea as groupby, just bucketing by calendar time instead of a category column.
12.11 — Readable Method Chaining

Every operation above returns a NEW DataFrame or Series — which means they can be chained directly, one .method() per line, instead of reassigning a variable at every step. Parenthesize the whole expression and it reads almost like a sentence.

Filter, group, sort — as one chain vs three separate steps
import pandas as pd orders = pd.read_csv('orders.csv') # one readable chain: exclude returns, total quantity per category, ranked highest first result = ( orders .query("is_returned == False") .groupby('product_category')['quantity'] .sum() .sort_values(ascending=False) ) print(result)
🔗
Real output: Electronics leads with 1230 units. This is IDENTICAL to writing step1 = orders.query(...), then step2 = step1.groupby(...)..., then result = step2.sort_values(...) — chaining doesn't change what runs, only how it reads. Use it once a pipeline is genuinely a straight-line sequence; break it back into named steps the moment you need to inspect or reuse an intermediate result, or the moment a single chain stops fitting on one screen.
Chapter 12 Summary
  • DataFrame = a table (rows + named columns). Series = a single column.
  • pd.read_csv() loads and type-converts a CSV in one line — always verify row count, columns, and nulls after loading.
  • .loc selects by label; .iloc selects by position.
  • df[condition] and .query() both filter rows. Never chain a filter and an assignment in one bracketed expression — use .loc[rows, col] = value.
  • .sort_values() ranks by any column. .groupby().agg([...]) computes multiple summaries per category at once.
  • .merge() (inner/left/right/outer) joins on a key — check for duplicate keys first, or row counts can silently multiply.
  • .pivot_table() reshapes long data into a wide summary grid.
  • Vectorized operations beat .apply(), especially row-wise (axis=1) apply — reach for apply only when vectorization genuinely isn't possible.
  • pd.to_datetime() turns date strings into a real dtype — needed for correct sorting/filtering and for .resample().
Interview Questions
You merge two DataFrames on a key and the row count is much higher than either input. What happened, and how do you prevent it?▶
One side almost certainly has a duplicate key — a merge matches EVERY row on one side to EVERY row with the same key on the other, so a key appearing twice on one side multiplies matching rows on the other. Before merging, check df['key'].duplicated().sum() on both sides, and confirm the output row count matches what you expect (usually the same as the "many" side of a one-to-many relationship) rather than discovering the inflation in a downstream aggregate.
What's the difference between an inner join and a left join, and when would you choose left?▶
Inner keeps only rows with a match on both sides; left keeps every row from the left DataFrame regardless of a match, filling unmatched right-side columns with NaN. Choose left when the left DataFrame is your "source of truth" and you need every one of its rows represented even when enrichment data (like a customer name) is missing — e.g. every order should appear in a report even if its customer record was deleted.
Why does `df[df['x']>5]['y'] = 10` sometimes silently fail to update anything?▶
This is chained assignment: df[df['x']>5] may return a COPY of the data, not a view into the original, so the second bracket's assignment can end up modifying that throwaway copy instead of df itself. Pandas can't always guarantee which one you'll get, which is exactly why it warns (or in newer pandas, raises) rather than staying silent. The fix is always a single .loc[df['x']>5, 'y'] = 10 call — one lookup, one unambiguous write target.
When is `.apply()` actually the right tool, instead of a vectorized expression?▶
When the per-row (or per-element) logic genuinely can't be expressed as column-level vector operations — e.g. calling an external function, complex conditional branching that doesn't map cleanly to np.where/pd.cut, or row-wise logic that legitimately needs several columns combined in a non-arithmetic way. Before reaching for it, check whether the same result is achievable with vectorized arithmetic, boolean masking, np.where, or pd.cut — those are typically far faster, especially for anything using axis=1.
You load a CSV and a date column shows dtype `object`. What problems does this cause, and how do you fix it?▶
An object-dtype date column is really just text, so sorting and comparisons happen ALPHABETICALLY, not chronologically — e.g. '2023-10-2' sorts before '2023-2-1' because '1' < '2' as characters, even though October is after February. The fix is pd.to_datetime(df['col']), converting it to a real datetime64 dtype, which also unlocks .dt accessors and .resample().
What's the difference between `groupby` and `pivot_table`, given they can produce similar results?▶
groupby collapses rows by one or more keys into a (typically long, indexed) result. pivot_table is built specifically to reshape into a WIDE grid — one column's distinct values become new column headers, which is exactly what you'd otherwise need groupby(...).unstack() for. Reach for pivot_table directly when the end goal is a cross-tabulated summary grid; reach for groupby when you just need one aggregated column per group.
Why should you verify a DataFrame right after loading it, instead of trusting `pd.read_csv()` and moving on?▶
A CSV load can succeed without error while still being wrong — extra/missing columns from a schema change, unexpected nulls from a bad export, a numeric column silently parsed as text because of one stray non-numeric value, or far fewer rows than expected from a truncated file. Checking .shape, .columns, .dtypes, and .isnull().sum() immediately after loading catches these before they quietly corrupt every downstream analysis.
