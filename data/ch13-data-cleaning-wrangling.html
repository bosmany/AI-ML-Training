Chapter 13:
Data Cleaning & Wrangling

Real datasets are never clean. Missing values, exact and near-duplicate rows, data spread across multiple files that need joining, and inconsistent text formatting — cleaning this up isn't a chore before "the real work," it IS most of the real work. Industry surveys consistently put data cleaning at 60-80% of a data scientist's time. This chapter is that 60-80%.

13.1 — Missing Values: Profile, Then Decide

Missing data shows up as NaN (Not a Number) in pandas. Before fixing anything, profile it systematically — which columns, how many, what fraction — rather than reacting to the first missing cell you notice. The running example for the rest of this chapter is a real, deliberately messy 415-row employee dataset, generated once with a fixed seed so every issue below is exact and reproducible.

Generating this chapter's real messy dataset, then profiling it
import numpy as np import pandas as pd # fixed seed -> the exact same messy dataset every run (see the Project tab for the full generator + every injected-issue count) rng = np.random.default_rng(7) n = 400 first_names = ['Asha','Ben','Chen','Dana','Eli','Farah','Gita','Hiro','Ivy','Jun','Kira','Leo','Maya','Nia','Omar','Priya','Quinn','Rosa','Sam','Tara','Uma','Victor','Wei','Xena','Yara','Zane'] last_names = ['Sharma','Patel','Kim','Nguyen','Silva','Khan','Ito','Lopez','Rao','Costa','Mensah','Novak','Haddad','Fischer','Okoro'] names = [f'{first_names[rng.integers(0,len(first_names))]} {last_names[rng.integers(0,len(last_names))]}' for _ in range(n)] departments = ['Engineering','Sales','Marketing','HR','Finance'] dept_true = rng.choice(departments, n, p=[0.35,0.25,0.15,0.10,0.15]) ages = rng.integers(22, 60, n).astype(float) base_salary = {'Engineering':95000,'Sales':70000,'Marketing':65000,'HR':60000,'Finance':80000} salary = np.array([base_salary[d] + rng.normal(0, 8000) for d in dept_true]).round(2) join_dates = pd.to_datetime('2018-01-01') + pd.to_timedelta(rng.integers(0, 2000, n), unit='D') performance = rng.integers(1, 6, n).astype(float) cities = ['New York','San Francisco','Chicago','Austin','Seattle'] city_true = rng.choice(cities, n, p=[0.30,0.25,0.20,0.15,0.10]) is_remote = rng.choice([True, False], n, p=[0.3,0.7]) df = pd.DataFrame({'employee_id': np.arange(1,n+1), 'name': names, 'department': dept_true, 'age': ages, 'salary': salary, 'join_date': join_dates.strftime('%Y-%m-%d'), 'performance_rating': performance, 'city': city_true, 'is_remote': is_remote}) def inject_missing(col, frac, off): r = np.random.default_rng(7 + off) idx = r.choice(n, size=int(n*frac), replace=False) df.loc[idx, col] = np.nan inject_missing('age', 0.05, 1); inject_missing('salary', 0.04, 2) inject_missing('department', 0.03, 3); inject_missing('performance_rating', 0.15, 4); inject_missing('city', 0.02, 5) df['salary'] = df['salary'].astype(object) r = np.random.default_rng(30) nn = df.index[df['salary'].notnull()] messy_sal = r.choice(nn, size=int(len(nn)*0.10), replace=False) for i in messy_sal: df.at[i, 'salary'] = f'${float(df.at[i,"salary"]):,.2f}' r = np.random.default_rng(40) dv = df.index[df['department'].notnull()] messy_dept = r.choice(dv, size=int(len(dv)*0.08), replace=False) dept_variants = {'Engineering':['eng','ENGINEERING','Engineering '],'Sales':['sales','SALES','Sales '], 'Marketing':['Mktg','marketing'],'HR':['H.R.','Human Resources','hr'],'Finance':['finance','FINANCE']} for i in messy_dept: v = dept_variants[df.at[i,'department']]; df.at[i, 'department'] = v[r.integers(0,len(v))] r2 = np.random.default_rng(41) cv = df.index[df['city'].notnull()] messy_city = r2.choice(cv, size=int(len(cv)*0.08), replace=False) city_variants = {'New York':['new york','NYC','New York City'],'San Francisco':['san francisco','SF','San Fran'], 'Chicago':['chicago','CHICAGO'],'Austin':['austin ','AUSTIN'],'Seattle':['seattle','Seattle ']} for i in messy_city: v = city_variants[df.at[i,'city']]; df.at[i, 'city'] = v[r2.integers(0,len(v))] r3 = np.random.default_rng(50) ia = r3.choice(df.index[df['age'].notnull()], size=3, replace=False) df.loc[ia[0],'age']=150; df.loc[ia[1],'age']=-5; df.loc[ia[2],'age']=200 num_sal = df['salary'].apply(lambda v: isinstance(v,(int,float)) and pd.notnull(v)) ps = r3.choice(df.index[num_sal], size=6, replace=False) for i,v in zip(ps, [-20000.0,-5000.0,2500000.0,1800000.0,215000.0,198000.0]): df.at[i,'salary']=v r4 = np.random.default_rng(60) dv2 = df.index[df['join_date'].notnull()] alt = r4.choice(dv2, size=int(len(dv2)*0.06), replace=False) for i in alt: d = pd.to_datetime(df.at[i,'join_date']) df.at[i,'join_date'] = d.strftime('%m/%d/%Y') if r4.integers(0,2)==0 else d.strftime('%B %d, %Y') inv = r4.choice(df.index.difference(alt), size=5, replace=False) for i,val in zip(inv, ['2021-13-45','','not_a_date','2021-02-30','00/00/0000']): df.at[i,'join_date']=val r5 = np.random.default_rng(70) dup_idx = r5.choice(df.index, size=15, replace=False) df = pd.concat([df, df.loc[dup_idx]], ignore_index=True) df.to_csv('employees_messy.csv', index=False) # write the real CSV — every later block in this chapter reads this same file df = pd.read_csv('employees_messy.csv') missing_count = df.isna().sum() missing_pct = (df.isna().mean() * 100).round(1) for col in df.columns: if missing_count[col] > 0: print(f'{col}: {missing_count[col]} missing ({missing_pct[col]}%)')
💡
Real output: performance_rating is missing the most (63 rows, 15.2%) — for a REAL, documented reason: new hires haven't been rated yet. Always ask WHY a column is missing before deciding how to handle it; "missing because it doesn't exist yet" (performance_rating) calls for a different fix than "missing because of a bad export" (a few age/salary cells here).

The very first decision is whether to drop incomplete rows or fill (impute) them — and dropping is riskier than it looks, because .dropna() with no arguments removes a row if any column is missing, even one you don't care about.

dropna() vs fillna() — how much data does dropping actually throw away?
import pandas as pd df = pd.read_csv('employees_messy.csv') # DROP: removes a row if ANY column is missing — simple, but can be far more aggressive than intended dropped = df.dropna() print(f'rows before: {len(df)} after dropna(): {len(dropped)}') print(f'data discarded: {(1 - len(dropped)/len(df))*100:.1f}%') # FILL: keeps every row, filling only the column that's actually incomplete filled = df.copy() filled['city'] = filled['city'].fillna('Unknown') print(f'rows after filling just city: {len(filled)} (all of them — none dropped)')
⚠️
Real output: dropna() discards 27.2% of the entire dataset (113 of 415 rows) — because 5 different columns each have a few missing values scattered across different rows, "drop if anything is missing" compounds into losing over a quarter of the data, including every OTHER perfectly good column on those rows. Filling instead keeps all 415 rows. When dropping is reasonable: the missing fraction is tiny (well under 1-2%) and rows are independent, or the row is unusable for its actual purpose without that field. When imputing is preferable: missingness is common enough that dropping would meaningfully shrink or bias the dataset — which is the case for most columns here. Risk either way: dropping silently changes WHO is left in your data (if missingness isn't random, you've biased the remaining sample); imputing invents a value that wasn't observed, which can understate real uncertainty if trusted too literally downstream.

Once profiled and past that drop-or-fill decision, you choose per column: mean (sensitive to outliers/skew), median (robust to both), mode (for categoricals — "most common value"), or group-based imputation (fill using the mean/median WITHIN a relevant subgroup, not the whole column) — each has different assumptions and risks.

Mean vs median vs mode vs group-based — same column, four decisions
import pandas as pd df = pd.read_csv('employees_messy.csv') print(f'age mean: {df["age"].mean():.4f} median: {df["age"].median()}') print(f'department mode: {df["department"].mode()[0]}') # GLOBAL mean: every missing age gets the SAME value, regardless of department global_mean_fill = df['age'].fillna(df['age'].mean()) # GROUP-BASED: each missing age gets ITS OWN department's mean age instead group_means = df.groupby('department')['age'].transform('mean') group_based_fill = df['age'].fillna(group_means) print(f'Engineering avg age: {df[df["department"]=="Engineering"]["age"].mean():.4f}') print(f'Overall avg age: {df["age"].mean():.4f}') print(f'rows where the two fills differ: {(global_mean_fill.round(4) != group_based_fill.round(4)).sum()}')
⚠️
Real output: Engineering's average age (42.51) differs from the overall average (41.52) — every one of the 23 missing ages gets a different fill value depending on which method you pick. Assumptions and risks: mean/median imputation assumes a missing value looks like a "typical" row overall; group-based imputation assumes it looks like a typical row within its group — a better assumption when groups genuinely differ, but it can leak group identity into the imputed value in a way that quietly flatters a downstream model if that same group is also predictive of your target. Mode imputation for categoricals has the blunt risk of over-representing whatever was already most common, understating genuine diversity. None of these are "safe defaults" — they're modeling decisions, and the right one depends on why the data is missing.
13.2 — Duplicates: Exact Repeats

.duplicated() flags rows that are exact repeats of an earlier row (keeping the first occurrence as "not a duplicate"). .drop_duplicates() removes them.

Finding and removing duplicate rows — the real employee dataset
import pandas as pd df = pd.read_csv('employees_messy.csv') print(f'Exact duplicate rows: {df.duplicated().sum()}') deduped = df.drop_duplicates() print(f'Rows after drop_duplicates: {len(df)} -> {len(deduped)}')
🔑
Real output: 15 exact duplicate rows, all safely dropped — a genuine re-exported batch. This worked cleanly because employee_id is a real unique identifier: define what actually makes a row a duplicate BEFORE deduplicating. With no clear key, .duplicated() defaults to "every column matches exactly," which misses a real duplicate that differs by even one re-typed field (e.g. the same employee entered twice with slightly different capitalization), and — the opposite risk — .duplicated(subset=['name']) would wrongly treat two DIFFERENT employees who happen to share a name as duplicates. Here, checking df.duplicated(subset=['employee_id']).sum() also gives exactly 15, confirming employee_id is a trustworthy key for this decision.
13.3 — Merging: Combining Data Sideways

Real data lives in multiple tables that share a key column (like name or user_id). pd.merge(left, right, on='key', how=...) joins them, SQL-style. how='inner' keeps only keys present in BOTH tables; how='left' keeps every row from the left table, filling missing matches with NaN.

Inner vs left join
import pandas as pd candidates = pd.DataFrame({'name': ['Alice','Bob','Carol'], 'score': [92,75,81]}) cities = pd.DataFrame({'name': ['Alice','Bob','Dave'], 'city': ['Hubli','Pune','Delhi']}) inner = pd.merge(candidates, cities, on='name', how='inner') # Carol and Dave both dropped — no match in the other table left = pd.merge(candidates, cities, on='name', how='left') # Carol kept, city becomes NaN print(f'Inner join names: {list(inner["name"])}') print(f'Left join rows: {len(left)}')
⭐
Always check row counts after a merge — a merge key with duplicate values on either side silently multiplies rows (a "fan-out"), which is one of the most common real-world data bugs. If your merged table has more rows than you expected, that's almost always why.
13.4 — Concatenating: Stacking Data Vertically

Merging combines tables SIDEWAYS (matching columns by a key). pd.concat([df1, df2]) stacks tables ON TOP of each other — the classic "combine this week's export with last week's" operation. ignore_index=True renumbers the index so it doesn't repeat 0,1,2 twice.

Stacking two batches of data
import pandas as pd batch1 = pd.DataFrame({'name': ['Alice','Bob'], 'score': [92,75]}) batch2 = pd.DataFrame({'name': ['Carol','Dave'], 'score': [81,60]}) combined = pd.concat([batch1, batch2], ignore_index=True) print(f'Combined rows: {len(combined)}') print(f'Combined names: {list(combined["name"])}')
13.5 — Pivot Tables: Reshaping for Analysis

A pivot table reshapes long, row-per-observation data into a wide summary grid — one row per category, one column per another category, values aggregated at each intersection. This is the same mental model as an Excel pivot table.

Sales by rep, by quarter
import pandas as pd sales = pd.DataFrame({ 'rep': ['Alice','Alice','Bob','Bob','Carol','Carol'], 'quarter': ['Q1','Q2','Q1','Q2','Q1','Q2'], 'amount': [100, 120, 90, 95, 150, 140], }) pivot = sales.pivot_table(values='amount', index='rep', columns='quarter', aggfunc='sum') print(pivot) print(f'Alice Q2: {pivot.loc["Alice","Q2"]}') print(f'Bob total: {pivot.loc["Bob"].sum()}')
13.6 — Cleaning Text and Fixing Types

Real text data has stray whitespace and inconsistent casing (' Alice ', 'BOB', 'carol'). The .str accessor runs string methods across a whole column at once. And a column that LOOKS numeric but was loaded as text needs .astype() before any math will work correctly on it.

.str accessor + astype()
import pandas as pd messy = pd.DataFrame({'name': [' Alice ', 'BOB', 'carol'], 'score_text': ['92', '75', '81']}) cleaned = messy.copy() cleaned['name'] = cleaned['name'].str.strip().str.title() # trim whitespace, then 'Title Case' cleaned['score'] = cleaned['score_text'].astype(int) # text '92' -> real integer 92 print(list(cleaned['name'])) print(f'Total score: {cleaned["score"].sum()}') # only works because score is now numeric, not text
🚫
Summing a text column silently does string concatenation, not addition — '92' + '75' gives '9275', not 167, and pandas won't warn you. Always confirm a column's dtype (df.dtypes) before trusting arithmetic on it.

Plain .astype() is fragile — it raises the moment it hits ONE value it can't convert. The real employee dataset's salary column mixes plain numbers with currency-formatted strings like "$95,432.10" — a single bad value would crash .astype(float) entirely.

Robust numeric coercion — strip formatting, THEN coerce
import pandas as pd df = pd.read_csv('employees_messy.csv') print(f'salary dtype: {df["salary"].dtype}') # object — because SOME values are text like "$95,432.10" # WRONG-ish: pd.to_numeric alone silently loses every "$"-formatted value to NaN naive = pd.to_numeric(df['salary'], errors='coerce') print(f'naive to_numeric, non-null count: {naive.notna().sum()} / {len(df)}') # RIGHT: strip currency formatting from strings FIRST, then coerce cleaned = df['salary'].apply(lambda v: str(v).replace('$','').replace(',','') if pd.notna(v) else v) salary_clean = pd.to_numeric(cleaned, errors='coerce') print(f'after stripping formatting, non-null count: {salary_clean.notna().sum()} / {len(df)}')
🚫
Real output: naive pd.to_numeric recovers only 358 of 415 values — the 41 currency-formatted strings all silently become NaN, indistinguishable from genuinely missing data unless you specifically checked the count. Stripping $/, first recovers all 399 non-null values (415 total minus the 16 genuinely missing). The fix pattern: inspect a sample of the "failed" conversions before trusting errors='coerce' — a big unexpected jump in null count almost always means a formatting issue, not real missingness.

Real categorical columns accumulate inconsistent labels from manual entry — 'eng', 'ENGINEERING', 'Engineering ' should all mean the same department.

Standardizing 18 messy department labels down to 5 canonical ones
import pandas as pd df = pd.read_csv('employees_messy.csv') print(f'distinct labels before: {df["department"].nunique()}') # canonical mapping, keyed by a normalized (stripped, lowercased) version of each messy label dept_map = { 'eng': 'Engineering', 'engineering': 'Engineering', 'sales': 'Sales', 'mktg': 'Marketing', 'marketing': 'Marketing', 'h.r.': 'HR', 'human resources': 'HR', 'hr': 'HR', 'finance': 'Finance', } department_std = df['department'].str.strip().str.lower().map(dept_map) print(f'distinct labels after: {department_std.nunique()}') print(f'still-missing after mapping: {department_std.isna().sum()}') # should equal the ORIGINAL missing count, not more
🏷️
Real output: 18 labels collapse to exactly 5, and the missing count after mapping (12) matches the original missing count exactly — proving the map covers every non-null variant that actually occurs. The real risk here: a mapping dict that's missing even one variant turns that variant into a NEW, silent NaN — always check that post-mapping missing count against the pre-mapping one; a jump means your map has a gap.

Dates are the hardest type-coercion case: they can be VALID but inconsistently formatted, or genuinely invalid.

Parsing, validating, and repairing a real mixed-format date column
import pandas as pd df = pd.read_csv('employees_messy.csv') # naive parse: pandas infers ONE format from the column and applies it uniformly naive_dates = pd.to_datetime(df['join_date'], errors='coerce') print(f'naive parse, became NaT: {naive_dates.isna().sum()} / {len(df)}') # format='mixed': let pandas infer a DIFFERENT format PER ROW instead of one for the whole column mixed_dates = pd.to_datetime(df['join_date'], format='mixed', errors='coerce') print(f'format=\'mixed\' parse, became NaT: {mixed_dates.isna().sum()} / {len(df)}') still_invalid = df['join_date'].notna() & mixed_dates.isna() print(f'genuinely unparseable strings: {still_invalid.sum()}') print(list(df.loc[still_invalid, 'join_date']))
🚫
Real output: naively parsing turns 29 values into NaT — far more than expected, because this column mixes ISO (2023-05-01), US-slash (05/01/2023), and spelled-out (May 1, 2023) formats, and pandas' default parser picks ONE format for the whole column, silently failing every row that doesn't match it. format='mixed' infers per-row and recovers all but 5 — 1 originally-empty cell plus 4 genuinely broken strings ('not_a_date', '00/00/0000', '2021-02-30' — a real calendar date that doesn't exist, and '2021-13-45'). Never trust a date column's NaT count from a naive parse — a large jump can mean "mixed formats," not "actually missing."
13.7 — Detecting and Handling Outliers

An outlier is a value that doesn't fit the rest of the data — but "doesn't fit" needs a definition. Three complementary approaches: domain rules (a human fact makes a value impossible, e.g. negative salary), the IQR method (statistically extreme relative to the middle 50% of the data), and robust statistics (comparing mean/std, which outliers distort, against median/IQR, which barely move).

Domain rules vs the IQR method, on real age and salary data
import pandas as pd df = pd.read_csv('employees_messy.csv') # domain rule: nobody employed here is under 18 or over 75 — that's a FACT about this company, not a statistic domain_bad_age = df[(df['age'] < 18) | (df['age'] > 75)] print(f'domain-rule impossible ages: {list(domain_bad_age["age"])}') # IQR method on cleaned salary (from 13.6's coercion) cleaned = df['salary'].apply(lambda v: str(v).replace('$','').replace(',','') if pd.notna(v) else v) salary = pd.to_numeric(cleaned, errors='coerce') q1, q3 = salary.quantile(0.25), salary.quantile(0.75) iqr = q3 - q1 low, high = q1 - 1.5*iqr, q3 + 1.5*iqr iqr_outliers = salary[(salary < low) | (salary > high)] print(f'IQR bounds: [{low:.2f}, {high:.2f}]') print(f'IQR-flagged salaries: {sorted(iqr_outliers.dropna().tolist())}') # robust vs non-robust: how much do these 6 values distort the mean? print(f'mean WITH outliers: {salary.mean():.2f} mean WITHOUT: {salary[(salary>=low)&(salary<=high)].mean():.2f}') print(f'median WITH outliers: {salary.median():.2f} median WITHOUT: {salary[(salary>=low)&(salary<=high)].median():.2f}')
⚠️
Real output: 3 domain-impossible ages (200, 150, -5) and 6 IQR-flagged salaries (two negative — -20000, -5000 — and four extreme highs, 198000 to 2500000). Removing the outliers barely moves the MEDIAN (75736.90 → 75338.71, a $398 shift) but moves the MEAN by over $10,500 (88717.45 → 78143.16) — exactly why the median is called "robust" and the mean isn't: a handful of extreme values can drag a mean a long way, while the median barely notices.

Detecting an outlier is only half the job — deciding its fate is the real judgment call, and it's rarely the same answer for every outlier:

  • Remove — for values that are IMPOSSIBLE (negative salary, age 200): they're errors, not real extreme cases, and keeping them only adds noise.
  • Cap / winsorize — for values that are real but extreme (a legitimately high earner): clip to the IQR boundary instead of deleting the row, keeping the rest of that row's data.
  • Transform — for a whole column that's naturally skewed (income, city population): a log transform can shrink the influence of the tail without discarding anything.
  • Retain — when the "outlier" is the actual thing you're trying to detect (fraud amounts, rare failures): removing it would delete the signal, not the noise.
13.8 — Encoding Categorical Variables

Models need numbers, not text. One-hot encoding turns a NOMINAL category (no natural order — department, city) into one 0/1 column per category. Ordinal encoding turns an ORDERED category (small/medium/large; a 1-5 rating) into a single number that preserves the order — one-hot would incorrectly imply "Marketing" and "Sales" have some numeric distance between them, which is meaningless.

One-hot for a nominal column (department, cleaned)
import pandas as pd df = pd.read_csv('employees_messy.csv') dept_map = {'eng':'Engineering','engineering':'Engineering','sales':'Sales','mktg':'Marketing', 'marketing':'Marketing','h.r.':'HR','human resources':'HR','hr':'HR','finance':'Finance'} department_std = df['department'].str.strip().str.lower().map(dept_map) onehot = pd.get_dummies(department_std, prefix='dept') print(f'columns created: {list(onehot.columns)}') print(f'shape: {onehot.shape}')
🔢
Real output: 5 new 0/1 columns, one per canonical department. performance_rating, by contrast, is ALREADY the right encoding for an ordinal scale — it's already a number (1-5) where 5 genuinely means "better than" 4, so it needs no further encoding at all; one-hot-encoding it would throw away that order for no benefit.
13.9 — Reproducible Cleaning Workflows

A cleaning script you run once, by hand, in a notebook is not reproducible — wrap the whole sequence into ONE function, taking raw data in and clean data out, so it can be rerun identically on tomorrow's export.

One function, run twice, proven identical
import pandas as pd def clean_employees(raw): df = raw.drop_duplicates(subset=['employee_id']).copy() dept_map = {'eng':'Engineering','engineering':'Engineering','sales':'Sales','mktg':'Marketing', 'marketing':'Marketing','h.r.':'HR','human resources':'HR','hr':'HR','finance':'Finance'} df['department'] = df['department'].str.strip().str.lower().map(dept_map) df['salary'] = pd.to_numeric( df['salary'].apply(lambda v: str(v).replace('$','').replace(',','') if pd.notna(v) else v), errors='coerce') df['join_date'] = pd.to_datetime(df['join_date'], format='mixed', errors='coerce') return df raw = pd.read_csv('employees_messy.csv') run1 = clean_employees(raw) run2 = clean_employees(raw) print(f'rows after cleaning: {len(run1)}') print(f'two runs identical: {run1.equals(run2)}')
♻️
Real output: two runs identical: True — because the function has no hidden state and no randomness, running it twice on the same input always gives the same output. This is the difference between "I cleaned the data" (a one-time, unrepeatable act) and "I have a cleaning PIPELINE" (a function anyone, including future-you, can re-run on a new export and trust).
13.10 — Preventing Leakage: Split Before You Fit

Every imputation value, encoding, or scaling statistic computed above was fit on the WHOLE dataset. That's fine for exploring and understanding data — but for building a model, it's data leakage: information from rows that should be "unseen test data" quietly influenced values used to train on. The fix is procedural, not clever: split first, fit cleaning statistics only on the training fold, then apply those same statistics to the test fold.

Leaky vs correct order of operations
LEAKY (common mistake):
  clean_and_impute(full_data) --> split(train, test)
  the imputed mean already "saw" every test-set value

CORRECT:
  split(full_data) --> train, test
  fit imputation mean on train ONLY --> apply that same mean to both train and test
The leak, measured — a mean that shifts depending on when you split
import pandas as pd from sklearn.model_selection import train_test_split df = pd.read_csv('employees_messy.csv') df['salary_clean'] = pd.to_numeric( df['salary'].apply(lambda v: str(v).replace('$','').replace(',','') if pd.notna(v) else v), errors='coerce') train, test = train_test_split(df, test_size=0.2, random_state=42) leaky_mean = df['salary_clean'].mean() # WRONG: computed on ALL rows, including test correct_mean = train['salary_clean'].mean() # RIGHT: computed on train rows ONLY print(f'leaky (full-data) mean: {leaky_mean:.2f}') print(f'correct (train-only) mean: {correct_mean:.2f}') print(f'difference: {abs(leaky_mean - correct_mean):.2f}') print(f'train rows: {len(train)} test rows: {len(test)}')
🚫
Real output: the leaky, full-data mean (88717.45) differs from the correct, train-only mean (91177.50) by $2,460.05 — a real, measurable difference from a mistake that produces no error, no warning, and a model that looks fine in development. The rule for every cleaning statistic (imputation values, scaler mean/std, encoding categories learned from data) is the same: fit only on the training fold, then apply — never fit — those exact values to the test fold.

  • Profile missing values first (count + %, and WHY). Then choose: mean, median, mode, or group-based imputation — each with different assumptions and risks.
  • Define your duplicate KEY before deduplicating — .duplicated()'s default (every column) can miss or over-flag duplicates depending on your real data.
  • pd.merge(..., on=key, how=...) joins tables sideways by a shared key — check row counts for accidental fan-out.
  • pd.concat([...]) stacks tables of the same shape vertically.
  • .pivot_table() reshapes long data into a wide summary grid.
  • Coerce, don't just cast — strip formatting before pd.to_numeric, use format='mixed' for inconsistently-formatted dates, and map messy categorical labels to a canonical set.
  • Outliers: detect via domain rules, IQR, or robust-vs-non-robust comparison; decide per case to remove, cap, transform, or retain.
  • Encoding: one-hot for nominal categories, ordinal/already-numeric for ordered ones.
  • Wrap cleaning in one deterministic function for reproducibility; always split before fitting any cleaning statistic, to prevent leakage.
Interview Questions
A column is 15% missing. What do you check before deciding how to handle it?▶
Why it's missing. "Missing because it doesn't exist yet" (e.g. a new hire's performance rating) needs a different treatment than "missing because of a bad export" — the first might justify leaving it missing or a placeholder category, the second is a candidate for imputation. Also check whether missingness itself correlates with anything meaningful (e.g. newer employees are disproportionately missing a rating) before picking a fill method.
What's the risk specifically introduced by group-based imputation that mean/median imputation don't have?▶
Group-based imputation can leak the group's identity into the imputed value — if the grouping column is also predictive of your target (e.g. department correlates with the outcome you're modeling), filling missing values with that group's mean effectively hands the model a hint derived from the label indirectly. It's often the better assumption when groups genuinely differ, but it needs to be justified, not applied automatically.
Why should you define a duplicate KEY before calling drop_duplicates(), instead of using the default?▶
The default checks every column for an exact match, which is often either too strict (a real duplicate that differs by one re-typed field is missed entirely) or too loose (two different real records that coincidentally share only the columns you'd naturally check on get merged into one). Defining the real business key first (e.g. an ID column) makes deduplication a deliberate, correct decision instead of an accidental one.
You call pd.to_numeric on a currency column and get a suspiciously high null count. What's the likely cause and fix?▶
The column likely mixes plain numbers with formatted strings (like "$95,432.10" or with thousands-separator commas) — to_numeric can't parse those directly and silently coerces them to NaN, which looks identical to genuine missingness. The fix is to strip the non-numeric formatting characters first (currency symbols, commas) and THEN coerce, and to always compare the before/after null count to catch this class of bug.
How do you decide whether a detected outlier should be removed, capped, transformed, or kept?▶
Ask whether the value is actually IMPOSSIBLE (a negative salary, an age of 200) — remove those, they're errors. If it's real but extreme (a legitimately very high earner), capping/winsorizing to a boundary keeps the rest of that row's data. If an entire column is naturally skewed, a transform (like log) reduces the tail's influence without deleting anything. And if the "outlier" is literally what you're trying to detect — fraud, rare failures — removing it deletes the signal you actually care about.
Why is fitting an imputation value or scaler on the full dataset before splitting into train/test considered data leakage?▶
Because that statistic (a mean, a std, a set of encoded categories) is computed using rows that should represent "unseen" future data — so information from the test set quietly influences values used during training, making evaluation on that test set overly optimistic. The fix is procedural: split first, fit every cleaning/preprocessing statistic on the training fold only, then apply those exact fitted values to the test fold without refitting.
Why wrap a data-cleaning process into a single function instead of a sequence of notebook cells?▶
A sequence of manually-run cells depends on execution order, which cells were re-run, and what state variables happen to hold — it's easy to silently get a different result the second time. A single deterministic function with no hidden state (raw data in, clean data out) can be re-run on tomorrow's export, tested, and trusted to produce identical output given identical input — the actual definition of "reproducible."
