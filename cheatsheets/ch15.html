Ch 15: ML Foundations & Workflow

Compiled from the chapter text on 2026-09-30. A study aid: the lesson has the explanations and the caveats.

In short

  • Know your dataset before modeling anything: shape, feature scales, and — critically — exactly what each target value MEANS.
  • Train / validation / test, stratified, with a fixed random_state: train fits, validation decides, test is touched exactly once.
  • DummyClassifier gives the floor every real model must beat — with a printed number, not an assumption.
  • Underfitting = too simple, bad everywhere. Overfitting = too complex, great on train, worse on test. Learning curves show this shape across many training sizes, not just one split.
  • accuracy / precision / recall / F1 — by hand or via sklearn.metrics. Choose the metric that matches the real cost of each error type, not just the highest number.
  • Data leakage — target leakage (a feature that IS the answer) and preprocessing leakage (fitting on data before splitting) both invalidate an evaluation, sometimes without even changing the score.
  • Pipeline fits every preprocessing step only on the data you give it — leakage-safe by construction, and identical preprocessing in training and inference.
  • Compare baseline → train → validation → test together, never tune against test, and document the seed/splits/model so results are reproducible.

Key ideas by section

The Real Dataset: Defining the Problem

  • Every supervised ML problem starts with a clear question: given some features (measurements), predict a target (the answer).

Separating Features from the Target

  • X (features) and y (target) must be kept strictly separate — X should NEVER contain the answer, or any column derived from it (Chapter 15.10 shows exactly how that mistake looks and what it does). load_breast_cancer() already…

  • If you train a model AND evaluate it on the exact same data, you learn nothing about whether it generalizes — a model that just memorizes the answer key will score perfectly and still fail on anything new.

Baseline First: DummyClassifier

  • Any real model that doesn't clear this bar isn't worth using.
  • Before training anything real, ask: what score would a model that learned NOTHING get? sklearn.dummy.DummyClassifier answers that precisely — e.g. strategy='most_frequent' always predicts whichever class is more common, completely ignoring the features.

Overfitting vs Underfitting

  • Underfitting: the model is too simple to capture the real pattern — it does poorly on both training AND test data. Overfitting: the model is complex enough to memorize noise and quirks specific to the training data — it does GREAT on training data but noticeably worse on test data.
  • The gap between train accuracy and test accuracy is the tell-tale sign of overfitting.

The Bias-Variance Tradeoff

  • Every model sits somewhere on this spectrum, and total error is roughly bias² + variance + irreducible noise.
  • You cannot drive both to zero at once — reducing one usually raises the other, which is exactly what depth 1 vs depth None showed above.

Classification Metrics, By Hand

  • For a binary classifier, every prediction falls into one of four buckets against the truth: True Positive (predicted 1, actually 1), False Positive (predicted 1, actually 0), False Negative (predicted 0, actually 1), True Negative (predicted 0, actually 0).

The Same Metrics via sklearn.metrics, and Choosing the Right One

  • But WHICH metric matters most depends entirely on the real-world cost of each error type — for this dataset, a false negative (predicting benign when the tumor is actually malignant) is far more dangerous than a false positive…
  • You'll never hand-roll the TP/FP/FN/TN loop in real code — sklearn.metrics provides accuracy_score, precision_score, recall_score, f1_score, and confusion_matrix, plus classification_report which prints all of them at once, per class.

Data Leakage: A Concrete Broken Example

  • Data leakage is when information that wouldn't be available at real prediction time sneaks into training, making evaluation look far better than reality.
  • The most dramatic form is target leakage: a feature that's accidentally derived from (or is nearly a copy of) the target itself — for example, a "treatment billing code" column that only gets recorded BECAUSE a diagnosis was already made.

Preprocessing Leakage: Fitting Before Splitting

  • A subtler, more common leak: fitting a preprocessing step (like StandardScaler) on the WHOLE dataset before splitting.
  • The scaler's mean/std then "sees" validation and test rows before the split ever happens — a real violation of "the model should never see test data," even though it doesn't touch y at all.

sklearn Pipeline Fundamentals

  • A Pipeline chains preprocessing and a model into ONE object with one .fit()/.predict() — and critically, when you call pipe.fit(X_train, y_train), every step inside (including the scaler) is fit ONLY on the data you pass in.
  • This makes 15.11's mistake structurally impossible to make by accident: there's no separate "fit the scaler on X" step to get wrong.
