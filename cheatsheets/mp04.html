MLOps 4: Monitoring & Drift

Compiled from the chapter text on 2026-09-21. A study aid: the lesson has the explanations and the caveats.

In short

  • Monitor four layers — service health, data quality, data drift, model performance — ordered by how fast each can detect trouble. Only the last needs labels, and it arrives last.
  • Percentiles, not means, describe latency; percentiles can't be averaged across instances (merge histograms instead).
  • An SLO defines an error budget (99.9% over 30 days = 43.2 minutes); burn rate says how fast you're spending it and is the right thing to alert on.
  • Data-quality checks (nulls, ranges, unseen categories) catch most "drift" incidents, which are really upstream bugs.
  • PSI (quantile bins from the reference, epsilon for empty bins; 0.1 / 0.25 rules of thumb) and the KS / chi-square tests detect drift — but on huge samples p-values flag meaningless shifts, so alert on effect size.
  • Use label-free signals (prediction distribution, input drift) as early warning and evaluate accuracy on matured cohorts; concept drift can move accuracy without moving any distribution.
  • Prevent alert fatigue with consecutive windows and hysteresis; gate releases with shadow/canary comparisons and an automated promote / hold / rollback policy.

Key ideas by section

What to Monitor: Four Layers, and Why Accuracy Alone Is Too Late

  • A model in production is two systems stacked on top of each other: a service (it can be slow, crash, or run out of memory like any other API) and a statistical artifact (it can quietly get worse while the service is perfectly healthy).
  • The engineering answer is to watch the label-free layers as early-warning signals, and treat accuracy as the slow, authoritative confirmation.
  • A model that returns HTTP 200 in 20 ms with garbage predictions looks green on every infrastructure dashboard.

Latency Percentiles: Why the Mean Lies

  • Some tools use the nearest-rank definition instead, which always returns a real observation.
  • Users experience the tail, so operators watch percentiles: p50 (the typical request), p95 and p99 (the slow tail that a real fraction of users hit on every session).
  • Average latency is the most common wrong number on a dashboard.

SLIs, SLOs, Error Budgets and Burn Rate

  • The gap between 100% and your SLO is the error budget — the amount of unreliability you are allowed to spend on deploys, experiments, and incidents.
  • Burn rate tells you how fast you're spending the budget: the observed error rate divided by the error rate the SLO allows.
  • That's why the SLO is a product decision and not "as high as possible": every nine costs real engineering effort.

Data Quality Checks: The Cheapest Drift Detector

  • The majority of "model drift" incidents are really upstream data bugs: a column that started arriving null, a unit change (dollars to cents), a new category the encoder has never seen, a timestamp in the wrong timezone.
  • Two habits make these checks useful: keep the valid ranges and known categories in a versioned data contract next to the model rather than hard-coded in the check, and alert on the rate over a batch, not on single rows, so one malformed request doesn't page anyone.
  • These checks are cheap, need no reference distribution, and catch problems within minutes.

Data Drift I: Population Stability Index From Scratch

  • First, the bins must come from the reference — cut it into quantiles so each reference bin holds an equal share, then count current data against those same cut points.
  • PSI compares the distribution of one feature between a reference (usually the training data) and current production data.
  • The verdict column uses the industry rule of thumb: below 0.1 stable, 0.1 to 0.25 moderate, above 0.25 major.

Data Drift II: KS Test, Chi-Square, and When p-Values Mislead

  • PSI is a heuristic; the two-sample Kolmogorov–Smirnov (KS) test is a proper statistical test for numeric features.
  • For categorical features the equivalent is a chi-square test on the category counts.
  • That is the trap: with enough rows, any difference — however meaningless — becomes statistically significant.

Prediction Drift and Delayed Labels

  • The proper accuracy number can only be computed on matured cohorts: predictions old enough that their label has arrived.
  • That is concept drift in miniature — the prediction distribution didn't move, the model just became wrong.
  • The distribution of predictions (the mean score, the share of positive predictions) is a free, label-free signal: if the model suddenly flags 80% of requests instead of 60%, either the inputs changed or the model is misbehaving — either way, look now.

Alerting Without Flapping: Hysteresis and Consecutive Windows

  • This is alert fatigue, and it is a design bug, not a people problem.
  • Two standard cures: require the condition to hold for N consecutive windows before firing, and use hysteresis — clear only when the metric drops well below the firing threshold, again for several consecutive windows.
  • Also give alerts a severity: a moderate PSI (0.1–0.25) should open a ticket for business hours, a major one should page, and every page should link to a runbook that says what to check first.

Canary, Shadow, and Automated Rollback

  • In a canary deployment a small slice (say 5%) of real traffic is actually served by the new model, so you see genuine service metrics and behavior before committing.
  • In a shadow deployment the new model receives a copy of live traffic but its answers are discarded — you compare it against the current model at zero user risk, at the cost of running two models and never seeing real user reactions.
  • A low agreement rate is not automatically bad — a better model is supposed to disagree with the old one on some requests — so it triggers a hold that needs a label-based or business-metric comparison rather than a blind rollback.

Exposing Metrics in Production (Reference Only)

  • The three metric types map onto what you just built: a counter feeds error-rate and burn-rate math, a gauge carries a drift score so an alert rule can apply the same hysteresis logic, and a histogram is the only correct way to get a fleet-wide p95.
  • The underlying ideas are the ones you just implemented.
  • Dedicated drift libraries (Evidently, WhyLabs, NannyML and others) package the statistical tests from 4.5–4.6 with reports and dashboards; their APIs change between versions, so check the current documentation before copying snippets from older tutorials.

Watch out

  • You cannot average percentiles. If instance A serves 1,000 requests with p95 = 50 ms and instance B serves 10 requests with p95 = 900 ms, the "average p95" of 475 ms is nonsense — nearly every user saw ~50 ms.
  • What PSI hides. (1) The value depends on the number and placement of bins — 5 bins and 20 bins give different numbers for the same data, so fix the binning per feature and keep it fixed.
