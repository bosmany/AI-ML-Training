MLOps 2: Experiment Tracking & Model Registry

Compiled from the chapter text on 2026-09-21. A study aid: the lesson has the explanations and the caveats.

In short

  • A run record is more than params + metrics: pin the data hash, git commit, environment, seed and artifact checksums, or the run cannot be reproduced.
  • Log metrics per step so you can tell best from last, quantify overfitting, and implement early stopping. Compare runs on the same footing.
  • Break ties with an explicit total ordering (metric, then cost, then run_id) — never rely on row order.
  • A registry gives each model an immutable version and a lifecycle; exactly one version serves as Production, and modern tools move aliases instead of fixed stages.
  • Promotion is a gate, not a feeling: metric floor, margin over production, passing validation, no open data-quality flags — and the gate returns all reasons it failed.
  • Rollback is a history lookup if every transition is recorded; lineage and a model card make the deployed model auditable.

Key ideas by section

What Goes Into an Experiment Record (and Why "I Remember the Settings" Fails)

  • A run record is more than params and metrics: it also pins the data version (a hash of the training data), the code version (git commit), the environment (Python and library versions), the random seed, and the artifacts the run produced (model file, plots) by checksum.
  • Six weeks later someone asks "which run produced the model that's in production, and can we rebuild it?" and nobody can answer. Experiment tracking is the discipline of writing down, automatically, everything needed to answer that question.
  • Every ML team starts the same way: a notebook, a few good runs, and a spreadsheet of numbers.

A Tiny Tracker: Run and Tracker

  • MLflow, Weights & Biases, Neptune and Comet all boil down to the same small object model: a run holds params, stepped metrics, tags and artifact checksums; a tracker creates runs and keeps them.
  • Two behaviors are worth copying exactly: params are write-once (silently overwriting a param would make the record lie), and a crashed run is still recorded with status FAILED — the failures are often the most informative rows.
  • Building a 40-line version makes every real tool's API obvious.

Stepped Metrics: Final vs Best vs Last

  • The same history drives early stopping: stop after patience steps without improvement and keep the checkpoint from the best step.
  • Log a metric per step (epoch or iteration) and you can answer three different questions: what was the best value and when, what was the last value (what you actually shipped if you didn't checkpoint), and how big the gap is.
  • A validation loss that bottoms out at epoch 3 and then rises is the signature of overfitting, and the last-vs-best gap quantifies it.

Comparing Runs: DataFrames and Deterministic Tie-Breaking

  • Fix it with an explicit total ordering: metric (descending), then a cost such as training time (ascending), then run_id as the final, always-unique tiebreaker.
  • Three runs at val_auc = 0.912 and code that just takes the first row will pick a different "winner" whenever the row order changes — a different machine, a re-sorted export, a parallel sweep finishing in another order.
  • Once you have dozens of runs, you compare them as a table: one row per run, param columns plus a metric.

Hyperparameter Grids with itertools.product

  • A grid search is the cross product of the values you list for each hyperparameter: 3 learning rates × 3 depths = 9 runs. itertools.product generates it lazily and in a stable order, so run ids line up between reruns.
  • The training call below is a deterministic stand-in formula (no randomness), which keeps the output identical everywhere.
  • Every combination becomes a tracked run — including the bad ones, because a sweep that only records winners can't tell you the shape of the search space.

A Model Registry: Versions and Stages

  • The invariant that matters most: at most one version per model is in Production, so promoting a new version must archive the old one in the same operation.
  • A tracker answers "what did we try?" A model registry answers "what are we serving, and what is allowed to serve?" It stores each registered model as an immutable numbered version that points back to the run that produced it…

Promotion Gates and Rollback

  • A promotion gate lists the conditions a candidate must meet, and returns all the reasons it failed (a list is far more useful in CI than a bare False).
  • The other half is rollback: because every transition is written to a history list, restoring the previous production version is a lookup, not an archaeology project.
  • Typical gates: a metric floor, a required margin over the current production model (small gains are usually noise), a passing validation suite, and no open data-quality flags.

Semantic Versioning, Model Cards, and Lineage

  • A model card is the human-readable record next to the artifact — intended use, what it must not be used for, metrics (including the worst segment, not just the average), limitations.
  • And lineage ties the deployed model back to the exact run, data hash, code commit, params, seed and environment — the difference between "we think this is the model" and an answer an auditor accepts.
  • Consumers of a model care about something else: will my integration break? Semantic versioning answers that for models: bump MAJOR when the input/feature contract or the metric definition changes (callers must change), MINOR when…

Watch out

  • The falsy-zero bug. not record.get("seed") treats seed=0 as "missing" because 0 is falsy.
