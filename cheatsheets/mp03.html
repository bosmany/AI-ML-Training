MLOps 3: Pipelines & Orchestration

Compiled from the chapter text on 2026-09-21. A study aid: the lesson has the explanations and the caveats.

In short

  • A pipeline is a DAG stored as data — task → dependencies — so it can be validated, drawn and scheduled before anything runs. Cycles are deadlocks and are rejected at parse time.
  • Kahn's algorithm gives a deterministic run order and detects cycles for free. The 'blocked tasks' it reports include innocents downstream of the cycle.
  • Wall-clock time is set by the critical path, not the task count. Optimise tasks on it; ignore the rest.
  • Failure propagation: run a task only if all upstream succeeded, otherwise skip it; independent branches continue. Never run on stale or partial inputs.
  • Retry transient errors with capped exponential backoff (plus jitter); never retry deterministic bugs. Retries only make sense for idempotent tasks.
  • A cache key (name + code version + params + upstream keys) lets unchanged work be skipped; failures are never cached.
  • Derive partitions from the logical date, not now(); a run fires after its interval ends. Backfill deliberately, and bound catchup with max_active_runs.

Key ideas by section

Why Pipelines, Not One Giant Script

  • Everything in this chapter — and everything Airflow, Prefect, Dagster and Kubeflow do — is a variation on those five.
  • Every ML system starts as one notebook or one train.py.
  • Then it gets put on a schedule, and it starts failing at 3 a.m. — usually at the last step, after two hours of work.

A DAG Is Just Data: Task → Dependencies

  • The dependency structure of a pipeline is a DAG — a directed acyclic graph.
  • A task with no dependencies is a root, a task nothing depends on is a leaf, and everything that has to wait for a task is downstream of it.
  • The example below is the pipeline the rest of the chapter reuses: two ingests feed validation, which fans out to feature building and data docs; two models train in parallel; and a quality gate decides whether the winner may be registered.

Topological Sort (Kahn's Algorithm) and Readable Cycle Errors

Parallel Levels and the Critical Path

  • A task's level is the length of the longest chain of dependencies leading to it (roots are level 0).
  • But wall-clock time is not the sum of task durations and not the number of levels either: it is the duration of the slowest chain, the critical path.
  • Speeding up train_lr or data_docs buys nothing here, because neither sits on the critical path; shaving minutes off featurize or train_rf shortens every single run.

Failure Propagation: Skip Downstream, Keep Independent Branches

  • If any upstream task failed or was itself skipped, the task is marked skipped (Airflow calls it upstream_failed) and never starts.
  • Orchestrators let you override this per task — Airflow's trigger rules (all_done for cleanup, one_failed for alerting) — but the default is the one to reason from.
  • The standard rule: a task runs only if every upstream task succeeded.

Retries: Attempt Counting, Backoff, and What NOT to Retry

  • A retry policy has four parts — a maximum number of attempts, a delay between attempts that grows (exponential backoff: 2 s, 4 s, 8 s…), a cap on that delay, and a rule for which errors are retryable.
  • Many production failures are weather, not bugs: a connection reset, a 503, a spot instance reclaimed mid-task.
  • A ValueError from a missing column will fail identically on every attempt; retrying it burns time, hides the bug, and delays the alert.

Caching: Skip Steps Whose Inputs Have Not Changed

  • The fix is a cache key: a hash of everything that determines a task's output — its name, its code version, its parameters and the keys of its upstream tasks.
  • Re-running a fifteen-minute ingest because you tweaked a training hyper-parameter is pure waste.
  • Including the upstream keys is what makes a change propagate: alter featurize and its key changes, so the keys of everything after it change too, while ingest and validate are untouched.

Idempotency: Safe to Run Twice

  • An orchestrator gives you at-least-once execution: after a timeout it cannot know whether the task finished, so it runs it again.
  • A task is idempotent when running it N times leaves the world in the same state as running it once.
  • The classic bug is a load that appends: the write succeeds, the acknowledgement is lost, the retry appends again, and the table now holds duplicates that quietly corrupt every metric downstream.

Logical Dates, Backfills and Catchup

  • A daily run is identified by its logical date (Airflow: ds, or logical_date since 2.2): the start of the data interval it processes.
  • Mixing the two up is the most common off-by-one bug in data engineering, and the cure is one rule: a task must derive its partition from the logical date the orchestrator hands it, never from datetime.now().
  • A backfill deliberately re-runs a range of past partitions (after a bug fix, or a new column). Catchup is the scheduler doing it automatically — creating a run for every interval missed since the DAG was last active.

Watch out

  • Why acyclic?If a waits for b and b waits for a, neither can ever start. A cycle is a deadlock written down, so orchestrators reject cyclic graphs at parse time.
  • The 'blocked' list is bigger than the cycle.Task e is not part of the cycle — it is merely downstream of it, so it is blocked too.
  • Never run a task on stale or partial upstream output.A green run that registered a model built from yesterday's features is far worse than a red run that registered nothing.
  • Three ways a cache silently lies to you.1. Leaving the code version out of the key, so an edited task still serves its old result. 2. Serialising params without sort_keys=True, so equal dicts hash…
  • Catchup can take a system down.Unpause a daily DAG after a month and catchup=True queues thirty runs at once, all hammering the same source database and the same worker pool.
