DevOps 1: Log Parsing & Text Processing

Compiled from the chapter text on 2026-09-21. A study aid: the lesson has the explanations and the caveats.

In short

  • Stream, don't slurp — iterate the file / use generators; remember generators are single-use.
  • Named groups + compile once + non-greedy or negated classes — and watch for catastrophic backtracking.
  • Never crash on a bad line — return None, count skips, and alert on the skip ratio.
  • Normalise, then count — UTC timestamps, query-stripped paths; Counter memory scales with distinct keys.
  • Percentiles over averages, sliding windows over fixed buckets — and know why you cannot average percentiles.

Key ideas by section

What a Log Is, and Why DevOps Engineers Read Them

  • A log is a diary a program writes: one line of text per event, appended in time order.
  • Engineers read logs because a live production system cannot be paused and inspected; the log is the only witness.
  • Almost every log question is one of four: what happened, when, how often, to whom.

Anatomy of a Log Line: Two Real Formats

  • A log line has a format: fields in a fixed order, separated by spaces, with quotes and brackets around fields that contain spaces.
  • nginx access lines carry IP, time, request, status code, bytes, referrer, user agent and request time. sshd lines carry a timestamp, host, program and a free-text event.
  • split() is quick, but fixed positions silently break when a field contains spaces or is missing.

Reading Big Files Lazily: Generators, Not .read()

  • .read() and .readlines() load the whole file into memory; for line in f reads one line at a time.
  • A generator function uses yield: it hands back one value, pauses, and resumes on the next request.
  • Chaining generators builds a lazy pipeline where memory depends on one item, not the whole file.

Regular Expressions From Zero, Part 1: Literals, Classes, Quantifiers

  • A regex describes the shape of text. re.search finds the first fit (or None); re.findall lists all fits.
  • Literals match themselves. Classes (\d, \s, \w, [abc], [^"], .) match ONE character from a set.
  • Quantifiers (+, *, ?, {n}) say how many times; anchors like $ match positions.

Regular Expressions, Part 2: Groups, Named Groups, and the Greedy Trap

  • Parentheses capture pieces. Named groups (?P<name>...) let you read m["name"] or m.groupdict().
  • Greedy quantifiers take as much as possible and back off. Lazy (*?) takes as little as possible. A negated class such as [^"]* is the precise choice.
  • | means or, (?:...)? makes a chunk optional, and re.VERBOSE with comments makes long patterns readable. Compile once with re.compile.

From Text to Typed Records (Without Crashing on Bad Lines)

  • Regex groups return strings. Convert to int and float once, at the edge, and keep real types afterwards.
  • The robust pattern is: return None for a line you cannot parse, count it, and carry on.
  • A dataclass is a named-field record: a tidy row with typed fields.
  • Raw strings are hard to work with; a dataclass with real types (an int status, a float latency, a timezone-aware datetime) is not.

Counter: Top-N Anything

  • Top-N questions are "count each item, then rank". A plain dict raises KeyError on a missing key; Counter treats it as 0.
  • Two habits separate a good answer from a sloppy one: normalise before you count (drop the ?query so /orders?id=1 and /orders?id=2 are one endpoint), and remember that memory grows with the number of distinct keys, not with the number of lines.
  • .most_common(n) returns the top n as (item, count) pairs.
  • "Top 10 IPs", "most requested endpoints", "status code distribution", "busiest user agents": these are all the same operation. collections.Counter is a dict subclass that counts hashable items, and .most_common(n) returns the top n as (item, count) pairs.

Time: Parsing Timestamps, Time Zones, Bucketing, and Error Rates

  • Log timestamps are text. strptime(text, format) makes a real datetime, and strftime turns one back into a label such as an hour bucket.
  • The UTC offset tells you how a local clock relates to UTC. Convert to UTC early with .astimezone(timezone.utc).

Reading Logs Lazily: Generators, Not .read()

  • A Python file object is already a lazy iterator: for line in f reads one line at a time, so memory stays roughly constant no matter how large the file is.
  • A generator function (any function with yield) lets you build a pipeline of small lazy steps — read, parse, filter, aggregate — without ever holding the whole file.

Regex for Log Lines: Named Groups and the Greedy Trap

  • str.split() is enough for simple whitespace-separated formats, but the nginx/Apache combined format has quoted fields that contain spaces (the request line and the user agent), so split() breaks on them.
  • The single most common regex bug in log parsing is greediness. .* takes as much as it can, so ".*" on a line with two quoted fields matches from the first quote to the last.

  • Parse the stamp with datetime.strptime using %z to capture the UTC offset, convert to UTC, and build a sortable key with strftime("%Y-%m-%d %H:00") (per hour) or "%H:%M" (per minute).

Latency Percentiles: Why the Average Lies

  • The nearest-rank method is the simplest: sort, take rank ceil(p/100 × n).
  • Latency has a long tail, so SLOs are written in percentiles: p50 is the typical request, p95 and p99 are what your slowest users feel.

Detecting Brute Force: The Sliding Window

  • The correct tool is a sliding window: keep a deque of recent timestamps per IP, and on each new event push it and pop from the left everything that has fallen out of the window. deque.popleft() is O(1), while list.pop(0) is O(n).
  • Each event is added once and removed once, so the whole pass is linear.

grep / awk / sort | uniq -c, and When the Shell Wins

  • In an interview, saying "I would start with a one-liner to look, then write a script once it needs to be repeatable" is exactly the right instinct.
  • Every Python idea above has a classic shell one-liner, and a good engineer knows both and picks deliberately.

Watch out

  • Following a log as it grows (tail -f)Watching a log live is the same idea as a generator with a loop that waits for new data.
  • Catastrophic backtracking is a real outage causeA pattern with nested quantifiers such as (a+)+$ can take exponential time on a line that almost matches, and one corrupted log line can pin a CPU (this is "ReDoS").
  • Cardinality is the hidden costA Counter's memory grows with the number of distinct keys (its cardinality), not with the number of lines. Fifty million lines from 200,000 distinct IPs is small.
  • Time is where log analysis goes wrongnginx writes local time plus an offset. syslog and auth.log lines (the sshd format from section 1.2) have no year and no time zone at all, so you must supply the year yourself and know which zone the server used.
  • A generator is single-use. After it is exhausted it silently yields nothing, so a second list(gen) returns [], not an error.
  • Reference code — not runnable in this browser. The sandbox has no real growing log file and no real clock, so there is no ▶ Run button on the next block. Copy it to a real machine to try it.
