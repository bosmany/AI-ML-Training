Ch 37: Dependency Injection & Error Handling

Compiled from the chapter text on 2026-09-21. A study aid: the lesson has the explanations and the caveats.

In short

  • Depends() shares setup logic across endpoints — functions or classes both work as dependencies.
  • Dependencies can depend on other dependencies — FastAPI resolves the whole chain for you.
  • HTTPException turns a failed lookup into a clean, structured error response instead of a crash.
  • Custom exceptions + @app.exception_handler keep business logic decoupled from HTTP status codes.
  • app.dependency_overrides swaps a real dependency for a test double, without touching route code.

Key ideas by section

Depends(): Sharing Logic Across Endpoints

  • A dependency is just a normal function; wrapping a parameter in Depends(that_function) tells FastAPI to call it first and pass its return value in.
  • Plenty of endpoints need the same setup: pagination, an auth check, a database session.
  • Writing that logic inside every route function duplicates it everywhere and duplicates every future bug fix too.

Class-Based Dependencies

  • FastAPI calls the class like a function (i.e. constructs an instance), so its __init__ parameters are parsed exactly like a function's would be.
  • This is useful when several related query parameters belong together as one object.
  • A dependency doesn't have to be a plain function — any callable works, including a class.

HTTPException

  • FastAPI catches it and converts it into a clean JSON error response with the status code and detail message you chose.
  • When a lookup fails inside a route, raise fastapi.HTTPException instead of letting a plain KeyError escape as an unhandled 500.

Custom Exception Classes & Handlers

  • HTTPException is fine for simple cases, but it couples your business logic directly to HTTP concerns.
  • A cleaner pattern for larger apps: raise a plain, framework-agnostic Python exception from your domain logic, then register an @app.exception_handler(...) that converts it into an HTTP response in exactly one place.

Sub-Dependencies

  • This is how larger apps compose small, single-purpose dependencies (get the DB session → get the current user from a token → check the user is an admin) into one route parameter.
  • Dependencies can depend on other dependencies — FastAPI resolves the whole chain automatically.

Status Code Cheat-Sheet

  • Picking the right status code is part of designing a clean API.

Testing With Dependency Overrides

  • Tests shouldn't depend on a real database or a real third-party service just to exercise route logic. app.dependency_overrides[original] = replacement swaps out any dependency for a test double, for the lifetime of the TestClient — the route code itself never changes.

Watch out

  • Reference code — run it in the Colab notebook, not here Every code block in this chapter needs a real FastAPI/Starlette install, so there's no "▶ Run" button.
  • Register exception handlers (and middleware) before the app handles its first request. Starlette builds and caches its handler stack on the first call, so a handler added afterwards is silently…
  • Always clear overrides after a test — app.dependency_overrides is shared, mutable state on the app object. Leaving an override in place leaks into every test that runs after it in the same process.
