MLOps 1: Reproducibility & Data Validation

Compiled from the chapter text on 2026-09-21. A study aid: the lesson has the explanations and the caveats.

In short

  • Reproducible = five pins: code, data, config, environment, randomness — captured in a hashed run manifest.
  • Seed with local generators and per-stage child streams, and assert on properties, never on raw draws.
  • Fingerprint data in canonical form (sorted, fixed float format, explicit nulls) so only real changes change the hash.
  • Audit requirements: pinned vs ranged vs unpinned; lock transitive dependencies.
  • Data checks are unit tests for data — a structured report, run first, blocking on failure, thresholds from history.
  • Contracts = schema + semantics + SLA + owner + version; pydantic validates records at boundaries, pandas validates in bulk.
  • Leakage and skew explain "great offline, bad in production": time/group splits, features unavailable at prediction time, training-vs-serving stats.

Key ideas by section

What "Reproducible" Actually Requires

  • The habit that makes this practical is a run manifest: one small, canonical JSON document listing all five, hashed into a run id you store next to the model.
  • "I can't reproduce last month's model" is one of the most expensive sentences in ML.
  • Miss one and "same code" still gives a different model.

Seeding Correctly

  • The classic mistake is one shared random stream consumed by several stages (split, augmentation, weight init): change the order or the number of draws in one stage and every stage after it silently changes too.
  • Prefer local generators (np.random.default_rng(seed), random.Random(seed)) over global state, and derive an independent child stream per stage from one root seed with SeedSequence.spawn — then reordering stages cannot change the train/test split.
  • Fewer people know why it still fails.

Dataset Fingerprinting

  • A fingerprint is a hash of a dataset's canonical form, stored in the run manifest.
  • If the data can change without anyone noticing, you cannot reproduce anything.
  • The word that matters is canonical: two files with identical content but different row order, column order, float formatting or NaN spelling must hash the same, or you will drown in false alarms and start ignoring the alarm.

Capturing and Auditing the Environment

  • Every line of a requirements.txt is one of three kinds: pinned (==: exactly this version), ranged (>=, ~=: any version in a window) or unpinned (a bare name: whatever is newest today).
  • An import numpy that works today and breaks next month usually means a dependency floated.
  • Reproducible builds want everything pinned — including transitive dependencies you never wrote down, which is why teams keep a human-edited requirements.in and compile it into a fully pinned lock file.

Data-Quality Checks as a Pass/Fail Report

  • Return a structured report — check name, pass/fail, detail — not a bare assert: a report can be logged, diffed between runs, and turned into an alert that says which check failed and by how much.
  • Data checks are unit tests for data.

Row-Level Validation and Data Contracts with pydantic

  • The model doubles as a data contract written in code: field types, ranges (Field(ge=..., le=...)), allowed values (Literal) and, with extra='forbid', a rule that unexpected columns are violations rather than silently ignored.
  • pandas checks are column-wise and vectorized; pydantic v2 validates one record at a time against a typed model, which is exactly what you want at a boundary — a request payload, a message from a queue, a sample of a new feed.
  • Each error carries a location and a machine-readable type, so you can count failures by field.

Leakage and Train/Serve Skew

  • (b) Target leakage: a feature that is really a consequence of the label — a cancel_reason field that support fills in after the customer churns.
  • Leakage means the model saw information at training time that will not exist at prediction time — so the offline metric is fiction.
  • The fixes are a time split (optionally with an embargo gap when labels take days to resolve) and a group split (a customer lives entirely on one side).

Tools You Will Meet: pandera, Great Expectations, DVC

  • Everything above is what these tools do for you at scale. pandera lets you declare a DataFrame schema (dtypes, checks, uniqueness) and validate it — with lazy=True it reports all failures instead of stopping at the first. Great…

Watch out

  • Never assert on raw random draws — assert on properties ("same seed gives identical output", "split is disjoint").
  • Floats and dtypes are the usual culprits. 0.1 + 0.2 != 0.3, and the same number can come back as 1.0000000000000002 from a different machine or aggregation order — so fix the digits you hash.
  • Reference-only. pip, uv and Docker need a real operating system, which this in-browser Python does not have — run these on your own machine. The parsing logic above is the part you can practice here.
  • Use the right tool for the volume. Validating millions of rows one pydantic object at a time is slow.
  • The interview tell. "Offline AUC 0.99, production is a coin flip" almost always means leakage or skew, not a bad algorithm.
  • Reference-only. pandera, Great Expectations and DVC are not available in this in-browser Python (DVC also needs git and remote storage).
