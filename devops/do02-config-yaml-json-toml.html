DevOps Python 2:
Config & Data Formats

Almost everything a DevOps or platform engineer touches is configuration: Kubernetes manifests, Terraform plans, docker-compose files, CI pipelines, Helm values, .env files. This chapter is about reading, validating, diffing and policing that data in Python — and about the traps that cause real outages: YAML that silently turns NO into False and 22:22 into 1342, config loaded with an unsafe parser, environment strings that are never converted to real types, and drift between what git says and what is actually running. These are also exactly the topics interviewers use to tell whether you have operated real systems.

2.1 — JSON: Nested Data, Safe Access, and Stable Output

JSON is the lingua franca of infrastructure: cloud APIs, kubectl get -o json, Terraform plans, CI job output and log pipelines all speak it. The parsing is one line (json.loads); the daily work is reaching into deeply nested data without crashing and producing output that is stable enough to diff and hash. Real API responses are irregular: a field that exists on 90% of objects is missing on the rest, and a script that indexes blindly with d["a"]["b"]["c"] dies on the first exception at 3 a.m.

Blind indexing vs .get chains on a deployment status document
import json raw = ''' { "service": "checkout", "deploy": { "strategy": "rolling", "replicas": {"desired": 6, "ready": 4} }, "endpoints": [ {"name": "http", "port": 8080}, {"name": "metrics", "port": 9090} ] } ''' cfg = json.loads(raw) # Blind chained indexing: one missing key anywhere = KeyError try: print(cfg["deploy"]["autoscaling"]["max"]) except KeyError as e: print("KeyError on missing key:", e) # .get chains with defaults fail soft, but they get ugly fast max_replicas = cfg.get("deploy", {}).get("autoscaling", {}).get("max", "not set") print("max_replicas:", max_replicas) replicas = cfg["deploy"]["replicas"] print("not ready:", replicas["desired"] - replicas["ready"])

Once you have more than two levels, a tiny path helper reads far better than chained .get() calls. This is a miniature version of what jq does on the command line:

A mini jq: dig() with dotted paths and list indexes
import json def dig(data, path, default=None): """dig(cfg, 'endpoints.1.port') -> value, or default if any step is missing.""" cur = data for part in path.split("."): if isinstance(cur, list): try: cur = cur[int(part)] except (ValueError, IndexError): return default elif isinstance(cur, dict) and part in cur: cur = cur[part] else: return default return cur cfg = json.loads('{"deploy": {"replicas": {"ready": 4}}, "endpoints": [{"port": 8080}, {"port": 9090}]}') print(dig(cfg, "deploy.replicas.ready")) print(dig(cfg, "endpoints.1.port")) print(dig(cfg, "deploy.autoscaling.max", "n/a")) print(dig(cfg, "endpoints.5.port", "n/a"))

Stable output: sort_keys, canonical form, and hashing

Two configs that mean the same thing can serialize differently just because a dict was built in a different order. That makes git diff noisy and breaks any hash you compute over the text. The fix is a canonical form: sort_keys=True and fixed separators. Kubernetes tooling uses the same trick — Helm charts commonly hash the rendered ConfigMap into a pod annotation (checksum/config) so that a config change automatically rolls the pods.

Canonical JSON: same config, same text, same hash
import json, hashlib a = {"replicas": 3, "image": "api:1.4", "env": {"B": "2", "A": "1"}} b = {"env": {"A": "1", "B": "2"}, "image": "api:1.4", "replicas": 3} # same config, different key order print("raw dumps equal: ", json.dumps(a) == json.dumps(b)) def canonical(d): return json.dumps(d, sort_keys=True, separators=(",", ":")) print("canonical dumps equal:", canonical(a) == canonical(b)) print("sha256 a:", hashlib.sha256(canonical(a).encode()).hexdigest()[:12]) print("sha256 b:", hashlib.sha256(canonical(b).encode()).hexdigest()[:12]) print(json.dumps(a, sort_keys=True, indent=2))
⚠️
JSON gotchas that bite in production. There are no comments and no trailing commas (a config file that needs either is not JSON). Duplicate keys are silently accepted and the last one wins. Python's json happily reads NaN and Infinity, which are not valid JSON and will break strict consumers. And integers beyond 253 are exact in Python but lose precision in JavaScript, so a large numeric ID that round-trips through a JS dashboard can change value — ship such IDs as strings.
2.2 — YAML with PyYAML: safe_load, Multi-Document Streams, Anchors

YAML is what humans write: Kubernetes manifests, Helm values, docker-compose, GitHub Actions, Ansible playbooks. In Python that means PyYAML (import yaml). The single most important rule: always use yaml.safe_load, never a bare yaml.load. The full loader can construct arbitrary Python objects, which means a YAML document can name any callable and have the parser itself call it while loading. The demo below uses a harmless print; a real attacker names os.system or subprocess.Popen.

yaml.safe_load refuses what the full loader will happily execute
import yaml evil = "x: !!python/object/apply:builtins.print ['this ran at PARSE time']" # safe_load only builds plain data: dict, list, str, int, float, bool, None, date try: yaml.safe_load(evil) except yaml.YAMLError as e: print("safe_load refused:", type(e).__name__) # The unsafe loader calls ANY callable the document names. Here it is a harmless print(). yaml.load(evil, Loader=yaml.UnsafeLoader)
⚠️
This is not theoretical. Config files arrive from pull requests, Helm charts pulled from the internet, and CI artifacts. Loading any of them with an unsafe loader turns "parse a file" into "run code from a stranger". PyYAML 6 made the Loader argument mandatory for yaml.load precisely because so many people were doing this by accident. Linters flag it too (Bandit rule B506).

Kubernetes tooling emits several documents in one file separated by ---, and docker-compose uses anchors (&name), aliases (*name) and the merge key (<<) to avoid repeating settings. safe_load_all returns one object per document; note that a trailing --- produces an empty document (None) you should filter out.

Multi-document manifests, anchors and merge keys
import yaml manifest = """ apiVersion: v1 kind: Service metadata: {name: web} --- apiVersion: apps/v1 kind: Deployment metadata: {name: web} --- """ docs = [d for d in yaml.safe_load_all(manifest) if d] # trailing --- yields None print([(d["kind"], d["metadata"]["name"]) for d in docs]) compose = """ x-defaults: &defaults restart: always mem_limit: 256m services: web: <<: *defaults mem_limit: 512m worker: <<: *defaults """ services = yaml.safe_load(compose)["services"] print(services["web"]) print(services["worker"]) print(yaml.safe_dump(services["web"], sort_keys=False))
⭐
Writing YAML back out: yaml.safe_dump(data, sort_keys=False) keeps your key order (PyYAML sorts keys by default, which scrambles hand-written files). Be aware that PyYAML does not preserve comments when you load and dump — if a script must edit a human-maintained file in place, reach for ruamel.yaml, which round-trips comments and formatting.
2.3 — YAML Gotchas: Type Coercion, the Norway Problem, and Base-60 Ports

YAML doesn't need quotes around strings, so the parser guesses a type for every bare word. PyYAML implements YAML 1.1, whose guesses are surprising. Every engineer who works with YAML config eventually loses an afternoon to one of these, and interviewers love asking about them:

Written in the filePyYAML gives youWhy it hurts
country: NO / answer: yes / flag: offFalse / True / False (bool)The "Norway problem": the country code NO becomes False
version: 1.101.1 (float)Trailing zero silently dropped; "1.10" and "1.1" become the same value
- 22:22 (unquoted port mapping)1342 (int)xx:yy with yy < 60 is read as a base-60 number: 22*60+22
mode: 0108 (int)Leading zero means octal — file permissions and zero-padded IDs break
when: 2024-01-05datetime.dateNot a string, and json.dumps raises TypeError on it
empty: ~None~ and null are both null
Watch the parser guess, then fix it with quotes
import yaml doc = """ country: NO answer: yes flag_off: off version: 1.10 ports: - "8080:80" - 22:22 - 5432:5432 octal: 010 when: 2024-01-05 tag: 3.10.4 """ data = yaml.safe_load(doc) for key, value in data.items(): print(f"{key:8} -> {value!r:22} {type(value).__name__}") print("--- everything a string: BaseLoader (great for linting the RAW text) ---") raw = yaml.load(doc, Loader=yaml.BaseLoader) print(raw["country"], raw["version"], raw["ports"]) print("--- fixed by quoting ---") fixed = yaml.safe_load('country: "NO"\nversion: "1.10"\nports:\n - "22:22"') print(fixed)
🧠
Why 5432:5432 survived but 22:22 did not. The base-60 rule only matches when every part after a colon is between 0 and 59. 5432:5432 doesn't qualify, so it stays a string, while 22:22 and 5:30 silently become integers. The Docker Compose docs explicitly tell you to always quote port mappings for this reason. The rule of thumb: if a value must be a string, quote it — and validate the parsed types (section 2.6) so a wrong guess fails loudly at startup instead of quietly in production.
2.4 — TOML with tomllib: Strict, Typed, and Boring (Good)

TOML is what pyproject.toml uses, and it's a popular choice for tool configuration (Ruff, Black, pytest, Poetry, Hugo). Python 3.11+ ships a reader in the standard library: tomllib. It is deliberately read-only (write with the third-party tomli_w), and it is strict: types are explicit (strings must be quoted, dates and datetimes are first-class), so there is no Norway problem — an unquoted NO is a syntax error, not a silent boolean.

Parsing a pyproject-style TOML document
import tomllib doc = """ [project] name = "billing-service" version = "2.3.1" requires-python = ">=3.11" dependencies = ["fastapi>=0.110", "pydantic>=2.6", "sqlalchemy[asyncio]>=2.0"] [tool.pytest.ini_options] addopts = "-q --maxfail=1" testpaths = ["tests"] [[tool.deploy.target]] name = "staging" replicas = 2 [[tool.deploy.target]] name = "prod" replicas = 6 released = 2024-03-01T09:30:00Z """ cfg = tomllib.loads(doc) print(cfg["project"]["name"], cfg["project"]["version"]) print(len(cfg["project"]["dependencies"]), "dependencies") print([(t["name"], t["replicas"]) for t in cfg["tool"]["deploy"]["target"]]) print(type(cfg["tool"]["deploy"]["target"][1]["released"]).__name__) # TOML has no Norway problem: an unquoted word is an error, not a silent bool try: tomllib.loads("country = NO") except tomllib.TOMLDecodeError: print("TOMLDecodeError raised - no silent coercion")

2.5 — .env Files and the Config Layering Rule

The twelve-factor app rule says configuration that varies between deploys (hostnames, credentials, feature toggles) belongs in the environment, not in code. In practice you end up with several sources at once, and the essential engineering decision is a clear precedence order. The near-universal convention is defaults < config file < environment variables < command-line flags: the more explicit and more temporary a source is, the higher it ranks. First, a hand-rolled .env parser, because understanding what python-dotenv does removes the magic:

Parse a .env file (and the classic bool("false") trap)
def parse_dotenv(text): env = {} for line in text.splitlines(): line = line.strip() if not line or line.startswith("#"): continue if line.startswith("export "): line = line[len("export "):] key, sep, value = line.partition("=") if not sep: continue value = value.strip() if len(value) >= 2 and value[0] == value[-1] and value[0] in "\"'": value = value[1:-1] env[key.strip()] = value return env dotenv = """ # database export DB_HOST=db.internal DB_PORT=5432 APP_DEBUG="false" GREETING='hello world' EMPTY= """ print(parse_dotenv(dotenv)) # Environment values are ALWAYS strings. This is the classic trap: print(bool("false")) # True - any non-empty string is truthy! def to_bool(s): return str(s).strip().lower() in {"1", "true", "yes", "on"} print(to_bool("false"), to_bool("True"), to_bool("0"))

Now the layering itself. A good resolver does three things: applies the precedence order, coerces environment strings to the type of the default, and records where each value came from — that last part turns "why is it listening on 9100?" from an hour of guessing into a one-line answer.

Resolve config across four layers and record the source of each value
DEFAULTS = {"log_level": "info", "timeout": 30, "tls": False} def coerce(value, like): if isinstance(like, bool): return str(value).strip().lower() in {"1", "true", "yes", "on"} if isinstance(like, int): return int(value) return value def resolve(defaults, file_cfg, env, cli, prefix="SVC_"): env_cfg = {k[len(prefix):].lower(): v for k, v in env.items() if k.startswith(prefix)} cfg, source = {}, {} for key, default in defaults.items(): cfg[key], source[key] = default, "default" if key in file_cfg: cfg[key], source[key] = file_cfg[key], "file" if key in env_cfg: cfg[key], source[key] = coerce(env_cfg[key], default), "env" if key in cli: cfg[key], source[key] = cli[key], "cli" return cfg, source cfg, source = resolve( DEFAULTS, file_cfg={"timeout": 60, "log_level": "warning"}, env={"SVC_TIMEOUT": "90", "SVC_TLS": "true", "HOME": "/root"}, cli={"log_level": "debug"}, ) print(cfg) print(source)

2.6 — Validating Config with Pydantic (and Never Logging Secrets)

Parsing a config file only tells you it is syntactically valid. Whether workers is a positive integer, whether port is in range, whether a required database host is present — that's validation, and doing it once, at startup is one of the highest-value habits in operations. A service that crashes at boot with "db.port: not a valid integer" costs you a minute; one that crashes on the first request at 3 a.m. because a string slipped through costs you an incident. Pydantic v2 gives you this from plain type hints. Note this chapter's Python loads Pydantic on first use, so the first run may pause a few seconds.

Typed config models, coercion, and SecretStr
from typing import Literal from pydantic import BaseModel, Field, SecretStr class DbConfig(BaseModel): host: str port: int = Field(default=5432, ge=1, le=65535) password: SecretStr class AppConfig(BaseModel): name: str workers: int = Field(default=2, ge=1, le=64) log_level: Literal["debug", "info", "warning", "error"] = "info" db: DbConfig raw = {"name": "billing", "workers": "4", "db": {"host": "db.internal", "password": "s3cr3t-p@ss"}} cfg = AppConfig(**raw) print(cfg.workers, type(cfg.workers).__name__) # "4" was coerced to the int 4 print(cfg.db.password) # masked print(repr(cfg.db)) # masked here too print(len(cfg.db.password.get_secret_value())) # you must ask for the real value explicitly

When validation fails, Pydantic reports every problem at once, with the exact location and a stable machine-readable type. Printing those as one line per problem is what turns a wall of traceback into a config error a tired on-call engineer can fix immediately:

Report every config problem at once, with its location
from typing import Literal from pydantic import BaseModel, Field, SecretStr, ValidationError class DbConfig(BaseModel): host: str port: int = Field(default=5432, ge=1, le=65535) password: SecretStr class AppConfig(BaseModel): name: str workers: int = Field(default=2, ge=1, le=64) log_level: Literal["debug", "info", "warning", "error"] = "info" db: DbConfig bad = {"name": "billing", "workers": 0, "log_level": "verbose", "db": {"host": "db.internal", "port": "54x2"}} try: AppConfig(**bad) except ValidationError as e: print(f"{e.error_count()} problems in config:") for err in e.errors(): where = ".".join(str(p) for p in err["loc"]) print(f" {where}: {err['type']}")

SecretStr protects a value only while it stays inside the model. Plain dicts leak: logging.info(config_dict) is one of the most common ways a password ends up in a log aggregator. A small recursive redaction helper is worth having anywhere you print or log configuration:

A redact() helper for anything you are about to log
import re SENSITIVE = re.compile(r"(pass(word)?|secret|token|api[_-]?key|credential)", re.I) def redact(obj): if isinstance(obj, dict): return {k: "***" if SENSITIVE.search(str(k)) else redact(v) for k, v in obj.items()} if isinstance(obj, list): return [redact(v) for v in obj] return obj print(redact({"db": {"host": "h", "password": "x"}, "api_key": "abc", "items": [{"token": "t", "id": 7}]}))
⭐
Where real secrets should live. Not in git, and ideally not in long-lived environment files either. Production setups inject them at runtime from a secret manager (AWS Secrets Manager, Vault, Kubernetes Secrets synced by External Secrets) and rotate them. Your Python's job is to receive them safely, validate they exist, never print them, and keep .env in .gitignore with a secret scanner such as gitleaks in CI as the safety net.
2.7 — Deep-Diffing Configs: The Heart of Drift Detection

Configuration drift is when what is running no longer matches what you declared: someone scaled a deployment by hand, an emergency hotfix never made it back to git, a console click changed a security group. Every drift tool — kubectl diff, terraform plan, ArgoCD's "OutOfSync" — is the same algorithm at heart: compare a desired document with a live one and report what was added, removed, or changed. That is a recursive diff, and it is short:

A recursive config differ (added / removed / changed)
def diff_config(old, new, path=""): changes = [] for key in sorted(set(old) | set(new)): here = f"{path}.{key}" if path else key if key not in old: changes.append(("+", here, None, new[key])) elif key not in new: changes.append(("-", here, old[key], None)) elif isinstance(old[key], dict) and isinstance(new[key], dict): changes.extend(diff_config(old[key], new[key], here)) elif old[key] != new[key]: changes.append(("~", here, old[key], new[key])) return changes desired = {"replicas": 3, "image": "api:1.4", "env": {"LOG_LEVEL": "info"}} live = {"replicas": 5, "image": "api:1.4", "env": {"LOG_LEVEL": "debug", "HOTFIX": "1"}} for op, path, was, now in diff_config(desired, live): print(op, path, was, "->", now)

Real objects carry volatile fields that always differ and have nothing to do with intent: Kubernetes adds status, metadata.resourceVersion, creationTimestamp and a uid to everything it stores. If you diff without removing them, every object looks drifted and the real signal drowns in noise. So drift detection is really normalize, then diff:

Normalize before you diff: strip volatile fields
import copy VOLATILE = {("status",), ("metadata", "resourceVersion"), ("metadata", "uid"), ("metadata", "creationTimestamp")} def normalize(doc): doc = copy.deepcopy(doc) for path in VOLATILE: cur = doc for part in path[:-1]: cur = cur.get(part, {}) if isinstance(cur, dict) else {} if isinstance(cur, dict): cur.pop(path[-1], None) return doc live = {"metadata": {"name": "web", "resourceVersion": "88231", "uid": "a1b2"}, "spec": {"replicas": 3}, "status": {"readyReplicas": 3}} desired = {"metadata": {"name": "web"}, "spec": {"replicas": 3}} print(normalize(live) == desired) # True - no real drift once noise is removed
🧠
Why lists are compared whole. The differ above treats a list as one value: if any element changes, the whole list shows as changed. That is deliberate for a first version — matching list items up (by name for containers, by port for ports) is a domain-specific decision that Kubernetes itself needed "strategic merge patch" to solve. Start simple, and add keyed list matching only when the noise justifies it.
2.8 — Linting Real Infrastructure YAML: Kubernetes Manifests

The most valuable use of everything above is policy checks before deploy: parse a manifest, apply rules, fail the pipeline on violations. The classic offenders, each responsible for real incidents: images pinned to :latest (a redeploy silently pulls different code), containers with no resource limits (one leaky pod starves a whole node), privileged: true (container escape = host compromise), and missing probes (traffic sent to pods that aren't ready). A Deployment nests its containers under spec.template.spec.containers, so the linter is mostly careful navigation with safe defaults.

A manifest linter with three rules
import yaml manifest = """ apiVersion: apps/v1 kind: Deployment metadata: {name: api} spec: template: spec: containers: - name: app image: myorg/api:latest securityContext: {privileged: true} - name: proxy image: envoyproxy/envoy:v1.29.0 resources: limits: {cpu: 200m, memory: 128Mi} """ def image_tag(image): last = image.rsplit("/", 1)[-1] # ignore a registry host:port prefix return last.split(":", 1)[1] if ":" in last else None def lint_deployment(doc): problems = [] name = doc["metadata"]["name"] for c in doc["spec"]["template"]["spec"].get("containers", []): tag = image_tag(c["image"]) if tag in (None, "latest"): problems.append(f"{name}/{c['name']}: unpinned image {c['image']}") if not c.get("resources", {}).get("limits"): problems.append(f"{name}/{c['name']}: no resource limits") if c.get("securityContext", {}).get("privileged") is True: problems.append(f"{name}/{c['name']}: privileged container") return problems for line in lint_deployment(yaml.safe_load(manifest)): print(line)
Reference only — Real-world tooling around this idea (reference only)
kubectl get deploy api -o json | jq '.spec.replicas' # inspect live state kubectl diff -f deployment.yaml # desired (file) vs live (cluster) kubectl apply --dry-run=server -f deployment.yaml # let the API server validate it kubeconform -strict manifests/ # schema-validate manifests offline kube-linter lint manifests/ # ready-made policy rules conftest test manifests/ -p policy/ # your own rules in OPA/Rego yq '.services | keys' docker-compose.yml # jq-for-YAML
⚠️
Reference-only: these are shell tools that need a real cluster or filesystem, so there is no Run button. Writing your own small Python linter (as above) is still valuable: it is trivial to run in CI, you control the rules, and interviewers ask you to write exactly this kind of check.
2.9 — Reading Terraform Plan JSON: Summarize Changes and Gate Dangerous Ones

terraform plan can emit a machine-readable plan (terraform show -json). Its resource_changes array lists every resource with change.actions: ["create"], ["update"], ["delete"], ["no-op"] — and a replacement appears as ["delete","create"] (destroy then recreate). That last one is the dangerous surprise: an innocent-looking change to an immutable attribute on a database replaces it. A short Python gate in CI that summarizes the plan and blocks destructive changes to stateful resources is a very common, very valuable script.

Summarize a plan and block destructive changes to stateful resources
import json from collections import Counter plan = json.loads("""{ "format_version": "1.2", "resource_changes": [ {"address": "aws_s3_bucket.logs", "type": "aws_s3_bucket", "change": {"actions": ["no-op"]}}, {"address": "aws_instance.web[0]", "type": "aws_instance", "change": {"actions": ["update"]}}, {"address": "aws_instance.web[1]", "type": "aws_instance", "change": {"actions": ["create"]}}, {"address": "aws_db_instance.main", "type": "aws_db_instance", "change": {"actions": ["delete", "create"]}}, {"address": "aws_security_group.old", "type": "aws_security_group", "change": {"actions": ["delete"]}} ] }""") def action_of(rc): actions = rc["change"]["actions"] if set(actions) == {"delete", "create"}: return "replace" return actions[0] summary = Counter(action_of(rc) for rc in plan["resource_changes"]) print(dict(summary)) STATEFUL = {"aws_db_instance", "aws_s3_bucket", "aws_ebs_volume"} blocked = [rc["address"] for rc in plan["resource_changes"] if action_of(rc) in {"delete", "replace"} and rc["type"] in STATEFUL] print("BLOCK - destroys stateful resources:", blocked)
⭐
Exit codes are part of the interface. terraform plan -detailed-exitcode returns 0 for no changes, 2 for changes and 1 for errors, so a pipeline can branch on it without parsing anything. Your gate script should follow the same convention — a non-zero exit when it finds a violation — because CI systems only understand exit codes.
DevOps Python 2 Summary
  • Parse safely: always yaml.safe_load (the full loader executes code named in the document); use safe_load_all for --- multi-document files and filter the empty trailing document.
  • Know the YAML 1.1 traps: NO/yes/off become booleans, 1.10 becomes 1.1, 22:22 becomes the base-60 integer 1342, 010 becomes octal 8, and dates aren't strings. Quote anything that must stay a string.
  • Choose the format on purpose: JSON for machines, YAML for human-written infra (with care), TOML for tool config (strict, no coercion), .env for per-deploy values that are always strings.
  • Layer config predictably: defaults < file < environment < CLI flags, coerce env strings to real types (bool("false") is True), and record which layer supplied each value.
  • Validate at startup with Pydantic: report every problem at once, use SecretStr, and redact anything you log — fail fast instead of failing at 3 a.m.
  • Drift detection = normalize, then diff: strip volatile fields, then compare desired and live recursively; kubectl diff and terraform plan are this idea at scale.
  • Write small policy gates in Python: lint manifests and gate Terraform plans, and exit non-zero on violations because CI only understands exit codes.

💼 Config & Data Formats — Interview Prep

10 questions on the exact topics DevOps, SRE and platform interviews probe when they ask about configuration: unsafe YAML loading, YAML's type-guessing traps, secrets, config layering, drift detection and Terraform plan gates. Click a question to reveal the answer.

Why is yaml.load without a safe loader dangerous, and what do you use instead?▶
The full/unsafe loader can construct arbitrary Python objects, which means a YAML document can name any importable callable (os.system, subprocess.Popen) and the parser will call it while loading — so parsing an untrusted or third-party file becomes remote code execution. Config files really do arrive from pull requests, downloaded Helm charts and CI artifacts. The fix is yaml.safe_load (or safe_load_all), which only builds plain data: dicts, lists, strings, numbers, booleans, None and dates. PyYAML 6 made the Loader argument mandatory for yaml.load for exactly this reason, and static analyzers such as Bandit flag it. A strong answer also mentions the follow-up: even with safe_load, huge or deeply aliased documents can exhaust memory (the "billion laughs" pattern), so cap input size for untrusted files.
What is the "Norway problem", and how do you protect yourself from YAML's implicit typing?▶
In YAML 1.1 (which PyYAML implements) unquoted NO, no, yes, on and off are booleans, so a list of country codes containing Norway's NO silently becomes False. The same family of surprises: 1.10 becomes the float 1.1, 010 becomes octal 8, 2024-01-05 becomes a date object, and 22:22 becomes the base-60 integer 1342. The defenses are layered: quote anything that must be a string; validate types after loading (Pydantic models or a schema) so a wrong guess fails loudly at startup; lint the raw text (or load with yaml.BaseLoader, which keeps everything as strings) in CI; or choose a stricter format such as TOML or JSON for data where the types matter. YAML 1.2 removed the boolean words, but many popular tools still parse 1.1.
A docker-compose file has an unquoted ports: - 22:22 and the container isn't reachable on port 22. What happened?▶
YAML 1.1 has a base-60 (sexagesimal) integer form, so 22:22 parses as the single integer 22*60+22 = 1342 rather than the string "22:22" that Compose needs. It only triggers when every part after a colon is under 60, which is why 5432:5432 happened to survive while 22:22 did not — a bug that appears and disappears with the port numbers. The fix is to always quote port mappings ("22:22"); the Compose documentation says exactly this. In review, docker compose config prints the resolved file so you can see what was actually parsed, and a CI lint on the raw text can catch the pattern before it ships.
How do you handle secrets in configuration?▶
Keep them out of git and out of images: secrets should be injected at runtime from a secret manager (AWS Secrets Manager, HashiCorp Vault, Kubernetes Secrets synced by a tool like External Secrets or Sealed Secrets) and rotated on a schedule. In the application: receive them through environment variables or mounted files, validate that they exist at startup, hold them in a type that masks itself (Pydantic SecretStr), and never print or log them — redact any dict before logging because logger.info(config) is a classic leak. In the repository: .env is git-ignored, only a .env.example with dummy values is committed, and a scanner such as gitleaks or trufflehog runs in CI and as a pre-commit hook. If a secret was committed, rotating it is mandatory — deleting the commit doesn't help because it has already been cloned and cached.
Explain the twelve-factor "config in the environment" principle and the usual precedence order.▶
Twelve-factor says anything that varies between deploys — database URLs, credentials, feature toggles — belongs in environment variables, not in code or in files baked into the image, so one build artifact runs unchanged in dev, staging and production. In practice you combine several sources, so you need a precedence rule; the near-universal one is defaults < config file < environment variables < command-line flags, because more explicit and more temporary sources should override more static ones. Good implementations also coerce environment strings to real types (the classic bug is bool("false") being True), validate everything at startup, and record which layer supplied each value so "why is it using port 9100?" has an instant answer. Pydantic's BaseSettings implements this pattern.
How would you detect configuration drift?▶
Define desired state (in git, or the Terraform state) and live state (read from the cluster or cloud API), normalize both, and diff them. Normalization matters: strip volatile fields such as status, resourceVersion, uid and timestamps, sort keys, and apply the same defaulting the platform does, otherwise every object looks drifted and the real signal drowns in noise. Then either report (a scheduled job that alerts on any difference) or reconcile (GitOps controllers like Argo CD or Flux continuously re-apply git). For Terraform, terraform plan -detailed-exitcode exits 2 when reality differs from code, which a scheduled pipeline can turn into an alert. The deeper point interviewers listen for: drift is best prevented by removing the manual path (read-only console access, all changes via pull request) and detected as a safety net.
JSON vs YAML vs TOML: how do you choose?▶
JSON is strict and unambiguous, has excellent tooling and is the right choice for machine-to-machine data and API responses — but it has no comments and is unpleasant to hand-edit. YAML is human-friendly, supports comments, anchors and multi-document files, and dominates infrastructure config (Kubernetes, CI, Compose, Ansible) — but its implicit typing, whitespace sensitivity and unsafe loaders create real footguns. TOML is explicit and strict, with native dates and no implicit coercion, which makes it ideal for tool and application config such as pyproject.toml, though deeply nested structures read awkwardly. A reasonable rule: JSON for data exchanged between programs, TOML for config a human edits that a program reads, YAML where the ecosystem already mandates it — with schema validation on top of any of them.
Why should an application validate its configuration at startup, and how do you do it in Python?▶
Because a bad value discovered at boot costs seconds, while the same bad value discovered on the first request (or worse, on a rarely used code path at 3 a.m.) is an incident. "Fail fast" means: load the config, validate types, ranges and required fields immediately, report all problems together with their locations, and refuse to start if any exist. In Python this is Pydantic models (or pydantic-settings when reading the environment): typed fields, Field(ge=1, le=65535) constraints, Literal for enumerations, SecretStr for credentials, and a top-level except ValidationError that prints one clear line per error and exits non-zero. The same validation can run in CI against every environment's config so a typo never reaches a deploy.
You run terraform plan in CI. What automated checks would you add before allowing apply?▶
First produce a machine-readable plan (terraform plan -out=tfplan, then terraform show -json tfplan) and write a small gate that reads resource_changes. Fail or require manual approval when: any delete or replace (["delete","create"]) touches a stateful resource type (databases, buckets, volumes); the number of destroyed resources exceeds a threshold; a security group opens 0.0.0.0/0 on a sensitive port; or resources appear outside the expected account or region. Add policy-as-code (OPA/Conftest, Sentinel, Checkov) for organization-wide rules, post the human-readable plan on the pull request for review, and use -detailed-exitcode so the pipeline can distinguish "no changes" (0), "changes" (2) and "error" (1). Emphasize that the gate exits non-zero on violation, because CI only understands exit codes.
What are YAML anchors, aliases and merge keys, and what are the risks of using them?▶
An anchor (&defaults) names a node, an alias (*defaults) reuses it, and the merge key (<<: *defaults) copies a mapping's keys into another so you can share settings across services (common in docker-compose and CI pipelines) without repeating them; keys defined locally override the merged ones. The risks: readability — a reader must hunt for where a value really comes from; tooling — not every consumer expands merge keys the same way (the merge key is a YAML 1.1 feature that some parsers dropped in 1.2); and safety — deeply nested aliases can expand exponentially when loaded (the "billion laughs" attack), so untrusted YAML needs size limits. For Kubernetes manifests, prefer Kustomize or Helm over YAML-level reuse, since the API server doesn't understand anchors — they are resolved by the client before the object is sent.
