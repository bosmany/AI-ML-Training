DevOps 4:
Cloud & Container Ops by Example

The Python you write for AWS, Kubernetes and Docker is mostly one skill: take a big nested JSON response and turn it into a decision. This chapter drills that skill on realistic data — EC2 and S3 responses, security groups, IAM policies, kubectl output, resource quantities, docker inspect — and the pagination, missing-key and throttling traps that break real scripts and fill interview loops.

4.1 — The Skill Behind Every Cloud Script: Handling the Response

Almost every DevOps script you'll write for AWS, Kubernetes or Docker has the same shape: call an API → get a big nested JSON document back → walk it → decide something (delete it, alert on it, total it, report it). The SDK call is one line. The value — and nearly every bug — lives in handling the response: keys that are silently missing, results that are paginated, units like 250m and 2Gi, errors that should or shouldn't be retried. That is what interviewers probe, and it's what this chapter drills.

🎬
Reference code — not runnable in this browser. boto3, the kubernetes client and the docker SDK needs real credentials and a real network, which this WebAssembly sandbox doesn't have, so there is no ▶ Run button. Every block that does have one operates on JSON shaped exactly like the real response, so the same loop works once you swap the fake for the real client.
Reference only — boto3 client vs resource
import boto3 # CLIENT: a 1:1 mapping of the AWS API. Dicts in, dicts out. Every service and operation exists here. ec2 = boto3.client("ec2", region_name="us-east-1") resp = ec2.describe_instances( Filters=[{"Name": "instance-state-name", "Values": ["running"]}] ) for reservation in resp["Reservations"]: for inst in reservation["Instances"]: print(inst["InstanceId"], inst["InstanceType"]) # RESOURCE: an object-oriented wrapper (only some services). Nicer to read, but AWS has put the # resource interface in maintenance mode - new features land in clients only. ec2r = boto3.resource("ec2", region_name="us-east-1") for inst in ec2r.instances.filter(Filters=[{"Name": "instance-state-name", "Values": ["running"]}]): print(inst.id, inst.instance_type)
⭐
Client or resource? Use the client. It maps 1:1 onto the AWS API, covers every service and operation, and gives you plain dicts (which is what you'll parse anyway). The resource layer reads nicely but exists for only a few services and gets no new features. Interviewers like hearing that you know why, not just which one you typed.
Reference only — no hard-coded keys: the credential chain and assume_role
import boto3 # No long-lived keys in scripts. On EC2/ECS/EKS the SDK finds credentials by itself # (instance profile / task role / IRSA). To act in ANOTHER account, assume a role: sts = boto3.client("sts") creds = sts.assume_role( RoleArn="arn:aws:iam::123456789012:role/ReadOnlyAudit", RoleSessionName="weekly-audit", DurationSeconds=3600, )["Credentials"] audit_session = boto3.Session( aws_access_key_id=creds["AccessKeyId"], aws_secret_access_key=creds["SecretAccessKey"], aws_session_token=creds["SessionToken"], # temporary: expires after DurationSeconds ) ec2 = audit_session.client("ec2", region_name="eu-west-1")
🔒
Never put access keys in a script or a repo. On EC2, ECS and EKS the SDK finds credentials by itself (instance profile, task role, IRSA). Locally it reads ~/.aws or environment variables. To work in another account you assume_role and get temporary credentials that expire. Long-lived keys in code are the classic breach.

Now the first response-handling trap, and it's a real one: boto3 omits the Tags key entirely when a resource has no tags — it is not an empty list. A script that does inst['Tags'] works in dev (everything's tagged) and crashes in prod on the one instance nobody tagged. Two tiny helpers fix this class of bug for good.

Missing keys: .get() and a safe nested lookup
# A real boto3 quirk: the 'Tags' key is OMITTED ENTIRELY when an instance has no tags. tagged = {"InstanceId": "i-0a1", "Tags": [{"Key": "Owner", "Value": "ml-platform"}]} untagged = {"InstanceId": "i-0b2"} # no 'Tags' key at all try: print(untagged["Tags"]) except KeyError as e: print(f"KeyError: {e} <- what crashes naive audit scripts") def tags_to_dict(instance): """[{'Key': 'Owner', 'Value': 'x'}] -> {'Owner': 'x'}; safe when 'Tags' is missing.""" return {t["Key"]: t["Value"] for t in instance.get("Tags", [])} print(tags_to_dict(tagged)) print(tags_to_dict(untagged)) def dig(obj, *path, default=None): """Walk nested dicts/lists without blowing up: dig(resp, 'Reservations', 0, 'Instances', 0).""" for key in path: try: obj = obj[key] except (KeyError, IndexError, TypeError): return default return obj resp = {"Reservations": [{"Instances": [{"State": {"Name": "running"}}]}]} print(dig(resp, "Reservations", 0, "Instances", 0, "State", "Name")) print(dig(resp, "Reservations", 5, "Instances", 0, default="<missing>"))
4.2 — EC2: the Reservations → Instances Shape

describe_instances doesn't return a list of instances. It returns Reservations, each holding Instances. A reservation is just one launch request, so its grouping is meaningless for your purposes — always flatten first. Tags arrive as [{'Key': ..., 'Value': ...}], which you'll want as a dict. Real responses carry datetime objects; here they're ISO strings so the data is easy to read.

Flatten, normalise tags, find stopped instances, estimate spend
from datetime import datetime, timezone import re DESCRIBE = { "Reservations": [ {"ReservationId": "r-01", "Instances": [ {"InstanceId": "i-0a1", "InstanceType": "m5.xlarge", "State": {"Name": "running"}, "StateTransitionReason": "", "LaunchTime": "2026-06-02T08:15:00+00:00", "Tags": [{"Key": "Owner", "Value": "ml-platform"}, {"Key": "Env", "Value": "prod"}]}, {"InstanceId": "i-0b2", "InstanceType": "t3.large", "State": {"Name": "running"}, "StateTransitionReason": "", "LaunchTime": "2026-08-20T11:00:00+00:00"}, ]}, {"ReservationId": "r-02", "Instances": [ {"InstanceId": "i-0c3", "InstanceType": "c5.2xlarge", "State": {"Name": "stopped"}, "StateTransitionReason": "User initiated (2026-07-01 10:00:00 GMT)", "LaunchTime": "2026-05-10T09:30:00+00:00", "Tags": [{"Key": "Owner", "Value": "data-eng"}]}, {"InstanceId": "i-0d4", "InstanceType": "t3.micro", "State": {"Name": "running"}, "StateTransitionReason": "", "LaunchTime": "2026-09-01T07:45:00+00:00", "Tags": [{"Key": "Env", "Value": "dev"}]}, ]}, ] } PRICE_PER_HOUR = {"t3.micro": 0.0104, "t3.large": 0.0832, "m5.xlarge": 0.192, "c5.2xlarge": 0.34} NOW = datetime(2026, 9, 18, tzinfo=timezone.utc) # injected "now" -> deterministic output def flatten_instances(resp): return [inst for res in resp.get("Reservations", []) for inst in res.get("Instances", [])] def tags_to_dict(inst): return {t["Key"]: t["Value"] for t in inst.get("Tags", [])} def stopped_since(inst): """describe_instances has no 'stopped at' field - it hides in StateTransitionReason.""" m = re.search(r"\((\d{4}-\d{2}-\d{2}) [\d:]+ GMT\)", inst.get("StateTransitionReason", "")) return datetime.strptime(m.group(1), "%Y-%m-%d").replace(tzinfo=timezone.utc) if m else None instances = flatten_instances(DESCRIBE) print(f"{len(instances)} instances across {len(DESCRIBE['Reservations'])} reservations") for inst in instances: tags = tags_to_dict(inst) state = inst["State"]["Name"] line = f"{inst['InstanceId']:6} {inst['InstanceType']:11} {state:8} owner={tags.get('Owner', '-')}" since = stopped_since(inst) if state == "stopped" and since: line += f" (stopped {(NOW - since).days} days)" print(line) untagged = [i["InstanceId"] for i in instances if "Owner" not in tags_to_dict(i)] stopped = [i["InstanceId"] for i in instances if i["State"]["Name"] == "stopped"] HOURS_PER_MONTH = 730 monthly = sum(PRICE_PER_HOUR[i["InstanceType"]] * HOURS_PER_MONTH for i in instances if i["State"]["Name"] == "running") print("Missing Owner tag:", untagged) print("Stopped:", stopped) print(f"Estimated monthly compute (running only): ${monthly:,.2f}")
🧠
Where the answers hide. There is no stopped_at field: the time an instance was stopped is buried inside StateTransitionReason as text like User initiated (2026-07-01 10:00:00 GMT), so you parse it with a regex. Also note the cost model: a stopped instance stops billing for compute, but its EBS volumes and Elastic IPs keep billing — which is why "stopped for 79 days" is a cleanup candidate, not a free resource.
⭐
Inject the clock. The code takes NOW as a constant instead of calling datetime.now(). That makes the audit deterministic and testable. Scripts that read the wall clock inside their logic are miserable to unit-test.
4.3 — Pagination: NextToken and ContinuationToken

Cloud APIs cap how much they return per call — S3's list_objects_v2 returns at most 1,000 keys. If the result is bigger, the response says IsTruncated: True and hands you a token to pass back. The dangerous failure mode is silence: a script that ignores pagination doesn't crash, it just reports numbers that are quietly wrong once the bucket grows past the first page.

Reference only — paginators, the manual loop underneath, and waiters
import boto3 s3 = boto3.client("s3") # 1) The paginator does the token bookkeeping for you (preferred): paginator = s3.get_paginator("list_objects_v2") total = 0 for page in paginator.paginate(Bucket="ml-artifacts", Prefix="models/"): for obj in page.get("Contents", []): # "Contents" is ABSENT on an empty page total += obj["Size"] # 2) The same thing by hand - what the paginator is doing underneath: token = None while True: kwargs = {"Bucket": "ml-artifacts", "Prefix": "models/"} if token: kwargs["ContinuationToken"] = token resp = s3.list_objects_v2(**kwargs) # at most 1,000 keys per call for obj in resp.get("Contents", []): total += obj["Size"] if not resp["IsTruncated"]: break token = resp["NextContinuationToken"] # opaque - never parse or build it yourself # 3) Waiters poll until a resource reaches a state, so you don't sleep() in a loop: ec2 = boto3.client("ec2") ec2.get_waiter("instance_running").wait( InstanceIds=["i-0a1"], WaiterConfig={"Delay": 15, "MaxAttempts": 40} )

The runnable version below uses a small fake S3 client that behaves like the real one, including the awkward detail that Contents is absent (not an empty list) on an empty page. Watch how the naive single call gives a confident, wrong answer.

A pagination loop against a fake S3 client
MB = 1024 * 1024 class FakeS3: """Mimics the parts of boto3's s3.list_objects_v2 that trip people up.""" def __init__(self, objects): self.objects = objects # list of (key, size_bytes) self.calls = 0 def list_objects_v2(self, Bucket, Prefix="", MaxKeys=1000, ContinuationToken=None): self.calls += 1 matching = [(k, s) for k, s in self.objects if k.startswith(Prefix)] start = int(ContinuationToken) if ContinuationToken else 0 page = matching[start:start + MaxKeys] resp = {"Name": Bucket, "KeyCount": len(page), "IsTruncated": start + MaxKeys < len(matching)} if page: resp["Contents"] = [{"Key": k, "Size": s} for k, s in page] # absent when empty! if resp["IsTruncated"]: resp["NextContinuationToken"] = str(start + MaxKeys) return resp s3 = FakeS3([ ("models/churn-v1.pkl", 40 * MB), ("models/churn-v2.pkl", 42 * MB), ("models/fraud-v1.pkl", 120 * MB), ("models/fraud-v2.pkl", 118 * MB), ("models/embed.bin", 300 * MB), ("models/rank-v1.pkl", 15 * MB), ("models/rank-v2.pkl", 16 * MB), ("logs/2026-09-01.gz", 5 * MB), ]) # WRONG: a single call only ever sees the first page (real S3: the first 1,000 keys) first = s3.list_objects_v2("ml-artifacts", Prefix="models/", MaxKeys=3) print("Naive total :", sum(o["Size"] for o in first["Contents"]) // MB, "MiB <- silently wrong") def list_all(client, bucket, prefix="", page_size=1000): token = None while True: kwargs = {"Bucket": bucket, "Prefix": prefix, "MaxKeys": page_size} if token: kwargs["ContinuationToken"] = token resp = client.list_objects_v2(**kwargs) yield from resp.get("Contents", []) # .get(): empty pages have no "Contents" if not resp["IsTruncated"]: return token = resp["NextContinuationToken"] s3.calls = 0 objs = list(list_all(s3, "ml-artifacts", "models/", page_size=3)) print("Correct total:", sum(o["Size"] for o in objs) // MB, "MiB") print(f"Objects: {len(objs)}, API calls: {s3.calls}") print("Empty prefix:", list(list_all(s3, "ml-artifacts", "nothing-here/")))

4.4 — Security-Group Audit: Where "Open to the World" Hides

A classic cloud-hygiene script: find security groups that expose SSH (22) or RDP (3389) to the internet. It sounds like a one-line if cidr == '0.0.0.0/0', and that one line misses three real cases: IPv6 (::/0 lives in a separate Ipv6Ranges list), port ranges (a rule for 20–25 covers 22), and the protocol -1 rule, which means every protocol, every port and has no FromPort/ToPort keys at all.

Auditing describe_security_groups for open SSH/RDP
SECURITY_GROUPS = {"SecurityGroups": [ {"GroupId": "sg-web", "GroupName": "web-tier", "IpPermissions": [ {"IpProtocol": "tcp", "FromPort": 443, "ToPort": 443, "IpRanges": [{"CidrIp": "0.0.0.0/0"}], "Ipv6Ranges": []}, {"IpProtocol": "tcp", "FromPort": 22, "ToPort": 22, "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "temp - Bob"}], "Ipv6Ranges": []}, ]}, {"GroupId": "sg-db", "GroupName": "postgres", "IpPermissions": [ {"IpProtocol": "tcp", "FromPort": 5432, "ToPort": 5432, "IpRanges": [{"CidrIp": "10.0.0.0/16"}], "Ipv6Ranges": []}, ]}, {"GroupId": "sg-legacy", "GroupName": "old-app", "IpPermissions": [ {"IpProtocol": "-1", "IpRanges": [{"CidrIp": "0.0.0.0/0"}], "Ipv6Ranges": []}, # no FromPort/ToPort! ]}, {"GroupId": "sg-jump", "GroupName": "jumpbox", "IpPermissions": [ {"IpProtocol": "tcp", "FromPort": 3000, "ToPort": 3400, "IpRanges": [], "Ipv6Ranges": [{"CidrIpv6": "::/0"}]}, ]}, ]} SENSITIVE = {22: "SSH", 3389: "RDP"} OPEN_CIDRS = {"0.0.0.0/0", "::/0"} def open_cidrs(rule): v4 = [r["CidrIp"] for r in rule.get("IpRanges", [])] v6 = [r["CidrIpv6"] for r in rule.get("Ipv6Ranges", [])] return [c for c in v4 + v6 if c in OPEN_CIDRS] def covers(rule, port): if rule["IpProtocol"] == "-1": # all protocols, all ports - and NO FromPort/ToPort keys return True return rule["IpProtocol"] == "tcp" and rule["FromPort"] <= port <= rule["ToPort"] def audit(resp): findings = [] for sg in resp["SecurityGroups"]: for rule in sg["IpPermissions"]: for cidr in open_cidrs(rule): for port, name in SENSITIVE.items(): if covers(rule, port): findings.append(f"{sg['GroupId']}: {name} (port {port}) open to {cidr}") return sorted(findings) for line in audit(SECURITY_GROUPS): print(line)
⚠️
Rules that reference other groups aren't CIDRs. A rule can allow traffic from another security group (UserIdGroupPairs) instead of an IP range. That's usually the good, least-privilege pattern — so a robust auditor treats it as "not world-open" rather than crashing on a missing IpRanges key. Always use .get(..., []) on these lists.
4.5 — IAM Policy Review: Reading Wildcards Programmatically

Least privilege means a role gets exactly the actions it needs on exactly the resources it needs. In a policy document the red flags are wildcards: Action: "*", "ec2:*", and Resource: "*". Parsing them has a well-known snag: IAM lets Statement, Action and Resource each be a single value or a list, so you normalise before you loop.

Flagging wildcard actions, wildcard resources and the NotAction trap
POLICIES = { "ci-deployer": {"Version": "2012-10-17", "Statement": [ {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::ml-artifacts/*"}, ]}, "legacy-admin": {"Version": "2012-10-17", "Statement": {"Effect": "Allow", "Action": "*", "Resource": "*"}}, # a dict, not a list! "ops-helper": {"Version": "2012-10-17", "Statement": [ {"Effect": "Allow", "Action": "ec2:*", "Resource": "*"}, {"Effect": "Deny", "Action": "ec2:TerminateInstances", "Resource": "*"}, {"Effect": "Allow", "Action": ["s3:*"], "Resource": ["arn:aws:s3:::logs", "arn:aws:s3:::logs/*"]}, ]}, "notaction-trap": {"Version": "2012-10-17", "Statement": [ {"Effect": "Allow", "NotAction": "iam:*", "Resource": "*"}, ]}, } def as_list(x): """IAM lets Statement, Action and Resource be a single value OR a list. Normalise first.""" return x if isinstance(x, list) else [x] def review(name, policy): issues = [] for i, st in enumerate(as_list(policy["Statement"])): if st["Effect"] != "Allow": continue # Deny statements only ever reduce access actions = as_list(st.get("Action", [])) resources = as_list(st.get("Resource", [])) if "NotAction" in st: issues.append(f"statement {i}: Allow + NotAction grants everything EXCEPT {st['NotAction']}") elif "*" in actions and "*" in resources: issues.append(f"statement {i}: FULL ADMIN (Action * on Resource *)") else: for a in actions: if a == "*" or a.endswith(":*"): issues.append(f"statement {i}: wildcard action {a}") if "*" in resources: issues.append(f"statement {i}: wildcard resource *") return issues for name, policy in POLICIES.items(): issues = review(name, policy) print(f"{name}: {'OK' if not issues else str(len(issues)) + ' issue(s)'}") for msg in issues: print(" -", msg)
🧠
What this reviewer deliberately ignores. It skips Deny statements (they only ever remove access, and an explicit Deny always wins) and it doesn't evaluate Condition blocks, which can narrow a wildcard a lot. In real life you'd also use IAM Access Analyzer and simulate_principal_policy. The point of the script is to triage hundreds of policies down to the few a human should read.
4.6 — Kubernetes: kubectl get pods -o json → Triage

When something is broken at 3 a.m., the useful output isn't a 400-line JSON dump — it's a one-line answer per pod. The trick is knowing where each symptom lives. The pod's status.phase is coarse (Pending/Running/Succeeded/Failed); the detail is in status.containerStatuses[*].state.waiting.reason, lastState.terminated, and the conditions list.

Reference only — the official kubernetes client
from kubernetes import client, config config.load_kube_config() # from ~/.kube/config. Inside a pod use: config.load_incluster_config() v1 = client.CoreV1Api() # Typed OBJECTS with attribute access - not dicts (unlike `kubectl get pods -o json`): pods = v1.list_pod_for_all_namespaces(limit=500) for p in pods.items: print(p.metadata.namespace, p.metadata.name, p.status.phase) # Big clusters: results are paged with a continue token, the k8s cousin of NextToken while pods.metadata._continue: pods = v1.list_pod_for_all_namespaces(limit=500, _continue=pods.metadata._continue) ... # To reuse dict-based code like the examples below, convert the objects back to plain dicts: as_dict = client.ApiClient().sanitize_for_serialization(pods)
Classifying pods from kubectl-style JSON
from collections import Counter PODS = {"kind": "List", "items": [ {"metadata": {"name": "api-7d9f-abc", "namespace": "prod"}, "spec": {"nodeName": "node-1"}, "status": {"phase": "Running", "conditions": [{"type": "Ready", "status": "True"}], "containerStatuses": [{"name": "api", "ready": True, "restartCount": 0, "state": {"running": {"startedAt": "2026-09-17T08:00:00Z"}}}]}}, {"metadata": {"name": "worker-5c6-xyz", "namespace": "prod"}, "spec": {"nodeName": "node-2"}, "status": {"phase": "Running", "conditions": [{"type": "Ready", "status": "False"}], "containerStatuses": [{"name": "worker", "ready": False, "restartCount": 14, "state": {"waiting": {"reason": "CrashLoopBackOff"}}, "lastState": {"terminated": {"reason": "OOMKilled", "exitCode": 137}}}]}}, {"metadata": {"name": "web-9b8-def", "namespace": "staging"}, "spec": {"nodeName": "node-1"}, "status": {"phase": "Pending", "conditions": [{"type": "Ready", "status": "False"}], # NOTE: Pending! ⚠️
Three things that fool every first attempt. 1. A pod in ImagePullBackOff reports phase: Pending, not Failed — the containers never started. 2. A finished Job's pod has Ready=False on purpose (reason: PodCompleted); flagging it is a false alarm. 3. Unscheduled pods have no containerStatuses key at all.

4.7 — Resource Quantities, Requests vs Limits, and QoS

Kubernetes writes CPU and memory as strings: 100m is 100 millicores (a tenth of a core), 0.5 and 500m are the same, 2 is two cores. Memory has binary suffixes (Ki Mi Gi, powers of 1024) and decimal ones (K M G, powers of 1000) — and they are not interchangeable. Before you can add anything up, you have to parse these into plain integers.

Parsing CPU and memory quantities
BINARY = {"Ki": 2**10, "Mi": 2**20, "Gi": 2**30, "Ti": 2**40} DECIMAL = {"k": 10**3, "K": 10**3, "M": 10**6, "G": 10**9, "T": 10**12} def parse_cpu(q): """'250m' -> 250, '2' -> 2000, '0.5' -> 500 (millicores)""" q = str(q) if q.endswith("m"): return int(q[:-1]) return int(round(float(q) * 1000)) def parse_mem(q): """'512Mi' -> bytes. Binary suffixes (Ki/Mi/Gi) are NOT the same as decimal (K/M/G).""" q = str(q) for suffix, mult in BINARY.items(): if q.endswith(suffix): return int(float(q[:-len(suffix)]) * mult) for suffix, mult in DECIMAL.items(): if q.endswith(suffix): return int(float(q[:-len(suffix)]) * mult) return int(float(q)) # plain bytes, or exponent form like 129e6 for q in ["100m", "0.5", "2"]: print(f"cpu {q:>5} = {parse_cpu(q)}m") for q in ["512Mi", "2Gi", "1G", "1Gi", "129e6", "134217728"]: print(f"mem {q:>9} = {parse_mem(q):>10} bytes = {parse_mem(q) / 2**20:8.2f} MiB")
⚠️
1G is not 1Gi. 1G is 1,000,000,000 bytes (953.67 MiB); 1Gi is 1,073,741,824 (1024 MiB). The gap is about 7%, so a sloppy parser makes capacity numbers drift. Note also that m means milli for CPU.

Two numbers per container matter, and they do different jobs. Requests are what the scheduler reserves — they decide which node a pod fits on. Limits are enforced by the kubelet at runtime: a container over its CPU limit is throttled (slowed, never killed), but one over its memory limit is OOMKilled. How requests and limits relate also decides the pod's QoS class, which decides who gets evicted first under node pressure.

Per-namespace totals and QoS classes

4.8 — Docker: inspect JSON, Image References and Container Hygiene

docker inspect returns the full configuration and state of a container as JSON, and the SDK's container.attrs is that same document. Typical audit checks: is the image pinned, is the container privileged, is a port published on every interface, did it get OOM-killed.

Reference only — the docker SDK
import docker client = docker.from_env() # talks to /var/run/docker.sock (or DOCKER_HOST) for c in client.containers.list(all=True): # all=True includes stopped containers, like `docker ps -a` print(c.name, c.status, c.image.tags) c = client.containers.get("api") print(c.attrs["HostConfig"]["RestartPolicy"]) # .attrs is the same JSON `docker inspect` prints c.reload() # attrs are a snapshot - reload() refreshes them print(c.logs(tail=50).decode()) # logs() returns BYTES print(c.stats(stream=False)["memory_stats"]["usage"])

Auditing image tags means parsing image references correctly. It's easy to get wrong because a registry host can contain a colon (a port), so localhost:5000/cache/redis has a colon that is not a tag separator. The rule: only look for a tag after the last slash.

Parsing image refs and auditing docker inspect output
INSPECT = [ {"Name": "/api", "Config": {"Image": "registry.example.com/team/api:latest"}, "HostConfig": {"Privileged": False, "RestartPolicy": {"Name": "unless-stopped"}, "PortBindings": {"8080/tcp": [{"HostIp": "0.0.0.0", "HostPort": "8080"}]}}, "State": {"Status": "running", "OOMKilled": False, "ExitCode": 0}}, {"Name": "/redis", "Config": {"Image": "localhost:5000/cache/redis:7.2.4"}, "HostConfig": {"Privileged": False, "RestartPolicy": {"Name": "no"}, "PortBindings": {"6379/tcp": [{"HostIp": "127.0.0.1", "HostPort": "6379"}]}}, "State": {"Status": "running", "OOMKilled": False, "ExitCode": 0}}, {"Name": "/tools", "Config": {"Image": "busybox"}, "HostConfig": {"Privileged": True, "RestartPolicy": {"Name": "no"}, "PortBindings": {}}, "State": {"Status": "exited", "OOMKilled": True, "ExitCode": 137}}, {"Name": "/pinned", "Config": {"Image": "ghcr.io/acme/model@sha256:9f86d081884c7d659a2feaa0c55ad015"}, "HostConfig": {"Privileged": False, "RestartPolicy": {"Name": "always"}, "PortBindings": {}}, "State": {"Status": "running", "OOMKilled": False, "ExitCode": 0}}, ] def parse_image(ref): """'localhost:5000/cache/redis:7.2.4' -> ('localhost:5000/cache/redis', '7.2.4', None). ⭐
Why :latest is a smell, and what to use instead. A tag is a mutable pointer: :latest can point at a different image tomorrow, so two hosts running "the same" deployment can run different code, and a rollback has nothing to go back to. Pin a version tag at minimum; pin a digest (@sha256:…) when you need bit-for-bit reproducibility.
4.9 — Errors, Throttling and Backoff

Cloud APIs rate-limit you, and scripts that loop over hundreds of resources will hit it. The rule of thumb: retry what is transient, fail fast on what isn't. Throttling, timeouts and 5xx errors are worth retrying with exponential backoff and jitter (so a fleet of scripts doesn't retry in lock-step). AccessDenied or a validation error will fail identically every time, so retrying only wastes minutes.

Reference only — botocore's built-in retries and reading ClientError
import boto3 from botocore.config import Config from botocore.exceptions import ClientError # Let botocore retry throttling/5xx for you. "adaptive" also rate-limits the client side. cfg = Config(retries={"max_attempts": 10, "mode": "adaptive"}, connect_timeout=5, read_timeout=30) ec2 = boto3.client("ec2", config=cfg) try: ec2.describe_instances(InstanceIds=["i-doesnotexist"]) except ClientError as e: code = e.response["Error"]["Code"] # e.g. "InvalidInstanceID.NotFound" status = e.response["ResponseMetadata"]["HTTPStatusCode"] if code in ("AuthFailure", "UnauthorizedOperation", "AccessDenied"): raise SystemExit(f"permissions problem, retrying will not help: {code}") raise
Backoff with an injected sleep and rng (deterministic)
class FakeClientError(Exception): """Shaped like botocore.exceptions.ClientError: the error code lives in e.response.""" def __init__(self, code, message=""): super().__init__(f"{code}: {message}") self.response = {"Error": {"Code": code, "Message": message}} RETRYABLE = {"Throttling", "ThrottlingException", "RequestLimitExceeded", "TooManyRequestsException", "RequestTimeout", "InternalError", "ServiceUnavailable"} def call_with_backoff(fn, max_attempts=5, base=0.5, cap=8.0, sleep=lambda s: None, rng=lambda: 1.0): """Exponential backoff with jitter. `sleep` and `rng` are injected so the demo is deterministic; in production pass time.sleep and random.random (full jitter: sleep a random 0..delay).""" for attempt in range(1, max_attempts + 1): try: return fn() except FakeClientError as e: code = e.response["Error"]["Code"] if code not in RETRYABLE or attempt == max_attempts: raise # AccessDenied etc: retrying can't help delay = min(cap, base * 2 ** (attempt - 1)) * rng() print(f"attempt {attempt}: {code} -> waiting {delay:.1f}s") sleep(delay) state = {"n": 0} def flaky_describe(): state["n"] += 1 if state["n"] < 3: raise FakeClientError("RequestLimitExceeded", "Request limit exceeded.") return {"Reservations": []} print("result:", call_with_backoff(flaky_describe), "after", state["n"], "calls") def denied(): raise FakeClientError("AccessDenied", "not authorized to perform ec2:DescribeInstances") try: call_with_backoff(denied) except FakeClientError as e: print("gave up immediately:", e.response["Error"]["Code"])
⚠️
Retries need idempotency. Retrying a read is always safe. Retrying a create can make two of the thing if the first call actually succeeded but the response was lost. That's why EC2's run_instances accepts a ClientToken: send the same token on every retry and AWS returns the original result instead of launching a second instance.
Chapter 4 Summary
  • Handle the response, not just the call — missing keys (Tags), nesting (Reservations → Instances), pagination and units are where scripts break.
  • Always paginate, ideally with a paginator, and filter server-side. Ignoring it fails silently.
  • Audit the sneaky cases: IPv6, port ranges, protocol -1, single-value-or-list IAM fields, NotAction.
  • Triage pods by symptom: phase is coarse; the answer is in containerStatuses and conditions.
  • Requests schedule, limits enforce: CPU over limit is throttled, memory over limit is OOMKilled. 1G ≠ 1Gi.
  • Retry only what is transient, with backoff and jitter, and make retried writes idempotent.

💼 Cloud & Container Ops — Interview Prep

12 questions on the angles interviewers use to tell whether you've actually operated AWS and Kubernetes, not just read the docs. Click a question to reveal what a strong answer includes.

How do you handle pagination with boto3, and what goes wrong if you ignore it?▶
Use a paginator (client.get_paginator('list_objects_v2')) or follow the token by hand: pass ContinuationToken (S3), NextToken (most services) or Marker (older APIs) until the more results flag is false. Ignoring it is dangerous because it fails silently: S3 returns the first 1,000 keys and a script that doesn't loop just reports a wrong total or deletes/keeps the wrong things once the bucket grows. Also mention that Contents is absent on an empty page, and that you filter server-side with Prefix/Filters to page through less data.
boto3 client vs resource: which do you use and why?▶
The client: it's a thin 1:1 mapping of the AWS API, covers every service and operation, returns plain dicts, and supports paginators and waiters everywhere. The resource interface is object-oriented and pleasant but exists for few services and AWS has stopped adding features to it. A strong answer adds that clients are easier to mock in tests (you stub a dict) and that you'd wrap either in your own small function so business logic isn't coupled to the SDK.
How would you find security groups that expose SSH to the internet? What are the traps?▶
Call describe_security_groups (paginated), walk each IpPermissions rule, and check whether the CIDR is 0.0.0.0/0 or ::/0 and whether the rule covers port 22. The traps: IPv6 lives in a separate Ipv6Ranges list; a rule is a range (20–25 covers 22); protocol -1 means all traffic and has no FromPort/ToPort keys (a KeyError waiting to happen); and rules can reference other security groups instead of CIDRs. Then say you'd rather use SSM Session Manager than expose SSH at all.
What is least privilege, and how would you audit IAM policies programmatically?▶
Least privilege: grant only the actions needed, on only the resources needed, for only as long as needed. Programmatically: normalise each policy (Statement/Action/Resource can each be a value or a list), skip Deny statements, and flag Action: *, service wildcards like s3:*, Resource: *, and Allow + NotAction (grants everything except). Mention that Condition blocks can narrow a wildcard, so triage with the script but confirm with IAM Access Analyzer or simulate_principal_policy, and prefer roles with temporary credentials over long-lived keys.
A pod is in CrashLoopBackOff. Walk me through debugging it.▶
1) kubectl describe pod: read Last State and the exit code (137 = SIGKILL, usually OOMKilled; 1 = app error; 143 = SIGTERM). 2) kubectl logs --previous — the current container has just restarted, the useful logs are from the one that died. 3) Check config: missing env vars/secrets/ConfigMaps, wrong command/args. 4) Check probes: an over-eager liveness probe kills a slow-starting app. 5) If OOMKilled, compare memory usage with the limit. The back-off delay (10s, 20s, 40s… up to 5 min) is Kubernetes protecting the node, not the bug itself.
A pod is stuck in Pending. What are the possible causes?▶
Run kubectl describe pod and read the FailedScheduling event, which says why. Common causes: insufficient cpu/memory on every node (the scheduler counts requests, not actual usage); taints without matching tolerations; nodeSelector or affinity that no node satisfies; an unbound PersistentVolumeClaim; a ResourceQuota or LimitRange rejecting it; or no nodes at all because the autoscaler hasn't added one. Note that a pod that is scheduled but still Pending (ContainerCreating, ImagePullBackOff) is a different problem.
ImagePullBackOff vs ErrImagePull — what's the difference and what causes them?▶
ErrImagePull is the first failed attempt; ImagePullBackOff is Kubernetes backing off before retrying. Same root causes: a typo in the image name or tag, a tag that doesn't exist, a private registry without an imagePullSecret (or an expired token), the wrong architecture, a registry rate limit (Docker Hub), or the node having no route to the registry. Gotcha worth mentioning: such a pod reports phase: Pending, so a script that only looks at phase will miss it.
Explain requests vs limits and QoS classes. What happens when a container exceeds each?▶
Requests are reserved capacity used by the scheduler to place the pod. Limits are runtime ceilings enforced by the kubelet. Exceed the CPU limit and the container is throttled (slower, not killed); exceed the memory limit and it is OOMKilled. QoS: Guaranteed (requests == limits for cpu and memory on every container), Burstable (some requests/limits), BestEffort (none). Under node pressure BestEffort is evicted first. Good follow-up: CPU limits can cause needless throttling, which is why some teams set requests but not CPU limits.
How do you handle API throttling in an automation script?▶
Retry only transient errors (Throttling, RequestLimitExceeded, timeouts, 5xx) with exponential backoff plus jitter so parallel scripts don't retry in lock-step; in boto3 you can set Config(retries={'mode': 'adaptive', 'max_attempts': 10}). Fail fast on AccessDenied/validation errors. Reduce the call volume too: paginate with server-side filters, cache results, use batch APIs, and avoid N+1 patterns (one call per resource). Retried writes must be idempotent — e.g. EC2 ClientToken.
What would you build for cloud cost hygiene, and how would you make it safe?▶
Scripts that find: untagged resources (no Owner/CostCenter), stopped instances that still pay for EBS, unattached volumes, old snapshots, idle load balancers, oversized instances. Make it safe: default to report-only / dry-run, require a tag or an allow-list to delete, notify the owner and wait a grace period, log every action, run with a narrowly-scoped role, and make each step idempotent so a re-run is harmless. The mistake interviewers listen for: an automated delete with no dry-run and a broad role.
Why is :latest a bad idea in production, and what do you use instead?▶
A tag is a mutable pointer, so :latest can refer to different images over time. Two nodes can run different code under the same manifest, a rollback has nothing to roll back to, and imagePullPolicy semantics get confusing. Use immutable version tags (git SHA or semver) and, for full reproducibility and supply-chain safety, pin by digest (image@sha256:…). Also parse image refs carefully in tooling — a registry host may contain a port colon.
How does a Python script running on EKS or EC2 get AWS credentials without keys in the code?▶
Through the SDK's credential chain: on EC2 the instance profile (IMDS), on ECS the task role, on EKS IRSA (IAM Roles for Service Accounts — a projected web-identity token exchanged with STS). Locally it falls back to environment variables or the shared profile. For cross-account access you assume_role and receive temporary credentials. Never hard-code keys, never commit them, and scope each role to the one job.
