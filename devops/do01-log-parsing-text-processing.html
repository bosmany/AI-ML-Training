DevOps Python 1:
Log Parsing & Text Processing

Every production incident starts the same way: someone opens a log and asks "what changed?" Log parsing is the single most common thing DevOps and SRE engineers write Python for, and "find the top 10 IPs in this access log" is one of the most repeated interview questions in the field. This chapter builds the whole toolkit on realistic nginx and sshd logs: reading huge files lazily, regexes with named groups, typed records that survive garbage lines, Counter top-N, per-hour error rates, latency percentiles, and a sliding-window brute-force detector.

1.1 — What a Log Is, and Why DevOps Engineers Read Them

Imagine you run a small online shop. At 10:59 a customer taps "Pay", and the page shows an error. Twenty minutes later the customer emails you. You open the shop's code and stare at it. The code looks fine. You have no idea what happened at 10:59, because a running program does not remember anything for you. Once a request is finished, the evidence is gone. Look at the smallest version of that problem.

A program that leaves no evidence
def handle_request(path): if path == "/checkout": return 502 # the payment service was down return 200 print(handle_request("/orders")) print(handle_request("/checkout")) print("Why did checkout fail at 10:59? ...no idea.")
Output
200
502
Why did checkout fail at 10:59?  ...no idea.

The program answered correctly and left nothing behind. Nobody can go back and ask what happened. The fix is very old: keep a diary. Every time something noteworthy happens, the program writes one line of text saying what, when and to whom. That diary is a log. Think of the paper tape a shop till prints: one line per sale, in the order they happened, never edited afterwards. If the shopkeeper wonders why the day's total is wrong, the tape holds the answer.

Here is the same program again, this time writing a diary line for every request. A real service appends each line to a file on disk. We use a plain Python list called log so it runs anywhere, because a list also grows at the end, one item at a time.

The smallest possible log
log = [] # stands in for a file on disk def handle_request(path): status = 502 if path == "/checkout" else 200 log.append(f"10:59:58 GET {path} -> {status}") # one line per event return status handle_request("/orders") handle_request("/checkout") handle_request("/orders") for line in log: print(line)
Output
10:59:58 GET /orders -> 200
10:59:58 GET /checkout -> 502
10:59:58 GET /orders -> 200
What Python does, line by line
  • log = [] creates an empty list. It plays the role of the log file: empty at first, growing only at the end.
  • Each call to handle_request works out a status and then log.append(...) adds exactly one new line describing that request. Nothing already in the log is changed.
  • After three calls the log holds three lines, in the order the requests arrived. That order matters: it is the timeline of what happened.
  • The final for loop reads the diary back, one line at a time. This "write lines, later read them back" pattern is the whole idea of logging.
Why DevOps engineers spend so much time in logs

DevOps is the work of keeping software running after it has been written: deploying it, watching it, and fixing it at 3 a.m. An engineer on call cannot attach a debugger to a live production server and freeze it, because real customers are using it. The log is the only witness. When something breaks, the engineer asks four questions of the logs: what happened, when did it start, how often, and to whom. Nearly everything in this chapter is one of those four questions turned into code.

Different programs keep different diaries. A web server access log (nginx or Apache) has one line per request. An authentication log (/var/log/auth.log) records every login attempt, successful or not. An application log holds whatever the developers chose to print. On Linux they usually live under /var/log/. Because they only ever grow, a busy server can produce gigabytes per day, so old files are renamed and compressed on a schedule. That renaming is called log rotation, and we will meet it again in section 1.3.

A first question: how often did it fail?
log = [ "10:59:58 GET /orders -> 200", "10:59:58 GET /checkout -> 502", "11:00:01 GET /orders -> 200", "11:00:03 GET /checkout -> 500", "11:00:04 GET /health -> 200", ] failures = 0 for line in log: if "-> 5" in line: # a status starting with 5 means a server error failures += 1 print("FAILED:", line) print(failures, "of", len(log), "requests failed")
Output
FAILED: 10:59:58 GET /checkout -> 502
FAILED: 11:00:03 GET /checkout -> 500
2 of 5 requests failed
From running program to answer
  running program            log file                 your script              answer
 +---------------+  writes  +----------------+  reads  +--------------+  ->  +---------------------+
 | web server    | -------> | one line per   | ------> | parse, count,|      | "5xx rate hit 40%   |
 | ssh daemon    |  (append)| event, oldest  |  (Python)| summarise    |      |  at 11:00; culprit  |
 | your app      |          | line first     |         |              |      |  is /checkout"      |
 +---------------+          +----------------+         +--------------+      +---------------------+
Every log analysis in this chapter follows these four stages. The chapter takes them one at a time.

That last block already answered a real question with only a loop and an if. It has a weakness, though. The test "-> 5" in line only works because we invented this tidy format ourselves. Real logs come from other people's programs and have a stricter, messier layout. To read them reliably we first have to understand how one line is put together, which is the next section.

Why can't an engineer add a print statement and re-run the failing request in production?
Reproducing the problem may be impossible (the payment service is up again), and experimenting on a live system affects real customers. The log was written at the moment it happened, so it is the only accurate record of that moment.
Why does the order of lines in a log matter?
Lines are appended as events happen, so their order is the timeline. Reading them top to bottom lets you see what led up to a failure.

Recap
  • A log is a diary a program writes: one line of text per event, appended in time order.
  • Engineers read logs because a live production system cannot be paused and inspected; the log is the only witness.
  • Almost every log question is one of four: what happened, when, how often, to whom.
  • A log analysis has four stages: the program writes, the file stores, your script reads and summarises, and you get an answer.
1.2 — Anatomy of a Log Line: Two Real Formats

A log line looks like noise until you know its format: the agreed order and punctuation of its parts. Each part is called a field. Once you can name the fields, the line reads like a sentence. We will use two formats for the rest of the chapter, because they are the two you will meet most often.

The first is the nginx combined access log, one line per web request. Here is one line with every field named underneath.

One nginx access line, field by field
203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /api/v1/orders?id=42 HTTP/1.1" 200 1532 "-" "Mozilla/5.0" 0.128
|           | |  |                          |                                  |   |    |   |           |
|           | |  |                          |                                  |   |    |   |           +-- request time (seconds)
|           | |  |                          |                                  |   |    |   +-- user agent (which client software)
|           | |  |                          |                                  |   |    +-- referrer (page that linked here)
|           | |  |                          |                                  |   +-- bytes sent back
|           | |  |                          |                                  +-- status code (200 ok, 404 missing, 500 server broke)
|           | |  |                          +-- request: method, path, protocol
|           | |  +-- timestamp with UTC offset
|           | +-- user name (- means none)
|           +-- ident (always - in practice)
+-- client IP address
Brackets and quotes are part of the format. That matters, because the request line and the browser name (user agent) contain spaces.

Two words need explaining. An IP address is the number that identifies the computer that sent the request, like a return address on a letter. A status code is a three-digit answer the server sends back. The first digit tells you the family: 2xx means success, 3xx redirect, 4xx the client did something wrong (wrong password, page not found), and 5xx means the server failed. Engineers watch 5xx the most, because a 5xx is our fault, not the customer's.

The simplest way to pull fields out of a line is str.split(). With no argument it cuts the text at every run of whitespace and returns a list of pieces, numbered from 0. Try it on our line.

split() cuts on whitespace
line = '203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /api/v1/orders?id=42 HTTP/1.1" 200 1532 "-" "Mozilla/5.0" 0.128' parts = line.split() print(len(parts), "pieces") print("ip :", parts[0]) print("path :", parts[6]) print("status :", parts[8]) print("bytes :", parts[9])
Output
13 pieces
ip     : 203.0.113.7
path   : /api/v1/orders?id=42
status : 200
bytes  : 1532
What Python does, line by line
  • line.split() looks for gaps made of spaces. Each stretch of characters between gaps becomes one item in a list of strings.
  • Position 0 is the IP. Positions 1 and 2 are the two dashes. Position 3 is [12/Mar/2026:10:15:32 and position 4 is +0000], because the timestamp itself contains a space.
  • The request "GET /api/v1/orders?id=42 HTTP/1.1" contains two spaces, so it is cut into three pieces at positions 5, 6 and 7. That is why the path is at index 6 and the status at index 8.
  • Every value in the list is still a string. parts[8] is the text "200", not the number 200. We will convert it in section 1.6.

This works, and for quick jobs it is a fine tool. But it is fragile, and the fragility comes from the fixed positions. The indexes 6 and 8 are only right if every line has exactly the same number of spaces. The user agent field is where that breaks: real browsers name themselves with spaces.

split() breaks when a field contains spaces
plain = '10.0.0.9 - - [12/Mar/2026:11:03:00 +0000] "GET /health HTTP/1.1" 200 2 "-" "kube-probe/1.29"' spaced = '10.0.0.9 - - [12/Mar/2026:11:03:00 +0000] "GET /health HTTP/1.1" 200 2 "-" "Mozilla/5.0 (X11; Linux x86_64)"' odd = '10.0.0.9 - - [12/Mar/2026:11:03:00 +0000] "-" 408 0 "-" "-"' for name, text in (("plain", plain), ("spaced", spaced), ("odd", odd)): parts = text.split() print(name, len(parts), "pieces; parts[8] =", parts[8])
Output
plain 12 pieces; parts[8] = 200
spaced 15 pieces; parts[8] = 200
odd 10 pieces; parts[8] = "-"

The first two lines happen to agree at index 8 because the extra spaces are at the end, after the status. The third line, a request that timed out before any request line arrived, shifts every field: index 8 now holds the quoted dash of the referrer field, not the status. The code did not crash. It quietly produced the wrong answer, which is the worst kind of bug. In section 1.4 we will replace fixed positions with patterns that describe the shape of each field.

The second format is the authentication log, written by the sshd program (the service that lets people log in to a server remotely). Its lines look like ordinary English with data in the gaps.

One sshd line
Mar 12 10:15:31 web01 sshd[2201]: Failed password for invalid user admin from 198.51.100.23 port 51122 ssh2
|______________| |___| |________|  |_______________________________________| |_____________|
   timestamp     host    program            what happened (free text)          who did it (IP)
No year and no time zone appear in this format. Section 1.8 explains why that is a trap.
Reading an sshd line by its words
line = "Mar 12 10:15:31 web01 sshd[2201]: Failed password for invalid user admin from 198.51.100.23 port 51122 ssh2" words = line.split() print("time :", " ".join(words[0:3])) print("host :", words[3]) print("event :", " ".join(words[5:7])) print("ip :", words[words.index("from") + 1])
Output
time    : Mar 12 10:15:31
host    : web01
event   : Failed password
ip      : 198.51.100.23

Here we found the IP without a fixed position: words.index("from") finds where the word from is, and the IP is the next item. That is the first hint of a better idea. Describe a field by what surrounds it, not by how many words came before it.

In the nginx line, why is the status code at index 8 and not index 6 of the split list?
The request in quotes contains two spaces, so it becomes three pieces (indexes 5, 6, 7). The timestamp also takes two pieces (3 and 4). Those extra pieces push the status to index 8.
Why is a wrong answer from a fixed-position split worse than a crash?
A crash is loud, so you notice and fix it. A wrong index silently returns a different field, so a report can look plausible while being wrong.
Try it. Add a fourth line to the "split() breaks" block: '1.2.3.4 - - [12/Mar/2026:11:03:00 +0000] "GET / HTTP/1.1" 404 0 "-" "curl/8.5.0"'. Predict what parts[8] prints before you run it.
Recap
  • A log line has a format: fields in a fixed order, separated by spaces, with quotes and brackets around fields that contain spaces.
  • nginx access lines carry IP, time, request, status code, bytes, referrer, user agent and request time. sshd lines carry a timestamp, host, program and a free-text event.
  • split() is quick, but fixed positions silently break when a field contains spaces or is missing.
  • Better plan: describe a field by its surroundings (a pattern), which is what regular expressions are for.
1.3 — Reading Big Files Lazily: Generators, Not .read()

A busy web server's access log can be several gigabytes. Suppose your laptop has 8 GB of memory. The most obvious way to read a file is open(path).read(), which loads the whole text into memory at once. On a 6 GB log that is a crash waiting to happen, and it tends to happen on the very server that is already in trouble. The other common call, .readlines(), is no better: it builds a list holding every line.

Two ways to read a big file
   .read() / .readlines()                     for line in f   (lazy)

   disk:   [line1][line2][line3]...[line N]   disk:   [line1][line2][line3]...[line N]
              |                                           |
              v   everything copied at once               v   one line at a time
   memory: [line1][line2][line3]...[line N]   memory: [ line k ]   <- the rest stays on disk
           needs  N lines of RAM                      needs  1 line of RAM
Memory use of the lazy version depends on the length of ONE line, not on the size of the file.

The idea that saves you is laziness: do the work for one item only when someone asks for it, and not before. A Python file object is already lazy. When you write for line in f, Python reads the next line from disk, hands it to your loop body, and forgets it when the loop moves on. Think of a conveyor belt at a checkout: the till serves one item at a time and never needs the whole shop's stock on the counter. To try this without a real 6 GB file, the next block writes a five-line file to Python's scratch disk and reads it back lazily.

A file object yields one line at a time
with open("/tmp/demo.log", "w") as f: f.write("line one\nline two\nline three\nline four\nline five\n") with open("/tmp/demo.log") as f: for number, line in enumerate(f, start=1): print(number, repr(line))
Output
1 'line one\n'
2 'line two\n'
3 'line three\n'
4 'line four\n'
5 'line five\n'

The with statement opens the file and promises to close it when the block ends, even if an error happens in the middle. Notice repr(line): it shows the hidden \n at the end of each line. Every line still carries its newline character, which is why you will often see line.rstrip("\n") in log code.

Your own lazy steps with yield

You want more than raw lines. You want a stream of clean lines, then a stream of parsed records, then a stream of only the failures. A generator function lets you build each of those steps. It looks like a normal function, but it uses yield instead of return. Where return ends the function, yield hands back one value and then pauses the function, remembering exactly where it stopped. The next request resumes it right after the yield. Watch the prints interleave.

A generator pauses at every yield
def read_lines(lines): for line in lines: print(" [generator] reading", line) yield line.upper() stream = read_lines(["a", "b", "c"]) print("created the generator; nothing has run yet") first = next(stream) print("main got:", first) second = next(stream) print("main got:", second)
Output
created the generator; nothing has run yet
   [generator] reading a
main got: A
   [generator] reading b
main got: B
What Python does, line by line
  • read_lines([...]) does NOT run the function body. It only builds a generator object and returns it. That is why the first print says nothing has run.
  • next(stream) starts the body. It runs up to the first yield, printing "reading a", then hands back "A" and pauses.
  • main got: A is printed by the caller. The generator is asleep, holding its place inside the for loop.
  • The second next(stream) wakes it. It continues after the yield, loops to item "b", prints "reading b", and hands back "B". The third item "c" was never touched, so it cost nothing.

Now chain several generators together into a pipeline: each step pulls one item from the step before it. The whole file is never held at once, no matter how long the pipeline is.

A small pipeline: read, then filter, then count
def read_lines(text): for line in text.splitlines(): yield line.strip() def only_failures(lines): for line in lines: if line.endswith("502") or line.endswith("500"): yield line text = "GET /a 200\nGET /b 502\nGET /c 200\nGET /d 500\nGET /e 200\n" failures = only_failures(read_lines(text)) count = 0 for line in failures: count += 1 print("failure:", line) print("total failures:", count)
Output
failure: GET /b 502
failure: GET /d 500
total failures: 2

Only one line is alive at a time, moving along the chain like a bucket passed hand to hand. Adding another step, say "parse each line", means writing one more small generator and wrapping it around the others.

Common mistakes with generators

Mistake 1: a generator can only be used once. Once every item has been handed out, the generator is spent. Asking again does not raise an error, it silently gives nothing, and that regularly makes a report show "0 requests".

A spent generator yields nothing
def read_lines(text): for line in text.splitlines(): yield line gen = read_lines("a\nb\nc") print("first pass :", list(gen)) print("second pass:", list(gen))
Output
first pass : ['a', 'b', 'c']
second pass: []

If you need two passes over the data (say a total and then percentages), either open the file again, or collect everything you need in ONE pass. Mistake 2: treating a generator like a list. A generator does not know its length in advance, because it has not produced the items yet.

Asking a generator for its lengthread-only
def read_lines(text): for line in text.splitlines(): yield line gen = read_lines("a\nb\nc") print(len(gen))
What Python says
Traceback (most recent call last):
  File "<exec>", line 6, in <module>
    print(len(gen))
           ^^^^^^^^
TypeError: object of type 'generator' has no len()

Read a traceback from the bottom up. The last line, TypeError: object of type 'generator' has no len(), is the diagnosis: len needs a sized thing and a generator is not one. The lines above it show where it happened. If you truly need the count, count while you loop, as the pipeline above did.

Why does print(...) inside a generator not run when you call the generator function?
Calling a generator function only creates the generator object. The body starts running when something asks for the first item, with next() or a for loop.
A colleague loads a 4 GB log with lines = f.readlines() and it is killed for using too much memory. What is the smallest change?
Loop directly over the file, for line in f:, and process each line as it arrives. Only one line is in memory at a time.

Recap
  • .read() and .readlines() load the whole file into memory; for line in f reads one line at a time.
  • A generator function uses yield: it hands back one value, pauses, and resumes on the next request.
  • Chaining generators builds a lazy pipeline where memory depends on one item, not the whole file.
  • A generator is single-use (a second pass gives nothing) and has no len().
1.4 — Regular Expressions From Zero, Part 1: Literals, Classes, Quantifiers

Section 1.2 ended with a problem: fixed positions break, and searching for the text "-> 5" only works on lines we invented. Suppose you want "every three-digit number that follows a quoted request". The string methods you know (in, split, startswith) can only look for exact text. They cannot say "any three digits". You need a way to describe the shape of text.

That description is a regular expression, or regex: a small pattern language for text. Think of a stencil, or the way you describe a postcode to a stranger: "two letters, then a digit, then a space". You do not list every possible postcode, you describe what they look like. Python's re module reads such patterns and finds the text that fits. Regex looks scary because it is written in symbols. We will learn it in three tiny pieces, and each piece is understandable on its own.

Piece 1: literal text

Ordinary letters and digits in a pattern match themselves. The pattern GET matches the three characters G, E, T in that order. re.search(pattern, text) scans the text for the first place the pattern fits and returns a match object describing where, or None if nothing fits.

The smallest regex: a literal
import re line = '198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "POST /login HTTP/1.1" 401 87' m = re.search("POST", line) print(m) print(m.group(), m.span()) print(re.search("DELETE", line))
Output
<re.Match object; span=(48, 52), match='POST'>
POST (48, 52)
None

The first print shows the match object: span=(48, 52) means the match sits at positions 48 up to (not including) 52 in the line. m.group() returns the matched text itself. The last line is the sad path: no match gives None, which is Python's "nothing here".

Piece 2: character classes

A character class matches ONE character out of a set. Square brackets list the set: [abc] means "one of a, b or c", and [0-9] means "one digit". Because the common sets are so useful, there are shortcuts: \d is any digit, \s is any whitespace (space, tab, newline), \w is a letter, digit or underscore, and a dot . is any character at all. Capitalising a shortcut flips it: \S is any character that is NOT whitespace. A caret at the start of a bracket also means "not": [^"] is any one character except a double quote.

PatternMatches one character that is...
\da digit, 0 to 9
\s / \Swhitespace / anything except whitespace
\wa letter, digit or underscore
[A-Z]a capital letter
[^"]anything except a double quote
.any character (except a newline)
Character classes match one character each
import re text = "GET /a 200" print(re.findall(r"\d", text)) print(re.findall(r"[A-Z]", text)) print(re.findall(r"\S", "GET /a")) print(re.findall(r"[^ ]", "GET /a"))
Output
['2', '0', '0']
['G', 'E', 'T']
['G', 'E', 'T', '/', 'a']
['G', 'E', 'T', '/', 'a']

re.findall(pattern, text) returns a list of every non-overlapping match. Each class matched a single character, so the digits came out one at a time: '2', '0', '0'. To grab a whole number we need a way to say "one or more".

Piece 3: quantifiers

A quantifier goes right after a piece of pattern and says how many times it may repeat. + means one or more, * means zero or more, ? means zero or one (optional), and {3} means exactly three. So \d+ reads "a run of digits", \d{3} reads "exactly three digits", and -?\d+ reads "an optional minus sign, then digits".

Quantifiers: how many times
import re line = '203.0.113.7 "GET /orders HTTP/1.1" 200 1532 0.128' print(re.findall(r"\d+", line)) print(re.search(r"\d{3}", line).group()) print(re.search(r"\d+\.\d+$", line).group()) print(re.findall(r"\d+\.?\d*", "7 and 7.5 and 12"))
Output
['203', '0', '113', '7', '1', '1', '200', '1532', '0', '128']
203
0.128
['7', '7.5', '12']
What Python does, line by line
  • \d+ scans left to right. At each digit it keeps going while digits continue, so 203 comes out whole, then 0, 113, and so on. The dots are not digits, so they end each run. The result is every run of digits in the line.
  • \d{3} asks for exactly three digits in a row and search stops at the first place it fits: 203, from the start of the IP address.
  • \d+\.\d+$ means digits, then a literal dot, then digits, then the end of the line. The $ is an anchor: it matches a position (the end of the text), not a character. This finds 0.128, the request time at the end.
  • \d+\.?\d* reads "digits, an optional dot, more digits if any". It matches 7, 7.5 and 12, so it handles whole numbers and decimals alike.

The dot after \d+ is written \. with a backslash. That brings us to the first real mistakes.

Common mistakes

Mistake 1: an unescaped dot. In a pattern, a bare . means "any character", not a full stop. To match a literal dot, put a backslash in front: \.. The bug is sneaky because the pattern still matches the text you meant. It also matches text you did not.

The dot matches anything
import re wanted = "10.0.0.9" print(bool(re.search("10.0.0.9", wanted))) print(bool(re.search("10.0.0.9", "10x0y0z9"))) print(bool(re.search(r"10\.0\.0\.9", "10x0y0z9")))
Output
True
True
False

The middle line is the trap: a pattern meant to find one IP address accepts a nonsense string. The escaped version rejects it.

Mistake 2: forgetting the raw-string r prefix. Python itself treats backslash as a special character inside ordinary strings (\n is a newline, and \b is a backspace). Regex also uses backslashes. If you write "\bGET\b", Python turns the \b into backspace characters before re ever sees it. Putting r in front makes a raw string, where Python leaves backslashes alone. Regex's own \b means "a word boundary", the edge between a word character and a non-word one.

Always write patterns as raw strings
import re text = "GET /a" print(re.search("\bGET\b", text)) print(re.search(r"\bGET\b", text))
Output
None
<re.Match object; span=(0, 3), match='GET'>

The first search returns None without any error. It quietly looks for a backspace character that is not there. Make it a habit: every regex pattern starts with r".

What does re.findall(r'\d{2}', '12345') return, and why not five items?
It returns ['12', '34']. Each match uses two digits and matches do not overlap, so after '12' the search continues at '3'. The leftover '5' has no partner and is not matched.
Which pattern finds a run of one or more non-space characters: \s+, \S+ or .+?
Only \S+. \s+ matches whitespace, and .+ would swallow spaces too.

Recap
  • A regex describes the shape of text. re.search finds the first fit (or None); re.findall lists all fits.
  • Literals match themselves. Classes (\d, \s, \w, [abc], [^"], .) match ONE character from a set.
  • Quantifiers (+, *, ?, {n}) say how many times; anchors like $ match positions.
  • Escape a literal dot as \., and write every pattern as a raw string r"...".
1.5 — Regular Expressions, Part 2: Groups, Named Groups, and the Greedy Trap

So far a regex only finds text. For log parsing we also need to pull pieces out: the IP here, the status there. The tool for that is the group. Put parentheses around part of a pattern and Python remembers whatever that part matched. It is like using a highlighter pen on a printed page: the whole pattern finds the sentence, and each pair of parentheses marks one phrase to keep.

Groups: parentheses capture pieces
import re line = '198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "POST /login HTTP/1.1" 401 87' m = re.search(r'"(\w+) (\S+) [^"]*" (\d+) (\d+)', line) print(m.group(0)) print(m.group(1), m.group(2), m.group(3)) print(m.groups())
Output
"POST /login HTTP/1.1" 401 87
POST /login 401
('POST', '/login', '401', '87')

group(0) is the entire match. group(1) is whatever the first pair of parentheses caught, group(2) the second, and so on, counted by the position of the opening bracket. m.groups() gives them all as a tuple. This works, but numbers are hard to remember. If someone inserts a group at the front, every later number shifts. The fix is to give each group a name.

Named groups

Write (?P<name>...) and the group is stored under that name. The ?P is the required spelling that tells Python "this group has a name". Afterwards you read m["name"] or the whole dictionary with m.groupdict(). The pattern now documents itself.

Named groups read like the log format
import re line = '198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "POST /login HTTP/1.1" 401 87' pattern = r'"(?P<method>[A-Z]+) (?P<path>\S+) [^"]*" (?P<status>\d{3}) (?P<size>\d+)' m = re.search(pattern, line) print(m["method"], m["path"], m["status"]) print(m.groupdict())
Output
POST /login 401
{'method': 'POST', 'path': '/login', 'status': '401', 'size': '87'}
How Python matches this pattern, step by step
  • re.search tries the pattern at position 0 of the line, then 1, then 2, and so on, until it fits. The first character the pattern needs is a double quote, so the attempt fails at every position until it reaches the quote before POST.
  • (?P<method>[A-Z]+) takes capital letters as long as they continue: P, O, S, T. The next character is a space, which is not a capital, so the run ends and method is POST.
  • A literal space matches the space. Then (?P<path>\S+) takes non-space characters: /login. It stops at the next space.
  • [^"]*" matches a space, then any number of non-quote characters (HTTP/1.1), then the closing quote. The negated class cannot run past the quote, which is exactly why it is safe.
  • (?P<status>\d{3}) takes a space and exactly three digits: 401. (?P<size>\d+) takes the space and the digits 87. The pattern is finished, so the match succeeds and all four names are filled in.
Greedy versus lazy: the classic log-parsing bug

Quantifiers are greedy by default: .* grabs as much text as it possibly can, and gives some back only if the rest of the pattern would otherwise fail. Picture a hungry person filling a plate at a buffet before reading the rest of the menu. In a log line with two quoted fields, the greedy pattern ".*" starts at the FIRST quote and runs all the way to the LAST quote.

Greedy vs lazy vs precise
import re line = 'GET /a "Mozilla/5.0" "https://example.com/x" 200' print(re.search(r'".*"', line).group()) print(re.search(r'".*?"', line).group()) print(re.findall(r'"([^"]*)"', line))
Output
"Mozilla/5.0" "https://example.com/x"
"Mozilla/5.0"
['Mozilla/5.0', 'https://example.com/x']
Why greedy overshoots: what the engine does with the greedy pattern
line:   GET /a "Mozilla/5.0" "https://example.com/x" 200
                ^                                  ^
   1. the opening " matches the first quote
   2. .*  swallows EVERYTHING to the end of the line:   Mozilla/5.0" "https://... 200
   3. now the closing " has nothing left to match -> BACK OFF one character at a time
   4. ...back off until a " is found: the LAST quote  -> match = first quote ... last quote

lazy  .*?  reverses it: take 0 characters, try the closing ", take 1 more, try again, ...
           stops at the FIRST closing quote -> match = "Mozilla/5.0"
Greedy takes everything, then backs off one character at a time until the final quote fits. Lazy does the opposite: it takes one character, checks the quote, and stops early.

Adding a ? after a quantifier makes it lazy: it takes as little as possible. That fixes this line, but the third pattern is the best habit. [^"]* says exactly what you mean, "anything that is not a quote", so it can never overshoot. It is also faster, because it never has to back off.

Optional parts and alternatives

Two more symbols finish the toolkit. The pipe | means or: the size field is either digits or a dash, written (?P<size>\d+|-). And (?:...) is a non-capturing group: it groups pieces so a quantifier can apply to them, without saving them. Following it with ? makes the whole chunk optional, which suits the request-time field that only some servers write. Now the full pattern for a combined log line. The flag re.VERBOSE lets us spread it over several lines and add comments; whitespace in the pattern is ignored.

The full combined-log pattern, one field per line
import re LOG_RE = re.compile(r''' (?P<ip>\S+)\s+\S+\s+\S+\s+ # client ip, ident, user \[(?P<ts>[^\]]+)\]\s+ # [12/Mar/2026:10:15:32 +0000] "(?P<method>[A-Z]+)\s+(?P<path>\S+)\s+[^"]+"\s+ # "GET /path HTTP/1.1" (?P<status>\d{3})\s+(?P<size>\d+|-)\s+ "(?P<referrer>[^"]*)"\s+"(?P<ua>[^"]*)" (?:\s+(?P<rt>\d+\.\d+))? # optional request_time ''', re.VERBOSE) line = '203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /api/v1/orders?id=42 HTTP/1.1" 200 1532 "-" "Mozilla/5.0" 0.128' m = LOG_RE.match(line) print(m.group("ip"), m.group("method"), m.group("path"), m.group("status"), m.group("rt")) print(m["ts"])
Output
203.0.113.7 GET /api/v1/orders?id=42 200 0.128
12/Mar/2026:10:15:32 +0000

re.compile turns the pattern text into a reusable object once, so a loop over a million lines does not rebuild it each time. Note [^\]]+: "one or more characters that are not a closing bracket", the same negated-class habit as before.

Mistake 1: using the result without checking for None. When a line does not fit, match returns None, and None has no .group. Real logs always contain lines that do not fit.

Mistake 2: mixing up match, search and fullmatch. They differ only in where the pattern may sit. match must fit at the very start, search may fit anywhere, and fullmatch must use the whole string.

match vs search vs fullmatch
import re text = 'GET /a 200' print(re.match(r"/a", text)) print(re.search(r"/a", text)) print(re.fullmatch(r"\w+ /a", text)) print(re.fullmatch(r"\w+ /a \d+", text))

What is the difference between (?P<ip>\S+) and (?:\S+)?
The first captures what it matches under the name ip, so you can read it afterwards. The second groups without capturing: it exists only so a quantifier or | can apply to the group.

Recap
  • Parentheses capture pieces. Named groups (?P<name>...) let you read m["name"] or m.groupdict().
  • Greedy quantifiers take as much as possible and back off. Lazy (*?) takes as little as possible. A negated class such as [^"]* is the precise choice.
  • | means or, (?:...)? makes a chunk optional, and re.VERBOSE with comments makes long patterns readable. Compile once with re.compile.

1.6 — From Text to Typed Records (Without Crashing on Bad Lines)

A regex hands back strings. Even m["status"] is the text "401", not the number 401. That looks harmless until you compare. Strings are compared letter by letter, like dictionary order, so text that looks like numbers sorts in surprising ways. Try to ask "is this a server error?" on the raw text.

Text that looks like a number is not one
print("9" > "10") print(9 > 10) print("500" >= "500") print(int("500") >= 500)
Output
True
False
True
True

The first line prints True: as text, "9" comes after "1", so "9" is "bigger" than "10". The second line uses real numbers and gives the answer you expect. Worse, mixing the two types is an outright error.

Comparing a string with a numberread-only
status = "502" if status >= 500: print("server error")
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
    if status >= 500:
       ^^^^^^^^^^^^^
TypeError: '>=' not supported between instances of 'str' and 'int'

Read the last line: TypeError: '>=' not supported between instances of 'str' and 'int'. It names the operator and both types. The cure is to convert once, at the edge of your program, and work with proper types everywhere else. A convenient container for the converted values is a dataclass: a class whose only job is to hold named fields, where Python writes the boring __init__ and printing code for you. Each field is declared with a type, such as status: int. We call an object like this a record, one tidy row of data.

A parser that survives garbage

Real logs also contain garbage: lines cut off when a disk filled up, output from another program writing to the same file, half-written records from a crashed process. If your parser raises an error on the first bad line, it is useless in production. The robust pattern has three rules: return None for a line you cannot parse, count it, and carry on. The caller then decides what "too many skipped" means. The timestamp field is left out of this record for now; section 1.8 turns it into a real date and time.

Parse into a typed record
import re from dataclasses import dataclass LOG_RE = re.compile(r'(?P<ip>\S+) \S+ \S+ \[[^\]]+\] "\w+ (?P<path>\S+) [^"]*" (?P<status>\d{3}) (?P<size>\d+|-)') @dataclass class Entry: ip: str path: str status: int size: int def parse_line(line): m = LOG_RE.match(line) if not m: return None # caller decides what "unparseable" means size = 0 if m["size"] == "-" else int(m["size"]) return Entry(m["ip"], m["path"], int(m["status"]), size) print(parse_line('203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /orders HTTP/1.1" 200 1532')) print(parse_line('198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "GET /logo.png HTTP/1.1" 304 -')) print(parse_line('this line is a truncated write from a crashed process'))
Output
Entry(ip='203.0.113.7', path='/orders', status=200, size=1532)
Entry(ip='198.51.100.23', path='/logo.png', status=304, size=0)
None
What Python does, line by line
  • LOG_RE.match(line) tries the pattern from the start of the line. For a well-formed line it fills the named groups. For the "truncated write" line it fails at once and returns None.
  • if not m: return None handles that sad path early and quietly. Nothing crashes, and the caller receives None as a signal.
  • int(m["status"]) converts the text "200" into the number 200. The size field is special: a dash means "no value" (a 304 response sends no body), so it is converted by hand to 0.
  • Entry(...) builds the record. Printing it shows every field with its name, and status and size are now numbers, not text.

Now the loop that goes with the parser. It sorts every line into one of two piles: entries holds the records and skipped counts the rest. To keep this block short, it uses a smaller parser that reads only the status.

Count what you skip
import re def parse_line(line): # a shortened parser: status only m = re.search(r'" (\d{3}) ', line) return int(m[1]) if m else None lines = [ '203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /orders HTTP/1.1" 200 1532', 'this line is a truncated write from a crashed process', '198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "POST /login HTTP/1.1" 401 87', '', ] statuses, skipped = [], 0 for ln in lines: s = parse_line(ln) if s is None: skipped += 1 else: statuses.append(s) print(len(statuses), "parsed,", skipped, "skipped:", statuses)
Output

Common mistake: int("-")

The dash is the log format's way of writing "no value". Passing it straight to int blows up on the first such line.

Converting a dash to a numberread-only

The skip count is a signal

Do not throw the skipped count away. If unparseable lines jump from 0.01% to 30% right after a deploy, the log format changed and your report is now silently missing data. Compute the ratio and warn when it crosses a threshold.

Recap
  • Regex groups return strings. Convert to int and float once, at the edge, and keep real types afterwards.
  • A dataclass is a named-field record: a tidy row with typed fields.

1.7 — Counter: Top-N Anything

"Who are the 10 busiest IPs?" "Which endpoints get the most traffic?" "How many of each status code?" These questions are all one operation: count how often each thing appears, then list the biggest counts. You already know a tool for counting, the dictionary. Here is what that looks like, and where it bites.

Counting with a plain dictread-only
ips = ["203.0.113.7", "198.51.100.23", "203.0.113.7"] counts = {} for ip in ips: counts[ip] += 1 print(counts)
What Python says
Traceback (most recent call last):
  File "<exec>", line 5, in <module>
    counts[ip] += 1
    ~~~~~~^^^^
KeyError: '203.0.113.7'

The message, KeyError: '203.0.113.7', says the key was not in the dictionary yet, so += 1 had nothing to add to. The usual fix needs a check on every line (if ip in counts: ... else: ...). Python ships a better tool for exactly this job: collections.Counter. It is a dictionary that treats any missing key as having count 0, so the first += 1 just works.

Counter counts, and most_common ranks
from collections import Counter ips = ["203.0.113.7", "198.51.100.23", "203.0.113.7", "192.0.2.55", "203.0.113.7", "198.51.100.23"] counts = Counter(ips) print(counts) print(counts.most_common(2)) print(counts["203.0.113.7"], counts["10.9.9.9"])
Output
Counter({'203.0.113.7': 3, '198.51.100.23': 2, '192.0.2.55': 1})
[('203.0.113.7', 3), ('198.51.100.23', 2)]
3 0
What Python does, line by line
  • Counter(ips) walks the list once and builds a dictionary from each distinct item to how many times it appeared.
  • counts.most_common(2) sorts by count, largest first, and returns the top 2 as a list of (item, count) pairs. Leave out the number to get every item, ranked.
  • counts["10.9.9.9"] is an IP that never appeared. A plain dict would raise KeyError. A Counter answers 0 without adding the key.

You can also count one item at a time inside a loop, with counts[key] += 1. Because you often want several rankings from the same pass over the log, keep one counter per question and update all of them together. Remember our note about generators: you get ONE pass, so gather everything in it.

Three rankings from one pass

Output

top paths : [('/login', 2), ('/orders?id=42', 1)]

The paths ranking looks wrong. /orders?id=42, /orders?id=43 and /orders?id=7 are three different strings, so each has a count of 1, even though they are the same endpoint. The lesson: normalise before you count. That means cleaning each key so that things you consider equal really are equal. Here we drop everything after the ? (the query string) with urlsplit from the standard library.

Normalise the key, then count
from collections import Counter from urllib.parse import urlsplit raw_paths = ["/orders?id=42", "/orders?id=43", "/login", "/orders?id=7", "/login"] print(Counter(raw_paths).most_common(2)) clean = [urlsplit(p).path for p in raw_paths] print(clean) print(Counter(clean).most_common(2))
Output
[('/login', 2), ('/orders?id=42', 1)]
['/orders', '/orders', '/login', '/orders', '/login']
[('/orders', 3), ('/login', 2)]

Now /orders correctly appears three times. Same data, different question answered, all because of one cleaning step. The same habit applies to IP addresses that differ only in case or whitespace, or to status codes stored as text versus numbers.

Cardinality is the hidden costA Counter's memory grows with the number of distinct keys (its cardinality), not with the number of lines. Fifty million lines from 200,000 distinct IPs is small. For truly huge cardinality, say in an interview that you would fall back to sort | uniq -c, which sorts on disk, or to an approximate structure such as a Count-Min Sketch.
What does Counter('banana').most_common(1) return?
It returns [('a', 3)]. Counting characters gives a=3, n=2, b=1, and most_common(1) keeps only the top pair.
Your top-paths report shows 5,000 different paths, each with count 1. What is the likely cause and fix?

  • .most_common(n) returns the top n as (item, count) pairs.

1.8 — Time: Parsing Timestamps, Time Zones, Bucketing, and Error Rates

"When did the errors start?" is the first question in almost every incident. To answer it we group requests by time. But the timestamp in a log is text, like 12/Mar/2026:10:15:32 +0000, and text is a poor way to handle time. Sort a few of them and see.

Text timestamps sort in the wrong order
stamps = ["12/Mar/2026:10:15:32", "02/Apr/2026:09:00:00", "28/Feb/2026:23:59:59"] print(sorted(stamps))
Output
['02/Apr/2026:09:00:00', '12/Mar/2026:10:15:32', '28/Feb/2026:23:59:59']

Text sorts letter by letter, starting with the day number, so 02 Apr lands before 12 Mar and 28 Feb, which is the wrong order in time. We need a real date-and-time value. Python's datetime type is one, and datetime.strptime(text, format) ("string parse time") builds it. You describe the text's layout with a format string, where each % code stands for one part: %d day, %b short month name, %Y four-digit year, %H:%M:%S hours, minutes, seconds and %z the UTC offset.

strptime turns text into a datetime
from datetime import datetime text = "12/Mar/2026:10:15:32 +0000" ts = datetime.strptime(text, "%d/%b/%Y:%H:%M:%S %z") print(ts) print(ts.hour, ts.minute, ts.isoformat()) print(sorted([ datetime.strptime(s, "%d/%b/%Y:%H:%M:%S") for s in ["12/Mar/2026:10:15:32", "02/Apr/2026:09:00:00", "28/Feb/2026:23:59:59"] ])[0])
Output
2026-03-12 10:15:32+00:00
10 15 2026-03-12T10:15:32+00:00
2026-02-28 23:59:59

The last line sorts the same three stamps again, now as real datetimes, and the earliest one (28 Feb) comes first. A datetime also knows how to give you its parts (.hour, .minute) and how to print itself in the standard sortable ISO layout with .isoformat().

Time zones: the same moment, two clocks

The +0000 in the log is a UTC offset: how far the server's local clock is from UTC (Coordinated Universal Time, the world reference clock). A server in Berlin in winter writes +0100. Two lines from different servers can therefore show different clock times for the same instant, like two friends in different cities looking at their own wall clocks. Before comparing or bucketing, convert everything to UTC with .astimezone(timezone.utc).

Same instant, different local clocks
from datetime import datetime, timezone fmt = "%d/%b/%Y:%H:%M:%S %z" berlin = datetime.strptime("12/Mar/2026:11:15:32 +0100", fmt) london = datetime.strptime("12/Mar/2026:10:15:32 +0000", fmt) print(berlin == london) print(berlin.astimezone(timezone.utc).isoformat()) print(berlin.hour, berlin.astimezone(timezone.utc).hour)
Output
True
2026-03-12T10:15:32+00:00
11 10

The two datetimes are equal, because they describe the same instant even though their clocks read 11:15 and 10:15. After converting to UTC, the hour is 10 for both. The rule that saves you: convert to UTC as early as possible, and only think about local time when you print for humans.

Bucketing and error rates

A bucket is a slice of time, such as "the hour starting at 10:00". To put each request in a bucket, turn its datetime into a label with strftime ("string format time", the reverse of strptime), such as "%Y-%m-%d %H:00". Everything from 10:00:00 to 10:59:59 gets the label 2026-03-12 10:00. Then count requests and errors per label and compute a rate, 5xx / total. A rate beats a raw count because during an outage traffic often drops, so the number of errors can fall while the percentage skyrockets. Only 5xx are server errors; a wave of 401 or 404 is a different problem.

Bucket by hour and compute the 5xx rate
from collections import defaultdict from datetime import datetime, timezone rows = [("12/Mar/2026:10:15:32 +0000", 200), ("12/Mar/2026:10:16:01 +0000", 401), ("12/Mar/2026:10:59:58 +0000", 502), ("12/Mar/2026:11:02:10 +0000", 200), ("12/Mar/2026:11:05:40 +0000", 500), ("12/Mar/2026:11:07:00 +0000", 500)] total, errors = defaultdict(int), defaultdict(int) for stamp, status in rows: ts = datetime.strptime(stamp, "%d/%b/%Y:%H:%M:%S %z").astimezone(timezone.utc) bucket = ts.strftime("%Y-%m-%d %H:00") total[bucket] += 1 if 500 <= status <= 599: errors[bucket] += 1 for bucket in sorted(total): rate = errors[bucket] / total[bucket] * 100 print(f"{bucket} {errors[bucket]}/{total[bucket]} = {rate:.1f}% 5xx")

What Python does, line by line
  • defaultdict(int) is a dictionary whose missing keys start at 0, so total[bucket] += 1 works the first time, like Counter.
  • For each row, strptime builds an aware datetime and astimezone(timezone.utc) moves it to UTC. strftime then makes the label, so 10:15 and 10:59 both become 2026-03-12 10:00.
  • Every row adds 1 to its bucket's total, and rows with status 500 to 599 also add 1 to its errors. The 401 is a client error and is not counted.
  • The final loop walks sorted(total), because a dictionary remembers arrival order, not time order. The 10:00 bucket has 1 error in 3 requests (33.3%); the 11:00 bucket has 2 errors in 3 (66.7%): errors are climbing.

1.1 — Reading Logs Lazily: Generators, Not .read()

A production access log is routinely several gigabytes. open(path).read() loads all of it into memory, and .readlines() builds a list of every line: either one can get your script OOM-killed on the very box that is already in trouble. A Python file object is already a lazy iterator: for line in f reads one line at a time, so memory stays roughly constant no matter how large the file is. A generator function (any function with yield) lets you build a pipeline of small lazy steps — read, parse, filter, aggregate — without ever holding the whole file.

Lazy reading: a generator over a file-like object
import io # io.StringIO stands in for open('/var/log/nginx/access.log') - same iteration API fake_file = io.StringIO("line one\nline two\nline three\nline four\n") def read_lines(f): for line in f: # the file object yields ONE line at a time yield line.rstrip("\n") gen = read_lines(fake_file) print(next(gen)) # only the first line has been read so far print(next(gen)) print("remaining:", list(gen)) # drains the rest - and now the generator is spent print("again:", list(gen)) # [] - a generator can only be consumed once
⚠️
A generator is single-use. After it is exhausted it silently yields nothing, so a second list(gen) returns [], not an error. If you need two passes (say a total and then percentages), either re-open the file or aggregate everything you need in ONE pass. This bug regularly makes a report show "0 requests".

Following a log as it grows (tail -f) is the same idea with a loop that waits for new data. It needs a real file that is being appended to and a real clock, so it is shown as reference only.

🎬
Reference code — not runnable in this browser. The sandbox has no real growing log file and no real clock, so there is no ▶ Run button on the next block. Copy it to a real machine to try it.
Reference only — a tail -f in Python
import os, time def follow(path): # what `tail -f` does with open(path) as f: f.seek(0, os.SEEK_END) # start at the END of the file while True: line = f.readline() if not line: # nothing new yet time.sleep(0.5) continue yield line for line in follow("/var/log/nginx/access.log"): print(line, end="")
💡
Log rotation breaks naive followers. When logrotate renames the file and creates a new one, the loop above keeps reading the OLD (now idle) file forever. tail -F (capital F) handles this by re-opening on inode change or truncation. In an interview, say that you would use tail -F or a library rather than hand-roll rotation handling.
1.2 — Regex for Log Lines: Named Groups and the Greedy Trap

str.split() is enough for simple whitespace-separated formats, but the nginx/Apache combined format has quoted fields that contain spaces (the request line and the user agent), so split() breaks on them. That is where re earns its place. Three habits matter: compile once outside the loop; use named groups (?P<ip>...) so the code reads like the log format; and use re.VERBOSE so you can lay the pattern out on several lines and comment it. Remember that match() anchors at the start of the string, search() looks anywhere, and fullmatch() must consume the whole string.

A named-group regex for the combined log format
import re LOG_RE = re.compile(r''' (?P<ip>\S+)\s+\S+\s+\S+\s+ # client ip, ident, user \[(?P<ts>[^\]]+)\]\s+ # [12/Mar/2026:10:15:32 +0000] "(?P<method>[A-Z]+)\s+(?P<path>\S+)\s+[^"]+"\s+ # "GET /path HTTP/1.1" (?P<status>\d{3})\s+(?P<size>\d+|-)\s+ "(?P<referrer>[^"]*)"\s+"(?P<ua>[^"]*)" (?:\s+(?P<rt>\d+\.\d+))? # optional request_time ''', re.VERBOSE) line = '203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /api/v1/orders?id=42 HTTP/1.1" 200 1532 "-" "Mozilla/5.0" 0.128' m = LOG_RE.match(line) print(m.group("ip"), m.group("method"), m.group("path"), m.group("status"), m.group("rt")) print(m.groupdict()["ts"])

The single most common regex bug in log parsing is greediness. .* takes as much as it can, so ".*" on a line with two quoted fields matches from the first quote to the last. Either make it lazy (.*?) or, better, say exactly what you mean: [^"]*, "anything that is not a quote".

Greedy vs. non-greedy: the classic log-parsing bug
import re line = 'GET /a "Mozilla/5.0" "https://example.com/x" 200' print(re.search(r'".*"', line).group()) # greedy: first quote ... LAST quote print(re.search(r'".*?"', line).group()) # lazy: stops at the next quote print(re.findall(r'"([^"]*)"', line)) # best: "anything that is not a quote"
🚨
Catastrophic backtracking is a real outage cause. A pattern with nested quantifiers such as (a+)+$ can take exponential time on a line that almost matches, and one crafted or corrupted log line can pin a CPU (this is "ReDoS"). Prefer negated character classes ([^"]*) over .*, anchor your patterns, and note that Python 3.11+ adds possessive quantifiers (a++) and atomic groups ((?>...)) that forbid backtracking.
1.3 — From Text to Typed Records (Without Crashing on Bad Lines)

Raw strings are hard to work with; a dataclass with real types (an int status, a float latency, a timezone-aware datetime) is not. But real logs contain garbage: lines truncated when a disk filled up, output from another program writing to the same file, half-written records from a crashed process. A parser that raises on the first bad line is useless in production. The robust pattern is: return None for a line you cannot parse, count it, and carry on. The caller decides what "too many skipped" means.

Parse into a typed record, and tolerate garbage lines
import re from dataclasses import dataclass from datetime import datetime LOG_RE = re.compile(r''' (?P<ip>\S+)\s+\S+\s+\S+\s+ # client ip, ident, user \[(?P<ts>[^\]]+)\]\s+ # [12/Mar/2026:10:15:32 +0000] "(?P<method>[A-Z]+)\s+(?P<path>\S+)\s+[^"]+"\s+ # "GET /path HTTP/1.1" (?P<status>\d{3})\s+(?P<size>\d+|-)\s+ "(?P<referrer>[^"]*)"\s+"(?P<ua>[^"]*)" (?:\s+(?P<rt>\d+\.\d+))? # optional request_time ''', re.VERBOSE) @dataclass class Entry: ip: str ts: datetime method: str path: str status: int size: int rt: float def parse_line(line): m = LOG_RE.match(line) if not m: return None # caller decides what "unparseable" means d = m.groupdict() return Entry( ip=d["ip"], ts=datetime.strptime(d["ts"], "%d/%b/%Y:%H:%M:%S %z"), method=d["method"], path=d["path"], status=int(d["status"]), size=0 if d["size"] == "-" else int(d["size"]), rt=float(d["rt"]) if d["rt"] else 0.0, ) lines = [ '203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /api/v1/orders?id=42 HTTP/1.1" 200 1532 "-" "Mozilla/5.0" 0.128', 'this line is a truncated write from a crashed process', '198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "POST /login HTTP/1.1" 401 87 "-" "curl/8.5.0" 0.045', ] entries, skipped = [], 0 for ln in lines: e = parse_line(ln) if e is None: skipped += 1 else: entries.append(e) print(len(entries), "parsed,", skipped, "skipped") print(entries[0]) print(entries[0].ts.isoformat())
⭐
The skipped count is a signal, not just noise. If unparseable lines jump from 0.01% to 30% right after a deploy, the log format changed. Alert on the skip ratio. Also note that - is the log format's way of writing "no value" (a size of - on a 304, an unknown user), so convert it deliberately rather than letting int("-") blow up.
1.4 — Counter: Top-N Anything

"Top 10 IPs", "most requested endpoints", "status code distribution", "busiest user agents": these are all the same operation. collections.Counter is a dict subclass that counts hashable items, and .most_common(n) returns the top n as (item, count) pairs. Two habits separate a good answer from a sloppy one: normalise before you count (drop the ?query so /orders?id=1 and /orders?id=2 are one endpoint), and remember that memory grows with the number of distinct keys, not with the number of lines.

Counter: the top-N tool you will use daily
import re from collections import Counter from urllib.parse import urlsplit LOG = """203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /api/v1/orders?id=42 HTTP/1.1" 200 1532 "-" "Mozilla/5.0" 0.128 203.0.113.7 - - [12/Mar/2026:10:15:33 +0000] "GET /api/v1/orders?id=43 HTTP/1.1" 200 1498 "-" "Mozilla/5.0" 0.131 198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "POST /login HTTP/1.1" 401 87 "-" "curl/8.5.0" 0.045 198.51.100.23 - - [12/Mar/2026:10:16:02 +0000] "POST /login HTTP/1.1" 401 87 "-" "curl/8.5.0" 0.044 192.0.2.55 - - [12/Mar/2026:10:17:45 +0000] "GET /static/app.js HTTP/1.1" 200 48211 "https://shop.example.com/" "Mozilla/5.0" 0.009 203.0.113.7 - - [12/Mar/2026:10:59:58 +0000] "POST /api/v1/checkout HTTP/1.1" 502 157 "-" "Mozilla/5.0" 3.204 192.0.2.55 - - [12/Mar/2026:11:02:10 +0000] "GET /api/v1/orders?id=7 HTTP/1.1" 200 1611 "-" "Mozilla/5.0" 0.140 10.0.0.9 - - [12/Mar/2026:11:03:00 +0000] "GET /health HTTP/1.1" 200 2 "-" "kube-probe/1.29" 0.001 198.51.100.23 - - [12/Mar/2026:11:04:12 +0000] "POST /login HTTP/1.1" 401 87 "-" "curl/8.5.0" 0.046 203.0.113.7 - - [12/Mar/2026:11:05:40 +0000] "POST /api/v1/checkout HTTP/1.1" 500 212 "-" "Mozilla/5.0" 2.871""" ips, paths, statuses = Counter(), Counter(), Counter() for line in LOG.splitlines(): parts = line.split() ips[parts[0]] += 1 path = urlsplit(parts[6]).path # drop the ?query so /orders?id=1 and ?id=2 group together paths[path] += 1 statuses[parts[8]] += 1 print("top IPs :", ips.most_common(2)) print("top paths :", paths.most_common(3)) print("status mix :", dict(statuses)) print("unique IPs :", len(ips))

Cardinality is the hidden cost. A Counter of 50 million lines from 200,000 distinct IPs is small; a Counter of full URLs including unique query strings or session IDs can hold tens of millions of keys and exhaust memory. 1.5 — Time: Parsing Timestamps, Bucketing, and Error Rates

To answer "when did the errors start?" you bucket requests by time. Parse the stamp with datetime.strptime using %z to capture the UTC offset, convert to UTC, and build a sortable key with strftime("%Y-%m-%d %H:00") (per hour) or "%H:%M" (per minute). Then compute a rate, 5xx / total, not a raw count: during an outage traffic often drops, so the count of errors can fall while the percentage skyrockets. Only 5xx are server errors; a wave of 404s or 401s is a different problem.

Bucket by hour and compute the 5xx error rate
import re from collections import defaultdict from datetime import datetime, timezone LOG = """203.0.113.7 - - [12/Mar/2026:10:15:32 +0000] "GET /api/v1/orders?id=42 HTTP/1.1" 200 1532 "-" "Mozilla/5.0" 0.128 203.0.113.7 - - [12/Mar/2026:10:15:33 +0000] "GET /api/v1/orders?id=43 HTTP/1.1" 200 1498 "-" "Mozilla/5.0" 0.131 198.51.100.23 - - [12/Mar/2026:10:16:01 +0000] "POST /login HTTP/1.1" 401 87 "-" "curl/8.5.0" 0.045 198.51.100.23 - - [12/Mar/2026:10:16:02 +0000] "POST /login HTTP/1.1" 401 87 "-" "curl/8.5.0" 0.044 192.0.2.55 - - [12/Mar/2026:10:17:45 +0000] "GET /static/app.js HTTP/1.1" 200 48211 "https://shop.example.com/" "Mozilla/5.0" 0.009 203.0.113.7 - - [12/Mar/2026:10:59:58 +0000] "POST /api/v1/checkout HTTP/1.1" 502 157 "-" "Mozilla/5.0" 3.204 192.0.2.55 - - [12/Mar/2026:11:02:10 +0000] "GET /api/v1/orders?id=7 HTTP/1.1" 200 1611 "-" "Mozilla/5.0" 0.140 10.0.0.9 - - [12/Mar/2026:11:03:00 +0000] "GET /health HTTP/1.1" 200 2 "-" "kube-probe/1.29" 0.001 198.51.100.23 - - [12/Mar/2026:11:04:12 +0000] "POST /login HTTP/1.1" 401 87 "-" "curl/8.5.0" 0.046 203.0.113.7 - - [12/Mar/2026:11:05:40 +0000] "POST /api/v1/checkout HTTP/1.1" 500 212 "-" "Mozilla/5.0" 2.871""" total = defaultdict(int) errors = defaultdict(int) for line in LOG.splitlines(): parts = line.split() stamp = " ".join(parts[3:5]).strip("[]") # "12/Mar/2026:10:15:32 +0000" ts = datetime.strptime(stamp, "%d/%b/%Y:%H:%M:%S %z").astimezone(timezone.utc) bucket = ts.strftime("%Y-%m-%d %H:00") # normalise to UTC before bucketing total[bucket] += 1 if parts[8].startswith("5"): errors[bucket] += 1 for bucket in sorted(total): # sorted(): dict order is arrival order, not time order rate = errors[bucket] / total[bucket] * 100 print(f"{bucket} {errors[bucket]}/{total[bucket]} = {rate:.1f}% 5xx")

1.6 — Latency Percentiles: Why the Average Lies

If 99 requests take 10 ms and one takes 10 seconds, the mean is about 110 ms, a number that describes nobody. Latency has a long tail, so SLOs are written in percentiles: p50 is the typical request, p95 and p99 are what your slowest users feel. The nearest-rank method is the simplest: sort, take rank ceil(p/100 × n). Be aware that other tools interpolate between neighbouring samples, so statistics.quantiles and numpy give slightly different p95s for the same data. Pick one definition and say which.

Percentiles: nearest-rank by hand, and why methods disagree
import math, statistics latencies = [0.011, 0.012, 0.012, 0.013, 0.014, 0.015, 0.016, 0.018, 0.021, 0.024, 0.027, 0.031, 0.036, 0.044, 0.052, 0.071, 0.098, 0.412, 1.905, 4.310] def nearest_rank(data, p): ordered = sorted(data) k = math.ceil(p / 100 * len(ordered)) # rank, 1-based return ordered[k - 1] print("mean :", round(sum(latencies) / len(latencies), 3)) print("p50 :", nearest_rank(latencies, 50)) print("p95 :", nearest_rank(latencies, 95)) print("p99 :", nearest_rank(latencies, 99)) q = statistics.quantiles(latencies, n=100, method="inclusive") # 99 cut points, interpolated print("stdlib p95 (interpolated):", round(q[94], 3))
⭐
You cannot average percentiles. The p95 of server A and the p95 of server B do not combine into the fleet p95: the average of two p95s is not a p95. To aggregate correctly you must merge the raw samples or, at scale, merge histograms (which is exactly why Prometheus records latency as histogram buckets rather than pre-computed percentiles). This is a favourite senior-level interview follow-up.
1.7 — Detecting Brute Force: The Sliding Window

"Flag any IP with 5 failed SSH logins in 10 seconds" sounds simple, but the naive approach, counting failures per fixed calendar minute, has a hole: an attacker who sends 5 attempts at 10:00:58 and 5 more at 10:01:02 is never caught, because each bucket only holds 5 spread across a boundary. The correct tool is a sliding window: keep a deque of recent timestamps per IP, and on each new event push it and pop from the left everything that has fallen out of the window. deque.popleft() is O(1), while list.pop(0) is O(n). Each event is added once and removed once, so the whole pass is linear.

Sliding window with a deque: detect brute force from auth.log
import re from collections import defaultdict, deque from datetime import datetime AUTH = """Mar 12 10:15:31 web01 sshd[2201]: Failed password for invalid user admin from 198.51.100.23 port 51122 ssh2 Mar 12 10:15:33 web01 sshd[2203]: Failed password for invalid user admin from 198.51.100.23 port 51130 ssh2 Mar 12 10:15:34 web01 sshd[2205]: Failed password for root from 198.51.100.23 port 51138 ssh2 Mar 12 10:15:36 web01 sshd[2207]: Failed password for root from 198.51.100.23 port 51144 ssh2 Mar 12 10:15:38 web01 sshd[2209]: Failed password for root from 198.51.100.23 port 51150 ssh2 Mar 12 10:16:02 web01 sshd[2301]: Accepted publickey for deploy from 192.0.2.55 port 40222 ssh2 Mar 12 10:20:00 web01 sshd[2410]: Failed password for alice from 203.0.113.7 port 60001 ssh2 Mar 12 10:25:00 web01 sshd[2411]: Failed password for alice from 203.0.113.7 port 60002 ssh2""" FAIL_RE = re.compile(r"^(?P<ts>\w{3}\s+\d+ [\d:]{8}) \S+ sshd\[\d+\]: Failed password for (?:invalid user )?(?P<user>\S+) from (?P<ip>\S+)") WINDOW, LIMIT = 10, 5 # 5 failures inside any 10-second window recent = defaultdict(deque) # ip -> timestamps still inside the window flagged = set() for line in AUTH.splitlines(): m = FAIL_RE.match(line) if not m: continue # Accepted logins etc. are not failures # syslog timestamps carry NO year - you must supply one yourself t = datetime.strptime("2026 " + m["ts"], "%Y %b %d %H:%M:%S").timestamp() q = recent[m["ip"]] q.append(t) while t - q[0] >= WINDOW: # evict everything that fell out of the window q.popleft() if len(q) >= LIMIT: flagged.add(m["ip"]) print("flagged:", sorted(flagged))
⚠️
Detection is not the same as blocking. A whole office or university often shares one NAT address and can trip a per-IP threshold with perfectly legitimate typos, so allow-list known ranges before you auto-ban anything. Also note that a distributed attack (thousands of IPs, one guess each) never trips a per-IP counter; you catch that by aggregating per username. Tools such as fail2ban implement exactly this pattern.

💼 Log Parsing & Text Processing — Interview Prep

10 questions that come up for DevOps, SRE and platform roles, with the answer a strong candidate gives (including the pitfall interviewers listen for). Click a question to reveal the answer.

How would you find the top 10 client IPs in a 50 GB access log?▶
Stream it: read line by line, pull the IP from the first field, and feed a Counter; then call .most_common(10). Memory depends on the number of distinct IPs, not the 50 GB, so it is usually tiny. If cardinality were enormous I would say so and fall back to awk '{print $1}' | sort | uniq -c | sort -rn | head (external sort spills to disk) or an approximate structure such as a Count-Min Sketch. To go faster, split the file (or the rotated files) across processes, build a Counter per shard, then merge them with +. Also mention that you would sanity-check that the log format is what you assume before trusting the answer.
Count the number of 5xx responses per hour. What can go wrong?▶
Parse the timestamp with strptime and %z, convert to UTC, bucket by strftime('%Y-%m-%d %H:00'), and count with a defaultdict(int). What goes wrong: mixed timezones or missing offsets, syslog lines with no year, unparseable lines silently dropped (so your denominator is wrong), iterating a dict in arrival order instead of sorted(), counting 4xx as errors, and reporting a raw count instead of a rate (traffic drops during an outage). I would also emit the number of skipped lines so the reader can judge how trustworthy the figure is.
How would you implement tail -f in Python, and where does it break?▶
Open the file, seek(0, os.SEEK_END), then loop: readline(); if it returns an empty string sleep briefly and try again; otherwise yield the line. It breaks on log rotation (the file is renamed, and the loop keeps reading the old inode), on truncation (copytruncate), and on partial lines (a writer flushed half a line). Production answer: use tail -F, or inotify/watchdog, or better, do not tail files at all — ship logs with an agent (Fluent Bit, Vector, Promtail) to a central store.
What is catastrophic backtracking in a regex, and how do you avoid it in log parsing?▶
Some patterns, typically nested quantifiers such as (a+)+$ or overlapping alternations, force the engine to try an exponential number of ways to match a line that almost matches. One malformed or attacker-controlled log line can then consume a CPU for minutes (ReDoS). Avoid it with negated character classes ([^"]* instead of .*), anchors, specific tokens instead of nested wildcards, possessive quantifiers/atomic groups (Python 3.11+), limiting line length before matching, and by not using a regex at all when split() or structured (JSON) logs will do.
Generator versus list when processing a large file: trade-offs?▶
A generator produces items lazily, so memory is O(1) and you can start processing immediately; a list holds everything, so memory is O(n) but you get random access, len(), sorting and multiple passes. The gotchas with generators: they are single-use (a second loop yields nothing, silently), you cannot index or take len(), and exceptions surface late, at consumption time. Rule of thumb: stream for one-pass aggregation, materialise only the reduced result (a Counter, a summary), not the raw data.
Why are p95/p99 more useful than the average latency, and how do you aggregate them across servers?▶
Latency is long-tailed: a few slow requests barely move the mean but define the experience of your unluckiest users, and in a fan-out architecture the tail dominates. SLOs are therefore written as percentiles (for example p99 < 500 ms). Aggregation is the trap: you cannot average percentiles. To get a fleet percentile, merge the raw samples or merge histograms (Prometheus histogram buckets, HDR histograms), then compute the percentile from the merged distribution. Also state which percentile definition you use (nearest-rank vs interpolated) because tools disagree slightly.
How would you detect an SSH brute-force attack from auth.log?▶
Extract failed-login events (regex on Failed password for ... from <ip>), then run a sliding window per IP: keep a deque of timestamps, append the new one, pop from the left while it is outside the window, and flag if the length reaches the threshold. Fixed buckets miss bursts that straddle a boundary. Caveats I would raise: syslog has no year/timezone, shared NAT addresses cause false positives (allow-list them), and distributed attacks need aggregation per username. In real life I would deploy fail2ban or rate-limit at the edge instead of hand-rolling enforcement.
Why do many teams prefer structured (JSON) logs, and how does that change parsing?▶
One JSON object per line removes the regex from the critical path: json.loads(line) gives typed fields, adding a field does not break existing parsers, and log platforms (Loki, Elasticsearch, CloudWatch Logs Insights) can index and query fields directly. You should still wrap json.loads in try/except for truncated lines and count failures. Good fields to include: a UTC ISO-8601 timestamp, level, service name, a request/trace ID for correlating across services, and the duration. The cost is verbosity and a bit more CPU to serialise.
What are the timezone pitfalls when analysing logs from many servers?▶
Servers may log in local time; nginx includes an offset, but syslog lines have neither year nor timezone; and daylight saving makes an hour repeat or vanish. The rules I follow: configure servers to log UTC (or ISO-8601 with offset), parse with %z and convert to UTC immediately, supply the year explicitly when parsing syslog (and handle the December/January rollover), sort by real timestamps rather than file order, and never compare a naive datetime to an aware one (Python raises TypeError).
When do you use a shell one-liner and when do you write a Python script for log analysis?▶
For quick, one-off exploration on a live machine I use grep/awk/sort | uniq -c: they stream, they are C-fast and they need no setup. I switch to Python when the logic gets stateful or non-trivial (sliding windows, percentiles, joins across files), when the result must be structured or tested, or when the script will be rerun or scheduled. For continuous, fleet-wide analysis neither is the answer: I would use a log pipeline (Loki/ELK/CloudWatch) with alerting, and use Python for glue and ad-hoc investigation.
