DevOps Bonus 5:
The Python Mock Interview

DevOps, SRE and platform interviews rarely ask you to invert a binary tree. They ask you to rate-limit an API, cache with expiry, merge layered config, spot a flapping service, find the slowest endpoints, or work out what order to deploy things in — and then to explain your choices out loud. This chapter builds each of those from scratch in plain Python, shows how to narrate it, covers the Python gotchas interviewers love, and ends with a timed three-problem mock.

5.1 — How to Approach a Python Interview Problem

Most failed interviews are not failed on algorithms — they are failed on process. Interviewers are scoring whether you can be trusted with an ambiguous production problem, and the process below is the same one you use on the job when someone hands you a vague ticket. Use it on every problem in this chapter.

StepWhat you doWhat it buys you
1. ClarifyRestate the problem. Ask about input size, duplicates, empty input, ordering, units, what to return on bad input.Catches misunderstandings while they are cheap
2. ExampleWork one tiny example by hand, out loud.Proves you understand the expected output
3. Brute forceState the obvious approach and its complexity — before improving it.A safety net, and it shows you know the baseline
4. OptimizeName the bottleneck, then the data structure that removes it.The part interviewers actually grade
5. CodeSmall named functions, clear variables, no clever one-liners.Readable code is reviewable code
6. TestEmpty input, one element, duplicates, the boundary case.Shows the production instinct
7. CloseState time and space complexity and what you would do with more time.Signals you have done this before

Here is the whole loop on a deliberately small DevOps problem: "which of the services I plan to deploy are not currently healthy?"

Brute force, then a set, then edge cases
scheduled = ["api", "auth", "billing", "cache", "search", "web"] healthy = ["web", "auth", "db", "cache", "queue"] # Step 1 - say the brute force out loud, then improve it def unhealthy_bruteforce(scheduled, healthy): out = [] for s in scheduled: # n iterations found = False for h in healthy: # m iterations each -> O(n * m) if s == h: found = True break if not found: out.append(s) return out # Step 2 - a set gives O(1) membership -> O(n + m) overall def unhealthy(scheduled, healthy): healthy_set = set(healthy) return [s for s in scheduled if s not in healthy_set] print("brute force :", unhealthy_bruteforce(scheduled, healthy)) print("with a set :", unhealthy(scheduled, healthy)) # Step 3 - prove it on tiny edge cases before claiming you're done print("empty scheduled:", unhealthy([], healthy)) print("empty healthy :", unhealthy(scheduled, [])) print("duplicates :", unhealthy(["api", "api"], healthy))
🗣️
Say out loud: "The brute force checks every scheduled service against every healthy one, so O(n times m). The repeated work is the membership test, so I will put the healthy list in a set to make that O(1) — O(n + m) overall. Let me check empty input and duplicates." Notice you named the bottleneck before you named the fix.
5.2 — Rate Limiting: the Token Bucket (and Why Clocks Get Injected)

A token bucket holds up to capacity tokens and refills at a steady rate. Each request spends a token; if the bucket is empty the request is denied. That gives you a sustained rate (the refill rate) and a controlled burst (the capacity) — which is what API gateways, nginx limit_req and cloud APIs actually implement. The clever part is that you never need a background timer: you refill lazily, computing how many tokens accrued since the last call.

Notice the class takes a clock argument instead of calling time.time() directly. That is the single most useful habit for time-dependent code: in a test (or an interview) you hand it a fake clock and control time exactly, with no sleep() and no flaky tests.

TokenBucket with an injected clock
class FakeClock: """A clock you control - the trick that makes time-based code testable.""" def __init__(self, start=0.0): self.t = start def __call__(self): return self.t def advance(self, seconds): self.t += seconds class TokenBucket: def __init__(self, capacity, refill_per_sec, clock): self.capacity = capacity self.refill_per_sec = refill_per_sec self.clock = clock self.tokens = float(capacity) # start full: allows an initial burst self.last = clock() def allow(self, cost=1): now = self.clock() elapsed = now - self.last self.last = now # refill lazily on each call - no background thread needed self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_per_sec) if self.tokens >= cost: self.tokens -= cost return True return False clock = FakeClock() bucket = TokenBucket(capacity=3, refill_per_sec=1, clock=clock) print("burst of 5 at t=0:", [bucket.allow() for _ in range(5)]) clock.advance(2) print("after 2 seconds :", [bucket.allow() for _ in range(3)]) clock.advance(0.5) print("0.5 seconds later:", bucket.allow(), "(only half a token has refilled)")
🧠
Floats and refill: tokens are floats because half a second at 1 token/sec is half a token. Always cap with min(capacity, ...) — otherwise an idle client accumulates unlimited tokens and can burst without bound after a long pause.

Why not just count requests per minute? Because of the fixed-window boundary problem: a client can spend its whole allowance at the end of one window and again at the start of the next.

Fixed window: the boundary burst
def fixed_window_allows(times, limit, window): counts, results = {}, [] for t in times: w = int(t // window) # which fixed window this request lands in counts[w] = counts.get(w, 0) + 1 results.append(counts[w] <= limit) return results # 5 requests in the last 0.1s of window 0, 5 more in the first 0.1s of window 1 times = [9.9] * 5 + [10.0] * 5 res = fixed_window_allows(times, limit=5, window=10) print("allowed:", sum(res), "of", len(times), "requests inside 0.1 seconds") print("a limit of 5 per 10s just let through a burst of 10")
⚠️
The comparison interviewers ask for: fixed window is simplest but allows 2x bursts at the boundary; sliding window (log or counter) is accurate but costs memory; token bucket allows deliberate bursts up to capacity; leaky bucket smooths output to a constant rate (it queues, it does not burst). In a distributed system the state lives in something shared like Redis, updated atomically.
5.3 — A TTL + LRU Cache with OrderedDict

Caches show up everywhere in operations tooling: DNS lookups, IAM token exchanges, API results you do not want to re-fetch. Two rules define this one: an entry expires after a time-to-live, and when the cache is full the least recently used entry is evicted. collections.OrderedDict gives both cheaply — move_to_end() marks a key as most recently used and popitem(last=False) removes the oldest, each in O(1).

TTLCache: expiry plus LRU eviction
from collections import OrderedDict class FakeClock: def __init__(self, start=0.0): self.t = start def __call__(self): return self.t def advance(self, seconds): self.t += seconds class TTLCache: def __init__(self, capacity, ttl, clock): self.capacity, self.ttl, self.clock = capacity, ttl, clock self._data = OrderedDict() # key -> (value, expires_at); order = LRU -> MRU def _purge(self): now = self.clock() for key in [k for k, (_, exp) in self._data.items() if exp <= now]: del self._data[key] def get(self, key): self._purge() if key not in self._data: return None self._data.move_to_end(key) # touching a key makes it most recently used return self._data[key][0] def put(self, key, value): self._purge() self._data[key] = (value, self.clock() + self.ttl) self._data.move_to_end(key) while len(self._data) > self.capacity: self._data.popitem(last=False) # evict the least recently used def keys(self): self._purge() return list(self._data) clock = FakeClock() cache = TTLCache(capacity=2, ttl=10, clock=clock) cache.put("a", 1) cache.put("b", 2) print("get a:", cache.get("a")) # a is now the most recently used cache.put("c", 3) # over capacity -> evicts b print("keys after adding c:", cache.keys()) clock.advance(11) print("get a after 11s:", cache.get("a")) print("keys after expiry:", cache.keys())
🧠
Trade-off to mention: this version purges expired keys on every call, which is O(n) per operation — chosen for clarity. In production you would expire lazily inside get() (O(1)) and optionally keep a heap keyed by expiry time for a background sweep. Being able to say why you kept it simple, and what you would change at scale, is exactly what the interviewer is fishing for. Also note that reading a key makes it "recently used" but does not extend its TTL — those are different policies, so state which one you chose.
5.4 — Deep-Merging Layered Config

Real config is layered: built-in defaults, then an environment file, then a per-service override, then maybe a CLI flag. Helm values, Kubernetes overlays, Ansible variables and most 12-factor apps all work this way. The naive implementation — {**defaults, **override} — is a classic bug, because it replaces a nested dict wholesale and silently drops sibling keys.

Shallow merge loses keys; deep merge does not
import copy, json def deep_merge(base, override): result = copy.deepcopy(base) # never mutate the caller's data for key, value in override.items(): if value is None: result.pop(key, None) # explicit null deletes the key elif isinstance(value, dict) and isinstance(result.get(key), dict): result[key] = deep_merge(result[key], value) # recurse into nested dicts else: result[key] = copy.deepcopy(value) # scalars and lists are replaced return result defaults = {"replicas": 2, "resources": {"cpu": "250m", "memory": "256Mi"}, "labels": {"team": "platform"}, "debug": True} prod = {"replicas": 6, "resources": {"memory": "1Gi"}, "debug": None} shallow = {**defaults, **prod} print("shallow merge resources:", shallow["resources"], "<- cpu was silently lost") merged = deep_merge(defaults, prod) print("deep merge:", json.dumps(merged, sort_keys=True)) print("defaults untouched:", defaults["replicas"] == 2 and "debug" in defaults)
⚠️
State your merge rules, because there is no single right answer: here nested dicts merge recursively, scalars and lists are replaced (not concatenated), and an explicit None deletes the key. Kubernetes strategic-merge-patch and Helm each make different choices about lists — interviewers like candidates who notice that. And always deepcopy: returning a structure that shares nested objects with the input lets a later mutation corrupt your defaults.
5.5 — Detecting a Flapping Service from an Event Stream

A flapping service bounces between up and down. It is worse than a clean outage because alerts fire and resolve repeatedly and people stop trusting them. Detection is a sliding-window problem: record the timestamps of genuine state changes, then ask whether any min_changes of them fit inside one window. Two details trip people up: the first time you see a service is not a change, and a repeated identical status is not a change either.

find_flapping: state changes inside a sliding window
from collections import defaultdict events = [ # (seconds, service, status), already ordered by time (0, "api", "up"), (0, "db", "up"), (0, "cache", "up"), (60, "api", "down"), (90, "api", "up"), (100, "cache", "down"), (120, "api", "down"), (150, "api", "up"), (200, "db", "down"), (500, "db", "up"), (700, "cache", "up"), (1500, "cache", "down"), ] def find_flapping(events, min_changes=3, window=300): last_status, changes = {}, defaultdict(list) for ts, service, status in events: if service in last_status and last_status[service] != status: changes[service].append(ts) # a real state change last_status[service] = status # first sighting is not a change flapping = [] for service, times in changes.items(): for i in range(len(times) - min_changes + 1): if times[i + min_changes - 1] - times[i] <= window: flapping.append(service) # min_changes changes fit in one window break return sorted(flapping), {s: len(t) for s, t in sorted(changes.items())} flapping, counts = find_flapping(events) print("flapping:", flapping) print("change counts:", counts) print("cache changed 3 times too, but spread over 1400s -> not flapping")
🗣️
Say out loud: "I only care about transitions, so I remember the last status per service. For each service I keep a list of change times; if the k-th change minus the first of any k consecutive changes is within the window, it is flapping. That is linear in the number of events. For a live stream I would keep a deque per service and drop timestamps older than the window."
5.6 — Top-N Slowest Endpoints with heapq

"Find the N slowest endpoints" is a daily log-analysis task. Sorting everything is O(n log n); heapq.nlargest(k, ...) does it in O(n log k), which matters when k is small and n is millions. When the data is a stream you cannot hold in memory, keep a min-heap of size k: the smallest of your current top k sits at heap[0], so a new value only matters if it beats that one.

nlargest, and a bounded heap for streams
import heapq from collections import defaultdict requests = [("/api/search", 120), ("/api/login", 45), ("/api/search", 480), ("/api/report", 900), ("/api/login", 55), ("/api/report", 1100), ("/health", 3), ("/api/search", 300), ("/api/upload", 700), ("/health", 2), ("/api/upload", 650), ("/api/report", 1000)] totals = defaultdict(lambda: [0, 0]) # endpoint -> [sum_ms, count] for endpoint, ms in requests: totals[endpoint][0] += ms totals[endpoint][1] += 1 averages = {ep: s / n for ep, (s, n) in totals.items()} top3 = heapq.nlargest(3, averages.items(), key=lambda kv: kv[1]) for ep, avg in top3: print(f"{ep:<12} avg {avg:7.1f} ms") # When the data is a stream you can't hold in memory: keep a min-heap of size k def top_k_streaming(stream, k): heap = [] # heap[0] is the smallest of the current top k for name, value in stream: if len(heap) < k: heapq.heappush(heap, (value, name)) elif value > heap[0][0]: heapq.heapreplace(heap, (value, name)) # pop smallest, push new, one O(log k) step return sorted(heap, reverse=True) print("streaming top 3:", top_k_streaming(averages.items(), 3))
🧠
Details worth saying: average latency hides tail pain — in real life you would rank by p95 or p99, and interviewers may ask you to. heapq is a min-heap, so a top-k uses the smallest element as the gatekeeper. Ties are broken by comparing the next tuple element, so put a stable key (like the endpoint name) second to keep output deterministic.
5.7 — Deployment Order: Topological Sort and Cycle Detection

Services depend on each other: the app needs the database, the database needs the network, and so on. Deploying in the wrong order fails; a dependency cycle makes it impossible. This is a topological sort. Kahn's algorithm tracks each node's in-degree (how many unmet dependencies it has), repeatedly deploys nodes with zero, and decrements their dependents. If you finish without visiting every node, the leftovers are blocked by a cycle. Using a heap for the ready set gives a deterministic, alphabetical tie-break — useful for reproducible plans.

Kahn's algorithm with cycle detection
import heapq from collections import defaultdict def deploy_order(deps): """deps maps service -> list of services that must be deployed first.""" indegree = {s: 0 for s in deps} dependents = defaultdict(list) for service, needs in deps.items(): for need in needs: indegree.setdefault(need, 0) # a leaf that only appears as a dependency indegree[service] += 1 dependents[need].append(service) ready = [s for s, d in indegree.items() if d == 0] heapq.heapify(ready) # heap => deterministic, alphabetical tie-break order = [] while ready: service = heapq.heappop(ready) order.append(service) for nxt in dependents[service]: indegree[nxt] -= 1 if indegree[nxt] == 0: heapq.heappush(ready, nxt) if len(order) != len(indegree): stuck = sorted(s for s, d in indegree.items() if d > 0) raise ValueError(f"cycle detected among: {stuck}") return order deps = {"web": ["api", "auth"], "api": ["db", "cache"], "auth": ["db"], "db": [], "cache": [], "worker": ["queue", "db"]} print("deploy order:", deploy_order(deps)) try: deploy_order({"a": ["b"], "b": ["c"], "c": ["a"], "d": []}) except ValueError as e: print("error:", e)
⚠️
Precision on the cycle report: the "stuck" set contains the cycle and everything downstream of it, because those services can never become ready either. If you must print the actual cycle, run a DFS with a "currently on the stack" marker on the stuck nodes. Complexity is O(V + E): each vertex and each edge is processed once.
5.8 — Python Gotchas Interviewers Love

Interviewers use small gotchas as a fast proxy for "has this person debugged real Python?". Every one of these has caused a production incident somewhere.

Mutable default arguments
def add_tag_bad(tag, tags=[]): # the [] is created ONCE, when def runs tags.append(tag) return tags print(add_tag_bad("a"), add_tag_bad("b")) # both prints show the SAME shared list def add_tag(tag, tags=None): if tags is None: tags = [] # a fresh list on every call tags.append(tag) return tags print(add_tag("a"), add_tag("b"))

A default value is evaluated once, when def executes — not on each call. A mutable default (list, dict, set) is therefore shared across every call and quietly accumulates state. The fix is the None sentinel.

Late binding, is vs ==, dict ordering, generators
hooks = [lambda: i for i in range(3)] print("late binding :", [h() for h in hooks]) # every lambda sees the final i hooks = [lambda i=i: i for i in range(3)] print("bound early :", [h() for h in hooks]) # default argument captures the value now a, b = [1, 2], [1, 2] print("== vs is :", a == b, a is b) # equal values, different objects x = None print("None check :", x is None) # use `is` for None/True/False singletons d1 = {"a": 1, "b": 2} d2 = {"b": 2, "a": 1} print("dict equality:", d1 == d2, "| key order differs:", list(d1) != list(d2)) lines = (line for line in ["a", "b", "c"]) print("first pass :", list(lines)) print("second pass :", list(lines), "<- a generator is exhausted after one pass")
🧠
The one-liners to remember: closures capture the variable, not its value at creation; == compares values while is compares identity (use is only for None); dicts preserve insertion order since Python 3.7 but compare equal regardless of it; a generator can be consumed only once, which is also why it is the right tool for a multi-gigabyte log — it holds one line in memory, not all of them.

Finally, the question every DevOps interview eventually reaches: threads, asyncio, or processes? The answer hinges on the GIL — in CPython only one thread runs Python bytecode at a time, but the lock is released while a thread waits on I/O.

WorkloadReach forWhy
Health-check 800 hostsasyncio (or a thread pool)Almost all time is spent waiting on sockets; the GIL is released while waiting
Blocking SDK calls (boto3, requests)ThreadPoolExecutorLibraries are not async; threads overlap their waiting

asyncio.gather: concurrent waiting
import asyncio async def check(name, delay): await asyncio.sleep(delay) # stands in for waiting on a network reply return name async def main(): # three "health checks" wait concurrently: total time ~ the slowest, not the sum return await asyncio.gather(check("web", 0.03), check("db", 0.01), check("cache", 0.02)) print("results in call order:", await main()) # in a real script: asyncio.run(main())
⚠️
In a real script you would call asyncio.run(main()). This browser console already runs an event loop, so bare top-level await is used here instead (the same convention as Chapter 7). And a blocking call inside a coroutine — a plain requests.get(), a time.sleep() — freezes the entire event loop; that is the most common asyncio bug.
DevOps 5 Summary
  • Process beats cleverness: clarify, work an example, state brute force, name the bottleneck, code small, test edge cases, state complexity.
  • Inject the clock (clock() callable or a fake) so time-based code — rate limiters, caches, alert windows — is deterministic to test.
  • Token bucket = sustained rate + bounded burst, refilled lazily; fixed windows leak 2x bursts at the boundary.
  • OrderedDict gives O(1) LRU via move_to_end / popitem(last=False); say which TTL policy you chose.
  • Deep merge needs explicit rules (recurse dicts, replace lists, None deletes) and a deepcopy.
  • Flapping = k state changes inside a window; top-N = heapq.nlargest / a size-k min-heap; deploy order = Kahn's algorithm, O(V + E), leftovers mean a cycle.
  • Gotchas: mutable defaults, late binding, is vs ==, exhausted generators; threads/asyncio for I/O, processes for CPU.

lateness if ts < watermark: late += 1 elif event_id in seen: dupes += 1 else: accepted.append(event_id) seen[event_id] = ts seen = {k: v for k, v in seen.items() if v >= watermark} return accepted, dupes, late accepted, dupes, late = process(arrivals) print(f'Accepted: {accepted}') print(f'Duplicates dropped: {dupes}') print(f'Late dropped: {late}') # ---------- Problem 3: retries under a time budget ---------- RETRYABLE = {429, 500, 502, 503, 504} def run_with_retries(statuses, base=1, factor=2, cap=8, budget=10): waited, attempts = 0, 0 while True: status = statuses[min(attempts, len(statuses) - 1)] attempts += 1 if 200 <= status < 300: return 'success', attempts, waited if status not in RETRYABLE: return 'failed_fast', attempts, waited delay = min(cap, base * factor ** (attempts - 1)) if waited + delay > budget: return 'budget_exhausted', attempts, waited waited += delay scenarios = { 'A': run_with_retries([503, 503, 200]), 'B': run_with_retries([500, 502, 503, 504, 200], budget=5), 'C': run_with_retries([404]), 'D': run_with_retries([503] * 10, budget=20), } for name, (outcome, attempts, waited) in scenarios.items(): print(f'{name} -> outcome={outcome} attempts={attempts} waited={waited}')

Complexity to state: Problem 1 is O(n·w) as written (O(n) with running sums); Problem 2 is O(n·s) as written where s is the retained-id count (O(n) with a heap or ordered expiry); Problem 3 is O(attempts). Notice the pruning in problem 2 — without it the dedupe set grows without bound on a real stream, a genuine production bug.

💼 DevOps Python Interview Prep

10 questions that DevOps, SRE and platform interviewers genuinely ask, each with what a strong answer contains and the common pitfall. Click a question to reveal the answer. Not graded — say each answer out loud before you open it.

A production server is slow. Walk me through how you investigate.▶
Narrow it first: slow for everyone or one endpoint, host or customer, and what changed (deploy, config, traffic, a dependency)? Then apply the USE method — Utilization, Saturation, Errors — to each resource. CPU: load average versus core count, run queue. Memory: swap activity, OOM kills in dmesg. Disk: iostat -x, await and %util. Network: retransmits, connection states with ss -s. Then the application: latency percentiles per endpoint, error rate, slow downstream calls, exhausted thread or connection pools, GC pauses. For a Python service, py-spy dump/top shows what it is doing on a live process without a restart, and a sync call inside an async handler blocks the whole event loop. Say your hypothesis, pick the cheapest test, and mitigate before root-causing (roll back, scale out). Pitfalls: running tools with no hypothesis, and restarting the service, which destroys the evidence.
Your script works when you run it by hand but fails under cron. Why?▶
Cron gives a script an almost empty world. PATH is minimal, there is no login shell so your profile never runs, the working directory is usually $HOME, no virtualenv is activated, no AWS_PROFILE or SSH agent variables exist, the shell is /bin/sh rather than bash, and stdout/stderr go to local mail or nowhere. Fixes: use absolute paths for the interpreter and the script (/opt/venv/bin/python /opt/app/job.py), set required environment variables explicitly, cd to a known directory, redirect output (>> /var/log/job.log 2>&1), log inside the script, and wrap it in flock so a slow run cannot overlap the next one. Reproduce it with env -i to see what cron sees. Remember that % is special in crontab lines. Pitfall: assuming it is a permissions problem before checking the environment.
What is the GIL, and how does it change how you parallelize DevOps scripts?▶
In CPython only one thread executes Python bytecode at a time. Threads still help for I/O-bound work because the lock is released while a thread blocks on a socket, file or sleep (and inside many C extensions, such as hashing large buffers). So: many blocking network calls — health checks, paginated API calls, boto3 — use a ThreadPoolExecutor or asyncio; CPU-bound work — compressing, hashing or parsing gigabytes — use ProcessPoolExecutor/multiprocessing, where each process has its own interpreter and GIL, or hand it to a native tool. asyncio needs async-aware libraries: one blocking call inside a coroutine freezes the entire event loop. Python 3.13 added an experimental free-threaded build, but it is not the default. Pitfall: saying "Python can't do threads" — it can, and for I/O they work fine.
What does idempotent mean, and why does automation care?▶
An operation is idempotent if running it once or many times leaves the system in the same final state. Automation cares because networks fail and retries are inevitable: if "create user" fails after the server acted but before the reply arrived, a blind retry either errors or creates a duplicate. Write scripts as desired state ("ensure this directory/user/bucket exists") rather than actions ("create"). Examples: mkdir -p, PUT to a fixed URL, terraform apply, an SQL INSERT ... ON CONFLICT DO NOTHING, and an idempotency key sent with a payment request. In Python: check-then-act with care about races (prefer atomic operations such as os.replace or Path.mkdir(exist_ok=True)), and make deletes tolerate "already gone". Pitfall: claiming an operation is idempotent because it "usually" works twice — name the state it converges to.
Name Python gotchas that have caused production bugs.▶
Mutable default arguments (def f(x, items=[]) shares one list across calls — use None). Late-binding closures (lambdas in a loop all see the final loop variable — bind with lambda i=i: i). is vs == (identity vs equality; use is for None only). Modifying a list while iterating it (skips elements — iterate a copy or build a new list). Exhausted generators (a second pass yields nothing). except Exception: pass swallowing real failures — catch specific errors and log. Naive datetimes compared with aware ones, and timezone-less timestamps in logs. subprocess with shell=True on untrusted input (command injection). Pitfall: listing them without the fix — each gotcha should come with the one-line remedy.
Compare rate-limiting algorithms. Which would you pick for an API gateway?▶
Fixed window counts requests per calendar window: trivial, but a client can burst 2x its limit across a boundary. Sliding window (log or weighted counter) is accurate at the cost of memory or approximation. Token bucket refills at a steady rate up to a capacity: it permits controlled bursts and is cheap (two numbers per client), which is why it is the usual choice for gateways and cloud APIs. Leaky bucket drains at a constant rate through a queue, smoothing traffic instead of allowing bursts. For a gateway I would choose token bucket, keyed per API key or client, with the state in Redis updated atomically (a Lua script) so all gateway nodes share one view. Also mention the response: HTTP 429 with a Retry-After header, and that clients should back off. Pitfall: forgetting that in-process counters do not work across multiple replicas.
How should a client retry failed requests?▶
Retry only errors that can succeed later: timeouts, connection resets, HTTP 429 and 5xx (502/503/504). Fail fast on 4xx like 400, 401 or 404 — retrying cannot fix them. Use exponential backoff with a cap and jitter: delays grow (1s, 2s, 4s, capped at, say, 30s) and each is randomized so a thousand clients that failed together do not all retry together (the thundering herd). Bound retries by a maximum attempt count and a total time budget, and honor Retry-After. Retries multiply load on a struggling dependency, so mature systems add a retry budget (retries may be at most ~10% of traffic) and circuit breakers. Only retry operations that are idempotent, or send an idempotency key. Pitfall: unbounded immediate retries, which turn a small outage into a big one.
How do you make a Python script safe to run from CI?▶
No interactive prompts — take everything from arguments or environment variables. Return meaningful exit codes (0 success, non-zero failure) so the pipeline can fail; do not swallow exceptions at top level. Log to stdout/stderr with timestamps and levels, never secrets. Read secrets from environment variables or a secret manager, and mask them. Pin dependencies (a lock file or hashes) so a build is reproducible. Put timeouts on every network call and subprocess. Offer a --dry-run mode for anything destructive, make the operation idempotent, and clean up temporary files in finally or with context managers. Keep the logic in importable functions with a thin if __name__ == "__main__": entry point so you can unit-test it. Pitfall: a script that prints "done" and exits 0 even after a step failed.
You must process a 20 GB log file on a small machine. How?▶
Stream it. Iterate the file object line by line (for line in f) or use a generator pipeline (read, then parse, then filter, then aggregate) so only one line is in memory at a time; never f.read() or readlines() the whole thing. Aggregate into a compact structure — a Counter or a running total — rather than storing rows. Compile regexes once outside the loop and prefer str methods when they suffice. If it is still too slow and CPU-bound, split the file into byte ranges and use a ProcessPoolExecutor, or use grep/awk for the first filtering pass. Remember a generator can be consumed once, so do not iterate it twice. Pitfall: building a list of all parsed records "for convenience" and running out of memory.
Your deployment plan has a circular dependency. How do you detect and handle it?▶
Model services as a directed graph (edge from dependency to dependent) and run a topological sort. With Kahn's algorithm, if you finish without visiting every node, the leftover nodes are blocked by a cycle — but that set also includes everything downstream of the cycle. To report the actual cycle, run a DFS with three colors (unvisited, on the current path, done): meeting a node that is on the current path means you found one, and the path segment is the cycle. Both approaches are O(V + E). In a pipeline I would fail the plan early with the cycle printed, because no deploy order exists. Real fixes are architectural: break the loop by removing a needless dependency, introducing a shared third component, or making one direction asynchronous (events or retries) so the services can start independently. Pitfall: "solving" it by deploying in an arbitrary order and hoping health checks eventually pass.
